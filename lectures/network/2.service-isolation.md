# 서비스 격리의 필요성

## 1. 격리가 없을 때 생기는 문제

여러 서비스가 한 서버에 함께 실행된다. 이때 각 서비스가 메모리를 얼마까지 사용할 수 있는지에 대한 제한이 없다.

한 서비스에서 메모리 누수가 발생하면 그 서비스가 서버의 남은 메모리를 계속 잠식한다.  
메모리가 고갈되면 운영체제는 OOM Killer를 통해 프로세스를 강제로 종료하여 메모리를 확보할 수 있다.

문제는 종료 대상을 선정하는 기준이다.

- 운영체제는 메모리 누수의 원인을 직접 분석하여 종료 대상을 선정하지 않는다.
- 메모리 사용량과 `oom_score_adj` 등의 정보를 반영한 OOM 점수를 기준으로 종료 대상을 선정한다.

따라서 누수가 발생한 서비스가 아니라, 아무 문제가 없는 다른 서비스가 종료될 수 있다.  
**장애가 발생한 지점과 원인이 있는 지점이 서로 달라진다.**

## 2. 가상 머신 - 격리는 되지만 비싸다.

가상 머신은 격리 문제를 해결했다.

- 서비스마다 독립된 메모리와 독립된 운영체제를 가진다. 
- 한 VM 내부의 장애가 다른 VM에 미치는 영향을 줄일 수 있다. 다만 호스트 자원 고갈과 같은 문제까지 완전히 차단하는 것은 아니다.
- 환경을 통째로 복제할 수 있어 "사람마다 다르게 실패하는" 문제도 해결된다.

그러나 비용이 크다. 가상 머신은 운영체제를 통째로 복제한다.  
커널까지 포함한 게스트 운영체제가 서비스마다 하나씩 붙는다.

문제점
- 용량: 이미지 하나가 수 기가바이트다.
- 기동 시간: 게스트 OS 부팅이 필요하므로 일반적으로 컨테이너보다 기동 시간이 길다.
- 서버 한 대에서 실행할 수 있는 VM 수가 자원에 따라 제한된다.

서비스가 실제로 쓰는 메모리보다 게스트 운영체제가 쓰는 메모리가 더 큰 경우가 흔하다.  
서비스를 돌리기 위해 자원을 쓰는 것이 아니라, **운영체제를 돌리기 위해 자원을 쓰는 셈**이다.

## 3. 중복된 커널

이 구조에는 중복이 있다.

- 서버의 운영체제는 리눅스다.
- 그 위에 올린 가상 머신의 운영체제도 리눅스다.
- 서비스를 격리하려면 호스트 커널 하나에 더해 **서비스 수만큼의 게스트 커널**이 추가로 올라간다.

각 VM의 게스트 커널은 독립적으로 동작한다.   
그러나 동일한 호스트 커널을 공유해도 되는 서비스를 격리하기 위해 매번 별도의 게스트 커널을 실행할 필요는 없다.

정말 필요한 것은 두 가지다.
1. 자원의 경계
2. 고정된 실행 환경

컨테이너 방식에서는 별도의 게스트 커널 없이 호스트 커널을 공유하여 프로세스를 격리할 수 있다.

그래서 **커널은 하나만 두고 프로세스 단위로만 격리하는 방식**이 나왔다. 이것이 **컨테이너**이다.

컨테이너가 쓰는 격리 기능은 새로 만들어진 것이 아니다. 리눅스가 이미 가지고 있던 기능이다.

- `namespace` - 격리
- `cgroup` - 제한

## 4. 가상 머신과 컨테이너 비교

### 가상 머신
- 하드웨어를 격리한다.
- 게스트 OS를 별도로 가진다.
- 게스트 OS를 포함하여 상대적으로 용량이 크다.
- 게스트 OS 부팅이 필요하여 상대적으로 기동 시간이 길다.
- 동일한 자원에서 실행 가능한 인스턴스 수가 상대적으로 적다.
- 격리 강도가 강하다.

### 컨테이너
- 프로세스를 격리한다.
- 호스트 커널을 공유한다.
- 게스트 OS를 포함하지 않아 상대적으로 용량이 작다.
- 별도 OS 부팅이 필요하지 않아 상대적으로 빠르게 기동한다.
- 동일한 자원에서 상대적으로 많은 인스턴스를 실행할 수 있다.
- 격리 강도가 상대적으로 약하다.
