# AWS 배포

## 1. AWS 인프라 구축

### 1) VPC 생성

AWS 내부에서 사용할 독립적인 가상 네트워크를 생성한다.

- 이름: `msa-vpc`
- 생성 옵션: VPC만
- IPv4 CIDR: `10.0.0.0/16`

```text
msa-vpc
└── 10.0.0.0/16
```

VPC 내부에 Public Subnet과 Private Subnet을 구성하여 애플리케이션 서버와 DB 서버의 네트워크 영역을 분리한다.

---

### 2) Subnet 생성

VPC의 IP 주소 범위를 역할에 따라 작은 네트워크로 나눈다.

#### Public Subnet

외부에서 접근해야 하는 애플리케이션 서버를 배치한다.

- 이름: `msa-public-a-subnet`
- IPv4 CIDR: `10.0.1.0/24`

#### Private Subnet

인터넷에 직접 노출할 필요가 없는 DB 서버를 배치한다.

- 이름: `msa-private-a-subnet`
- IPv4 CIDR: `10.0.11.0/24`

```text
msa-vpc
├── Public Subnet  : 10.0.1.0/24
└── Private Subnet : 10.0.11.0/24
```

---

### 3) Internet Gateway 생성

Internet Gateway(IGW)는 VPC와 인터넷을 연결한다.

- 이름: `msa-igw`
- 생성 후 `작업 → VPC에 연결`
- 연결 대상: `msa-vpc`

IGW를 VPC에 연결해야 Public Subnet의 Routing Table에서 인터넷 경로로 지정할 수 있다.

```text
Internet
   ↕
msa-igw
   ↕
msa-vpc
```

---

### 4) NAT Gateway 생성

NAT Gateway는 Private Subnet의 서버가 인터넷으로 요청을 보낼 수 있도록 한다.

예를 들어 Private Subnet의 DB 서버에서 다음 명령을 실행하려면 외부 인터넷 접근이 필요하다.

```bash
sudo apt update
```

이때 통신 흐름은 다음과 같다.

```text
msa-db
  ↓
NAT Gateway
  ↓
Internet Gateway
  ↓
Internet
```

NAT Gateway는 외부 사용자가 Private EC2에 직접 접근하기 위한 장치가 아니다.

- VPC: `msa-vpc`
- Public Subnet에 생성
- Elastic IP 할당

---

### 5) Security Group 생성

Security Group은 EC2에 대한 인바운드·아웃바운드 통신을 제어하는 가상 방화벽이다.

#### msa-app-sg

애플리케이션 EC2에서 사용한다.

인바운드 규칙:

- SSH `22`: 내 IP에서만 허용
- HTTP `80`: 외부 HTTP 요청 허용

#### msa-db-sg

DB EC2에서 사용한다.

인바운드 규칙:

- SSH `22`: `msa-app-sg`에서만 허용
- MySQL/Aurora `3306`: `msa-app-sg`에서만 허용

따라서 DB 서버에는 외부에서 직접 접근할 수 없으며 애플리케이션 EC2를 통해서만 접근한다.

```text
내 PC ──SSH──> msa-app ──SSH──> msa-db
                    │
                    └──3306──> MySQL
```

`msa-app`은 이 구조에서 Private Subnet의 DB 서버로 접근하기 위한 Bastion 역할도 수행한다.

---

### 6) EC2 생성

#### msa-app

애플리케이션을 실행하는 EC2이다.

- 인스턴스 타입: `t3.small`
- 키 페어: `.pem` 키 사용
- VPC: `msa-vpc`
- Subnet: `msa-public-a-subnet`
- Public IP 자동 할당: 활성화
- Security Group: `msa-app-sg`

Public Subnet에 위치하며 사용자의 요청을 받는 외부 진입점 역할을 한다.

```text
Internet
   ↓
IGW
   ↓
msa-app
```

> `.pem` 파일은 인증에 사용되는 Private Key이므로 GitHub에 커밋하지 않는다.

##### Elastic IP 연결

`msa-app`의 Public IP가 변경되지 않도록 Elastic IP를 생성하여 연결한다.

- Elastic IP를 생성한다.
- 생성한 Elastic IP에서 `탄력적 IP 주소 연결`을 선택한다.
- 리소스 유형에서 `인스턴스`를 선택한다.
- 인스턴스에서 `msa-app`을 선택한다.
- 연결할 Private IP를 선택하여 Elastic IP를 할당한다.

#### msa-db

MySQL을 실행하는 DB 서버이다.

- 인스턴스 타입: `t3.small`
- 키 페어: `.pem` 키 사용
- VPC: `msa-vpc`
- Subnet: `msa-private-a-subnet`
- Public IP 자동 할당: 비활성화
- Security Group: `msa-db-sg`

DB 서버는 인터넷에서 직접 접근할 필요가 없으므로 Public IP를 할당하지 않는다.

애플리케이션 서버에서 Private IP 또는 Private DNS를 이용하여 접근한다.

```text
msa-app
   ↓
VPC 내부 통신
   ↓
msa-db:3306
```

---

### 7) Routing Table 설정

Routing Table은 목적지에 따라 네트워크 패킷을 어디로 전달할지 결정한다.

#### Public Routing Table

- 이름: `msa-public-rt`
- VPC: `msa-vpc`
- Route 추가

```text
Destination : 0.0.0.0/0
Target      : Internet Gateway (msa-igw)
```

Subnet 연결:

```text
msa-public-a-subnet
```

이를 통해 Public Subnet의 EC2가 IGW를 통해 인터넷과 통신할 수 있다.

#### Private Routing Table

- 이름: `msa-private-rt`
- VPC: `msa-vpc`
- Route 추가

```text
Destination : 0.0.0.0/0
Target      : NAT Gateway (msa-nat)
```

Subnet 연결:

```text
msa-private-a-subnet
```

Private Subnet의 서버는 NAT Gateway를 통해 외부 인터넷으로 요청을 보낼 수 있다.

## 2. SSH와 SCP

### SSH

SSH(Secure Shell)는 원격 서버에 안전하게 접속하기 위한 프로토콜이다.

Windows PowerShell에서는 다음과 같이 사용할 수 있다.

```powershell
ssh -i "C:\Users\<USER>\Desktop\msa-key.pem" ubuntu@<APP_PUBLIC_IP>
```

- `-i`: SSH 인증에 사용할 Private Key 지정
- `ubuntu`: EC2의 사용자 계정
- `<APP_PUBLIC_IP>`: 접속할 EC2의 Public IP

---

### SCP

SCP(Secure Copy)는 SSH 연결을 이용하여 파일을 안전하게 전송한다.

로컬 PC의 `.pem` 파일을 `msa-app` EC2로 복사하는 경우:

```powershell
scp -i "C:\Users\<USER>\Desktop\msa-key.pem" `
  "C:\Users\<USER>\Desktop\msa-key.pem" `
  ubuntu@<APP_PUBLIC_IP>:~/
```

각 부분의 의미는 다음과 같다.

```text
-i <KEY>
→ 서버 접속 시 사용할 SSH 인증 키

C:\Users\<USER>\Desktop\msa-key.pem
→ 복사할 로컬 파일

ubuntu@<APP_PUBLIC_IP>:~/
→ 파일을 전송할 원격 서버와 경로
```

`msa-app`을 거쳐 `msa-db`에 SSH로 접속해야 하는 실습 구조에서 사용할 수 있다.

> `.pem` 파일을 서버로 복사한 경우 접근 권한을 제한한다.

```bash
chmod 400 msa-key.pem
```

## 3. Linux 기본 명령어

EC2에서는 Ubuntu Linux 환경을 사용한다.

### 경로 표기

- `/` : 최상위 루트 디렉터리
- `~` : 현재 사용자의 홈 디렉터리. Ubuntu EC2에서는 일반적으로 `/home/ubuntu`
- `.` : 현재 디렉터리
- `..` : 상위 디렉터리
- `.이름` : 숨김 파일. `.git`, `.env`, `.ssh` 등이 있으며 `ls -a`로 확인할 수 있다.

---

### 이동 및 조회

- `pwd` : 현재 위치 출력
- `ls` : 현재 디렉터리의 파일 목록 확인
- `ls -a` : 숨김 파일을 포함한 목록 확인
- `cd <DIRECTORY>` : 디렉터리 이동
- `cat <FILE>` : 파일 전체 내용 출력
- `grep <WORD> <FILE>` : 파일에서 특정 문자열이 포함된 줄 검색
- `tail -f <FILE>` : 파일 끝에 추가되는 내용을 실시간으로 확인
- `Ctrl + C` : `tail -f`와 같이 실행 중인 명령 종료
- `head -n 20 <FILE>` : 파일의 앞부분 20줄 확인
- `tail -n 20 <FILE>` : 파일의 뒷부분 20줄 확인

---

### 파일 및 디렉터리 관리

- `mkdir <DIRECTORY>` : 디렉터리 생성
- `touch <FILE>` : 빈 파일 생성
- `cp <SOURCE> <DESTINATION>` : 파일 복사
- `cp -r <SOURCE_DIRECTORY> <DESTINATION>` : 디렉터리와 하위 항목 전체 복사
- `mv <SOURCE> <DESTINATION>` : 파일 또는 디렉터리 이동 및 이름 변경
- `rm <FILE>` : 파일 삭제
- `rm -r <DIRECTORY>` : 디렉터리와 하위 항목 삭제
- `rm -rf <DIRECTORY>` : 확인 없이 디렉터리와 하위 항목 강제 삭제

Linux의 `rm`으로 삭제한 파일은 일반적인 휴지통으로 이동하지 않고 즉시 삭제되므로 주의한다.

특히 시스템 루트 디렉터리를 대상으로 `rm -rf`를 실행하면 시스템 전체 파일을 삭제할 수 있으므로 실행해서는 안 된다.

---

### 리다이렉션과 파이프

- `>` : 명령 실행 결과를 파일에 덮어쓴다.
- `>>` : 기존 파일 끝에 실행 결과를 추가한다.
- `|` : 앞 명령의 실행 결과를 다음 명령의 입력으로 전달한다.

```bash
echo hello > a.txt
echo world >> a.txt
docker ps | grep auth
```

여러 줄의 내용을 파일로 저장할 때 Heredoc을 사용할 수 있다.

```bash
cat <<'EOF' > example.txt
hello
world
EOF
```

---

### vi 기본 사용법

- `vi <FILE>` : 파일 열기
- `i` : 입력 모드로 전환
- `Esc` : 명령 모드로 복귀
- `/검색어` : 문자열 검색
- `:wq` : 저장 후 종료
- `:q!` : 저장하지 않고 종료
- `dd` : 현재 줄 삭제
- `u` : 이전 작업 되돌리기

---

### chmod

`chmod`는 파일 및 디렉터리의 접근 권한을 변경한다.

- `r = 4` : Read
- `w = 2` : Write
- `x = 1` : Execute
- `rw- = 6`
- `rwx = 7`

주요 사용 예시는 다음과 같다.

- `chmod 400 <FILE>` : 소유자만 읽기 가능
- `chmod 600 <FILE>` : 소유자만 읽기·쓰기 가능
- `chmod 644 <FILE>` : 모든 사용자가 읽을 수 있고 소유자만 수정 가능
- `chmod 700 <DIRECTORY>` : 소유자만 디렉터리 접근 가능
- `chmod 755 <FILE>` : 모든 사용자가 실행할 수 있고 소유자만 수정 가능
- `chmod +x <FILE>` : 실행 권한 추가

---

### 관리자 권한과 사용자

- `sudo <COMMAND>` : 관리자 권한으로 명령 실행
- `whoami` : 현재 로그인한 사용자 확인

---

### 패키지 관리

- `sudo apt update` : 설치 가능한 패키지 목록 갱신
- `sudo apt upgrade -y` : 설치된 패키지 업그레이드
- `sudo apt install -y <PACKAGE>` : 패키지 설치

예:

```bash
sudo apt install -y git
sudo apt install -y nginx
sudo apt install -y mysql-server
```

---

### systemctl

`systemctl`은 Linux의 서비스를 관리한다.

- `sudo systemctl status <SERVICE>` : 서비스 상태 확인
- `sudo systemctl start <SERVICE>` : 서비스 시작
- `sudo systemctl stop <SERVICE>` : 서비스 중지
- `sudo systemctl restart <SERVICE>` : 서비스 재시작
- `sudo systemctl enable <SERVICE>` : 서버 부팅 시 서비스 자동 시작 설정

`status` 결과가 `active (running)`이면 서비스가 정상적으로 실행 중인 상태이다.

---

### SSH 접속과 파일 전송

- `ssh -i <KEY> ubuntu@<IP>` : SSH를 이용해 서버에 접속
- `exit` : SSH 접속 종료
- `scp -i <KEY> <LOCAL_FILE> ubuntu@<IP>:~/` : 로컬 PC에서 서버로 파일 전송
- `scp -i <KEY> ubuntu@<IP>:~/<REMOTE_FILE> .` : 서버에서 로컬 PC로 파일 전송

## 4. DB 서버 설정

Private Subnet의 `msa-db` EC2에 MySQL을 설치한다.

### 패키지 업데이트

- `sudo apt update` : 설치 가능한 패키지 목록 갱신
- `sudo apt upgrade -y` : 설치된 패키지 업그레이드

두 명령을 연속으로 실행할 수도 있다.

```bash
sudo apt update && sudo apt upgrade -y
```

---

### Timezone 설정

```bash
sudo timedatectl set-timezone Asia/Seoul
```

---

### MySQL 설치 및 서비스 확인

- `sudo apt install -y mysql-server` : MySQL Server 설치
- `mysql --version` : 설치된 MySQL 버전 확인
- `sudo systemctl status mysql` : MySQL 서비스 상태 확인
- `sudo systemctl enable mysql` : 서버 부팅 시 MySQL 자동 시작 설정

---

### MySQL 네트워크 접속 설정

MySQL 설정 파일을 연다.

```bash
sudo vi /etc/mysql/mysql.conf.d/mysqld.cnf
```

기존 설정:

```text
bind-address = 127.0.0.1
```

다음과 같이 변경한다.

```text
bind-address = 0.0.0.0

character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci
```

`127.0.0.1`은 현재 DB 서버 내부에서만 MySQL에 접속할 수 있도록 제한한다.

`0.0.0.0`으로 변경하면 다른 네트워크 인터페이스에서도 MySQL 연결을 받을 수 있다. 실제 접근 가능 범위는 `msa-db-sg`의 Security Group과 MySQL 사용자 권한을 통해 제한한다.

설정 변경 후 MySQL을 재시작한다.

```bash
sudo systemctl restart mysql
```

---

### MySQL 접속

```bash
sudo mysql
```

---

### 애플리케이션용 사용자 생성

애플리케이션에서 사용할 별도의 DB 사용자를 생성한다.

```sql
CREATE USER 'app'@'10.0.1.%' IDENTIFIED BY '<DB_PASSWORD>';
```

`10.0.1.%`는 `10.0.1.x` 범위의 호스트에서 접속하는 `app` 사용자에게 접속을 허용한다.

애플리케이션에서 사용하는 Database에 권한을 부여한다.

```sql
GRANT ALL PRIVILEGES ON board_auth.* TO 'app'@'10.0.1.%';
GRANT ALL PRIVILEGES ON board_app.* TO 'app'@'10.0.1.%';

FLUSH PRIVILEGES;
```

`root` 계정을 애플리케이션에서 직접 사용하지 않고 별도의 `app` 사용자를 생성하여 사용한다.

> 실제 DB 비밀번호는 GitHub 문서나 소스 코드에 직접 기록하지 않는다.

## 5. 애플리케이션 서버 설정 및 배포

Public Subnet의 `msa-app` EC2에 Docker와 Git을 설치하고 애플리케이션을 배포한다.

### Docker 설치

패키지 목록과 설치된 패키지를 갱신하고 서버의 Timezone을 설정한다.

```bash
sudo apt update && sudo apt upgrade -y
sudo timedatectl set-timezone Asia/Seoul
```

Docker를 설치한다.

```bash
curl -fsSL https://get.docker.com | sudo sh
```

현재 사용자인 `ubuntu`를 `docker` 그룹에 추가하면 이후 `sudo` 없이 Docker 명령을 실행할 수 있다.

```bash
sudo usermod -aG docker ubuntu
```

그룹 변경 사항은 다시 로그인해야 적용되므로 SSH 연결을 종료하고 재접속한다.

```bash
exit
```

재접속 후 Docker와 Docker Compose 설치 여부를 확인한다.

```bash
docker version
docker compose version
```

---

### Git 설치

Git을 설치한다.

```bash
sudo apt install -y git
```

---

### GitHub Deploy Key 설정

EC2에서 GitHub Repository의 최신 코드를 가져오기 위해 Deploy Key를 사용한다.

다음 명령으로 SSH Key를 생성한다.

```bash
ssh-keygen -t ed25519 -C "msa-app-deploy" -f ~/.ssh/github_deploy -N ""
```

각 옵션의 의미는 다음과 같다.

- `ssh-keygen`: SSH Key를 생성한다.
- `-t ed25519`: Key 생성 알고리즘으로 Ed25519를 사용한다.
- `-C "msa-app-deploy"`: 공개키를 구분하기 위한 설명을 추가한다.
- `-f ~/.ssh/github_deploy`: Key를 저장할 경로를 지정한다.
- `-N ""`: Key의 Passphrase를 설정하지 않는다.

생성되는 파일은 다음과 같다.

```text
~/.ssh/github_deploy
→ Private Key

~/.ssh/github_deploy.pub
→ Public Key
```

Private Key는 EC2 서버에 보관하고 외부에 공개하지 않는다.

Public Key의 내용을 확인한다.

```bash
cat ~/.ssh/github_deploy.pub
```

출력된 Public Key를 GitHub Repository의 Deploy Key로 등록한다.

인증 흐름은 다음과 같다.

```text
GitHub Repository
       ↑
Public Key 등록
       ↑
서명 검증
       ↑
msa-app EC2
       │
Private Key로 인증
```

1. GitHub에 Public Key를 Deploy Key로 등록한다.
2. EC2가 GitHub에 연결할 때 Private Key를 사용한다.
3. GitHub가 등록된 Public Key를 이용하여 인증한다.

### SSH Config 설정

GitHub에 연결할 때 생성한 Deploy Key를 사용하도록 SSH 설정을 추가한다.

```bash
cat <<'EOF' >> ~/.ssh/config
Host github.com
    IdentityFile ~/.ssh/github_deploy
    IdentitiesOnly yes
EOF

chmod 600 ~/.ssh/config
```

각 설정의 의미는 다음과 같다.

- `Host github.com`: `github.com`에 연결할 때 해당 설정을 적용한다.
- `IdentityFile`: 사용할 Private Key의 경로를 지정한다.
- `IdentitiesOnly yes`: 지정한 Key만 인증에 사용한다.

GitHub SSH 연결을 확인한다.

```bash
ssh -T git@github.com
```

### AWS Docker Compose 설정

AWS에서는 여러 MSA 서비스를 Docker Compose로 함께 실행한다.

AWS 배포용 Compose 파일은 다음 위치에서 관리한다.

```text
lectures/docker/docker-compose.aws.yml
```

설정은 다음과 같다.

```yaml
name: msa-aws

networks:
  msa-network:
    name: msa-network

x-common: &common
  restart: unless-stopped
  networks: [msa-network]

services:
  config-service:
    <<: *common
    build: ../../practice/msa/config-service
    image: config-service:latest
    container_name: config-service
    volumes:
      - ../../practice/msa/config-repo:/config-repo:ro
    environment:
      CONFIG_REPO_PATH: file:/config-repo
      JAVA_OPTS: ${JAVA_OPTS}
    # ports 없음 → 호스트에도 공개하지 않음. 같은 네트워크의 컨테이너만 접근
    healthcheck:
      test: ["CMD", "bash", "-c", "echo > /dev/tcp/127.0.0.1/8888"]
      interval: 5s
      timeout: 3s
      retries: 40

  auth-service:
    <<: *common
    build: ../../practice/msa/auth-service
    image: auth-service:latest
    container_name: auth-service
    depends_on:
      config-service: { condition: service_healthy }
    environment:
      CONFIG_SERVICE_URL: http://config-service:8888

      AUTH_DB_URL: "jdbc:mysql://${DB_HOST}:3306/board_auth?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8"
      AUTH_DB_USERNAME: ${DB_USER}
      AUTH_DB_PASSWORD: ${DB_PASSWORD}

      KAKAO_CLIENT_ID: ${KAKAO_CLIENT_ID}
      KAKAO_CLIENT_SECRET: ${KAKAO_CLIENT_SECRET}
      JWT_SECRET_KEY: ${JWT_SECRET_KEY}
      SERVICE_TOKEN: ${SERVICE_TOKEN}

      BOARD_SERVICE_URL: http://board-service:8081
      # OAuth 성공 후 브라우저를 돌려보낼 주소 (application.yaml의 web-service.url)
      WEB_SERVICE_URL: http://${PUBLIC_HOST}
      JAVA_OPTS: ${JAVA_OPTS}

  board-service:
    <<: *common
    build: ../../practice/msa/board-service
    image: board-service:latest
    container_name: board-service
    depends_on:
      config-service: { condition: service_healthy }
    environment:
      CONFIG_SERVICE_URL: http://config-service:8888

      BOARD_DB_URL: "jdbc:mysql://${DB_HOST}:3306/board_app?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8"
      BOARD_DB_USERNAME: ${DB_USER}
      BOARD_DB_PASSWORD: ${DB_PASSWORD}

      JWT_SECRET_KEY: ${JWT_SECRET_KEY}
      SERVICE_TOKEN: ${SERVICE_TOKEN}

      AUTH_SERVICE_URL: http://auth-service:8082
      JAVA_OPTS: ${JAVA_OPTS}
    volumes:
      - board-uploads:/app/uploads

  edge-service:
    <<: *common
    build: ../../practice/msa/edge-service
    image: edge-service:latest
    container_name: edge-service
    depends_on:
      config-service: { condition: service_healthy }
    environment:
      AUTH_SERVICE_URL: http://auth-service:8082
      BOARD_SERVICE_URL: http://board-service:8081
      SPRING_CLOUD_GATEWAY_SERVER_WEBMVC_TRUSTED_PROXIES: ".*"
      JAVA_OPTS: ${JAVA_OPTS}
    ports:
      - "127.0.0.1:8000:8000"   # 호스트의 Nginx만 접근 가능

  web-service:
    <<: *common
    build: ../../practice/msa/web-service
    image: web-service:latest
    container_name: web-service
    environment:
      EDGE_SERVICE_URL: http://edge-service:8000
      JAVA_OPTS: ${JAVA_OPTS}
    ports:
      - "127.0.0.1:8080:8080"

volumes:
  board-uploads: {}
```

모든 서비스는 동일한 Docker Network인 `msa-network`를 사용한다.

```text
msa-network
├── config-service
├── auth-service
├── board-service
├── edge-service
└── web-service
```

서비스 간 통신에서는 EC2의 IP나 `localhost` 대신 Docker Compose의 Service Name을 Hostname으로 사용한다.

```text
http://config-service:8888
http://auth-service:8082
http://board-service:8081
http://edge-service:8000
```

`config-service`, `auth-service`, `board-service`는 Host Port를 공개하지 않으므로 같은 Docker Network에 속한 Container에서만 접근할 수 있다.

`edge-service`와 `web-service`는 Host의 Loopback Interface인 `127.0.0.1`에만 Port를 Binding한다.

```text
127.0.0.1:8000 → edge-service:8000
127.0.0.1:8080 → web-service:8080
```

따라서 외부에서는 Container Port에 직접 접근할 수 없으며 Nginx를 통해 요청을 전달한다.

```text
외부 요청
   ↓
Nginx
   ├── 127.0.0.1:8000 → edge-service
   └── 127.0.0.1:8080 → web-service
```

`depends_on`과 `healthcheck`를 이용하여 `config-service`가 정상적으로 실행된 이후 `auth-service`, `board-service`, `edge-service`가 실행되도록 구성한다.

`board-uploads` Volume은 `board-service`의 업로드 파일을 Container가 교체되어도 유지하기 위해 사용한다.

DB 접속 정보, OAuth 정보, JWT Secret 등 환경별로 달라지는 값은 `.env`를 통해 주입한다.

### 환경 변수 설정

Docker Compose에서 사용할 서버별 환경 변수는 `.env` 파일로 관리한다.

`docker-compose.aws.yml`이 위치한 디렉터리에서 `.env`를 생성한다.

```bash
cat <<'EOF' > .env
PUBLIC_HOST=<Elastic IP>
DB_HOST=<DB_PRIVATE_IP>
DB_USER=app
DB_PASSWORD=<DB_PASSWORD>

KAKAO_CLIENT_ID=<KAKAO_CLIENT_ID>
KAKAO_CLIENT_SECRET=<KAKAO_CLIENT_SECRET>

JWT_SECRET_KEY=<JWT_SECRET_KEY>
SERVICE_TOKEN=<SERVICE_TOKEN>

JAVA_OPTS=-Xms64m -Xmx256m -XX:MaxMetaspaceSize=160m -Xss512k -XX:+UseSerialGC -XX:TieredStopAtLevel=1
EOF
```

환경 변수의 주요 역할은 다음과 같다.

- `PUBLIC_HOST`: 외부에서 접근하는 `msa-app`의 Elastic IP
- `DB_HOST`: Private Subnet에 위치한 `msa-db`의 Private IP
- `DB_USER`, `DB_PASSWORD`: 애플리케이션용 MySQL 계정
- `KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET`: Kakao OAuth 인증 정보
- `JWT_SECRET_KEY`: JWT 생성 및 검증에 사용하는 Secret Key
- `SERVICE_TOKEN`: 서비스 간 인증에 사용하는 Token
- `JAVA_OPTS`: 각 JVM Container의 메모리 사용량을 제한하는 옵션

`.env`에는 인증 정보가 포함되므로 파일 권한을 제한한다.

```bash
chmod 600 .env
```

> `.env` 파일과 Secret 값은 GitHub에 커밋하지 않는다.

### 배포 스크립트

반복되는 배포 작업은 `deploy.sh`로 자동화한다.

배포 과정은 다음과 같다.

```text
GitHub 최신 코드 가져오기
        ↓
Docker Image Build
        ↓
Container 교체
        ↓
사용하지 않는 Image 정리
```

배포 스크립트의 주요 구조는 다음과 같다.

```bash
#!/bin/bash

set -e
cd "$(dirname "$0")"

COMPOSE="docker compose -f docker-compose.aws.yml"
SERVICES="${*:-config-service auth-service board-service edge-service web-service}"

echo "[1/4] 최신 코드 받기"
git pull --ff-only

echo "[2/4] 이미지 빌드 (메모리 때문에 하나씩)"
for s in $SERVICES; do
  echo "  - $s"
  $COMPOSE build "$s"
done

echo "[3/4] 컨테이너 교체"
$COMPOSE up -d $SERVICES

echo "[4/4] 이전 이미지 정리"
docker image prune -f

echo
$COMPOSE ps
```

`set -e`는 명령 실행 중 오류가 발생하면 스크립트를 즉시 종료한다.

```bash
git pull --ff-only
```

`--ff-only`를 사용하면 EC2의 Git History와 원격 Repository의 History가 갈라진 경우 임의로 Merge하지 않고 배포를 중단한다.

EC2의 메모리 사용량을 고려하여 여러 Service Image를 동시에 Build하지 않고 하나씩 순차적으로 Build한다.

```bash
for s in $SERVICES; do
  $COMPOSE build "$s"
done
```

스크립트에 실행 권한을 추가한다.

```bash
chmod +x deploy.sh
```

전체 서비스를 배포한다.

```bash
./deploy.sh
```

특정 서비스만 변경된 경우 해당 서비스만 지정하여 배포할 수 있다.

```bash
./deploy.sh auth-service
./deploy.sh edge-service
```

## 6. Nginx 설정

Nginx를 `msa-app` EC2의 Reverse Proxy로 사용한다.

외부 사용자는 각 Docker Container에 직접 접근하지 않고 HTTP `80` Port의 Nginx를 통해 애플리케이션에 접근한다.

```text
사용자
  ↓
HTTP :80
  ↓
Nginx
  ↓
Docker Container
```

### Nginx 설치

Nginx를 설치한다.

```bash
sudo apt install -y nginx
```

Nginx가 정상적으로 실행되는지 확인한다.

```bash
curl -I http://127.0.0.1
```

---

### Nginx 설정 파일 구조

Ubuntu에서 Nginx의 주요 설정 파일 구조는 다음과 같다.

```text
/etc/nginx/
├── nginx.conf
├── sites-available/
│   ├── default
│   └── msa
└── sites-enabled/
    └── default -> ../sites-available/default
```

- `nginx.conf`: Nginx의 기본 설정 파일
- `sites-available`: 사이트별 설정 파일을 보관한다.
- `sites-enabled`: 실제로 활성화할 사이트의 Symbolic Link를 둔다.

`sites-available`에 설정 파일을 생성하는 것만으로는 적용되지 않는다.

---

### Reverse Proxy 설정

다음 파일을 생성한다.

```bash
sudo vi /etc/nginx/sites-available/msa
```

설정은 다음과 같다.

```nginx
server {
    listen 80 default_server;
    server_name _;

    # 게시글 첨부 최대 10MB
    client_max_body_size 10M;

    # 원래 요청의 Host, Client IP, Protocol 정보를 뒷단 서비스에 전달
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host  $host;

    # Kakao OAuth 로그인 시작 및 Callback
    location /oauth2/ {
        proxy_pass http://127.0.0.1:8000;
    }

    location /login/oauth2/ {
        proxy_pass http://127.0.0.1:8000;
    }

    # 화면 및 일반 API 요청
    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

`client_max_body_size 10M`은 Nginx가 허용하는 요청 Body의 최대 크기를 설정한다.

Nginx의 기본 제한보다 큰 첨부 파일 요청을 처리하기 위해 애플리케이션의 Multipart 제한과 맞춘다.

`proxy_set_header`를 통해 Reverse Proxy 뒤의 서비스가 브라우저의 원래 요청 정보를 확인할 수 있도록 한다.

- `Host`: 사용자가 요청한 Host
- `X-Real-IP`: 실제 Client IP
- `X-Forwarded-For`: Proxy를 거친 Client IP 정보
- `X-Forwarded-Proto`: 원래 요청 Protocol
- `X-Forwarded-Host`: 원래 요청 Host

요청 경로에 따른 전달 구조는 다음과 같다.

```text
/oauth2/**
/login/oauth2/**
        ↓
edge-service:8000
        ↓
auth-service

그 외 요청
        ↓
web-service:8080
```

---

### Nginx 설정 활성화

생성한 `msa` 설정을 `sites-enabled`에 Symbolic Link로 연결한다.

```bash
sudo ln -s /etc/nginx/sites-available/msa /etc/nginx/sites-enabled/msa
```

설치 시 기본으로 활성화되어 있는 `default` 설정은 제거한다.

```bash
sudo rm /etc/nginx/sites-enabled/default
```

Nginx는 `sites-enabled`에 있는 설정을 실제로 사용하므로 `msa` 설정을 연결하고 기본 설정을 제거해야 한다.

설정 문법을 검사한다.

```bash
sudo nginx -t
```

정상적인 경우 설정을 다시 불러온다.

```bash
sudo systemctl reload nginx
```

---

### 요청 흐름

Nginx를 적용한 전체 요청 흐름은 다음과 같다.

```text
브라우저 ──:80──> Nginx
                  │
                  ├── /oauth2/**
                  │   /login/oauth2/**
                  │        ↓
                  │   edge-service:8000
                  │        ↓
                  │   auth-service
                  │
                  └── 그 외 요청
                           ↓
                     web-service:8080
                           ↓
                     edge-service:8000
                           ↓
                     auth / board
```

OAuth 요청은 `web-service`를 거치지 않고 Nginx에서 바로 `edge-service`로 전달한다.

일반 화면 및 API 요청은 먼저 `web-service`로 전달되고, 필요한 경우 `web-service`가 `edge-service`를 통해 각 Backend Service로 요청을 전달한다.

### Kakao Redirect URI 설정

Kakao OAuth의 Redirect URI에는 Docker 내부 주소가 아니라 사용자가 실제로 접근하는 외부 주소를 등록한다.

```text

```

Kakao Developers에서 해당 URI를 Redirect URI로 등록한다.

## 7. 배포 구조

전체적인 요청 흐름은 다음과 같다.

```text
사용자
  ↓
Internet
  ↓
Internet Gateway
  ↓
Public Subnet
  ↓
msa-app EC2
  ↓
Nginx
  ↓
Docker Container
  ├── web-service
  ├── edge-service
  ├── auth-service
  └── board-service
        ↓
VPC 내부 통신
        ↓
Private Subnet
        ↓
msa-db EC2
        ↓
MySQL
```

일반적인 서비스 요청에서 NAT Gateway를 거치지는 않는다.

NAT Gateway는 Private Subnet의 DB 서버가 인터넷으로 요청을 보내야 할 때 사용한다.

```text
msa-db
  ↓
NAT Gateway
  ↓
Internet Gateway
  ↓
Internet
```

관리 목적으로 DB 서버에 SSH 접속할 때는 Public Subnet의 `msa-app`을 거친다.

```text
내 PC
  ↓ SSH
msa-app
  ↓ SSH
msa-db
```

이때 `msa-app`은 Bastion 역할을 한다.

## 8. AWS 리소스 삭제

실습 종료 후 불필요한 비용 발생을 막기 위해 생성한 AWS 리소스를 정리한다.

주요 확인 대상:

- EC2
- NAT Gateway
- Elastic IP(EIP)
- Security Group
- Key Pair
- VPC
  - Subnet
  - Internet Gateway
  - Routing Table

특히 EC2, NAT Gateway, Elastic IP 등은 비용이 발생할 수 있으므로 실습 종료 후 사용 여부를 확인한다.

AWS 계정에서 기본으로 제공되는 Default VPC 관련 리소스와 직접 생성한 실습 리소스를 구분하여 삭제한다.
