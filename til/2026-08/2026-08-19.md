## 오늘 배운 내용

오늘은 사용자·관리자 프론트를 실제 백엔드 API와 연결한 상태에서 전체 흐름을 테스트하고, 화면과 현재 API가 맞지 않는 부분을 확인해 필요한 변경을 요청했다.

Toss 결제창에서 사용자가 직접 결제를 취소한 경우에도 서버에는 `PENDING_PAYMENT` 구매가 남을 수 있으므로 결제 취소와 Purchase 취소를 별도로 처리해야 했다.   
명시적인 사용자 취소에서는 구매 취소 API를 즉시 호출하고,   
브라우저 종료나 페이지 이탈처럼 취소 요청 자체가 전달되지 않은 경우에는 timeout Scheduler가 처리하도록 역할을 구분했다.

상품 이미지와 관리자 상품 화면도 실제 API 데이터에 맞춰 연결했다.   
이 과정에서 사용자용 상품 조회와 관리자용 상품 조회의 목적이 다르며,   
관리자 화면에서는 비활성 상품까지 조회·수정할 수 있는 별도의 API가 필요하다는 점을 프론트 테스트를 통해 확인했다.

k6 부하 테스트에서는 TPS와 p95 같은 성능 지표뿐 아니라 실제 성공 Purchase 수,   
최종 Redis 재고와 초과 판매 여부 등 데이터 정합성을 함께 확인해야 한다는 점을 정리했다.

Redis 재설계 PR을 리뷰하면서 Warm-up, Key 유실, 재고 복구와 Purchase timeout 정책을 확인했다.   
이후 로컬에서 실제 Redis 연결과 Warm-up, 판매 상태 전환, 구매 시 재고 차감까지 직접 검증하면서   
RDB 상태만이 아니라 Redis의 판매 정보와 재고 Key가 실제 구매 흐름의 기준이 된다는 점을 확인했다.

## 실습 및 과제

> 결제 취소 및 구매내역 보완

구매 취소 버튼의 스타일을 정리하고, Toss 결제창에서 사용자가 직접 결제를 취소했을 때 구매 취소 API도 함께 호출하도록 연결했다.

기존에는 결제만 취소되고 서버의 Purchase가 `PENDING_PAYMENT` 상태로 남아 다시 구매할 때 중복 구매로 판단될 수 있었다.   
이를 해결하기 위해 명시적인 결제 취소 시 `POST /api/purchases/{purchaseId}/cancel`을 호출해 Purchase와 재고가 즉시 정리되도록 했다.

결제 전에 취소된 구매는 `CANCELED` 상태이면서 `purchasedAt`이 없기 때문에 실제 구매 완료 이력에서는 제외했다.   
반대로 결제 완료 후 취소된 구매는 `purchasedAt`이 존재하므로 취소된 구매 이력으로 유지했다.

> 상품 이미지 프론트 연동

런타임에 생성되는 업로드 이미지 디렉터리를 Git 추적 대상에서 제외했다.

프론트에서 사용할 상품 이미지를 추가하고 API의 `imageUrl`을 판매 목록, 판매 상세, 결제 화면과 관리자 상품 화면에 연결했다.

Mock 이미지가 아니라 실제 상품 데이터가 가진 이미지 경로를 사용하도록 변경해 상품 조회와 화면 표시가 같은 데이터를 기준으로 동작하도록 맞췄다.

> 관리자 상품 및 판매 화면 보완

관리자 상품 수정 기능을 현재 백엔드 API에 맞춰 다시 연결했다.

프론트 테스트 과정에서 일반 사용자용 상품 상세 API로는 `INACTIVE` 상품을 조회할 수 없어 관리자 화면에서 수정할 수 없는 문제를 확인했다.   
관리자에서는 비활성 상품도 조회·수정할 수 있어야 하므로 관리자 전용 상세 조회 API가 필요하다는 점을 담당자에게 전달했다.

이후 반영된 관리자 상세 조회 API에 맞춰 프론트를 수정하고, 관리자 상품 목록도 전체 상품을 조회하는 관리자용 API를 사용하도록 연결했다.

판매 상태는 `READY`, `ON_SALE`, `SOLD_OUT`, `CLOSED`를 화면에서 쉽게 구분할 수 있도록 표시 색상과 문구를 보완했다.

> k6 부하 테스트 학습

Redis 기반 선착순 구매를 테스트하기 전에 k6에서 어떤 지표와 시나리오를 확인해야 하는지 공부했다.

동시 사용자 수를 증가시키면서 TPS, p95 응답시간과 실패율을 확인하고, 성능뿐 아니라 최종 Redis 재고가 음수가 되지 않는지,   
초기 재고보다 많은 Purchase가 생성되지 않는지, 사용자별 구매 제한이 정상적으로 지켜지는지도 함께 확인해야 한다.

Redis 적용 전후를 같은 조건으로 비교해야 실제 성능 개선의 근거로 사용할 수 있다는 점도 정리했다.

> Redis 기반 재설계 PR 코드리뷰 및 동작 검증

Redis Warm-up, Key 유실 시 처리와 Purchase timeout 구조를 중심으로 재설계 PR을 검토했다.

수동 Warm-up이 Redis Key 유실 후 재고를 복구하는 용도인지,   
`ON_SALE` 상태에서 잘못 호출하면 이미 차감된 Redis 재고를 RDB의 `remainingStock`으로 덮어쓸 가능성이 없는지 확인 요청했다.

`stock_restore.lua`에서도 stock Key가 없는 상태에서 `INCRBY`가 실행되면   
복구 수량만 가진 새로운 Key가 만들어질 수 있어 현재 Key 유실 정책과 맞는지 검토했다.

Purchase timeout 처리에서는 여러 대상을 하나의 트랜잭션으로 처리할 경우 Redis 복구 실패 시 Payment와 Purchase 상태가 어긋날 가능성이 있는지 확인하고,   
한 건 단위 트랜잭션 처리가 필요한지 리뷰 의견을 전달했다.

반영된 코드에서는 Warm-up 대상 상태 제한, stock Key 존재 여부 확인과 timeout 대상별 처리 구조가 의도한 정책에 맞는지 다시 확인했다.

이후 실제 구매 과정에서 화면에는 `ON_SALE`로 보이지만 구매 API에서는 판매 상태가 아니라는 오류가 발생해 Redis 연결을 추적했다.

Spring 로그에서는 Warm-up 성공이 출력됐지만 Docker Redis에는 Key가 없어 확인한 결과 Windows Redis와 Docker Redis가 동시에 실행되고 있었고,   
Spring Boot와 직접 확인하던 Redis가 서로 달랐다.

로컬 Redis 프로세스를 종료하고 Docker Redis로 연결을 맞춘 뒤 `sale:{id}:stock`, `sale:{id}:info` Key 생성과 `READY → ON_SALE` 전환을 확인했다.

실제 프론트에서 구매를 진행해 Redis 재고가 `45 → 44`로 감소하는 것까지 확인하면서   
`Warm-up → ON_SALE → Lua Script 검증 → Redis 재고 차감` 흐름을 직접 검증했다.

> 초기 데이터 구성

프론트 전체 화면 확인과 이후 테스트에 사용할 상품·판매 초기 데이터를 구성했다.

기존 자동 실행 방식 대신 필요할 때 실행할 수 있는 `init-data.sql`을 사용하고, 특정 날짜에 종속되지 않도록 `NOW()`와 `INTERVAL`을 이용해 판매 시간을 설정했다.

판매 중으로 사용할 데이터도 SQL에서 바로 `ON_SALE` 상태로 만들지 않고 `READY` 상태에서 실제 Warm-up과 Scheduler를 거쳐 `ON_SALE`로 변경되도록 구성했다.

이를 통해 RDB에만 판매 중 상태가 존재하고 Redis에는 판매 Key가 없는 비정상적인 초기 상태를 방지했다.

Purchase와 Payment는 SQL에서 임의로 생성하지 않고 실제 구매·결제 흐름을 통해 생성하도록 분리했다.

## 헷갈렸던 점

Toss 결제창에서 사용자가 취소하면 Purchase도 자동으로 취소되는지 헷갈렸다.  
결제 UI의 취소와 서버의 Purchase 상태 변경은 별개의 동작이므로 프론트에서 구매 취소 API까지 호출해야 즉시 상태와 재고를 정리할 수 있다.

결제 전에 취소된 Purchase도 구매내역에 남겨야 하는지 고민했다.  
실제 결제까지 완료된 적이 없는 `CANCELED` Purchase는 `purchasedAt`이 없기 때문에 일반적인 구매 이력에서는 제외하고,   
결제 완료 후 취소된 구매만 기존 이력으로 유지하는 방향으로 구분했다.

관리자 화면에서도 사용자용 상품 API를 그대로 사용하면 되는지 헷갈렸다.  
비활성 상품은 사용자에게 노출하면 안 되지만 관리자는 조회·수정할 수 있어야 하므로 프론트 테스트 중 관리자 전용 조회 API가 필요하다는 점을 확인하고 수정 요청했다.

Redis Warm-up을 판매 중 Key 유실 복구에도 사용할 수 있는지 확인했다.  
판매 중에는 Redis에서 이미 실시간 재고가 변경됐을 수 있으므로 RDB 값으로 다시 Warm-up하면 실제 재고를 덮어쓸 수 있다.

Spring에서는 Warm-up 성공 로그가 나오는데 Docker Redis에는 Key가 보이지 않아 Redis 저장 문제라고 생각했다.  
실제 원인은 로컬 Redis와 Docker Redis가 동시에 실행되어 Spring Boot와 직접 확인하는 Redis가 서로 달랐던 것이었다.

k6 테스트에서도 TPS와 응답시간만 보면 되는지 고민했다.  
선착순 구매에서는 성능뿐 아니라 최종 재고와 실제 성공 Purchase 수가 일치하는지 등 데이터 정합성을 함께 확인해야 한다.

## 오늘 느낀 점

오늘은 프론트 API 연동을 실제로 끝까지 테스트하면서 화면을 구현하는 것뿐 아니라 현재 백엔드 API가 사용자와 관리자 흐름에 맞는지 확인하는 과정도 중요하다는 점을 느꼈다.

특히 관리자 상품처럼 사용자 화면과 조회 범위가 다른 기능은 실제 프론트에서 사용해봐야 필요한 API의 경계가 더 명확하게 드러났다.

Redis 기반 구조에서는 RDB 상태만 보고 판매가 정상이라고 판단할 수 없고 Warm-up, Redis Key와 실제 재고까지 함께 확인해야 한다는 점도 실제 구매 테스트를 통해 이해했다.

Redis 연결 문제 역시 코드가 아니라 서로 다른 Redis 실행 환경을 보고 있었던 것이 원인이었다.   
로그뿐 아니라 실제 연결 대상과 Key, 재고 변화를 확인하면서 문제를 좁혀가는 과정이 중요했다.

또한 오늘은 백엔드 코드를 직접 작성하기보다 프론트 테스트와 Redis PR 코드리뷰 과정에서 문제를 발견하고,   
필요한 변경을 담당자에게 요청한 뒤 반영된 결과를 다시 검증하는 방식으로 협업했다.
