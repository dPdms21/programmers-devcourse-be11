## 오늘 배운 내용

오늘은 프로그래머스 데브코스 BE11의 2차 팀 프로젝트를 마무리하며 Gudit 프로젝트를 발표하고 다른 팀의 발표도 함께 들었다.

자유 주제로 진행됐지만 여러 팀이 동시성·성능·정합성 문제를 공통적으로 다뤘고,   
같은 기술적 문제를 다루더라도 각 팀이 집중한 기술의 깊이와 핵심 구현 목표는 달랐다.

Gudit에서는 선착순 구매의 초과 판매와 중복 구매, Redis·RDB·외부 결제 시스템 사이의 정합성 문제를 중심으로 해결 과정과 테스트 결과를 발표했다.

회고에서는 현재 보상 처리만으로 장애 상황의 정합성을 완전히 보장하기 어렵다는 한계를 확인하고,   
3차에서 Message Queue, Transactional Outbox, Inbox와 재처리·모니터링 구조로 확장할 방향을 정리했다.

발표 이후에는 관리자 권한을 일반 사용자와 분리하고, 2차 프로젝트의 핵심 구현과 테스트 결과, 한계와 개선 방향을 README에 정리했다.

## 실습 및 과제

> 2차 팀 프로젝트 발표

Gudit 2차 팀 프로젝트의 최종 발표를 진행했다.

한정 수량 상품의 선착순 구매를 주제로 재고 100개에 많은 요청이 동시에 들어올 때 발생할 수 있는   
초과 판매, 중복 구매와 데이터 정합성 문제를 프로젝트의 핵심 문제로 설명했다.

Redis와 Lua Script를 이용한 재고 선점, Purchase·Payment 상태 관리, 결제 승인·취소 동시성 제어, Toss Webhook 상태 보정과 k6 테스트까지   
하나의 구매 흐름으로 연결해 발표했다.

성능 테스트 역시 단순히 TPS나 p95 결과만 보여주는 것이 아니라   
최종 재고와 Purchase·Payment 상태까지 함께 확인해 서비스의 정합성을 검증한 과정으로 설명했다.

발표 피드백으로는 PostgreSQL을 사용했다는 사실만 제시하기보다,   
다른 RDBMS와 비교해 왜 PostgreSQL을 선택했는지 기술 선택의 근거를 정리해 포트폴리오에 명시해두면 좋을 것이라는 조언을 받았다.

> 다른 팀 프로젝트 발표 확인

자유 주제로 진행된 다른 팀의 프로젝트 발표를 들으며 서비스 주제와 핵심 구현, 기술 적용 방식과 테스트 결과를 확인했다.

프로젝트 전에 진행된 특강의 영향으로 여러 팀이 동시성이나 성능 테스트를 시도했고,   
데이터 정합성이나 실제 운영 상황을 고려한 문제를 다룬 경우가 많아 기술적인 방향에서는 비슷한 부분도 있었다.

다만 비슷한 문제를 다루더라도 각 팀이 집중한 기술과 해결 방식, 구현한 범위에는 차이가 있었고,   
같은 기술을 사용하더라도 어느 부분을 핵심으로 보고 얼마나 깊게 검증했는지가 달랐다.

이를 보면서 사용한 기술 자체보다 프로젝트에서 어떤 문제를 가장 중요하게 보고 얼마나 깊게 검증했는지가 프로젝트의 특징을 만든다는 점을 확인했다.

> Gudit 2차 프로젝트 회고

2차 프로젝트의 구현 과정과 결과를 돌아보며 현재 구조에서 해결한 문제와 남아 있는 한계를 정리했다.

Redis 재고 차감과 사용자별 구매 제한은 Lua Script로 원자적으로 처리하고,   
Purchase·Payment 상태 변경에는 비관적 락과 보상 처리를 적용해 동시성과 정합성을 보완했다.

하지만 Redis와 RDB는 하나의 트랜잭션으로 묶을 수 없기 때문에 DB 처리는 완료됐지만   
Redis 복구에 실패하는 등의 상황에서는 두 저장소의 상태가 달라질 가능성이 남아 있다.

Toss Payments 역시 내부 DB와 단일 트랜잭션으로 처리할 수 없어 Webhook과 보상 취소를 사용하고 있지만,   
보상 처리 자체가 실패할 경우에는 별도의 복구 수단이 필요하다.

3차에서는 Transactional Outbox를 이용해 처리해야 할 이벤트를 DB 트랜잭션과 함께 저장하고 Message Queue를 통해 전달하는 구조를 검토하기로 했다.

Consumer에서는 Inbox를 통해 중복 처리와 처리 여부를 관리하고, 실패한 작업을 재시도하거나 별도로 복구할 수 있는 구조까지 확장할 계획이다.

> 관리자 권한 분리

프로젝트 회고 이후 관리자 기능을 일반 사용자와 분리했다.

`ADMIN` 권한을 가진 사용자만 관리자 페이지와 상품 관리 API에 접근할 수 있도록 Spring Security 설정을 변경했다.

프론트에서도 로그인 사용자의 역할을 기준으로 관리자 메뉴가 노출되도록 처리했다.

이를 통해 관리자 메뉴를 화면에서 보이지 않게 만드는 것과 실제 관리자 API 접근을 차단하는 것은 별개의 문제라는 점을 확인했다.

프론트의 메뉴 노출 제어는 사용자 경험을 위한 처리이고, 실제 보안은 서버에서 권한을 검증해야 한다.

2차 프로젝트를 마무리하며 팀 저장소 README를 작성했다.

프로젝트 소개와 팀원 역할, 주요 기능, 기술 스택, 시스템 구성도와 ERD를 정리하고   
Redis 재고 처리와 Purchase·Payment 결제 흐름, 동시성 제어 등 핵심 구현 내용을 포함했다.

k6를 이용한 동시성·성능 테스트에서는 테스트 목적과 발생한 문제, 개선 결과를 함께 정리했다.

Redis-RDB와 외부 결제 시스템 사이의 정합성처럼 현재 구조에서 남아 있는 한계도 함께 작성하고,   
Message Queue와 Outbox/Inbox, 재처리·복구와 모니터링을 3차 개선 방향으로 구분했다.

현재 README는 2차 프로젝트의 실제 구현과 검증 결과를 중심으로 구성하고, 3차 프로젝트 종료 후 개선 전후 결과와 최종 성과를 추가할 예정이다.

> 2차 알고리즘 특강 모의고사

모의고사 문제 중 `방문 길이`를 풀었다.

`더 맵게`는 이전에 이미 풀었던 문제라 이번에는 다시 풀지 않았다.

`방문 길이`는 방문한 좌표가 아니라 처음 지나간 길의 개수를 세는 문제라,   
이동 전·후 좌표를 하나의 경로로 저장하고 반대 방향 이동도 같은 경로로 처리해 중복을 제거했다.

좌표 범위 `-5 ~ 5`를 벗어나는 이동은 무시하고, 실제로 이동한 경로만 `set`에 저장해 처음 지나간 길의 개수를 계산했다.

## 헷갈렸던 점

프로젝트 발표에서 사용한 기술을 얼마나 자세히 설명해야 하는지 고민했다.

Redis, 비관적 락, Webhook 같은 기술을 각각 설명하기보다 선착순 구매에서 어떤 문제가 발생했고   
그 문제를 해결하기 위해 왜 해당 기술을 사용했는지를 연결하는 것이 프로젝트의 핵심을 전달하기에 더 적절했다.

2차에서 이미 보상 처리를 구현했는데도 왜 3차에서 Outbox나 Message Queue가 필요한지도 다시 정리했다.

현재 보상 처리는 정상적으로 실행되면 상태를 복구할 수 있지만, 보상 처리 자체가 장애로 실패하면 복구해야 할 작업이 유실될 수 있다.

따라서 처리해야 할 작업을 먼저 기록하고 실패하더라도 다시 수행할 수 있는 구조가 필요하며,   
이를 위한 방법으로 Transactional Outbox와 Message Queue를 검토할 수 있다.

Message Queue를 도입하면 정합성 문제가 바로 해결되는지도 구분했다.

Message Queue 자체는 메시지를 전달하는 수단이므로 발행 실패, 중복 전달, Consumer 처리 실패가 발생할 수 있다.   
Outbox와 Inbox, 멱등성, 재시도와 모니터링까지 함께 설계해야 실제 장애 복구 구조가 된다.

관리자 메뉴를 화면에서 숨기는 것만으로 관리자 기능 접근을 제한할 수 있는지도 확인했다.

사용자가 직접 API를 호출할 수 있기 때문에 실제 접근 제어는 서버의 Spring Security에서 수행해야 하고, 프론트의 관리자 메뉴 노출 여부는 이를 대신할 수 없다.

README에 3차에서 적용할 기술을 어느 정도까지 작성해야 하는지도 고민했다.

아직 구현하거나 검증하지 않은 내용을 현재 프로젝트의 성과처럼 작성하지 않고,   
2차의 실제 결과와 한계를 중심으로 정리한 뒤 3차 내용은 개선 방향으로 구분하는 것이 적절했다.

## 오늘 느낀 점

오늘은 2차 프로젝트 발표를 마무리하고 다른 팀들의 발표까지 들으면서   
1차 프로젝트 때보다 프로젝트에서 기술을 사용하는 이유와 문제 해결 과정을 더 중요하게 보게 됐다는 점을 느꼈다.

Gudit에서는 단순한 구매 기능 구현보다 Redis 재고 처리, 결제 동시성, 외부 결제와 내부 상태의 정합성처럼   
실제 서비스에서 발생할 수 있는 문제를 직접 테스트하고 수정하는 경험을 할 수 있었다.

특히 k6 테스트에서 deadlock이나 Redis와 DB의 상태 불일치를 직접 확인하고 원인을 찾아 수정한 과정처럼   
처음부터 계획했던 기능보다 테스트 과정에서 발견한 문제가 더 의미 있는 경험으로 남았다.

회고를 하면서도 현재 구조가 모든 문제를 해결한 것은 아니라는 점이 명확해졌다.   
보상 처리까지 실패하는 상황이나 메시지 유실처럼 2차에서 남은 한계를 기준으로 3차의 기술을 선택해야겠다고 생각했다.

1차 프로젝트에서는 기본 기능을 완성하고 전체 기능을 통합하는 데 집중했다면,   
이번 프로젝트에서는 실제 서비스 상황을 가정해 동시성과 정합성 문제를 발견하고 테스트 결과를 근거로 개선하는 경험을 할 수 있었다.

3차에서도 새로운 기술을 많이 사용하는 것을 목표로 하기보다,   
현재 서비스에서 해결해야 하는 문제가 무엇인지 먼저 정의하고 그 문제를 해결하는 데 필요한 기술을 선택해야겠다.
