## 오늘 배운 내용

오늘은 Redis가 적용된 이후의 한정판매 전체 흐름과 재고 정책을 확인하고, 기존 RDB 기반 백엔드와 프론트 화면을 실제 API로 연결했다.

판매 중 실시간 재고는 Redis를 기준으로 관리하고, Redis Warm-up 이후 Lua Script로 재고와 사용자별 구매 수량을 원자적으로 처리하는 구조를 확인했다.   
결제 실패·취소나 Purchase 저장 실패가 발생하면 Redis 재고와 사용자별 구매 수량을 함께 복구해야 한다.

Redis와 RDB는 하나의 트랜잭션으로 묶이지 않기 때문에 판매 종료 시점의 재고 동기화와 결제 지연·실패로 뒤늦게 발생하는 재고 복구 사이의 정합성도 고려해야 한다.   
특히 Payment가 `IN_PROGRESS`인 경우 실제 Toss 승인 여부가 불명확할 수 있으므로 즉시 실패 처리하거나 재고를 복구해서는 안 된다.

프론트에서는 기존 Mock 데이터를 제거하고 판매·구매·결제·관리자 기능을 실제 API와 연결했다.   
이 과정에서 DTO에 필요한 필드가 존재하는 것뿐 아니라 실제 응답을 생성하는 각 매핑 경로에서도 값이 제대로 설정되어야 한다는 점을 확인했다.

JWT 인증에서는 서비스의 세션과 카카오 브라우저 로그인 세션이 서로 다른 개념이라는 점을 구분했다.   
JWT 기반 인증에서는 Spring Security를 Stateless하게 구성하고 Access/Refresh Token으로 서비스 인증 상태를 유지해야 한다.

판매 상태는 프론트에서 임의로 계산하기보다 DB·Redis·Scheduler가 관리하는 백엔드 상태를 기준으로 사용해야 하며,   
화면에서 잘못된 상태가 보일 경우 상태 전환 Scheduler와 Redis 동기화 흐름까지 함께 확인해야 한다.

## 실습 및 과제

> Redis 한정판매 전체 흐름 및 정책 확인

Redis 적용 이후 한정판매가 `Warm-up → 판매 시작 → 재고 선점 → 구매·결제 생성 → 결제 처리 → 재고 복구 → 판매 종료` 순서로 동작하는 전체 흐름을 확인했다.

재고 차감과 사용자별 구매 수량 증가는 하나의 Lua Script에서 원자적으로 처리하고,   
실패나 취소가 발생하면 복구 Script를 통해 두 값을 함께 되돌리도록 구성된 정책을 확인했다.

실시간 판매 재고는 Redis를 기준으로 사용하고 RDB의 `remainingStock`은 판매 종료 시 동기화하는 구조다.

다만 판매 종료 이후에도 미결제 timeout이나 결제 실패 처리를 통해 Redis 재고가 다시 증가할 수 있으므로,   
판매 종료 시 한 번만 동기화하면 최종 Redis와 RDB 재고가 달라질 가능성이 있다는 점을 확인했다.

Payment가 `IN_PROGRESS`인 상태에서는 실제 Toss 결제 결과를 확인하기 전까지 재고를 바로 복구하지 않고, 결제 상태에 따라 완료·실패·불확실 상태를 구분해야 한다.

아직 Toss 승인 단계에 진입하지 않은 `READY` 상태의 결제는 사용자 취소나 timeout 시 취소 상태로 전환할 수 있도록 별도의 상태 전이가 필요하다는 점도 정리했다.

> Payment 예외 처리 및 API 문서 보완

Payment 내부 오류는 공통 `BusinessException`과 `PaymentErrorCode`를 사용하고,   
Toss API 자체에서 발생한 오류는 `TossPaymentException`으로 구분하는 구조를 확인했다.

결제 내역 없음, 금액·`orderId` 불일치, 승인 실패, 결제 상태 확인 불가, 잘못된 상태 전이, 승인 후 DB 반영 실패와 보상 처리 실패 등을   
각각 다른 오류로 구분하도록 정리했다.

API 명세에는 결제 승인 API와 요청·응답 DTO를 추가하고, Purchase 생성 응답에도 `PENDING_PAYMENT` 상태와 `orderId`가 포함되는 현재 결제 흐름을 반영했다.

> 사용자 프론트 API 연동

판매 목록과 상세 화면을 `/api/sales`, `/api/sales/{saleId}`와 연결해 실제 상품명, 가격, 재고, 상태와 판매 기간을 표시하도록 수정했다.

구매 목록과 상세 화면도 실제 Purchase API와 연결했다.

구매 생성 이후 반환되는 `purchaseId`, `orderId`와 결제 금액을 결제 화면으로 전달하고, Toss 인증 성공 이후 실제 결제 승인 API를 호출하도록 흐름을 연결했다.

결제 성공·실패 화면에서도 Mock 데이터를 제거하고 실제 구매·결제 결과를 표시하도록 변경했다.

Toss 결제창에서 사용자가 직접 결제를 취소한 경우와 실제 결제 처리 실패도 구분해 안내하도록 했다.

> 관리자 프론트 API 연동

관리자 상품·판매 목록과 등록·수정 화면을 실제 백엔드 API에 연결했다.

상품 이미지 업로드에서는 JSON 데이터와 이미지 파일을 함께 전송해야 하므로   
`multipart/form-data`와 `@RequestPart` 구조가 필요하다는 점을 확인하고 백엔드 수정을 요청했다.

판매 등록 과정에서는 `datetime-local`의 날짜 형식과 백엔드에서 요구하는 날짜 형식이 달라 요청이 실패했다.

전송 전에 `T`를 공백으로 변경하고 초를 추가해 백엔드 요청 형식에 맞추도록 처리했다.

최신 Controller의 수정 API Method도 확인해 프론트 요청 방식과 맞췄다.

> Sale 응답 DTO 및 매핑 확인

실제 화면에서 상품 설명, 이미지, 초기 재고와 남은 재고가 필요해 Sale·Goods 응답 DTO에 필요한 필드 추가를 요청했다.

Redis 재고를 반영하는 별도의 응답 생성 메서드에서는 DTO에 필드가 선언되어 있어도 `description`, `imageUrl` 등의 실제 매핑이 빠질 수 있다는 점을 확인했다.

여러 `from()` 메서드나 생성 경로가 존재하는 경우 모든 경로에서 필요한 데이터가 제대로 설정되는지 확인해야 한다는 점을 정리했다.

> 로그인 상태 및 JWT 인증 흐름 수정

공통 헤더에서 `/api/users/me`를 호출해 로그인 상태에 따라 카카오 로그인 버튼과 사용자 닉네임·로그아웃 영역을 전환하도록 연결했다.

서비스에서 로그아웃한 뒤 카카오 로그인을 다시 실행했을 때 자동으로 기존 계정으로 로그인되는 현상을 확인했다.

Spring Security의 인증 세션과 카카오 브라우저 로그인 세션은 서로 별개이며,   
JWT 기반 서비스에서는 `SessionCreationPolicy.STATELESS`로 HttpSession 기반 인증 상태가 남지 않도록 해야 한다는 점을 확인했다.

Stateless는 로그인 상태를 유지하지 않는다는 의미가 아니라 서버 세션 대신 Access/Refresh Token으로 인증을 유지한다는 의미다.

카카오 자체의 기존 로그인 세션으로 같은 계정이 자동 선택되는 문제는 OAuth 요청에서 계정 선택이 가능하도록 별도로 처리했다.

> 프론트 상품 이미지 준비

실제 판매 화면과 상품 관리 화면에서 사용할 굿즈 이미지를 제작해 프론트에 적용할 기본 상품 리소스를 준비했다.

> 관리자 UI 구분

사용자 화면과 관리자 화면의 구분을 강화하고 상품 관리와 판매 관리가 비슷하게 보이는 부분을 수정했다.

관리자 배경을 기존보다 진한 연회색으로 조정하고 판매 관리에서는 블루 네이비를 정보 계층을 나타내는 보조 색상으로 적용했다.

하늘색은 주요 액션과 상태 표현에 사용하고 네이비는 관리자 정보 표현에 사용하도록 역할을 구분해 기존 디자인 시스템을 유지했다.

> 판매 상태 Scheduler 확인

판매 시작 시간이 지났는데도 화면과 DB에서 `READY` 상태가 유지되는 문제를 확인했다.

판매 상태 전환 Scheduler 자체에는 `@Scheduled`가 있었지만 스케줄링이 활성화되지 않아 자동 전환이 실행되지 않고 있었다.

스케줄링을 활성화한 뒤 기존 `READY` 판매가 `ON_SALE`로 정상 전환되는 것을 확인했다.

동시에 판매 종료 시간이 지난 기존 데이터가 Redis 재고 Key를 가지고 있지 않아 종료 Scheduler에서 오류가 발생하는 문제도 확인했다.

프론트에서 시간을 기준으로 상태를 임의 계산해 문제를 숨기기보다 DB·Redis·Scheduler 간 상태 동기화를 백엔드에서 해결하는 것이 적절하다는 점을 정리했다.

## 헷갈렸던 점

응답 생성 경로가 여러 개라면 DTO 필드 선언뿐 아니라 각 `from()` 등의 매핑 로직에서도 실제 값을 설정해야 한다.

로그아웃 이후 카카오 로그인을 누르면 같은 계정으로 다시 로그인되는 현상이 모두 Spring Security 세션 때문인지 고민했다.  
서비스의 HttpSession 인증 문제와 카카오 브라우저의 로그인 세션은 별개이며    
JWT 인증에서는 Stateless 설정이 필요하지만 카카오 계정 선택은 OAuth 쪽에서 따로 처리해야 한다.

`SessionCreationPolicy.STATELESS`를 사용하면 서버 재시작 이후 로그인 정보도 모두 사라지는지 헷갈렸다.  
인증 상태를 HttpSession이 아니라 JWT로 판단하므로 유효한 토큰과 동일한 서명키가 존재하면 서버 세션과 관계없이 인증할 수 있다.

판매 시작 시간이 지났다면 프론트에서 `ON_SALE`로 계산해 보여줘도 되는지도 고민했다.  
판매 상태는 재고 Warm-up과 Redis 상태까지 연결된 백엔드 도메인 상태이므로 프론트에서 임의로 변경하기보다 Scheduler의 상태 전환 문제를 해결하는 것이 맞다.

## 오늘 느낀 점

오늘은 Redis가 추가되면서 단순히 재고 저장소만 RDB에서 Redis로 바뀌는 것이 아니라 구매·결제·판매 종료까지 전체 상태 관리 방식이 함께 달라진다는 점을 확인했다.

특히 Redis 재고와 RDB Purchase·Payment가 서로 다른 저장소에 있기 때문에 실패와 취소가 어느 시점에 발생하느냐에 따라 복구해야 하는 상태가 달라지고,   
최종 재고 동기화 시점도 중요해졌다.

프론트를 실제 API에 연결하면서 백엔드의 DTO와 상태 값이 화면에 그대로 영향을 준다는 점도 더 명확하게 확인했다.   
단순히 API가 응답하는지만 보는 것이 아니라 실제 화면에 필요한 값이 모든 응답 경로에서 정확하게 전달되는지 확인해야 했다.

또한 판매 상태가 잘못 표시되는 문제를 확인하면서 프론트에서 임시로 보정하기보다   
Redis Warm-up, DB 상태와 Scheduler까지 실제 상태 변경 흐름을 따라가며 원인을 찾는 것이 중요하다는 점을 느꼈다.

이제 사용자·관리자 화면과 실제 API의 기본 연결이 진행된 만큼 이후에는 Redis 기반 구매 흐름과 결제 실패·취소 상황을 실제 화면에서 끝까지 검증하고,   
동시성 및 부하 테스트를 통해 RDB 방식과 Redis 적용 이후의 차이를 확인해야겠다.
