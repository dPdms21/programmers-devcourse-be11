## 오늘 배운 내용

오늘은 기존 JWT 인증 구조에 카카오 OAuth2 로그인과 소셜 회원가입 흐름을 실제로 연결했다.

`/oauth2/authorization/kakao`와 `/login/oauth2/code/kakao`는 별도의 Controller가 처리하는 경로가 아니다.  
Spring Security의 OAuth2 필터가 해당 경로를 가로채   
카카오 로그인 화면 이동, `state` 검증, 인가 코드와 카카오 Access Token 교환, 사용자 정보 조회까지 처리한다.

개발자는 사용자 정보 조회 이후의 회원 연결과 인증 성공·실패 후처리를 구현한다.  
`SecurityConfig`의 `oauth2Login()`에는 `CustomOAuth2UserService`, `OAuth2SuccessHandler`, `OAuth2FailureHandler`를 등록했다.

`CustomOAuth2UserService`는 `DefaultOAuth2UserService`의 `loadUser()`를 호출해 카카오 사용자 정보 조회를 Spring Security에 맡긴다.   
이후 `registrationId`를 `AuthProvider`로 변환하고,   
`OAuth2UserInfoFactory`를 통해 카카오 응답을 `KakaoUserInfo`로 감싸 공통 형태로 사용한다.

카카오 사용자 정보에서 이메일을 가져오지 못한 경우에는 일반 예외가 아니라 `OAuth2AuthenticationException`을 발생시켜야 한다.   
그래야 Spring Security가 이를 OAuth2 인증 실패로 처리하고 `OAuth2FailureHandler`로 전달한다.

OAuth2 회원은 변경될 수 있는 이메일이나 닉네임이 아니라 `provider`와 `providerId`의 조합으로 조회한다.   
기존 회원이면 최신 프로필 정보를 반영한 뒤 회원 정보가 포함된 `CustomOAuth2User`를 반환하고,   
회원이 없으면 바로 DB에 저장하지 않고 미가입 상태의 객체를 반환한다.

카카오 인증 성공과 서비스 회원가입 완료는 별개의 상태다.  
미가입 사용자는 카카오 계정 인증에는 성공했지만 아직 서비스 가입에 동의하지 않았으므로 `user`가 `null`이고 임시 `ROLE_GUEST` 권한을 가진다.   
`OAuth2SuccessHandler`는 회원 등록 여부를 확인해 기존 회원과 미가입 사용자를 구분한다.

기존 회원에게는 자체 Access Token과 Refresh Token을 발급한다.   
Refresh Token은 `HttpOnly` 쿠키에 저장하고, 이후 프론트가 재발급 API를 호출해 Access Token을 얻는다.   
카카오 Access Token은 사용자 정보를 조회할 때만 사용하고 이후 API 인증은 자체 JWT로 통일한다.

미가입 사용자에게는 10분 동안 유효한 `signupToken`을 발급한다.   
가입 토큰에는 `provider`, `providerId`, 이메일, 이름과 `type=signup`을 포함한다.   
토큰 용도를 별도로 검증해 일반 Access Token이 소셜 회원가입에 사용되지 않도록 구분했다.

`OAuthSignUpRequestDto`는 프론트에서 전달받은 검증 전 요청이고,   
`SignupPayloadDto`는 서버가 가입 토큰의 서명·만료 시간·용도를 검증한 뒤 Claim에서 복원한 내부 데이터다.   
실제 회원가입에는 프론트가 전달한 이메일이나 이름이 아니라 검증된 가입 토큰의 정보를 사용한다.

`UserService.oauthSignUp()`에서는 가입 토큰을 검증한 뒤 다시 `provider`와 `providerId`로 회원을 조회한다.   
같은 가입 요청이 반복되더라도 이미 회원이 존재하면 추가 저장하지 않아 최종 결과가 달라지지 않도록 구성했다. 이러한 특성을 멱등성이라고 한다.

회원이 없으면 카카오 사용자 ID를 바탕으로 내부 `userId`를 생성하고 회원 정보를 저장한다.   
저장 후 자체 Access Token과 Refresh Token을 발급해 별도 로그인 없이 즉시 로그인 상태로 연결한다.

클래스에 `@Transactional(readOnly = true)`가 적용되어 있더라도   
실제 저장을 수행하는 `oauthSignUp()`에는 쓰기용 `@Transactional`을 별도로 적용해야 한다.

또한 만료된 Access Token을 처리하는 JWT 필터와 토큰 재발급 API의 관계를 확인했다.

`permitAll()`은 요청이 보안 필터를 거치지 않는다는 뜻이 아니라, 필터 체인의 인가 단계에서 인증 없이 접근할 수 있다는 뜻이다.   
앞쪽의 `TokenAuthenticationFilter`가 만료된 토큰을 발견하자마자 `401` 응답을 설정하고 요청을 종료하면,   
`permitAll()`로 설정한 `/api/tokens/refresh`도 Controller에 도달할 수 없다.

따라서 만료된 Access Token은 인증 객체를 생성하지 않고 다음 필터로 요청을 전달해야 한다.   
보호된 API는 인증 정보가 없으므로 최종적으로 `AuthenticationEntryPoint`가 `401`을 반환하고,   
재발급 API는 `permitAll()` 경로이므로 쿠키의 Refresh Token을 이용해 새로운 토큰을 발급할 수 있다.

## 실습 및 과제

> 카카오 OAuth2 로그인과 회원 연동

`SecurityConfig`에 `oauth2Login()`을 설정하고 사용자 정보 조회 Service와 인증 성공·실패 Handler를 연결했다.

`CustomOAuth2UserService`에서는 카카오 사용자 정보를 공통 객체로 변환하고, `provider`와 `providerId`를 기준으로 기존 회원을 조회했다.   
기존 회원은 최신 닉네임을 반영하고, 미가입 사용자는 DB에 저장하지 않은 상태로 성공 Handler에 전달했다.

`OAuth2SuccessHandler`에서는 기존 회원에게 자체 JWT를 발급하고 Refresh Token을 쿠키에 저장했다.   
미가입 사용자에게는 짧은 수명의 가입 토큰을 발급해 추가 가입 화면으로 이동시켰다.

소셜 회원가입 API에서는 가입 토큰의 서명, 만료 시간과 용도를 검증한 뒤 토큰에서 복원한 사용자 정보로 회원을 저장했다.   
이미 동일한 소셜 회원이 존재하면 기존 회원을 사용해 중복 가입을 방지하고, 가입 완료 후 자체 JWT를 발급해 로그인 상태로 연결했다.

> JWT 필터와 토큰 재발급 흐름

`TokenAuthenticationFilter`에서 만료된 Access Token을 발견했을 때 응답을 즉시 종료하던 코드를 제거했다.

만료된 토큰으로 보호된 API를 요청하면 인증 객체가 생성되지 않아 최종 인가 단계에서 `401`이 반환된다.   
반면 `/api/tokens/refresh`는 요청이 Controller까지 전달되므로 유효한 Refresh Token으로 Access Token과 Refresh Token을 재발급할 수 있다.

> 개인 면담

개인 면담에서는 AI를 단순한 코드 작성 보조 도구로 사용하는 데 그치지 않고,   
프로젝트 관리와 반복 업무를 맡길 수 있는 에이전트를 직접 구성하고 운영해 보라는 조언을 들었다.

노션이나 일정·일감 관리 도구와 AI를 연결해 작업 분석, 역할 분배와 QA를 보조하는 에이전트를 구성하고,   
프로젝트별 Context를 유지하면서 토큰과 비용을 효율적으로 관리하는 방법도 고민해 보라는 조언을 들었다.

> 제2회 교과목 성취도 평가

Spring 관련 교과목 성취도 평가를 통해 지금까지 학습한 개념을 다시 점검했다.

예상보다 틀린 문제가 있어 알고 있는 개념도 문제의 조건과 표현을 끝까지 정확히 읽고 판단해야 한다는 점을 확인했다.

## 헷갈렸던 점

OAuth2 로그인 경로에 별도의 Controller가 없는 이유가 헷갈렸다.  
`/oauth2/authorization/kakao`는 `OAuth2AuthorizationRequestRedirectFilter`가 처리하고,   
`/login/oauth2/code/kakao`는 `OAuth2LoginAuthenticationFilter`가 처리하는 Spring Security의 규약 경로다.

`CustomOAuth2UserService`에서 발생한 예외를 일반 예외로 던져도 되는지 헷갈렸다.   
OAuth2 인증 실패 Handler로 연결하려면 `OAuth2AuthenticationException`으로 전달해 Spring Security의 인증 실패 흐름에 포함해야 한다.

카카오 인증에 성공한 미가입 사용자도 로그인된 회원인지 헷갈렸다.   
카카오가 사용자를 확인한 것과 우리 서비스의 회원가입 동의가 완료된 것은 다르므로,   
회원이 DB에 없으면 `ROLE_GUEST` 상태에서 추가 가입 절차를 진행해야 한다.

`OAuthSignUpRequestDto`와 `SignupPayloadDto`의 역할도 구분해야 했다.   
전자는 프론트가 전달한 검증 전 요청이고, 후자는 서버가 가입 토큰을 검증한 후 신뢰할 수 있는 Claim을 복원한 내부 데이터다.

가장 헷갈렸던 부분은 만료된 Access Token을 JWT 필터에서 즉시 `401`로 종료해야 하는지였다.  
필터가 요청을 먼저 종료하면 `permitAll()`로 설정된 재발급 API도 실행되지 않는다.   
JWT 필터는 유효한 토큰으로 인증 객체를 복원하는 역할을 맡고, 인증 필요 여부와 최종 `401`·`403` 처리는 이후 인가 및 예외 처리 단계가 담당해야 한다.

`permitAll()`도 필터를 건너뛰는 설정이라고 생각하기 쉽지만, 모든 요청은 필터 체인을 통과한다.   
`permitAll()`은 최종 인가 판단에서 인증 없이 접근을 허용한다는 의미다.

## 오늘 느낀 점

카카오 OAuth2 로그인을 실제로 연결하면서 Spring Security가 담당하는 표준 흐름과 개발자가 구현해야 하는 서비스 로직의 경계를 확인할 수 있었다.

프레임워크는 인가 요청, 콜백, 토큰 교환과 사용자 정보 조회를 처리하고,   
애플리케이션은 외부 사용자를 내부 회원과 연결한 뒤 가입 여부에 따라 자체 JWT 발급 또는 추가 가입 절차로 분기한다.

특히 카카오 인증 이후에도 우리 서비스의 회원 상태를 다시 확인하고, 미가입자의 정보를 즉시 저장하지 않은 채 가입 동의를 받는 구조가 중요했다.   
가입 토큰의 용도까지 검증하고 중복 요청을 멱등하게 처리하는 이유도 실제 사용자 흐름과 함께 이해할 수 있었다.

JWT 필터의 함정 코드를 수정하면서 각 보안 구성요소의 책임도 더 명확하게 구분했다.   
필터가 모든 인증 실패 응답을 직접 결정하는 것이 아니라,   
유효한 토큰일 때 `SecurityContext`를 구성하고 이후 인가 단계가 요청 경로에 맞게 결과를 결정하도록 해야 한다.

개인 면담을 통해 AI를 활용한 에이전트 구성을 생각하는 데서 그치지 않고, 프로젝트 관리나 반복 업무에 실제로 적용해 운영해 봐야겠다고 느꼈다.

성취도 평가에서는 개념을 대략 알고 있는 것과 문제의 조건을 정확히 읽어 정답을 판단하는 것은 다르다는 점을 확인했다.
