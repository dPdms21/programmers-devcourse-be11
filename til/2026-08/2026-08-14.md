## 오늘 배운 내용

오늘은 Purchase와 Payment의 실제 결제 흐름을 정리하고, 결제 상태와 재고가 서로 어긋나지 않도록 실패·취소 보상 로직을 보강했다.

구매 요청 시 Purchase를 바로 구매 완료로 처리하지 않고 `PENDING_PAYMENT`, Payment를 `READY` 상태로 생성한 뒤 재고만 먼저 확보한다.   
Toss 결제 인증 이후 승인 요청을 시작하면 Payment를 `IN_PROGRESS`로 변경하고,   
Toss 승인과 내부 DB 반영이 모두 성공한 경우에만 Payment를 `DONE`, Purchase를 `PURCHASED`로 확정하도록 흐름을 구성했다.

Payment 상태가 임의로 변경되지 않도록 허용된 상태 전이만 수행할 수 있는 가드를 추가했다.   
정상 결제 흐름뿐 아니라 Toss 승인 성공 후 내부 DB 반영이 실패하는 상황처럼 별도의 상태 전이가 필요한 경우도 구분해 처리했다.

외부 PG와 내부 DB는 하나의 트랜잭션으로 묶을 수 없으므로 Toss 승인 성공 이후 DB 처리가 실패하면 승인된 결제를 다시 취소하는 보상 처리가 필요하다.   
반면 카드 승인 거절처럼 실패가 명확한 경우와 네트워크 오류처럼 승인 여부를 알 수 없는 경우는 같은 방식으로 처리해서는 안 된다는 점도 확인했다.

Redis 재고 구현은 Payment가 직접 Redis를 사용하는 구조가 아니라 기존처럼 `InventoryService`를 통해 재고를 처리하도록 유지했다.   
이를 통해 이후 RDB 기반 Inventory가 Redis 기반으로 변경되더라도 Purchase와 Payment의 핵심 흐름은 크게 변경하지 않는 구조를 유지할 수 있다.

프론트에서는 실제 서비스 흐름에 사용할 결제 확인·성공·실패 화면을 Mock 데이터로 구현했다.   
기존 Toss 연동 테스트용 페이지와 실제 서비스용 화면을 분리하고, 추후 API가 연결되면 결제 정보와 승인 요청을 실제 데이터로 교체할 예정이다.

## 실습 및 과제

> Payment 상태 전이 가드 적용

Payment의 상태가 아무 순서로나 변경되지 않도록 상태 전이 검증을 추가했다.

기본 결제 흐름은 `READY → IN_PROGRESS → DONE`으로 구성하고,   
승인 실패 시 `IN_PROGRESS → FAILED`, 정상 취소 시 `DONE → CANCELED`로 변경하도록 했다.

허용되지 않은 상태에서 상태 변경 메서드를 호출하면 `INVALID_PAYMENT_STATUS` 예외가 발생하도록 구성했다.

Toss 승인은 성공했지만 내부 DB 반영이 실패한 경우에는   
일반 결제 취소와 시작 상태가 다르므로 `IN_PROGRESS → CANCELED` 상태 전이를 별도로 처리하도록 했다.

> Toss 승인 후 DB 실패 보상 처리

Toss 승인 성공과 내부 DB 완료 처리는 하나의 트랜잭션으로 처리할 수 없으므로 두 시스템의 상태가 불일치할 수 있는 상황을 고려했다.

Toss에서는 결제가 승인됐지만 내부 DB 완료 처리에 실패한 경우 승인된 결제를 자동 취소하고   
Payment와 Purchase를 `CANCELED`로 변경한 뒤 확보한 재고도 복구하도록 구성했다.

카드 승인 거절처럼 실패가 명확한 경우에는 Payment를 `FAILED`, Purchase를 `CANCELED`로 변경하고 재고를 복구한다.

반면 timeout이나 네트워크 오류처럼 실제 결제 승인 여부를 확정할 수 없는 경우에는   
바로 실패나 취소로 변경하지 않고 Toss의 결제 상태를 다시 조회하도록 했다.

조회 결과 실제 결제가 완료된 상태라면 내부 완료 처리를 이어가고,   
여전히 결과를 확정할 수 없는 경우에는 Payment `IN_PROGRESS`, Purchase `PENDING_PAYMENT` 상태와 확보된 재고를 유지하도록 했다.

> 구매 및 결제 취소 흐름 정리

결제 전 구매와 결제 완료 후 구매의 취소 흐름을 분리했다.

`PENDING_PAYMENT` 상태에서는 실제 승인된 Toss 결제가 없으므로 Toss 취소 요청 없이 Purchase를 취소하고 재고를 복구한다.

`PURCHASED`와 Payment `DONE` 상태에서는 Toss 결제를 먼저 취소한 뒤 Payment와 Purchase를 모두 `CANCELED`로 변경하고 재고를 복구한다.

취소된 구매는 다시 구매할 수 있도록 활성 구매만 중복 구매로 판단하는 기존 정책도 유지했다.

> Payment 테스트 보강

기존 Purchase 테스트를 `PENDING_PAYMENT` 기반 결제 흐름에 맞게 수정하고 Payment 관련 테스트를 추가했다.

Payment 엔티티의 정상·비정상 상태 전이와 `orderId`, 결제 금액 검증을 확인했다.

Payment Service에서는 정상 승인, 명확한 승인 실패, 불확실한 결제 오류 재조회,   
Toss 승인 후 DB 실패 보상과 보상 처리 자체가 실패하는 상황까지 주요 분기를 검증했다.

관련 테스트와 전체 빌드를 실행해 변경된 결제 흐름이 정상적으로 동작하는 것을 확인했다.

> Inventory userId 연동

Redis 재고 구현에 필요한 사용자 구분을 위해 `InventoryService`의 재고 차감·복구 메서드에 `userId`가 추가된 변경사항을 반영했다.

Purchase에서는 이미 인증 과정에서 전달받은 `userId`를 그대로 Inventory에 전달하도록 수정했다.

Payment의 실패·취소 보상 과정에서는 연결된 Purchase의 사용자 ID를 이용해 재고를 복구하도록 변경했다.

이 과정에서도 Purchase와 Payment가 Redis 자체를 직접 알지 않고 `InventoryService` 인터페이스만 사용하도록 구조를 유지했다.

> 결제 프론트 기본 화면 구현

기존 Toss Payments 테스트 페이지와 별도로 실제 서비스에서 사용할 결제 확인, 결제 성공, 결제 실패 화면을 구현했다.

결제 확인 화면에서는 상품명, 구매 수량, 상품 금액과 최종 결제 금액을 확인한 뒤 결제를 진행할 수 있도록 구성했다.

결제 성공 화면에서는 구매 내역과 상품 목록으로 이동할 수 있도록 하고,   
실패 화면에서는 상품으로 돌아가거나 결제를 다시 시도할 수 있도록 사용자 흐름을 구성했다.

현재는 Mock 데이터를 사용하며 Toss 결제 요청 로직은 아직 연결하지 않았다.   
이후 Purchase API에서 받은 `orderId`, 결제 금액과 Toss 설정을 실제 화면에 연결할 예정이다.

Mock 화면 확인 과정에서 인증이 필요한 경로가 차단되는 것도 확인하고, 화면 확인에 필요한 경로만 임시로 Security 설정에서 허용했다.

## 헷갈렸던 점

Payment에 상태 enum만 두면 잘못된 상태 변경도 자연스럽게 막을 수 있는지 고민했다.  
상태 값 자체만 정의해서는 임의의 상태 변경을 막을 수 없으므로 현재 상태에서 허용된 다음 상태인지 검증하는 상태 전이 가드가 별도로 필요했다.

Toss 승인 성공 후 DB 반영이 실패하면 Payment를 `FAILED`로 처리해야 하는지도 고민했다.  
외부 결제 자체는 이미 성공한 상태이므로 단순 승인 실패와 의미가 다르다.   
승인된 결제를 보상 취소한 뒤 Payment를 `CANCELED`로 변경하는 것이 실제 상태에 더 맞다는 점을 구분했다.

결제 승인 API에서 오류가 발생하면 바로 Purchase와 재고를 복구해도 되는지도 다시 확인했다.  
승인 거절처럼 실패가 명확한 경우에는 가능하지만   
timeout이나 네트워크 장애는 Toss에서 실제 승인이 완료됐을 가능성이 있으므로 먼저 실제 결제 상태를 확인해야 한다.

결제 전 취소에서도 Payment를 함께 `CANCELED`로 변경해야 하는지 고민했다.  
아직 Toss 승인 자체가 발생하지 않은 단계이므로 현재 흐름에서는 Purchase 취소와 재고 복구를 우선 처리하며 실제 승인 완료 결제와 취소 의미를 구분했다.

Redis Inventory 적용을 위해 Payment에서도 Redis를 직접 호출해야 하는지도 확인했다.  
재고 저장소가 RDB인지 Redis인지는 Inventory 영역의 책임이므로   
Purchase와 Payment에서는 기존처럼 `InventoryService`를 통해서만 재고를 처리하는 구조가 적절하다.

`InventoryService`에 `userId`가 추가됐을 때 Payment에서는 어떤 사용자 ID를 넘겨야 하는지도 확인했다.  
결제 실패나 취소 대상 Payment는 Purchase와 연결되어 있으므로 해당 Purchase의 사용자 ID를 사용하면 된다.

현재 구매 수량이 항상 1인데 `maxPurchaseQuantity`까지 바로 연결해야 하는지도 고민했다.  
현재 프로젝트의 우선순위는 Redis 재고, 메시지 큐와 동시성 테스트이므로 당장은 1인 1개 구매를 유지하고,   
이후 필요할 때 구매 요청에서 수량을 받아 확장하는 것이 적절하다고 판단했다.

## 오늘 느낀 점

오늘은 결제 성공만 처리하는 것보다 결제 과정에서 발생할 수 있는 실패 상태를 정확하게 구분하는 것이 더 중요하다는 점을 느꼈다.

특히 Toss 승인 성공 후 내부 DB가 실패하는 상황은 외부 결제와 내부 트랜잭션이 분리되어 있기 때문에 발생하는 문제이고,   
단순 rollback이 아니라 실제 결제 취소라는 보상 작업이 필요했다.

Payment의 상태 전이도 단순히 enum 값을 변경하는 것이 아니라   
현재 상태에서 어떤 상태로 이동할 수 있는지 도메인 규칙으로 제한하면서 각 상태의 의미가 더 명확해졌다.

또한 Redis 적용을 앞두고 Purchase와 Payment가 재고 구현 방식에 직접 의존하지 않고   
`InventoryService`만 사용하도록 유지한 것이 중요하다는 점도 확인했다.   
이후 재고 저장소가 변경되더라도 구매·결제 흐름의 변경 범위를 최소화할 수 있을 것 같다.

백엔드의 구매·결제 흐름과 주요 테스트까지 정리한 만큼 다음에는 Redis 기반 Inventory와 실제 프론트 결제를 연결하고,   
동시 요청과 실패 상황에서도 전체 상태가 일관되게 유지되는지 확인해야겠다.
