## 오늘 배운 내용

오늘은 Gudit 프로젝트의 기획을 마무리하고 역할 분담, 기능 정의서, 유저 스토리와 API 명세서를 작성했다.

프로젝트에서 구현할 기능을 인증·사용자, 상품·판매·재고, 구매 영역으로 구분하고 각 담당자가 맡을 범위를 정리했다.   
단순히 기능을 나누는 것뿐 아니라 구매가 사용자 인증과 판매·재고 기능에 의존하는 것처럼 도메인 간 연결 관계도 함께 확인했다.

기능 정의서와 유저 스토리를 작성하면서 사용자가 판매 중인 굿즈를 조회하고 상세 정보를 확인한 뒤 구매하고,   
구매 내역을 조회하거나 취소하는 전체 흐름을 구체화했다.   
이를 바탕으로 각 기능의 HTTP Method, URI와 요청·응답 데이터를 정리해 API 명세서를 작성했다.

기획을 마친 뒤 담당한 Purchase 도메인의 기본 구조를 구현했다.   
구매 당시의 가격을 `purchasePrice`로 저장해 이후 상품 가격이 변경되더라도 기존 구매 기록이 영향을 받지 않도록 했으며,   
동일 사용자의 동일 판매 중복 구매는 서비스 로직과 DB의 Unique Constraint를 함께 이용해 방지하도록 구성했다.

현재 1인 1개 구매 정책이므로 `quantity`는 유지하되 `totalPrice`는 별도로 저장하지 않고, 다중 수량 구매가 필요할 경우 확장하기로 했다.

프론트는 Thymeleaf와 vanilla JavaScript를 이용해 사용자용 기본 화면을 구현했다.   
홈, 판매 목록·상세, 구매 목록·상세 화면을 구성하고 이후 백엔드 API가 완성되면 JavaScript의 `fetch()`로 연동할 수 있도록 구조를 잡았다.

강사 피드백을 통해 향후 메시지 큐를 활용한 비동기 구매 처리와 중복 요청 대응, 결제 과정에서 발생할 수 있는 결제·DB 정합성 문제도 추가로 검토하기로 했다.

## 실습 및 과제

> Gudit 프로젝트 기획

프로젝트 기획서를 마무리하고 팀원별 역할과 구현 범위를 정리했다.

인증·사용자, 상품·판매·재고, 구매 영역으로 역할을 구분하고 각 기능이 다른 영역과 어떻게 연결되는지도 함께 확인했다.

기능 정의서를 작성해 서비스에 필요한 기능과 각 기능의 범위를 구체화했다.   
사용자가 판매 상품을 조회하고 구매한 뒤 구매 내역을 확인하거나 취소하는 흐름을 중심으로 필요한 기능을 정리했다.

유저 스토리에서는 실제 사용자 관점에서 서비스 이용 과정을 정리해 기능 간 순서와 관계를 확인했다.

이를 바탕으로 API 명세서를 작성하고 각 기능의 HTTP Method, URI, 요청·응답 구조를 정의했다.   
구매 API는 특정 판매에 대한 구매 요청이라는 의미가 드러나도록 판매 ID를 기준으로 설계했다.

> Purchase 도메인 기본 구현

담당한 구매 영역의 `Purchase` 엔티티와 `PurchaseStatus`를 구현했다.

동일 사용자가 같은 판매를 중복 구매하지 못하도록 `user_id + sale_id`에 Unique Constraint를 적용하고,   
구매 당시 가격은 `purchasePrice`에 저장하도록 했다.

Repository에서는 중복 구매 여부와 사용자별 구매 목록, 특정 사용자의 구매 상세를 조회할 수 있도록 구성했다.

Service에서는 중복 구매 방지, 구매 목록·상세 조회와 중복 취소 방지 로직을 먼저 구현했다.   
판매 상태 확인과 재고 차감·복구처럼 다른 도메인에 의존하는 부분은 관련 기능이 구현된 이후 연동할 예정이다.

구매 생성·취소와 중복 구매, 존재하지 않는 구매 조회, 중복 취소에 대한 단위 테스트도 작성했다.

> 사용자용 프론트 기본 화면 구현

Spring Boot 내부에서 Thymeleaf와 vanilla JavaScript를 이용해 사용자용 화면을 구성했다.

홈, 판매 목록·상세, 구매 목록·상세 화면을 만들고 판매 상태, 남은 수량, 판매 기간과 구매 상태 등을 확인할 수 있도록 했다.

아직 API가 구현되지 않은 부분은 Mock 데이터를 이용해 화면을 먼저 구성하고, 이후 REST API가 완성되면 `fetch()`를 이용해 실제 데이터와 연결할 예정이다.

## 헷갈렸던 점

구매 엔티티에 `quantity`와 `totalPrice`를 모두 저장해야 하는지 고민했다.
현재는 1인 1개 구매이므로 `quantity`는 향후 확장 가능성을 위해 유지하고,   
`purchasePrice`와 동일한 값이 되는 `totalPrice`는 별도로 저장하지 않기로 했다.

중복 구매를 Service 로직에서만 막아도 되는지도 고민했다.
동시에 여러 요청이 들어오는 상황에서는 애플리케이션의 사전 조회만으로 중복 저장을 완전히 막기 어려울 수 있으므로,   
`user_id + sale_id` Unique Constraint를 함께 두어 DB에서도 방어하도록 했다.

Purchase Service를 어느 범위까지 먼저 구현할 수 있는지도 구분해야 했다.
구매 생성 자체는 사용자 정보와 판매 상태, 재고 차감이 모두 연결되어야 하므로 다른 도메인이 완성되기 전에는 전체 흐름을 구현하기 어렵다.   
따라서 현재는 중복 구매 검사, 조회와 취소 상태 변경처럼 독립적으로 구현할 수 있는 부분부터 작성했다.

프론트도 백엔드 API가 완성된 뒤에 시작해야 하는지 고민했다.
현재는 화면 구조와 사용자 흐름을 먼저 확인하기 위해 Mock 데이터로 구현하고,   
이후 REST API가 완성되면 JavaScript의 `fetch()` 기반으로 실제 데이터 연동 부분만 교체하는 방향으로 정리했다.

## 오늘 느낀 점

오늘은 구현보다 프로젝트 기획을 구체화하는 작업의 비중이 가장 컸다.

기능 정의서와 유저 스토리를 작성하면서 필요한 기능을 단순히 나열하는 것보다   
사용자가 실제로 서비스를 이용하는 순서를 기준으로 정리하는 것이 기능 간 관계를 파악하는 데 도움이 됐다.

API 명세까지 작성하면서 각 기능이 실제 코드에서 어떤 도메인과 연결되는지도 조금 더 명확해졌다.   
특히 구매 기능은 Purchase만으로 완성되는 것이 아니라 사용자 인증, 판매 상태와 재고 처리가 모두 연결되어야 한다는 점을 확인했다.

기획을 마친 뒤 담당한 Purchase에서 독립적으로 구현 가능한 부분부터 작성했고, 프론트도 백엔드 기능을 확인할 수 있는 최소한의 사용자 화면으로 범위를 정했다.

강사 피드백으로 Redis, 메시지 큐와 실제 결제 연동 등의 개선 방향도 확인했지만,   
우선 현재 기획에서 정의한 기본 기능을 완성한 뒤 필요한 부분에 단계적으로 적용할 예정이다.
