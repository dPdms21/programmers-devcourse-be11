## 오늘 배운 내용

오늘은 Toss Payments Webhook을 실제 테스트 환경과 연결해 결제 상태 보정 흐름을 검증하고,   
k6를 이용해 결제 승인과 취소가 동시에 발생하는 상황의 동시성 문제를 확인했다.

Webhook은 전달받은 상태를 그대로 신뢰하지 않고 `paymentKey`로 Toss 결제를 다시 조회한 뒤   
`paymentKey`, `orderId`, `amount`가 일치하는지 확인하고 실제 PG 상태를 기준으로 Payment와 Purchase를 보정하도록 구성했다.

동일 Webhook이 여러 번 들어오거나 사용자 취소·timeout과 동시에 실행될 수 있기 때문에 현재 상태를 다시 확인하고   
이미 최종 처리된 경우에는 추가 상태 변경이나 Redis 재고 복구를 하지 않는 멱등성이 필요하다.

실제 Toss Webhook 테스트에서는 외부 서버가 로컬 애플리케이션에 접근할 수 있도록 ngrok을 사용했다.   
Webhook DTO의 날짜 타입이 실제 Toss payload 형식과 달라 500이 발생했고,   
실제 요청 형식에 맞게 수정한 뒤 재전송과 신규 Webhook이 모두 정상 처리되는 것을 확인했다.

k6 동시성 테스트에서는 동일 Payment 승인 요청과 결제 승인·취소가 동시에 들어오는 상황을 검증했다.   
특히 서로 다른 트랜잭션이 같은 자원을 다른 순서로 Lock하면 deadlock이 발생할 수 있으므로   
전체 처리에서 Lock 획득 순서를 일관되게 유지해야 한다는 점을 확인했다.

또한 Redis는 DB 트랜잭션과 함께 rollback되지 않기 때문에   
DB rollback 가능성이 남아 있는 상태에서 Redis 재고를 먼저 복구하면 DB와 Redis 상태가 어긋날 수 있다.   
DB commit 이후 Redis 재고를 복구하도록 처리 시점을 조정해 정합성 문제를 해결했다.

## 실습 및 과제

> Toss Payments Webhook 실제 연동 검증

`PAYMENT_STATUS_CHANGED` Webhook을 수신하면 `paymentKey`로 Toss의 실제 결제 정보를 다시 조회하고 Webhook의 주문 정보와 일치하는지 검증하도록 했다.

Toss 상태에 따라 `DONE`은 결제·구매 완료, `CANCELED`는 취소와 재고 복구, `ABORTED`는 결제 실패, `EXPIRED`는 결제 만료로 보정하고   
`READY`, `IN_PROGRESS` 같은 중간 상태는 별도로 변경하지 않도록 했다.

Webhook과 사용자 취소·timeout이 동시에 실행될 수 있어 Purchase를 비관적 락으로 다시 조회하고 현재 Payment와 Purchase 상태를 확인한 뒤 처리하도록 했다.

이미 최종 상태인 경우에는 동일 Webhook이 다시 전달되어도 상태를 다시 변경하거나 Redis 재고를 중복 복구하지 않도록 처리했다.

로컬에서 이미 `CANCELED`인데 Toss의 실제 상태가 `DONE`인 경우에는 Purchase를 다시 완료 상태로 되돌리지 않고 Toss 결제만 보상 취소하도록 했다.

ngrok으로 로컬 서버를 외부에 노출한 뒤 Toss 개발자센터에 실제 Webhook URL을 등록해 요청을 직접 수신했다.

Webhook의 `createdAt`이 offset 없는 날짜 형식으로 전달됐지만 DTO를 `OffsetDateTime`으로 선언해 역직렬화 과정에서 500이 발생했다.   
실제 payload에 맞춰 `LocalDateTime`으로 수정한 뒤 정상적으로 `200 OK`가 반환되는 것을 확인했다.

500 응답 이후 Toss가 동일 Webhook을 재전송하는 것도 직접 확인했고, 수정 이후 재전송 요청과 신규 결제 Webhook이 모두 정상 처리되는 것을 검증했다.

> k6 Case1 성능 측정 구간 확인

Case1 `missing-before-app-or-after-settle-window`를 통해 애플리케이션 기동 전이나 테스트 종료 후 안정화 구간 밖에서 발생한 요청은   
측정 결과에서 누락될 수 있다는 점을 확인했다.

성능 테스트에서는 단순히 k6 실행 시간만 보는 것이 아니라 애플리케이션이 실제 요청을 받을 준비가 된 시점과   
테스트 종료 후 남은 요청이 처리되는 시간까지 고려해야 한다는 점을 정리했다.

> k6 Case6 결제 승인 동시성 제어

동일 Payment에 50개의 승인 요청이 동시에 들어오는 상황을 테스트했다.

초기에는 여러 요청이 동시에 승인 흐름에 진입할 수 있는 문제가 확인돼 Payment 조회에 비관적 락을 적용했다.

결제 시작과 완료 과정의 Lock 획득 순서를 `Payment → Purchase`로 맞춘 뒤 다시 테스트했다.

수정 후에는 50건 중 1건만 정상 승인되고 나머지 요청은 이미 처리 중이거나 완료된 상태로 정상 거절되는 것을 확인했다.

최종적으로 Purchase는 `PURCHASED`, Payment는 `DONE`, Redis 재고는 99로 유지되어 중복 승인으로 인한 추가 재고 차감이 발생하지 않았다.

> k6 Case7 결제 승인·취소 동시성 제어

동일 구매에 대해 결제 승인과 구매 취소 요청이 동시에 발생하는 상황을 테스트했다.

최초 테스트에서는 승인 흐름이 `Payment → Purchase`, 취소 흐름이 `Purchase → Payment` 순서로 Lock을 획득하면서 PostgreSQL deadlock이 발생했다.

한 요청이 500 오류로 실패했고 DB에는 Purchase `PURCHASED`, Payment `DONE`이 남았지만   
Redis 재고는 100으로 복구되어 DB와 Redis가 불일치하는 문제도 확인했다.

원인을 해결하기 위해 구매 취소에서도 Payment를 먼저 잠금 조회하도록 변경해 전체 Lock 획득 순서를 `Payment → Purchase`로 통일했다.

또한 취소 트랜잭션 내부에서 Redis 재고를 바로 복구하면 DB가 rollback되더라도 Redis 변경은 되돌아가지 않는 문제가 있어   
DB transaction commit 이후에만 Redis 재고를 복구하도록 변경했다.

수정 후 다시 테스트한 결과 deadlock과 500 오류가 발생하지 않았고   
Purchase와 Payment가 모두 `CANCELED`, Redis 재고가 100으로 일관되게 유지되는 것을 확인했다.

> 동시성 변경에 따른 테스트 보완

Payment 조회에 비관적 락이 추가되면서 기존 테스트의 Repository mock과 검증도 잠금 조회 메서드를 기준으로 수정했다.

구매 취소에서도 Payment 잠금 조회 메서드를 사용하도록 테스트를 변경했다.

실제 코드에서 더 이상 호출하지 않는 `purchase.getId()` stubbing이 남아 Mockito의 `UnnecessaryStubbingException`이 발생했고,   
사용하지 않는 stubbing을 제거해 해결했다.

기존 취소 동시성 Case5와 Case6, Case7을 다시 실행해 재고가 중복 복구되지 않고 승인·취소 경쟁 상황이 정상적으로 처리되는 것을 확인했다.

마지막으로 전체 테스트를 실행해 변경된 동시성 처리로 기존 기능에 회귀가 없는지 확인했고 `BUILD SUCCESSFUL`로 통과했다.

## 헷갈렸던 점

Webhook payload의 날짜 필드를 `OffsetDateTime`으로 받아도 되는지 헷갈렸다.
실제 Toss Webhook의 `createdAt`은 offset이 포함되지 않은 형식으로 전달돼 현재 DTO에서는 역직렬화가 실패했다.   
외부 API의 실제 payload 형식에 맞는 타입을 사용해야 했다.

Webhook 처리에 실패하면 Toss에서 요청이 끝나는지도 궁금했다.  
실제 500 응답 이후 동일 Webhook이 다시 전달되는 것을 확인하면서   
Webhook Handler 자체도 동일 요청의 재처리를 고려해 멱등하게 작성해야 한다는 점을 확인했다.

동일 Payment 승인 요청이 동시에 들어와도 상태 검증만으로 막을 수 있는지 고민했다.  
여러 트랜잭션이 상태를 변경하기 전에 동시에 같은 상태를 읽을 수 있기 때문에 Payment 자체를 비관적 락으로 조회해 한 요청씩 처리하도록 해야 했다.

비관적 락을 사용하기만 하면 deadlock이 발생하지 않는지도 헷갈렸다.  
각 흐름에서 여러 Row를 서로 다른 순서로 Lock하면 서로 상대방의 Lock을 기다리는 deadlock이 발생할 수 있으므로   
전체 유스케이스에서 Lock 획득 순서를 통일해야 했다.

결제 승인·취소 경쟁에서 DB가 rollback되면 Redis 재고 복구도 함께 취소되는지 다시 확인했다.  
Redis는 PostgreSQL 트랜잭션에 참여하지 않으므로 트랜잭션 내부에서 먼저 Redis를 변경하면 DB rollback 이후에도 Redis 값은 그대로 남는다.

따라서 DB transaction이 실제 commit된 이후 Redis 재고를 복구하도록 실행 시점을 조정하는 것이 필요했다.

k6 테스트에서 API 요청 결과만 정상이라면 동시성 문제가 해결됐다고 볼 수 있는지도 확인했다.  
응답 코드뿐 아니라 최종 Purchase·Payment 상태와 Redis 재고까지 함께 확인해야 실제 정합성이 유지되는지 판단할 수 있었다.

## 오늘 느낀 점

오늘은 Webhook을 실제 Toss 환경에서 받아보고 결제 승인·취소 동시성 테스트까지 진행하면서,   
단위 테스트만으로는 확인하기 어려운 문제들이 실제 환경에서 드러난다는 점을 느꼈다.

특히 Case7에서 DB의 Purchase와 Payment는 결제 완료인데 Redis 재고만 복구되는 상황을 직접 확인하면서   
DB 트랜잭션과 Redis 작업의 경계를 어디에 두는지가 정합성에 큰 영향을 준다는 점을 이해했다.

비관적 락도 단순히 추가하면 되는 것이 아니라 여러 기능이 같은 데이터를 어떤 순서로 잠그는지까지 통일해야 deadlock을 방지할 수 있었다.

Webhook 역시 정상 요청만 처리하는 것이 아니라 외부 시스템의 재전송, 내부 timeout과 사용자 취소처럼 동시에 발생할 수 있는 흐름까지 고려해야   
실제 상태 보정 기능으로 사용할 수 있다는 점을 확인했다.

실제 테스트에서 발생한 문제를 Lock 순서와 Redis 복구 시점까지 따라가며 원인을 찾고,  
같은 Case를 다시 실행해 문제가 해결된 것을 직접 확인할 수 있어 동시성 처리 과정을 더 명확하게 이해할 수 있었다.
