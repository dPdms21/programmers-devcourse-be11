## 오늘 배운 내용

오늘은 전날 구성한 MSA 프로젝트를 실제로 실행하면서 기존 인증·인가와 게시판 기능을 `auth-service`, `board-service`로 분리하는 과정을 실습했다.

서비스를 분리하면 코드만 나누는 것이 아니라 각 서비스의 실행 환경, 설정, DB 소유권과 서비스 간 데이터 조회 방식까지 함께 분리해야 한다는 점을 확인했다.

특히 Config Server를 사용하더라도 필수 설정이 존재하지 않으면 애플리케이션이 정상 동작하지 않을 수 있고,   
`DB per service` 구조에서는 다른 서비스의 데이터를 FK로 직접 연결하기보다 식별자만 저장하고 필요한 정보는 API를 통해 조회해야 한다는 점을 정리했다.

이후 이력서 작성 특강에서는 프로젝트의 모든 기능과 기술을 나열하기보다 백엔드 직무와 직접 연결되는 경험을 선별하고,   
실제로 내가 담당한 문제와 해결 과정, 측정 결과를 중심으로 작성해야 한다는 점을 배웠다.

특히 Gudit에서 동시성 문제를 직접 재현하고 Lock 순서와 Redis 처리 시점을 변경해 결과를 개선한 경험처럼   
`문제 상황 → 원인 분석 → 해결 → 수치로 검증한 결과`가 드러나는 사례가 이력서에서 중요한 경험이 된다는 점을 확인했다.

## 실습 및 과제

> MSA 서비스 실행

`config-service → auth-service / board-service → edge-service → web-service` 순서로 각 서비스를 실행하며 전체 구조를 확인했다.

각 서비스는 별도 포트에서 실행되고,   
사용자 화면은 `web-service(:8080)`에서 접근하지만 실제 요청은 Gateway와 각 마이크로서비스로 전달되는 구조를 확인했다.

> auth-service 분리

기존에 학습했던 Spring Security, JWT, OAuth2 로직을 새로 구현하는 것이 아니라 인증 서비스의 독립된 책임으로 분리했다.

로그인·회원가입, access/refresh token 처리, `UserDetailsService`, Kakao OAuth2 사용자 정보 처리 등을 `auth-service`에서 담당하고,   
`web-service`에서는 `AuthClient`를 이용해 인증 서비스를 호출하도록 구성했다.

Config Server 연동 이후 `Client id of registration 'kakao' must not be empty` 오류가 발생하면서   
중앙 설정이 실제 서비스에 주입되는 흐름도 확인했다.

`auth-service`의 `spring.config.import`를 통해 `config-service(:8888)`의 `auth-service.yml`을 읽기 때문에   
Config Server가 실행되지 않으면 Kakao `client-id` 같은 설정을 가져올 수 없다.

`optional:`을 사용하더라도 Config Server 연결 실패 자체만 선택적으로 처리할 뿐,   
이후 Bean 생성에 필요한 필수 설정이 없다면 애플리케이션은 다시 실패할 수 있다는 점을 확인했다.

> board-service 분리

게시글과 댓글을 `board-service`의 독립된 책임으로 분리하고 `Board`, `Comment` 엔티티와 JPA Repository, Security 및 예외 처리 기본 구조를 구성했다.

인증 서비스와 게시판 서비스는 각각 `board_auth`, `board_app` DB를 사용하는 `DB per service` 구조로 분리했다.

`board.user_id`에는 `auth-service` 사용자의 식별자를 저장하지만 서로 다른 서비스의 DB 사이에는 FK를 연결하지 않고 느슨하게 참조하도록 했다.

게시글 작성자 이름과 같이 사용자 상세 정보가 필요하면 `auth-service`를 API로 호출해   
데이터를 조합하는 API Composition 방식을 사용할 수 있다는 점을 확인했다.

반대로 `Board`와 `Comment`처럼 동일한 `board-service`가 소유하는 데이터 사이에는 FK를 유지할 수 있다는 차이를 확인했다.

> 백엔드 이력서 작성 기준 정리

백엔드 이력서에서는 프로젝트에 사용한 기술 전체와 내가 실제로 깊게 다룬 기술을 구분해야 한다는 점을 정리했다.

상단 기술 스택에는 면접에서 사용 이유와 동작 원리를 설명할 수 있는 기술을 우선 배치하고,   
프로젝트의 `사용 언어 및 개발 환경`에는 전체 기술 스택을 작성하더라도 `담당 구현 기능`에는 실제 내가 맡은 내용만 작성하는 것이 적절했다.

Gudit은 구매·결제 도메인과 외부 결제 시스템 정합성, 동시성 제어 경험을 핵심으로 정리했다.

동일 Payment에 50건의 승인 요청이 동시에 발생했을 때 초기에는 여러 요청이 승인 흐름에 진입했지만,   
Payment 비관적 락을 적용하고 Lock 순서를 `Payment → Purchase`로 통일한 뒤 1건만 성공하고 49건은 정상 거절되는 것을 확인했다.

결제 승인과 구매 취소의 경합에서는 서로 다른 Lock 순서로 Deadlock과 `COMMON_500`, DB와 Redis 상태 불일치가 발생했다.

Lock 순서를 통일하고 Redis 재고 복구를 DB commit 이후로 변경한 뒤 checks를 50%에서 100%로 개선하고   
경합 처리 시간을 약 3.8초에서 0.68초까지 줄인 결과를 이력서의 핵심 문제 해결 사례로 활용할 수 있다는 점을 정리했다.

> 프로젝트별 경험 선별

Gudit에서는 Purchase·Payment 백엔드와 Frontend 전체 구현·API 연동을 담당했지만,   
다른 팀원이 구현한 Timeout Scheduler 같은 기능은 내 구현처럼 작성하지 않도록 구분했다.

Frontend 전체 구현은 프로젝트 완성에 기여한 경험이지만 백엔드 이력서의 핵심 기술 소재는 아니므로   
`담당 구현 기능`보다 `성과 및 기여`에서 전체 연동 경험으로 보여주는 방향이 적절했다.

S:ote 역시 전체 기능을 모두 나열하기보다 Spring Security·JWT 인증, 사용자별 데이터 접근 제어,   
Spring Boot와 FastAPI AI 서버의 데이터 흐름, 감정 기반 상태 관리와 FCM 알림 등 백엔드 경험을 우선 배치하기로 했다.

AI 추천 결과가 반복되거나 편향되는 문제를 Prompt와 후처리 로직으로 개선한 경험, Render Sleep 상태로 첫 분석 요청이 누락되는 문제를   
Wake 엔드포인트와 FCM 알림으로 보완한 경험도 문제 해결 사례로 활용할 수 있다는 점을 정리했다.

프로젝트는 Gudit을 가장 강한 경험으로 두고 S:ote와 진행 중인 Chaerok을 주요 프로젝트로 활용하며,   
프로젝트마다 면접 질문으로 연결될 수 있는 핵심 경험 3~4개 정도를 선별하는 방향으로 정리했다.

> 교육 · 활동 · 연구 경험 정리

프로그래머스 데브코스는 Java, Spring Boot, JPA, Spring Security, RDBMS 기반 백엔드 개발과 팀 프로젝트 경험을 중심으로 작성하기로 했다.

9oorm × kakao 9oormthonUNIV 백엔드 스터디는 주차별 학습 내용을 정리해 팀원에게 설명하고 질의응답한 경험과   
Spring Boot, JPA, Spring Security, JWT 실습 경험을 중심으로 정리했다.

SEASONTHON 해커톤은 Backend Developer로 Worknet Open API 기반 채용 공고 수집·조회,   
자기소개서, 아카이브와 AI 피드백 조회 API를 구현한 경험을 활용하기로 했다.

S:ote의 2025 캡스톤 경진대회 수상과 멀티모달 행동 인식 연구 논문도 별도의 수상·연구 경험으로 정리할 수 있다는 점을 확인했다.

## 헷갈렸던 점

Config Server 설정에 `optional:`을 사용하면 Config Server가 실행되지 않아도 `auth-service`가 항상 정상적으로 실행되는지 헷갈렸다.

`optional:`은 Config Server 연결 자체가 실패해도 즉시 종료하지 않도록 하는 설정이지만,   
Kakao `client-id`처럼 이후 Bean 생성에 반드시 필요한 값까지 없어도 된다는 의미는 아니었다.

`DB per service` 구조에서 `board.user_id`와 사용자 테이블을 FK로 연결해도 되는지도 다시 확인했다.

서로 다른 서비스가 각자의 DB를 소유한다면 DB 레벨의 FK로 직접 결합하지 않고   
사용자 식별자만 저장한 뒤 필요한 정보는 서비스 간 API를 통해 조회해야 서비스 간 결합도를 낮출 수 있다.

이력서의 기술 스택에 프로젝트에서 한 번이라도 사용한 기술을 모두 적어도 되는지도 고민했다.

프로젝트 전체 환경에는 사용한 기술을 표시할 수 있지만,   
이력서 상단의 핵심 기술 스택에는 사용 이유와 동작 원리, 문제 해결 경험을 설명할 수 있는 기술을 우선 배치하는 것이 적절했다.

프로젝트에서 팀이 구현한 기능을 어느 범위까지 내 담당 경험으로 적어야 하는지도 다시 구분했다.

서비스 전체 기능과 내가 직접 구현하거나 주도한 부분은 분리해야 하며, 다른 팀원이 구현한 기능을 내가 수행한 것처럼 작성하지 않아야 한다.

이력서에 프로젝트의 기능을 많이 넣는 것이 좋은지도 고민했다.

단순 CRUD나 기능 목록을 늘리기보다 직무와 직접 연결되고 면접에서 문제 상황과 해결 과정을 깊게 설명할 수 있는 경험을 3~4개 정도 선별하는 것이 더 적절했다.

성과를 보여주기 위해 수치를 꼭 만들어야 하는지도 다시 확인했다.

측정하지 않은 개선율을 추정해서 작성하는 것이 아니라 실제 테스트에서 확인한 `50건 중 1건 성공·49건 정상 거절`,   
`checks 50% → 100%`, `3.8초 → 0.68초`처럼 재현 가능한 결과만 사용해야 했다.

## 오늘 느낀 점

MSA 실습에서는 기존에 구현했던 JWT나 게시판 기능 자체보다 하나의 애플리케이션에 있던 책임을 서비스별로 분리했을 때   
무엇이 달라지는지를 확인하는 것이 더 중요했다.

인증과 게시판을 분리하자 설정과 DB도 각 서비스의 책임에 맞게 나누어야 했고,   
다른 서비스의 데이터를 직접 FK로 연결할 수 없기 때문에 API를 통해 조합해야 하는 등 모놀리식 구조에서는 크게 신경 쓰지 않았던 문제들이 새롭게 생겼다.

이력서 특강에서는 프로젝트에서 많은 기능을 구현했다는 사실보다 어떤 문제를 직접 발견하고 해결했으며   
그 결과를 어떻게 검증했는지가 더 중요한 경험이 된다는 점을 다시 확인했다.

특히 Gudit의 동시성 테스트처럼 처음부터 계획했던 기능보다 실제 경합 상황을 재현하면서 Deadlock과 데이터 불일치를 발견하고,   
원인을 분석해 Lock 순서와 Redis 처리 시점을 변경한 경험이 백엔드 문제 해결 역량을 보여주기에 더 적절하다고 느꼈다.

앞으로 프로젝트를 진행할 때도 구현한 기능만 기록하기보다 발생한 문제와 확인한 로그·수치, 시도한 방법과 최종 결과를 함께 남겨   
이후 이력서와 포트폴리오에서 실제 근거로 활용할 수 있도록 해야겠다.
