## 오늘 배운 내용

오늘은 Kotlin 기본 문법을 복습하고, MSA에서 인증과 게시판 서비스를 분리한 이후 JWT 인증과 서비스 간 데이터 조회가 어떻게 동작하는지 정리했다.

MSA에서는 서비스가 분리되더라도 기존 비즈니스 로직 자체가 완전히 달라지는 것은 아니지만,   
각 서비스가 자신의 데이터와 책임을 소유하게 되면서 다른 서비스의 정보가 필요할 때 API 통신이 추가된다는 점을 확인했다.

JWT 역시 `auth-service`에서 발급한 뒤 모든 요청을 다시 `auth-service`에서 검증하는 것이 아니라,   
인증이 필요한 각 서비스가 전달받은 토큰을 직접 검증하고 실제 사용자 상세 정보가 필요할 때만 `auth-service`를 호출한다는 차이를 정리했다.

이후 Repoary에서는 기존 커밋 분석 결과를 재사용해 TIL Markdown 초안을 생성하고 저장·조회·수정할 수 있는 백엔드 API를 구현했다.

자동 생성 기능에서는 실제 커밋으로 확인할 수 있는 내용만 생성하고, 질문이나 감상처럼 분석 데이터만으로 알 수 없는 내용은 임의로 만들어내지 않는 것이 중요했다.   
또한 사용자 수정 내용을 보호하기 위해 같은 저장소·날짜의 TIL 중복 생성을 차단하고, API 오류도 상황에 맞는 HTTP 상태 코드로 구분했다.

## 실습 및 과제

> Kotlin 기본 타입 실습

Kotlin의 `val`과 `var` 차이를 다시 확인했다.

`val`은 한 번 할당한 값을 다시 변경할 수 없고, `var`는 값을 변경할 수 있다.

Kotlin은 기본적으로 `null`을 허용하지 않으며 null이 필요한 경우 `String?`처럼 타입 뒤에 `?`를 붙여 nullable 타입으로 선언한다.

Nullable 값에는 safe call `?.`을 사용해 null이 아닐 때만 이후 연산을 실행할 수 있고,   
Elvis operator `?:`를 이용해 null인 경우 사용할 기본값을 지정할 수 있다는 점을 정리했다.

> MSA 사용자 정보와 게시판 조회 실습

기존 애플리케이션을 `auth-service`, `board-service`, `web-service`, `edge-service`, `config-service`로 분리한 이후   
서비스 간 요청과 데이터 조회 흐름을 다시 확인했다.

서비스와 DB가 분리되면서 `board-service`에서 `auth-service`의 Repository나 DB를 직접 조회하지 않고,   
게시글 작성자의 실제 사용자 정보가 필요하면 API를 통해 요청해 데이터를 조합해야 한다.

게시글과 댓글처럼 `board-service` 내부에서 관리하는 데이터는 기존 `Controller → Service → Repository → DB` 구조를 그대로 유지하고,   
다른 서비스가 소유한 데이터가 필요한 경우에만 서비스 간 통신이 추가된다는 점을 구분했다.

게시판 검색에서는 `BoardRepositoryCustom`과 `BoardRepositoryImpl`을 이용한 QueryDSL Custom Repository 구조도 확인했다.

이는 MSA 때문에 필요한 구조라기보다 여러 검색 조건을 동적으로 처리하기 위한 JPA/QueryDSL 방식이며, 서비스 분리와 별개의 개념이라는 점을 정리했다.

> 2차 프로젝트 결과 및 피드백 확인

Gudit이 2차 프로젝트 최우수팀으로 선정된 결과를 확인하고, 강사님과 FT님의 피드백을 정리했다.

Redis와 RDB 사이의 정합성 문제를 여러 상황으로 나누어 대응하고, 동시성·성능 테스트를 통해 문제를 재현한 뒤 원인까지 분석한 과정이 긍정적으로 평가됐다.   
특히 결제 승인과 구매 취소 경쟁에서 발생한 Deadlock의 원인을 락 획득 순서 차이로 좁히고 수정 후 다시 검증한 점이 의미 있는 문제 해결 과정으로 평가됐다.

반면 실제 운영 관점에서는 알림과 장애 대응, 정합성 보완 구조로 확장하고,   
복잡해진 로직을 분리해 유지보수성을 높일 필요가 있다는 피드백도 확인해 3차 개선 방향과 연결해 정리했다.

> JWT 인증과 Security 흐름 복습

`auth-service`는 로그인 시 사용자 정보를 검증하고 JWT를 발급하지만, 이후 `board-service`의 모든 요청을 대신 인증하지는 않는다.

`board-service`에도 `TokenProvider`, `TokenAuthenticationFilter`, `SecurityConfig`가 존재하며 전달받은 JWT를 자체적으로 검증한다.

매 요청마다 `auth-service`에 토큰 검증을 요청하면 네트워크 호출이 증가하고   
인증 서비스에 대한 의존성이 커지므로 각 서비스가 공통 Secret을 이용해 토큰을 검증하는 구조를 사용한다.

반면 사용자 이름이나 상세 프로필처럼 JWT에 포함되지 않은 실제 사용자 데이터가 필요한 경우에는 `auth-service` API를 호출한다.

> Repoary 분석 작업 시각 KST 표시 오류 수정

Repoary에서 분석 작업 시간을 표시할 때 UTC와 KST 기준이 맞지 않는 문제를 수정했다.

분석 대상 날짜와 실제 분석 작업 생성 시각은 서로 다른 의미를 가지며, 사용자에게 보여주는 작업 시각은 한국 시간 기준으로 일관되게 표현되어야 한다는 점을 확인했다.

`GET /analysis-jobs`에 표시되는 날짜 역시 GitHub에 커밋이 존재하는 모든 날짜가 아니라   
Repoary에서 실제 분석 작업을 실행해 `analysis_jobs`에 저장된 날짜라는 점을 다시 구분했다.

> Repoary TIL 초안 생성 및 저장

완료된 `analysis_jobs`의 `StoredAnalysisResult`를 재사용해 GitHub 커밋을 다시 조회하거나 재분석하지 않고 TIL Markdown 초안을 생성하도록 구현했다.

TIL 저장을 위해 `til_documents`와 `TilDocument`를 추가하고 저장소, 분석 작업, 학습 날짜, 제목, Markdown 내용과 상태를 저장하도록 구성했다.

같은 저장소와 날짜에 TIL을 다시 생성하면 사용자가 수정한 문서를 덮어쓸 수 있어 중복 생성을 차단하고 기존 문서가 있는 경우 `409 Conflict`로 처리했다.

저장된 커밋의 `commitType`, `scope`, `categories`, 변경 파일 정보를 이용해   
`lectures`, `practice`, `assignments`, `codingtest` 단위로 학습 내용을 분류했다.

링크는 변경 파일 하나가 아니라 실제 학습 단위를 기준으로 생성하도록 했다.   
예를 들어 `practice/msa/board-service/...`가 변경돼도 `practice/msa`를 가리키고,   
코딩테스트처럼 문제 파일 자체가 학습 단위인 경우에는 해당 파일을 직접 연결한다.

커밋 메시지의 날짜는 TIL 제목과 중복돼 제거하고, `committedAt` 기준으로 정렬해 실제 커밋 순서가 Markdown에도 유지되도록 했다.

또한 커밋 분석 데이터만으로 사용자가 실제로 헷갈린 점이나 느낀 점까지 알 수는 없기 때문에   
`헷갈렸던 점`, `오늘 느낀 점`, `추가 학습 예정`은 임의로 생성하지 않도록 했다.

> TIL 조회·수정 및 예외 처리

완료된 분석 결과를 이용한 TIL 생성 외에도 날짜별 조회, 문서 ID 상세 조회, Markdown 수정 API를 구현했다.

Swagger 검증 중 인증된 상태에서 TIL 중복 생성이나 존재하지 않는 문서 조회가 기대한 상태 코드와 다르게 처리되는 문제를 확인했다.

처음에는 Security 설정 문제를 의심했지만 TIL API 역시 기존 `.authenticated()` 정책의 적용을 받고 있었고,   
실제 문제는 서비스 예외를 HTTP 상태로 변환할 전역 예외 처리 구조가 없다는 점이었다.

`NotFoundException`, `ConflictException`, `ErrorResponse`, `GlobalExceptionHandler`를 추가해 중복 생성은 `409 Conflict`,   
존재하지 않는 TIL은 `404 Not Found`, 잘못된 입력은 `400 Bad Request`, 비정상적인 저장 분석 결과는 `500 Internal Server Error`로 구분했다.

Swagger에서 실제 분석 결과를 이용해 TIL 생성·조회·수정까지 확인했고, 수정 시 `createdAt`은 유지되고 `updatedAt`만 변경되는 것도 검증했다.

> TIL 생성 테스트 보완

`TilServiceTest`, `TilMarkdownGeneratorTest`를 추가해 TIL 생성·중복 방지·조회·수정·접근 제어와 Markdown 생성 규칙을 검증했다.

Markdown에서는 날짜 제거, `practice/msa` 폴더 링크, 코딩테스트 파일 직접 링크, 근거 없는 섹션 미생성, 커밋 시간순 정렬을 확인했다.

또한 `study(kotlin):`이 기존 기본 커밋 규칙에 없어 `commitType`과 `scope`가 `null`로 저장되는 문제를 발견해   
`study(kotlin): → study / kotlin` 규칙을 추가하고 관련 테스트도 수정했다.

## 헷갈렸던 점

MSA에서 `auth-service`가 이미 JWT를 확인하는데 왜 `board-service`에도 JWT 관련 클래스가 필요한지 헷갈렸다.

`auth-service`는 로그인과 토큰 발급을 담당하고, 이후 각 요청의 인증은 해당 요청을 처리하는 서비스가 JWT를 직접 검증한다.   
매 요청마다 `auth-service`로 토큰 검증 요청을 보내지 않고 각 서비스가 독립적으로 인증 상태를 복원하기 위한 구조라는 점을 이해했다.

JWT 검증과 사용자 정보 조회의 경계도 처음에는 헷갈렸다.

토큰의 서명과 만료 여부, 사용자 식별자와 권한처럼 JWT 자체에 있는 정보는 서비스가 직접 검증할 수 있지만,   
사용자 이름 등 실제 DB 데이터가 필요하면 해당 데이터를 소유한 `auth-service`를 호출해야 한다.

TIL을 같은 날짜에 다시 생성할 때 기존 내용을 갱신하는 방식이 나은지도 고민했다.

사용자가 자동 생성된 초안을 이미 직접 수정했을 수 있기 때문에   
자동 재생성으로 기존 Markdown을 덮어쓰기보다 중복 생성을 차단하고 명시적인 수정 API만 제공하는 것이 안전했다.

Swagger에서 예상하지 못한 상태 코드가 반환돼 Security 설정에 TIL 경로를 따로 추가해야 하는지도 확인했다.

이미 비공개 API 전체가 인증을 요구하고 있었기 때문에 경로 설정 문제가 아니었고,   
실제 원인은 도메인 예외를 HTTP 상태 코드로 변환하는 전역 예외 처리가 없었던 것이었다.

## 오늘 느낀 점

오늘 MSA 실습에서는 인증 서비스와 게시판 서비스를 분리하면서 동일한 JWT 로직이 여러 서비스에 존재하는 이유와,   
토큰 검증과 실제 사용자 데이터 조회가 서로 다른 책임이라는 점을 이전보다 명확하게 이해할 수 있었다.

MSA에서는 코드 자체보다 서비스별 책임과 데이터 소유권을 먼저 구분해야 하고,   
서비스가 나뉘면 기존에 내부 호출로 끝나던 부분이 네트워크 통신이나 독립적인 인증 처리로 바뀐다는 점이 중요했다.

Repoary에서는 실제로 작성해왔던 TIL 형식을 자동화 기능으로 옮기면서   
단순히 Markdown 문자열을 만드는 것보다 어떤 정보를 근거로 생성할 수 있는지 경계를 정하는 것이 더 중요했다.

특히 커밋 분석 데이터만으로 알 수 없는 `헷갈렸던 점`이나 `오늘 느낀 점`을 억지로 생성하지 않고  
비워두는 방향을 선택하면서 자동화 기능에서도 정확성과 신뢰성이 결과의 양보다 중요하다고 느꼈다.

또한 중복 생성으로 사용자 수정 내용을 덮어쓰지 않도록 정책을 정하고,   
잘못된 요청을 `404`, `409`처럼 의미에 맞는 상태 코드로 구분하는 과정에서 단순 기능 구현뿐 아니라 실제 사용자가 TIL을 생성하고 수정하는 흐름까지 생각할 수 있었다.

오늘로 Repoary의 TIL 초안 생성 백엔드까지 구현하면서 기존 GitHub 분석 결과가 실제 사용자가 활용할 수 있는 학습 문서로 이어지는 흐름을 완성했다.   
다음에는 프론트에서 생성·편집·미리보기와 복사 기능을 연결하면서 실제 사용 흐름을 마무리해야겠다.
