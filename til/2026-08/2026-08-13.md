## 오늘 배운 내용

오늘은 최신 `dev`를 반영해 Purchase 영역을 팀의 공통 예외 처리와 재고 구조에 맞추고, Purchase와 Payment를 실제 구매 흐름으로 연결했다.

Purchase에서는 구매 흐름을 담당하고 재고와 판매 규칙은 `InventoryService`에 위임하도록 책임을 정리했다.   
현재 RDB 방식에서는 재고 차감과 Purchase 저장이 같은 트랜잭션에 참여하므로 저장 실패 시 재고도 함께 롤백된다.

구매 상태는 결제 연동에 맞춰 생성 직후 `PENDING_PAYMENT`로 시작하고, Toss 결제 승인이 완료된 이후에만 `PURCHASED`로 변경하도록 분리했다.

외부 결제 API는 DB 트랜잭션에 함께 참여하지 않으므로 결제 승인과 내부 상태 변경을 하나의 긴 트랜잭션으로 묶지 않았다.   
DB 상태 변경은 짧은 트랜잭션으로 분리하고, 그 사이에 Toss 승인 API를 호출하는 구조로 정리했다.

결제 실패도 모두 같은 방식으로 처리하지 않았다.   
명확한 승인 거절은 Purchase 취소와 재고 복구까지 수행하고,   
실제 승인 여부를 알 수 없는 네트워크 오류나 PG 오류는 상태를 확정하지 않은 채 Toss 결제 상태를 다시 조회하도록 구분했다.

취소 정책은 판매 종료 이후에도 구매를 취소할 수 있도록 변경했다.   
재고는 복구하지만 판매 기간이 종료된 Sale은 다시 `ON_SALE` 상태로 열리지 않도록 기존 도메인 규칙을 유지했다.

## 실습 및 과제

> Purchase 공통 예외 처리 및 재고 구조 정리

Purchase 전용 개별 예외를 팀의 `BusinessException + ErrorCode` 구조에 맞춰 정리했다.

테스트에서도 단순히 `BusinessException`이 발생했는지만 확인하지 않고 예외가 가진 `ErrorCode`를 검증해 실제 실패 원인을 구분하도록 수정했다.

`PurchaseService`에서 판매 상태, 구매 수량과 재고 부족 검증을 반복하지 않고 `InventoryService.decreaseStock()`에 재고 관련 책임을 위임했다.

현재 RDB 기반 Inventory는 Sale을 비관적 락으로 조회한 뒤 판매 가능 여부와 수량을 검증하고 재고를 차감한다.   
Purchase에서는 이를 호출해 구매 흐름만 조합하도록 역할을 나눴다.

> 구매 취소 정책 및 테스트 변경

기존에는 판매 종료 이후 취소를 막았지만, 정책을 변경해 판매 종료 후에도 취소할 수 있도록 했다.

취소 시 `InventoryService.restoreStock()`으로 재고를 복구하고 Purchase를 `CANCELED`로 변경한다.

판매 기간이 이미 종료된 경우 재고 수량은 증가하지만 Sale 내부의 기간 검증으로 다시 판매 중 상태로 변경되지는 않는다.

정책 변경에 맞춰 기존 취소 실패 테스트를 성공 테스트로 수정하고, 사용하지 않는 Mockito stubbing을 제거했다.

> PostgreSQL 포트 충돌 해결

Docker PostgreSQL 내부에서는 정상 접속되지만 Windows에서 인증이 실패하는 문제를 확인했다.

`netstat`으로 확인한 결과 Docker PostgreSQL과 Windows에 설치된 PostgreSQL 서비스가 모두 5432 포트를 사용하고 있었다.

Windows PostgreSQL 서비스를 중지해 Docker PostgreSQL만 해당 포트를 사용하도록 한 뒤 정상적으로 연결했다.

뒤이어 발생한 Hibernate Dialect 오류도 별도의 Dialect 설정 문제가 아니라 datasource 연결 실패에 따른 연쇄 오류였다는 점을 확인했다.

> Purchase와 Payment 실제 연동

Purchase 생성 시 RDB 재고를 먼저 차감하고 `Purchase(PENDING_PAYMENT)`와 `Payment(READY)`를 함께 생성하도록 연결했다.

Purchase 응답에는 서버가 생성한 `orderId`를 전달하고,   
이후 Toss 결제 인증이 완료되면 발급받은 `paymentKey`와 함께 결제 승인 API를 호출하도록 흐름을 구성했다.

Purchase의 `purchasedAt`은 row 생성 시점이 아니라 실제 결제 승인이 완료돼 구매가 확정된 시점에 기록하도록 변경했다.

Payment는 `READY → IN_PROGRESS → DONE` 상태로 전환하고, 최종 승인 이후 `Purchase.complete()`를 호출해 Purchase를 `PURCHASED`로 변경한다.

> Payment 트랜잭션 분리

처음에는 `PaymentService` 내부에서 같은 클래스의 `@Transactional` 메서드를 호출했지만   
Spring Proxy의 self-invocation 문제로 트랜잭션이 적용되지 않았다.

이 때문에 Toss에서는 결제가 `DONE`인데 DB에서는 Payment가 `READY`, Purchase가 `PENDING_PAYMENT`로 남는 문제가 발생했다.

이를 해결하기 위해 `PaymentTransactionService`를 별도 Bean으로 분리했다.

결제 시작 상태 변경과 승인 완료 상태 변경을 각각 짧은 DB 트랜잭션으로 처리하고,   
그 사이에서 Toss 승인 API를 호출하도록 구성해 DB 상태가 정상적으로 반영되는 것을 확인했다.

> 결제 실패 및 취소 보상 처리

명확한 결제 승인 거절이 발생하면 Payment를 `FAILED`, Purchase를 `CANCELED`로 변경하고 재고를 복구하도록 했다.

반면 PG 내부 오류나 네트워크 타임아웃처럼 실제 승인 여부를 확정할 수 없는 경우에는   
Payment를 `IN_PROGRESS`, Purchase를 `PENDING_PAYMENT`로 유지하고 재고도 복구하지 않았다.

이 경우 동일 승인을 바로 다시 요청하기보다 `paymentKey`를 이용해 Toss의 실제 결제 상태를 조회하도록 처리했다.

결제 전 `PENDING_PAYMENT` 상태에서 구매를 취소하면 아직 실제 승인된 결제가 없으므로 Toss 취소 API 없이 Purchase만 취소하고 재고를 복구한다.

결제가 완료된 `PURCHASED` 상태에서는 Toss 결제 취소 이후 Payment와 Purchase를 모두 `CANCELED`로 변경하고 재고를 복구하도록 했다.

> 취소 후 재구매 정책 적용

기존 `UNIQUE(user_id, sale_id)` 제약은 취소된 Purchase까지 중복 구매로 판단해 재구매를 막았다.

정책을 활성 상태의 구매만 1인 1개로 제한하는 것으로 변경하고, 중복 조회에서도 `CANCELED` 상태를 제외하도록 수정했다.

DB에서도 전체 Unique Constraint 대신 `status <> 'CANCELED'`인 row에만 적용되는 partial unique index를 사용해   
`PENDING_PAYMENT`, `PURCHASED` 상태에서는 중복 구매를 막고 취소 이후에는 다시 구매할 수 있도록 했다.

## 헷갈렸던 점

Purchase와 Inventory에서 같은 판매 검증을 모두 해야 하는지 고민했다.  
구매 유스케이스를 담당하는 Purchase와 판매·재고 규칙을 담당하는 Inventory의 책임을 구분하고,   
재고와 판매 가능 여부 검증은 Inventory 쪽에 맡기는 것이 중복을 줄이는 구조라는 점을 정리했다.

RDB 기반 재고에서도 Purchase 저장 실패 시 별도 보상 처리가 필요한지 다시 확인했다.  
현재는 재고와 Purchase가 같은 PostgreSQL 트랜잭션에 참여하므로 전체가 함께 롤백된다.   
Redis로 전환한 이후에는 서로 다른 저장소가 되기 때문에 명시적인 재고 보상이 필요하다.

판매가 끝난 뒤 구매를 취소하면 복구된 재고 때문에 다시 판매가 열리는지도 확인했다.  
재고 수량은 복구되지만 `restoreStock()`에서 판매 기간을 함께 확인하기 때문에 종료된 판매는 다시 `ON_SALE`로 변경되지 않는다.

`@Transactional` 메서드를 같은 클래스 내부에서 호출해도 트랜잭션이 적용되는지 헷갈렸다.  
Spring의 기본 트랜잭션은 Proxy를 통과할 때 적용되므로 self-invocation에서는 기대한 트랜잭션이 시작되지 않을 수 있다.   
별도 Bean으로 분리해 Proxy를 거치도록 해야 했다.

결제 승인 요청이 오류를 반환하면 항상 결제가 실패한 것인지도 구분해야 했다.  
카드사 승인 거절처럼 실패가 명확한 경우에는 바로 보상할 수 있지만, 네트워크   
타임아웃이나 PG 내부 오류는 실제 승인 여부를 알 수 없으므로 상태를 확정하면 안 된다.

타임아웃이 발생했을 때 동일한 confirm을 바로 다시 호출하면 되는지도 고민했다.  
멱등키를 사용하면 재시도할 수 있지만 현재 구조에서는 먼저 결제 조회 API로 실제 PG 상태를 확인하는 방향을 선택했다.

결제 취소와 구매 취소도 항상 같은 동작을 하는 것은 아니었다.  
`PENDING_PAYMENT`에서는 실제 승인된 결제가 없으므로 Purchase 취소와 재고 복구만 필요하고,   
`PURCHASED`에서는 PG 취소까지 성공한 이후 내부 상태와 재고를 변경해야 한다.

기존 Unique Constraint를 유지하면 취소 이후에도 재구매가 불가능하다는 점도 확인했다.  
애플리케이션의 중복 검사뿐 아니라 DB 제약도 현재 비즈니스 정책과 동일한 기준으로 맞춰야 한다.

## 오늘 느낀 점

오늘은 Purchase와 Payment를 실제로 연결하면서 단순한 CRUD보다 상태와 정합성을 설계하는 일이 훨씬 중요하다는 점을 크게 느꼈다.

특히 Toss 승인 성공 여부와 우리 DB의 상태가 항상 동시에 변경되는 것이 아니기 때문에,   
외부 시스템을 사용하는 순간부터 단일 DB 트랜잭션만으로는 전체 흐름을 보장할 수 없었다.

명확한 실패와 결과를 알 수 없는 실패를 구분하고, 상태를 바로 확정할지 재조회할지 판단하는 것도 결제 처리에서 중요한 부분이었다.

또한 `PENDING_PAYMENT`, `PURCHASED`, `CANCELED`처럼 상태를 명확하게 나누면서 구매 생성 시점과 실제 구매 확정 시점의 의미도 더 분명해졌다.

현재는 RDB 기반 Purchase와 Payment의 1차 흐름을 연결했으므로 다음에는 테스트를 보강하고 Redis Inventory를 적용한 뒤,   
DB 트랜잭션으로 해결할 수 없게 되는 재고 보상과 멱등성 문제를 실제로 처리해 봐야겠다.
