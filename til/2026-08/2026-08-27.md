## 오늘 배운 내용

오늘은 Kotlin 특강을 통해 JVM 언어의 실행 구조와 Kotlin이 등장한 배경, Java와 비교되는 주요 특징을 학습했다.

Java와 Kotlin이 모두 JVM 위에서 동작하기 때문에 하나의 프로젝트에서 함께 사용할 수 있으며,   
기존 Java 코드를 필요한 부분부터 Kotlin으로 점진적으로 전환할 수 있다는 점을 확인했다.

Java → Kotlin 변환 실습에서는 IntelliJ의 자동 변환 기능을 사용할 수 있지만   
nullable 타입, Java getter/setter, Lombok과의 상호운용처럼 변환 이후 직접 확인해야 하는 부분이 있다는 점을 경험했다.

이후 MSA 실습에서는 `web-service`, `edge-service`, `config-service`, `auth-service`, `board-service`로 서비스를 분리하고   
각 서비스의 역할과 데이터 소유권을 나누는 구조를 구성했다.

Config Server에서는 로컬 `config-repo`를 이용해 공통 설정과 서비스별 설정을 중앙에서 관리하고,   
Secret이나 OAuth2 Client 정보는 환경변수로 분리해 관리하는 방식을 적용했다.

## 실습 및 과제

> Kotlin 기본 문법 및 JVM 구조

Java 소스 코드가 바이트코드로 컴파일된 뒤 JVM에서 실행되는 흐름과 Stack, Heap, Method 영역의 역할을 다시 확인했다.

`javap -c -v` 명령을 이용해 컴파일된 바이트코드를 확인하는 방법도 살펴봤다.

Kotlin에서는 `val`, `var`, 타입 추론, `when`, nullable 타입, safe call `?.`, Elvis operator `?:`, expression 형태의 함수와   
immutable/mutable collection 등의 기본 문법을 확인했다.

Null Safety를 언어 수준에서 지원하고 Java와 상호운용할 수 있다는 점이 Kotlin의 주요 특징이라는 점을 정리했다.

> Java → Kotlin 변환 실습

간단한 `User` 도메인과 Repository, Service, Controller, 테스트 코드를 Java로 구성한 뒤 `UserService`만 Kotlin으로 변환했다.

이를 통해 Java와 Kotlin 코드를 하나의 Spring 프로젝트에서 함께 사용할 수 있고, 전체 프로젝트를 한 번에 전환하지 않아도 된다는 점을 확인했다.

IntelliJ 자동 변환 과정에서 Java의 `Long`, `String` 타입이 `Long?`, `String?`처럼 nullable 타입으로 변환되면서   
`JpaRepository`가 요구하는 non-null 타입과 맞지 않는 문제가 발생했다.

`Optional<User?>` 역시 기존 Java 코드의 반환 타입과 일치하지 않아 nullable 여부를 직접 수정해야 했다.

Lombok으로 생성되는 setter를 Kotlin 컴파일러에서 정상적으로 인식하지 못해   
`setName`, `setEmail` 호출이나 Kotlin 프로퍼티 접근에서 컴파일 오류가 발생하는 경우도 확인했다.

자동 변환 기능은 완성된 코드를 만들어주는 기능이라기보다 변환 초안을 생성하는 도구로 보고,   
변환 후 타입과 Java-Kotlin 상호운용 부분을 직접 검증해야 한다는 점을 정리했다.

기존 프로젝트를 Kotlin으로 전환할 때는 테스트 코드를 이용해 변환 전후 동작이 동일한지도 확인하는 것이 중요했다.

> MSA 서비스 분리

하나의 애플리케이션을 역할에 따라 다음 서비스로 분리했다.

- `web-service`: Thymeleaf 화면과 Feign 기반 API 중계
- `edge-service`: Gateway를 이용한 단일 진입점과 서비스 라우팅
- `config-service`: 중앙 설정 관리
- `auth-service`: 인증, OAuth2, 사용자 정보 관리
- `board-service`: 게시판 기능

서비스별 데이터 소유권을 분리하는 `DB per service` 구조를 적용해 `auth-service`와 `board-service`가 서로 다른 DB를 사용하도록 구성했다.

이를 통해 서비스 분리는 코드 패키지를 나누는 수준이 아니라 기능과 데이터의 책임까지 분리해야 한다는 점을 확인했다.

> Config Server 구성

Config Server에서 `native` 프로필을 사용해 외부 Git 저장소 대신 로컬 `config-repo`의 설정 파일을 읽도록 구성했다.

`application.yml`에는 여러 서비스에서 공통으로 사용하는 설정을 두고,   
`auth-service.yml`처럼 `{service-name}.yml`에는 해당 서비스에 필요한 설정을 분리했다.

`curl.exe http://localhost:8888/auth-service/default` 요청을 통해 Config Server가 실제 설정을 정상적으로 반환하는지 확인했다.

> 환경변수 및 민감 정보 관리

실제 값은 환경변수로 분리하고 yml에는 `${JWT_SECRET_KEY}`, `${KAKAO_CLIENT_ID}`와 같은 placeholder만 남기는 방식으로 구성했다.

Spring Boot 자체는 `.env` 파일을 자동으로 읽지 않기 때문에   
MSA 루트에 공통 `.env`를 두고 IntelliJ EnvFile 설정을 이용해 각 서비스가 같은 파일을 참조하도록 했다.

> 서비스별 의존성 분리

`auth-service`는 Security, OAuth2 Client, JPA, MySQL 등의 의존성이 필요하지만,   
`board-service`는 OAuth2 로그인 자체를 수행하지 않으므로 OAuth2 Client가 필요하지 않다는 점을 구분했다.

서비스를 분리했다면 각 서비스가 실제 담당하는 기능에 필요한 의존성만 포함하는 것이 적절하다는 점을 확인했다.

또한 Spring Boot 4.1.1과 Spring Cloud 2025.1.3 환경에서는   
이전 Spring Boot 3 프로젝트와 의존성 이름이나 구성이 달라질 수 있다는 점도 확인했다.

## 헷갈렸던 점

Kotlin의 nullable 타입이 Java 코드와 자동으로 자연스럽게 호환되는지 헷갈렸다.

IntelliJ 자동 변환 과정에서 Java 타입이 nullable로 변환될 수 있고,   
`JpaRepository`나 기존 Java 메서드가 요구하는 타입과 맞지 않을 수 있기 때문에 변환된 타입을 그대로 사용하면 안 된다는 점을 확인했다.

Java에서 Lombok으로 생성한 getter/setter를 Kotlin에서도 그대로 사용할 수 있는지도 헷갈렸다.

Java 컴파일과 Kotlin 컴파일, Lombok의 코드 생성 시점 때문에   
Kotlin에서 Lombok이 생성하는 메서드를 정상적으로 인식하지 못하는 경우가 있어 상호운용 시 별도로 확인해야 했다.

Config Server의 `application.yml`과 `auth-service.yml`의 역할도 처음에는 구분이 헷갈렸다.

`application.yml`은 공통 설정으로 사용할 수 있고,   
`{service-name}.yml`은 특정 서비스에만 필요한 설정을 제공하는 용도로 사용할 수 있다는 점을 정리했다.

MSA로 서비스를 나누면 각 서비스에 같은 Spring 의존성을 모두 추가해야 하는지도 확인했다.

서비스가 담당하는 역할에 따라 필요한 의존성이 달라지며, OAuth2 로그인을 처리하지 않는 `board-service`에는 OAuth2 Client가 필요하지 않았다.

## 오늘 느낀 점

Kotlin은 Java와 완전히 다른 환경으로 옮기는 것이 아니라   
JVM과 기존 Java 생태계를 그대로 활용하면서 필요한 부분부터 점진적으로 적용할 수 있다는 점이 인상적이었다.

다만 자동 변환 기능이 있어도 nullable 타입이나 Lombok처럼 Java와 Kotlin 사이의 경계에서 문제가 발생할 수 있어,   
단순히 문법을 변환하는 것보다 두 언어가 서로 어떻게 컴파일되고 호출되는지 이해하는 것이 중요하다고 느꼈다.

MSA 실습에서는 서비스를 여러 개 만드는 것보다 각 서비스가 어떤 책임과 데이터를 소유하는지 구분하는 것이 핵심이라는 점을 다시 확인했다.

오늘 실습을 통해 서비스 분리뿐 아니라 설정, DB, 의존성까지 서비스 책임에 맞게 나누어야 실제 MSA 구조에 가까워진다는 점을 이해할 수 있었다.
