## 오늘 배운 내용

오늘은 User/Auth와 Goods/Sale 담당자의 변경사항을 반영해 Purchase 도메인을 실제 사용자·판매·재고 구조와 연결했다.

구매 처리에서 Purchase가 직접 재고를 수정하는 것이 아니라 `InventoryService`를 통해 재고 차감과 복구를 요청하도록 역할을 분리했다.   
현재 RDB 방식에서는 비관적 락으로 동일한 판매 재고의 동시 수정을 제어하고,
구매 처리 전체를 같은 트랜잭션에 참여시켜 Purchase 저장 실패 시 재고 변경도 함께 롤백되도록 구성했다.

선착순 구매에서는 `@Transactional`이나 중복 구매 Unique Constraint만으로 모든 동시성 문제가 해결되지는 않는다.   
재고 자체에 대한 동시성 제어가 필요하며,   
이후 Redis를 적용하면 빠른 원자적 재고 처리가 가능하지만 Redis와 RDB가 서로 다른 저장소이므로 별도의 정합성 및 보상 처리가 필요하다.

메시지 큐는 재고 동시성을 직접 해결하는 기술이 아니라 구매 후속 처리를 비동기화하고 순간 트래픽을 완충하는 역할을 한다.   
메시지 재전달이나 처리 실패를 고려해 Consumer의 멱등성, Retry, DLQ와 보상 처리까지 함께 설계해야 한다.

프론트에서는 기존 사용자 화면에 이어 관리자용 상품·판매 관리 화면을 추가하고, 카카오 로그인 버튼을 헤더에 직접 배치해 로그인 흐름을 단순화했다.

## 실습 및 과제

> User/Auth 변경사항 반영 및 Purchase 기본 구조 연동

User/Auth 변경사항을 반영하고 기존 Purchase 코드가 실제 `User` 엔티티와 `UserRepository`를 사용하도록 연결했다.

사용자 조회와 사용자별 구매 목록·상세 조회가 실제 인증 도메인 구조를 기준으로 동작하도록 PurchaseRepository와 PurchaseService 구조를 정리했다.

> Purchase 구매·취소 및 재고 연동

Goods/Sale 영역의 최신 구조를 확인하고 Purchase에서 실제 판매 정보를 나타내는 `Sale`을 사용하도록 연결했다.

재고 처리는 Purchase Service에서 직접 수행하지 않고 `InventoryService`를 호출하도록 구성했다.   
`InventoryService`는 비관적 락으로 Sale을 조회한 뒤 재고 차감·복구와 판매 상태 변경을 담당하는 도메인 로직을 실행한다.

구매 시에는 동일 판매에 대한 중복 구매를 검사하고 User와 Sale을 조회한 뒤 판매 기간과 상태를 검증한다.   
이후 재고를 1개 차감하고 구매 당시 가격을 저장해 Purchase를 생성하도록 연결했다.

구매 취소에서는 이미 취소된 구매와 판매 종료 여부를 확인한 뒤 구매 수량만큼 재고를 복구하고 Purchase 상태를 `CANCELED`로 변경하도록 했다.

공통 예외 처리 구조에 맞춰 중복 구매, 구매 내역 없음, 중복 취소와 판매 불가 상황을 도메인 예외로 처리하도록 정리했다.

> 관리자 화면 및 카카오 로그인 UI 구현

기존 사용자용 화면에 이어 관리자 상품 관리, 상품 등록·수정, 판매 관리와 판매 등록·수정 화면을 구현했다.

상품은 실제 데이터를 삭제하기보다 활성·비활성 상태를 변경하는 소프트 딜리트 흐름을 기준으로 화면을 구성했다.

판매 관리에서는 판매 예정·판매 중·품절·판매 종료 상태와 재고, 판매 기간을 확인할 수 있도록 했다.   
판매 상태는 관리자가 임의로 선택하기보다 판매 시간과 재고에 따라 결정되는 구조를 기준으로 잡았다.

카카오 로그인만 제공하는 서비스이므로 별도의 로그인 페이지를 만들지 않고 헤더에서 바로 OAuth2 로그인으로 이동하도록 구성했다.   
카카오 공식 축약형 로그인 버튼 리소스도 적용했다.

구매 흐름은 별도 구매 페이지를 추가하지 않고 판매 상세에서 바로 구매를 요청한 뒤 구매 결과와 내 구매 내역으로 이어지는 구조를 유지했다.

> 선착순 구매 동시성 및 메시지 큐 학습

RDB 기반 재고 동시성 처리 방법으로 비관적 락, 낙관적 락과 Atomic UPDATE의 차이를 정리했다.

비관적 락은 동일 행의 수정을 잠가 정합성을 보장하지만 요청이 집중되면 락 대기가 증가할 수 있다.   
낙관적 락은 버전 충돌을 감지해 재시도하는 방식이므로 충돌이 많은 선착순 환경에서는 Retry가 증가할 수 있다.

Redis에서는 재고 확인과 감소를 여러 명령으로 나누지 않고 원자적으로 처리해야 한다.   
이후 Redis 재고를 적용할 경우 Redis 차감 성공 후 Purchase 저장 실패와 같은 상황에는 재고를 되돌리는 보상 처리가 필요하다.

메시지 큐 후보로 RabbitMQ, Redis Streams와 Kafka를 비교했다.   
이번 프로젝트에서는 Redis 기반 재고와 Purchase 흐름을 먼저 완성한 뒤 비동기 처리의 필요성을 확인하고   
RabbitMQ 또는 Redis Streams 적용 여부를 판단하기로 했다.

RabbitMQ를 적용한다면 Producer가 구매 메시지를 발행하고 Consumer가 Purchase 저장을 수행하는 구조를 고려할 수 있다.   
Consumer 처리 완료 전 장애가 발생하면 같은 메시지가 다시 전달될 수 있으므로 중복 처리 방지를 위한 멱등성이 필요하다.

PostgreSQL, Redis와 RabbitMQ 같은 개발 인프라는 로컬에서 Docker Compose로 구성할 수 있다는 점도 확인했다.
실제 배포 시에는 애플리케이션이 접근할 수 있는 별도의 실행 환경이 필요하다.

## 헷갈렸던 점

`GoodsSales`와 `Sale`이 함께 존재해 Purchase에서 어느 객체를 사용해야 하는지 헷갈렸다.  
코드 구조를 확인한 결과 Purchase에서는 실제 판매 회차와 재고 정보를 가지는 `Sale`을 사용하고, `Goods`는 상품 자체 정보를 담당한다는 점을 구분했다.

`Sale`, `SaleRepository`, `InventoryService`가 각각 왜 필요한지도 처음에는 구분하기 어려웠다.  
`Sale`은 재고 변경과 판매 상태 전환이라는 도메인 규칙을 가지고, Repository는 비관적 락을 이용해 안전하게 Sale을 조회하며,   
InventoryService는 이 둘을 이용해 재고 처리 유스케이스를 제공한다.

`@Transactional`을 사용하면 재고 동시성도 자동으로 해결되는지 헷갈렸다.  
트랜잭션은 하나의 구매 과정에서 재고 변경과 Purchase 저장이 함께 성공하거나 실패하도록 보장하지만,   
여러 트랜잭션이 같은 재고를 동시에 읽고 수정하는 문제까지 자동으로 막아주지는 않는다.

`UNIQUE(user_id, sale_id)`도 동시성 문제 전체를 해결하는 것은 아니다.  
동일 사용자의 중복 Purchase 저장은 막을 수 있지만 서로 다른 사용자가 같은 재고를 동시에 차감해 발생하는 초과 판매는 별도의 재고 동시성 제어가 필요하다.

Redis를 적용하면 `@Transactional`로 PostgreSQL과 Redis를 함께 롤백할 수 있는지도 헷갈렸다.  
두 저장소는 별도의 트랜잭션 영역이므로 Redis 재고 차감 후 DB 저장이 실패하면 Redis 값을 복구하는 보상 처리가 필요하다.

메시지 큐가 재고 동시성까지 해결하는 기술인지도 구분해야 했다.  
메시지 큐는 작업을 비동기화하고 요청을 완충하는 역할이며, 실제 재고 경쟁은 RDB 락이나 Redis 원자 연산 등으로 별도로 해결해야 한다.

RabbitMQ, Redis Streams와 Kafka 중 무엇을 사용할지도 고민했다.  
Kafka는 현재 프로젝트 범위에 비해 학습·운영 범위가 크고, RabbitMQ는 Ack·Retry·DLQ와 같은 전형적인 메시지 큐 구조를 경험하기 좋다.   
Redis Streams는 이미 Redis를 사용하는 경우 별도 인프라를 줄일 수 있다는 장점이 있어 실제 적용 시 두 방식을 다시 비교하기로 했다.

## 오늘 느낀 점

오늘은 다른 팀원의 User/Auth와 Goods/Sale 구현을 실제 Purchase 코드에 연결하면서 도메인 간 역할 분리가 왜 중요한지 더 명확하게 이해할 수 있었다.

특히 PurchaseService가 직접 재고를 수정하는 대신 InventoryService에 요청하도록 구성하면   
현재 비관적 락 기반 구현에서 이후 Redis 기반 구현으로 변경되더라도 구매 유스케이스 자체의 변경을 줄일 수 있다는 점이 인상적이었다.

선착순 구매는 단순히 Purchase를 저장하는 기능보다 동시에 많은 요청이 들어왔을 때 재고와 구매 기록을 정확하게 유지하는 것이 핵심이라는 점도 다시 확인했다.

Redis나 메시지 큐도 기능을 추가하기 위해 사용하는 것이 아니라 먼저 현재 RDB 방식의 문제를 재현하고 성능과 정합성을 측정한 뒤 필요한 지점에 도입해야 한다.   
이후 k6 테스트에서 초과 판매 여부와 처리 성능을 확인하고 개선 전후를 수치로 비교해 보고 싶다.
