## 오늘 배운 내용

오늘은 카카오 OAuth2 로그인 구조와 기존 JWT 인증 흐름이 어떻게 연결되는지 학습했다.

OAuth2는 서비스가 사용자의 카카오 아이디와 비밀번호를 직접 받는 방식이 아니다.  
사용자가 카카오에서 로그인과 정보 제공에 동의하면 인가 코드를 받고, 이를 카카오 Access Token으로 교환한 뒤 사용자 정보를 조회한다.

카카오 Access Token은 카카오 API에서 사용자 정보를 조회하는 데 사용하고,   
서비스의 JWT Access Token은 로그인 완료 후 API 요청을 인증하는 데 사용한다. 두 토큰은 이름은 같지만 발급 주체와 사용 목적이 다르다.

OAuth2 Authorization Code 흐름에서 로그인 화면 이동, `state` 검증, 인가 코드 교환과 사용자 정보 조회 같은 표준 과정은 Spring Security가 처리한다.   
개발자는 조회한 사용자 정보를 회원과 연결하는 `OAuth2UserService`와 로그인 성공 후 JWT를 발급하는 후처리를 구현한다.

카카오와 구글처럼 제공자마다 사용자 정보 응답 구조가 다르기 때문에 `OAuth2UserInfo` 공통 인터페이스를 만들고,   
`KakaoUserInfo`에서 카카오 응답의 중첩된 값을 꺼내도록 구성했다.

회원은 `AuthProvider`를 통해 `LOCAL`과 `KAKAO`로 구분하고,   
OAuth2 회원은 변경될 수 있는 이메일이나 닉네임 대신 `provider`와 `providerId`의 조합으로 식별한다.

카카오 인증에 성공한 것과 서비스 가입이 완료된 것은 별개의 상태다.   
대응하는 회원이 DB에 없으면 `ROLE_GUEST` 권한으로 추가 가입 절차를 진행하고, 이미 가입된 회원이면 기존 권한으로 우리 서비스의 JWT를 발급한다.

`CustomOAuth2User`는 OAuth2 로그인 과정에서 카카오 사용자 정보와 우리 DB 회원을 함께 관리하고,   
`CustomUserDetails`는 자체 로그인과 JWT 인증 이후의 API 요청에서 사용한다.

소셜 미가입자에게 전달하는 `signupToken`의 Payload는 브라우저에서 읽을 수 있지만 암호화된 값은 아니다.   
실제 가입 처리에서는 화면에 표시된 값을 신뢰하지 않고 서버가 토큰의 Signature와 만료 시간을 검증한 뒤 내부 정보를 사용해야 한다.

OAuth2는 외부 제공자를 통해 사용자를 최초로 확인하는 로그인 입구이고, JWT는 확인된 사용자의 우리 서비스 로그인 상태를 유지하는 수단이다.   
자체 로그인과 카카오 로그인은 시작 과정이 다르지만, 회원이 확정된 뒤에는 같은 JWT 인증 흐름을 사용한다.

Repoary에서는 2주차 개발 진행 상황과 다음 작업 계획을 정리했다.

이번 주에는 연결된 저장소를 기준으로 경로 분류 규칙과 커밋 규칙을 관리하는 기능을 구현했다.   
날짜별 GitHub 커밋과 각 커밋의 변경 파일을 조회하고, 저장소별 규칙을 적용해 분석 결과를 생성·저장하는 백엔드 흐름도 완성했다.

GitHub에서 조회한 커밋 메시지와 변경 파일 경로가 규칙에 따라 올바르게 분류되는지 확인하기 위해 분석 테스트를 추가했다.   
프론트에서는 저장소 규칙 관리, 날짜별 분석 실행과 결과 조회 화면을 구현했으며,   
기간별 커밋 컨벤션 사용 현황을 확인할 수 있는 일관성 분석 API와 화면도 추가했다.

보고서를 작성하며 2주차 목표였던 저장소별 규칙 관리와 커밋 분석 백엔드 기능은 완료됐고,   
3주차 범위인 분석 프론트엔드 기능도 일부 미리 진행됐다는 점을 정리했다.

## 실습 및 과제

> 카카오 OAuth2 로그인 구조 실습

OAuth2 Client 의존성을 추가하고 카카오 Client 정보와 인증 Endpoint를 설정했다.

OAuth2 제공자별로 서로 다른 사용자 정보 구조를 공통 형태로 처리하기 위해 `OAuth2UserInfo`를 정의하고, 카카오 응답을 처리하는 `KakaoUserInfo`를 구현했다.

회원의 가입 방식을 구분하기 위한 `AuthProvider`를 추가하고, `User` 엔티티에 `provider`와 `providerId`를 저장하도록 구성했다.

OAuth2 로그인 중 사용하는 `CustomOAuth2User`를 구현해 카카오 원본 attributes와 우리 서비스의 회원 정보를 함께 관리하도록 했다.   
가입된 사용자는 기존 권한을 사용하고, 아직 가입되지 않은 사용자는 `ROLE_GUEST` 권한을 가질 수 있도록 구분했다.

소셜 미가입자에게 전달할 `signupToken`의 역할과 Payload 표시 방식을 확인했다.   
화면에 표시되는 값은 확인용으로만 사용하고, 실제 회원가입에서는 서버가 검증한 토큰 정보를 기준으로 처리해야 한다.

추가로 기간별 커밋 컨벤션 사용 현황을 확인하는 일관성 분석 API와 화면을 구현해 다음 주차 범위도 일부 진행했다.

## 헷갈렸던 점

OAuth2 로그인에서 개발자가 인가 코드 교환과 사용자 정보 조회를 모두 직접 구현해야 하는지 헷갈렸다.   
Spring Security가 표준 Authorization Code 흐름을 처리하며,   
개발자는 받아온 사용자 정보를 우리 회원과 연결하고 성공 이후 JWT를 발급하는 서비스별 로직을 구현한다.

카카오 인증에 성공하면 우리 서비스 회원가입도 끝난 것으로 생각할 수 있지만, 외부 제공자가 사용자를 인증한 것과 우리 DB에 회원이 등록된 것은 별개의 상태다.   
DB에서 `provider`와 `providerId`에 해당하는 회원을 찾지 못하면 추가 가입 절차가 필요하다.

`CustomOAuth2User`와 `CustomUserDetails`의 역할도 비슷하게 느껴졌다.   
`CustomOAuth2User`는 외부 OAuth2 인증 과정에서 사용하고, `CustomUserDetails`는 자체 로그인이나 우리 JWT 인증 이후의 API 요청에서 사용한다.

JWT Payload를 브라우저에서 읽을 수 있다는 점 때문에 토큰이 안전하지 않은 것처럼 느껴졌지만, JWT의 Payload는 원래 암호화된 영역이 아니다.   
토큰의 안전성은 내용을 숨기는 것이 아니라 서버가 Signature를 검증해 위·변조 여부를 확인하는 방식으로 보장된다.   
따라서 비밀번호나 Secret 같은 민감한 정보는 Payload에 넣으면 안 된다.

실습 프로젝트의 인증 관련 파일이 기존 프로젝트보다 세세하게 나뉘어 있어 실제 프로젝트에서도 매번 같은 구조를 모두 작성해야 하는지 궁금했다.   
학습에서는 OAuth2 응답 처리, principal 생성, 회원 연결과 JWT 발급의 내부 흐름을 이해하기 위해 각 책임을 직접 구현하지만,   
실무에서는 공통 인증 모듈이나 팀 템플릿 등으로 일부 구조가 추상화될 수 있다.

## 오늘 느낀 점

OAuth2 로그인은 카카오 로그인 버튼을 연결하는 기능 하나가 아니라,   
외부 제공자의 사용자 확인 결과를 우리 서비스 회원과 연결하고 기존 JWT 인증 구조로 전환하는 전체 흐름이었다.

카카오 OAuth2와 자체 JWT 인증의 역할을 분리해 보니,   
OAuth2는 사용자를 처음 확인하는 과정이고 JWT는 이후 우리 서비스 안에서 로그인 상태를 유지하는 방식이라는 차이를 이해할 수 있었다.

또한 제공자마다 사용자 정보 응답 구조가 다르기 때문에 공통 인터페이스와 제공자별 구현체를 나누는 이유를 확인했다.   
`OAuth2UserInfo`, `KakaoUserInfo`, `CustomOAuth2User`, `AuthProvider`가 각각 어떤 경계에서 필요한지 구분하니 파일이 많아진 이유도 이해하기 쉬웠다.

Spring Boot의 Controller, DTO, Service, Repository와 Entity가 요청 처리 과정에서 어떻게 연결되는지도 다시 정리하면서,   
각 파일을 이름만 외우기보다 데이터와 로직이 이동하는 흐름을 기준으로 이해해야 한다고 느꼈다.

Repoary 보고서를 작성하며 이번 주 목표와 실제 완료 범위를 비교해 보니,   
커밋 분석 백엔드 기능뿐 아니라 규칙 관리와 날짜별 분석 프론트 화면까지 연결한 상태라는 점을 확인했다.

기능을 단순히 나열하기보다 주차별 목표, 완료율과 다음 작업을 함께 정리하니 현재 프로젝트 진행 위치가 더 명확하게 보였다.   
다음에는 저장된 분석 결과를 실제 TIL Markdown 초안으로 변환하는 흐름을 구현해야 한다.
