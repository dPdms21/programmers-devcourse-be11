## 오늘 배운 내용

오늘은 Purchase와 Payment의 단건 구매·결제 흐름을 실제 PostgreSQL, Redis와 Toss 결제를 이용해 전체 검증하고,   
프론트 연동에서 발견한 구매·결제 예외 상황을 보완했다.

Purchase·Payment 통합 검증에서는 정상 구매뿐 아니라   
결제 전 취소, 명확한 결제 승인 실패, 결제 timeout, Toss 승인 성공 후 DB 처리 실패에 대한 보상 취소까지 확인했다.   
Payment와 Purchase 상태만 보는 것이 아니라 Redis 재고와 사용자별 구매 수량 Key의 차감·복구까지 함께 확인해야   
전체 구매 흐름의 정합성을 판단할 수 있다는 점을 정리했다.

백엔드에서는 프론트 연동에 필요한   
구매내역 최신순 정렬과 구매 생성 응답의 `createdAt` 추가, 테스트용 JWT Key와 초기 구매 수량 제한 데이터를 현재 정책에 맞게 보완했다.

프론트에서는 비로그인 사용자, Toss 결제창 직접 취소, timeout과 재구매 같은 실제 예외 상황을 구분해 처리했다.   
특히 사용자 취소를 오류 메시지 문자열로 추측하지 않고   
Toss가 제공하는 명시적인 오류 코드를 기준으로 판별해야 다른 결제 실패와 잘못 구분되는 문제를 줄일 수 있었다.

결제 timeout 역시 프론트의 결제 화면 진입 시점부터 임의로 계산하지 않고   
백엔드의 `Purchase.createdAt`을 기준으로 계산해 실제 timeout Scheduler와 동일한 기준을 사용하도록 했다.

마지막으로 브라우저 성공 콜백에만 의존하지 않고 Toss Webhook에서 실제 PG 상태를 다시 확인해 Payment와 Purchase 상태를 보정하는 구조를 구현했다.   
사용자 취소, timeout과 Webhook이 동시에 실행될 수 있으므로 현재 상태를 다시 확인하고 중복 상태 변경과 재고 복구를 막는 것이 중요했다.

## 실습 및 과제

> Purchase · Payment 단건 통합 검증

정상 구매, 결제 전 취소, 명확한 결제 승인 실패, 결제 timeout과 Toss 승인 후   
DB 처리 실패에 대한 보상 취소까지 실제 PostgreSQL·Redis·Toss 환경에서 검증했다.

정상 구매에서는 Purchase와 Payment 상태가 정상적으로 완료되는지와 함께 Redis 재고와 사용자별 구매 수량이 차감되는지 확인했다.

결제 실패·취소·timeout에서는 Purchase와 Payment 상태가 의도한 값으로 변경되는지, Redis 재고와 사용자별 구매 수량이 다시 정상적으로 복구되는지 확인했다.

Toss 승인 이후 내부 DB 처리가 실패하는 경우에는 승인된 결제가 보상 취소되고 Purchase·Payment와 재고 상태가 함께 정리되는 것도 검증했다.

이를 통해 결제 상태만 확인하는 것이 아니라 Purchase, Payment, Redis의 상태를 함께 확인해야 전체 구매 흐름이 정상인지 판단할 수 있다는 점을 확인했다.

> 구매·결제 백엔드 보완

프론트에서 구매내역을 확인했을 때 최신 구매가 먼저 표시될 수 있도록 구매 목록 조회의 정렬 기준을 보완했다.

결제 timeout 카운트다운에서 백엔드 Scheduler와 동일한 기준 시각을 사용할 수 있도록 구매 생성 응답에 `createdAt`을 추가했다.

테스트 환경에서는 JWT 테스트 Secret이 실제 서명 알고리즘의 Key 길이 조건을 만족하도록 수정했다.

현재 서비스가 한 번에 구매 수량 1개만 허용하는 정책이므로 초기 판매 데이터의 `max_purchase_quantity`도 1로 맞췄다.

> 비로그인 사용자 구매 접근 처리

비로그인 사용자가 구매하거나 구매내역에 접근했을 때 단순 오류로 끝나지 않고 로그인 필요 안내 후 카카오 로그인으로 이동하도록 `401` 응답을 처리했다.

판매 목록은 비로그인 사용자도 조회할 수 있어야 하므로 판매 조회에는 인증 처리를 추가하지 않고,   
실제 보호 API인 구매 생성과 구매내역 조회에서만 로그인 처리를 적용했다.

> 결제 취소 및 재구매 흐름 보완

Toss 결제창에서 사용자가 직접 취소했는지는 오류 메시지 문자열이 아니라   
`PAY_PROCESS_CANCELED`, `USER_CANCEL`과 같은 명시적인 Toss 오류 코드로만 판별하도록 수정했다.

사용자 취소가 확인되면 구매 취소 API를 호출해 Purchase와 Redis 재고를 즉시 정리하도록 했다.

이미 취소된 Purchase의 기존 `orderId`로 다시 결제를 시도하지 않고 상품 상세로 돌아가 새로운 Purchase와 Payment를 생성하도록 재구매 흐름도 수정했다.

브라우저 종료나 페이지 이탈처럼 프론트에서 명시적인 취소 요청을 전달하지 못한 경우에는 기존 10분 timeout Scheduler가 처리하도록 역할을 구분했다.

> 결제 timeout 카운트다운 표시

프론트에서 결제 페이지에 들어온 순간부터 새로 10분을 계산하면 실제 Purchase 생성 시각과 백엔드 timeout 기준이 달라질 수 있다는 점을 확인했다.

구매 생성 응답의 `createdAt`을 이용해 실제 Purchase 생성 시점을 기준으로 남은 시간을 계산하도록 변경했다.

결제 화면에는 10분 카운트다운을 표시하고, 남은 시간이 1분 이하이면 경고 UI를 보여주며 시간이 만료되면 결제 버튼을 비활성화하도록 했다.

> 구매 및 관리자 UI 보완

관리자 상품·판매 테이블의 수정 버튼 영역 때문에 행 정렬이 어긋나는 문제를 수정했다.

구매내역과 구매 상세에서는 상품 이미지가 잘리지 않도록 목록과 상세의 이미지 클래스를 구분하고 표시 방식을 보완했다.

> Toss Payments Webhook 상태 보정 구현

브라우저의 결제 성공 콜백에만 의존하지 않고 `PAYMENT_STATUS_CHANGED` Webhook을 이용해 Toss의 실제 결제 상태를 다시 확인하도록 구현했다.

Webhook을 수신하면 `paymentKey`를 이용해 Toss 결제를 재조회하고,   
전달받은 `paymentKey`, `orderId`, `amount`가 실제 Toss 결제 정보와 일치하는지 검증한다.

실제 Toss 상태에 따라 `DONE`은 구매 완료, `CANCELED`는 구매 취소와 재고 복구,   
`ABORTED`는 결제 실패와 재고 복구, `EXPIRED`는 결제 만료에 따른 취소와 재고 복구로 처리했다.

`READY`, `IN_PROGRESS`처럼 아직 최종 결과가 확정되지 않은 상태는 별도 보정을 수행하지 않도록 했다.

이미 사용자 취소나 timeout으로 로컬 Purchase가 `CANCELED`인데 Toss에서는 `DONE`인 경우에는   
Purchase를 다시 `PURCHASED`로 되돌리지 않고 Toss 결제만 보상 취소하도록 분리했다.   
이미 Redis 재고가 복구된 로컬 상태를 다시 완료 처리하면 재고 정합성이 깨질 수 있기 때문이다.

상태 보정에서는 Purchase를 비관적 락으로 조회한 뒤 현재 Payment와 Purchase 상태를 다시 확인해   
사용자 취소, timeout과 Webhook이 동시에 실행되더라도 중복 취소와 중복 재고 복구가 발생하지 않도록 했다.

Payment와 Purchase의 상태를 변경한 뒤 `restoreStock()`을 호출하고,   
Redis 복구에서 예외가 발생하면 같은 트랜잭션의 DB 변경도 롤백되도록 처리 순서를 정리했다.

Webhook용 Payment 상태 전이와 `DONE`, `CANCELED`, `ABORTED`, `EXPIRED` 보정, Webhook 데이터 불일치,   
이미 최종 상태인 경우와 동일 Webhook 재처리까지 테스트하고 관련 단위 테스트가 통과하는 것을 확인했다.

## 헷갈렸던 점

Purchase·Payment 통합 검증에서 결제 실패를 의도했는데 실패 흐름이 아니라 사용자 취소 흐름으로 처리되어 원인을 확인했다.  
결제 실패 자체의 처리와 프론트에서 오류를 사용자 취소로 판별하는 로직은 별개의 문제였으며,   
문자열에 `cancel`이나 `취소`가 포함됐는지를 기준으로 판단하면 정상적인 실패까지 사용자 취소로 잘못 분류될 수 있었다.

비로그인 처리를 판매 화면 전체에 적용해야 하는지도 고민했다.  
판매 조회 자체는 공개 기능이므로 실제 인증이 필요한 구매 생성과 구매내역 조회에서만 `401`을 처리하는 것이 적절했다.

프론트 결제 timeout을 결제 페이지 진입 시점부터 10분으로 계산해도 되는지 헷갈렸다.  
백엔드 Scheduler는 `Purchase.createdAt`을 기준으로 하므로 프론트에서도 같은 값을 사용해야 화면의 카운트다운과 실제 timeout 시점이 일치한다.

사용자가 Toss 결제를 취소한 뒤 기존 결제 정보로 다시 시도해도 되는지도 확인했다.  
이미 Purchase가 취소되고 Redis 재고가 복구된 상태이므로 기존 결제를 재사용하지 않고 새로운 구매부터 시작해야 한다.

Webhook에서 Toss 상태가 `DONE`이면 항상 Purchase를 `PURCHASED`로 변경해야 하는지도 고민했다.  
이미 사용자 취소나 timeout으로 로컬 상태가 `CANCELED`라면 Purchase를 다시 완료 상태로 변경할 경우   
이미 복구된 Redis 재고와 충돌하므로 로컬 상태를 유지하고 Toss 결제만 보상 취소해야 한다.

Webhook, 사용자 취소와 timeout이 동시에 실행되면 재고가 여러 번 복구될 수 있는지도 확인했다.  
Purchase를 Lock으로 다시 조회하고 현재 상태를 검증한 뒤 이미 처리된 경우에는 추가 상태 변경과 재고 복구를 하지 않도록 해야 한다.

Redis 재고를 먼저 복구한 뒤 DB 상태를 변경해도 되는지도 고민했다.  
Redis 복구 후 DB 처리에서 실패하면 Redis만 변경되는 불일치가 생길 수 있으므로 DB 상태 변경과 재고 복구를 하나의 처리 흐름으로 구성하고   
Redis 복구 실패 시 DB 변경도 롤백되도록 하는 것이 적절했다.

## 오늘 느낀 점

오늘은 개별 기능을 추가하는 것보다 Purchase, Payment와 Redis가 실제 정상·실패·취소 상황에서 서로 일관된 상태를 유지하는지 검증하는 작업의 중요성을 느꼈다.

실제 통합 검증에서는 Payment 상태가 기대한 값이라고 끝나는 것이 아니라   
Redis 재고와 사용자별 구매 수량까지 확인해야 구매 전체 흐름이 제대로 처리됐다고 판단할 수 있었다.

프론트에서도 단순히 오류를 표시하는 것보다 비로그인 상태, 사용자의 직접 결제 취소, timeout과 재구매처럼   
사용자가 실제로 겪는 상황을 각각 구분해 적절한 다음 흐름으로 연결하는 것이 중요했다.

Webhook을 구현하면서 브라우저의 성공 콜백만으로는 외부 결제와 내부 상태의 최종 일치를 보장할 수 없고,   
PG의 실제 상태를 다시 확인해 내부 상태를 복구할 수 있는 경로가 필요하다는 점도 더 명확하게 이해했다.

이제 Purchase·Payment 단건 통합 흐름과 Webhook 단위 테스트까지 확인했으므로   
다음에는 실제 Toss Webhook 요청과 여러 처리 흐름이 동시에 실행되는 상황에서도 결제 상태와 Redis 재고가 중복 처리되지 않는지 확인해야겠다.
