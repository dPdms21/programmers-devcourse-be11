## 오늘 배운 내용

오늘은 Gudit 프로젝트 발표 자료를 구성하고 팀원들의 확인을 받아 수정하면서,   
구현한 기능을 나열하기보다 선착순 구매에서 어떤 문제가 발생했고 이를 어떤 구조로 해결했는지를 중심으로 프로젝트 전체 흐름을 다시 정리했다.

프로젝트의 핵심 문제는 한정 수량 상품에 많은 사용자가 동시에 접근할 때 발생할 수 있는 초과 판매, 중복 구매와 데이터 정합성 문제로 잡았다.   
재고 100개에 1,000개의 동시 요청이 들어오는 상황을 기준으로 RDB 기본 처리, 비관적 락과 `Redis + Lua` 방식의 차이를 비교하고 Redis를 사용한 이유를 정리했다.

Redis를 도입해 재고 차감 자체는 빠르고 원자적으로 처리할 수 있지만, Redis와 RDB를 하나의 트랜잭션으로 묶을 수 없기 때문에 새로운 정합성 문제가 생긴다.   
Redis 재고 선점 이후 Purchase 저장이 실패하면 Redis 재고와 사용자별 구매 수량을 보상 복구하도록 구성한 이유를 다시 확인했다.

구매·결제 영역에서는 Purchase와 Payment의 상태를 분리하고,   
Toss와 내부 DB 사이에서 발생할 수 있는 명확한 실패와 결과가 불확실한 실패를 다르게 처리하는 구조를 정리했다.   
Webhook을 이용해 외부 PG의 실제 상태를 다시 확인하고 내부 상태를 보정하는 이유도 발표 흐름에 포함했다.

동시성 처리에서는 비관적 락 자체보다 여러 흐름에서 같은 자원을 동일한 순서로 Lock하고, Lock을 획득한 뒤 최신 상태를 다시 검증하는 것이 중요하다는 점을 정리했다.

성능 테스트 역시 단순 응답 속도 측정이 아니라 동시 요청에서 재고와 Purchase가 정확하게 유지되는지를 검증하는 수단으로 정리하고,   
동시성·부하·용량 테스트의 목적과 주요 지표를 구분했다.

마지막으로 현재 구조에서 완전히 해결하지 못한 Redis-RDB, Toss-DB 간 정합성과 1인 1구매 정책, 분산된 로그 관리 문제를 프로젝트 한계로 정리하고   
Inbox/Outbox, Message Queue와 통합 로그·모니터링을 향후 개선 방향으로 검토했다.

## 실습 및 과제

> Gudit 발표 자료 구성

프로젝트 개요에서는 한정 수량 판매에서 발생하는 `Concurrency`와 `Consistency` 문제를 중심으로 발표의 문제 정의를 구성했다.

재고 100개에 1,000개의 요청이 동시에 들어오는 상황을 예시로 사용해 초과 판매와 중복 구매가 왜 발생할 수 있는지 설명하고,   
이후 기술적인 해결 과정으로 자연스럽게 이어지도록 발표 흐름을 잡았다.

기능을 구현한 순서대로 나열하기보다 `문제 발생 → 해결 방법 검토 → 적용 → 새로운 정합성 문제 → 보상 처리 및 동시성 제어` 순서로 자료를 구성했다.

> Redis 재고 처리 구조 정리

RDB 기본 재고 처리와 비관적 락, `Redis + Lua` 방식을 비교하고 각각의 특징과 Redis를 최종적으로 선택한 이유를 정리했다.

판매 전에는 Warm-up을 통해 RDB의 판매 정보와 재고를 Redis에 준비하고,   
구매 시 Lua Script가 판매 상태, 판매 기간, 사용자 구매 제한과 재고를 검증한 뒤   
재고 차감과 사용자 구매 수량 증가를 하나의 원자적 연산으로 수행하는 흐름을 정리했다.

Redis 선점 이후 DB 저장이 실패하면 DB rollback만으로 Redis까지 되돌릴 수 없기 때문에   
`restoreStock()`을 이용한 보상 복구가 필요하다는 점도 발표 자료에 반영했다.

판매 종료 시에는 Redis 판매 상태를 먼저 종료 상태로 변경해 신규 구매를 막고 최종 Redis 재고를 RDB에 동기화하는 흐름을 정리했다.

> Purchase · Payment 결제 흐름 정리

Purchase는 `PENDING_PAYMENT → PURCHASED / CANCELED`, Payment는 `READY → IN_PROGRESS → DONE / FAILED / CANCELED` 상태로 관리하는 이유를 정리했다.

결제 승인에서는 Payment와 Purchase의 최신 상태와 금액을 다시 검증한 뒤 Toss 승인을 요청하고, 중복 승인 요청에는 Idempotency Key를 사용하는 구조를 확인했다.

명확한 승인 실패는 Purchase 취소와 Redis 재고 복구로 처리하고,   
네트워크 오류처럼 승인 여부가 불확실한 경우에는 바로 실패 처리하지 않고 Toss 상태를 다시 조회하도록 구분했다.

Toss 승인은 성공했지만 내부 DB 반영이 실패한 경우에는 Toss 결제를 보상 취소하고 내부 Purchase·Payment와 Redis 재고를 다시 맞추는 구조도 정리했다.

> Webhook · Timeout · 동시성 흐름 정리

브라우저 콜백이 유실되더라도 최종 결제 상태를 보정할 수 있도록 Toss Webhook에서 `paymentKey`로 실제 결제 상태를 다시 조회하는 구조를 정리했다.

동일 Webhook이 재전송되는 경우 이미 최종 상태라면 no-op 처리해 중복 취소와 Redis 재고 중복 복구를 막는다.

결제 승인, 사용자 취소와 timeout은 동일한 Purchase와 Payment를 동시에 변경할 수 있으므로 비관적 락을 사용하고,   
Lock 획득 후 최신 상태를 다시 확인하는 구조를 발표에 반영했다.

Timeout은 단순히 10분이 지났다는 이유만으로 처리하는 것이 아니라 Purchase가 `PENDING_PAYMENT`, Payment가 `READY`인 경우에만 취소한다.   
실제 결제가 진행 중일 가능성이 있는 `IN_PROGRESS`는 재고를 바로 복구하지 않는 이유도 정리했다.

> 성능 테스트 결과 및 의미 정리

성능 테스트는 `Concurrency`, `Load`, `Capacity`로 구분해 각 테스트의 목적을 정리했다.

동시성 테스트에서는 재고 차감, 중복 구매, 구매·취소와 결제 승인·취소 경합 상황의 데이터 정합성을 검증했다.

부하 테스트에서는 Baseline, Stress, Spike, Soak, Mixed Load를 통해 서비스가 다양한 부하에서 어떻게 동작하는지 확인하고,   
Capacity 테스트에서는 VU를 단계적으로 증가시켜 처리량과 응답시간의 임계점을 확인하는 방향으로 정리했다.

주요 결과는 Success, p95, TPS와 Error Rate뿐 아니라 최종 재고와 Purchase 상태가 일치하는지도 함께 확인하도록 구성했다.

Windows 환경에서 1,000 VU 테스트 시 요청 누락이 발생해 Linux 환경으로 변경했던 경험을 통해 테스트 대상 서버뿐 아니라   
부하를 발생시키는 클라이언트와 OS 환경도 성능 측정의 병목이 될 수 있다는 점을 정리했다.

> 프로젝트 한계 및 향후 개선 방향 정리

Redis와 RDB를 하나의 트랜잭션으로 묶을 수 없기 때문에 현재 보상 처리만으로 모든 장애 상황의 정합성을 완전히 보장하기는 어렵다는 한계를 정리했다.

향후에는 Transactional Outbox를 이용해 재고 복구 이벤트를 DB 트랜잭션과 함께 기록하고 재시도하는 구조를 검토할 수 있다.

Toss와 내부 DB 사이의 상태 동기화 역시 Inbox/Outbox와 Message Queue 기반 비동기 처리로 확장할 수 있다는 방향을 정리했다.

현재 1인 1구매 제한은 `userId` 기준이므로 여러 계정을 사용하는 실제 사용자를 완전히 제한할 수 없다는 한계가 있다.   
이를 줄이기 위해 카카오 OAuth2로 로그인 경로를 제한했으며, 이후 본인인증이나 Rate Limiting, 비정상 요청 탐지 등을 추가할 수 있다.

Redis 재고, Purchase·Payment, Toss 승인·Webhook과 Scheduler 로그가 각각 분리되어 있어 전체 요청 흐름을 추적하기 어렵다는 점도 한계로 정리했다.   
이후 `traceId` 기반 구조화 로그와 중앙 로그·모니터링 환경을 적용하는 방향을 검토했다.

## 헷갈렸던 점

Redis를 도입했다는 사실 자체를 프로젝트의 핵심 성과로 설명해도 되는지 고민했다.  
Redis는 해결책일 뿐이고, 먼저 RDB 재고 처리에서 어떤 문제가 발생할 수 있었는지와   
Redis를 선택한 이유, Redis 도입 이후 새롭게 발생한 정합성 문제와 보상 처리까지 함께 설명해야 기술 선택의 의미가 드러난다는 점을 정리했다.

Warm-up이 실제 판매를 시작시키는 기능인지 다시 구분했다.  
Warm-up은 판매 전에 재고와 판매 정보를 Redis에 준비하는 과정이고, 실제 판매 상태 전환과 구매 처리는 별도의 흐름이다.

비관적 락을 사용했다는 것만 설명하면 동시성 처리 설명이 충분한지도 고민했다.  
실제 Case7에서 서로 다른 Lock 획득 순서 때문에 deadlock이 발생했으므로,   
락 사용 여부보다 전체 유스케이스의 Lock 순서와 Lock 이후 상태 재검증까지 설명해야 했다.

결제 timeout이 발생하면 바로 재고를 복구해도 되는지도 다시 확인했다.  
Payment가 `IN_PROGRESS`라면 실제 Toss 승인 여부가 불확실하므로 단순 시간 초과만으로 취소하거나 재고를 복구해서는 안 된다.

성능 테스트에서는 TPS와 p95 결과만 보여줘도 되는지 고민했다.  
선착순 서비스의 핵심은 빠른 응답뿐 아니라 초과 판매와 중복 구매가 발생하지 않는 것이므로 성능 지표와 함께 데이터 정합성 결과를 보여주는 것이 필요했다.

`1인 1구매`라고 표현해도 실제 한 명의 사용자를 완전히 식별할 수 있는지도 확인했다.  
현재는 카카오 계정의 `userId` 기준으로 제한하므로 동일 사용자의 다계정 이용까지 막는 것은 불가능하고, 이를 프로젝트 한계로 명확하게 설명하는 것이 적절했다.

## 오늘 느낀 점

오늘은 발표 자료를 만들면서 지금까지 구현한 기능을 다시 나열하기보다   
프로젝트에서 실제로 어떤 문제를 정의했고 왜 현재의 기술과 구조를 선택했는지 다시 정리할 수 있었다.

특히 Redis, 비관적 락, Webhook 같은 기술을 각각 설명하는 것보다 하나의 구매 요청이 들어왔을 때 재고 선점부터 결제, 실패 보상, timeout과 판매 종료까지   
어떻게 상태를 유지하는지를 하나의 흐름으로 연결해 설명하는 것이 더 중요하다는 점을 느꼈다.

또한 프로젝트에서 해결한 문제뿐 아니라 Redis-RDB 정합성이나 실제 사용자 단위의 1인 1구매처럼 아직 남아 있는 한계를 함께 정리하면서,   
현재 구조가 완벽해서 선택한 것이 아니라 프로젝트 범위 안에서 어떤 문제까지 해결하고 어떤 부분을 다음 개선 대상으로 남겼는지도 더 명확해졌다.

발표 자료는 직접 전체 흐름을 구성한 뒤 팀원들에게 확인받고 필요한 부분을 수정하면서 마무리했다.   
프로젝트 구현 과정을 다시 정리한 만큼 이후 포트폴리오에서도 기술 이름보다 문제 정의와 시행착오, 해결 근거와 측정 결과를 중심으로 정리해야겠다.
