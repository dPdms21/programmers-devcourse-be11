## 오늘 배운 내용

오늘은 Purchase 도메인을 실제 API로 사용할 수 있도록 Controller와 테스트를 보강하고,   
Toss Payments 테스트 환경에서 결제 인증부터 승인·조회·취소까지 전체 흐름을 검증했다.

Purchase Controller에서는 요청에서 사용자 ID를 직접 받지 않고 `@AuthenticationPrincipal`을 통해 인증된 사용자의 정보를 사용한다.   
JWT 인증이 필터를 거쳐 `SecurityContext`에 저장된 이후 Controller는 이미 인증된 사용자 정보만 이용한다는 흐름을 다시 확인했다.

테스트에서는 Service 단위 테스트와 Controller 테스트의 역할을 구분했다.   
Service에서는 정상 처리와 비즈니스 예외를 검증하고, `@WebMvcTest`에서는 실제 HTTP 요청·응답과 인증 사용자, CSRF, Service 호출 여부를 확인했다.

운영 환경과 테스트 환경도 분리했다.   
테스트에서는 H2와 테스트용 OAuth2·JWT 설정을 사용하고, 로컬 실행에서는 환경변수와 Docker PostgreSQL을 별도로 구성했다.

구매 도메인의 생성 · 수정 시각은 JPA Auditing으로 관리하고,   
`purchasedAt`, `canceledAt`처럼 실제 비즈니스 이벤트가 발생한 시각은 직접 관리하도록 역할을 구분했다.

결제는 Purchase와 별도의 `Payment` 도메인으로 설계하고 Toss Payments와의 거래 상태와 식별자를 관리하도록 했다.   
결제 인증이 성공해 `paymentKey`를 받았다고 바로 결제가 완료되는 것이 아니라,   
서버에서 승인 API를 호출해 `DONE` 상태가 되어야 실제 결제가 완료된다는 흐름을 확인했다.

Toss 테스트 환경에서 결제창 호출, 카드 인증, 서버 승인, 결제 조회와 취소까지 직접 검증했다.   
향후 Purchase와 연결할 때는 결제 금액을 클라이언트 값만 신뢰하지 않고 구매 당시 저장한 가격과 서버에서 다시 비교해야 한다.

외부 결제와 Redis는 PostgreSQL 트랜잭션에 함께 참여하지 않으므로 실패 상황에서 자동 롤백되지 않는다.   
따라서 Purchase, Redis 재고와 Payment를 최종 연결할 때는 멱등성, 보상 처리와 상태 복구 전략이 필요하다.

## 실습 및 과제

> Purchase API 및 테스트 구현

`PurchaseController`를 구현해 구매 생성, 내 구매 내역 조회, 구매 상세 조회와 취소 기능을 실제 인증 사용자 기준으로 호출하도록 연결했다.

Controller에서는 `@AuthenticationPrincipal CustomUserDetails`로 현재 사용자의 `userId`를 가져와 `PurchaseService`에 전달했다.

PurchaseService 테스트에서는 정상 구매뿐 아니라   
중복 구매, 존재하지 않는 구매 조회, 중복 취소, 판매 시작 전·종료 후 구매와 판매 불가 상태 등의 예외 상황을 검증했다.

정상 구매에서는 재고 차감과 Purchase 저장이 실행되는지 확인하고, 정상 취소에서는 재고 복구가 호출되는지 검증했다.

Controller 테스트는 Spring Security가 적용된 `@WebMvcTest` 환경에서 인증 사용자를 설정하고,   
POST 요청에는 CSRF 처리를 추가했다. 필터가 테스트 Context에 포함되므로 JWT 관련 의존성도 Mock으로 구성했다.

> 테스트 및 로컬 실행 환경 정리

테스트 실행 시 운영용 PostgreSQL과 OAuth2 · JWT 설정 때문에 Spring Context가 실패하는 문제를 해결하기 위해   
`src/test/resources/application.yml`에 테스트 전용 설정을 구성했다.

JWT Secret은 Base64 디코딩과 서명 알고리즘의 키 길이 조건을 만족하도록 테스트용 값을 별도로 사용했다.

로컬 실행에서는 프로젝트 루트의 `.env` 파일이 Spring Boot에 자동으로 적용되는 것이 아니라는 점을 확인하고   
IntelliJ Run Configuration에 환경변수를 설정했다.

Docker PostgreSQL에 애플리케이션에서 사용하는 데이터베이스가 존재하지 않아 연결에 실패한 문제도 확인하고   
필요한 데이터베이스를 생성해 애플리케이션 실행까지 검증했다.

> Purchase 시간 필드 및 예외 처리 정리

`createdAt`, `updatedAt`은 JPA Auditing의 `@CreatedDate`, `@LastModifiedDate`로 관리하도록 변경했다.

반면 `purchasedAt`, `canceledAt`은 엔티티 생성·수정 시각이 아니라 실제 구매와 취소가 발생한 시점이므로 비즈니스 로직에서 명시적으로 관리하도록 유지했다.

프로젝트에 이미 JPA Auditing 설정이 존재하는 상태에서 다시 `@EnableJpaAuditing`을 추가하면 관련 Bean이 중복 생성될 수 있다는 점도 확인했다.

공통 예외 처리 구조가 정리되면 Purchase의 개별 예외도 공통 `ErrorCode` 구조에 맞춰 변경하기로 했다.   
내부 로그용 메시지와 클라이언트에 반환할 오류 메시지는 구분해야 한다는 점도 확인했다.

> Toss Payments 결제 구조 설계

Purchase와 결제 거래의 책임을 분리하기 위해 `Payment` 도메인을 별도로 설계했다.

Purchase는 사용자가 어떤 판매 상품을 얼마에 구매하는지를 관리하고, Payment는 PG의 주문 식별자, 결제 식별자, 금액과 결제 상태를 관리하도록 역할을 나눴다.

결제 상태는 인증 전, 인증 후 승인 전, 승인 완료, 실패와 취소 상태를 구분할 수 있도록 설계했다.

현재 Purchase는 생성 즉시 구매 완료 상태가 되지만,   
실제 결제를 연결할 때는 결제 대기 상태를 추가하고 결제 승인 성공 이후에 구매 완료 상태로 전환하는 방향을 정리했다.

> Toss Payments 테스트 연동

브라우저에서 결제를 요청해 카드 인증을 완료한 뒤 전달받은 `paymentKey`, `orderId`, `amount`를 이용해 서버에서 승인 API를 호출했다.

승인 성공 후 결제 조회를 통해 완료 상태를 확인하고, 동일 결제를 취소해 취소 상태까지 변경되는 것을 검증했다.

승인과 취소 요청에는 동일 요청의 재시도를 고려해 고정된 멱등성 키를 사용하는 방향으로 설계했다.

## 헷갈렸던 점

`@AuthenticationPrincipal`이 사용자 정보를 어디서 가져오는지 다시 확인했다.   
JWT 필터가 유효한 토큰에서 인증 객체를 생성해 `SecurityContext`에 저장하고, Controller에서는 해당 인증 Principal을 전달받아 사용하는 구조다.

`@WebMvcTest`에서도 Security Filter가 동작하는지 헷갈렸다.   
Controller만 테스트하더라도 Security 설정과 Filter가 함께 적용될 수 있어   
인증 사용자와 CSRF, 필터가 의존하는 Bean까지 테스트 환경에 맞게 준비해야 했다.

JPA Auditing을 사용하면 엔티티 단위 테스트에서도 `createdAt`과 `updatedAt`이 자동으로 설정되는지도 헷갈렸다.   
Auditing은 실제 영속성 Context를 통해 저장·수정될 때 동작하므로 단순 객체 생성 테스트에서 해당 값을 검증해서는 안 된다.

현재 RDB Inventory에서는 재고 차감 후 Purchase 저장이 실패할 때 별도 보상 코드가 필요한지도 고민했다.   
같은 DB 트랜잭션에 참여하므로 전체 작업이 롤백되지만, Redis Inventory로 변경하면 Redis까지 함께 롤백되지 않아 별도의 재고 보상이 필요하다.

DB Unique Constraint와 멱등성의 차이도 다시 구분했다.   
Unique Constraint는 중복 데이터 생성을 막는 마지막 방어선이지만,   
동일 요청을 여러 번 보냈을 때 최초와 동일한 결과를 반환하는 완전한 멱등성까지 제공하지는 않는다.

`paymentKey`를 받으면 결제가 완료된 것인지 처음에는 흐름이 헷갈렸다.   
카드 인증 성공은 결제 승인을 요청할 수 있는 상태이고, 서버에서 Toss 승인 API가 성공해야 실제 결제가 완료된다.

`permitAll()`로 결제 테스트 경로를 열면 POST 요청도 그대로 통과한다고 생각했지만 인증 허용과 CSRF 검사는 별개였다.   
테스트 POST 요청에는 별도로 CSRF 정책을 처리해야 했다.

외부 결제 승인 성공 후 내부 DB 저장이 실패하면 `@Transactional`로 Toss 결제까지 취소할 수 있는지도 고민했다.   
외부 PG는 DB 트랜잭션에 참여하지 않으므로 결제 상태를 다시 조회하거나 취소 API를 호출하는 보상 처리가 필요하다.

## 오늘 느낀 점

오늘은 Purchase 기능이 Service 내부 로직에서 실제 인증 API와 테스트 가능한 구조까지 확장되면서 구매 기능의 기본 흐름을 한 단계 마무리할 수 있었다.

특히 단위 테스트뿐 아니라 Security가 포함된 Controller 테스트와 별도의 테스트 환경을 구성하면서,   
기능 코드가 맞는 것과 실제 애플리케이션 환경에서 안정적으로 검증할 수 있는 것은 다른 문제라는 점을 느꼈다.

Toss Payments도 문서로 흐름만 확인하는 것보다 실제 카드 인증부터 승인 · 조회 · 취소까지 직접 실행해 보면서   
인증과 승인 단계가 분리되는 이유와 외부 PG 상태를 별도로 관리해야 하는 이유를 더 명확하게 이해할 수 있었다.

Purchase, Redis 재고와 Payment는 각각 독립적으로는 구현할 수 있지만   
최종적으로 연결하면 서로 다른 저장소와 외부 시스템 사이의 정합성 문제가 핵심이 될 것 같다.

현재는 Purchase 기본 구현과 Toss 단독 연동을 먼저 완료했으므로,   
다음에는 Redis Inventory가 준비된 뒤 재고 차감과 Purchase 저장 사이의 실패 보상 및 중복 요청 처리를 먼저 안정화하고 결제를 연결해야겠다.
