## 오늘 배운 내용

오늘은 Y:ON 최종 팀 프로젝트 발표를 위한 PPT 제작을 중심으로 작업했다.   
프로젝트의 문제 정의와 주요 기능, 시스템 아키텍처, 기술적 문제 해결 과정 및 성능 개선 결과를 발표 흐름에 맞게 정리했다.

특히 통합 검색 품질 개선, 개인화 추천 성능 최적화, 공고 상세 조회 SQL 최적화 경험을 Before/After 그래프와 비교 자료로 구성했다.   
단순한 기능 소개보다 문제 원인과 기술적 선택의 근거, 실제 측정 결과를 전달하는 데 중점을 두었다.

이후 청년정책의 다중 분류 데이터가 검색·추천에 정확하게 반영되도록 개선했다.   
공고 유형별 분류 필터를 구분하고, 정규화된 분류를 API 응답과 프런트엔드 화면에도 일관되게 적용했다.

## 실습 및 과제

> 최종 팀 프로젝트 PPT 발표자료 제작

미리캔버스를 활용하여 Y:ON의 서비스 기획, 주요 기능, 시스템 아키텍처 및 팀 프로젝트 성과를 발표용 슬라이드로 제작했다.

서비스가 해결하려는 문제를 정보의 분산, 복잡한 신청 조건, 변경 정보 확인의 어려움으로 구분하고,   
사용자 조건 등록부터 통합 검색·신청 가능성 확인·개인화 추천·변경 알림으로 이어지는 흐름을 정리했다.

주요 기능에서는 청년정책과 직업훈련의 분류·날짜 기준을 통합하는 검색과 신청 조건의 원문 근거를 제공하는 상세 조회를 설명했다.

개인화 추천은 신청 가능성 `ELIGIBLE`·`POSSIBLY_ELIGIBLE`과 관심 적합도 HIGH·MEDIUM에 따른   
A~D 우선순위 및 공고 유형별 임박 기준을 시각화했다.

시스템 아키텍처에서는 AWS EC2 역할 분리, S3·CloudFront 기반 프런트엔드 제공, Terraform·GitHub OIDC 기반 인프라·배포 관리,   
gRPC·SQS 통신과 PostgreSQL Primary·Streaming Replica 구조를 정리했다.

또한 팀원별 담당 영역과 협업 과정을 구분하고, 실제 구현 성과와 서비스의 기대 효과, 현재 인프라 구조의 한계가 혼동되지 않도록 구성했다.

> 주요 기술적 성과 및 성능 개선 시각화

본인이 담당한 통합 검색, 개인화 추천, 공고 상세 조회의 기술적 문제 해결 과정을 발표용 자료로 정리했다.

통합 검색에서는 기존 `LIKE` 방식의 후보 누락과 관련도 정렬 문제를 개선한 B1 후보 확장·B2 규칙 기반 랭킹을 설명했다.   
BM25 비교 실험에서 일관된 품질 우위를 확인하지 못했으며, 운영 복잡도와 데이터 동기화 비용을 고려해 B2를 유지한 이유를 정리했다.

개인화 추천에서는 Java의 전체 후보 탐색을   
PostgreSQL Native SQL과 `row_number()` 기반 후보 선정으로 변경한 구조를 Before/After로 비교했다.

기존 측정 결과인 응답 시간 9.8~12.4초에서 0.57~1.04초, SQL 실행 횟수 3,951~4,933회에서 4~11회로 감소한 결과를 그래프로 표현했다.   
주요 시나리오에서 약 11~17배 개선됐지만 실제 다중 사용자 부하 테스트 결과는 아니라는 점도 구분했다.

공고 상세 조회에서는 불필요한 요약 정보 재조회로 발생하는 중복 SQL을 경량 `EligibilityDecision`으로 해결한 과정을 정리했다.

청년정책 SQL 10→7회, 직업훈련 SQL 11→8회 및 평균 응답 시간 약 30% 단축 결과를 Before/After 그래프로 구성했다.

이를 통해 기존에 수행한 성능 개선 결과를 단순히 수치로 나열하기보다 문제 원인과 해결 방법, 측정 범위를 함께 전달할 수 있도록 했다.

> 청년정책 다중 분류 검색·추천 매칭 개선

기존 청년정책의 대·중분류는 `일자리,교육`, `취업,미래역량강화`처럼 쉼표로 연결된 문자열로 저장되어 있었다.

이로 인해 특정 분류 검색이나 사용자 관심 분야 매칭에서 일부 공고가 누락되는 문제가 발생했다.

이에 현재 공고 버전의 `opportunity_categories`를 기준으로 검색 필터와 추천 매칭을 변경했다.

대분류와 중분류를 개별 문자열로 비교하지 않고 실제 분류 쌍을 기준으로 매칭하여 잘못된 조합이 검색 결과에 포함되지 않도록 했다.

또한 청년정책과 직업훈련에서 분류명이 겹치는 문제를 해결하기 위해 공고 유형별 필터를 구분했다.

PostgreSQL 통합 테스트로 다중 분류 검색과 추천 매칭을 검증하고, 관련 시나리오를 필수 테스트 정책에 추가했다.   
검색 API 변경에 영향을 받은 레플리카 통합 테스트의 요청 형식도 수정했다.

> 청년정책 분류 API 응답 및 화면 표시 개선

검색·추천에서는 정규화된 분류를 사용하지만, 검색 결과와 상세 화면에는 쉼표로 연결된 원본 문자열이 표시되는 문제를 발견했다.

프런트엔드에서 문자열을 직접 분리하면 정규화 규칙이 중복되고 실제 분류 관계와 달라질 수 있다고 판단했다.

이에 기존 API 필드를 유지하면서 정규화된 대·중분류 쌍을 `categories` 필드로 추가했다.

검색·저장 목록·추천에서는 결과가 확정된 후 분류 정보를 일괄 조회하고, 상세에서는 현재 버전의 분류를 조회하도록 구현했다.

분류 조회 추가 후 검색 SQL은 4→5회로 증가했으며, 저장 목록 3회, 추천 11회, 청년정책 상세 8회로 측정됐다.

청년정책 1건과 4건을 조회했을 때 SQL 실행 횟수가 동일함을 검증하여 N+1 문제가 발생하지 않도록 했다.

프런트엔드에서는 검색 결과·상세·홈 추천·저장 목록에 공통 분류 표시 함수를 적용했다.   
동일한 대분류를 묶고 실제 관계가 확인된 중분류만 표시하도록 구성했다.

이를 통해 정확한 분류 정보를 제공하기 위한 추가 SQL 1회는 허용하되, 조회 공고 수에 비례하는 불필요한 쿼리는 발생하지 않도록 검증했다.

## 헷갈렸던 점

청년정책의 대분류와 중분류를 각각 비교해도 정확한 검색 결과를 얻을 수 있는지 확인했다.   
다중 분류에서는 실제 연결된 분류 쌍을 기준으로 매칭해야 잘못된 조합을 방지할 수 있다는 점을 이해했다.

분류 조회를 추가하면서 SQL 실행 횟수가 증가하는 것이 성능 문제인지 검토했다.   
SQL 1회 증가 자체보다 조회 공고 수에 따라 추가 쿼리가 반복되는지를 확인하는 것이 중요하며,   
일괄 조회를 통해 N+1 문제를 방지할 수 있다는 점을 확인했다.

기존 관심 분야 값을 정규화하면 검색·추천 문제도 함께 해결되는지 검토했다.   
해당 데이터를 사용하는 변경 추적 기능에도 영향을 줄 수 있으므로 데이터 변경 전 의존 관계를 확인해야 한다는 점을 이해했다.

## 오늘 느낀 점

오늘은 최종 프로젝트 PPT를 제작하면서 구현한 기능을 많이 보여주는 것보다   
실제로 어떤 문제를 발견하고 해결했는지 명확하게 전달하는 것이 중요하다고 느꼈다.   
특히 성능 개선은 Before/After 수치로, 기술 선택은 비교 실험과 선택 근거로 표현해야 핵심 내용을 효과적으로 전달할 수 있었다.

또한 프로젝트 전체 성과와 본인이 직접 담당한 작업을 구분하고, 실제 구현 결과와 향후 기대 효과가 혼동되지 않도록 정리하는 과정이 필요했다.

청년정책 다중 분류 개선에서는 데이터 정규화가 검색·추천뿐 아니라   
API 응답과 화면 표시, 사용자 관심 분야 및 변경 추적에도 영향을 줄 수 있다는 점을 확인했다.   
이를 통해 공통 데이터를 변경할 때는 관련 기능의 의존 관계까지 고려해야 한다는 점을 배웠다.
