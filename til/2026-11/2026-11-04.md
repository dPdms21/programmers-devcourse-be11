## 실습 및 과제

> 이력서·포트폴리오·GitHub README 내용 검증

이력서 V2와 포트폴리오 허브, 프로젝트 상세 페이지, GitHub README의 내용과 측정 수치가 일치하는지 확인했다.

Gudit 동시성 테스트에서 기존에 사용한 비정상 응답 40건→0건은 코드 개선이 아니라   
`PURCHASE_004` 응답의 테스트 분류 기준 변경에 따른 결과임을 확인했다.

이에 해당 수치를 개선 성과에서 제외하고,   
실제 중복 승인 9건→0건과 비관적 락 적용 후 발생한 500 오류를 락 순서 통일로 해결한 과정을 중심으로 수정했다.

또한 Case 7의 응답 지연 3.8초→0.68초처럼 기존 기록에 근거가 있지만 이력서에 빠져 있던 성과를 추가했다.

이를 통해 측정값의 변화가 실제 코드 개선에 따른 것인지 확인하고, 수치의 출처와 원인을 명확하게 설명해야 한다는 점을 배웠다.

> 프로젝트별 기술적 표현 및 기여 범위 수정

S:ote의 Wake 호출은 서버 요청 자체가 비동기로 실행되는 구조가 아니므로, 프런트엔드에서 응답을 기다리지 않는 동작으로 표현을 수정했다.

채록의 OOM 문제는 단일 원인을 확정하지 못했으므로 완전히 해소했다고 표현하지 않고, 측정 조건에서 재현되지 않았다는 범위로 정리했다.

Kotlin 전환율 98.1%는 팀 전체 성과임을 명시하고, 본인이 담당한 61개 파일의 전환 작업과 구분했다.

또한 프로젝트 기술 스택과 이력서의 Skills를 실제 기여 및 설명 가능한 경험을 기준으로 검토했다.

Gudit의 Toss Payments 연동은 결제 승인과 동시성 제어 문제를 설명하는 핵심 맥락이므로 유지하되,   
테스트 키 사용과 성능 측정 시 stub 적용 조건을 구분했다.

이를 통해 기술적 표현의 정확성과 실제 기여 범위가 문서의 신뢰성을 결정한다는 점을 확인했다.

> Y:ON 프로젝트 포트폴리오 정리

Y:ON의 검색·상세 조회·개인화 추천·행동 이벤트 관련 기술 문서를 검토하고, 포트폴리오에서 강조할 대표 경험을 선정했다.

가장 중요한 경험으로 개인화 추천 후보 선정 구조 개선을 선택했다.

기존에는 짧은 SQL을 수천 번 반복하는 구조가 병목이었으며, 숨김 조회 일괄화와 배치 크기 변경 실험에서 기대한 성능 개선을 얻지 못했다.   
이후 후보 선정을 DB로 이동하고 기존 구현과의 결과 동등성을 검증한 과정을 핵심 이야기로 정리했다.

통합 검색은 PostgreSQL JIT 컴파일이 주요 지연 원인으로 드러난 분석 과정과 B1·B2 검색 개선을 중심으로 구성했다.

상세 조회는 SQL 감소와 평균 응답 시간 약 30% 개선이라는 수치뿐 아니라, 반복 측정을 통해 성능 차이를 검증한 방법을 강조했다.

행동 이벤트에서는 `AFTER_COMMIT`과 `REQUIRES_NEW` 조합의 커넥션 점유 문제를 분석하고,   
기록 시점을 변경한 뒤 HikariCP 풀 크기 1 환경에서 검증한 경험을 정리했다.

또한 저장 목록 API의 문서와 실제 코드 경로가 일치하지 않는 부분을 확인하고, 출처가 불명확한 성능 수치는 추가 검증이 필요하다고 판단했다.

이를 통해 상세 기술 문서는 근거 자료로 유지하고, 포트폴리오에는 문제 해결 과정이 뚜렷한 경험을 우선 배치하도록 했다.

> IT 포트폴리오 작성 가이드 특강

특강에서는 이력서와 포트폴리오의 목적이 다르다는 점을 학습했다.

이력서는 지원자의 핵심 역량과 성과를 빠르게 전달하는 문서이고, 포트폴리오는 해당 결과에 도달한 기술적 문제 해결 과정을 증명하는 자료다.

따라서 기능 목록이나 기술 스택을 나열하기보다 문제 정의, 해결 방법 탐색, 실행, 결과 검증의 흐름으로 대표 경험을 구성해야 한다는 점을 확인했다.

특히 성능 개선에서는 측정 환경과 조건을 명시하고, 여러 개선 방법의 효과를 구분해야 신뢰할 수 있는 결과를 제시할 수 있다는 점을 배웠다.

또한 병목 원인과 호출 구조는 다이어그램으로 설명하고, PR·테스트·측정 자료 등 실제 근거를 연결하는 것이 중요하다는 점을 정리했다.

> 포트폴리오 컨설팅 및 개선 방향 검토

포트폴리오 컨설팅에서는 작성된 내용이 충분하더라도 첫 페이지에서 핵심 경험이 바로 드러나지 않으면 전달력이 떨어질 수 있다는 피드백을 받았다.

이에 첫 화면에서 대표적인 기술적 문제와 성과를 보여주고, 상세 페이지에서 원인 분석과 해결 과정을 설명하는 방향을 검토했다.

Gudit은 결제 동시성 제어의 성공·실패 원인과 락 동작을 구체화하고, 단계별 부하 테스트와 응답 시간·TPS 측정 결과를 보완할 필요가 있음을 확인했다.

채록은 Warm-up의 실제 동작과 외부 API 호출 구조, OOM 분석 과정을 더 명확하게 정리하기로 했다.

또한 기술 선택 이유를 별도의 목록으로 나열하기보다 문제 해결 과정 안에서 자연스럽게 설명하고, 본문을 반복하는 결론은 줄이도록 했다.

이를 통해 포트폴리오는 모든 경험을 보여주는 자료가 아니라, 면접에서 깊이 있게 설명할 수 있는 대표 경험을 선별하는 자료라는 점을 이해했다.

---

> 취업 멘토링 - 자기소개서 및 기술 면접 준비

취업 멘토링을 통해 자기소개서 작성과 기술 면접 준비 방향을 학습했다.

지원 동기는 단순히 사용한 기술을 강조하기보다 지원 기업의 도메인과 직무에 대한 이해를 바탕으로 작성해야 한다는 점을 확인했다.

프로젝트 경험에서는 전체 아키텍처를 이해하되 본인의 담당 영역과 팀 전체 성과를 구분하고,   
기술적으로 어려웠던 문제는 가설 수립과 검증 과정, 최종 선택의 근거를 중심으로 설명하는 것이 중요하다는 점을 배웠다.

자기소개서는 핵심 내용을 먼저 전달하는 두괄식으로 작성하고,   
주요 프로젝트 경험을 미리 정리하여 기업별 요구사항에 맞게 활용하는 방법을 학습했다.

기술 면접에서는 정답뿐 아니라 판단의 근거를 논리적으로 설명하고 꼬리질문에 대응하는 능력이 중요하다는 점을 확인했다.   
모르는 내용은 솔직하게 인정하되, 자신이 설명한 기술의 동작 원리와 선택 이유는 충분히 준비해야 한다는 조언을 들었다.

또한 현업의 기능 조직과 목적 조직의 차이, A/B 테스트, 팀원 간 업무 공유 및 장애 대응 사례를 통해   
개발자의 역할이 기능 구현뿐 아니라 협업과 안정적인 서비스 운영까지 이어진다는 점을 이해했다.

## 헷갈렸던 점

이력서와 포트폴리오에 같은 프로젝트 경험을 어느 정도까지 반복해서 작성해야 하는지 고민했다.   
이력서는 핵심 역할과 성과를 간결하게 전달하고,   
포트폴리오는 문제 해결 과정과 근거를 구체적으로 설명하는 문서이므로 같은 경험이라도 목적에 따라 설명의 깊이를 달리해야 한다는 점을 이해했다.

포트폴리오에 기술적 경험을 얼마나 자세히 작성해야 하는지도 고민했다.   
모든 구현 과정을 나열하기보다 중요한 문제를 선별하고,   
문제 정의 → 해결 방식 설계 → 실행 → 피드백의 4단계로 정리하는 것이 효과적이라는 점을 확인했다.

## 오늘 느낀 점

오늘은 기존 이력서와 포트폴리오, GitHub README를 수정하면서 같은 경험도 어떤 관점에서 정리하느냐에 따라 전달력이 달라질 수 있다는 점을 느꼈다.

특히 포트폴리오 특강을 통해 단순히 구현한 기능이나 사용한 기술을 나열하기보다,   
문제 정의 → 해결 방식 설계 → 실행 → 피드백의 4단계로 문제 해결 경험을 정리하는 것이 중요하다는 점을 배웠다.   
앞으로 포트폴리오를 작성할 때 이 구조를 기준으로 내용을 구성해야겠다고 생각했다.

포트폴리오 컨설팅도 현재 문서의 부족한 부분을 객관적으로 확인하는 데 도움이 됐다.   
특히 첫 페이지의 전달력과 대표 경험의 구체적인 설명을 보완할 필요가 있다는 피드백을 받았으며, 이를 바탕으로 기존 포트폴리오를 개선해야겠다.

---

취업 멘토링에서는 좋은 프로젝트 경험을 갖는 것과 그 경험을 면접에서 설득력 있게 설명하는 것은 별개의 역량이라는 점을 느꼈다.   
앞으로는 프로젝트의 문제 해결 과정을 정리하는 것뿐 아니라 기술 선택의 근거와 시행착오를 두괄식으로 설명하고,   
예상되는 꼬리질문에도 답할 수 있도록 준비해야겠다고 생각했다.
