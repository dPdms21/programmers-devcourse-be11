## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습에서 Querydsl을 이용한 게시글 동적 검색과 댓글 수 조회 구조를 학습했다.

기존 Spring Data JPA의 메서드 이름 쿼리는 조건이 많아질수록 메서드명이 길어지고,   
제목·작성자·날짜처럼 선택적으로 들어오는 검색 조건을 처리하기 어렵다.   
Querydsl은 문자열 JPQL이 아니라 `QBoard`, `QMember`, `QComment` 같은 Q타입을 사용해   
자바 코드로 쿼리를 작성하므로 필드명 오타나 타입 오류를 컴파일 시점에 확인할 수 있다.

Q타입은 직접 작성하는 클래스가 아니라,   
`@Entity`가 붙은 클래스를 Querydsl annotation processor가 컴파일 시점에 읽어서 자동 생성하는 클래스다.   
`QBoard cannot find symbol` 오류는 Q타입이 아직 생성되지 않았거나,   
Querydsl 의존성·annotationProcessor 설정이 잘못되었거나, `compileJava`가 실행되지 않았을 때 발생할 수 있다.

Repository 구조에서는 기본 CRUD를 담당하는 `BoardRepository`,   
직접 구현할 검색 메서드를 선언하는 `BoardRepositoryCustom`, Querydsl 검색 로직을 구현하는 `BoardRepositoryImpl`을 분리했다.   
`BoardRepository`가 `BoardRepositoryCustom`을 함께 상속해야 기본 JPA 메서드와 커스텀 검색 메서드를 같은 Repository에서 사용할 수 있다.

댓글은 댓글 작성 기능이 아니라 게시글 목록에서 댓글 수를 함께 보여주기 위한 구조로 추가했다.   
`Comment` 엔티티는 `Board`와 `@ManyToOne(fetch = FetchType.LAZY)` 관계를 가지며,   
LAZY는 연관된 게시글을 바로 가져오지 않고 실제로 필요할 때 조회하는 지연 로딩 설정이다.

PBL Mission 07에서는 Spring Boot 기반 TODO REST API를 구현하며 Controller, Service, Repository, DTO, 예외 처리 흐름을 학습했다.   
이전 미션들이 순수 Java 도메인 로직 중심이었다면,   
이번 미션은 HTTP 요청과 응답, 상태 코드, JSON 에러 응답까지 포함해 API 계약을 맞추는 것이 핵심이었다.

Repoary 프로젝트에서는 GitHub OAuth 로그인과 JWT 인증 흐름을 구현했다.   
GitHub 로그인은 단순히 로그인 화면으로 이동하는 것이 아니라,   
로그인 URL 생성, GitHub 승인, callback code 수신, access token 교환, GitHub 사용자 정보 조회 순서로 진행된다는 점을 확인했다.

## 실습 및 과제

> Spring Boot jpa-board Querydsl 검색 실습

Querydsl을 사용해 게시글 목록 동적 검색을 구현했다.

`JPAQueryFactory`를 사용해   
`select()`, `from()`, `leftJoin().on()`, `where()`, `orderBy()`, `offset()`, `limit()`, `fetch()` 흐름으로 게시글 목록을 조회했다.   
`select()`는 조회할 값을 지정하고, `from()`은 기준 엔티티를 정하며,   
`leftJoin().on()`은 게시글 작성자 아이디와 회원 아이디를 연결해 작성자 이름을 함께 조회하는 역할을 한다.

검색 조건은 `BooleanExpression` 메서드로 분리했다.   
제목 검색은 `contains()`로 부분 일치 조건을 만들고, 작성자 아이디는 `eq()`로 정확히 일치 조건을 만들었다.   
작성일 범위는 `goe()`, `loe()`를 사용해 시작일 이후, 종료일 이전 조건을 만들었다.

조건 값이 없으면 `null`을 반환하고, Querydsl의 `where()`는 `null` 조건을 무시한다.   
이를 통해 입력된 조건만 적용되는 동적 검색을 구현할 수 있었다.

> Spring Boot jpa-board 댓글 수 조회 실습

게시글 목록에서 댓글 수를 함께 조회하는 구조를 확인했다.

게시글별 댓글 수는 `QComment`와 `JPAExpressions` 서브쿼리를 사용해   
`comment.board.id`가 현재 게시글 id와 같은 댓글 개수를 조회하는 방식으로 계산했다.

목록 응답은 Entity 전체를 반환하지 않고 `Projections.constructor()`를 사용해 `BoardListItemResponseDto`로 바로 조회했다.   
이를 통해 게시글 id, 제목, 작성자 아이디, 작성자 이름, 댓글 수, 작성일처럼 목록에 필요한 값만 가져올 수 있었다.

현재 페이지 데이터는 `fetch()`로 조회하고, 전체 개수는 count 쿼리와 `fetchOne()`으로 조회한 뒤   
`PageableExecutionUtils.getPage()`를 사용해 `Page<BoardListItemResponseDto>` 형태로 반환했다.

> PBL Mission 07 TODO API 구현

Spring Boot 기반 TODO REST API를 구현했다.

`TodoController`는 `POST /todos`, `GET /todos/{id}`, `GET /todos`, `PATCH /todos/{id}/complete` 요청을 받아   
`TodoService`에 위임하는 역할을 했다.   
Controller가 직접 저장소를 조회하거나 TODO 상태를 변경하지 않고 Service에 넘기도록 구성했다.

`TodoService`에서는 TODO 생성, 단건 조회, 목록 조회, 완료 처리 로직을 구현했다.   
생성 요청에서는 `@RequestBody(required = false)` 때문에 요청 body가 없으면 request 자체가 `null`로 들어올 수 있으므로,   
`request == null`, `request.title() == null`, `request.title().isBlank()`를 함께 검증했다.

단건 조회에서는 `TodoRepository.findById(id)`가 존재하지 않는 id에 대해 `null`을 반환하므로,   
결과를 바로 DTO 변환 메서드에 넣지 않고 먼저 변수에 담아 null 여부를 확인했다.   
TODO가 없으면 404 예외를 던지고, 있으면 `TodoResponse`로 변환해 반환했다.

완료 처리에서는 먼저 id로 TODO를 조회하고, 존재하지 않으면 404 예외를 던졌다.   
이미 완료된 TODO에 다시 완료 요청이 들어오면 상태 충돌이므로 409 응답으로 처리했다.   
정상인 경우에는 Repository의 `markCompleted(id)`를 호출해 완료 상태로 갱신했다.

이번 미션에서는 공개 테스트 2개와 hidden review 6개를 모두 통과하며   
TODO 생성, 조회, 목록 조회, 완료 처리, 입력 검증, 404·409 예외 처리, DTO 변환, 계층 분리 구조가 정상적으로 동작함을 확인했다.

> Repoary GitHub OAuth 로그인 구현

Repoary 프로젝트에서 GitHub OAuth 로그인 흐름을 구현했다.

`GET /api/auth/github/login`은 실제 로그인을 처리하는 API가 아니라 GitHub 인증 페이지로 이동할 URL을 만들어주는 역할이다.   
사용자가 GitHub에서 승인하면 GitHub가 `redirect_uri`로 임시 `code`를 전달하고, 백엔드는 이 `code`를 GitHub access token으로 교환한다.

GitHub access token 요청에서는 요청 본문 형식도 중요했다.   
Java record 객체를 그대로 JSON body로 보내는 방식보다,   
`client_id`, `client_secret`, `code`, `redirect_uri` 값을 form 방식으로 전달하는 흐름이 적합하다는 점을 확인했다.   
Java 필드명인 `clientId`, `clientSecret`과 GitHub가 기대하는 snake_case 파라미터명이 다르면 정상 처리되지 않을 수 있다.

GitHub 사용자 정보는 access token을 이용해 GitHub `/user` API를 호출해서 조회했다.   
MVP에서는 이메일이나 프로필 이미지는 저장하지 않고, GitHub 고유 ID와 로그인 아이디만 `users` 테이블에 저장한다.   
같은 계정으로 다시 로그인했을 때 새 사용자가 중복 생성되지 않고 기존 사용자 id가 반환되도록 `github_id`를 기준으로 사용자를 식별했다.

> Repoary JWT 인증 구현

Repoary 자체 인증을 위해 GitHub access token을 그대로 사용하지 않고, 로그인 성공 후 Repoary JWT를 별도로 발급했다.

JWT에는 사용자 식별자인 `userId`를 `sub`에 담고, 이후 요청에서는 `Authorization: Bearer {accessToken}` 헤더를 통해 인증하도록 구성했다.   
브라우저 주소창으로는 Authorization 헤더를 붙일 수 없기 때문에,   
JWT가 필요한 API는 Postman처럼 헤더를 직접 넣을 수 있는 도구로 테스트해야 한다는 점을 확인했다.

Spring Security에서는 공개 API와 인증이 필요한 API를 구분했다.   
`/api/auth/**`, `/api/health`, Swagger 관련 경로는 공개하고, `/api/users/me`는 JWT 인증이 있어야 접근하도록 구성했다.   
JWT 필터에서는 Authorization 헤더에서 Bearer 토큰을 꺼내 검증하고,   
토큰의 `sub` 값에서 사용자 ID를 추출해 SecurityContext에 인증 정보를 저장했다.

`/api/users/me`는 userId를 파라미터로 받는 임시 API로 만들 수도 있었지만, JWT 인증을 사용할 예정이므로 처음부터 JWT 기반으로 구현했다.   
이를 통해 임시 구현을 줄이고 실제 인증 흐름에 가까운 구조로 진행했다.

GitHub 저장소 목록 조회 단계로 넘어가기 전에 GitHub access token 저장이 필요하다는 점도 확인했다.   
Repoary JWT는 Repoary 서버 인증용이고, GitHub API를 호출하려면 GitHub에서 발급한 access token이 필요하므로   
다음 단계에서는 GitHub access token 저장 또는 관리 방식이 필요하다.

## 헷갈렸던 점

Q타입이 직접 만드는 클래스인지 헷갈렸다.   
`QBoard`는 직접 작성하는 클래스가 아니라 Querydsl annotation processor가 Entity를 기반으로 컴파일 시점에 자동 생성하는 클래스다.   
따라서 Q타입을 찾을 수 없다는 오류가 발생하면 의존성, annotationProcessor 설정, Gradle 빌드 실행 여부를 확인해야 한다.

Querydsl의 `where()`에 `null` 조건이 들어가도 되는지 헷갈렸다.   
Querydsl은 `where()`에 전달된 `null` 조건을 무시하므로,   
조건 값이 없을 때 `BooleanExpression` 메서드에서 `null`을 반환하면 입력된 검색 조건만 동적으로 적용할 수 있다.

`fetch = FetchType.LAZY`의 의미도 다시 확인했다.   
LAZY는 연관 엔티티를 즉시 조회하지 않고, 실제로 해당 연관 객체가 필요할 때 조회하는 지연 로딩 설정이다.

PBL에서는 `record` 접근자 방식이 헷갈렸다.   
`Todo`가 record이면 Lombok getter처럼 `getId()`, `getTitle()`, `isCompleted()`를 사용하는 것이 아니라   
`id()`, `title()`, `completed()`, `createdAt()` 형태의 접근자를 사용해야 한다.

`@RequestBody(required = false)` 때문에 요청 body가 없을 때 request가 null로 들어올 수 있다는 점도 헷갈렸다.   
제목 검증을 하기 전에 request 자체가 null인지 먼저 확인해야 한다.

GitHub OAuth에서는 로그인 code를 새로고침해서 다시 사용할 수 있는지 헷갈렸다.   
OAuth code는 한 번 사용하면 다시 사용할 수 없으므로 callback URL을 새로고침하면 안 된다.

Repoary JWT와 GitHub access token의 역할도 헷갈렸다.   
Repoary JWT는 Repoary 서버 인증용이고, GitHub API 호출에는 GitHub에서 발급한 access token이 필요하다.   
두 토큰은 목적이 다르므로 저장과 사용 흐름을 분리해서 봐야 한다.

## 오늘 느낀 점

Querydsl을 사용해 보니 조건이 많아질수록 메서드 이름 쿼리보다 자바 코드로 쿼리를 조립하는 방식이 더 유연하다는 점을 느꼈다.   
특히 조건 메서드를 분리해 null을 반환하는 방식으로 동적 검색을 처리하는 흐름이 인상적이었다.

댓글 수 조회처럼 목록 화면에 필요한 집계 값이 추가되면 단순 Entity 조회만으로는 한계가 있고,   
DTO로 필요한 값만 조회하는 구조가 중요하다는 점을 느꼈다.

PBL Mission 07을 진행하면서 Spring Boot API는 단순히 메서드 결과만 맞추는 것이 아니라,   
HTTP 상태 코드, JSON 에러 응답, 요청 검증, DTO 변환까지 API 계약을 맞추는 것이 중요하다고 느꼈다.

Repoary GitHub OAuth와 JWT 인증을 구현하면서 외부 인증과 서비스 자체 인증을 분리해서 생각해야 한다는 점을 배웠다.   
GitHub access token은 GitHub API 호출을 위한 토큰이고,   
Repoary JWT는 Repoary 서버에 접근하기 위한 토큰이므로 역할을 명확히 나누는 것이 중요하다.

이슈 관리에서는 이미 끝난 1주차 초기 세팅 이슈는 기록용으로 만들고 닫고,   
2주차 GitHub 연동 이슈는 OAuth 로그인, JWT 인증, 저장소 목록 조회, 저장소 연결까지 추적하는 이슈로 열어두었다.
