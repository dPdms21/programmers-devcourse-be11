## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습과 과제를 이어서 진행하면서 로그인 처리 흐름과 게시판 목록 조회 구조를 학습했다.

로그인에서는 `MemberService`가 `findByUserId()`로 회원을 조회하고,   
`Optional.filter()`로 비밀번호 일치 여부를 확인해 로그인 성공과 실패를 판단하는 흐름을 확인했다.   
로그인에 성공하면 `session.setAttribute()`로 `userId`, `userName`을 세션에 저장하고,   
실패하면 `orElseGet(LoginResponseDto::fail)`로 실패 응답을 반환했다.

`Optional.filter()`, `map()`, `orElseGet()`의 역할도 정리했다.   
`filter()`는 값이 있고 조건을 만족할 때만 값을 유지하고,   
`map()`은 값이 있을 때 다른 형태로 변환하며, `orElseGet()`은 값이 없을 때 실행할 함수를 넘기는 방식이다.   
`LoginResponseDto::fail`의 `::`는 메서드 참조이며, `fail()`을 즉시 실행하는 것이 아니라 필요할 때 실행할 메서드를 넘기는 문법이다.

게시판 목록에서는 화면을 반환하는 `BoardController`와 JSON 데이터를 반환하는 `BoardApiController`의 역할을 구분했다.   
`/` 요청은 게시판 목록 화면을 반환하고, `/api/boards` 요청은 게시글 목록과 페이징 정보를 JSON으로 반환한다.

---

Java 게시판 과제에서는 JDBC를 사용해 콘솔 기반 로그인 게시판을 구현하면서 DB 연결, SQL 실행, 계층 분리 흐름을 다시 확인했다.   
`Connection`은 DB 연결, `PreparedStatement`는 SQL 실행 준비와 `?` 값 바인딩, `ResultSet`은 `SELECT` 결과를 한 줄씩 읽는 객체다.

회원가입과 로그인에서는 DAO가 DB 조회와 검증을 담당하고, `NoticeImpl`은 사용자 입력과 메뉴 흐름을 담당하도록 분리했다.   
글 수정·삭제에서는 `WHERE id = ? AND user_id = ?` 조건을 사용해 로그인한 사용자의 글만 수정·삭제되도록 처리했다.   
회원 탈퇴에서는 작성 글 삭제와 회원 삭제가 함께 처리되어야 하므로 트랜잭션으로 하나의 작업 단위로 묶었다.

## 실습 및 과제

> Spring Boot jpa-board 로그인 실습

세션 기반 로그인 흐름을 확인했다.

로그인 요청이 들어오면 `MemberService`에서 `findByUserId()`로 회원을 조회하고,   
`Optional.filter()`를 사용해 비밀번호가 일치하는 경우에만 로그인 성공 응답으로 변환했다.

로그인 성공 시에는 세션에 `userId`, `userName`을 저장해 이후 요청에서도 로그인 사용자의 정보를 사용할 수 있도록 구성했다.

> Spring Boot jpa-board 게시판 목록 조회 실습

게시판 목록 화면과 게시판 목록 API의 역할을 분리했다.

`BoardController`는 `/` 요청에서 `board-list` 화면을 반환하고, `/write` 요청에서 글쓰기 화면을 반환한다.   
이때 세션에 저장된 `userId`, `userName`을 Model에 담아 화면에서 사용할 수 있도록 구성했다.

`BoardApiController`는 `/api/boards` 요청을 받아 게시글 목록 데이터를 JSON으로 반환한다.   
목록 조회에서는 `page`, `size` 값을 받고, Service에서 `PageRequest`를 사용해 페이지 단위로 데이터를 조회했다.

> 게시판 로그인 과제

로그인 요청 데이터 처리 방식에서 `@ModelAttribute`와 `@RequestBody`의 차이를 확인했다.

`@RequestBody`는 JSON 요청 본문을 DTO로 변환할 때 사용하고,   
`@ModelAttribute`는 HTML form 데이터처럼 `application/x-www-form-urlencoded` 형식으로 넘어온 값을 DTO에 바인딩할 때 사용한다.   

로그인 요청의 `username`은 실제 이름이 아니라 로그인 아이디 값을 담는 파라미터명이다.   
화면에서 입력한 아이디는 `LoginRequestDto.username`으로 들어오고, 서비스에서는 이 값을 이용해 DB의 `userId`를 조회한다.

> 게시판 목록 페이징 조회 과제

게시글 목록 조회에서는 `PageRequest`를 사용했다.   
화면에서는 페이지 번호를 1부터 사용하지만 Spring Data JPA의 `Pageable`은 0부터 시작하므로 `page - 1`로 변환해야 한다.   
조회 결과는 Builder를 사용해 게시글 목록, 마지막 페이지 여부, 전체 페이지 수를 담아 반환했다.

`Board` 엔티티와 Repository 타입도 확인했다.   
`@GeneratedValue(strategy = GenerationType.IDENTITY)`는 기본키 생성을 DB의 자동 증가 방식에 맡기는 설정이고,   
`columnDefinition = "TEXT"`는 게시글 본문처럼 긴 문자열을 저장하기 위해 DB 컬럼 타입을 지정하는 설정이다.

> Java 게시판 JDBC 구현 과제

JDBC를 사용해 콘솔 기반 로그인 게시판을 구현했다.

`Connection`, `PreparedStatement`, `ResultSet`의 역할을 구분하고,   
`SELECT`는 `executeQuery()`, `INSERT`, `UPDATE`, `DELETE`는 `executeUpdate()`를 사용한다는 점을 확인했다.

순수 Java 콘솔 프로그램에서는 Spring Boot처럼 `.env`를 자동으로 읽지 않으므로,    
`dotenv-java` 라이브러리를 사용해 DB 연결 정보를 읽도록 구성했다.

회원가입과 로그인에서는 DAO가 DB 조회와 검증을 담당하고, `NoticeImpl`은 사용자 입력과 메뉴 흐름을 담당하도록 역할을 분리했다.    
로그인 결과는 `SignInResponseDTO`로 전달해 아이디 없음, 비밀번호 불일치, 로그인 성공 상태를 구분했다.

글 수정과 삭제에서는 글 번호만 기준으로 처리하지 않고,   
`WHERE id = ? AND user_id = ?` 조건을 사용해 로그인한 사용자의 글만 수정·삭제되도록 처리했다.

회원 탈퇴에서는 회원이 작성한 글 삭제와 회원 삭제를 트랜잭션으로 묶어 처리했다.   
두 DB 작업 중 하나만 성공하면 데이터가 애매해질 수 있으므로 하나의 작업 단위로 처리해야 한다.

목록 조회에서는 `ContentDTO`를 사용해 DAO는 데이터만 반환하고, `NoticeImpl`에서 출력 형식을 담당하도록 분리했다.

게시글 검색과 페이징에서는 `LIKE`, `LIMIT`, `OFFSET`, `COUNT(*)`를 사용했다.   
검색은 `LIKE ?`와 `%검색어%`를 조합해 처리하고, 페이징은 `offset = (page - 1) * size`로 계산했다.

## 헷갈렸던 점

`Optional.filter()`, `map()`, `orElseGet()`의 실행 흐름이 헷갈렸다.   
값이 있는 경우 조건을 검사하고, 조건을 통과한 값만 응답 DTO로 변환하며,   
값이 없거나 조건을 통과하지 못한 경우에만 실패 응답을 생성한다는 흐름으로 정리했다.

`LoginResponseDto::fail`에서 `::`가 무엇인지 헷갈렸다.   
이는 메서드 참조이며, `fail()`을 바로 실행하는 것이 아니라 `Optional`이 비었을 때 실행할 메서드를 넘기는 문법이다.

`@ModelAttribute`와 `@RequestBody`도 헷갈렸다.   
JSON 요청은 `@RequestBody`, form 데이터 요청은 `@ModelAttribute`로 받는다는 기준을 다시 확인했다.

---

DAO에서 문자열을 만들어 반환하는 방식과 DTO를 반환하는 방식의 차이도 헷갈렸다.   
DAO는 데이터 접근을 담당하고, 출력 형식은 화면 흐름을 담당하는 쪽에서 처리하는 것이 역할 분리에 더 적절하다는 기준으로 정리했다.

글 수정·삭제에서 글 번호만 확인하면 작성자 검증이 빠질 수 있다는 점도 확인했다.   
수정·삭제 SQL에는 글 번호뿐 아니라 로그인한 사용자 아이디 조건을 함께 넣어야 한다.

## 오늘 느낀 점

로그인 기능은 단순히 아이디와 비밀번호를 비교하는 것에서 끝나는 것이 아니라,   
요청 데이터 바인딩, Service 조회, Optional 처리, 세션 저장, 응답 URL 이동까지 이어지는 흐름으로 봐야 한다고 느꼈다.

게시판 목록 조회도 화면 요청과 API 요청을 분리해서 보니 `@Controller`와 `@RestController`의 역할 차이가 더 명확해졌다.

JPA의 Entity, Repository, DTO, Pageable이 각각 어떤 위치에서 사용되는지 연결해 보면서 게시판 기능의 기본 구조를 조금 더 이해할 수 있었다.
