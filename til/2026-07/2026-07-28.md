## 오늘 배운 내용

오늘은 DB에 저장된 사용자를 Spring Security 인증 과정에 연결하고, Form Login의 로그인과 로그아웃 흐름을 완성했다.

로그인 폼에서 전송된 `userId`와 `password`는 Controller가 아니라 `UsernamePasswordAuthenticationFilter`가 가로챈다.  
이후 `AuthenticationManager`와 `DaoAuthenticationProvider`를 거치며,   
`UserDetailsService`가 DB에서 사용자를 조회하고 `PasswordEncoder`가 입력한 비밀번호와 저장된 암호화 비밀번호를 비교한다.

프로젝트의 `User` 엔티티는 Spring Security가 직접 사용하는 타입이 아니므로 `CustomUserDetails`로 감싸 `UserDetails` 표준에 맞게 변환했다.  
`getUsername()`과 `getPassword()`는 인증에 사용되고, `getAuthorities()`는 사용자의 권한을 `GrantedAuthority`로 변환해 인가 판단에 제공한다.

로그인 화면과 실제 인증 처리 경로도 구분했다.  
`GET /users/login`은 Controller가 로그인 화면을 반환하지만,   
`POST /users/login`은 `loginProcessingUrl()`에 등록된 요청이므로 보안 필터가 직접 처리한다.   
폼의 아이디 필드명이 기본값인 `username`이 아니라 `userId`이기 때문에 `usernameParameter("userId")`로 요청 파라미터 이름을 맞췄다.

로그인 성공과 실패는 커스텀 Handler에서 처리했다.  
Handler는 `DispatcherServlet`에 도달하기 전 필터 영역에서 실행되므로   
`@ResponseBody`와 `HttpMessageConverter`의 자동 JSON 변환을 사용할 수 없다.   
따라서 응답 DTO를 `ObjectMapper`로 직접 JSON 문자열로 변환해 `HttpServletResponse`에 작성해야 한다.

인증에 성공하면 `Authentication`이 `SecurityContext`에 저장되고 서버 세션을 통해 인증 상태가 유지된다.  
브라우저는 이후 요청마다 `JSESSIONID` 쿠키를 보내고, 서버는 해당 세션에서 `SecurityContext`를 복원한다.   
로그아웃은 `LogoutFilter`가 처리하며 세션을 무효화하고 `JSESSIONID` 쿠키를 삭제한다.

HTTP Basic과 Form Login의 인증 상태 관리 방식도 비교했다.  
HTTP Basic은 브라우저가 매 요청마다 `Authorization` 헤더로 자격 증명을 전송하지만,   
Form Login은 인증 성공 후 서버 세션에 인증 정보를 저장하고 브라우저가 세션 쿠키를 전송한다.

## 실습 및 과제

> DB 사용자 기반 Form Login 인증

`UserDetailsService`를 구현해 로그인 아이디로 DB 사용자를 조회하고,   
조회한 `User` 엔티티를 `CustomUserDetails`로 변환해 Spring Security 인증 과정에 연결했다.

`CustomUserDetails`에서는 사용자 아이디, 암호화된 비밀번호와 권한을 Spring Security에 제공했다.  
계정 만료, 잠금, 자격 증명 만료와 활성 상태를 확인하는 메서드는 현재 별도의 계정 상태 정책이 없으므로 모두 `true`를 반환하도록 구성했다.

BCrypt로 저장된 비밀번호는 로그인할 때 다시 인코딩해 문자열로 비교하지 않고,   
`DaoAuthenticationProvider`가 `PasswordEncoder.matches()`를 사용해 입력한 평문 비밀번호와 저장된 해시를 검증하도록 했다.

> 로그인 성공·실패와 로그아웃 처리

로그인 성공과 실패 Handler를 구현해 기존의 리다이렉트 대신 JSON 응답을 반환했다.

로그인 성공 시 `Authentication`의 `principal`에서 `CustomUserDetails`와 실제 `User`를 꺼내   
사용자 아이디와 이름, 이동할 URL을 응답했다. 화면에서 사용할 수 있도록 `userId`와 `userName`도 세션에 추가로 저장했다.

로그인 실패 시에는 `401 Unauthorized`와 공통 실패 메시지를 반환했다.  
로그아웃은 별도의 Controller를 만들지 않고 `LogoutFilter`가 처리하도록 설정했으며, 서버 세션 무효화와 `JSESSIONID` 쿠키 삭제가 수행되도록 구성했다.

> HTTP Basic과 Form Login 과제

HTTP Basic 과제에서는 인메모리 사용자를 등록하고 모든 요청에 인증을 요구하도록 설정해 기본 인증 흐름을 구현했다.

Form Login 과제에서는 회원가입, DB 사용자 조회, BCrypt 비밀번호 검증, 로그인 성공·실패 Handler와 세션 기반 인증 유지 흐름을 구현했다.  
로그인 요청은 `application/json`이 아니라 `application/x-www-form-urlencoded` 형식으로 전달하고,   
`UsernamePasswordAuthenticationFilter`가 요청 파라미터에서 `userId`와 `password`를 읽도록 설정했다.

회원가입 화면과 API, 정적 파일은 `permitAll()`로 허용하고 나머지 요청에는 인증을 요구했다.  
`anyRequest()`는 모든 요청에 일치하므로 구체적인 경로 설정보다 마지막에 작성해야 한다는 점도 확인했다.

## 헷갈렸던 점

로그인 화면 요청과 로그인 처리 요청이 같은 `/users/login` 경로를 사용해도 HTTP Method에 따라 처리 주체가 달랐다.  
`GET /users/login`은 Controller가 화면을 반환하지만,   
`POST /users/login`은 `UsernamePasswordAuthenticationFilter`가 가로채므로 로그인 처리를 위한 별도의 POST Controller가 필요하지 않았다.

`UserDetailsService`가 사용자 조회와 비밀번호 비교를 모두 담당한다고 생각하기 쉽지만, 실제 역할은 사용자 조회와 `UserDetails` 반환까지다.  
조회된 사용자의 암호화 비밀번호와 입력한 평문 비밀번호의 비교는 `DaoAuthenticationProvider`가 `PasswordEncoder`를 사용해 처리한다.

BCrypt는 같은 비밀번호를 인코딩해도 매번 다른 문자열이 생성될 수 있으므로, 로그인 시 입력 비밀번호를 다시 인코딩한 뒤 `equals()`로 비교하면 안 된다.  
`PasswordEncoder.matches()`를 사용해 평문과 저장된 해시의 일치 여부를 검증해야 한다.

Spring Security가 관리하는 인증 상태와 성공 Handler에서 세션에 직접 저장한 사용자 정보도 구분해야 했다.  
`Authentication`은 이미 `SecurityContext`와 세션에 저장되며, `userId`와 `userName`은 화면에서 편리하게 사용하기 위해 추가한 데이터다.

실패 Handler에서는 응답 DTO를 Builder로 생성한 뒤 실제 응답에 다른 빈 DTO를 전달하면 모든 필드가 비어 반환된다.  
Builder 결과를 변수에 저장하고 동일한 객체를 `ObjectMapper`에 전달해야 한다는 점을 확인했다.

## 오늘 느낀 점

Form Login은 로그인 폼만 만드는 기능이 아니라 필터, 인증 관리자, 사용자 조회, 비밀번호 검증, 성공·실패 처리와 세션 유지가 연결된 구조였다.  
각 컴포넌트의 역할을 분리해 확인하면서 로그인 요청을 Controller가 직접 처리하지 않는 이유와 `UserDetails`가 필요한 이유를 이해할 수 있었다.

Handler처럼 Controller 외부에서 실행되는 코드에서는 평소 사용하던 Spring MVC의 자동 JSON 응답 기능이 적용되지 않았다.  
같은 응답을 반환하더라도 코드가 실행되는 위치에 따라 직접 처리해야 하는 범위가 달라진다는 점을 함께 고려해야 한다.

또한 HTTP Basic과 Form Login은 모두 아이디와 비밀번호를 사용하지만, 인증 정보를 매 요청에 전달하는 방식과 서버 세션에 유지하는 방식이라는 차이가 있었다.   
인증 방식의 이름만 구분하기보다 자격 증명과 인증 상태가 어디에 저장되고 어떻게 전달되는지를 이해할 필요가 있었다.
