## 오늘 배운 내용

오늘은 Compose Bean 프로젝트의 최종 통합과 안정화 작업을 진행했다.

담당자가 구현한 상품 소프트 딜리트와 주문 배치 기능을 통합한 뒤 실패하는 테스트를 확인하고 직접 수정했다.   
이 과정에서 삭제된 상품과 주문을 어떤 요청에서 제외해야 하는지 확인하고, 상세 조회와 상태 변경에 대한 예외 검증을 보완했다.

소프트 딜리트는 삭제 시점을 기록하는 것으로 끝나는 것이 아니라   
일반 조회, 상세 조회, 수정, 재고 변경, 신규 주문과 기존 주문 이력처럼 조회 목적에 따라 삭제 데이터를 다르게 처리해야 한다.  
삭제된 주문은 일반 주문 조회, 상세 조회와 배송 상태 변경 대상에서 제외하고, 존재하지 않거나 삭제된 주문은 동일한 비즈니스 예외로 처리하도록 보완했다.

주문 배치 처리에서는 결제 상태와 그룹화 조건의 역할을 구분했다.  
`PAID`는 배치 대상 주문을 조회하는 조건이며, 실제 주문을 하나의 그룹으로 묶는 기준은 이메일과 배송지다.

조회된 주문을 병합할 때는 그룹 내 상품과 금액을 합산하고 기존 주문을 소프트 딜리트해 일반 주문 조회에서 제외한다.  
배치 테스트가 기존 데이터나 테스트 실행 순서에 영향을 받지 않도록 조건을 보완하면서,   
테스트는 단순한 실행 성공이 아니라 실제 비즈니스 규칙을 검증해야 한다는 점을 확인했다.

Slack 주문 알림에는 관리자 주문 페이지 링크를 추가했다.  
주문 생성 Service가 주문 생성 이벤트를 발행하고, 트랜잭션 커밋 이후 이벤트 리스너가 Slack 알림을 전송하는 기존 구조는 유지했다.

상품 이미지 기능에서는 이미지를 교체하거나 제거할 때 기존 로컬 파일도 함께 정리하도록 보완했다.  
외부 URL이나 이미 존재하지 않는 경로는 파일 삭제 대상에서 제외하고,   
상품 자체를 소프트 딜리트할 때는 기존 주문 이력에서 이미지 정보를 사용할 수 있도록 파일을 유지했다.

프로젝트 실행과 시연을 위한 상품 및 주문 초기 데이터도 추가했다.  
애플리케이션을 다시 실행해도 같은 데이터가 중복 생성되지 않도록 조건을 적용해 팀원들이 동일한 상태에서 기능과 화면을 확인할 수 있도록 했다.

## 실습 및 과제

> 주문 배치와 소프트 딜리트 예외 검증 보완

담당자가 구현한 주문 배치 처리와 소프트 딜리트 기능을 통합한 뒤 실패하던 테스트를 확인하고, 비즈니스 규칙에 맞게 직접 수정했다.

삭제되지 않은 주문만 조회하도록 Repository 메서드를 보완하고,   
삭제된 주문의 상세 조회와 배송 상태 변경 요청은 `OrderNotFoundException`으로 처리했다.

배치 대상은 결제가 완료된 주문으로 제한하고, 조회된 주문을 이메일과 배송지를 기준으로 그룹화하도록 역할을 구분했다.  
그룹 내 주문상품과 금액을 하나의 주문으로 합산하고, 기존 주문은 소프트 딜리트해 일반 조회에서 제외했다.

상품 이미지 용량 초과와 요청값 형식 오류도 공통 예외 응답으로 처리할 수 있도록 오류 코드와 전역 예외 처리를 보완했다.

> Slack 주문 알림 개선

신규 주문 Slack 알림에 관리자 주문 페이지 링크를 추가했다.

알림에는 주문 정보와 함께 관리자가 후속 작업을 수행할 수 있는 주문 관리 화면 주소를 포함했다.  
리스너 테스트에서는 생성된 메시지에 관리자 페이지 링크가 포함되는지 검증했다.

Slack 알림은 주문 상태를 직접 관리하는 기능이 아니라 신규 주문 발생을 알리고 관리자 화면으로 연결하는 역할로 구분했다.

> 상품 이미지 파일 정리

상품 이미지를 새 파일로 교체하거나 이미지 삭제를 요청했을 때 기존 로컬 파일도 함께 제거하도록 처리했다.

현재 이미지 URL이 로컬 업로드 경로인지 확인한 뒤 실제 파일이 존재하는 경우에만 삭제했다.  
외부 URL이거나 이미 파일이 존재하지 않는 경우에는 삭제를 시도하지 않도록 예외 상황을 구분했다.

상품 자체를 소프트 딜리트할 때는 기존 주문 이력에서 이미지 정보가 필요할 수 있으므로 파일을 삭제하지 않았다.

> 상품 및 주문 초기 데이터 추가

프로젝트 실행과 발표 시연에 사용할 상품과 주문 초기 데이터를 추가했다.

상품 데이터에는 정적 이미지 경로를 연결하고, 주문 데이터는 실제 주문 조회와 관리 화면을 확인할 수 있도록 구성했다.  
초기화 로직이 여러 번 실행돼도 동일한 데이터가 중복 저장되지 않도록 기존 데이터 여부를 확인했다.

> 상품 및 주문 화면 개선

상품 목록, 상품 관리, 주문 조회, 주문 관리와 영수증 화면의 레이아웃을 정리했다.

상품 이미지 크기와 배치, 주문 상태 표시와 금액 강조 방식을 통일하고, 실제 주문 흐름을 확인하기 쉽도록 화면 구성을 개선했다.

> 최종 문서 정리

팀장과 문서화 담당으로서 최종 구현 내용을 기준으로 기획서와 제출 문서를 정리했다.

프로젝트 개요, 서비스 흐름, 주요 정책, 예외 처리, ERD와 시스템 구성을 실제 구현과 일치하도록 검수했다.

최종 결과물은 모든 기능이 반영된 `develop` 브랜치를 기준으로 확인했다.

## 헷갈렸던 점

오늘은 여러 기능을 한꺼번에 통합하고 검수해야 해서 각 기능이 어디까지 구현되어 있고, 어떤 부분을 추가로 수정해야 하는지 계속 구분해야 했다.

특히 주문 배치와 소프트 딜리트 기능을 통합한 뒤 여러 테스트가 연쇄적으로 실패하면서, 단순히 한 테스트만 고치는 것으로 끝나지 않았다.   
삭제된 상품과 주문이 일반 조회, 상세 조회, 배송 상태 변경과 배치 처리에서 각각 어떻게 제외되어야 하는지 확인해야 했고,   
수정한 내용이 다른 테스트나 기존 기능에 영향을 주지 않는지도 계속 점검해야 했다.   
한 부분을 수정하면 다른 테스트가 실패하는 경우가 있어 전체 흐름을 반복해서 확인해야 했다.

상품 이미지 파일을 언제 삭제해야 하는지도 구분이 필요했다.   
이미지를 교체하거나 삭제를 명시적으로 요청한 경우에는 기존 로컬 파일을 제거해야 하지만,   
상품 자체를 소프트 딜리트한 경우에는 기존 주문 이력에서 이미지 정보가 필요할 수 있으므로 파일을 유지해야 했다.   
데이터의 삭제 상태와 실제 파일의 삭제 시점이 항상 같지 않다는 점을 확인했다.

초기 데이터는 애플리케이션을 실행할 때마다 같은 데이터가 다시 삽입되지 않도록 해야 했다.   
상품과 주문 데이터를 시연에 사용할 수 있는 형태로 구성하면서도 기존 데이터에는 영향을 주지 않아야 했고,   
재실행 시 중복 생성 여부와 화면에서 정상적으로 조회되는지도 함께 확인해야 했다.

화면 개선에서는 상품 이미지의 크기와 비율, 카드 안에서의 위치와 여백처럼 세부 요소를 하나씩 조정해야 했다.
세부 레이아웃을 수정한 뒤 다른 화면과의 균형을 다시 확인하는 과정을 반복했다.

코드 작업이 끝난 뒤에도 기획서, 발표 자료와 WBS의 설명이 실제 구현과 일치하는지 계속 대조해야 했다.   
결제 완료 여부는 배치 대상 조회 조건이고 이메일과 배송지는 그룹화 기준이라는 차이처럼,   
코드에서는 구분되어 있지만 문서에서는 쉽게 혼동될 수 있는 내용을 다시 확인했다.   
코드, 테스트, 화면과 문서를 동시에 맞춰야 했기 때문에 하나의 변경이 다른 결과물에 미치는 영향까지 계속 확인해야 했다.

## 오늘 느낀 점

오늘은 새로운 기능을 많이 추가하기보다 프로젝트 전체를 실제로 제출하고 시연할 수 있는 상태로 통합하고 안정화하는 데 대부분의 시간을 사용했다.

팀원이 구현한 주문 배치와 소프트 딜리트 기능을 통합한 뒤 발생한 테스트 실패를 하나씩 수정하고, 모든 테스트가 성공하도록 기능과 예외 처리 흐름을 안정화했다.  
한 부분을 수정하면 다른 조회나 상태 변경 테스트가 실패하는 경우가 있어,   
개별 테스트의 기대값만 맞추지 않고 기존 기능에 미치는 영향까지 반복해서 확인해야 했다.

Slack 알림 링크 추가, 이미지 파일 정리, 초기 데이터 구성과 화면 개선은 각각 작은 작업처럼 보이지만 실제 프로젝트 완성도에는 큰 영향을 주었다.  
관리자가 알림에서 주문 화면으로 바로 이동할 수 있어야 했고,   
이미지 교체 후 불필요한 파일이 남지 않아야 했으며, 팀원들이 동일한 데이터로 기능과 화면을 확인할 수 있어야 했다.

화면 개선에서는 상품 이미지의 크기와 비율, 위치와 여백 같은 세부 요소를 조정한 뒤 다른 화면과의 통일성을 계속 확인해야 했다.  
기능이 동작하는 상태에서 끝나는 것이 아니라 전체 서비스가 하나의 프로젝트처럼 보이도록 맞추는 과정에도 많은 시간이 필요했다.

팀장과 문서화 담당으로서 내 담당 코드만 확인하는 것이 아니라 팀원들이 구현한 기능, 테스트, 화면과 문서를 하나의 기준으로 맞춰야 했다.  
수업과 팀 작업 이후에도 기획서와 실제 구현이 일치하는지 다시 검수하면서, 최종 통합과 문서화가 기능 구현만큼 많은 집중력을 요구한다는 점을 체감했다.

처리해야 할 작업이 많아 바빴지만, 팀 전체 결과물을 끝까지 확인하고 부족한 부분을 보완해 최종 완성도를 높였다는 점에서 의미가 있었다.
