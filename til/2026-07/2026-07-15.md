## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습에서 작성자별 통계, 로그, 스케줄러를 추가하면서 단순 CRUD 이후의 운영성 기능을 학습했다.

작성자별 게시글 통계는 게시글 목록을 그대로 조회하는 것이 아니라,   
작성자를 기준으로 게시글을 묶고 각 작성자가 쓴 게시글 수를 계산하는 집계 조회다.   
이 과정에서 Querydsl의 `groupBy`, `count`, `having`, `orderBy` 흐름을 확인했다.   
`where`는 그룹화 전 개별 데이터에 조건을 거는 것이고, `having`은 `groupBy` 이후 계산된 게시글 수 같은 집계 결과에 조건을 거는 것이다.

로그는 기존 `System.out.println()` 대신 SLF4J의 `log.info()`, `log.warn()`, `log.debug()`를 사용하는 방식으로 정리했다.   
`System.out.println()`은 단순 콘솔 출력이라 로그 레벨을 구분하거나 환경별로 제어하기 어렵지만,   
SLF4J는 목적에 따라 로그 레벨을 나누어 관리할 수 있다.

스케줄러는 사용자가 API를 호출하지 않아도 정해진 시간이나 간격마다 자동으로 실행되는 작업이다.   
메인 클래스에 `@EnableScheduling`을 붙여 스케줄 기능을 활성화하고,   
실행할 메서드에 `@Scheduled`를 붙여 게시글 통계 리포트와 업로드 폴더의 고아 파일 점검 같은 배치성 작업을 실행할 수 있다.

PBL에서는 Mission 10과 Mission 11을 진행하면서 Spring Boot API에서 요청 검증과 예외 응답을 처리하는 흐름을 정리했다.   
Mission 10에서는 Bean Validation을 사용해 회원가입 요청을 검증했고,   
Mission 11에서는 여러 실패 응답을 `ErrorResponse`와 `FieldErrorResponse` 기반의 공통 구조로 표준화했다.

Repoary 프로젝트에서는 GitHub OAuth 로그인 이후 서비스를 실제로 사용할 수 있는 프론트·백엔드 흐름을 연결했다.   
GitHub 로그인, JWT 저장, 사용자 정보 조회, 저장소 목록 조회, 저장소 연결, 연결 해제, 배포 확인까지 이어지면서

> Spring Boot jpa-board 통계 기능 실습

작성자별 게시글 통계 기능을 구현했다.

작성자별 통계는 작성자를 기준으로 게시글을 그룹화하고, 각 작성자가 작성한 게시글 수를 계산하는 집계 조회다.   
Querydsl에서 `groupBy`로 작성자별 그룹을 만들고, `count`로 게시글 수를 계산했으며, `having`으로 집계 결과에 조건을 적용했다.

통계 기능을 붙이면서 `/stats`와 `/api/boards/stats/authors`의 역할 차이도 정리했다.   
`/stats`는 통계 화면 HTML을 보여주는 경로이고, `/api/boards/stats/authors`는 작성자별 게시글 수 데이터를 JSON으로 내려주는 API다.   
화면 경로와 API 경로를 분리해서 봐야 한다는 점을 확인했다.

`BoardAuthorStatsResponseDto`에는 `@QueryProjection`을 붙여 Querydsl에서 `QBoardAuthorStatsResponseDto`를 사용했다.   
QDTO는 DTO 파일을 만든다고 바로 생기는 것이 아니라, Gradle 빌드나 `compileJava` 과정에서 annotation processor가 실행되어야 생성된다.

> Spring Boot jpa-board 로그 실습

기존 출력 코드를 SLF4J 기반 로그로 변경했다.

`System.out.println()`은 단순 콘솔 출력이지만, SLF4J는 `debug`, `info`, `warn`, `error`처럼 목적에 따라 로그 레벨을 나눌 수 있다.   
이를 통해 개발 중 확인이 필요한 로그와 운영 중 주의가 필요한 로그를 구분할 수 있다.

`LoginAspect`에서는 Controller 요청을 AOP로 감싸 요청 시작, 파라미터, 완료, 실패 로그를 남기도록 구성했다.   
예외가 발생했을 때 로그만 남기고 끝내면 전역 예외 처리로 전달되지 않을 수 있으므로, 실패 로그를 남긴 뒤 예외를 다시 던져야 한다는 점을 확인했다.

> Spring Boot jpa-board 스케줄러 실습

스케줄러를 사용해 정해진 시간이나 간격마다 자동 실행되는 작업을 구성했다.

`cron`은 특정 시각에 실행할 때 사용하고, `fixedDelay`는 이전 작업이 끝난 뒤 일정 시간이 지난 후 다시 실행할 때 사용한다.   
오늘은 게시글 통계 리포트와 업로드 폴더의 고아 파일 점검 같은 배치성 작업을 확인했다.

고아 파일 점검에서는 업로드 폴더에 실제 존재하는 파일 목록과 DB 게시글들이 참조 중인 파일명을 비교했다.   
DB에서 참조 중인 파일명은 `Set`으로 모아두고, 실제 파일 목록을 돌면서 `Set`에 없는 파일을 고아 파일로 판단했다.   
`Set`을 사용하는 이유는 파일마다 포함 여부를 빠르게 확인하기 위해서다.

고아 파일은 당장 서버 오류를 만들지는 않지만, 게시글에서 더 이상 사용하지 않는 첨부파일이 디스크에 남아 저장 공간을 낭비하는 문제로 볼 수 있다.   
다른 프로젝트에서도 이미지 업로드 후 게시글 삭제나 수정 과정에서 파일이 남을 수 있으므로 적용해 볼 수 있는 점검 방식이라고 생각했다.

> PBL Mission 10 Member API 검증 구현

회원가입 API에 Bean Validation을 적용했다.

처음에는 `name`, `email`, `age`를 Service에서 if문으로 직접 검사해야 하는지 헷갈렸지만,   
이번 미션의 핵심은 DTO에 붙은 검증 어노테이션을 `@Valid`로 실제 요청 흐름에 연결하는 것이었다.   
`SignupRequest`에는 `@NotBlank`, `@Email`, `@Min`, `@Max`가 붙어 있고,   
Controller의 `@RequestBody` 앞에 `@Valid`를 붙이면 Spring이 요청을 Service로 넘기기 전에 검증을 수행한다.

Service에서는 기본 입력값 검증을 다시 하지 않고, 비즈니스 규칙인 중복 이메일만 확인했다.   
`memberRepository.existsByEmail(request.email())`로 이미 가입된 이메일인지 확인하고, 중복이면 409 Conflict로 처리했다.   
중복이 아니면 `memberRepository.save()`로 회원을 저장하고, 저장된 Member를 `MemberResponse`로 변환해 201 Created로 반환했다.

`ResponseEntity.ok()`는 200 OK를 의미하므로,   
회원가입처럼 새 리소스를 생성하는 요청에는 `ResponseEntity.status(HttpStatus.CREATED).body(response)`를 사용해야 한다는 점도 다시 확인했다.

> PBL Mission 11 Error Response 표준화 구현

여러 API에서 발생하는 실패 응답을 하나의 공통 구조로 표준화했다.

이전에는 validation 오류, 중복 이메일, 게시글 미존재 오류가 각각 다른 방식으로 처리될 수 있었지만,   
이번 미션에서는 `ErrorResponse`와 `FieldErrorResponse`를 사용해 `code`, `message`, `timestamp`를 공통으로 포함하고,   
validation 실패에는 `fieldErrors`를 추가하도록 구성했다.

`FieldErrorResponse`는 `fieldErrors` 배열의 원소 구조를 정의하는 DTO이고, 실제 변환 로직은 `GlobalExceptionHandler`에서 처리했다.   
`@Valid` 검증에 실패하면 Spring이 `MethodArgumentNotValidException`을 발생시키고,   
이 예외의 `getBindingResult().getFieldErrors()`를 통해 어떤 필드가 왜 실패했는지 꺼낼 수 있다.

중복 이메일과 게시글 미존재 오류는 Service에서 직접 `ErrorResponse`를 만들어 반환하는 방식이 아니라,   
각각 `DuplicateEmailException`, `PostNotFoundException`을 던지고 `@RestControllerAdvice`가 이를 잡아 공통 응답으로 변환하도록 정리했다.   
이를 통해 Controller나 Service마다 다른 에러 응답을 만들지 않고, 실패 응답을 한 곳에서 일관되게 관리하는 구조를 이해했다.

> Repoary GitHub 저장소 연동 흐름 구현

Repoary에서 GitHub OAuth 로그인 이후의 전체 흐름을 프론트 화면까지 연결했다.

GitHub로 시작하기를 눌렀을 때 화면이 잠깐 깜빡이고 다시 돌아오는 현상은 오류가 아니라,   
이미 GitHub에 로그인되어 있고 Repoary OAuth App 승인도 끝난 상태라   
GitHub가 승인 화면을 다시 보여주지 않고 바로 callback으로 넘겨주는 정상 동작이었다.

Repoary의 로그아웃은 GitHub 계정 로그아웃이 아니라 `localStorage`에 저장된 Repoary JWT를 삭제하는 것이다.   
따라서 다시 시작하기를 누르면 GitHub 세션을 이용해 곧바로 재로그인될 수 있다는 점을 확인했다.

프론트 구조는 `App.tsx` 하나에 모든 흐름을 넣지 않고,   
`LoginPage`, `CallbackPage`, `RepositoryPage`, `Layout`, `api/client.ts`, `types`로 역할을 분리했다.   
로그인 성공 후 `/auth/callback`에서 토큰을 저장하고 `/repositories`로 이동한 뒤,   
`/api/users/me`로 사용자 정보를 조회하고 `/api/github/repositories`로 GitHub 저장소 목록을 불러오는 흐름을 만들었다.

저장소 연결 기능에서는 DB의 `connected_repositories` 테이블과 프론트의 연결 상태가 어떻게 맞물리는지 확인했다.   
저장소를 연결하면 DB에 row가 생기고, 연결된 저장소는 프론트에서 연결 해제 버튼으로 표시되도록 했다.   
반대로 연결 해제를 하면 `DELETE /api/repositories/connected/{githubRepositoryId}` 요청을 보내 DB row를 삭제하고,   
프론트 상태에서도 해당 저장소를 제거해 버튼이 다시 연결로 바뀌도록 했다.

연결 해제 요청은 여러 번 들어와도 오류가 나지 않도록 `findByUserAndGithubRepositoryId(...).ifPresent(delete)` 방식으로 수정했다.   
저장소가 연결되어 있으면 삭제하고, 이미 해제되어 있으면 아무 작업 없이 204 No Content를 반환하므로 프론트 더블클릭이나 상태 지연에도 안전하다.

> Repoary 배포와 Git 작업 정리

배포 과정에서는 `application.yml`에 Git 충돌 마커가 남아 Render에서 Spring Boot 애플리케이션이 실행되지 않는 문제를 해결했다.

`<<<<<<<`, `=======`, `>>>>>>>` 같은 충돌 표시가 YAML 파일에 남아 있어 `mapping values are not allowed here` 오류가 발생했고,   
`server`, `spring`, `github`, `frontend`, `jwt` 설정을 모두 최상위 구조에 맞게 다시 정리했다.   
stash 적용이나 merge 이후에는 충돌 마커가 남아 있지 않은지 반드시 확인해야 한다는 점을 알게 되었다.

Git 작업에서는 처음에 프론트 브랜치와 저장소 해제 브랜치를 따로 가져가려 했지만,   
실제 작업 흐름이 GitHub 로그인부터 저장소 목록 조회, 연결, 연결 해제까지 하나로 이어져 있어서  
`feat/github-repository-flow` 브랜치 하나로 정리했다.

> LMS w2-06

문자열 탐색과 조건 검증 관련 코딩테스트 문제를 풀이하고, 이진 탐색 구현 흐름을 정리했다.

`전화번호 목록`은 정렬 후 인접한 전화번호끼리만 비교했다.   
어떤 번호가 다른 번호의 접두어라면 정렬했을 때 서로 가까이 위치하므로, 모든 쌍을 비교하지 않아도 인접한 값만 확인할 수 있다.

`문자열 내 p와 y의 개수`는 문자열을 순회하면서 `p/P`를 만나면 `cnt`를 증가시키고, `y/Y`를 만나면 `cnt`를 감소시키는 방식으로 풀이했다.   
최종적으로 `cnt == 0`이면 두 문자의 개수가 같다고 판단할 수 있었다.

`스킬트리`는 각 스킬트리 문자열에서 선행 스킬에 포함된 문자만 골라낸 뒤,   
그 결과가 `skill`의 시작 부분과 일치하는지 `startsWith()`로 확인했다.   
필요한 문자만 남기고 비교 범위를 줄이는 방식으로 문제를 단순화할 수 있었다.

이진 탐색은 정렬된 데이터에서 사용할 수 있는 탐색 방식이다.   
가운데 값을 기준으로 찾는 값이 왼쪽에 있는지, 오른쪽에 있는지 판단하면서 탐색 범위를 절반씩 줄인다.

구현할 때는 `min`, `max`, `mid`의 의미를 명확히 잡아야 한다.   
가운데 인덱스는 단순히 `(min + max) / 2`로 계산하기보다 `min + (max - min) / 2`로 계산하는 방식이 안전하다.

## 헷갈렸던 점

`/stats`와 `/api/boards/stats/authors`의 역할도 헷갈렸다.   
`/stats`는 통계 화면 HTML을 반환하는 요청이고, `/api/boards/stats/authors`는 작성자별 게시글 수 데이터를 JSON으로 반환하는 API다.   
통계 화면에서 500 에러가 난 이유는 통계 API가 없어서가 아니라, 화면 이동용 Controller 매핑이 없었기 때문이었다.

`QBoardAuthorStatsResponseDto`를 찾지 못하는 오류도 다시 확인했다.   
QDTO는 `@QueryProjection`이 붙은 DTO를 기준으로 annotation processor가 생성하므로,   
오류가 발생하면 코드 자체보다 Q타입 생성 여부와 Gradle 빌드 실행 여부를 먼저 확인해야 한다.

스케줄러의 `cron`과 `fixedDelay` 차이도 정리했다.   
`cron`은 특정 시각에 실행할 때 사용하고, `fixedDelay`는 이전 작업이 끝난 뒤 일정 시간이 지난 후 다시 실행할 때 사용한다.

DB 연결 오류에서는 맨 위의 `Unable to determine Dialect without JDBC metadata`만 보고 판단하면 안 된다는 점을 확인했다.   
실제 원인은 아래쪽의 `Public Key Retrieval is not allowed`였고, MySQL JDBC URL에 `allowPublicKeyRetrieval=true`를 추가해 해결했다.

PBL에서는 Bean Validation과 Service 검증의 역할이 헷갈렸다.   
`@Valid`와 검증 어노테이션은 기본 입력값 검증을 담당하고, Service는 중복 이메일 같은 비즈니스 규칙을 검증한다.

`FieldErrorResponse`에 직접 로직을 넣는 것인지도 헷갈렸다.   
`FieldErrorResponse`는 validation 실패 필드 정보를 담는 DTO이고, 실제 변환 로직은 `GlobalExceptionHandler`에서 처리한다.

Repoary에서는 OAuth 로그인과 서비스 로그아웃의 차이가 헷갈렸다.   
Repoary 로그아웃은 GitHub 로그아웃이 아니라 Repoary JWT 삭제이므로,   
GitHub 세션이 살아 있으면 다시 로그인할 때 GitHub 승인 화면 없이 callback으로 바로 이동할 수 있다.

저장소 연결 해제에서 path variable로 넘기는 값도 헷갈렸다.   
연결 해제 API에는 `connected_repositories.id`가 아니라 GitHub 저장소의 id인 `githubRepositoryId`를 넘겨야 한다.

---

`전화번호 목록`에서는 모든 전화번호 쌍을 비교해야 하는지 헷갈렸다.   
정렬하면 접두어 관계가 있는 값들이 인접하게 오므로, 인접한 전화번호끼리만 `startsWith()`를 확인해도 된다.

`스킬트리`에서는 모든 문자를 순서대로 비교하려고 하면 복잡해질 수 있다는 점을 확인했다.   
먼저 선행 스킬에 포함된 문자만 필터링하고, 필터링된 결과가 주어진 스킬 순서의 앞부분과 일치하는지만 보면 된다.

이진 탐색에서는 `min`, `max`, `mid` 갱신 기준이 헷갈렸다.   
찾는 값이 가운데 값보다 크면 왼쪽 범위는 버리고 `min = mid + 1`로 이동하며,   
찾는 값이 가운데 값보다 작으면 오른쪽 범위를 줄이는 방향으로 처리해야 한다.

## 오늘 느낀 점

게시판 기능에 통계, 로그, 스케줄러를 붙이면서 CRUD 이후에는 운영과 관리에 필요한 기능이 중요해진다는 점을 느꼈다.   
단순히 글을 저장하고 조회하는 것을 넘어, 통계를 보고, 로그를 남기고, 사용하지 않는 파일을 점검하는 흐름까지 고려해야 한다.

고아 파일 점검은 게시판 실습뿐 아니라 이미지 업로드가 있는 다른 프로젝트에도 적용할 수 있을 것 같다.   
DB에서는 더 이상 참조하지 않지만 실제 파일은 남아 있는 경우가 생길 수 있으므로, 업로드 기능을 구현할 때 파일 정리 방식까지 함께 생각해야 한다.

PBL Mission 10과 11을 진행하면서 요청 검증과 예외 응답을 한 곳에서 일관되게 관리하는 구조가 중요하다는 점을 다시 확인했다.   
입력값 검증은 `@Valid`로 처리하고, 비즈니스 예외는 Service에서 예외를 던진 뒤 전역 예외 처리에서 공통 응답으로 변환하는 흐름이 더 깔끔하다.

Repoary에서는 GitHub OAuth 이후 저장소 목록 조회, 저장소 연결, 연결 해제까지   
프론트와 백엔드가 함께 맞물리면서 실제 서비스 흐름이 완성되는 느낌이 들었다.   
단순히 API 하나를 만드는 것보다, 화면 상태와 DB 상태가 함께 바뀌는 흐름을 맞추는 과정이 더 중요하다고 느꼈다.

배포와 Git 작업에서는 코드 구현 외에도   
설정 파일 충돌, 환경변수, 브랜치 정리, 커밋 분리 같은 작업이 전체 개발 흐름에 큰 영향을 준다는 점을 다시 느꼈다.   
특히 merge나 stash 이후에는 충돌 마커가 남아 있지 않은지 확인하는 습관이 필요하다.

---

코딩테스트 문제를 풀면서 문자열 문제도 단순 순회만이 아니라   
정렬, 접두어 비교, 필요한 문자 필터링처럼 조건을 단순화하는 과정이 중요하다고 느꼈다.   
이진 탐색을 정리하면서는 반복문 자체보다 매 단계에서 탐색 범위를 어떻게 줄일지 명확히 잡는 것이 핵심이라는 점을 확인했다.
