## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습에서 세션 로그아웃, AOP 요청 로깅, Repository 테스트와 Service 단위 테스트를 학습했다.

로그아웃은 `session.invalidate()`로 현재 세션을 무효화하고, `redirect:/members/login`으로 로그인 화면에 다시 접근하도록 처리했다.   
로그아웃처럼 세션 상태를 바꾸는 요청 뒤에는 뷰를 바로 반환하기보다 리다이렉트하는 흐름이 자연스럽다는 점을 확인했다.

AOP에서는 Controller마다 반복될 수 있는 요청 시작 로그, 파라미터 출력, 실행 시간 측정, 예외 로그를 Aspect로 분리했다.   
`@Pointcut`은 AOP를 적용할 대상을 정하고, `@Around`는 대상 메서드 실행 전후를 감싸는 역할을 한다.   
특히 `joinPoint.proceed()`를 호출해야 실제 Controller 메서드가 실행되며,   
예외를 잡은 뒤에는 다시 던져야 기존 예외 처리 흐름이 유지된다는 점을 확인했다.

테스트 코드에서는 Repository 테스트와 Service 테스트의 목적이 다르다는 점을 정리했다.   
Repository 테스트는 `@DataJpaTest`와 H2 메모리 DB를 사용해 실제 JPA Repository의 저장·조회 동작을 확인하고,   
Service 테스트는 Mockito로 Repository와 Mapper를 Mock 처리해 Service 로직만 검증한다.

개인 프로젝트 Repoary는 GitHub 학습 저장소의 커밋과 변경 파일을 분석해 TIL 초안과 월별 README 행 생성을 돕는 서비스이다.   
날짜별 커밋과 변경 파일을 기준으로 학습 내용을 분류하고, 기록 누락 여부를 점검하는 흐름을 MVP의 중심으로 잡았다.

## 실습 및 과제

> Spring Boot jpa-board 로그아웃 실습

세션 기반 로그아웃 흐름을 확인했다.

로그아웃 요청이 들어오면 `session.invalidate()`로 현재 세션을 무효화하고, 로그인 화면으로 리다이렉트하도록 구성했다.   
세션 상태를 변경하는 요청은 같은 뷰를 바로 반환하기보다 리다이렉트해 주소와 상태 흐름을 정리하는 것이 적절하다는 점을 확인했다.

> Spring Boot jpa-board AOP와 테스트 코드 실습

Controller 요청 로깅을 AOP로 분리했다.

`@Pointcut`으로 Controller 계층을 대상으로 지정하고, `@Around`에서 요청 시작, 파라미터, 실행 시간, 예외 로그를 처리했다.   
`ProceedingJoinPoint.proceed()`를 기준으로 실제 대상 메서드 실행 전후 흐름이 나뉜다는 점을 확인했다.

테스트 코드에서는 Repository 테스트와 Service 테스트의 역할을 구분했다.   
Repository 테스트는 실제 JPA Repository 동작을 확인하고,   
Service 테스트는 Repository와 Mapper를 Mock으로 대체해 Service 로직만 검증한다.

> 게시판 로그아웃 과제

게시판 과제에 로그아웃 기능을 추가했다.

로그아웃 시 현재 세션을 무효화하고 로그인 화면으로 이동하도록 처리했다.   
로그인 상태를 세션으로 관리하고 있으므로, 로그아웃은 세션에 저장된 사용자 정보를 제거하는 방식으로 구현했다.

> 게시판 AOP 로깅과 단위 테스트 과제

반복되는 Controller 실행 로그를 `LoggingAspect`로 분리했다.

`@Pointcut`으로 `com.example.jpaboard.controller` 하위 메서드를 대상으로 지정하고,   
`@Around`에서 Controller 실행 전후로 시작 로그와 종료 로그, 실행 시간을 출력했다.   
`proceed()`의 반환값은 실제 Controller 응답이 될 수 있으므로 그대로 반환해야 한다는 점을 확인했다.

Service 테스트에서는 Mockito를 사용했다.   
`MemberRepository`, `MemberMapper`를 `@Mock`으로 만들고,   
`@InjectMocks`로 `MemberService`에 주입해 로그인 성공과 중복 아이디 예외 상황을 검증했다.   
중복 아이디 회원가입 테스트에서는 예외 발생뿐 아니라   
`verify(memberRepository, never()).save(any())`로 저장 로직이 실행되지 않았는지도 함께 확인했다.

Repository 테스트에서는 `@DataJpaTest`를 사용했다.   
`existsByUserId()`와 `findByUserId()`가 실제 JPA 환경에서 정상 동작하는지 확인했다.   
테스트 DB는 실제 MySQL이 아니라 H2 인메모리 DB를 사용하고, `src/test/resources/application.yml`에 테스트 전용 설정을 분리했다.

> Repoary 기획서 작성

개인 프로젝트 Repoary의 서비스 방향과 MVP 범위를 정리했다.

Repoary는 GitHub 학습 저장소의 커밋과 변경 파일을 분석해 TIL 초안과 월별 README 행 생성을 돕는 서비스이다.   
GitHub 로그인, 저장소 선택, 기본 규칙 설정, 날짜별 학습 기록 분석, TIL 초안 생성·편집, README 행 생성을 MVP 기능으로 정리했다.

기능 범위가 커지지 않도록 GitHub 파일 직접 수정, AI API 연동, 로컬 미커밋 파일 분석, 고급 규칙 관리는 제외 범위로 분리했다.   
먼저 하나의 사용자 흐름이 끝까지 동작하는 것을 목표로 잡았다.

데이터 모델은 사용자, 연결 저장소, 분류 규칙, 커밋 규칙, 분석 작업, 커밋 기록, 변경 파일, 생성 문서를 중심으로 설계했다.   
개인정보 수집 범위는 GitHub 사용자 ID와 로그인명으로 최소화하고,   
프로필 이미지나 이메일처럼 필요하지 않은 정보는 수집하지 않는 방향으로 정리했다.

## 헷갈렸던 점

AOP에서 `proceed()`를 호출해야 하는 이유가 헷갈렸다.   
`@Around`는 대상 메서드 실행 전체를 감싸기 때문에,   
`proceed()`를 호출하지 않으면 AOP 로직만 실행되고 실제 Controller 메서드는 실행되지 않는다.

AOP에서 예외를 잡은 뒤 처리 흐름도 헷갈렸다.   
예외 로그를 남긴 뒤 예외를 다시 던져야 전역 예외 처리나 기존 오류 응답 흐름이 유지된다.

Repository 테스트와 Service 테스트의 목적 차이도 헷갈렸다.   
Repository 테스트는 실제 JPA Repository가 DB와 상호작용하는 흐름을 확인하고,   
Service 테스트는 의존 객체를 Mock으로 대체해 Service 로직만 검증한다.

## 오늘 느낀 점

로그아웃, AOP, 테스트 코드를 추가하면서 게시판 기능이 단순 CRUD를 넘어 운영과 검증까지 확장되는 흐름을 볼 수 있었다.

AOP를 사용하니 Controller마다 반복되는 로깅 코드를 줄일 수 있었고,   
공통 관심사를 별도 계층으로 분리하는 이유를 더 명확히 이해할 수 있었다.

테스트에서는 모든 것을 실제 DB로 확인하는 것이 아니라,   
검증하려는 대상에 따라 Mock 기반 단위 테스트와 JPA 기반 Repository 테스트를 구분해야 한다는 점을 느꼈다.

Repoary 기획서를 작성하면서 하고 싶은 기능을 모두 넣기보다,   
GitHub 로그인부터 저장소 선택, 날짜별 분석, TIL 초안 생성, README 행 생성까지 하나의 흐름이 끝까지 동작하는 것을 우선해야 한다고 정리했다.
