* Compose Bean: 1차 팀 프로젝트 - 비회원 카페 주문 서비스 기획 및 설계

## 오늘 배운 내용

오늘은 데브코스 1차 팀 프로젝트를 시작하며 비회원 카페 주문 서비스의 주제와 핵심 기능을 구체화했다.

기본 요구사항을 확인하고, 이를 바탕으로 주문 조회와 배송 관리 등의 추가 기능을 검토했다.

처음에는 팀원마다 생각하는 주문 흐름과 기능 범위가 달라 같은 기능을 서로 다르게 이해하는 부분이 있었다.  
ERD, API 명세서, DTO 구조를 함께 작성하면서 기능 정의와 데이터 구조, API 요청·응답이 서로 일치하도록 기준을 맞췄고,   
논의를 거치며 프로젝트의 전체 방향을 점차 확립했다.

특히 DTO를 설계하는 과정이 가장 공부가 되었다.  
요청 DTO와 응답 DTO는 사용하는 목적과 포함하는 값이 다르므로 분리해야 하며,   
주문 목록처럼 여러 데이터를 반환할 때는 전체 응답 DTO 안에 개별 항목 DTO를 포함하는 구조로 설계할 수 있다는 점을 이해했다.

또한 단순히 데이터를 전달하는 DTO에는 Java의 `record`를 활용할 수 있다는 점을 확인했다.  
사용자가 직접 전달하는 값과 서버에서 조회하거나 계산하는 값을 구분하면서, API의 책임에 따라 DTO에 필요한 필드만 포함해야 한다는 점을 정리했다.

## 실습 및 과제

> Compose Bean 프로젝트 기획 및 설계

비회원이 카페 상품을 주문하고 이메일을 통해 주문 내역을 조회할 수 있는 서비스를 주제로 정했다.

기본 요구사항을 바탕으로 상품 관리, 주문 생성, 주문 조회, 결제 상태와 배송 상태 관리 등의 기능을 구체화했다.  
기능을 단순히 나열하는 데서 끝내지 않고, 사용자가 어떤 흐름으로 서비스를 이용하는지와 각 기능에 필요한 데이터를 연결해 구현 범위를 정리했다.

> WBS 및 설계 문서 작성

WBS를 작성해 프로젝트 일정과 작업 순서, 담당 영역을 정리했다.

WBS 내 기능 정의서, API 명세서와 Mock Server, 프로젝트 기획서, 와이어프레임, 유저 스토리, ERD를 완성했다.  
기능 정의서와 프로젝트 기획서는 논의된 내용을 기준으로 정리했으며, API 명세서와 유저 스토리, ERD는 전반적인 방향을 주도해 작성했다.

`Product`, `Order`, `OrderItem`을 중심으로 엔티티 관계와 필요한 필드를 정리하고,   
상품 조회·관리, 주문 생성·조회, 배송 상태 변경 기능에 필요한 API 경로와 요청·응답 형식을 정의했다.

ERD와 API 명세서, DTO 구조를 함께 비교하면서 특정 필드가 어디에 저장되고 어떤 응답에서 사용되는지 확인했다.  
이 과정을 통해 팀원마다 다르게 생각했던 기능의 동작 방식을 하나씩 통일했다.

> 역할 분담 및 팀 진행 관리

전체 구현 범위를 상품 도메인·공통 처리, 주문 생성·결제·재고 처리, 주문 조회·배송 정책으로 나누어 담당 영역을 정리했다.

팀장을 맡아 현재 진행 상황과 결정 사항을 공유하고, 멘토링 일정을 팀원들과 조율했다.  
팀원들의 프로젝트 경험과 이해도를 고려해 기능 흐름과 구현 순서를 정리하고, 설계 단계가 구체적으로 진행될 수 있도록 방향을 맞췄다.

## 헷갈렸던 점

처음에는 팀원마다 생각하는 주문 흐름과 기능 범위가 달라 같은 용어를 사용하면서도 서로 다른 동작을 생각하는 경우가 있었다.  
말로만 논의할 때는 차이가 명확히 드러나지 않았지만, ERD와 API 명세서로 표현하면서 서로 다르게 이해한 부분을 확인할 수 있었다.

DTO를 어느 정도까지 분리해야 하는지도 헷갈렸다.  
요청과 응답은 필요한 데이터가 다르기 때문에 별도로 설계해야 하며,   
목록 응답에서는 전체 목록을 감싸는 DTO와 각 항목을 표현하는 DTO를 나누는 방식이 필요하다는 점을 정리했다.

또한 엔티티에 존재하는 필드를 모두 요청 DTO에 넣는 것이 아니라,   
사용자가 전달해야 하는 값만 요청으로 받고 가격이나 상태처럼 서버가 결정하는 값은 서버에서 처리해야 한다는 점을 확인했다.

## 오늘 느낀 점

프로젝트 첫날에는 바로 코드를 작성하기보다 팀원들이 생각하는 기능과 데이터 흐름을 먼저 맞추는 과정이 중요하다고 느꼈다.

처음에는 프로젝트 경험과 이해도의 차이로 논의가 다소 혼란스러웠지만,   
ERD와 API 명세서처럼 구체적인 문서를 기준으로 대화하면서 점차 공통된 방향을 만들 수 있었다.

팀장과 문서화 역할을 맡아 프로젝트의 진행 상황과 일정, 설계 기준을 정리했다.  
특히 문서를 작성하는 과정에서 팀의 생각을 하나로 모으고, 이후 구현에서 사용할 공통 기준을 만드는 것이 중요하다는 점을 느꼈다.

DTO를 설계하면서 API 요청과 응답의 책임을 구분하는 과정이 가장 공부가 되었다.  
실제 구현 전에 데이터가 어떤 형태로 이동하고 각 계층이 어떤 책임을 가지는지 정리해 두는 것이   
이후 개발 과정의 혼란과 충돌을 줄이는 데 도움이 될 것 같다.
