## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습에서 Controller 계층 테스트, 전역 예외 처리, Swagger API 문서화, 응답 DTO 분리를 학습했다.

`@WebMvcTest`와 `MockMvc`를 사용하면 실제 서버를 띄우지 않고 Controller의 HTTP 요청과 응답 흐름을 검증할 수 있다.   
이 테스트의 관심사는 Service 비즈니스 로직이 아니라 URL 매핑, JSON 요청 파싱, 상태 코드, 응답 JSON, 예외가 HTTP 응답으로 변환되는 흐름이다.

전역 예외 처리에서는 `@RestControllerAdvice`와 `@ExceptionHandler`의 역할을 정리했다.   
Controller와 Service는 예외를 직접 잡지 않고 던지고,   
`GlobalExceptionHandler`가 예외 타입에 따라 409, 404, 500 같은 HTTP 응답으로 변환한다.

Swagger 문서화에서는 `@Tag`, `@Operation`, `@Parameter`, `@ApiResponse`, `@Schema`를 사용해   
API 그룹, 설명, 파라미터, 응답 상태 코드, 요청·응답 DTO를 문서에 표시했다.   
파일 업로드가 포함된 API는 JSON이 아니라 `multipart/form-data` 요청이므로   
`@ModelAttribute`와 `MultipartFile` 조합을 사용해야 한다는 점도 다시 확인했다.

Swagger 화면을 확인하면서 Entity가 응답 Schema에 그대로 노출되는 문제도 발견했다.   
Entity는 DB 테이블과 연결된 내부 모델이고, API 응답은 클라이언트에게 보여줄 DTO로 분리하는 것이 적절하다.   
그래서 목록 응답에서 `Board` Entity를 직접 반환하지 않고, `BoardSummaryResponseDto`, `BoardDetailResponseDto`로 변환하는 흐름을 정리했다.

개인 프로젝트 Repoary에서는 초기 개발 환경을 구성했다.   
모노레포 구조에서 `backend`는 Spring Boot, `frontend`는 Vite React로 분리하고, 백엔드에는 `/api/health`와 Swagger 접근 설정을 추가했다.   
Supabase PostgreSQL 연결, Render 백엔드 배포, Vercel 프론트 배포 흐름도 함께 확인했다.

## 실습 및 과제

> Spring Boot jpa-board Controller 테스트 실습

Controller 계층 테스트의 목적을 확인했다.

`@WebMvcTest`는 웹 계층만 로딩하고, `MockMvc`는 실제 서버를 띄우지 않고 HTTP 요청과 응답을 검증한다.   
Controller 테스트에서는 Service 내부 로직보다 요청 방식, 상태 코드, 응답 JSON 구조, 예외 응답 변환 흐름을 확인하는 것이 핵심이다.

회원가입 Controller 테스트에서는 `@MockitoBean`으로 `MemberService`를 Mock 처리했다.   
회원가입 성공 시에는 200 응답과 `/members/login` URL이 반환되는지 검증하고,   
중복 아이디 상황에서는 Service가 예외를 던지도록 설정한 뒤 409 응답과 에러 메시지를 확인했다.

응답 JSON은 `jsonPath("$.url")`, `jsonPath("$.message")`처럼 특정 필드를 지정해 검증했다.

> Spring Boot jpa-board 전역 예외 처리 실습

전역 예외 처리 흐름을 정리했다.

`DuplicateUserIdException`은 409, `BoardNotFoundException`은 404, 그 외 예외는 500 응답으로 변환되도록 구성했다.   
예외 처리도 공통 관심사처럼 보이지만, JSON 변환 실패나 파라미터 타입 불일치처럼   
Controller 메서드 호출 전에도 발생할 수 있는 웹 계층 예외는 AOP보다 `@RestControllerAdvice`로 처리하는 것이 적절하다는 점을 확인했다.

> Spring Boot jpa-board Swagger 문서화 실습

Swagger를 사용해 API 문서를 구성했다.

`@Tag`로 API 그룹을 나누고, `@Operation`으로 API 설명을 작성했다.   
`@Parameter`, `@ApiResponse`, `@Schema`를 사용해 파라미터, 응답 상태 코드, 요청·응답 DTO 정보를 문서에 표시했다.

파일 업로드가 포함된 게시글 작성·수정 API에서는   
`MultipartFile` 필드에 `@Schema(type = "string", format = "binary")`를 붙여 Swagger UI에서 파일 선택 버튼이 보이도록 처리했다.

파일 다운로드 API는 `ResponseEntity<Resource>`로 상태 코드, 헤더, 본문을 직접 제어했다.   
`Content-Disposition: attachment` 헤더를 설정해 브라우저가 파일을 다운로드로 처리하도록 하고, 한글 파일명은 `URLEncoder`로 인코딩해 처리했다.

> 게시판 컨트롤러 테스트 과제

게시판 과제에 Controller 테스트를 추가했다.

`MemberApiControllerTest`에서는 `@WebMvcTest(MemberApiController.class)`로 웹 계층만 로딩하고,   
`MockMvc`를 사용해 `POST /api/members/join` 요청을 검증했다.

회원가입 성공 테스트에서는 JSON 요청을 보내고, 응답 상태가 200인지와 응답 body의 `url` 값이 `/members/login`인지 확인했다.   
회원가입 API는 `@RequestBody`로 요청을 받기 때문에 테스트에서도 `contentType(MediaType.APPLICATION_JSON)`을 지정해야 한다.

중복 아이디 테스트에서는 `memberService.join()`이 `DuplicateUserIdException`을 던지는 상황을 Mock으로 만들었다.   
`join()`은 반환값이 없는 `void` 메서드이므로 `given().willReturn()`이 아니라 `willThrow().given()`을 사용해야 한다는 점을 확인했다.

이번 테스트를 통해 Service 테스트, Repository 테스트, Controller 테스트의 역할을 다시 구분했다.   
Service 테스트는 Mockito로 의존 객체를 Mock 처리해 로직을 검증하고,   
Repository 테스트는 `@DataJpaTest`로 JPA 메서드가 실제 DB 환경에서 동작하는지 확인한다.   
Controller 테스트는 `@WebMvcTest`와 `MockMvc`로 HTTP 요청, 상태 코드, JSON 응답을 검증한다.

> Repoary 초기 개발 환경 구성

Repoary 개인 프로젝트의 초기 개발 환경을 구성했다.

프로젝트는 모노레포 구조로 두고, 루트 아래에 `backend`와 `frontend`를 분리했다.   
백엔드는 Spring Boot로 생성하고, 프론트엔드는 Vite React로 생성해 각각 IntelliJ와 VS Code에서 실행하는 흐름을 확인했다.

백엔드에서는 `/api/health`를 만들고, Spring Security에서 health check 경로와 Swagger 경로를 공개하도록 설정했다.   
Swagger UI 접속까지 확인하면서 배포 후 상태 확인에 사용할 기본 API를 먼저 구성했다.

Supabase PostgreSQL 연결 과정에서는 Direct connection이 IPv6 문제로 실패할 수 있다는 점을 확인하고,   
Session pooler를 사용해 DB 연결을 성공시켰다.   
`.env`는 실제 DB 비밀번호를 담는 로컬 전용 파일이므로 커밋하지 않고,   
`.env.example`에는 실제 비밀번호와 프로젝트 식별자를 노출하지 않는 예시값만 두는 방식으로 정리했다.

배포는 개발 중에는 `develop` 브랜치를 기준으로 Render와 Vercel에 연결하고,   
MVP가 안정되면 `main`으로 병합해 최종 배포 기준을 바꾸는 전략으로 정리했다.   
Render는 Dockerfile을 추가해 Docker 방식으로 백엔드를 배포하고, health check path는 `/api/health`로 설정했다.

Vercel에서는 모노레포 구조 때문에 Root Directory를 `frontend`로 지정해야 한다는 점을 확인했다.   
조직 레포지토리 권한 문제로 일반적인 GitHub 연동 배포가 막히는 상황에 처했다.  
그래서 Vercel CLI를 사용해 로컬의 `develop` 브랜치 상태를 직접 배포하는 방식으로 해결했다.

## 헷갈렸던 점

`@WebMvcTest`의 테스트 범위가 헷갈렸다.   
`@WebMvcTest`는 Service 로직까지 검증하는 테스트가 아니라 Controller의 HTTP 요청과 응답 흐름을 검증하는 테스트다.   
따라서 Controller가 의존하는 Service는 `@MockitoBean`으로 Mock 처리해야 한다.

`void` 메서드의 Mock 예외 설정도 헷갈렸다.   
반환값이 있는 메서드는 `given().willReturn()`을 사용할 수 있지만,   
반환값이 없는 `void` 메서드에서 예외를 던지게 하려면 `willThrow().given()`을 사용해야 한다.

웹 계층 예외를 AOP로 처리해야 하는지, `@RestControllerAdvice`로 처리해야 하는지도 헷갈렸다.   
Controller 메서드 실행 전에도 발생할 수 있는 요청 파싱 오류나 타입 불일치 예외까지 처리하려면   
`@RestControllerAdvice`가 더 적절하다는 점을 확인했다.

Swagger에서 파일 업로드 필드가 제대로 보이지 않는 이유도 확인했다.   
`multipart/form-data` 요청에서는 `MultipartFile` 필드를 문서화할 때   
`@Schema(type = "string", format = "binary")`를 지정해야 파일 선택 형태로 표시된다.

Repoary 배포에서는 조직 레포지토리 권한과 설정이 가장 헷갈렸다.   
Vercel이 조직 레포지토리에 접근하지 못해 일반 GitHub 연동 배포가 꼬였다.

Vercel CLI 설치 과정에서는 Windows PowerShell의 Execution Policy 때문에 스크립트 실행 오류가 발생했다.   
`Set-ExecutionPolicy RemoteSigned -Scope CurrentUser`로 현재 사용자 범위의 실행 권한을 조정해 해결했다.

## 오늘 느낀 점

Controller 테스트를 작성하면서 테스트도 계층별로 목적이 다르다는 점을 더 명확히 이해했다.   
Service 테스트는 로직을 검증하고, Repository 테스트는 JPA 동작을 확인하며, Controller 테스트는 HTTP 요청과 응답 계약을 확인한다.

Swagger 문서화를 하면서 API 응답에 Entity가 그대로 노출되는 문제를 더 분명하게 볼 수 있었다.   
Entity와 DTO를 분리하고 Mapper를 통해 변환하는 구조가 단순한 형식 문제가 아니라 API 설계와 유지보수에 필요한 구조라는 점을 느꼈다.

Repoary 초기 세팅을 하면서 개인 프로젝트도 처음부터 로컬 실행, DB 연결, 배포 기준 브랜치, health check를 함께 잡아두는 것이 중요하다고 느꼈다.

Repoary 프론트 배포를 진행하면서 Vercel 설정을 여러 가지로 확인했지만,   
조직 레포지토리 권한 문제로 일반적인 GitHub 연동 배포가 막혀 예상보다 많은 시간을 사용했다.   
Fork 방식도 고려했지만 관리 부담이 커질 수 있어 적절하지 않다고 판단했고,   
결국 Vercel CLI로 로컬 `develop` 브랜치 상태를 직접 배포하는 방식으로 해결했다.   
안내가 명확하지 않은 상황에서 직접 해결 방법을 찾아야 해서 힘들었지만, 배포 흐름을 끝까지 연결할 수 있어 뿌듯했다.
