## 오늘 배운 내용

오늘은 기존 JPA 게시판의 세션 기반 로그인 구조를 Spring Security와 JWT를 사용하는 토큰 기반 인증 구조로 변경했다.

회원 엔티티에는 `Role`을 추가하고, 회원가입 시 `PasswordEncoder`로 비밀번호를 암호화해 저장했다.   
Spring Security가 회원 정보를 인증에 사용할 수 있도록 `CustomUserDetails`와 `UserDetailsService`를 구현했으며,   
로그인 요청은 `AuthenticationManager`를 통해 아이디와 비밀번호를 검증하도록 구성했다.

로그인에 성공하면 Access Token과 Refresh Token을 각각 발급한다.  
Access Token에는 사용자 식별 정보와 권한, `ACCESS` 타입을 포함해 API 인증에 사용하고,   
Refresh Token은 `REFRESH` 타입으로 구분해 토큰 재발급에만 사용했다.

Access Token은 응답 body로 전달해 브라우저의 `localStorage`에 저장하고,   
Refresh Token은 JavaScript에서 직접 접근할 수 없도록 `HttpOnly` 쿠키에 저장했다.   
이후 API 요청에서는 JavaScript가 Access Token을 `Authorization: Bearer <token>` 헤더에 추가하도록 연결했다.

`TokenAuthenticationFilter`는 요청 헤더에서 Access Token을 추출하고 서명, 발급자, 만료 여부와 토큰 타입을 검증한다.   
유효한 토큰이면 회원 정보를 조회해 `Authentication`을 생성하고 `SecurityContextHolder`에 저장한다.   
Refresh Token은 일반 API 인증에 사용할 수 없도록 타입을 별도로 검사했다.

Access Token이 만료되어 `401 Unauthorized`가 반환되면 Refresh Token 쿠키를 이용해 재발급 API를 호출한다.   
검증에 성공하면 새로운 Access Token과 Refresh Token을 발급하고, 새 Access Token으로 실패했던 요청을 한 번 다시 실행하도록 구현했다.

현재 재발급 과정에서는 새 Refresh Token을 쿠키에 덮어쓰지만 기존 토큰을 서버에 저장하거나 폐기하지는 않는다.   
따라서 이전 Refresh Token의 재사용까지 차단하는 완전한 Refresh Token Rotation 구조는 아니라는 점을 확인했다.

게시글 작성에는 요청으로 전달받은 회원 ID가 아니라 Spring Security 인증 객체의 사용자 ID를 사용했다.   
게시글 수정과 삭제에는 작성자 또는 관리자 권한 검사를 적용해   
일반 회원은 자신의 게시글만 처리하고, 관리자는 모든 게시글을 수정·삭제할 수 있도록 구성했다.

인증되지 않은 요청은 `401 Unauthorized`, 인증은 되었지만 작성자나 관리자가 아닌 사용자의 요청은 `403 Forbidden`으로 처리했다.

Repoary에서는 GitHub 커밋 분석 과정에 대한 백엔드 테스트를 추가했다.

저장소 소유권 확인, 날짜별 커밋 조회, 커밋별 변경 파일 조회, 경로 분류 규칙과 커밋 규칙 적용, 분석 작업 상태 변경이 의도한 대로 동작하는지 검증했다.

단순히 API 응답 여부만 확인하는 것이 아니라 GitHub에서 가져온 커밋과 변경 파일이 사용자가 설정한 규칙에 따라 올바르게 분류되고,   
최종 분석 결과에 포함되는지를 확인하는 것이 중요했다.

---

수업 후에는 Repoary의 규칙 관리와 분석 기능을 실제 사용자 화면에 연결했다.

저장소 규칙 관리 화면에서는 연결된 저장소의 경로 분류 규칙과 커밋 규칙을 조회하고 추가·수정·삭제할 수 있도록 구현했다.   
기본 규칙 복원 기능도 연결해 사용자가 변경하거나 삭제한 규칙을 초기 상태로 되돌릴 수 있도록 했다.

날짜별 커밋 분석 화면에서는 사용자가 날짜를 선택해 분석을 실행하고, `analysis_jobs`의 상태를 확인한 뒤 완료된 결과를 표시하도록 구성했다.   
분석 전, 실행 중, 완료, 결과 없음과 오류 상태를 구분해 보여주도록 했다.

커밋 컨벤션 일관성 분석 기능은 특정 경로에서 하나의 커밋 type만 허용하는 기능이 아니라,   
기존 커밋에서 실제로 사용된 형식을 모아 보여주는 기능으로 구현했다.

변경 파일을 경로와 category별로 묶은 뒤 일치한 커밋 규칙별로 다시 그룹화하고, 어떤 규칙에도 일치하지 않는 커밋은 별도 그룹으로 구분했다.

프론트에서는 기존 날짜별 커밋 분석과 컨벤션 일관성 분석을 탭으로 분리했다.   
분석 기간을 선택하면 분석한 커밋 수, 사용된 경로 수와 커밋 형식 수를 확인하고, 경로별 실제 커밋 메시지와 GitHub 링크까지 조회할 수 있도록 구성했다.

## 실습 및 과제

> 게시판 JWT 인증·인가 및 토큰 재발급

기존 세션 로그인 코드를 제거하고 Spring Security와 JWT 기반 인증 구조를 적용했다.   
로그인 성공 시 Access Token은 응답으로 전달하고 Refresh Token은 `HttpOnly` 쿠키에 저장했다.

Access Token 검증 필터를 Security Filter Chain에 등록하고, 인증된 사용자 정보를 `SecurityContext`에 저장하도록 구성했다.   
Access Token 만료 시에는 Refresh Token을 검증해 두 토큰을 재발급하고,   
로그아웃 시에는 Refresh Token 쿠키와 브라우저의 Access Token을 제거하도록 처리했다.

게시글 작성 시 현재 인증된 사용자의 ID를 사용하도록 변경했다.   
수정과 삭제에는 작성자 또는 관리자 검사를 적용해 클라이언트가 전달한 회원 ID나 권한을 신뢰하지 않고 서버가 검증한 인증 정보를 기준으로 처리했다.

JWT와 게시글 인가 로직에 대한 단위 테스트도 작성했다.   
Access Token과 Refresh Token 생성, 토큰 타입, 만료·변조 토큰 검증과 토큰 재발급을 확인하고,   
게시글 작성자·다른 일반 회원·관리자의 수정 및 삭제 결과를 각각 검증했다.

> Repoary GitHub 커밋 분석 테스트

GitHub 커밋 목록 조회, 커밋별 변경 파일 조회, 규칙 적용과 분석 결과 저장 흐름에 대한 테스트를 추가했다.

저장소와 분석 날짜를 기준으로 커밋 조회와 규칙 적용이 수행되는지 확인하고, 커밋 메시지와 파일 경로가 올바르게 분석 결과에 반영되는지 검증했다.

분석 실행 과정에서 작업 상태가 `PENDING`, `RUNNING`, `COMPLETED` 또는 `FAILED`로 변경되고,   
분석된 커밋과 변경 파일이 최종 결과에 포함되는지도 확인했다.

---

> Repoary 규칙 관리와 분석 화면 구현

저장소 규칙 관리 페이지에 경로 분류 규칙과 커밋 규칙의 조회·추가·수정·삭제 및 기본 규칙 복원 기능을 연결했다.

날짜별 커밋 분석 페이지에는 날짜 선택, 분석 실행, 진행 상태 확인과 완료 결과 조회 흐름을 구현했다.

커밋 컨벤션 일관성 분석 API에서는 기간 내 커밋을 경로와 category별로 분류하고, 실제로 사용된 커밋 규칙에 따라 다시 그룹화해 반환하도록 구성했다.

프론트 화면에서는 컨벤션 분석 결과와 실제 커밋 메시지, GitHub 링크를 확인할 수 있도록 구현했다.

배포 후 GitHub OAuth 로그인을 진행했을 때 인증 완료 후 프론트의 `/auth/callback` 경로에서 Vercel `404 NOT_FOUND`가 발생했다.   
React 애플리케이션에 해당 경로가 있어도 주소로 직접 진입하면 Vercel이 먼저 실제 파일을 찾기 때문이었다.

`vercel.json`에 모든 경로를 `index.html`로 전달하는 rewrite 설정을 추가해 React Router가 callback 경로를 처리하도록 수정했다.   
재배포 후 GitHub 로그인부터 callback 처리까지 정상 동작하는 것을 확인했다.

## 헷갈렸던 점

JWT 필터가 토큰을 검증하고 현재 사용자를 확인하는 과정은 인증이고, 인증된 사용자가 게시글을 수정·삭제할 수 있는지 검사하는 과정은 인가다.   
인증 실패의 `401`과 권한 부족의 `403`도 이에 따라 구분해야 한다.

로그아웃 시 브라우저의 토큰과 Refresh Token 쿠키를 삭제하더라도 이미 발급된 Access Token은 만료 시점까지 유효할 수 있다.   
Stateless 구조에서 즉시 무효화하려면 블랙리스트나 별도의 토큰 저장소가 필요하다.

GitHub 커밋 분석 테스트에서는 API가 정상 응답하는 것만 확인하는 것으로 충분한지 고민했다.   
실제 분석 기능은 GitHub 응답을 규칙에 따라 가공하는 것이 핵심이므로, 커밋과 변경 파일의 분류 결과와 작업 상태까지 검증해야 했다.

---

커밋 컨벤션 일관성 분석을 처음에는 경로별로 하나의 커밋 규칙만 허용하거나 위반 여부를 판별하는 기능으로 이해하기 쉬웠다.   
실제 목적은 기존 커밋에서 사용된 형식을 보여주고 이후 커밋 작성 시 참고하도록 하는 것이므로, 같은 경로에서 여러 type이 발견되는 것은 오류가 아니다.

분석 결과를 그룹화할 때 규칙 엔티티의 ID로 다시 규칙을 조회하면 테스트에서 아직 저장되지 않은 엔티티의 ID가 `null`일 수 있었다.   
이미 분석된 커밋 객체가 일치한 규칙 정보를 가지고 있으므로 해당 정보를 직접 사용해 응답을 만드는 방식이 더 안정적이었다.

`docs(assignments): ...`에서 추출한 `scope`는 경로 규칙의 category나 scope가 아니라   
커밋 메시지에 직접 작성된 `assignments`라는 점도 구분해야 했다.

## 오늘 느낀 점

JWT 인증을 기존 게시판 전체 흐름에 적용하면서 토큰 발급만 구현하는 것으로 끝나지 않고,   
인증 필터, `SecurityContext`, 프론트 요청 처리와 서비스 인가 로직까지 연결해야 한다는 점을 확인했다.

클라이언트가 전달한 사용자 ID나 권한을 그대로 사용하지 않고 서버가 검증한 인증 객체를 기준으로 게시글 작성자와 권한을 판단해야 안전한 구조가 된다.   
테스트에서도 토큰 생성 여부뿐 아니라 작성자, 다른 사용자와 관리자의 권한 차이를 각각 검증해야 인가 로직을 정확히 확인할 수 있었다.

Repoary 커밋 분석 테스트에서는 외부 API 호출 결과부터 규칙 적용과 분석 상태 변경까지 전체 흐름을 검증해야 실제 기능의 안정성을 확인할 수 있었다.

수업 후에는 규칙 관리, 날짜별 분석과 컨벤션 분석을 프론트에 연결하고 실제 배포 환경에서 로그인 흐름까지 검증했다.

로컬에서 동작하는 React 라우팅도 정적 배포 환경에서는 rewrite 설정이 필요할 수 있으므로,   
기능 구현 후 실제 배포 주소에서 OAuth 로그인과 화면 이동을 포함한 전체 사용자 흐름을 확인하는 과정이 중요했다.

커밋 컨벤션 분석도 규칙 위반 여부를 판단하는 기능으로 단정하기보다,   
사용자가 기존 작성 경향을 확인하고 이후 형식을 선택하도록 돕는 기능으로 목적을 구체화하면서 적절한 데이터 구조와 화면 구성을 결정할 수 있었다.
