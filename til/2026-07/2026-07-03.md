## 오늘 배운 내용

오늘은 Spring MVC에서 요청이 `DispatcherServlet`을 거쳐 컨트롤러에 전달되는 흐름과 필터의 동작 위치를 학습하고,   
REST API를 직접 구현한 뒤 OpenFeign을 이용해 다른 API를 호출하는 과정을 실습했다.

OpenFeign은 외부 API 호출 코드를 직접 작성하지 않고 인터페이스에 요청 형식만 선언하면   
Spring이 런타임에 프록시 구현 객체를 생성해 실제 HTTP 요청을 수행한다.

외부 API의 쿼리 파라미터는 `@RequestParam`으로 표현하고, 중첩된 JSON 응답은 실제 계층과 동일한 DTO 구조로 매핑해야 한다.  
기상청 초단기실황 API는 자료 제공 시점을 고려해 현재 분이 40분보다 작으면 한 시간 전 발표 시각을 요청하도록 구성했다.

복습에서는 객체와 참조의 관계, 제네릭 타입 선언, `Iterator`, `Comparator`, Spring Bean과 프록시의 동작을 다시 정리했다.

PBL에서는 좌석 예약 상태를 `List<Seat>`로 관리하고,   
불변 객체의 상태를 직접 변경하지 않고 새로운 객체를 생성해 기존 위치에 교체하는 방식을 구현했다.

## 실습 및 과제

> DispatcherServlet과 필터 동작

Spring MVC에서는 클라이언트 요청이 먼저 `DispatcherServlet`으로 전달되고, 요청 경로와 HTTP 메서드에 맞는 컨트롤러 메서드가 실행된다.

필터는 `DispatcherServlet`보다 앞에서 요청과 응답을 가로챌 수 있으며,   
인증 확인, 요청 로깅, 문자 인코딩처럼 여러 요청에 공통으로 적용할 처리를 담당할 수 있다.

> REST API CRUD 구현

REST API에서 생성, 조회, 수정, 삭제 기능을 각각 HTTP 메서드와 연결해 구현했다.

컨트롤러는 요청을 받고 응답을 반환하며, 실제 데이터 처리와 비즈니스 로직은 서비스 계층으로 분리하는 흐름을 확인했다.

요청 본문은 `@RequestBody`, 경로에 포함된 값은 `@PathVariable`, 쿼리 문자열은 `@RequestParam`으로 받을 수 있다.

> OpenFeign 기반 REST API 호출

`@EnableFeignClients`로 Feign Client 탐색을 활성화하고, `@FeignClient` 인터페이스에 외부 API의 기본 URL과 요청 메서드를 선언했다.

인터페이스는 직접 `new`로 생성할 수 없지만,   
OpenFeign이 런타임에 HTTP 호출 기능을 가진 프록시 구현 객체를 만들고 Spring Bean으로 등록한다.

외부 API 쿼리 파라미터는 다음과 같이 `@RequestParam`으로 선언했다.

```java
@RequestParam("base_date") String baseDate
```

어노테이션에 작성한 이름은 외부 API에 전달되는 실제 파라미터명이므로 API 명세와 정확히 일치해야 한다.

> 날씨 API 호출 과제

기상청 초단기실황 API를 OpenFeign으로 호출하고, 응답 데이터를 사용자에게 보여줄 문자열 목록으로 가공했다.

인증키는 코드에 직접 작성하지 않고 환경변수에서 읽어 `@Value("${weather.api.key}")`로 주입했다.

이미 URL 인코딩된 인증키를 Feign이 다시 인코딩하면 인증 오류가 발생할 수 있으므로,   
인코딩 키와 디코딩 키가 따로 제공되는 경우에는 디코딩 키를 사용해야 한다.

응답 JSON은 다음과 같이 여러 계층으로 중첩되어 있으므로 DTO도 같은 구조로 구성했다.

```text
response
 ├─ header
 └─ body
     └─ items
         └─ item
```

JSON의 배열은 `List<Item>`으로 선언해 각 원소가 어떤 타입인지 명확하게 지정했다.  
필드명과 JSON 키가 같으면 Jackson이 값을 자동으로 매핑한다.

초단기실황 자료는 정각 직후 바로 제공되지 않을 수 있으므로 현재 분을 기준으로 발표 시각을 계산했다.

* 현재 분이 40분 미만 → 한 시간 전 자료 요청
* 현재 분이 40분 이상 → 현재 시간대 자료 요청

서비스에서는 전체 응답에서 관측 항목을 꺼낸 뒤 기상 코드와 값을 사람이 읽을 수 있는 문자열로 변환했다.

* `T1H` → 기온
* `REH` → 습도
* `PTY` → 강수 형태
* `RN1` → 1시간 강수량
* `WSD` → 풍속

컨트롤러는 기상청 원본 응답 전체가 아니라 최종적으로 가공된 `List<String>`만 반환하도록 구성했다.

> PBL Mission 06

공연장 좌석을 등록하고 예약·취소·조회하는 기능을 구현했다.

`addSeat()`에서는 좌석 번호가 `null`이거나 blank이면 `IllegalArgumentException`을 발생시켰다.  
같은 좌석 번호가 이미 등록되어 있으면 `IllegalStateException`으로 중복 등록을 차단했다.

좌석을 조회할 때는 `List<Seat>` 자체에서 좌석 번호를 조회하는 것이 아니라,   
반복문으로 각 `Seat` 객체를 꺼내 `getSeatNumber()`로 비교했다.

예약 시에는 좌석 번호와 예약자 입력을 검증하고 다음 상태를 구분했다.

* 존재하지 않는 좌석 → `NoSuchElementException`
* 이미 예약된 좌석 → `IllegalStateException`
* 정상 예약 → `reserved=true`, 예약자 정보가 포함된 새 객체로 교체

`Seat`가 불변 객체이므로 기존 객체의 필드를 직접 변경하지 않고,   
새로운 `Seat`를 생성해 `List.set(index, value)`로 같은 위치에 저장했다.

예약 취소 시에는 예약되지 않은 좌석의 취소를 예외 처리하고, 정상 취소에서는 `reserved=false`, `reserver=null`인 객체로 교체했다.

`getReservedCount()`는 전체 좌석 수인 `seats.size()`를 반환하지 않고, `isReserved()`가 `true`인 좌석만 순회하며 개수를 계산했다.

> 객체와 참조 복습

클래스는 객체 생성을 위한 설계도이며, 객체는 `new`를 통해 메모리에 생성된 실제 대상이다.

기존 객체의 필드값을 변경할 때마다 새 객체를 생성하는 것은 아니다.  
같은 객체의 참조를 여러 변수가 공유하면 한 변수를 통해 변경한 값이 다른 변수에서도 동일하게 보인다.

> 제네릭과 컬렉션 순회 복습

제네릭의 `<T>`는 어떤 값이든 저장한다는 뜻이 아니라, 실제 사용할 타입을 나중에 지정하기 위한 타입 매개변수다.

`Map<String, List<Item>>`은 바깥 구조부터 읽으면 key는 `String`, value는 `List<Item>`인 Map이다.

컬렉션의 순서는 `Iterator`가 만드는 것이 아니라 컬렉션 구현체의 특성에 따라 결정된다.

* `ArrayList` → 입력 순서 유지
* `HashSet`, `HashMap` → 순서 보장 없음
* `TreeSet` → 값 기준 정렬
* `TreeMap` → key 기준 정렬

`Iterator`는 컬렉션을 하나씩 순회하는 객체다. 단순 조회는 향상된 `for`문으로도 가능하지만,   
순회 중 요소를 안전하게 제거할 때는 `iterator.remove()`를 사용할 수 있다.

객체의 우선순위는 `Comparator`로 지정하고, 첫 번째 조건이 같을 때는 `thenComparing()`으로 다음 조건을 연결할 수 있다.

> Spring Bean과 프록시 복습

Spring Bean은 Spring 컨테이너가 생성하고 보관하며 의존관계를 연결해 주는 Java 객체다.

`@Component`, `@Service`, `@Repository`, `@Controller`, `@RestController`, `@Configuration` 등은 Bean 등록과 관련되지만,   
모든 어노테이션이 Bean을 생성하는 것은 아니다.

`@GetMapping`과 `@RequestBody`는 요청 처리와 관련되고, Lombok의 `@Builder`는 객체 생성 코드를 만드는 역할을 한다.

`@RequiredArgsConstructor`는 `final` 필드와 `@NonNull` 필드를 매개변수로 받는 생성자를 자동으로 생성한다.  
실제 필요한 Bean을 찾아 생성자에 전달하는 작업은 Spring이 담당한다.

프록시는 실제 객체 대신 요청을 먼저 받아 부가기능을 처리하거나 실제 대상 호출로 변환하는 대리 객체다.  
OpenFeign에서는 인터페이스 메서드 호출을 실제 HTTP 요청으로 변환한다.

## 헷갈렸던 점

일반 객체는 기존 필드값을 변경할 수 있지만, 필드가 `final`이고 setter가 없는 불변 객체는 기존 상태를 직접 변경할 수 없다.  
이 경우 PBL의 `Seat`처럼 새로운 상태의 객체를 생성해 기존 컬렉션 위치에 교체해야 한다.

`Iterator`는 이미 정해진 컬렉션의 순회 방식을 이용해 요소를 하나씩 접근한다.  
향상된 `for`문으로도 조회할 수 있지만, 순회 중 현재 요소를 안전하게 삭제해야 할 때는 `iterator.remove()`가 필요하다.

`@RequiredArgsConstructor`가 의존성을 직접 주입하는 것으로 생각하기 쉬웠지만, 이 어노테이션은 생성자만 만든다.  
생성된 생성자를 호출하고 필요한 Bean을 전달하는 것은 Spring 컨테이너다.

인터페이스는 직접 객체를 만들 수 없는데 `@FeignClient`를 주입받을 수 있는 이유도 확인했다.  
OpenFeign이 해당 인터페이스의 프록시 구현 객체를 런타임에 생성해 Bean으로 등록하기 때문이다.

초단기실황 API에서는 현재 시각을 그대로 요청하면 정각 직후 아직 생성되지 않은 자료를 조회할 수 있다.  
발표 자료가 제공되는 시간을 고려해 40분 기준으로 요청 시각을 계산해야 한다.

중첩 JSON을 DTO로 매핑할 때는 필요한 값만 생각해 하나의 DTO에 모두 넣는 것이 아니라 실제 JSON 계층과 필드명을 맞춰야 한다.

PBL에서는 상태 변경에 `add()`를 사용하면 기존 좌석이 교체되는 것이 아니라 새 요소가 추가되어 중복 데이터가 생길 수 있다.  
같은 위치의 객체 상태를 변경하려면 `List.set()`을 사용해야 한다.

`getReservedCount()`도 전체 좌석 개수와 예약된 좌석 개수를 구분해야 했다.  
예약된 좌석 수는 목록을 순회하며 상태가 `true`인 객체만 세어야 한다.

## 오늘 느낀 점

OpenFeign을 사용하면 외부 API 호출 코드를 줄일 수 있지만,   
요청 파라미터 이름과 JSON 응답 구조, 인증키 인코딩, 발표 시각 규칙은 API 명세에 맞게 직접 처리해야 한다는 점을 확인했다.

객체, 제네릭, 컬렉션, Spring Bean과 프록시를 다시 연결해서 복습하면서   
각각 따로 배운 개념이 실제 Spring 코드에서 어떻게 함께 사용되는지 이해할 수 있었다.

PBL에서는 불변 객체의 상태를 직접 수정하지 않고 새 객체로 교체하면서,   
상태에 따라 허용되는 동작과 금지되는 동작을 예외로 구분하는 것이 중요했다.
