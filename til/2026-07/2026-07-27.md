## 오늘 배운 내용

오늘은 Spring Security의 인증 처리 흐름을 확인하고, HTTP Basic 인증과 회원가입 기능을 실습했다.

Spring Security는 Controller가 실행되기 전에 필터 체인에서 인증과 인가를 처리한다.  
요청은 `DelegatingFilterProxy`를 거쳐 Spring Bean으로 관리되는 `FilterChainProxy`에 전달되고,   
요청과 일치하는 `SecurityFilterChain`의 보안 필터를 순서대로 통과한다.

HTTP Basic 인증에서는 `BasicAuthenticationFilter`가 `Authorization` 헤더를 확인하고,   
`AuthenticationManager`와 `DaoAuthenticationProvider`를 통해 인증을 수행한다.  
`UserDetailsService`는 사용자 정보를 조회하고 `PasswordEncoder`는 전달된 비밀번호와 저장된 비밀번호를 비교한다.

이번 실습에서는 `InMemoryUserDetailsManager`에 `user / 1234` 사용자를 등록하고 모든 요청에 인증을 요구하도록 설정했다.  
인증 정보가 없는 `/hello` 요청에는 `401 Unauthorized`가 반환되고, 올바른 계정으로 인증한 요청에는 `Hello World!`가 반환되는 흐름을 확인했다.

Form Login 실습에서는 회원가입 화면과 회원가입 API를 분리했다.  
`@Controller`는 Thymeleaf 화면을 반환하고, `@RestController`는 JSON 형식의 회원가입 요청을 처리했다.  
`Service`에서는 아이디 중복 여부를 확인하고 비밀번호를 `BCryptPasswordEncoder`로 암호화한 뒤 JPA `Repository`를 통해 MySQL에 저장했다.

회원가입 화면과 API, CSS와 JavaScript 경로에는 `permitAll()`을 적용하고 나머지 요청은 인증된 사용자만 접근하도록 설정했다.  
현재 구현 범위는 회원가입과 보안 접근 설정까지이며, DB에 저장된 사용자를 조회하는 실제 `.formLogin()` 인증은 아직 구현하지 않았다.

취업역량 강화 특강에서는 프로젝트 경험을 이력서와 면접 재료로 정리하는 기준을 확인했다.  
채용 과정에서는 사용한 기술의 수보다 문제를 어떻게 정의했고, 어떤 대안을 검토했으며, 해당 기술이나 구조를 선택한 이유와 적용 결과를 설명할 수 있는지가 중요하다.

프로젝트 경험은 `문제 → 필요성 → 대안 비교 → 선택 근거 → 구현 → 검증 결과`의 흐름으로 정리해야 한다.  
프로젝트마다 문제 발견 과정, 원인 분석, 해결 방법을 선택한 이유와 적용 이후의 변화를 포함한 트러블 슈팅 경험을 준비할 필요가 있다.

성과는 응답 시간, 쿼리 수, 오류 횟수, 테스트 수처럼 실제 측정한 자료가 있을 때 수치로 제시한다.  
정확한 수치가 없다면 억지로 작성하지 않고 기능 적용 전후의 동작 차이와 검증 방법을 구체적으로 설명해야 한다.

이력서는 하나의 기본 원본을 만든 뒤 채용공고에 따라 핵심 역량, 기술 스택 순서, 대표 프로젝트와 강조 경험을 조정하는 방식으로 관리해야 한다.  
채용공고도 지원할 회사를 찾는 용도에 그치지 않고, 시장에서 반복적으로 요구하는 기술과 경험을 확인해 학습 방향을 점검하는 자료로 활용할 수 있다.

## 실습 및 과제

> HTTP Basic 인증 실습

`SecurityFilterChain`에 `httpBasic()`과 `anyRequest().authenticated()`를 설정하고 인메모리 사용자를 등록했다.

인증 정보가 없는 요청과 올바른 계정을 포함한 요청을 각각 전송해 `401 Unauthorized`와 정상 응답의 차이를 확인했다.  
인증 성공 후에는 새로운 페이지로 이동하는 것이 아니라 원래 요청한 경로가 계속 처리된다는 점도 함께 확인했다.

> 회원가입과 보안 접근 설정

Thymeleaf 회원가입 화면에서 JavaScript를 사용해 `POST /api/users/join` 요청을 전송했다.

서버에서는 `SignUpRequestDto`로 입력값을 전달받고, 아이디 중복 여부를 검사한 뒤 비밀번호를 BCrypt로 암호화해 사용자 정보를 저장했다.  
회원가입 관련 화면과 정적 리소스는 인증 없이 접근할 수 있도록 허용하고 나머지 요청에는 인증을 요구했다.

> 취업역량 강화 특강과 경험 정리

채용 담당자는 기술 사용 경험 자체보다 기술을 선택하고 문제를 해결해 결과를 만든 과정을 확인한다는 점을 정리했다.

프로젝트 경험은 문제, 원인, 대안, 선택 근거, 적용 내용, 결과와 검증 방법을 키워드로 먼저 정리한 뒤 완성된 문장으로 다듬는 방식이 적절하다.  
처음부터 표현을 완성하려고 하면 실제 경험보다 문장 작성에 집중할 수 있으므로, 로그와 테스트 결과를 확인해 정확한 사실부터 정리해야 한다.

팀장이나 팀원이라는 역할 자체보다 요구사항 해석 조율, 구현 대안 제시, 일정 조정, 작업 기준 문서화와 같은 실제 행동이 프로젝트에 어떤 영향을 주었는지를 설명해야 한다.  
직접 구현한 기능이 아니더라도 문제 해결과 협업 개선에 주도적으로 참여한 경험은 자기소개서와 면접 소재로 활용할 수 있다.

## 헷갈렸던 점

HTTP Basic 인증 후 `/hello`로 자동 이동한다고 생각했지만, 인증 성공 후에는 처음 요청한 경로의 처리가 이어진다는 점을 확인했다.  
`/`에서 인증한 뒤 발생한 Whitelabel `404`는 인증 실패가 아니라 해당 경로에 매핑된 Controller가 없었기 때문이었다.

회원가입 기능을 구현한 것과 실제 로그인 인증을 구현한 것도 구분해야 했다.  
회원가입은 사용자 정보를 암호화해 저장하는 과정이고, 로그인은 저장된 사용자를 `UserDetailsService`로 조회하고 비밀번호를 검증한 뒤   
인증 정보를 `SecurityContext`에 저장하는 별도의 과정이다.

정확한 개선 수치가 없을 때 성과를 어떻게 표현해야 하는지도 고민했다.  
확인되지 않은 수치를 만드는 대신 적용 전후의 동작 차이, 테스트 통과 여부와 검증 방법을 구체적으로 작성하는 것이 적절하다는 점을 확인했다.

## 오늘 느낀 점

Spring Security는 설정 코드만 외우기보다 요청이 어떤 필터를 통과하고, 어떤 객체가 사용자 조회와 비밀번호 검증을 담당하는지 전체 흐름을 이해하는 것이 중요했다.  
`401`과 `404`처럼 서로 다른 처리 단계에서 발생하는 응답도 인증 필터와 Controller의 역할을 구분해야 정확히 판단할 수 있었다.

취업 준비에서도 새로운 기술과 경험을 계속 추가하는 것보다   
이미 진행한 프로젝트를 문제, 선택 기준, 해결 과정과 검증 결과가 드러나도록 정리하는 작업이 우선이라고 느꼈다.

프로젝트에서 팀장 역할이나 여러 영역을 담당했다는 사실만 강조하기보다,   
어떤 상황에서 어떤 판단을 내렸고 프로젝트 완성에 어떤 영향을 주었는지를 구체적으로 설명할 필요가 있다.
