## 오늘 배운 내용

오늘은 Spring Boot와 JPA를 이용해 회원가입·로그인 기능이 있는 게시판 프로젝트를 구현하면서,   
웹 애플리케이션의 요청 처리 흐름을 실제로 연결해 보았다.

화면을 여는 요청과 데이터를 처리하는 API 요청이 분리된다는 점을 확인했다.  
`/members/login`, `/members/join`은 HTML 화면을 반환하고,   
`/api/members/login`, `/api/members/join`은 JavaScript에서 보낸 데이터를 처리하는 API로 구성했다.

JPA에서는 Entity와 실제 DB 테이블 구조가 일치해야 한다.  
`Member` 엔티티의 `userId` 필드는 DB에서 `user_id` 컬럼으로 매핑되므로,   
실제 `member` 테이블에 해당 컬럼이 없으면 조회 시 오류가 발생할 수 있다.

Spring Data JPA에서는 `existsByUserId`, `findByUserId`처럼 메서드명을 규칙에 맞게 작성하면 Entity 필드명을 기준으로 쿼리를 자동 생성한다.  
이때 기준은 DB 컬럼명이 아니라 Entity의 필드명이며, Hibernate가 이를 실제 SQL로 변환해 DB에 실행한다.

`application.yml`에서 환경변수 값을 사용하려면 실제 환경변수로 등록하거나 `spring.config.import`로 `.env` 파일을 읽도록 설정해야 한다.

## 실습 및 과제

> JPA 기반 게시판 구현 실습

Spring Boot와 JPA를 이용해 회원가입과 로그인 기능이 포함된 게시판 프로젝트의 기본 흐름을 구현했다.

화면 요청과 API 요청을 분리했다.  
화면을 반환하는 요청은 `/members/login`, `/members/join`으로 두고,   
실제 데이터를 처리하는 요청은 `/api/members/login`, `/api/members/join`으로 구성했다.

Whitelabel Error Page가 서버 실행 실패를 의미하는 것은 아니며,   
요청한 URL에 해당하는 Controller 매핑이 없을 때 404로 표시될 수 있다는 점을 확인했다.  
따라서 임의의 `/login` 주소가 아니라 실제 `@GetMapping`에 정의된 `/members/login`으로 접근해야 했다.

로그인 기능에서는 세션 기반 로그인 흐름을 확인했다.  
로그인 요청이 들어오면 `MemberService`에서 `findByUserId`로 회원을 조회하고 비밀번호를 비교한 뒤,   
성공하면 `HttpSession`에 `userId`, `userName`을 저장했다.

이를 통해 서버가 로그인 상태를 기억하는 방식과 JWT가 아닌 세션 방식의 기본 흐름을 정리했다.

> Spring Data JPA Repository 메서드

`JpaRepository`를 상속하면 기본 저장, 조회, 삭제 기능을 사용할 수 있다.

`existsByUserId()`, `findByUserId()`처럼 메서드명을 규칙에 맞게 작성하면 Spring Data JPA가 메서드명을 분석해 쿼리를 자동으로 생성한다.

이때 `findByUserId`는 DB의 `user_id` 컬럼을 직접 기준으로 해석되는 것이 아니라, `Member` 엔티티의 `userId` 필드를 기준으로 해석된다.  
이후 Hibernate가 Entity 매핑 정보를 바탕으로 실제 SQL을 만들어 DB에 실행한다.

> DB 연결 설정

`.env` 파일에 값을 적었다고 해서 Spring Boot가 자동으로 읽는 것은 아니다.

`application.yml`에서 `${DB_URL}`, `${DB_USERNAME}`, `${DB_PASSWORD}`를 사용하려면 실제 환경변수로 등록하거나   
다음처럼 `.env` 파일을 읽도록 설정해야 한다.

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
```

> JPA 기반 회원가입 과제

회원가입 화면 요청과 API 요청을 분리했다.  
화면은 `/members/join`에서 반환하고, 실제 저장 처리는 `/api/members/join`에서 담당하도록 구성했다.

회원가입 요청은 Controller에서 받고, 중복 아이디 검사와 저장 로직은 Service에서 처리했다.  
Controller가 직접 중복 검사 로직을 담당하지 않도록 계층 역할을 나눴다.

중복 아이디가 존재하면 직접 만든 예외를 발생시키고, `@RestControllerAdvice`에서 해당 예외를 JSON 응답으로 변환하도록 구성했다.

> 개인 프로젝트 기획 정리

개인 프로젝트의 방향과 핵심 기능을 정리했다.

학습 기록, 커밋, TIL, 루틴 관리와 같은 키워드를 바탕으로 프로젝트 아이디어를 구체화하고, 실제 구현 범위와 서비스 성격을 고민했다.

## 헷갈렸던 점

화면 요청과 API 요청의 역할이 처음에는 헷갈렸다.

`/members/join`은 회원가입 화면을 보여주는 요청이고, `/api/members/join`은 JavaScript에서 보낸 회원가입 데이터를 처리하는 요청이다.  
HTML 화면을 반환하는 Controller와 JSON 데이터를 처리하는 API Controller는 역할이 다르다.

중복 아이디 예외 처리에서는 예외 클래스 import를 잘못 선택한 것이 문제였다.  
직접 만든 예외와 `@ExceptionHandler`가 처리하는 예외 타입이 일치해야 원하는 JSON 응답과 브라우저 알림 흐름이 동작한다.

## 오늘 느낀 점

Spring Data JPA가 메서드명으로 쿼리를 만들어 주더라도,   
그 기준이 Entity 필드명이라는 점을 이해하니 Repository 메서드의 동작 방식이 더 명확해졌다.

회원가입과 로그인 흐름을 화면 요청, API 요청, Service 로직, Repository 조회, 세션 저장으로 나누어 보면서   
웹 애플리케이션의 요청 처리 구조를 연결해 볼 수 있었다.

예외 처리는 서버에서 발생시키는 것만으로 끝나는 것이 아니라,   
Handler가 어떤 응답으로 바꾸고 브라우저가 그 응답을 어떻게 읽는지까지 이어서 확인해야 한다고 느꼈다.
