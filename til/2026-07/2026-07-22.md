## 오늘 배운 내용

오늘은 프로젝트 공통 처리 영역을 보완하며 예외 처리, 파일 업로드, 소프트 딜리트와 외부 API 연동 흐름을 정리했다.

공통 예외 처리는 `BusinessException`과 `ErrorCode`를 기준으로 오류 응답을 통일했다.  
REST API에서 발생한 예외는 공통 JSON 형식으로 반환하고,   
Thymeleaf 화면 요청에서 발생한 예외는 오류 메시지를 전달한 뒤 관리자 화면으로 이동하도록 처리했다.

상품 삭제에는 데이터를 실제로 제거하지 않고 `deletedAt`에 삭제 시점을 기록하는 소프트 딜리트를 적용했다.   
일반 상품 목록·검색·상세 조회·수정·재고 변경과 관리자 상품 목록에서 삭제된 상품을 제외하도록 상품 조회 범위를 조정했다.

주문 생성 이후 관리자에게 Slack DM을 전송하는 기능도 구현했다.  
주문 생성 Service가 Slack API를 직접 호출하지 않고 주문 생성 이벤트를 발행하도록 구성했으며,   
트랜잭션이 정상적으로 커밋된 이후 이벤트 리스너가 알림을 전송하도록 처리했다.

Slack Bot Token과 관리자 멤버 ID는 환경변수로 관리했다.  
Slack 전송 실패가 정상적인 주문 생성에 영향을 주지 않도록 외부 API 호출 예외는 이벤트 리스너 내부에서 처리했다.

## 실습 및 과제

> 상품 공통 예외 처리 보완

상품과 주문 영역에서 발생하는 비즈니스 예외와 요청값 검증 오류를 공통 예외 처리 구조에 연결했다.

REST API 요청에서는 `ErrorResponse` 형식으로 JSON 오류 응답을 반환하도록 구성했다.    
Thymeleaf 관리자 화면에서 발생한 예외는 JSON으로 반환하지 않고 오류 메시지를 전달한 뒤 상품 관리 화면으로 이동하도록 처리했다.

> 상품 이미지 업로드

상품 등록·수정 요청을 `multipart/form-data`로 변경하고 이미지 파일을 업로드할 수 있도록 구현했다.

업로드된 파일의 이미지 형식과 크기를 검증하고, UUID 기반 파일명으로 로컬 경로에 저장한 뒤 생성된 이미지 URL을 상품 정보에 반영했다.  
업로드 경로는 정적 리소스로 접근할 수 있도록 `WebConfig`에 리소스 핸들러를 추가했다.

상품 수정에서는 기존 이미지 유지, 새 이미지 교체와 이미지 제거를 구분해 처리했다.  
관리자 화면에는 현재 상품 이미지 미리보기와 업로드 오류 메시지를 추가했다.

이미지 업로드 기능을 추가한 뒤 `ProductServiceTest`에서 새로 주입된 `ImageStorageService`가 설정되지 않아 테스트가 실패했다.  
테스트에 Mock 객체를 추가하고 이미지 저장 결과를 Stub으로 설정해 해결했다.

> 상품 소프트 딜리트

상품 삭제 시 DB 데이터를 실제로 제거하지 않고 `deletedAt`에 삭제 시점을 기록하도록 변경했다.

활성 상품만 조회하는 Repository 메서드를 추가하고, 상품 목록·검색·상세 조회·수정·재고 변경에서 삭제된 상품을 제외하도록 처리했다.

관리자 화면에서도 삭제된 상품이 노출되지 않도록 상품 조회 범위를 조정했다.

> Slack 주문 알림

Slack 앱을 생성하고 `chat:write` Bot 권한을 설정한 뒤 Bot User OAuth Token을 발급받았다.

주문 생성이 완료되면 주문 생성 이벤트를 발행하고, `OrderCreatedEventListener`가 트랜잭션 커밋 이후 실행되도록 구성했다.  
알림에는 주문 번호, 주문자 이메일, 배송지, 주문 상품, 총금액과 주문 시각을 포함했다.

Slack API 호출은 `RestClient`로 처리하고, Bot Token을 `Authorization: Bearer` 헤더에 담아 전송했다.  
응답의 `ok` 값을 확인해 성공 여부를 판단하고, 실패한 경우에는 예외를 주문 처리로 전파하지 않고 로그만 기록했다.

리스너 단위 테스트에서는 주문 정보로 Slack 메시지가 정상적으로 생성되는 경우와 Slack 전송 실패 시 예외가 외부로 전파되지 않는 경우를 검증했다.

## 헷갈렸던 점

웹용 `PageController`가 기존 REST Controller를 다시 호출하거나 같은 기능을 중복 구현하는 것인지 헷갈렸다.

두 Controller는 요청과 응답 형식만 다르며 서로를 호출하지 않는다.  
REST Controller는 JSON 요청과 응답을 처리하고,   
`PageController`는 Thymeleaf 화면 요청을 처리하며 실제 비즈니스 로직은 공통 `ProductService`에 위임한다.

소프트 딜리트를 적용할 때 모든 상품 조회에 전역 필터를 적용해도 되는지도 고민됐다.  
전역 필터를 적용하면 상품을 참조하는 다른 도메인의 조회에도 영향을 줄 수 있으므로,   
상품 목록·검색·상세 조회·수정·재고 변경처럼 활성 상품만 필요한 Repository 메서드에 조회 조건을 명시적으로 적용했다.

Slack 요청의 `Authorization` 헤더가 Compose Bean의 사용자 로그인 인증과 관련된 것인지도 헷갈렸다.  
해당 헤더는 Compose Bean 서버가 Slack API에 요청할 때 Bot의 권한을 증명하기 위한 외부 API 인증이며, 프로젝트 내부 로그인 인증과는 별개다.

주문 저장 직후 Slack API를 직접 호출하면 트랜잭션이 이후 롤백되더라도 알림이 먼저 전송될 수 있다는 점도 확인했다.  
따라서 `AFTER_COMMIT` 이벤트 리스너를 사용해 실제 주문 트랜잭션이 성공한 이후에만 알림을 전송하도록 구성해야 했다.

## 오늘 느낀 점

기능 하나를 추가할 때 Service 코드만 수정하는 것이 아니라   
DTO, Controller, 웹 폼, 예외 처리, 정적 리소스 설정, Repository 조회 조건, 환경변수와 테스트까지 함께 변경해야 정상적인 기능이 완성된다는 점을 체감했다.

특히 이미지 업로드와 Slack 연동처럼 파일 시스템이나 외부 API를 사용하는 기능은 핵심 비즈니스 로직과 분리하고,   
실패가 전체 기능에 미치는 범위를 명확히 정해야 했다.

주문 생성과 Slack 알림을 이벤트로 분리하면서 주문 Service가 Slack API의 구체적인 구현을 직접 알지 않도록 구성할 수 있었다.  
트랜잭션 커밋 이후 처리와 부가 기능 실패 격리가 필요한 이유를 실제 코드로 확인했다.

소프트 딜리트도 단순히 삭제 쿼리를 변경하는 작업이 아니라,  
상품 목록·검색·상세 조회·수정·재고 변경 등 각 기능에서 삭제된 상품을 제외하도록 조회 조건을 함께 설계해야 하는 작업이었다.
