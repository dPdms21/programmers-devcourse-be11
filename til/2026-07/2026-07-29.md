## 오늘 배운 내용

오늘은 Spring Security에서 세션 대신 JWT를 이용해 요청마다 인증 정보를 복원하는 흐름을 학습했다.

JWT는 Header, Payload, Signature로 구성된다.  
Payload는 암호화된 영역이 아니므로 비밀번호와 같은 민감한 정보를 저장하면 안 된다.   
서버는 비밀 키로 토큰의 서명과 만료 시간을 검증하고, 검증된 Claim에서 사용자 ID와 권한을 꺼내 인증 정보를 복원한다.

`TokenAuthenticationFilter`는 `Authorization: Bearer <JWT>` 헤더에서 토큰을 추출하고 유효성을 검증한다.  
검증에 성공하면 사용자 정보를 바탕으로 `Authentication`을 생성해 `SecurityContextHolder`에 저장한다.   
토큰을 검증하는 것만으로 인증이 완료되는 것이 아니라, 현재 요청에서 사용할 인증 객체를 `SecurityContext`에 등록해야 한다.

JWT 관련 클래스의 세부 메서드를 모두 외우기보다 각 구성 요소의 역할을 구분하는 것이 중요했다.  
`TokenProvider`는 토큰 생성·검증·정보 추출을 담당하고, `TokenAuthenticationFilter`는 요청 헤더의 토큰을 처리한다.   
`CustomUserDetails`는 도메인 사용자를 Spring Security 형식으로 변환하고, `SecurityConfig`는 Stateless 세션 정책과 필터 등록을 담당한다.

`@ConfigurationProperties`는 필드 순서가 아니라 설정 이름을 기준으로 값을 연결한다.  
`access-token-validity`는 `accessTokenValidity`에 매핑되며,   
setter 방식으로 바인딩하는 클래스에 setter가 없으면 `No setter found for property` 오류가 발생한다.

Repoary에서는 저장소별 분류 규칙과 커밋 규칙을 관리하는 기능을 구현했다.  
저장소를 연결할 때 기본 규칙을 자동으로 생성하고, 사용자가 규칙을 조회·추가·수정·비활성화·삭제할 수 있도록 구성했다.   
삭제한 기본 규칙을 복원하고, 복원 요청을 반복해도 같은 규칙이 중복 생성되지 않도록 처리했다.

기능 구현 이후에는 다른 사용자의 저장소 접근 차단, 중복 패턴 검증, 활성화 상태 변경과 기본 규칙 복원 동작을 테스트했다.   
현재 완료한 범위는 저장소 규칙을 생성하고 관리하는 기능까지이며, 실제 GitHub 커밋을 조회해 규칙을 적용하는 분석 기능은 아직 남아 있다.

## 실습 및 과제

> JWT 토큰 인증 실습

`TokenProvider`를 통해 JWT를 생성하고 서명, 만료 시간과 Claim을 검증하는 흐름을 확인했다.

`TokenAuthenticationFilter`에서는 Bearer 접두사를 제거해 토큰을 추출하고, 유효한 토큰에서 사용자 정보를 복원했다.   
이후 `UsernamePasswordAuthenticationToken`을 생성해 `SecurityContextHolder`에 등록하고,   
`filterChain.doFilter()`를 호출해 요청을 다음 필터로 전달했다.

회원가입 테스트 과정에서는 기존 Form Login 실습의 `user` 테이블과 현재 `User` 엔티티 구조가 달라 오류가 발생했다.  
기존 테이블을 참조하는 외래 키 때문에 `user` 테이블을 바로 삭제할 수 없어 참조 테이블을 먼저 제거한 뒤 현재 엔티티 구조에 맞게 다시 생성했다.

테이블 삭제 후에는 자동 생성 설정이 없어 테이블을 찾을 수 없었으므로 `spring.jpa.hibernate.ddl-auto: update`를 적용했다.   
이후 저장 과정에서 `Connection is read-only` 오류가 발생했으며,   
클래스의 `@Transactional(readOnly = true)`가 회원가입 메서드에도 적용된 것이 원인이었다.   
회원가입 메서드에 별도의 `@Transactional`을 적용해 쓰기 트랜잭션으로 실행되도록 수정했다.

> Repoary 저장소 규칙 생성 및 관리

`classification_rules`, `convention_rules` 테이블과 엔티티를 기반으로 저장소 연결 시 기본 분류 규칙과 커밋 규칙이 자동 생성되도록 구현했다.

규칙 조회·추가·수정·비활성화·삭제 API를 구현하고, 삭제한 기본 규칙을 다시 생성하는 복원 기능을 추가했다.  
반복해서 복원을 요청하더라도 같은 패턴의 규칙이 중복 생성되지 않도록 검증했다.

규칙 서비스 테스트를 통해 저장소 소유권 검증, 중복 패턴 차단, 활성화 상태 변경과 기본 규칙 복원 결과를 확인했다.

규칙 관리 기능 구현 후에는 Controller와 DTO의 Swagger 설명을 정리해 요청값과 응답 구조, API별 처리 내용을 문서에서 확인할 수 있도록 수정했다.  
정리한 Swagger 문서를 기준으로 저장소 소유권 검증, 중복 패턴 차단, 활성화 상태 변경과 기본 규칙 복원 동작을 수동 테스트했다.

기능 브랜치를 `develop`에 직접 병합하고 원격 저장소에 반영한 뒤 로컬·원격 기능 브랜치를 정리하고 관련 이슈를 닫았다.  
이번 이슈에는 규칙 관리와 테스트까지만 포함하고, GitHub 커밋 조회와 규칙 적용, 분석 작업 상태 관리는 다음 기능 범위로 분리했다.

## 헷갈렸던 점

JWT를 검증하면 인증 처리가 모두 끝나는 것으로 생각하기 쉬웠지만,   
토큰에서 복원한 사용자 정보를 `Authentication`으로 변환해 `SecurityContext`에 저장해야 현재 요청이 인증된 요청으로 처리된다.

JWT 관련 코드에는 처음 보는 라이브러리 메서드가 많아 전체를 직접 작성하기 어렵게 느껴졌다.  
세부 문법을 모두 외우기보다 토큰 생성·검증, 요청 헤더 처리, 사용자 변환과 인증 객체 등록으로 역할을 나누어 흐름을 이해할 필요가 있었다.

`@ConfigurationProperties`는 필드 선언 순서에 따라 값을 주입하는 것이 아니라 설정 이름을 기준으로 바인딩한다.   
`JwtProperties`에 getter만 두었을 때는 값을 주입할 setter가 없어 오류가 발생했다.

회원가입 API 주소와 성공 후 이동할 화면 주소도 구분해야 했다.  
`POST /api/users/join`은 회원가입 요청을 처리하는 백엔드 API이고, 응답의 `/users/login`은 처리가 끝난 뒤 이동할 화면 경로다.

Repoary 규칙 관리 기능이 끝난 뒤 전체 백엔드 개발까지 완료된 것인지 헷갈렸지만, 이번에 완료한 범위는 규칙 생성과 관리까지다.   
실제 커밋 데이터를 조회하고 규칙에 따라 분석 결과를 만드는 기능은 별도의 작업으로 남아 있다.

## 오늘 느낀 점

JWT 인증은 토큰을 생성하는 기능 하나가 아니라 로그인 후   
토큰 발급, 클라이언트의 토큰 전달, 필터의 검증, 사용자와 권한 복원, `Authentication` 생성과 `SecurityContext` 등록으로 이어지는 전체 흐름이었다.

처음부터 JWT 관련 코드를 모두 작성하기는 어렵지만,   
요청이 들어온 뒤 각 클래스가 어떤 역할을 수행하는지 순서대로 확인하면 기존 프로젝트에서 사용했던 JWT 구조도 더 명확하게 이해할 수 있었다.

Repoary에서는 기능 구현뿐 아니라 이슈 단위의 완료 범위를 구분하는 것이 중요했다.  
규칙 관리 기능은 마이그레이션부터 API, 복원 처리, 테스트와 병합까지 마무리했지만,   
이를 전체 분석 기능 완료로 확대하지 않고 남은 작업과 구분해야 실제 진행 상황을 정확히 판단할 수 있다.
