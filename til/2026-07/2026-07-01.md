## 오늘 배운 내용

오늘은 트랜잭션 부가기능을 비즈니스 로직에서 분리한 뒤, 프록시와 AOP를 통해 자동으로 적용하는 흐름을 학습했다.

프록시는 실제 서비스 객체 앞에서 요청을 먼저 받아 트랜잭션과 같은 부가기능을 수행한 뒤 실제 객체의 메서드를 호출한다.  
이를 통해 `UserServiceImpl`은 사용자 등급 변경과 같은 핵심 비즈니스 로직만 담당하고,   
트랜잭션 시작·커밋·롤백은 프록시가 담당하도록 분리할 수 있다.

JDK 다이내믹 프록시에서는 `InvocationHandler`가 프록시로 전달된 메서드 호출을 처리하고,   
`Method` 객체와 `method.invoke(target, args)`를 이용해 실제 대상 메서드를 실행한다.

Spring AOP에서는 부가기능을 담당하는 Advice와 적용 대상을 선택하는 Pointcut을 분리하고, 두 요소를 Advisor로 묶어 프록시에 적용한다.  
자동 프록시 생성기를 사용하면 서비스마다 프록시를 직접 등록하지 않아도 조건에 맞는 Spring Bean에 동일한 부가기능을 적용할 수 있다.

최종적으로 `@Transactional`을 사용하면 프록시, Advice, Pointcut을 직접 구성하지 않고   
선언만으로 트랜잭션을 적용할 수 있지만, 내부적으로는 여전히 프록시를 통해 동작한다.

과제에서는 성능 측정과 예외 로깅을 AOP Advice로 분리하고, Pointcut을 이용해 서비스 계층의 메서드에 자동으로 적용했다.

PBL에서는 도서의 등록, 조회, 대출, 반납 기능을 구현하며 객체의 상태를 직접 변경할 수 없는 구조에서 새 객체로 교체하는 방법을 학습했다.

## 실습 및 과제

> JDK 다이내믹 프록시와 리플렉션

`Proxy.newProxyInstance()`를 이용해 런타임에 `UserService` 인터페이스의 프록시 객체를 생성했다.

프록시로 전달된 모든 메서드 호출은 `InvocationHandler`의 `invoke()`로 전달된다.  
호출된 메서드 정보는 `Method` 객체로 전달되며, `method.invoke(target, args)`를 실행해 실제 대상 객체의 메서드를 호출했다.

`TransactionHandler`에서는 메서드 이름이 지정한 패턴으로 시작하는지 확인해 트랜잭션 적용 여부를 결정했다.

조건에 맞는 메서드는 트랜잭션을 시작한 뒤 실제 메서드를 실행하고, 성공하면 커밋하며 예외가 발생하면 롤백하도록 구성했다.

> Spring ProxyFactoryBean과 AOP 구성 요소 분리

`ProxyFactoryBean`을 사용해 프록시 생성을 Spring에 맡겼다.

이전에는 `TransactionHandler`가 트랜잭션 기능과 적용 대상 선정 로직을 모두 담당했지만, 이번에는 이를 Advice와 Pointcut으로 분리했다.

* Advice → 트랜잭션처럼 실제로 수행할 부가기능
* Pointcut → 부가기능을 적용할 메서드 선택
* Advisor → Advice와 Pointcut을 묶은 적용 규칙

`TransactionAdvice`는 실제 대상 객체를 직접 보관하지 않고   
`invocation.proceed()`를 호출해 다음 Advice나 실제 서비스 메서드로 실행을 전달했다.

적용 대상은 `NameMatchMethodPointcut`을 사용해 `upgrade*`처럼 특정 이름 패턴과 일치하는 메서드로 한정했다.

> 자동 프록시 생성과 선언적 트랜잭션

`DefaultAdvisorAutoProxyCreator`를 사용해 Spring Bean 생성 시 등록된 Advisor와 일치하는 객체를 자동으로 프록시로 감싸도록 구성했다.

서비스는 일반 Bean으로 등록하고 Advisor만 준비하면 되므로, 서비스마다 `ProxyFactoryBean`을 직접 등록하는 반복을 줄일 수 있었다.

이후 `@EnableTransactionManagement`와 `@Transactional`을 사용해 직접 구성했던 프록시와 트랜잭션 Advice 설정을 선언적인 방식으로 변경했다.

코드에서는 어노테이션만 사용하지만 실제로는 Spring 프록시가 메서드 호출을 먼저 받아 트랜잭션을 시작하고, 성공 시 커밋하며 실패 시 롤백한다.

> AOP 과제

`AspectJExpressionPointcut`에 다음과 같은 표현식을 적용해 서비스 패키지와 하위 패키지의 모든 메서드를 대상으로 지정했다.

```java
execution(* com.example.spring.aop.service..*.*(..))
```

성능 측정 Advice에서는 `MethodInterceptor`의 `proceed()` 전후 시간을 비교했다.  
예외가 발생해도 실행 시간을 출력할 수 있도록 후처리 로직은 `finally`에 작성했다.

예외 로깅 Advice에서는 대상 메서드에서 발생한 예외 정보를 출력한 뒤 반드시 다시 던지도록 구현했다.  
예외를 다시 던지지 않으면 Advice가 실패를 숨겨 호출자가 정상적으로 예외를 처리할 수 없기 때문이다.

`DefaultAdvisorAutoProxyCreator`가 Advisor의 Pointcut과 일치하는 Spring Bean을 자동으로 프록시로 감싸므로,   
서비스 구현체에는 AOP 관련 코드를 작성하지 않고 비즈니스 로직만 유지했다.

새로운 서비스가 같은 패키지 아래에 Spring Bean으로 등록되면   
기존 Pointcut 표현식과 일치하므로 별도의 AOP 설정 변경 없이 동일한 Advice가 적용된다.

여러 Advisor의 실행 순서는 `DefaultPointcutAdvisor`의 `setOrder()`로 지정했다.  
숫자가 작을수록 바깥쪽에 위치하므로 메서드 호출 전에는 작은 순서부터 실행되고, 대상 메서드 실행 후에는 역순으로 종료된다.

> PBL Mission 04

도서 등록, 대출, 반납, 단건 조회, 전체 조회 기능을 담당하는 `LibraryService`를 구현했다.

도서를 등록할 때 제목이 `null`이거나 blank이면 `IllegalArgumentException`을 발생시켰다.  
도서 ID는 `nextId`를 사용해 1부터 순차적으로 증가시켰으며, 생성한 `Book` 객체를 반드시 `books` 목록에 추가한 뒤 반환했다.

`books`는 `List<Book>`이므로 리스트 자체에서 `getId()`를 호출할 수 없다.  
반복문으로 `Book` 객체를 하나씩 꺼낸 뒤 `book.getId()`로 비교해야 한다.

존재하지 않는 도서에 대한 예외는 목록을 끝까지 탐색한 뒤 발생시켜야 한다.  
반복문 중간에 현재 ID가 다르다는 이유로 즉시 예외를 던지면 뒤에 존재하는 도서를 찾을 수 없다.

`Book`의 모든 필드가 `final`이고 setter가 없으므로 기존 객체의 대출 상태를 직접 변경할 수 없었다.  
따라서 대출과 반납 시 같은 ID와 제목을 유지한 새로운 `Book` 객체를 생성한 뒤 `List.set(index, value)`로 기존 위치의 객체를 교체했다.

대출 시에는 이미 대출된 도서인지 확인하고 `rented=true`, `renter=대출자`인 새 객체로 교체했다.  
반납 시에는 대출 중인지 확인한 뒤 `rented=false`, `renter=null`인 객체로 교체했다.

전체 도서 목록은 내부 `List`를 직접 반환하지 않고 `new ArrayList<>(books)`로 방어적 복사해 반환했다.

공개 테스트 1개와 hidden review 4개를 모두 통과해   
도서 등록, ID 증가, 대출·반납 상태 변경, 예외 처리와 내부 컬렉션 보호가 정상적으로 동작함을 확인했다.

## 헷갈렸던 점

다이내믹 프록시와 리플렉션 API를 개발자가 모두 직접 구현해야 하는지 헷갈렸다.

실제 개발에서는 대부분 `@Transactional`과 Spring AOP를 사용하므로   
`Proxy.newProxyInstance()`, `InvocationHandler`, `Method` API의 세부 사용법을 암기할 필요는 없다.

다만 `@Transactional`이 프록시를 통해 동작한다는 흐름은 이해해야 한다.  
같은 클래스 내부에서 메서드를 직접 호출하거나 프록시가 가로챌 수 없는 메서드를 호출하면 트랜잭션이 적용되지 않을 수 있기 때문이다.

`MethodInterceptor`의 `proceed()`는 단순히 다음 코드를 실행하는 것이 아니라 다음 Advice 또는 실제 대상 메서드로 호출을 전달한다.

AOP가 적용된 서비스 객체를 직접 `new`로 생성하면 Spring 프록시를 거치지 않는다.  
따라서 자동 프록시가 적용된 객체는 Spring 컨테이너에서 조회해야 한다.

여러 Advisor가 적용될 때 `order` 값이 작을수록 먼저 실행되지만,   
이는 바깥쪽에서 호출을 감싸는 구조이므로 대상 메서드 실행 후에는 반대 순서로 종료된다는 점을 확인했다.

PBL에서는 `List<Book>`과 `Book` 객체를 구분해야 했다.  
리스트에서 바로 `getId()`를 호출하는 것이 아니라 반복문으로 각 `Book`을 꺼내 ID를 비교해야 한다.

또한 도서를 찾는 반복문 안에서 첫 번째로 일치하지 않는 ID를 만났다고 바로 예외를 발생시키면 안 된다.  
모든 도서를 확인한 뒤에도 찾지 못한 경우에만 `NoSuchElementException`을 발생시켜야 한다.

`Book` 객체는 불변 구조이므로 대출 상태를 setter로 변경할 수 없었다.  
`List.set()`을 이용해 기존 위치의 객체를 새로운 상태의 객체로 교체해야 하며, `add()`를 사용하면 기존 요소가 교체되지 않고 목록 크기만 증가한다.

## 오늘 느낀 점

프록시와 AOP는 단순히 반복 코드를 줄이는 기능이 아니라,   
핵심 비즈니스 로직과 트랜잭션·로깅·성능 측정 같은 부가기능의 책임을 분리하는 방식이라는 점을 이해했다.

직접 다이내믹 프록시를 구현한 뒤 `ProxyFactoryBean`, 자동 프록시 생성기, `@Transactional` 순서로 학습하니   
선언적 트랜잭션 내부에서 어떤 과정이 자동화되는지 확인할 수 있었다.

AOP는 Pointcut의 범위를 넓게 지정하면 새로운 서비스에도 자동으로 적용할 수 있지만,   
의도하지 않은 Bean이나 메서드까지 포함되지 않도록 적용 범위를 정확히 설계해야 한다고 느꼈다.

PBL에서는 객체의 상태를 직접 변경하지 못하는 경우 기존 객체를 수정하려고 하기보다 새로운 상태의 객체를 만들어 교체하는 방법을 적용했다.

또한 컬렉션을 탐색할 때 예외를 발생시키는 위치와 내부 목록을 외부에 노출하지 않는 방어적 복사가 중요하다는 점을 다시 확인했다.
