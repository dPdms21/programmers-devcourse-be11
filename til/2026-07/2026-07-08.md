## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습과 과제에서 게시글 상세 조회, 작성, 수정, 삭제까지 이어지는 CRUD 흐름을 학습했다.

게시글 상세 조회에서는 목록 화면에서 특정 게시글 `id`를 기준으로 상세 화면에 접근하고,   
URL 경로의 값을 `@PathVariable`로 받아 게시글 하나를 조회하는 구조를 확인했다.   
Entity를 그대로 응답하지 않고 `BoardDetailResponseDto`로 변환해 화면에 필요한 데이터만 내려주는 흐름도 정리했다.

게시글 작성과 수정에서는 파일 첨부가 포함될 수 있으므로 JSON 요청이 아니라   
`FormData` 기반의 `multipart/form-data` 요청을 사용해야 한다는 점을 확인했다.   
이때 Controller에서는 `@RequestBody`가 아니라 `@ModelAttribute`로 DTO를 받아야 한다.

파일 처리에서는 `MultipartFile`로 업로드 파일을 받고, 다운로드에서는 `Resource`를 `ResponseEntity`에 담아 반환하는 흐름을 학습했다.   
단순히 파일 내용만 반환하는 것이 아니라 `Content-Disposition` 헤더를 설정해야 브라우저가 파일을 다운로드로 처리한다.   
한글 파일명은 `URLEncoder`로 UTF-8 인코딩하고, 공백 처리를 위해 `+`를 `%20`으로 치환해야 한다는 점도 정리했다.

수정 기능에서는 JPA의 dirty checking을 사용했다.   
`@Transactional` 안에서 조회한 Entity는 영속 상태이므로,   
`board.update()`로 값을 변경하면 트랜잭션 커밋 시점에 JPA가 변경을 감지해 UPDATE SQL을 실행한다.

## 실습 및 과제

> Spring Boot jpa-board 게시글 CRUD 실습

게시글 목록에서 상세 화면으로 이동하고, 상세 화면에서 게시글 데이터를 API로 조회하는 흐름을 확인했다.

`BoardController`는 `/detail`, `/update/{id}`처럼 화면을 여는 요청을 처리하고,   
`BoardApiController`는 `/api/boards/{id}`처럼 실제 게시글 데이터를 JSON으로 반환하는 요청을 처리한다.   
화면 요청과 API 요청의 역할을 분리해 구성했다.

게시글 작성에서는 `FormData`를 사용해 제목, 내용, 작성자 아이디, 파일을 함께 전송했다.   
서버에서는 `@ModelAttribute BoardWriteRequestDto`로 값을 받고, 업로드된 파일은 `MultipartFile`로 처리했다.

파일 다운로드에서는 `Resource`를 `ResponseEntity`에 담아 반환했다.   
다운로드로 처리되도록 `Content-Disposition: attachment` 헤더를 설정하고, 한글 파일명이 깨지지 않도록 파일명을 UTF-8로 인코딩했다.

수정과 삭제에서는 DB 데이터만 변경하는 것이 아니라   
기존 첨부파일 삭제, 새 파일 저장, `filePath` 갱신 같은 실제 파일 정리 흐름도 함께 고려해야 한다는 점을 확인했다.

> 게시판 상세 조회와 예외 처리 과제

게시글 상세 조회에서는 `/detail?id=...`와 `/api/boards/{id}`의 역할을 구분했다.

`/detail?id=...`는 상세 화면 HTML을 여는 요청이고, `/api/boards/{id}`는 실제 게시글 데이터를 JSON으로 가져오는 API다.   
상세 화면에서는 Controller가 `id`를 Model에 담아 전달하고, JavaScript가 해당 값을 이용해 상세 API를 호출한다.

게시글이 존재하지 않는 경우에는 직접 만든 예외를 발생시키고, 공통 예외 처리에서 JSON 응답으로 변환하도록 구성했다.

> 게시판 글쓰기와 파일 업로드 과제

글쓰기에서는 파일이 포함될 수 있으므로 `FormData`와 `multipart/form-data` 방식을 사용했다.

서버에서는 `@RequestBody`가 아니라 `@ModelAttribute BoardWriteRequestDto`로 제목, 내용, 작성자 아이디, 파일을 받았다.   
업로드된 파일은 `MultipartFile.transferTo()`로 저장하고, DB에는 파일 자체가 아니라 `filePath`를 저장했다.

> 게시판 수정·삭제와 파일 처리 과제

수정 요청도 파일이 포함될 수 있으므로 `FormData`와 `@ModelAttribute BoardUpdateRequestDto`를 사용했다.

기존 파일을 유지할지, 새 파일로 교체할지, 파일을 제거할지는 `fileFlag`로 구분했다.   
`fileFlag`가 `false`이면 기존 파일 경로를 유지하고,   
`true`이면 기존 파일을 삭제한 뒤 새 파일이 있으면 저장하고 없으면 `filePath`를 `null`로 처리한다.

삭제 기능에서는 `DELETE /api/boards/{id}`로 게시글을 삭제하고,   
요청 body에 담긴 `filePath`를 이용해 서버에 저장된 첨부파일도 함께 삭제했다.   
삭제 요청은 JSON body를 사용하므로 `@RequestBody BoardDeleteRequestDto`로 받는 것이 맞다.

## 헷갈렸던 점

`@RequestParam`과 `@PathVariable`의 차이가 헷갈렸다.   
`?id=1`처럼 쿼리 파라미터로 전달되는 값은 `@RequestParam`으로 받고,   
`/api/boards/1`처럼 URL 경로에 포함된 값은 `@PathVariable`로 받는다는 기준을 정리했다.

요청 바인딩 방식도 헷갈렸다.   
JSON 요청은 `@RequestBody`, 일반 form 요청이나 파일이 포함된 multipart 요청은 `@ModelAttribute`로 받아야 한다.   
파일이 포함된 요청을 `@RequestBody`로 받으면 `Content-Type 'multipart/form-data' is not supported` 오류가 발생할 수 있다.

파일 다운로드에서는 `Resource`만 반환하면 다운로드 파일명과 응답 헤더를 제어하기 어렵다는 점이 헷갈렸다.   
파일 다운로드로 처리하려면 `ResponseEntity`로 상태 코드, 헤더, 본문을 함께 구성해야 한다.

## 오늘 느낀 점

게시판 CRUD는 단순히 DB에 데이터를 저장하고 조회하는 기능이 아니라,   
화면 요청, API 요청, DTO 변환, 파일 저장, 예외 처리, 트랜잭션 흐름이 함께 연결되어야 완성된다는 점을 느꼈다.

특히 파일 업로드와 다운로드가 들어가면서 요청 방식과 응답 헤더를 정확히 구분해야 했다.   
`@RequestBody`, `@ModelAttribute`, `@RequestParam`, `@PathVariable`을 상황에 맞게 선택하는 기준이 조금 더 명확해졌다.

JPA의 dirty checking을 직접 수정 기능에 적용해 보면서, 트랜잭션 안에서 Entity 상태를 변경하는 방식이 어떻게 UPDATE로 이어지는지 이해할 수 있었다.
