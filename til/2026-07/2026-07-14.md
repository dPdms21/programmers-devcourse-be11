## 오늘 배운 내용

오늘은 Spring Boot 게시판 실습에서 게시글 상세 화면에 댓글 기능을 붙이면서   
`Board`와 `Comment`의 JPA 연관관계, 댓글 목록 조회, 댓글 작성 흐름을 학습했다.

댓글은 특정 게시글에 속하므로 `Comment`에서 `Board`를 `@ManyToOne(fetch = FetchType.LAZY)`로 참조하고,   
게시글 상세에서 댓글 목록을 사용하기 위해 `Board`에는 `@OneToMany(mappedBy = "board")`로 댓글 목록을 추가했다.  
`mappedBy`는 실제 외래키의 주인이 `Comment.board` 쪽에 있다는 의미이며,   
`Board.comments`는 게시글에서 댓글 목록을 조회하기 위한 반대 방향 연관관계다.

연관관계 조회에서는 LAZY와 EAGER의 차이를 정리했다.   
댓글이 필요하다고 해서 EAGER로 바꾸면 모든 게시글 조회에서 댓글까지 항상 가져오게 되어 불필요한 조회가 생길 수 있다.   
따라서 기본은 LAZY로 두고, 게시글 상세처럼 댓글 목록이 꼭 필요한 조회에서만 fetch join으로 함께 가져오는 방식이 더 적절하다.

PBL에서는 Mission 08 Board API와 Mission 09 DTO Mapping Boundary를 진행했다.   
Mission 08에서는 게시글 CRUD API를 구현하며 HTTP 상태 코드, 요청 검증, `ResponseEntity` 응답 흐름을 정리했다.   
Mission 09에서는 Entity와 API 응답 DTO의 경계를 분리하고, 목록 조회와 상세 조회 목적에 맞게 DTO를 나누는 구조를 학습했다.

Repoary 프로젝트에서는 GitHub 저장소 목록 조회와 저장소 연결 기능을 구현하고, 배포 환경 설정을 보완했다.   
Repoary JWT는 Repoary API 인증에 사용하고, GitHub access token은 서버가 GitHub API를 호출할 때 사용하는 값이라는 점을 다시 정리했다.

## 실습 및 과제

> Spring Boot jpa-board 댓글 작성과 상세 댓글 조회 실습

게시글 상세 화면에 댓글 작성과 댓글 목록 조회 기능을 추가했다.

댓글을 작성할 때는 단순히 댓글 내용만 저장하는 것이 아니라,   
`boardId`로 게시글을 먼저 조회한 뒤 `Comment`에 `board`를 연결해서 저장해야 한다.   
그래야 `comment` 테이블의 `board_id`에 해당 게시글 id가 저장된다.

댓글 목록은 게시글 상세 응답에 포함되도록 `BoardWithCommentsResponseDto`와 `CommentResponseDto`로 분리했다.   
`BoardMapper`에서는 `Board`와 `Comment` Entity를 응답 DTO로 변환하도록 구성했다.

상세 조회에서는 댓글 목록 전체가 필요하므로 fetch join을 사용하고,   
목록 조회에서는 댓글 내용 전체가 필요하지 않으므로 DTO projection으로 필요한 필드와 댓글 수만 조회하는 흐름을 구분했다.

> Spring Boot jpa-board 댓글 수정과 삭제 추가 구현

선택 기능으로 댓글 수정과 삭제를 구현했다.

댓글 수정은 `PUT /api/boards/{boardId}/comments/{commentId}`,   
삭제는 `DELETE /api/boards/{boardId}/comments/{commentId}`로 처리했다.   
수정·삭제 시에는 `commentId`로 댓글을 조회한 뒤,   
해당 댓글이 요청한 `boardId` 게시글에 속하는지 확인하고 요청한 `userId`가 댓글 작성자와 같은지 검증했다.

화면에서 본인 댓글에만 수정·삭제 버튼을 보여주더라도 실제 권한 검증은 서버에서 해야 한다는 점을 확인했다.

프론트에서는 댓글 수정 방식을 `prompt()`가 아니라 댓글 본문을 `textarea`로 바꾼 뒤 저장·취소 버튼을 보여주는 방식으로 수정했다.   
댓글 작성, 조회, 수정, 삭제 후에는 `loadBoardDetail()`을 다시 호출해 상세 화면과 댓글 목록을 최신 상태로 갱신했다.

> PBL Mission 08 Board API 구현

Spring Boot 기반 게시글 CRUD API를 구현했다.

게시글 작성과 수정에서는 `title`, `content`가 `null`이거나 blank이면 400 Bad Request로 처리했다.   
`@RequestBody(required = false)`를 사용하면 request body 자체가 `null`로 들어올 수 있으므로,   
필드 검증 전에 `request == null`을 먼저 확인해야 한다.

응답은 `ResponseEntity`를 사용해 구성했다.   
`ResponseEntity.status(HttpStatus.CREATED).body(response)`는 201 Created 응답을,   
`ResponseEntity.ok(response)`는 200 OK 응답을, `ResponseEntity.noContent().build()`는 204 No Content 응답을 의미한다.   
삭제 성공은 응답 본문이 없어야 하므로 DTO를 반환하지 않고 204로 처리했다.

게시글 조회에서는 `findById(id)`가 없는 게시글에 대해 `null`을 반환할 수 있으므로,   
DTO 변환 전에 `post == null`을 먼저 확인하고 404 응답으로 처리했다.   
목록 조회에서는 `List<Post>`를 그대로 반환하지 않고 `List<PostResponse>`로 변환했다.

수정 기능에서는 `exists(id)`로 게시글 존재 여부를 먼저 확인한 뒤 `update()`를 호출했다.   
`update()` 내부에서는 기존 `createdAt`은 유지하고 `updatedAt`만 새로 갱신되는 흐름을 확인했다.

> PBL Mission 09 DTO Mapping Boundary 구현

Entity와 API 응답 DTO의 경계를 분리했다.

Entity는 내부 데이터 구조이고 API 응답은 외부에 공개되는 계약이므로, Entity를 그대로 반환하면 내부 필드가 노출될 수 있다.   
목록 조회와 상세 조회의 목적이 다르기 때문에 하나의 DTO로 처리하지 않고 `PostListResponse`와 `PostDetailResponse`를 따로 만들었다.

목록 응답에는 `id`, `title`, `authorName`, `createdAt`만 포함하고,   
상세 응답에는 `id`, `title`, `content`, `authorName`, `createdAt`만 포함하도록 구성했다.   
`authorEmail`, `internalNote` 같은 내부 필드는 응답에 포함하지 않았다.

`record`는 DTO처럼 값을 담는 클래스를 간결하게 만들 수 있는 문법이다.   
record는 getter가 `getId()` 형태가 아니라 `id()`, `title()`처럼 필드명과 같은 메서드 형태로 생성된다.   
`PostListResponse.from(Post post)`는 `Post` 하나를 DTO 하나로 변환하는 메서드이므로,   
`List<Post>` 전체를 한 번에 넣는 것이 아니라 반복문으로 하나씩 변환해야 한다.

> Repoary GitHub 저장소 조회와 연결 기능 구현

Repoary 2주차 GitHub 연동 기능의 남은 흐름을 구현했다.

백엔드에서는 GitHub OAuth 로그인 이후 받아온 GitHub access token을 사용자 정보에 저장하고,   
Repoary JWT로 인증된 사용자가 자신의 GitHub 저장소 목록을 조회할 수 있도록 구현했다.   
`GET /api/github/repositories`를 호출해 사용자의 GitHub 저장소 목록이 정상적으로 반환되는 것을 확인했다.

이후 사용자가 분석할 저장소를 선택해 연결할 수 있도록 `connected_repositories` 테이블을 만들고,   
저장소 연결 API와 연결된 저장소 목록 조회 API를 구현했다.   
이 테이블은 GitHub 전체 저장소를 저장하는 용도가 아니라, 사용자가 Repoary에서 분석 대상으로 선택한 저장소만 저장하는 용도다.

외부 GitHub API 응답 DTO와 내부 요청 DTO의 필드명 차이도 정리했다.   
GitHub 원본 응답은 `id`, `full_name`, `html_url`, `private`, `default_branch`처럼 snake_case를 사용하지만,   
Repoary 요청 DTO는 `githubRepositoryId`, `fullName`, `htmlUrl`, `privateRepository`,   
`defaultBranch`처럼 camelCase를 사용했다.   
특히 `privateRepository`에 값이 매핑되지 않으면 primitive boolean에 null을 넣으려는 오류가 발생할 수 있다.

이를 해결하기 위해 GitHub API 응답 DTO에서는 `@JsonAlias`를 사용하는 방향으로 정리했다.   
`@JsonProperty`는 직렬화와 역직렬화 모두에 영향을 줄 수 있지만,   
`@JsonAlias`는 외부에서 받은 snake_case 값을 Java 필드에 매핑할 때 사용할 수 있다.   
이를 통해 외부 API 응답 형식과 Repoary 내부 API 응답 형식을 분리했다.

> Repoary 배포 환경 설정 보완

Repoary 백엔드와 프론트엔드 배포 환경 설정을 보완했다.

Render 백엔드 배포에서는 포트 바인딩과 메모리 제한 문제를 확인했다.   
Render는 실행 시 `PORT` 환경변수를 제공하므로 Spring Boot가 이 값을 사용하도록 `server.port: ${PORT:8080}` 설정이 필요했다.   
로컬에서는 `PORT`가 없으므로 기본값인 8080을 사용하고, Render에서는 지정된 포트로 실행되도록 구성했다.

Render 배포 중 `Out of memory (used over 512Mi)` 오류도 확인했다.   
처음에는 포트가 열리지 않았다는 메시지 때문에 포트 문제처럼 보였지만, 실제 원인은 메모리 제한으로 애플리케이션이 포트를 열기 전에 종료된 것이었다.   
이를 해결하기 위해 Render 환경변수에 `JAVA_TOOL_OPTIONS`를 추가해 JVM heap 크기를 제한하고, 작은 메모리 환경에 맞는 GC 옵션을 설정했다.

프론트엔드에서는 배포 환경에서 백엔드 API 주소를 관리하는 방식을 정리했다.   
로컬 개발에서는 `VITE_API_BASE_URL=http://localhost:8080`을 사용하고,   
Vercel 배포 환경에서는 `VITE_API_BASE_URL`에 Render 백엔드 주소를 설정하는 방식으로 분리했다.   
Vite는 `VITE_`로 시작하는 환경변수만 프론트 코드에서 읽을 수 있고, Vercel 환경변수는 재배포해야 실제 빌드에 반영된다.

GitHub OAuth App도 로컬용과 배포용을 분리했다.   
GitHub OAuth App은 callback URL을 여러 개 등록할 수 없기 때문에,   
기존 앱은 로컬용으로 두고 배포용 앱을 새로 만들어 Vercel 프론트 URL과 Render 백엔드 callback URL을 연결했다.

브랜치 운영에서는 2주차 GitHub 연동 작업을 기능 브랜치에서 완료한 뒤 `develop`에 머지했다.   
개인 프로젝트에서는 기능 브랜치를 `develop`에 직접 머지하고, MVP가 안정화된 뒤 `develop`에서 `main`으로 큰 단위 PR을 만드는 방향으로 정리했다.

> LMS w2-05

Stack과 Queue의 기본 구조와 활용 기준을 정리하고, 관련 코딩테스트 문제를 풀이했다.

`Stack`은 가장 나중에 넣은 값을 먼저 꺼내는 LIFO 구조이고, `Queue`는 먼저 넣은 값을 먼저 꺼내는 FIFO 구조다.   
`Deque`는 양쪽 끝에서 삽입과 삭제가 가능하므로 Stack과 Queue처럼 모두 사용할 수 있다.

`올바른 괄호`는 Stack을 사용해 여는 괄호와 닫는 괄호의 짝이 맞는지 확인했다.   
닫는 괄호를 만났을 때 Stack이 비어 있으면 잘못된 문자열이고, 모든 문자를 처리한 뒤 Stack이 비어 있어야 올바른 괄호 문자열이다.

`기능개발`, `주식가격`, `프로세스`는 순서 유지, 대기열 처리, 우선순위 비교를 중심으로 풀이했다.   
문제마다 입력 순서를 유지해야 하는지, 가장 최근 값을 먼저 확인해야 하는지, 우선순위 비교가 필요한지를 먼저 판단해야 한다는 점을 확인했다.

## 헷갈렸던 점

`mappedBy`의 의미가 헷갈렸다.   
`mappedBy = "board"`는 실제 외래키의 주인이 `Comment.board` 쪽에 있다는 의미이며, `Board.comments`는 조회 편의를 위한 반대 방향 연관관계다.

댓글 목록이 필요하다고 해서 EAGER로 바꾸면 되는지도 헷갈렸다.   
EAGER는 모든 게시글 조회에서 댓글까지 함께 가져올 수 있으므로 불필요한 조회가 생길 수 있다.   
기본은 LAZY로 두고, 댓글 목록이 필요한 상세 조회에서만 fetch join을 사용하는 것이 더 적절하다.

fetch join, DTO projection, EntityGraph의 차이도 정리했다.   
fetch join은 Entity를 조회하면서 연관 Entity까지 함께 가져오는 방식이고,   
DTO projection은 Entity 전체가 아니라 화면에 필요한 필드만 DTO로 바로 조회하는 방식이다.   
EntityGraph는 Repository 메서드에 특정 연관관계를 함께 조회하라고 선언하는 방식이다.

PBL에서는 `@RequestBody(required = false)` 때문에 request 자체가 `null`로 들어올 수 있다는 점이 헷갈렸다.   
필드 검증 전에 request가 null인지 먼저 확인해야 한다.

`List.copyOf()`로 반환된 리스트를 정렬하려고 하면 수정할 수 없다는 점도 확인했다.   
정렬이 필요하면 `new ArrayList<>(...)`로 복사한 뒤 정렬해야 한다.

Repoary에서는 GitHub 원본 응답 DTO와 내부 요청 DTO의 필드명 차이가 헷갈렸다.   
외부 API는 snake_case를 사용하고 내부 API는 camelCase를 사용하므로, 변환 책임을 명확히 두어야 한다.

Render 배포에서는 포트 문제처럼 보였던 오류가 실제로는 메모리 부족 때문에 발생할 수 있다는 점이 헷갈렸다.   
배포 환경에서는 로컬과 달리 메모리, 포트, 환경변수 조건을 별도로 맞춰야 한다.

입력 순서를 유지해야 하는지, 가장 최근 값을 먼저 확인해야 하는지, 우선순위 비교가 필요한지를 먼저 판단해야 한다.

## 오늘 느낀 점

댓글 기능을 붙이면서 JPA 연관관계는 단순히 어노테이션을 붙이는 문제가 아니라, 외래키의 주인과 조회 방향을 정확히 이해해야 한다는 점을 느꼈다.

목록 화면과 상세 화면은 필요한 데이터가 다르므로 조회 방식도 달라져야 한다.   
목록에서는 DTO projection으로 필요한 값과 댓글 수만 가져오고, 상세에서는 댓글 목록까지 fetch join으로 가져오는 방식이 더 적절하다는 점을 이해했다.

PBL Mission 08과 09를 진행하면서 API 구현에서는 기능 동작뿐 아니라 상태 코드, 응답 본문 유무, Entity와 DTO의 경계가 중요하다는 점을 다시 확인했다.   
특히 내부 필드가 API 응답으로 노출되지 않도록 DTO를 분리하는 기준이 중요했다.

Repoary에서는 GitHub OAuth 이후 저장소 목록 조회와 저장소 연결까지 이어지면서 실제 서비스의 핵심 흐름이 조금 더 구체화되었다.   
GitHub access token과 Repoary JWT의 역할을 분리하고, 사용자가 선택한 저장소만 연결 테이블에 저장하는 구조가 서비스 목적에 맞다고 느꼈다.

배포 과정에서는 로컬에서 정상 실행되는 코드도 Render나 Vercel 같은 배포 환경에서는   
포트, 메모리, 환경변수, OAuth callback 설정 때문에 다르게 동작할 수 있다는 점을 확인했다.   
기능 구현만큼이나 배포 환경을 기준으로 설정을 검증하는 과정이 중요하다고 느꼈다.
