## 오늘 배운 내용

오늘은 팀 프로젝트에서 상품 도메인과 공통 예외 처리 구조를 구현하고, 프로젝트 공통 개발 환경을 구성했다.

상품 도메인에서는 `Product` 엔티티를 중심으로 DTO, Repository, Service, Controller의 역할을 분리했다.  
상품 목록·상세 조회, 등록, 수정, 삭제와 상품명 검색, 재고 수정 기능을 구현하고,   
각 계층이 데이터 조회와 비즈니스 처리, HTTP 요청·응답을 나누어 담당하도록 구성했다.

상품 등록·수정·재고 수정 요청 DTO에는 Bean Validation을 적용했다.  
요청값 검증에 실패하면 필드별 오류 메시지를 추출해 공통 오류 응답으로 반환하도록 구성하면서,   
서비스와 컨트롤러마다 검증 오류 형식을 별도로 작성하지 않아도 된다는 점을 확인했다.

공통 예외 처리는 `ErrorCode`, `BusinessException`, `ErrorResponse`, `GlobalExceptionHandler`로 분리했다.  
비즈니스 예외, Bean Validation 실패, 올바르지 않은 JSON 요청과 예상하지 못한 서버 오류를 전역에서 처리해 API 오류 응답 형식을 통일했다.

## 실습 및 과제

> Compose Bean 상품 CRUD 및 공통 예외 처리 구현

상품 목록 조회, 상세 조회, 등록, 수정, 삭제 API를 구현했다.

상품 목록 API에서는 상품명 일부를 쿼리 파라미터로 받아 검색할 수 있도록 구성하고,   
목록 응답은 `ProductListResponse` 안에 여러 `ProductResponse`를 포함하도록 설계했다.

상품 등록·수정 요청과 재고 수정 요청은 별도의 DTO로 분리했다.  
각 요청 DTO에 상품명, 가격, 재고 수량 등의 조건을 검증하는 어노테이션을 적용하고, Controller에서 `@Valid`로 검증을 실행했다.

존재하지 않는 상품을 조회하거나 수정·삭제하려는 경우에는 `ProductNotFoundException`을 발생시키고,   
공통 예외 처리에서 `PRODUCT_NOT_FOUND` 코드와 404 응답으로 변환하도록 구성했다.

상품 수정과 재고 수정 후에는 변경된 상품 정보를 `ProductResponse`로 반환했다.  
변경 감지 이후 갱신된 `updatedAt`을 응답에 바로 반영하기 위해 `flush()`를 호출한 뒤 응답 DTO를 생성했다.

> 상품 기능 테스트

상품 Service와 Controller 단위 테스트를 작성했다.

Service 테스트에서는 상품 목록·검색·상세 조회, 등록, 수정, 재고 수정, 삭제의 정상 동작과 상품이 존재하지 않는 경우의 예외를 검증했다.

Controller 테스트에서는 `@WebMvcTest`와 `MockMvc`를 사용해 API 상태 코드와 JSON 응답을 확인했다.  
상품 등록·수정 요청의 검증 실패와 상품 미존재 예외가 공통 오류 응답으로 반환되는지도 함께 확인했다.

> 프로젝트 공통 환경 구성

Spring Boot 프로젝트에 MySQL 연결 설정을 추가하고, `.env`와 환경변수를 통해 데이터베이스 접속 정보를 주입하도록 구성했다.

Swagger를 적용해 구현한 API 명세를 확인하고 직접 요청을 테스트할 수 있도록 기본 설정을 추가했다.

상품과 주문 등 각 도메인에서 공통으로 사용할 수 있도록 오류 응답 형식과 전역 예외 처리 구조를 정리했다.

기능 브랜치를 `develop`에 병합한 후에는 `application.yml`에 중복된 데이터베이스 설정과 하드코딩된 접속 정보가 남아 있는 것을 확인해 제거했다.  
패키지명과 클래스명에 작성된 `schedular`, `OrderDeliverySchedular` 오타도 각각 `scheduler`, `OrderDeliveryScheduler`로 수정했다.

## 헷갈렸던 점

상품 수정 후 응답의 `updatedAt`이 즉시 변경되지 않는 이유가 헷갈렸다.  
JPA의 변경 감지는 트랜잭션이 끝나거나 영속성 컨텍스트가 flush되는 시점에 SQL로 반영될 수 있다.   
따라서 응답 DTO를 생성하기 전에 `flush()`를 호출해 변경 내용을 DB에 반영하고, 갱신된 `updatedAt`을 응답에 포함하도록 처리했다.

기능 브랜치를 병합할 때 Git 충돌이 발생하지 않으면 코드도 정상적으로 통합된 것으로 생각하기 쉬웠다.  
하지만 충돌 여부는 Git이 변경 내용을 자동으로 합칠 수 있는지를 의미할 뿐이며,   
병합 후 설정 중복이나 환경변수 누락, 패키지명 오타와 같은 문제는 별도로 확인해야 했다.

또한 주문 도메인과 상품 도메인을 연결할 때 주문 당시 상품명과 가격을 별도로 저장해야 하는지,   
주문 이력이 있는 상품을 실제로 삭제해도 되는지, 주문 생성과 재고 차감을 하나의 트랜잭션으로 처리해야 하는지가 명확하지 않았다.

## 오늘 느낀 점

오늘은 상품 기능 구현뿐 아니라 팀 프로젝트에서 공통으로 사용할 환경과 예외 처리 구조를 함께 구성했다.

각 기능이 개별 브랜치에서 정상적으로 동작하더라도 `develop`에 병합한 이후에는 설정 파일과 공통 코드가 함께 동작하는지 다시 확인해야 했다.  
Git에서 충돌 없이 병합됐다는 사실이 애플리케이션 전체가 정상적으로 동작한다는 의미는 아니므로, 병합 후 컴파일과 실행, 설정 파일 검증이 필요하다고 느꼈다.

상품 CRUD는 독립적인 기능처럼 보였지만 주문 도메인과 연결하면 상품 삭제 정책, 주문 당시 가격 보존, 재고 동시성, 트랜잭션과 같은 추가 설계가 필요했다.

기능을 빠르게 구현하는 것도 중요하지만, 다른 도메인과 연결됐을 때 데이터가 어떻게 유지되고 실패 상황에서 일관성을 어떻게 보장할지도 함께 고려해야 한다고 느꼈다.
