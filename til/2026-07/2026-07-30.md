## 오늘 배운 내용

오늘은 JWT 생성·검증 구조에 로그인, Access Token과 Refresh Token 발급, 토큰 재발급, 로그아웃과 권한별 접근 제어를 연결했다.

JWT 로그인에서는 `AuthenticationManager.authenticate()`가 아이디와 비밀번호 검증의 진입점이 된다.  
내부적으로 `UserDetailService`를 통해 사용자를 조회하고 `PasswordEncoder`로 비밀번호를 비교한 뒤, 인증에 성공하면 `Authentication`을 반환한다.   
Form Login에서는 필터가 이 과정을 처리했지만,   
JWT 방식에서는 Form Login을 비활성화했으므로 `UserService`에서 `AuthenticationManager`를 직접 호출한다.

Access Token은 실제 API 요청의 `Authorization: Bearer <token>` 헤더에 담아 사용자를 인증하는 데 사용한다.  
Refresh Token은 Access Token이 만료됐을 때 새로운 토큰을 발급받는 데 사용하며, JavaScript에서 직접 접근하기 어렵도록 `HttpOnly` 쿠키에 저장했다.

로그인 성공 후 Access Token은 응답 본문으로 전달하고 Refresh Token은 쿠키에 저장했다.  
응답 DTO의 Refresh Token 값을 `null`로 변경해 쿠키에 저장한 토큰이 JSON 응답에도 다시 노출되지 않도록 처리했다.

Access Token이 만료되면 쿠키의 Refresh Token을 검증하고, Claim에서 사용자 정보를 복원해 새로운 Access Token과 Refresh Token을 발급한다.   
새 Refresh Token은 다시 쿠키에 저장해 기존 값을 교체하며, Refresh Token이 없거나 만료·변조된 경우에는 `401 Unauthorized`를 반환한다.

인증된 사용자 정보는 `TokenAuthenticationFilter`가 Access Token을 검증한 뒤 `Authentication`으로 만들어 `SecurityContext`에 저장한다.  
Controller에서는 `@AuthenticationPrincipal`을 통해   
`Authentication.principal`에 저장된 `CustomUserDetails`를 전달받으므로 JWT를 다시 직접 파싱할 필요가 없다.

메서드별 권한 검사를 위해 `@EnableMethodSecurity`와 `@PreAuthorize`를 적용했다.  
`ROLE_ADMIN`이 `ROLE_USER`를 포함하는 권한 계층을 설정해 관리자는 일반 사용자 API와 관리자 API에 모두 접근할 수 있고,   
일반 사용자는 관리자 API에 접근할 수 없도록 구성했다.

인증 정보가 없거나 토큰이 만료·변조된 경우에는 `401 Unauthorized`, 인증은 되었지만 필요한 권한이 없는 경우에는 `403 Forbidden`이 발생한다.   
`AuthenticationEntryPoint`는 인증 실패를 처리하고 `AccessDeniedHandler`는 권한 부족을 처리한다.

---

Repoary에서는 사용자가 선택한 날짜를 기준으로 GitHub 커밋과 각 커밋의 변경 파일을 조회하고, 저장소별 규칙을 적용해 분석 결과를 만드는 기능을 구현했다.

분석 날짜는 한국 시간 오전 6시부터 다음 날 오전 6시 전까지로 정했다.   
이는 자동 분석을 실행하는 스케줄러 시간이 아니라, 사용자가 지정한 날짜의 커밋을 어느 범위까지 조회할지 결정하는 기준이다.

커밋 메시지에는 커밋 규칙을 적용해 `commitType`과 `scope`를 분류하고,   
변경 파일에는 `practice/**`, `til/**`과 같은 경로 규칙을 적용해 카테고리를 판별했다.   
여러 경로 규칙이 일치하면 더 구체적인 경로를 우선하고, 구체성이 같으면 우선순위 값이 낮은 규칙을 선택하도록 했다.

TIL 생성에 필요한 실제 변경 파일명은 저장하되   
Gradle Wrapper, Git 설정 파일, lock 파일과 빌드 산출물처럼 학습 내용을 설명하는 데 도움이 적은 파일은 제외했다.   
이미 작성된 TIL을 다시 새로운 TIL의 근거로 사용하지 않도록 `docs(til)` 커밋도 분석 결과에서 제외했다.

분석 작업은 `PENDING → RUNNING → COMPLETED` 순서로 상태가 변경되고, 오류가 발생하면 `FAILED`로 기록된다.   
같은 저장소와 날짜를 다시 분석해도 새로운 작업을 생성해 재분석 이력을 남기며, 커밋이 없는 날짜는 빈 결과를 가진 정상 완료 작업으로 처리했다.

## 실습 및 과제

> JWT 로그인과 토큰 관리 실습

`UserService`에서 `AuthenticationManager`를 호출해 로그인 요청의 아이디와 비밀번호를 검증하고,   
인증 성공 후 Access Token과 Refresh Token을 발급했다.

`TokenService`에서는 같은 토큰 생성 기능에 서로 다른 유효 시간을 전달해 두 토큰을 생성하고,   
`TokenPair`로 묶어 반환했다. Access Token은 응답으로 전달하고 Refresh Token은 `CookieUtil`을 통해 `HttpOnly` 쿠키에 저장했다.

재발급 API에서는 쿠키의 Refresh Token을 찾아 유효성을 검증하고 새로운 Access Token과 Refresh Token을 발급했다.   
로그아웃 시에는 Refresh Token 쿠키를 만료시키고, 화면의 JavaScript에서 보관 중인 Access Token을 삭제하도록 처리했다.

사용자·관리자 API에는 `@PreAuthorize`를 적용하고 권한 계층을 설정했다.   
API 요청의 인증 실패와 권한 부족을 각각 `401`, `403`으로 처리하고, 일반 화면 요청은 접근 거부 화면으로 이동하도록 구분했다.

> JWT 인증과 인가 과제

로그인 성공 후 Access Token을 브라우저의 `localStorage`에 저장하고 Refresh Token은 `HttpOnly` 쿠키에 저장하도록 구현했다.

이후 API 요청에서는 Access Token을 `Authorization` 헤더에 담아 전달하고,   
`TokenAuthenticationFilter`가 토큰 검증과 사용자 조회를 수행한 뒤 인증 객체를 `SecurityContext`에 등록하도록 구성했다.

Access Token 만료 시 Refresh Token으로 두 토큰을 재발급하고, 로그아웃 시 Refresh Token 쿠키와 브라우저의 Access Token을 제거하도록 구현했다.

화면 이동 시 `localStorage`의 Access Token이 `Authorization` 헤더에 자동으로 포함되지 않아 접근이 거부되는 문제를 확인했다.   
HTML 화면 경로는 공개하고, 화면에서 JavaScript로 호출하는 실제 데이터 API에 JWT 인증과 역할 검사를 적용하도록 경로를 구분했다.

`curl -c cookie.txt`로 응답 쿠키를 파일에 저장하고 `curl -b cookie.txt`로 다음 요청에 전달해 재발급 흐름을 테스트했다.   
`cookie.txt`, `.env`와 JWT Secret 원문은 저장소에 포함하지 않고 로컬 파일과 환경변수로 관리해야 한다.

> Repoary GitHub 커밋 분석

GitHub API를 통해 날짜 범위에 포함되는 커밋의 SHA, 메시지, 링크와 시간을 조회하고,   
각 SHA로 변경 파일의 경로와 `added`, `modified`, `removed`, `renamed` 상태를 추가 조회했다.   
파일 이름이 변경된 경우에는 이전 경로도 확인할 수 있도록 처리했다.

조회한 커밋 메시지와 파일 경로에는 저장소별 커밋 규칙과 분류 규칙을 적용했다.   
이후 TIL 작성에 의미 있는 커밋과 파일만 남겨 축약 결과를 만들고, `analysis_jobs`의 JSONB 컬럼에 저장했다.

분석 실행 API에서는 커밋 조회, 변경 파일 분석, 규칙 적용, 핵심 파일 필터링과 결과 저장을 한 번에 처리했다.   
작업 ID로 상태와 결과를 조회하는 API와 저장소별 분석 이력을 최신순으로 조회하는 API도 구현했다.   
날짜를 지정하면 해당 날짜의 재분석 이력만 조회하고, 날짜가 없으면 전체 이력을 반환하도록 구성했다.

Swagger를 통해 커밋이 있는 날짜와 없는 날짜의 분석 실행, 완료 결과 조회와 재분석 이력 조회를 확인했다.

## 헷갈렸던 점

Form Login과 JWT 로그인에서 `AuthenticationManager`가 사용되는 방식이 달랐다.  
Form Login에서는 필터가 인증 관리자를 내부적으로 호출하지만, JWT 방식에서는 로그인 API를 구현한 `UserService`가 직접 호출해야 했다.

Access Token과 Refresh Token을 모두 JWT로 생성하므로 역할이 비슷하게 느껴졌지만,   
Access Token은 API 인증에 사용하고 Refresh Token은 Access Token 재발급에만 사용한다는 차이가 있다.

브라우저가 일반 링크로 화면을 이동할 때는 `localStorage`의 Access Token을 자동으로 헤더에 넣지 않는다.  
따라서 HTML 화면을 공개하는 것과 실제 사용자 정보나 관리자 기능을 제공하는 API를 공개하는 것은 다르며,   
보호가 필요한 데이터 API에 인증과 인가를 적용해야 한다.

로그아웃 시 쿠키와 브라우저의 토큰을 삭제하면 모든 토큰이 즉시 무효화된다고 생각하기 쉽지만, 이미 발급된 Access Token은 만료 시점까지 유효할 수 있다.   
즉시 무효화하려면 블랙리스트나 별도의 토큰 저장소가 필요하다.

인증 실패와 인가 실패도 구분해야 했다.  
사용자를 확인할 수 없는 경우에는 `401 Unauthorized`, 로그인 사용자의 권한이 부족한 경우에는 `403 Forbidden`을 반환한다.

---

분석 결과를 JSONB로 저장하는 과정에서는 Spring Boot 4가 사용하는 Jackson 3와 Hibernate 내부의 Jackson 2 타입이 충돌했다.   
엔티티 필드를 Jackson 3의 `JsonNode`로 선언했을 때 Hibernate가 다른 버전의 `JsonNode`로 역직렬화를 시도해 오류가 발생했다.

엔티티에는 JSON 문자열을 저장하고, API 응답을 만들 때 Jackson 3의 `JsonMapper`로 `JsonNode`로 변환하는 방식으로 수정했다.   
또한 완료 상태 저장 중 발생한 예외를 다시 `fail()`로 처리하면서 최초 예외가 덮이지 않도록 현재 상태를 확인한 뒤 실패 처리하도록 변경했다.

## 오늘 느낀 점

JWT 인증은 토큰을 생성하는 기능 하나가 아니라 로그인, 두 토큰의 발급과 보관, 요청별 인증 복원, 재발급, 로그아웃과 권한 검사까지 이어지는 전체 흐름이었다.

각 기능을 한꺼번에 보면 코드가 많고 복잡하게 느껴졌지만,   
`UserService`는 로그인 인증, `TokenService`는 토큰 발급과 재발급, `CookieUtil`은 Refresh Token 쿠키 관리,   
`TokenAuthenticationFilter`는 요청 인증 복원, `SecurityConfig`는 공개 경로와 권한 처리를 담당하는 것으로 구분하니 구조를 이해하기 쉬웠다.

화면 경로와 API 경로를 구분하면서 인증 방식은 토큰 생성 코드만으로 결정되는 것이 아니라,   
클라이언트가 토큰을 어디에 저장하고 어떤 요청에 전달하는지까지 함께 설계해야 한다는 점을 확인했다.

---

Repoary 분석 기능은 GitHub API에서 데이터를 가져오는 것만으로 끝나지 않고,   
날짜 기준 설정, 규칙 우선순위, 불필요한 파일 제외와 분석 상태 관리까지 함께 결정해야 했다.

특히 TIL 초안을 만들기 위해 어떤 데이터를 저장해야 하는지 구분하는 과정이 중요했다.   
변경 파일을 모두 저장하기보다 커밋 메시지와 핵심 파일처럼 실제 학습 내용을 설명할 수 있는 정보만 남겨야 이후 생성 결과도 불필요하게 길어지지 않는다.
