## 오늘 배운 내용

오늘은 웹 서버와 WAS의 역할 차이, HTTP 요청과 응답의 특징, 쿠키와 세션을 이용해 사용자 상태를 유지하는 방법을 학습했다.

Tomcat은 Servlet을 실행할 수 있는 WAS이며,   
Spring Boot에는 내장 Tomcat이 포함되어 있어 `main()`을 실행하는 것만으로 서버를 시작할 수 있다.

`@SpringBootApplication`은 설정 등록, 컴포넌트 스캔, 자동 구성을 함께 수행한다.  
`SpringApplication.run()`은 Spring 컨테이너를 생성하고 내장 Tomcat을 실행한다.

HTTP는 이전 요청의 상태를 기억하지 않는 무상태 프로토콜이다.  
따라서 로그인 상태나 사용자 설정을 유지하려면 쿠키나 세션 같은 별도의 상태 관리 수단이 필요하다.

쿠키는 브라우저에 이름과 값 형태로 저장되고, 조건에 맞는 요청을 보낼 때 서버로 자동 전송된다.  
세션의 실제 데이터는 서버에 저장되며, 브라우저에는 해당 세션을 식별하기 위한 세션 ID가 쿠키로 저장된다.

과제에서는 세션에 로그인 상태를 저장하고, 테마와 마지막 방문 시각처럼 로그아웃 이후에도 유지할 설정은 쿠키에 저장했다.

PBL에서는 할인 계산 로직을 `DiscountPolicy` 인터페이스로 추상화하고, 정액 할인과 정률 할인 정책을 교체할 수 있도록 구현했다.

## 실습 및 과제

> HTTP와 Spring Boot 실행 구조

웹 서버는 정적 파일 제공을 중심으로 처리하고, WAS는 Servlet 실행과 동적 요청 처리를 담당한다.

Spring Boot에서는 `@SpringBootApplication`이 선언된 시작 클래스를 기준으로 하위 패키지를 탐색한다.  
따라서 `@Controller`와 같은 컴포넌트가 시작 클래스의 하위 패키지에 있어야 기본 컴포넌트 스캔 대상에 포함된다.

HTTP 메서드 중 GET, PUT, DELETE는 일반적으로 동일한 요청을 반복해도 최종 서버 상태가 같아 멱등성을 가진다.  
반면 POST는 요청할 때마다 새로운 데이터가 생성될 수 있어 일반적으로 멱등하지 않다.

> 쿠키 조회와 삭제

쿠키는 `request.getCookies()`로 배열을 가져와 직접 순회하거나, `@CookieValue`를 이용해 특정 쿠키 값을 바로 주입받을 수 있다.

직접 쿠키 배열을 조회할 때는 쿠키가 없으면 `null`이 반환될 수 있으므로 먼저 확인해야 한다.  
`@CookieValue`를 사용할 때 쿠키가 없을 가능성이 있다면 `required = false`를 설정해야 한다.

쿠키를 삭제할 때는 같은 이름의 쿠키를 다시 만들고 `Max-Age`를 `0`으로 설정해 응답에 추가해야 한다.

이때 생성할 때 지정한 `Path`와 삭제할 때 지정한 `Path`가 같아야 브라우저가 같은 쿠키로 인식해 삭제할 수 있다.

> 세션과 화면 데이터 전달

세션에는 `setAttribute()`로 값을 저장하고 `getAttribute()`로 조회한다.

로그아웃 시 `session.invalidate()`를 호출하면 현재 세션과 세션에 저장된 데이터가 제거된다.  
다만 브라우저에 별도로 저장된 사용자 설정 쿠키까지 삭제되는 것은 아니다.

`@Controller`에서 반환한 문자열은 Thymeleaf 템플릿 이름으로 사용된다.  
`Model`에 `addAttribute()`로 저장한 값은 HTML에서 `${username}`, `${theme}`, `${lastVisit}`처럼 출력할 수 있다.

> 세션과 쿠키 과제

로그인 시 `session.setAttribute()`를 이용해 사용자 이름을 세션에 저장했다.

대시보드에 접근할 때 세션에서 사용자 이름을 조회하고, 로그인 정보가 없으면 `redirect:/login`으로 이동시켜 비로그인 사용자의 접근을 막았다.

로그아웃할 때는 `session.invalidate()`로 서버의 로그인 세션을 제거했다.

테마와 마지막 방문 시각은 로그아웃 후에도 유지될 수 있도록 쿠키에 저장했다.  
쿠키의 `maxAge`는 초 단위이며, `30 * 24 * 60 * 60`은 30일을 의미한다.

마지막 방문 시각은 `System.currentTimeMillis()`로 밀리초 값을 저장했다.  
쿠키에서 읽은 값은 `Long.parseLong()`으로 변환하고,  
`Instant.ofEpochMilli()`와 `ZoneId.systemDefault()`를 이용해 현재 시간대의 날짜와 시간으로 변환했다.

화면에서는 `th:if`로 값의 존재 여부에 따라 출력 내용을 나누고, `th:classappend`로 쿠키에서 읽은 테마를 `<body>`의 클래스에 추가했다.

> PBL Mission 05

할인 계산 로직을 정책별로 분리하고 `DiscountPolicy` 인터페이스를 통해 정액 할인과 정률 할인을 교체할 수 있도록 구현했다.

`FixedAmountDiscountPolicy`는 생성자로 받은 할인 금액을 필드에 저장하고, 음수 값이 전달되면 `IllegalArgumentException`을 발생시켰다.

정액 할인액이 원금액보다 큰 경우에는 다음과 같이 원금액까지만 할인되도록 처리했다.

```java
Math.min(originalAmount, discountAmount)
```

`RateDiscountPolicy`는 할인율이 0보다 작거나 100보다 크면 예외를 발생시켰다.

할인 금액을 계산할 때 큰 금액의 중간 곱셈이 `int` 범위를 넘지 않도록 먼저 `long`으로 변환했다.

```java
(int) ((long) originalAmount * ratePercent / 100)
```

정수 나눗셈을 사용하므로 계산 결과의 소수점 이하는 버려진다.

`OrderCalculator`는 생성자로 `DiscountPolicy`를 전달받아 필드에 저장했다.  
구체적인 할인 정책이 아니라 인터페이스 타입에 의존하므로 정책 객체만 교체해 다른 할인 방식을 적용할 수 있었다.

할인 정책은 할인 금액만 계산하고, 최종 결제 금액은 `OrderCalculator`가 계산하도록 책임을 나눴다.

```java
Math.max(0, originalAmount - discount)
```

정책 객체가 잘못된 할인 금액을 반환하더라도 최종 결제 금액이 음수가 되지 않도록 처리했다.

공개 테스트 1개와 hidden review 4개를 모두 통과해 정액 할인, 정률 할인, 입력 검증, 큰 금액 계산과 정책 교체가 정상적으로 동작함을 확인했다.

## 헷갈렸던 점

세션 데이터는 서버에 저장되지만, 브라우저가 자신의 세션을 식별하려면 세션 ID를 저장해야 한다.  
일반적으로 이 세션 ID가 쿠키에 저장되므로 세션은 쿠키를 이용해 동작할 수 있다.

Session Storage와 서버의 `HttpSession`도 이름은 비슷하지만 서로 다른 기능이다.  
Session Storage는 브라우저 안에 데이터를 저장하며 서버로 자동 전송되지 않는다.

`@RequestParam`은 요청 파라미터를 받을 여러 타입에 사용할 수 있다.

반면 `HttpSession`, `HttpServletResponse`, `Model`은 Spring MVC가 전달하는 객체이므로 `@RequestParam`을 붙이지 않는다.

`session.invalidate()`는 서버의 세션을 제거하지만 브라우저의 일반 쿠키까지 삭제하지 않는다.  
쿠키를 삭제하려면 같은 이름과 경로를 가진 쿠키에 `setMaxAge(0)`을 적용해야 한다.

PBL에서는 `discount()`가 최종 결제 금액이 아니라 실제 할인 금액을 반환해야 한다는 점을 구분해야 했다.

또한 생성자로 전달받은 할인 금액이나 할인 정책을 다른 메서드에서도 사용하려면 매개변수로만 두는 것이 아니라 필드에 저장해야 한다.

정률 할인 계산에서는 결과를 `long`으로 받는 것만으로는 중간 곱셈의 overflow를 막을 수 없다.  
곱셈이 실행되기 전에 피연산자 하나를 먼저 `long`으로 변환해야 한다.

## 오늘 느낀 점

HTTP가 상태를 기억하지 않는다는 특징을 이해하니 쿠키와 세션이 필요한 이유와 각각 어떤 데이터를 저장해야 하는지가 더 명확해졌다.

로그인 정보는 서버가 관리하는 세션에 두고, 테마처럼 장기간 유지할 사용자 설정은 쿠키에 저장하는 방식으로 역할을 구분할 수 있었다.

Spring MVC가 요청 파라미터, 세션, 응답 객체, 화면 데이터를 각각 어떤 방식으로 컨트롤러에 전달하는지 실습을 통해 연결해 볼 수 있었다.

PBL에서는 인터페이스를 이용해 할인 정책을 분리하면서 전략 패턴이 단순히 클래스를 나누는 것이 아니라,   
변경되는 정책과 최종 계산 책임을 구분하는 구조라는 점을 확인했다.
