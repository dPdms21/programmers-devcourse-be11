## 오늘 배운 내용

오늘은 Docker Compose를 이용해 기존 MSA 서비스를 여러 컨테이너로 구성하고 한 번에 실행·관리하는 방법을 학습했다.

기존에는 서비스마다 `docker build`, `docker run`을 직접 실행하고 `host.docker.internal`로 호스트를 경유했지만,   
Compose에서는 data · service · front 구성을 나누고 동일한 `msa-network`에 연결했다.   
같은 네트워크에 있는 컨테이너는 Docker DNS를 통해   
`mysql`, `config-service`, `auth-service`와 같은 서비스 이름으로 직접 통신할 수 있다는 점을 이해했다.

Compose 파일을 작성하면서 YAML의 리스트와 맵 구조, 호스트 포트와 컨테이너 포트의 차이,   
`external: true`, bind mount와 named volume, Healthcheck와 `depends_on`의 역할을 정리했다.

또한 `start.sh`, `stop.sh`를 통해 여러 Compose 명령을 순서대로 실행하는 방법을 학습하고,   
기존 Spring 설정도 환경변수를 이용하도록 변경해 로컬 실행과 Compose 실행에서 동일한 설정을 재사용할 수 있도록 구성했다.

Gudit은 3차 프로젝트 평가 결과와 피드백을 확인하고 기존 회고 내용을 정리했다.

Repoary에서는 먼저 실제 GitHub 커밋 사례를 기준으로 누락 점검의 학습 날짜 판정 기준을 다시 검토했다.

기존의 커밋 메시지 날짜 우선 처리와 오전 6시 이전 커밋을 전날 학습으로 보는 기준은 유지하되,   
`docs(readme):`처럼 학습과 직접 관련 없는 README 관리 커밋이 학습일로 오탐되는 문제를 확인했다.   
이에 기존 `docs(til):`과 함께 `docs(readme):`도 학습일 판정에서 제외하도록 개선했다.

이후 누락 점검 화면에는 `전체 / 완료 / 확인 필요` 요약과 `누락만 보기` 필터를 추가했다.   
기존 조회 결과를 프론트엔드에서 필터링해 추가 API 호출 없이 필요한 기록만 확인할 수 있도록 했다.

## 실습 및 과제

> Docker Compose 구성 및 서비스 연동

MSA 실행 환경을 data · service · front 세 Compose 파일로 분리했다.

* `docker-compose.data.yml`: MySQL과 공용 `msa-network`
* `docker-compose.service.yml`: Config·Auth·Board·Edge Service
* `docker-compose.front.yml`: Web Service

data Compose가 `msa-network`를 생성하고 나머지 Compose에서는 `external: true`로 기존 네트워크를 참조하도록 구성했다.

같은 Docker 네트워크에서는 호스트 포트를 거치지 않고 서비스 이름과 컨테이너 포트를 사용한다.   
PC에서 MySQL에 접근할 때는 `3307`을 사용하지만 Auth·Board 컨테이너에서는 `mysql:3306`으로 접근한다.

Config · Auth · Board · Edge 간 호출도   
`config-service:8888`, `auth-service:8082`, `board-service:8081`과 같이 서비스 이름을 사용하도록 구성했다.

볼륨에서는 초기 SQL을 전달하는 bind mount와 MySQL 데이터·Board 업로드 파일을 유지하는 named volume의 차이를 확인했다.   
일반적인 `down`에서는 named volume이 유지되지만 `down -v`를 사용하면 Compose가 관리하는 볼륨까지 삭제된다는 점을 정리했다.

MySQL은 실제 `SELECT 1` 쿼리로 Healthcheck를 수행하고, Config Service는 `/dev/tcp`를 이용해 8888 포트를 확인하도록 구성했다.   
`depends_on`과 `condition: service_healthy`를 사용해 의존 서비스의 Healthcheck 통과 후 다음 서비스를 시작하도록 했다.

다만 `docker compose up -d` 명령의 성공이 모든 애플리케이션의 준비 완료를 의미하는 것은 아니라는 점도 확인했다.

> Docker Compose 실행 자동화 및 설정 변경

`start.sh`에서 data → service → front 순서로 Compose 환경을 실행하고, `stop.sh`에서는 front → service → data 순서로 종료하도록 구성했다.

`set -e`를 사용해 앞 단계 명령 실패 시 이후 실행을 중단하고,   
`cd "$(dirname "$0")"`를 이용해 실행 위치와 관계없이 스크립트 파일이 있는 디렉터리를 기준으로 Compose 파일을 찾도록 했다.

`./stop.sh`는 볼륨을 유지하고, `./stop.sh -v`는 `$1`을 확인해 관리 볼륨까지 삭제하도록 분기했다.

Board와 Edge의 Spring 설정도 환경변수를 사용하도록 변경했다.   
로컬에서는 기존 `localhost` 기본값을 사용하고 Compose에서는   
`CONFIG_SERVICE_URL`, `AUTH_SERVICE_URL`, `BOARD_SERVICE_URL`에 내부 서비스 주소를 주입하도록 구성했다.

Nginx는 실제 실행하지 않고 향후 구조만 학습했다.   
앞단에 Nginx를 두면 외부 진입점을 80/443으로 통일하고 Web과 Edge로 요청을 전달할 수 있으며,   
HTTPS 종료와 로드 밸런싱으로 확장할 수 있다는 점을 정리했다.

> Repoary 누락 점검 학습 날짜 판정 기준 개선

실제 GitHub 기록을 기준으로 누락 점검의 학습 날짜 판정 기준을 검토했다.

기존에는 커밋 메시지에 명시된 학습 날짜를 우선하고, 날짜가 없는 커밋은 KST 기준 오전 6시 이전이면 전날 학습으로 처리하고 있었다.

이 과정에서 `docs(readme): 프로젝트 목록 추가`와 같은 README 관리 커밋이 실제 학습과 무관하지만 학습일로 포함되는 사례를 확인했다.

기존 `docs(til):` 제외 기준에 `docs(readme):`를 추가해 두 커밋 유형은 학습 날짜 생성 대상에서 제외하도록 변경했다.

반면 `docs(assignments)`, `docs(lectures)`, `docs(practice)`와 `refactor`, `style`, `chore` 등   
실제 학습 과정에서 발생할 수 있는 커밋은 학습일로 유지했다.

05:59는 전날, 06:00은 당일로 처리되는 날짜 경계와 같은 날짜에 실제 `study` 커밋이 존재하는 경우 학습일이 유지되는지도 테스트로 검증했다.

> Repoary 누락 점검 요약 및 필터 UX 개선

누락 점검 화면에 `전체 / 완료 / 확인 필요` 건수를 표시해 월별 기록 상태를 한눈에 볼 수 있도록 개선했다.

`전체 보기`와 `누락만 보기` 필터를 추가하고, 누락만 보기에서 대상이 없을 경우 `확인 필요한 기록이 없습니다.`라는 빈 상태를 표시하도록 했다.

필터는 이미 조회한 `result.items`를 프론트엔드에서 처리하므로 별도의 서버 요청을 추가하지 않았다.

월 변경이나 `다시 점검`, TIL·README 보완 후 기존 재조회 흐름도 유지했다.   
완료와 누락이 섞인 달과 전체 완료된 달을 각각 확인하면서 요약 숫자, 필터 전환, 빈 상태, 기존 보완 액션이 정상 동작하는 것을 검증했다.

## 헷갈렸던 점

YAML에서 `-`가 어떤 경우에 붙는지 헷갈렸다.   
`-`는 단순히 `:`이 없는 곳에 사용하는 문법이 아니라 리스트를 표현하며,   
각 Compose 필드가 리스트와 맵 중 어떤 구조를 받는지는 Docker Compose 스펙에서 결정된다는 점을 이해했다.

`3307:3306`에서 서비스 간 통신에도 3307을 사용해야 하는지 헷갈렸다.   
3307은 호스트에서 컨테이너에 접근하기 위한 포트이고,   
같은 Docker 네트워크의 컨테이너끼리는 `mysql:3306`처럼 서비스 이름과 컨테이너 포트를 사용한다는 점을 정리했다.

`external: true`가 새로운 네트워크를 생성하는 설정인지 헷갈렸다.   
실제로는 다른 Compose에서 이미 생성한 네트워크를 참조하겠다는 의미이므로   
`msa-network`를 생성하는 data Compose를 먼저 실행해야 한다는 점을 확인했다.

컨테이너가 실행 중이면 서비스도 바로 사용할 수 있는지 확인했다.   
컨테이너 프로세스 실행과 애플리케이션 준비 완료는 다른 상태이며,   
Healthcheck를 통해 실제 요청을 받을 수 있는 상태인지 별도로 판단해야 한다는 점을 이해했다.

Repoary에서는 새벽 커밋의 날짜 보정 기준보다 학습과 무관한 커밋이 학습일로 포함되는 것이 실제 문제라는 점을 확인했다.   
기존 06:00 기준을 변경하기보다 오탐 원인이었던 `docs(readme):`를 제외하는 방향이 적절하다고 판단했다.

## 오늘 느낀 점

Docker Compose를 사용하면서 여러 컨테이너를 한 번에 실행하는 것보다   
네트워크, 볼륨, 의존성, Healthcheck까지 실행 환경 자체를 선언적으로 관리한다는 점이 중요하다고 느꼈다.

어제 `host.docker.internal`을 이용했던 구조에서   
오늘은 동일 네트워크의 서비스 이름으로 직접 통신하도록 변경하면서 Docker 네트워크의 역할을 더 명확하게 이해할 수 있었다.

Gudit 결과를 정리하면서는 좋은 평가 자체보다 어떤 부분이 실제 강점으로 평가됐는지,   
그리고 팀 전체의 결과와 내가 직접 수행한 경험을 구분해 기록하는 것이 중요하다고 느꼈다.

Repoary에서는 정해 둔 규칙을 복잡하게 확장하기보다 실제 GitHub 기록에서 발생한 오탐 사례를 기준으로 최소한의 판정 기준을 보완했다.   
프론트엔드에서도 새로운 API를 추가하지 않고 기존 데이터를 활용해 필요한 정보만 빠르게 확인할 수 있도록 개선한 점이 의미 있었다.
