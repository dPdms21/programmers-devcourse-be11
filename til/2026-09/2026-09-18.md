## 실습 및 과제

> Gudit README 업데이트

3차 프로젝트의 최종 구현 결과를 반영하도록 README를 업데이트했다.

기존 2차 프로젝트의 구현 내용과 3차에서 추가로 개선한 내용을 구분하고,   
프로젝트 소개·팀원별 역할·주요 기능·기술 스택을 현재 서비스 기준으로 정리했다.

핵심 구현에는 기존 Redis Lua 기반 재고 처리와 구매·결제 동시성 제어뿐 아니라,   
3차에서 추가한 Transactional Outbox·Redis Streams 기반 재고 복구와 결제 보상 재처리 구조를 반영했다.

또한 Kotlin 전환, GitHub Actions 기반 CI, n8n을 활용한 AI 코드 리뷰 · CI 실패 분석, AI CS 및 모니터링 기능을 추가해   
최종 프로젝트의 전체 범위가 드러나도록 했다.

테스트 결과도 최종 검증 수치에 맞춰 전체 테스트 283건과 동시성 테스트 42회를 구분해 작성했다.   
2차에서 측정한 성능 개선 결과를 Kotlin 전환 효과로 혼동하지 않도록 프로젝트별 측정 결과를 분리했다.

30분 부하 테스트의 iteration 미실행과 전체 장애 복구 E2E 검증 등 추가 확인이 필요한 부분도 별도로 정리했다.

이를 통해 README가 단순한 기능 목록이 아니라 프로젝트의 문제 정의, 구현 방식, 검증 결과와 향후 개선 방향까지 전달할 수 있도록 구성했다.

> Gudit 3차 팀 프로젝트 최종 발표

2차에서 발견한 문제와 3차에서 적용한 개선 방법을 중심으로 최종 발표를 진행했다.

2차에서는 Redis Lua 기반 재고 처리와 구매·결제 상태 관리 및 동시성 제어를 구현했지만,   
재고 복구나 결제 보상 자체가 실패했을 때 이를 재처리할 수 있는 구조가 부족했다.

3차에서는 Transactional Outbox와 Redis Streams를 적용해 복구 요청을 보존하고 재처리할 수 있도록 개선했다.
또한 기존 Java 코드를 Kotlin으로 전환하고, CI · AI 자동화 · AI CS와 모니터링 기능을 추가했다.

Kotlin 전환 과정에서는 기존 기능을 유지하며 도메인별로 점진적으로 전환한 방식과 Java·Kotlin 간 호환성 문제를 해결한 경험을 공유했다.

검증 결과로는 전체 테스트 283건과 동시성 테스트 42회 통과를 제시했다.   
Kotlin 환경의 30분 부하 테스트에서 예정된 iteration 중 46건이 실행되지 않은 결과도 함께 설명하고, 추가 원인 분석이 필요한 항목으로 구분했다.

제한된 발표 시간 안에서 팀원 각자가 구현한 모든 기능과 주요 개선 결과를 소개하며 발표를 마무리했다.

강사님으로부터 AI 자동화를 운영 · 유지보수에 적용한 부분이 실제 개발 환경과 유사하다는 긍정적인 피드백을 받았다.

다른 팀의 발표에서는 짧은 기간에도 각 팀이 다양한 개선을 진행한 점을 확인했다.   
특히 테스트 결과를 시각화하고 핵심 내용을 이해하기 쉽게 전달한 발표 방식을 참고했다.

> Gudit 3차 프로젝트 회고

프로젝트의 구현 과정과 결과를 돌아보며 잘한 점과 향후 개선 방향을 정리했다.

**잘한 점**

짧은 프로젝트 기간에도 팀원들이 별도로 시간을 할애해 2차에서 발견한 문제를 개선하고, Kotlin 전환과 AI 자동화 등 추가 기능까지 구현했다.

특히 2차에서 개선 방향으로 남겨두었던 재고 복구 및 결제 보상 실패 문제를 실제 구현으로 연결했다.   
정상적인 구매·결제 처리뿐 아니라 장애 발생 이후의 복구까지 고려하도록 구조를 확장했다는 점이 의미 있었다.

또한 기존 동작과 테스트를 유지하면서 담당 도메인별 Kotlin 전환을 진행하고, 병합 과정에서 발생한 호환성 문제를 해결해 통합을 마무리했다.

AI 코드 리뷰, CI 실패 분석, AI CS와 모니터링 기능까지 추가하면서 서비스 기능뿐 아니라 개발 및 운영·유지보수 과정도 개선할 수 있었다.

**추가 개선 방향**

개인적으로 담당한 AI CS는 구매 내역 기반 문의와 관리자 답변 초안 생성까지 구현했다.   
결제 문의 외의 도메인으로 확장하고, 관리자 검토 이후 실제 고객에게 답변을 전달하는 전체 처리 흐름도 추가로 구현하고 싶다.

장애 복구에서는 개별 발행 실패·재처리·멱등 처리 시나리오를 검증했으므로,   
향후 실제 비즈니스 요청부터 최종 DB·Redis 정합성 복구까지 전체 경로를 반복 검증하는 자동화 E2E 테스트를 보강할 계획이다.

반복 실패 이벤트의 DLQ 정책과 고부하 구간의 병목 분석도 추가로 검토할 과제로 정리했다.

회고와 Fact & Lesson을 작성하면서 팀 전체의 성과와 내가 직접 담당하고 해결한 문제를 구분했다.   
팀 전체의 Kotlin 전환과 통합 검증 결과를 개인 성과로 표현하지 않고,    
Purchase·Payment·Outbox·CS 전환 및 실제 테스트 호환성 문제 해결 경험을 개인 기여로 정리했다.

## 헷갈렸던 점

프로젝트 최종 성과를 정리하면서 2차에서 측정한 개선 결과와 3차 Kotlin 전환 결과를 함께 표현해도 되는지 확인했다.

두 프로젝트는 기능과 구조, 측정 기준이 다르므로 각각의 결과를 구분해야 한다.   
특히 2차의 성능 개선 수치를 Kotlin 전환으로 얻은 효과처럼 설명하지 않도록 주의했다.

또한 전체 프로젝트 성과와 개인 기여를 어떻게 구분해야 하는지도 고민했다.

전체 테스트와 전체 Kotlin 전환율은 팀의 성과로 기록하고,   
내가 담당한 도메인의 구현과 전환 과정에서 직접 발견하고 해결한 문제는 개인 경험으로 정리해야 한다는 점을 확인했다.

## 오늘 느낀 점

이번 3차 프로젝트는 기간이 짧았지만, 2차에서 발견한 문제를 개선하는 동시에 Kotlin 전환과 AI 자동화 등 새로운 기능도 구현하느라 바쁘게 진행됐다.   
별도로 시간을 할애해 각자 맡은 작업을 진행했고, 여러 기능을 통합해 프로젝트를 마무리할 수 있었다는 점이 만족스러웠다.

발표에서도 팀원 각자가 구현한 모든 기능을 소개했다.   
다만 발표 시간이 제한되어 있어 설명해야 할 내용이 많았고, 일부 구현 과정이나 기술적 특징은 조금 더 쉽고 자세하게 전달할 방법이 있었을 것 같다.   
앞으로는 전체 기능을 모두 보여주면서도 핵심 내용을 충분히 이해할 수 있도록 시각 자료와 시연, 시간 배분을 더 고민해 보고 싶다.

프로젝트 회고와 README를 작성하면서 2차에서 발견한 문제를 3차의 실제 개선으로 연결한 과정을 다시 확인할 수 있었다.   
구현한 기능을 나열하는 것보다 어떤 문제를 해결하기 위해 구조를 변경했고, 그 결과 무엇을 검증했는지 연결해 설명하는 것이 중요하다고 느꼈다.

개인적으로는 AI CS Workflow를 구매 내역 기반 문의와 관리자 답변 초안 생성까지 구현한 점이 의미 있었다.   
프로젝트 기간에는 관리자 검토 이후 실제 고객 응답까지 연결하지 못했지만 
종료 후에도 개발을 이어가며 실제 서비스에서 사용할 수 있는 CS 처리 흐름으로 발전시키고 싶다.
