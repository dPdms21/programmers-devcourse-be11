오늘은 AI CS의 내부 인증과 결제 조회 구조를 보완하고, 담당 도메인인 Outbox·Purchase·Payment·CS의 Java 코드를 Kotlin으로 전환했다.

특히 타입과 생성자 구조를 변경할 때 실제 데이터 계약과 객체의 생명주기를 기준으로 판단하고,   
트랜잭션 경계·상태 전이·이벤트 재처리·결제 보상 흐름이 달라지지 않도록 주의했다.

도메인별 Production·테스트 코드를 전환한 뒤 PR 4건을 `dev`에 병합하면서 다른 팀원의 Kotlin 코드와 발생한 호환성 문제를 해결했다.   
최종적으로 전체 테스트 290건 통과를 확인하며 개별 도메인뿐 아니라 통합 상태까지 검증했다.

## 실습 및 과제

> AI CS 내부 인증 및 결제 조회 구조 보완

내부 API 인증 경로와 JWT 검사 제외 경로의 판별 기준을 확인했다.   
Auth 병합 과정에서 JWT 필터의 내부 API 판정을 `requestURI`에서 `servletPath`로 변경해   
Context Path 환경에서도 동일한 경로 기준을 사용하도록 했으며, `InternalApiKeyFilter`를 Kotlin으로 전환하면서 해당 인증 계약을 유지했다.

`/api/internal/`로 시작하는 내부 API 경로에만 `X-INTERNAL-KEY` 인증을 적용하고,  
정상 Key는 JWT 없이 통과시키되 Key 누락·불일치·빈 헤더는 차단하도록 검증했다.   
`INTERNAL_API_KEY`가 비어 있거나 공백이면 애플리케이션 기동 단계에서 실패하도록 설정값 검증도 추가했다.

또한 CS Controller가 PaymentService를 호출하고 PaymentService가 다시 CS DTO를 반환하는 순환 의존성을 발견했다.

결제 조회 결과를 Payment 도메인의 `PaymentStatusResult`로 분리하고,   
CS Controller에서 `CsPaymentStatusResponse`로 변환하도록 변경해 도메인별 책임을 구분했다.

> Kotlin 전환 기준 수립

기존 비즈니스 로직을 유지하는 것을 우선으로 하고, 언어 전환과 별도의 기능 개선은 구분했다.

DTO는 Java record를 Kotlin `data class`로 전환하고, Lombok의 생성자·Getter는 Kotlin의 주 생성자와 프로퍼티로 대체했다.

반면 JPA Entity는 `data class`로 변경하지 않고 일반 클래스로 유지했다.   
Entity의 식별자와 Auditing 필드는 영속성 생명주기에 맞춰 nullable 여부와 초기화 시점을 검토하고,   
기존 LAZY 로딩 및 JPA 매핑 설정을 유지했다.

Java 호출부가 남아 있는 동안에는 `@JvmRecord`, `@JvmStatic`, `Optional` 등 기존 호출 계약에 필요한 요소를 유지했다.   
전체 Kotlin 전환이 끝나기 전에 무조건 Kotlin식 API로 변경하면 다른 도메인의 Java 코드가 컴파일되지 않을 수 있기 때문이다.

nullability 역시 Java의 boxed 타입과 실제 데이터 계약을 기준으로 결정했다.   
값이 없을 수 있는 필드는 nullable로 표현하되, 필수 의존성이나 특정 상태에서 반드시 존재해야 하는 값까지 nullable로 완화하지 않도록 주의했다.

> Outbox Kotlin 전환

Outbox의 Production 16개 파일과 관련 테스트 5개를 Kotlin으로 전환했다.

Java record DTO는 `data class`로 변경했지만 `OutboxEvent`는 JPA 생성자와 프록시 동작을 고려해 일반 클래스로 유지했다.   
식별자와 Auditing 필드는 저장 전후의 생명주기를 고려해 초기화 방식과 nullability를 검토했다.

기존 Purchase·Payment와 연결되는 API 계약을 유지하기 위해 Java boxed 타입의 null 허용 범위를 `Long?`로 반영하고,   
Java 호출부에 필요한 `@JvmStatic`도 유지했다.

또한 Kotlin 전환 과정에서 Java와 다른 타입 추론이 적용되는 부분을 확인했다.   
Micrometer Gauge 반환값을 `Double`로 명시하고, `Range.unbounded<String>()`과 같이 제네릭 타입을 지정해 컴파일 오류를 해결했다.

Redis Streams의 발행·소비·Pending 재처리·ACK 처리 순서도 기존과 동일하게 유지했다.   
특히 Outbox는 트랜잭션 및 여러 도메인과 연결되므로 코드 형태를 간결하게 만드는 것보다 이벤트 처리 계약을 유지하는 데 집중했다.

Production과 테스트 컴파일을 통과시키고 기존 테스트 검증 범위를 유지하는 것을 확인했다.

> Purchase Kotlin 전환

Purchase의 Production 14개 파일과 테스트 7개를 Kotlin으로 전환했다.

Lombok을 Kotlin 생성자와 프로퍼티로 대체하고, JPA Entity의 LAZY 로딩과 Auditing 설정을 유지했다.   
식별자와 시각 필드는 기존 Java 코드의 null 허용 계약을 기준으로 전환했다.

또한 다른 도메인의 Java 코드와 연결되는 부분은 `@JvmRecord`, `@JvmStatic`, `Optional`을 필요한 범위에서 유지했다.

구매 상태 전이, 트랜잭션 경계, 비관적 락, 구매 취소·Timeout 및 재고 보상 순서가 전환 과정에서 변경되지 않도록 확인했다.

특히 `InventoryMetrics`가 테스트의 Mock 누락을 이유로 `InventoryMetrics?`로 선언된 문제를 발견했다.

운영 환경에서 반드시 주입되는 의존성이므로 Production 타입을 non-null로 복원하고, 테스트에 누락된 Mock을 추가했다.   
테스트를 통과시키기 위해 실제 의존성 계약을 변경해서는 안 된다는 점을 확인했다.

테스트 전환 과정에서는 Repository 선언, AssertJ 오버로드 및 Mockito matcher의 Kotlin 타입 호환성도 조정했다.   
팀원의 User Kotlin 전환으로 사용할 수 없게 된 `User.builder()`는 현재 생성자 방식에 맞게 변경했다.

기존 Java Purchase 테스트 34건을 먼저 통과시킨 뒤 테스트를 Kotlin으로 전환하고,   
다시 34건과 전체 테스트를 실행해 기존 검증 범위가 유지되는 것을 확인했다.

> Payment Kotlin 전환

Payment의 Production 22개 파일과 테스트 6개를 Kotlin으로 전환했다.

Toss API의 승인·조회·취소 요청 및 응답 구조, Webhook 처리, JPA 매핑과 결제 상태 전이를 유지했다.   
특히 Toss 승인 이후 내부 DB 처리에 실패했을 때의 보상 흐름은 호출 순서와 트랜잭션 경계가 달라지지 않도록 확인했다.

nullability를 적용할 때는 결제 진행 단계에 따라 값이 존재하는 시점이 달라질 수 있다는 점을 고려했다.   
단순히 모든 필드를 non-null로 변경하거나 기본값을 넣는 대신 실제 상태를 기준으로 타입을 결정했다.

테스트를 Kotlin으로 전환할 때는 Mockito와 AssertJ의 Java API가 Kotlin에서 그대로 동작하지 않는 문제가 발생했다.

AssertJ의 `satisfies` 오버로드는 `Consumer<Throwable>` 타입을 명시해 해결하고,   
Mockito matcher가 런타임에 null을 반환하면서 Kotlin non-null 파라미터와 충돌하는 문제는   
테스트 전용 `anyNonNull`, `eqNonNull` 래퍼로 해결했다.

최초 Payment 테스트 69건 중 11건이 실패했지만, 테스트 코드의 Kotlin 호환성 문제를 수정한 뒤 69건 전체와 전체 테스트 통과를 확인했다.

이 과정에서 기존 Mockito 검증과 예외·호출 횟수 검증을 제거하지 않고 유지했다.

> CS 및 내부 인증 Filter Kotlin 전환

CS의 Production 8개 파일과 테스트 3개를 Kotlin으로 전환했다.

Java record DTO에는 `@JvmRecord`를 적용해 기존 Java 호출부와의 호환성을 유지하고,   
요청 DTO에는 `@field:NotBlank`, `@field:Size`를 적용해 Bean Validation 제약이 실제 필드에 적용되도록 했다.

기존 문의 처리 순서인 `사용자 소유 Purchase 조회 → Payment 조회 → n8n Workflow 호출`을 유지하고,   
Purchase 조회가 실패하면 이후 Payment 조회와 Workflow 호출이 실행되지 않도록 기존 검증을 보존했다.

내부 API의 URL·HTTP 메서드·응답 구조와 n8n의 JSON Body, 연결 3초·읽기 5초 타임아웃도 변경하지 않았다.

추가로 `InternalApiKeyFilter`와 테스트를 Kotlin으로 전환하면서 설정값을 `String?`로 표현하고 `isNullOrBlank()`로 검증했다.

Java와 Kotlin의 `protected` 접근 범위 차이로 테스트에서 메서드를 호출할 수 없어, 기존 테스트의 접근 계약을 확인하고 `public override`로 변경했다.

기존 CS 테스트 5건과 필터 테스트 7건을 Kotlin으로 전환하고 인증·조회·실패 처리 동작이 유지되는 것을 확인했다.

> Kotlin 전환 병합 및 통합 검증

Outbox → Purchase → Payment → CS 순서로 도메인별 PR 4건을 `dev`에 병합했다.

개별 브랜치에서는 테스트가 통과했지만,   
다른 팀원들이 전환한 User·Sale·Inventory 코드와 통합하면서 Java/Kotlin 호출 방식과 타입 계약 차이로 컴파일 오류가 발생했다.

예를 들어 Java의 `status()`나 `orderId()`와 같은 호출은 Kotlin 프로퍼티로 전환된 뒤 `status`, `orderId` 방식으로 수정해야 했다.

또한 `PaymentTransactionService`에서는 `String?`인 `paymentKey`를 `String`이 필요한 곳에 전달하면서 컴파일 오류가 발생했다.

결제 시작 전에는 null일 수 있지만 보상 Outbox를 생성하는 시점에는 반드시 존재해야 한다는 상태 불변식을 확인하고 `checkNotNull()`로 명시했다.   
`!!`로 강제하거나 빈 문자열로 대체하지 않고, 값이 필요한 이유를 코드에 반영했다.

Production 컴파일 오류를 해결한 뒤에도 테스트 코드의 `User.builder()` 호출로 테스트 컴파일이 중단돼   
현재 Kotlin User의 생성자에 맞게 수정했다.

이를 통해 `Production 컴파일 → 테스트 컴파일 → 도메인 테스트 → 전체 테스트` 순서로 검증해야 하며,   
개별 브랜치의 테스트 통과가 병합 후 동작까지 보장하지는 않는다는 점을 확인했다.

최종적으로 담당 도메인 전환 PR 4건을 `dev`에 병합하고 전체 테스트 290건 통과를 확인했다.

## 헷갈렸던 점

JPA Entity를 DTO처럼 `data class`로 전환해도 되는지 확인했다.

DTO는 값 전달을 목적으로 하므로 `data class`를 활용할 수 있지만, JPA Entity는 식별자·영속성 생명주기·프록시·연관관계를 고려해야 한다.   
따라서 문법의 간결함보다 객체의 역할과 JPA 동작을 기준으로 전환 방식을 결정해야 한다는 점을 확인했다.

Java의 boxed 타입과 `Optional`을 Kotlin nullable로 바로 대체해도 되는지도 고민했다.

Kotlin 내부에서는 nullable 타입이 자연스럽지만 Java 호출부가 남아 있다면 메서드 시그니처와 호출 방식이 달라질 수 있다.   
따라서 Kotlin 문법에 맞추는 것과 기존 Java 코드의 호출 계약을 유지하는 것을 구분해야 한다는 점을 정리했다.

Mockito와 AssertJ 테스트가 Java에서는 통과했지만 Kotlin에서 실패하는 이유도 확인했다.

Mockito matcher의 null 반환과 Kotlin non-null 파라미터가 충돌하거나,   
AssertJ의 Java 오버로드를 Kotlin이 명확하게 선택하지 못할 수 있었다.   
이 경우 Production의 타입 계약이나 테스트 검증을 완화하는 대신   
Java 라이브러리와 Kotlin 타입 시스템의 차이를 고려해 테스트 코드를 수정해야 한다는 점을 배웠다.

마지막으로 Kotlin 컴파일 오류가 발생했을 때 nullable 선언이나 `!!`로 해결해도 되는지 고민했다.

실제로 값이 없을 수 있는 경우와 반드시 존재해야 하는 경우를 구분해야 한다.   
필수 의존성은 non-null 계약을 유지하고, 특정 상태에서만 값이 보장된다면 그 상태 불변식을 명시하는 것이 중요하다는 점을 확인했다.

## 오늘 느낀 점

오늘은 Kotlin 전환에서 문법을 간결하게 바꾸는 것보다 기존 코드의 계약과 동작을 정확히 이해하는 것이 중요하다는 점을 느꼈다.   
타입과 생성자를 변경할 때도 단순히 컴파일을 통과시키는 것이 아니라 실제 객체의 역할과 상태를 기준으로 판단해야 했다.

또한 개별 도메인에서 테스트가 통과하더라도 팀원의 전환 코드와 병합하면서 새로운 호환성 문제가 발생했다.   
따라서 언어 전환의 완료 기준은 개별 파일의 변환이나 컴파일 성공이 아니라, 전체 코드와 테스트가 함께 정상 동작하는 상태여야 한다는 점을 확인했다.

코드 리뷰에서 발견한 기존 설계 문제는 Kotlin 전환 회귀와 구분해 후속 작업으로 분리했다.   
이번 작업의 목적과 변경 범위를 유지하면서도 발견한 문제의 원인과 검증 조건을 기록하는 것이 중요하다고 느꼈다.

## 추가 학습 예정

- Kotlin 전환 후 주요 도메인 회귀 테스트 및 Java 상호운용성 추가 검증
- Purchase 중복 구매 동시성 재현 및 해결 방안 검증
- Payment 예외 처리·Webhook 응답 계약 및 테스트 보완
- 팀 통합 환경에서 구매·결제·Outbox·CS 전체 흐름 검증
