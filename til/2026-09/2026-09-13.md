## 오늘 배운 내용

오늘은 Toss 결제 승인 이후 내부 처리와 보상 취소까지 실패한 경우에도 작업이 유실되지 않도록 결제 보상 재처리 구조를 구현했다.

보상 실패 시 `PAYMENT_COMPENSATION_REQUIRED` 이벤트를 Outbox에 별도 Transaction으로 저장하고,   
Redis Streams를 통해 Consumer가 다시 처리하도록 구성했다.

Consumer에서는 Toss 취소를 바로 다시 호출하지 않고 실제 결제 상태를 재조회해 `DONE`이면 취소를 재시도하고,   
`CANCELED`이면 외부 취소는 이미 완료된 것으로 판단해 내부 상태만 보정하도록 했다.

또한 Redis Streams의 Pending 재처리와 Toss의 `Idempotency-Key`, 외부 상태 재조회, 내부 상태 검증을 함께 사용해   
동일 이벤트가 다시 전달되더라도 중복 보상이 발생하지 않도록 했다.

## 실습 및 과제

> 결제 보상 실패 Outbox 처리

기존에는 Toss 결제 승인 이후 내부 `Payment`·`Purchase` 처리에 실패하면 즉시 Toss 보상 취소를 요청했다.

하지만 보상 취소 자체까지 실패하면 다시 처리할 정보가 남지 않는 문제가 있어,   
실패 내용을 `PAYMENT_COMPENSATION_REQUIRED` Outbox 이벤트로 저장하도록 변경했다.

결제 완료 Transaction은 이미 rollback된 상태이므로 보상 이벤트를 같은 Transaction에 저장하면 함께 rollback될 수 있다.

따라서 `REQUIRES_NEW`를 이용해 별도 Transaction에서 Outbox 이벤트를 저장하고,   
기존 Outbox Publisher를 통해 `stream:payment-compensation`으로 발행하도록 했다.

> Toss 실제 상태 기반 보상 재처리

`PaymentCompensationConsumer`에서는 메시지를 받자마자 Toss 취소를 다시 호출하지 않고 실제 결제 상태를 먼저 조회하도록 했다.

Toss 상태가 `DONE`이면 아직 결제가 승인된 상태이므로 취소를 다시 시도하고 내부 `Payment`와 `Purchase` 상태도 보정한다.

반대로 `CANCELED`이면 Toss 취소 자체는 이미 성공한 것으로 보고 외부 취소를 다시 호출하지 않고 내부 상태만 보정한다.

이를 통해 Toss 취소 자체가 실패한 경우와 Toss 취소는 성공했지만 내부 DB 보상만 실패한 경우를 하나의 재처리 흐름에서 처리할 수 있도록 했다.

> Redis Streams Pending 재처리

Consumer가 메시지를 읽으면 처리 완료 전까지 Pending Entries List에 남고 정상적으로 처리된 경우에만 ACK하도록 했다.

Toss API 호출이나 내부 보상 처리 중 예외가 발생하면 ACK하지 않아 메시지가 Pending 상태로 유지된다.

일정 시간이 지난 Pending 메시지는 다시 조회한 뒤 `claim()`으로 가져와 재처리하도록 했으며,   
실제 Redis에서도 실패 메시지의 Pending 상태와 delivery count가 증가하는 것을 확인했다.

ACK는 단순히 메시지를 읽었다는 의미가 아니라 해당 메시지의 비즈니스 처리가 정상적으로 끝났다는 확인 응답이라는 점을 다시 정리했다.

> 결제 보상 멱등 처리

Redis Streams의 at-least-once 처리에서는 동일 이벤트가 다시 전달될 수 있으므로 중복 보상 방지가 필요했다.

결제 보상에서는 별도의 Inbox를 추가하는 대신 Toss 취소 요청에 동일한 `Idempotency-Key`인 `GUDIT_CANCEL_{paymentKey}`를 사용했다.

Consumer는 Toss의 실제 상태를 다시 조회하고, 내부 `Payment`가 이미 `CANCELED` 상태라면 추가 상태 변경 없이 정상 종료하도록 했다.

따라서 내부 보상까지 완료된 직후 ACK 전에 장애가 발생해 동일 이벤트가 다시 전달되더라도 Toss 취소와 내부 보상이 중복 실행되지 않도록 구성했다.

> Inbox Pattern 적용 여부 검토

결제 보상에도 Inbox Pattern이 필요한지 검토했다.

Inbox에 `eventId`를 저장하면 동일 이벤트의 중복 소비 여부는 확인할 수 있지만,   
Inbox DB 저장과 Toss API 호출을 하나의 Transaction으로 묶을 수 없기 때문에   
외부 Side Effect 자체를 정확히 한 번 실행하도록 보장하지는 못한다.

현재 구조에서는 Toss의 `Idempotency-Key`, 실제 외부 상태 재조회, 내부 상태의 멱등 처리를 조합하는 방식이   
결제 보상 문제에 더 직접적인 해결책이라고 판단했다.

재고 복구에서는 Redis Lua Script로 `eventId` 확인과 재고 변경을 원자 처리하고,   
결제 보상에서는 외부 API 특성에 맞게 다른 멱등 전략을 사용한다는 차이도 확인했다.

> 비동기 흐름 추적 및 테스트 보강

`eventId`는 개별 Outbox·Stream 이벤트 식별과 멱등 처리에 사용하고,   
`traceId`는 HTTP 요청부터 비동기 Consumer까지 전체 처리 흐름을 연결하는 값으로 구분했다.

Outbox 저장 시 MDC의 `traceId`를 함께 저장하고 Stream 메시지를 통해 Consumer까지 전달한 뒤,   
Consumer에서 다시 MDC에 등록하고 처리 종료 후 제거하도록 했다.

테스트에서는 Outbox 저장, Stream 분기, Toss 상태가 `DONE`·`CANCELED`인 경우의 처리,   
Toss 조회·취소·내부 보상 실패 시 ACK하지 않는 경우, Pending 재처리와 이미 취소된 Payment의 중복 보상 방지까지 검증했다.

전체 `clean test`가 통과했고, 실제 Redis에서도 Pending과 재전달 흐름을 확인했다.

## 헷갈렸던 점

Redis Streams의 Consumer Group에도 Pending과 재처리가 있는데 Kafka의 offset과 어떤 차이가 있는지 다시 확인했다.

Redis Streams에서는 ACK되지 않은 메시지를 PEL에 남기고 `XPENDING`, `XCLAIM`을 이용해 다시 처리한다.   
Kafka처럼 파티션별 offset을 기준으로 소비 위치를 관리하는 방식과는 구조가 다르다는 점을 정리했다.

결제 보상에도 Inbox Pattern을 적용해야 하는지 고민했다.

Inbox는 중복 이벤트 자체를 식별하는 데는 도움이 되지만 외부 Toss API 호출과 Inbox DB 저장을 하나의 Transaction으로 묶을 수 없기 때문에   
현재 문제의 외부 Side Effect 원자성을 직접 해결하지 못한다는 점을 확인했다.

Kafka를 사용하지 않은 이유도 비용 때문인지 헷갈렸다.

Kafka 자체는 오픈소스로 직접 운영할 수 있으며, 이번에 Redis Streams를 선택한 핵심 이유는   
라이선스 비용이 아니라 현재 요구사항 대비 별도 Kafka 클러스터와 운영·모니터링 복잡도를 추가할 필요가 없고   
기존 Redis로 필요한 Consumer Group, ACK, Pending, 재처리 기능을 충족할 수 있기 때문이라고 정리했다.

## 오늘 느낀 점

결제 보상 재처리를 구현하면서 비동기 처리에서 중요한 것은 단순히 실패한 메시지를 다시 실행하는 것이 아니라   
실패가 어느 단계에서 발생했는지 알 수 없는 상황에서도 안전하게 다시 실행할 수 있도록 만드는 것이라는 점을 느꼈다.

특히 외부 Toss 취소가 실패했는지, 취소는 성공했지만 내부 DB 보상만 실패했는지를 이벤트 자체만 보고 구분하기 어렵기 때문에   
실제 외부 상태를 다시 조회하는 과정이 중요했다.

또한 모든 중복 처리 문제에 같은 방법을 적용하는 것이 아니라   
재고 복구는 Redis Lua Script, 결제 보상은 Toss `Idempotency-Key`와 상태 재조회처럼   
Side Effect의 특성에 맞는 멱등 전략을 선택해야 한다는 점을 확인했다.
