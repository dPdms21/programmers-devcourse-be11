## 오늘 배운 내용

오늘은 MSA에서 서비스 간 데이터를 조회하고 내부 API 요청을 보호하는 흐름과 Kotlin의 함수·조건문을 실습했다.

MSA에서는 서비스와 DB가 분리되면서 다른 서비스의 데이터를 직접 조회할 수 없기 때문에 API를 통해 필요한 정보를 가져와 조합해야 한다.   
게시글 조회에서는 여러 `userId`를 모아 `auth-service`에 한 번에 요청해 사용자 정보를 가져오는 방식으로   
반복적인 서비스 간 호출을 줄이는 구조를 확인했다.

또한 사용자 요청을 인증하는 JWT와 서비스 간 내부 요청을 보호하는 Service Token의 역할을 구분했다.   
각 서비스는 전달받은 JWT를 자체 검증하고, 실제 사용자 정보가 필요할 때만 다른 서비스를 호출한다는 점을 다시 정리했다.

Kotlin에서는 Java와 유사한 연산자와 조건문을 확인하고,   
`Unit`, 표현식 형태의 함수, 문자열 템플릿, 순수 함수와 고차 함수, 값을 반환하는 `if`와 다양한 조건을 처리할 수 있는 `when` 등   
Kotlin에서 달라지는 부분을 중심으로 학습했다.

제3회 알고리즘 코딩테스트에서는 단순히 자료형이나 알고리즘 유형을 아는 것보다 문제 조건을 해석하고 구현 로직을 직접 구성해야 하는 문제가 까다롭게 느껴졌다.   
Web Project 과제는 상대적으로 수월하게 진행해 제한 시간을 조금 더 줄여도 될 것 같다고 느꼈다.

## 실습 및 과제

> MSA 서비스 토큰과 게시판 조회 연동 실습

`board-service`에서 게시글을 조회할 때 작성자의 사용자 정보는 `auth-service`가 소유하므로 게시글의 `userId`를 이용해   
사용자 정보를 API로 조회하고 최종 응답에 조합하는 흐름을 구현했다.

게시글마다 사용자 정보를 개별 호출하는 대신 여러 `userId`를 모아 한 번에 전달하고,   
`auth-service`에서는 `findByUserIdIn()`으로 사용자 정보를 조회하도록 해 서비스 간 호출과 반복 조회를 줄였다.

서비스 간 내부 API 요청에는 일반 사용자 인증용 JWT와 별도로 Service Token을 사용했다.

`board-service`의 `ServiceTokenInterceptor`가 Feign 요청에 `X-Service-Token`을 추가하고,   
`auth-service`의 `ServiceTokenFilter`가 해당 값을 검증한다.

토큰이 일치하지 않으면 `401 Unauthorized`를 반환하고,   
정상적인 내부 요청이면 `filterChain.doFilter()`를 호출해 이후 Security Filter와 Controller로 요청을 전달한다.

사용자 인증과 서비스 간 인증은 목적이 다르므로 JWT와 Service Token을 별도로 사용한다는 점을 정리했다.

> JWT와 Spring Security 흐름 복습

`auth-service`는 로그인 시 JWT를 발급하지만 이후 모든 서비스의 요청을 대신 검증하지 않는다.

`board-service`에도 `TokenProvider`, `TokenAuthenticationFilter`, `SecurityConfig`가 존재하며 요청에 포함된 JWT를 자체적으로 검증한다.

매 요청마다 `auth-service`에 토큰 검증을 요청하면 네트워크 호출이 증가하고 인증 서비스에 대한 의존성이 커지기 때문에 각 서비스가 JWT를 직접 검증한다.

반면 사용자 이름처럼 JWT에 포함되지 않은 실제 사용자 데이터가 필요한 경우에는 데이터를 소유한 `auth-service`를 호출한다.

`TokenAuthenticationFilter`는 `Authorization: Bearer ...` 헤더에서 JWT를 추출하고, 유효하면 `Authentication`을 생성해 `SecurityContext`에 저장한다.

인증 자체가 되지 않은 요청은 `AuthenticationEntryPoint`에서 `401`, 인증은 되었지만 권한이 부족한 요청은 `AccessDeniedHandler`에서 `403`으로 처리한다.

JWT를 Authorization 헤더로 전달하는 Stateless 구조에서는 `SessionCreationPolicy.STATELESS`를 사용하고 CSRF를 비활성화했다.   
다만 JWT를 쿠키처럼 브라우저가 자동 전송하는 구조에서는 CSRF 방어를 다시 고려해야 한다는 점도 확인했다.

> Kotlin 함수와 조건문 실습

산술·대입·증감·비교·논리 연산자는 Java와 유사하게 사용할 수 있었고 `&&`, `||`의 단락 평가도 확인했다.

반환값이 없는 함수에서는 `Unit`을 사용하며 Java의 `void`와 비슷하게 이해할 수 있다.

함수 본문이 하나의 표현식이라면 중괄호와 `return` 대신 `=`를 사용할 수 있고, 반환 자료형도 타입 추론을 통해 생략할 수 있다.

문자열 템플릿에서는 `$변수`로 값을 넣고 `${표현식}`으로 연산이나 함수 호출 결과를 문자열에 포함할 수 있다는 점을 확인했다.

순수 함수는 같은 입력에 항상 같은 결과를 반환하고 외부 상태를 변경하지 않는 함수이며, 고차 함수는 함수를 매개변수로 받거나 반환하는 함수라는 차이를 정리했다.

Kotlin의 `if`는 값을 반환하는 표현식이기 때문에 Java의 삼항 연산자 대신 사용할 수 있고,   
`when`은 값 비교뿐 아니라 범위와 타입 검사 등 다양한 조건을 처리할 수 있다는 점을 확인했다.

> 제3회 알고리즘 코딩테스트

제3회 알고리즘 코딩테스트에 응시했다.

4문제 중 2문제는 제출해 통과했고, 1문제는 풀이와 구현까지 진행했지만 제한 시간 안에 제출하지 못했다. 나머지 1문제는 문제를 확인했지만 풀이를 시작하지 못했다.

한 문제는 비교적 쉽게 해결했지만 나머지 문제들은 단순히 자료형이나 알고리즘 유형을 알고 있는 것만으로 바로 풀기 어려웠다.

문제의 여러 조건을 코드로 어떻게 표현할지 정리하고 전체 로직을 직접 구성해야 하는 부분에서 시간이 많이 소요됐다.

최근 특강에서 여러 유형을 연습했지만 실제 평가에서는 유형을 알아보는 것보다 조건을 놓치지 않고 구현 가능한 로직으로 바꾸는 능력이 더 필요하다는 점을 확인했다.

현재 난이도라면 제한 시간이 조금 줄어도 충분히 대응할 수 있을 것 같다고 느꼈다.

## 헷갈렸던 점

MSA에서 `auth-service`가 JWT를 발급하고 인증을 담당하는데 왜 `board-service`에도 JWT 검증 로직이 필요한지 다시 헷갈렸다.

로그인과 토큰 발급은 `auth-service`의 책임이지만, 발급 이후의 요청은 각 서비스가 전달받은 JWT를 직접 검증한다.   
실제 사용자 데이터가 필요한 경우에만 `auth-service`를 호출한다는 차이를 구분했다.

JWT와 Service Token의 역할도 처음에는 비슷하게 느껴졌다.

JWT는 로그인 사용자가 누구인지 확인하기 위한 인증 수단이고,   
Service Token은 서비스 간 내부 API 요청이 신뢰할 수 있는 서비스에서 온 요청인지 확인하기 위한 수단이라는 차이를 정리했다.

Kotlin의 순수 함수와 고차 함수도 개념이 헷갈렸다.

순수 함수는 함수의 입력과 출력 및 외부 상태 변경 여부에 대한 개념이고,   
고차 함수는 함수를 값처럼 전달하거나 반환하는 구조에 대한 개념으로 서로 다른 기준이라는 점을 확인했다.

알고리즘 코딩테스트에서는 알고리즘이나 자료형을 알고 있으면 구현까지 자연스럽게 이어질 것이라고 생각했지만,   
실제로는 문제의 조건을 어떤 상태와 분기로 표현할지 결정하는 과정에서 시간이 많이 걸렸다.

특히 여러 조건을 동시에 만족시켜야 하는 문제에서는 바로 코드를 작성하기보다 입력, 상태 변화, 예외 조건과 종료 조건을 먼저 정리하는 연습이 더 필요했다.

## 오늘 느낀 점

MSA 실습에서는 서비스가 분리되면서 단순히 호출 대상만 달라지는 것이 아니라   
사용자 인증, 서비스 간 인증과 데이터 조회 책임까지 각각 구분해야 한다는 점을 이전보다 명확하게 이해할 수 있었다.

특히 JWT 자체 검증과 `auth-service` 사용자 정보 조회, Service Token 검증은 모두 인증과 관련돼 보여도   
각각 해결하는 문제가 다르기 때문에 전체 요청 흐름 안에서 역할을 구분해 보는 것이 중요했다.

Kotlin은 Java와 유사한 문법이 많아 기본 연산자나 조건문은 비교적 쉽게 이해할 수 있었지만,   
표현식 기반 문법과 함수형 프로그래밍처럼 Kotlin에서 강조되는 방식은 앞으로 람다와 컬렉션을 사용하면서 더 익혀야 할 것 같다.

이번 알고리즘 코딩테스트에서는 단순한 유형 암기보다 조건을 분석하고 구현 가능한 로직으로 구체화하는 연습이 더 필요하다는 점을 느꼈다.

쉬운 문제는 빠르게 해결했지만 조건이 많아지자 구현 방향을 정하는 데 시간이 오래 걸렸고 결국 모든 문제를 제출하지 못했다.   
앞으로는 조건 분기와 상태 관리가 필요한 문제를 꾸준히 풀면서 문제를 코드 구조로 바꾸는 연습을 더 해야겠다.

반면 Web Project 과제는 크게 어렵지 않았고 이전보다 빠르게 요구사항을 파악하고 구현할 수 있었다.   
웹 과제는 현재 수준이라면 시간 관리보다 정확한 요구사항 반영과 검증에 집중해도 될 것 같다.
