## 오늘 배운 내용

오늘은 MSA에서 Refresh Token 재발급과 로그아웃, 게시글 삭제·파일 다운로드, 작성자별 게시글 통계 기능을 연결했다.

특히 `auth-service`가 내려준 `Set-Cookie`를 `web-service`가 다시 브라우저에 전달해야 하는 흐름과,   
`board-service`에서 집계한 `userId`별 게시글 수에 `auth-service`의 사용자 정보를 bulk 조회해 조합하는 방식을 확인했다.

이후 Kotlin에서는 추상 클래스, 인터페이스, `this`·`super`, 캡슐화와 접근 제어자를 학습했다.   
`private set`을 이용해 외부에서는 조회만 가능하고 내부에서만 값을 변경하도록 제한하는 방식과, 커스텀 setter에서 `field`를 사용하는 구조를 이해했다.

객체지향 회원 관리 실습에서는 기존 배열 중심 구조를 `Member`, `MemberManager`, `MemberApp`으로 나눠 데이터, 관리 규칙, 입출력 책임을 분리했다.

회원 관리2 과제에서는 `Member`를 추상 클래스로 두고 `NormalMember`, `VipMember`가 이를 상속하도록 구성하면서   
nullable 타입, 다형성, 스마트 캐스트를 실제 코드에 적용했다.

## 실습 및 과제

> MSA Refresh Token과 로그아웃 연동

Refresh Token을 이용한 토큰 재발급과 로그아웃 흐름을 서비스 간 요청 구조에서 연결했다.

클라이언트가 직접 `auth-service`를 호출하는 구조가 아니라 `web-service`를 거쳐 요청하기 때문에,   
`auth-service`가 내려준 `Set-Cookie`를 브라우저까지 전달하려면 `web-service`가 해당 응답 헤더를 다시 전달해야 한다는 점을 확인했다.

기존에는 JWT 검증 자체에 집중했다면, 오늘은 인증 서비스의 응답을 실제 클라이언트까지 어떻게 중계할지가 중요한 부분이었다.

> MSA 게시글 기능 확장

게시글 삭제와 첨부파일 다운로드 기능을 추가했다.

게시글 삭제 시에는 게시글 데이터뿐 아니라 연결된 파일까지 함께 정리해야 했고,   
파일 다운로드에서는 `FileService`가 저장된 파일을 `Resource`로 반환하도록 구성했다.

기존 작성·조회·수정에 삭제까지 연결하면서 게시글 CRUD 흐름을 확장했다.

> 작성자별 게시글 통계

`board-service`에서 작성자별 게시글 수를 집계했다.

먼저 `userId`별 게시글 수를 `groupBy`와 `having`으로 집계한 뒤,  
`auth-service`에 사용자 정보를 bulk 조회해 `userId`, `userName`, `boardCount` 형태로 응답을 조합했다.

서비스별로 데이터를 따로 관리하면서도 필요한 경우 각 서비스의 결과를 조합해 하나의 응답을 만들 수 있다는 점을 확인했다.

> Kotlin 추상 클래스와 인터페이스 실습

추상 클래스는 직접 인스턴스를 만들 수 없고, `abstract`로 선언된 프로퍼티나 메서드는 자식 클래스가 `override`해야 한다.

인터페이스는 여러 개를 동시에 구현할 수 있고 기본 구현 메서드도 가질 수 있다.

여러 인터페이스에서 동일한 기본 메서드가 겹치는 경우에는 다음처럼 어느 구현을 사용할지 직접 지정할 수 있다.

`super<인터페이스>.메서드()`

> Kotlin `this`와 `super`

`this`는 현재 객체를, `super`는 부모를 가리킨다.

`this(...)`는 같은 클래스의 다른 생성자를 호출하고, `super(...)`는 부모 생성자를 호출할 때 사용한다.

부 생성자는 빈 객체를 만들기 위한 문법이 아니라 별도의 생성 경로가 필요한 경우 사용하는 방식이라는 점도 정리했다.

단순히 일부 생성자 인자를 생략하고 싶은 경우에는 주 생성자의 기본값으로 충분한 경우가 많다.

> Kotlin 캡슐화와 접근 제어자 실습

`public`, `private`, `protected`, `internal`의 차이를 확인했다.

특히 `private set`은 프로퍼티 전체를 `private`으로 만드는 것이 아니라 setter만 제한하는 방식이다.

외부에서는 값을 읽을 수 있지만 직접 수정할 수 없고, 클래스 내부에서는 값을 변경할 수 있다.

커스텀 setter는 `set()`을 직접 호출하는 방식이 아니라 프로퍼티에 값을 대입할 때 자동으로 실행되며, 내부에서는 실제 저장 공간을 의미하는 `field`를 사용한다.

> Kotlin 객체지향 회원 관리 실습

기존 배열과 전역 함수 중심 회원 관리 코드를 `Member`, `MemberManager`, `MemberApp`으로 분리했다.

`Member`는 회원 한 명의 데이터를 담당하고, `MemberManager`는 회원 목록과 추가·조회·삭제 등의 규칙을 관리하며,   
`MemberApp`은 메뉴와 입력·출력을 담당하도록 역할을 나눴다.

`memberCnt`에는 `private set`을 적용해 외부에서 임의로 변경하지 못하도록 하고,   
`isFull`은 별도 값을 저장하지 않고 현재 회원 수를 기준으로 계산하는 프로퍼티로 구현했다.

> 회원 관리2 과제

기존 배열 기반 회원 관리 프로그램을 추상 클래스와 다형성을 사용하는 구조로 확장했다.

`Member`를 추상 클래스로 두고 `NormalMember`, `VipMember`가 이를 상속해 `grade`와 `monthlyFee()`를 각각 구현하도록 했다.

공통 프로퍼티인 `name`, `email`, `phone`은 부모 클래스에서 관리하고, 등급별로 달라지는 동작만 자식 클래스에서 구현했다.

부모 타입인 `Member` 배열에 일반 회원과 VIP 회원을 함께 저장하고,   
월회비 계산 시 등급별 분기 없이 각 객체의 `monthlyFee()`를 호출하도록 해 다형성을 적용했다.

`Member?`는 `Member` 또는 `null`을 가질 수 있는 nullable 타입이다.

`Array<Member?>`를 사용해 비어 있는 배열 칸을 `null`로 두고, 실제 회원이 존재한다고 보장되는 범위에서는 `!!`를 사용해 값을 꺼냈다.

다만 `!!`는 실제 값이 `null`이면 예외가 발생할 수 있으므로 사용 범위를 제한해야 한다는 점을 확인했다.

회원 삭제에서는 삭제한 위치 이후의 회원을 앞으로 한 칸씩 이동한 뒤 마지막 칸을 `null`로 비우도록 수정했다.

회원 수정에서는 새 값을 입력받는 것만으로는 데이터가 변경되지 않기 때문에   
조회한 객체의 `name`, `email`, `phone`에 직접 값을 대입해야 실제 수정이 반영된다는 점도 확인했다.

`if (member is VipMember)`로 타입을 확인한 뒤에는 스마트 캐스트가 적용되어 별도 형 변환 없이 `sendGift()` 같은 VIP 전용 기능을 호출할 수 있었다.

## 헷갈렸던 점

MSA에서는 `auth-service`가 설정한 쿠키가 왜 바로 브라우저에 전달되지 않는지 헷갈렸다.

클라이언트가 `web-service`를 거쳐 요청하기 때문에   
`auth-service`의 `Set-Cookie` 응답을 `web-service`가 다시 클라이언트 응답에 포함해야 한다는 점을 확인했다.

`private set`이 프로퍼티 자체를 `private`으로 만드는 것인지도 헷갈렸다.

getter는 공개된 상태로 유지되고 setter만 `private`이기 때문에 외부에서는 읽기만 가능하다는 의미라는 점을 이해했다.

주 생성자와 부 생성자의 역할도 다시 정리했다.

부 생성자는 매개변수가 없는 객체를 만들기 위한 전용 문법이 아니라 추가적인 생성 경로가 필요할 때 사용하는 방식이며,   
단순한 인자 생략은 주 생성자의 기본값으로 처리할 수 있다.

`Member?`의 `?`가 상속과 관련된 표기인지도 헷갈렸다.

`Member?`는 nullable 타입을 의미하고, `!!`는 값이 null이 아니라고 개발자가 강제로 가정하는 연산자라는 차이를 다시 확인했다.

## 오늘 느낀 점

MSA에서는 앞선 실습에서 서비스 분리와 Feign 호출 구조를 충분히 확인했기 때문에,   
오늘은 인증 응답의 쿠키 중계와 서비스별 데이터를 조합하는 작성자 통계처럼 서비스가 분리되면서 새롭게 필요한 처리에 집중하는 것이 더 도움이 됐다.

Kotlin에서는 추상 클래스와 인터페이스 자체는 Java에서 익힌 객체지향 개념과 유사했지만,   
`private set`, nullable 타입, 스마트 캐스트처럼 Kotlin에서 제공하는 문법을 함께 적용하면서 객체 상태와 역할을 더 명확하게 표현할 수 있었다.

회원 관리 실습과 과제에서는 단순 CRUD보다 `Member`, `MemberManager`, `MemberApp`으로 책임을 나누고,   
추상 클래스와 다형성을 이용해 등급별 동작을 분리하는 구조가 핵심이었다.

같은 기능을 다시 구현하더라도 단순히 코드를 옮기는 것이 아니라, 상태와 책임을 어떤 객체에 둘지 판단하는 과정이 객체지향 설계에서 중요하다는 점을 느꼈다.
