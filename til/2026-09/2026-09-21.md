## 오늘 배운 내용

오늘은 AWS 인프라 학습을 위해 네트워크 기초부터 서비스 격리, Docker의 동작 원리까지 학습했다.

IPv4의 주소 구조와 CIDR을 통해 네트워크 범위를 계산하는 방법을 이해하고, VPC와 서브넷을 이용한 AWS 네트워크 구성을 정리했다.   
특히 Public/Private 서브넷은 공인 IP 보유 여부가 아니라 라우트 테이블의 인터넷 연결 경로를 기준으로 구분하며,   
실제 외부 통신에는 IP 할당과 보안 설정도 함께 고려해야 한다는 점을 이해했다.

서비스 격리에서는 하나의 서버에서 여러 프로세스가 자원을 공유할 때 발생할 수 있는 장애를 살펴보았다.   
가상 머신과 컨테이너의 구조를 비교하면서 컨테이너가 호스트 커널을 공유하고,   
`namespace`와 `cgroup`을 통해 실행 환경과 자원 사용을 관리한다는 점을 학습했다.   
Docker 이미지의 계층 구조와 캐시를 통해 빌드 및 배포 과정의 중복을 줄일 수 있다는 점도 정리했다.

AWS 계정 생성 과정에서는 일반 AWS 계정과 교육용 실습 환경의 차이를 이해하고, 서울 리전인 `ap-northeast-2`를 확인했다.

---

이후 Repoary의 보안 및 예외 처리 구조를 개선했다.

서버 실행 시 출력되는 Spring Security 임시 비밀번호의 원인을 확인하고, 불필요한 기본 사용자 자동 생성 기능을 비활성화했다.   
이어서 공통 에러 코드와 예외 처리 구조를 도입해 응답 형식을 통일하고, 내부 오류 정보가 클라이언트에 노출되지 않도록 개선했다.

인증 처리에서는 Repoary JWT와 GitHub Access Token의 역할을 구분했다.   
GitHub API에서 인증·권한 오류가 발생했다고 해서 Repoary의 로그인까지 해제할 필요는 없으므로,   
프론트엔드가 HTTP 상태 코드뿐 아니라 에러 코드를 기준으로 오류를 처리하도록 변경했다.

이번 작업을 통해 예외 처리는 단순히 오류 메시지를 반환하는 기능이 아니라,   
오류의 발생 위치와 원인에 따라 클라이언트의 후속 동작을 결정하는 중요한 역할을 한다는 점을 이해했다.

## 실습 및 과제

> 네트워크 및 AWS 인프라 기초 학습

IPv4 주소 구조와 서브넷 마스크, CIDR을 이용한 네트워크 범위 계산 방법을 학습했다.

IPv4는 32비트로 구성되며, CIDR의 숫자가 커질수록 호스트부가 줄어 네트워크 크기가 작아진다.

`/24`는 전체 256개의 주소를 가지며, 일반적인 IPv4 서브넷에서는 네트워크 주소와 브로드캐스트 주소를 제외한 254개를 호스트에 할당할 수 있다.   
AWS에서는 서브넷마다 5개의 주소를 예약하므로 `/24` 기준 251개를 사용할 수 있다는 차이를 확인했다.

VPC는 AWS에서 생성하는 전체 가상 네트워크이고, 서브넷은 VPC의 주소 범위를 나누어 사용하는 네트워크다.   
각 서브넷은 하나의 AZ에 속하며, 여러 AZ에 자원을 분산하면 가용성을 높일 수 있다.

Public 서브넷은 Internet Gateway로 향하는 기본 경로를 가지며,    
Private 서브넷은 NAT Gateway 등을 이용해 외부 API 호출과 같은 아웃바운드 통신을 수행할 수 있다.

또한 라우트 테이블은 패킷의 이동 경로를 결정하고, Security Group과 NACL은 트래픽 허용 여부를 제어한다는 역할 차이를 정리했다.

> 서비스 격리와 Docker 동작 원리 학습

여러 서비스가 하나의 서버에서 자원 제한 없이 실행될 때 발생할 수 있는 문제를 학습했다.

한 서비스의 메모리 누수로 서버의 메모리가 고갈되면 OOM Killer가 실행되어 원인 프로세스와 다른 프로세스가 종료될 수도 있다.   
서비스 간 자원 격리가 필요한 이유를 이해했다.

가상 머신은 하이퍼바이저를 통해 각각의 게스트 OS와 커널을 실행하지만, 컨테이너는 호스트 커널을 공유한다.

컨테이너는 `namespace`로 프로세스·네트워크 등의 실행 환경을 격리하고, `cgroup`으로 CPU와 메모리 등 자원 사용을 관리한다.

Docker의 핵심 구성 요소도 정리했다.

- Image: 애플리케이션과 실행 환경을 담은 읽기 전용 패키지
- Container: 이미지를 기반으로 생성되는 실행 환경
- Registry: 이미지를 저장하고 공유하는 저장소

Docker 이미지가 파일 시스템 계층과 메타데이터로 구성되며 호스트 커널을 포함하지 않는다는 점을 확인했다.

Dockerfile의 `FROM`, `WORKDIR`, `COPY` 역할과 이미지 계층 공유·빌드 캐시의 원리를 학습했다.   
Java 베이스 이미지인 `eclipse-temurin`, `amazoncorretto`도 확인하고 실행 환경에 적합한 이미지와 태그를 선택해야 한다는 점을 정리했다.

> AWS 계정 생성

AWS 인프라 실습을 위해 계정을 생성하고, 무료·유료 플랜과 신규 가입 크레딧 및 학생 혜택을 확인했다.

서울 리전(`ap-northeast-2`)을 선택하고, 서비스별 무료 사용 한도와 과금 조건을 확인했다.

---

> Spring Security 기본 사용자 자동 생성 제거

Repoary 서버 실행 로그에 `Using generated security password`가 출력되는 원인을 확인했다.

해당 비밀번호는 GitHub OAuth 인증에 사용하는 비밀번호가 아니라, Spring Security가 기본 사용자를 자동 생성하면서 출력하는 임시 비밀번호였다.

현재 서비스는 GitHub OAuth 기반 인증을 사용하므로 별도의 기본 사용자가 필요하지 않다고 판단했다.

`application.yml`에서 `UserDetailsServiceAutoConfiguration`을 제외해 기본 사용자 자동 생성 기능을 비활성화했다.

변경 후 서버를 재실행해 임시 비밀번호 출력이 사라진 것을 확인했다.   
기존 OAuth 로그인과 주요 기능이 정상 동작하고, 인증되지 않은 요청의 접근 제한도 유지되는지 검증했다.

단순히 로그 출력을 숨기는 것이 아니라 불필요한 사용자 자동 생성 자체를 제거하는 방식으로 개선했다.

> 공통 예외 처리 및 에러 응답 구조 개선

기존 예외 처리 구조를 정리하고, 공통 `ErrorCode`와 `BusinessException` 및 도메인별 에러 코드를 도입했다.

각 예외에 적절한 HTTP 상태 코드와 메시지를 지정하고,   
기존 `ErrorResponse`의 `status`, `message`, `timestamp`를 유지하면서 `code` 필드를 추가했다.

이를 통해 프론트엔드가 HTTP 상태 코드만으로 모든 오류를 판단하지 않고, 구체적인 에러 코드를 기반으로 후속 동작을 결정할 수 있도록 했다.

예상하지 못한 서버 예외에서는 원본 예외 메시지가 클라이언트에 그대로 노출되지 않도록 변경했다.   
클라이언트에는 안전한 메시지를 반환하고, 상세한 오류 원인은 서버 로그에서 확인하도록 역할을 분리했다.

JWT 필터에서도 토큰 검증 과정에서 발생한 인증 오류와 이후 요청 처리 과정에서 발생한 오류를 구분해야 한다는 점을 확인했다.

> GitHub 인증 오류 처리 및 프론트엔드 보완

기존 프론트엔드는 모든 401·403 응답을 Repoary 인증 실패로 판단해 로그아웃 처리하고 있었다.

하지만 Repoary JWT 만료와 GitHub Access Token 만료·권한 부족은 서로 다른 문제다.

Repoary JWT가 만료된 경우에는 재로그인이 필요하지만, GitHub API 오류가 발생했다고 해서 Repoary 로그인 상태까지 무효화할 필요는 없다.

에러 코드를 기준으로 Repoary 인증 실패와 GitHub API 오류를 구분하도록 프론트엔드 처리를 개선했다.

GitHub 외부 API 연동에서도 인증 실패, 권한 부족, 요청 제한, 서버 오류, 연결 실패 및 타임아웃을 구분하고 연결·응답 타임아웃을 설정했다.

다만 Repoary 로그인 상태를 유지하더라도 GitHub 토큰이 자동으로 복구되는 것은 아니므로,   
실제 토큰 만료 시에는 별도 재인증이 필요할 수 있다는 점을 확인했다.

> 기능 검증 및 배포

예외 처리와 인증 로직 변경 이후 기존 기능이 정상적으로 유지되는지 검증했다.

분석 화면에서 특정 날짜의 TIL을 조회할 때 발생하는 404는 해당 날짜에 문서가 없는 경우의 정상적인 응답이며,   
이후 `TIL 초안 만들기` 버튼을 표시하는 것이 의도된 흐름임을 확인했다.

로그아웃 상태에서 분석 페이지 URL에 직접 접근하면 메인 페이지로 이동하는 동작도 확인했다.

백엔드 테스트 122개와 프론트엔드 빌드·Lint를 통과했으며, 변경 사항을 `develop` 브랜치에 병합한 뒤 배포를 진행했다.

GitHub 토큰 만료 및 저장소 접근 권한 부족 상황은 실제 환경에서 별도로 재현하지 않았으므로, 구현·테스트 결과와 실환경 검증 범위를 구분했다.

## 헷갈렸던 점

VPC와 서브넷이 각각 어떤 범위를 의미하는지, 공인 IP가 있으면 Public 서브넷이 되는 것인지 헷갈렸다.

VPC는 전체 가상 네트워크이고 서브넷은 VPC의 주소 범위를 나눈 네트워크이며,   
Public/Private 구분은 라우트 테이블의 IGW 경로를 기준으로 한다는 점을 이해했다.   
실제 인터넷 통신에는 공인 IP와 보안 설정 등 추가 조건도 필요하다.

---

서버 실행 로그에 표시되는 임시 비밀번호가 GitHub OAuth 인증과 관련된 것인지 헷갈렸다.

Spring Security의 기본 사용자 자동 생성으로 발생한 로그이며, OAuth 인증과 별개라는 점을 확인했다.   
로그 출력만 제거하는 대신 사용하지 않는 기본 사용자 자동 생성 기능을 비활성화했다.

GitHub API에서 401·403 오류가 발생했을 때 Repoary에서도 로그아웃해야 하는지 확인했다.

두 토큰의 인증 대상이 다르므로 GitHub API 오류를 Repoary 인증 실패로 처리하면 안 된다는 점을 이해했다.   
다만 GitHub 토큰이 실제로 만료된 경우에는 별도 재인증이 필요할 수 있다.

## 오늘 느낀 점

네트워크와 Docker를 각각의 기술로만 이해하는 것이 아니라, 서버의 통신 구조와 서비스 격리라는 관점에서 연결해 학습할 수 있었다.   
AWS 인프라를 구성하기 전에 VPC와 서브넷, 컨테이너의 동작 원리를 먼저 이해하는 것이 중요하다고 느꼈다.

---

Repoary에서는 실행 로그의 임시 비밀번호 문제부터 공통 예외 처리와 인증 오류 구분까지 개선했다.   
단순히 눈에 보이는 오류를 없애는 데 그치지 않고, 원인을 확인한 뒤 기존 기능을 유지하면서 구조를 개선한 점이 의미 있었다.

특히 모든 401·403 오류를 동일하게 처리하던 방식에서 벗어나 인증 주체와 오류 원인에 따라 후속 동작을 구분해야 한다는 점을 배웠다.   
앞으로도 실제 오류 원인을 파악하고 검증 범위를 명확하게 구분하며 개선해 나가고 싶다.
