오늘은 Gudit 3차 프로젝트의 Kotlin 전환 결과를 최종 측정하고, 2차에서 3차로 이어진 개선 과정과 성과를 정리해 발표 PPT를 제작했다.

Java에서 Kotlin으로 전환한 결과 코드 규모는 감소했지만, 두 언어 모두 JVM 기반이므로 실행 특성에서 큰 차이를 확인하지는 못했다.   
오히려 Clean Build 시간은 증가해 코드 간결성과 실행 성능은 별개라는 점을 확인했다.

이번 전환은 기존 기능과 테스트를 유지하면서 도메인별로 진행했다.   
Java와 Kotlin을 함께 사용하는 것이 가능해 전체 코드를 한 번에 변경하지 않아도 됐으며,   
통합 과정에서 발생한 타입·호출 방식 차이를 해결하면서 점진적으로 전환할 수 있다는 점을 경험했다.

발표 자료를 구성하면서는 담당 영역뿐 아니라 팀원들이 구현한 CI·AI 리뷰·로깅·모니터링 구조도 함께 정리했다.   
각 기능이 독립적으로 존재하는 것이 아니라 서비스의 안정성과 운영 편의성을 높이기 위해 어떤 역할을 하는지 이해하는 데 도움이 됐다.

또한 2차에서 발견한 문제를 3차에서 어떤 방식으로 개선했고,   
그 결과 무엇을 검증했으며 어떤 한계가 남았는지를 중심으로 프로젝트 전체 흐름을 정리했다.

## 실습 및 과제

> Kotlin 전환 코드 규모 최종 측정

3차 프로젝트에서 기능 추가와 구조 개선을 완료한 Java 버전을 Baseline으로 설정하고, Kotlin 전환 후 버전과 비교했다.

2차와 3차 프로젝트는 기능과 구조가 달라 언어 전환 효과만 비교하기 어렵기 때문에 동일한 3차 기능을 기준으로 측정했다.

전체 Production 파일 158개 중 155개를 Kotlin으로 전환해 파일 기준 전환율 98.1%를 확인했다.

전체 Production LOC는 8,399줄에서 7,338줄로 1,061줄 감소해 12.6% 감소했으며,   
담당 영역은 3,367줄에서 2,719줄로 648줄 감소해 19.2% 감소했다.

동일한 파일을 대응시켜 공백 제외 LOC를 분석한 결과는 13.7% 감소했다.   
전체 LOC 집계와 대응 파일 분석은 측정 범위가 다르므로 별도로 구분했다.

Purchase와 Payment는 각각 34.4%, 25.4% 감소했지만 일부 도메인은 Java 호환성 유지를 위한 코드가 추가되면서 오히려 증가했다.

Kotlin 전환으로 전체 코드 규모는 줄었으나, LOC 감소가 모두 중복 로직 제거 또는 코드 품질 향상을 의미하는 것은 아니라는 점을 확인했다.

> Kotlin 전환 실행 특성 비교

Clean Build 평균은 Java 176.58초에서 Kotlin 193.64초로 약 9.7% 증가했다.

Startup 시간은 전체 평균 기준 12.3% 감소했지만, 첫 실행을 제외하면 감소 폭이 3.6%로 줄어들었다.

두 언어 모두 JVM에서 실행되므로 언어 전환만으로 큰 실행 성능 차이를 기대하기는 어려웠으며,   
이번 측정에서도 Kotlin 자체의 성능 향상을 입증할 만큼 일관된 차이는 확인하지 못했다.

반면 코드 규모 감소와 빌드 시간 증가는 실제 측정 결과로 확인했다.   
전환 효과를 평가할 때 코드의 간결함과 빌드·실행 비용을 함께 고려해야 한다는 점을 정리했다.

> 최종 테스트 결과 재검증

발표 자료에 전체 테스트 수가 280건·283건·290건으로 혼재되어 있어 현재 코드 기준으로 다시 확인했다.

`.\gradlew.bat clean test --no-build-cache`를 실행하고 Gradle XML 테스트 보고서를 직접 집계했다.

최종 결과는 전체 테스트 283건, 성공 283건으로 확인했으며 발표 자료의 수치를 수정했다.

또한 전체 테스트 283건과 동시성 테스트 7개 시나리오를 각각 3회 실행한 결과는 서로 다른 검증 항목이므로 구분해 정리했다.

> 3차 프로젝트 발표 PPT 제작

2차 프로젝트의 구현 결과를 바탕으로 3차에서 어떤 문제를 추가로 발견하고 개선했는지 중심으로 발표 흐름을 구성했다.

2차에서는 Redis Lua를 활용한 원자적 재고 차감과 구매·결제 상태 관리를 구현했지만,   
DB 상태 변경 이후 재고 복구가 실패하거나 Toss 결제 보상까지 실패하는 상황에 대한 재처리 구조가 부족했다.

3차에서는 이러한 문제에 대응하기 위해 Transactional Outbox와 Redis Streams를 적용하고,   
실패 요청 기록·재처리·멱등 처리를 통해 장애 복구 구조를 보완했다는 점을 정리했다.

다른 팀원들이 담당한 기능도 함께 확인했다.

GitHub Actions는 필수 CI를 담당하고, n8n은 AI 코드 리뷰와 CI 실패 분석을 수행하도록 역할을 분리했다.   
로깅·모니터링에서는 Loki·Prometheus·Grafana를 통해 비동기 이벤트의 실패와 재처리 상태를 관측하도록 구성했다.

AI CS는 구매 내역을 기반으로 결제 상태를 분석하고 Slack으로 결과를 전달하되,   
실제 결제 취소·환불은 수행하지 않는 보조 도구라는 점을 명확히 했다.

발표 자료에는 Kotlin 전환의 정량 결과와 테스트 결과도 반영하고, 기능 구현·실제 검증·후속 개선 항목을 구분했다.

이번 과정을 통해 개별 도메인의 구현뿐 아니라 팀원들의 작업이 서비스 전체에서 어떤 문제를 해결하는지 이해할 수 있었다.

## 헷갈렸던 점

Kotlin 전환 후 Startup 시간이 감소한 결과를 언어 자체의 성능 개선으로 설명해도 되는지 확인했다.

첫 실행 포함 여부에 따라 결과가 달라졌으며,   
Gradle의 `UP-TO-DATE` 상태는 작업이 재실행되지 않았다는 의미이므로 실제 실행 시간 측정에 포함할 수 없었다.   
동일한 조건에서 측정한 결과만 비교하고, 확인되지 않은 성능 개선을 단정하지 않아야 한다는 점을 정리했다.

최종 테스트 수가 자료마다 달라 어떤 결과를 사용해야 하는지도 확인했다.

기존 자료에 기재된 수치를 그대로 사용하지 않고 현재 코드의 테스트 보고서를 직접 집계해 283건으로 확정했다.

발표 자료에서 장애 복구 구조의 구현과 실제 검증 범위를 어디까지 설명할 수 있는지도 확인했다.

Outbox 발행 실패·Consumer 재처리·멱등 처리 등을 단계별로 검증한 결과와 전체 비즈니스 요청부터 최종 정합성 복구까지 검증한 결과는 다르다.   
따라서 발표에서는 확인한 결과만 근거로 제시하고, 전체 E2E 검증은 후속 과제로 구분했다.

## 오늘 느낀 점

이번 Kotlin 전환을 통해 Java와 Kotlin이 같은 JVM 환경에서 동작한다는 점을 바탕으로,   
기존 서비스를 한 번에 교체하지 않고 도메인별로 점진적으로 전환할 수 있다는 것을 경험했다.

타입과 Java 라이브러리 호환성 등의 문제는 있었지만,   
기존 기능과 테스트를 유지하며 작은 단위로 전환하니 전체 구조를 다시 설계하지 않고도 작업을 마무리할 수 있었다.   
Kotlin 전환의 의미는 큰 실행 성능 향상보다 코드 표현의 간결함과 null 계약의 명시, 점진적 전환 경험에 있었다.

또한 발표 자료를 제작하면서 담당 기능에 집중할 때는 충분히 이해하지 못했던   
팀원들의 CI · AI 자동화 · 모니터링 작업을 전체 서비스 흐름과 연결해 볼 수 있었다.

2차에서 구현한 기능을 바탕으로 3차에서 실패 복구와 운영 관측을 보완한 과정을 정리하면서,   
프로젝트의 성과는 새로운 기술을 얼마나 많이 추가했는지가 아니라 기존 문제를 어떤 근거로 발견하고 개선했는지에 있다는 점을 확인했다.
