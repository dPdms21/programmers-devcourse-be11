## 오늘 배운 내용

오늘은 어제 구매 취소 흐름에 적용한 Transactional Outbox를 결제 실패와 Timeout까지 확장하고,   
Outbox에 저장된 재고 복구 이벤트를 Redis Streams를 통해 실제로 처리하는 흐름을 구현했다.

`Purchase`·`Payment` 상태 변경과 `STOCK_RESTORE_REQUESTED` Outbox 저장은 동일 DB Transaction에서 처리하고,   
이후 `OutboxPublisher`가 `PENDING` 이벤트를 Redis Stream에 발행하도록 구성했다.

Consumer에서는 성공한 메시지만 ACK하고 실패한 메시지는 Pending에 남긴 뒤 다시 가져와 재처리하도록 했다.   
또한 at-least-once 방식에서는 동일 이벤트가 다시 전달될 수 있으므로 `eventId`를 이용한 멱등 처리를 추가했다.

재고 복구와 이벤트 처리 여부 기록을 각각 수행하면 동시 처리 시 중복 복구가 발생할 수 있어,   
Redis Lua Script 안에서 중복 확인 · 재고 복구 · 구매량 수정 · 처리 완료 기록을 원자적으로 수행하도록 했다.

## 실습 및 과제

> Transactional Outbox 적용 범위 확장

기존 구매 취소뿐 아니라 결제 실패와 Timeout에서도   
`Purchase`·`Payment` 상태 변경과 재고 복구 Outbox 저장을 동일 DB Transaction에서 처리하도록 통일했다.

DB 상태가 변경된 뒤 Redis 재고 복구가 실패해 요청 자체가 유실되는 문제를 막기 위해 실제 Redis 처리는 이후 비동기 흐름으로 분리하고,   
DB에는 먼저 `PENDING` 이벤트를 남기도록 했다.

반면 구매 생성 시 Redis 재고를 먼저 차감한 뒤 DB Transaction 자체가 rollback되는 경우에는 Outbox 이벤트도 함께 rollback되기 때문에   
기존 `TransactionSynchronization` 기반 재고 보상은 유지했다.

즉 DB Transaction이 성공한 이후 수행할 후속 작업은 Outbox로 남기고,   
DB Transaction 자체가 실패해 Redis 선점 상태를 되돌려야 하는 경우에는 기존 보상 처리를 사용한다는 차이를 구분했다.

> Redis Streams Publisher와 Consumer 구현

`OutboxPublisher`가 `PENDING` Outbox 이벤트를 조회해 `stream:stock-restore`에 발행하고,   
Redis 발행이 성공한 이벤트만 `PUBLISHED` 상태로 변경하도록 했다.

발행에 실패하면 Outbox는 `PENDING` 상태로 남기 때문에 다음 Publisher 실행에서 다시 시도할 수 있다.

Redis Streams는 별도 브로커를 추가하는 방식이 아니라 기존 Redis에서 제공하는 메시지 스트림 기능이며,  
Spring에서는 `StringRedisTemplate.opsForStream()`을 통해 사용했다.

`XADD`로 Stream에 메시지를 추가하고 Consumer Group을 통해 메시지를 읽도록 구성했다.

Consumer는 재고 복구가 정상적으로 완료된 경우에만 ACK하도록 했다.   
ACK되지 않은 메시지는 Pending Entries에 남기 때문에 Consumer 처리 실패 여부를 이후 다시 확인할 수 있다.

> Pending 메시지 재처리

Consumer에게 전달된 메시지가 처리 도중 실패해 Pending에 남더라도 새 메시지처럼 자동으로 다시 소비되는 것은 아니었다.

따라서 일정 시간 이상 처리되지 않은 Pending 메시지를 조회하고 `claim()`을 통해 다시 가져와 처리하는 재처리 흐름을 추가했다.

Redis 명령 기준으로는 `XREADGROUP`으로 Consumer Group 메시지를 읽고, `XPENDING`으로 미처리 메시지를 확인하며,   
`XCLAIM`으로 오래된 Pending 메시지를 다시 가져오는 구조다.

실제로 강제로 Pending 상태를 만든 뒤 재처리가 수행되고, 성공 후 ACK되어 Pending이 0이 되는 것까지 확인했다.

> eventId 기반 멱등 처리

재고 복구가 성공한 직후 ACK 전에 애플리케이션 장애가 발생하면 동일 메시지가 다시 전달될 수 있다.

Redis Streams의 at-least-once 처리에서는 메시지 유실을 줄이는 대신 중복 전달 가능성이 있으므로,   
동일 이벤트가 여러 번 소비돼도 실제 재고는 한 번만 복구되도록 멱등 처리가 필요했다.

`restoreStockIdempotently()`에서 Redis Lua Script를 실행해   
`eventId` 처리 여부 확인, 재고 복구, 사용자 구매량 수정, 처리 완료 Key 저장을 하나의 Script로 묶었다.

Java 코드에서 중복 확인과 재고 복구를 각각 Redis에 요청하면 두 Consumer가 동시에 같은 이벤트를 처리할 가능성이 있지만,   
Lua Script를 사용하면 Redis 내부에서 해당 작업을 원자적으로 실행할 수 있다.

동일 `eventId`를 두 번 실행했을 때 재고가 `99 → 100 → 100`으로 유지되는 것을 확인해 중복 재고 복구가 발생하지 않는 것도 검증했다.

처리 완료 `eventId`는 영구적으로 보관하지 않고 TTL을 적용해 일정 시간이 지나면 제거하도록 했다.

> 실패·재처리 및 Transaction 검증

Redis Streams 발행 실패 후 Outbox가 `PENDING`으로 유지되어 다시 발행되는지,   
Consumer 실패 후 Pending 메시지가 재처리되는지, 동일 `eventId`가 여러 번 전달돼도 재고가 한 번만 복구되는지를 테스트했다.

또한 `TransactionTemplate`을 이용해 실제 DB Transaction에서 Outbox 이벤트를 저장한 뒤 강제로 예외를 발생시켜   
Transaction rollback 시 Outbox도 함께 rollback되는 것을 검증했다.

`TransactionTemplate`은 운영 흐름에 적용하기 위한 기능이 아니라 테스트에서 Transaction 경계를 명확하게 만들어   
Transactional Outbox의 핵심 특성을 검증하기 위해 사용했다.

Inbox Pattern도 검토했지만 현재 구조에서는 적용하지 않았다.

Inbox를 RDB에 저장하더라도 Redis 재고 변경과 Inbox INSERT를 하나의 Transaction으로 묶을 수 없기 때문에   
실제 Redis side effect의 중복 문제를 직접 해결하지 못한다.   
현재 문제에는 Redis 안에서 `eventId` 확인과 재고 변경을 Lua Script로 함께 처리하는 방식이 더 적합하다고 판단했다.

## 헷갈렸던 점

Redis Streams에서 Consumer가 메시지를 한 번 읽으면 실패해도 자동으로 다시 전달되는지 헷갈렸다.

Consumer Group에서 전달됐지만 ACK되지 않은 메시지는 Pending에 남을 뿐 새 메시지처럼 자동 소비되지 않기 때문에,   
`XPENDING`으로 확인하고 `XCLAIM`을 이용해 다시 가져오는 별도의 재처리 흐름이 필요하다는 점을 확인했다.

ACK의 의미도 단순히 메시지를 읽었다는 표시가 아니라 Consumer가 해당 메시지의 처리를 정상적으로 끝냈다는 확인 응답이라는 점을 정리했다.

Outbox 재발행과 Consumer 재처리를 구현하면 이벤트 유실은 줄일 수 있지만 동일 이벤트가 여러 번 전달될 수 있다는 점도 중요했다.   
이를 해결하기 위해 Consumer 측에서 `eventId`를 기준으로 멱등성을 보장해야 하고,   
Redis 변경과 중복 확인을 분리하지 않고 Lua Script로 원자 처리해야 한다는 점을 이해했다.

Inbox Pattern도 중복 이벤트 문제를 해결하는 방법이라 현재 구조에 적용할 수 있을지 고민했지만,   
RDB Inbox만으로는 Redis 재고 변경과의 원자성을 보장할 수 없어 현재 문제에는 Lua 기반 멱등 처리가 더 직접적인 해결책이라고 판단했다.

## 오늘 느낀 점

어제는 DB 상태와 재고 복구 요청을 함께 남기는 데 초점을 맞췄다면,   
오늘은 그 이벤트를 실제로 전달하고 실패했을 때 어떻게 다시 처리할지까지 연결하면서 Outbox 이후의 흐름을 더 구체적으로 이해할 수 있었다.

특히 비동기 처리는 단순히 메시지를 발행하고 Consumer가 읽는 것으로 끝나는 것이 아니라   
발행 실패, 처리 실패, ACK 직전 장애, 중복 전달처럼 각 단계에서 발생할 수 있는 실패를 기준으로 구조를 설계해야 한다는 점을 느꼈다.

Redis Streams의 Pending 재처리와 Lua Script 기반 멱등 처리를 직접 연결하면서   
at-least-once 전달에서는 재시도를 가능하게 만드는 것과 중복 처리를 안전하게 만드는 것이 함께 필요하다는 점도 확인했다.
