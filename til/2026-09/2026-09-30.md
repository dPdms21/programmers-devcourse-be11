또한 카테고리 분류 규칙, 작업 그룹화, 입력 데이터 누락 문제를 점검했다.

특히 기술 스택보다 데이터 확보 가능성, 사용자 수요, 운영 비용과 문제 해결 경험을 중심으로 아이디어를 검토했다.

## 실습 및 과제

> GitHub Actions 기반 EC2 배포 워크플로 추가

GitHub Actions가 SSH를 통해 EC2에 접속하고 기존 `deploy.sh`를 실행하는 배포 워크플로를 추가했다.

처음에는 특정 브랜치에 `push`할 때 자동 배포하도록 구성했지만,   
현재는 상시 배포가 필요하지 않아 `push` 트리거를 비활성화하고 `workflow_dispatch`만 유지했다.

EC2 접속 정보와 SSH Private Key는 코드에 직접 작성하지 않고 `EC2_HOST`, `EC2_SSH_KEY` Repository Secrets를 통해 전달하도록 구성했다.

현재 워크플로는 별도의 빌드 · 테스트 단계를 포함하지 않고 EC2에서 배포 스크립트를 실행하는 CD 중심 구조다.   
워크플로 작성과 설정 변경까지 완료했으며 GitHub Actions를 통한 실제 배포 실행은 검증하지 않았다.

> AWS 인프라 구축 및 MSA 배포 복습

AWS에서 VPC와 Public·Private Subnet, IGW, NAT Gateway, Security Group을 다시 구성하고 애플리케이션 서버와 DB 서버를 배치했다.

DB 서버에는 MySQL을 설정하고, 애플리케이션 서버에는 Docker와 Git을 설치했다.   
GitHub Deploy Key를 이용해 Repository를 내려받은 뒤 Docker Compose로 Config·Auth·Board·Edge·Web Service를 빌드하고 실행했다.

배포 과정에서는 `./gradlew: Permission denied` 오류가 발생했다.   
Gradle Wrapper에 실행 권한이 없는 것이 원인이었으며, 각 서비스의 `gradlew`에 실행 권한을 부여해 해결했다.

이후 JWT 비밀 키가 누락되어 인증 서비스에서 `WeakKeyException`이 발생했다.   
`.env` 파일의 위치와 환경변수를 점검하고 인증 서비스 컨테이너를 재생성해 해결했다.

로그인 성공 후 게시판 조회가 정상적으로 동작하지 않는 문제도 발생했다.   
실행 중인 컨테이너에는 변경된 환경변수가 자동으로 반영되지 않으므로 관련 서비스의 환경변수를 점검하고 컨테이너를 재생성해야 한다는 점을 확인했다.

최종적으로 OAuth 로그인과 게시판 조회가 정상적으로 동작하는 것을 확인해 AWS 수동 배포를 완료했다.

> Repoary AI TIL 생성 및 출력 형식 개선

Gemini 기반 AI TIL 생성 결과를 검토하면서 카테고리 분류와 출력 형식, 입력 데이터 구성을 개선했다.

TIL 제목과 6개 섹션, 카테고리별 학습 정리 및 GitHub 링크는 Java에서 생성하도록 하고,   
Gemini는 커밋과 변경 파일을 근거로 본문을 생성하도록 역할을 분리했다.

사용자 정의 규칙이 Conventional Commit fallback보다 먼저 적용되는 구조를 확인했으며,   
잘못 정의되어 있던 `docs(practice)` 기본 규칙을 `type=docs`, `scope=practice`, `category=docs`로 수정했다.   
기존 사용자 규칙과 분석 결과에는 변경 사항이 자동으로 반영되지 않아 재분석이 필요하다는 점도 확인했다.

동일 커밋의 변경 파일이 별도 학습 항목으로 나뉘는 문제를 개선하기 위해 관련 파일을 그룹화하고 대표 링크를 결정하도록 했다.   
또한 긴 patch는 앞부분과 뒷부분을 함께 전달해 입력 크기 제한으로 주요 내용이 누락되는 문제를 줄였다.

> 4차 최종 프로젝트 아이디어 구상

4차 프로젝트의 목표를 실제 사용자에게 필요한 서비스를 운영하고, 새로운 백엔드 문제 해결 경험을 확보하는 것으로 설정했다.

기존 Gudit에서 경험한 구매·결제와 동시성·비동기 처리 외에 검색·추천·개인화·조회 최적화 등의 영역을 검토했다.

사용자 수요와 반복 이용 가능성, 무료 API 및 공개 데이터의 안정적인 확보, 개발 일정과 운영 비용 등을 기준으로 아이디어를 비교했다.

단순 정보 제공보다는 사용자가 직접 해결하기 어려운 문제를 계산하거나 최적화하는 서비스를 중심으로 방향을 검토했으며, 구체적인 주제는 확정하지 않았다.

> 제4회 교과목 성취도 평가

제4회 교과목 성취도 평가에 응시했다.

Linux 관련 내용은 기존 학습 경험을 바탕으로 비교적 수월하게 풀었지만, AWS 인프라와 네트워크 구성 관련 내용은 일부 헷갈렸다.

이번 평가에는 주관식 문제가 많아 예상보다 틀린 문제가 있었지만 전반적으로 나쁘지 않았다고 느꼈다.

> AI 활용 입사서류 작성법 특강

이력서는 채용 담당자의 관심을 유도해 면접 기회를 얻기 위한 자료이므로   
모든 경험을 상세하게 나열하기보다 핵심 강점과 대표 프로젝트를 중심으로 구성해야 한다는 점을 학습했다.

프로젝트 경험은 본인의 기여도와 기술적 선택, 문제 해결 과정 및 검증 가능한 성과를 중심으로 작성한다.   
성과를 수치화할 때는 단순히 개선 수치를 제시하는 것이 아니라 측정 환경과 산출 근거를 함께 설명해야 한다.

AI는 문장 수정과 요약, 포트폴리오 구성 및 채용공고 탐색에 활용할 수 있지만, 강조할 경험과 기술적 의사결정은 직접 판단해야 한다.   
AI 활용 역량 역시 도구 사용 경험보다 문제 해결 과정과 생성 결과의 검증 경험을 중심으로 설명해야 한다는 점을 정리했다.

> Repoary AI TIL 생성 결과 및 오류 처리 개선

다양한 날짜의 GitHub 기록을 이용해 AI TIL 생성 결과를 검증하고, 실제 설정값과 생성 내용이 일치하도록 개선했다.

GitHub Actions 설정에서 Secrets를 참조하는 값과 코드에 직접 지정한 값을 AI가 혼동하는 문제를 확인했다.   
환경변수와 Secrets, 활성 설정과 주석 처리된 설정을 구분하도록 지침을 보완했다.

Gemini가 본문을 지나치게 축약하거나 보고서형 목록으로 생성하는 문제를 해결하기 위해 실제 작업 단위별로 내용을 그룹화하고,   
제목 아래에는 자연스러운 문단으로 작성하도록 프롬프트와 서버 후처리를 개선했다.

Gemini API 오류 처리에서는 잘못된 API 키를 입력했을 때 서비스 혼잡 메시지가 표시되는 문제를 확인했다.   
Google의 `400 INVALID_ARGUMENT`와 `API_KEY_INVALID` 응답을 고려해 HTTP 상태 코드뿐 아니라 실제 오류 정보도 분석하도록 개선했다.

인증 실패, 요청 한도 초과, 연결 실패, 타임아웃 및 일반 API 오류를 구분하고, 일시적인 `503 UNAVAILABLE`에 대해서만 지수 백오프 재시도를 적용했다.   
프론트엔드에서도 백엔드 ErrorCode에 따라 적절한 오류 메시지를 표시하도록 보완했다.

보안 측면에서는 API 키를 요청 단위로만 사용하고 저장하지 않는 BYOK 방식과 Markdown 미리보기의 XSS 방어를 점검했다.

마지막으로 신규 TIL 생성과 저장, 기존 TIL 적용, 취소 시 데이터 유지 및 잘못된 API 키에 대한 오류 처리를 검증했다.   
백엔드와 프론트엔드 테스트를 통과하고 변경 사항을 병합한 뒤 Render와 Vercel에 배포했다.

## 헷갈렸던 점

GitHub Actions에서는 워크플로를 작성하는 것과 실제 자동 배포를 완료하는 것의 차이를 정리했다.   
현재는 `workflow_dispatch`를 통한 수동 실행만 허용하는 CD 중심 구성으로, 실제 워크플로 실행과 배포 성공 여부는 별도로 검증해야 한다.

AWS 인프라를 다시 구축하면서 서브넷의 가용 영역과 기존 Elastic IP의 연결 상태 등을 확인해야 했다.   
개별 개념을 이해하는 것과 실제 리소스를 올바르게 연결해 배포하는 것은 별개의 과정이라는 점을 확인했다.

Docker의 `.env` 파일을 수정했는데도 서비스에 변경 사항이 반영되지 않는 이유가 헷갈렸다.   
`.env`를 변경하더라도 실행 중인 컨테이너의 환경변수는 자동으로 갱신되지 않으므로 컨테이너를 재생성해야 한다는 점을 확인했다.

Repoary에서는 규칙을 수정했는데도 기존 분석 결과에 변경 사항이 반영되지 않는 이유를 확인했다.   
기본 규칙과 기존 사용자 규칙은 구분되며, 저장된 분석 결과도 자동으로 갱신되지 않으므로 재분석 과정이 필요하다.

---

잘못된 Gemini API 키를 입력했는데도 서비스 혼잡 메시지가 표시되는 원인도 확인했다.   
Google은 잘못된 API 키에 대해 `400 INVALID_ARGUMENT`와 `API_KEY_INVALID`를 반환할 수 있으므로   
HTTP 상태 코드만으로 오류를 분류하지 않고 실제 오류 정보도 함께 확인해야 한다는 점을 배웠다.

또한 Gemini가 NAT Gateway의 역할을 부정확하게 설명하는 사례를 통해 프롬프트를 보완하더라도 기술적 정확성이 항상 보장되지는 않으며,   
실제 기술 문서 및 구현 내용과 비교하는 검증 과정이 필요하다는 점을 확인했다.

## 오늘 느낀 점

GitHub Actions를 활용하면 기존 수동 배포 과정을 반복 가능한 워크플로로 구성할 수 있다는 점을 이해했다.   
다만 워크플로를 작성하는 것과 실제 실행을 검증하는 것은 구분해야 하며, 현재 필요한 범위에 맞게 수동 실행 방식으로 구성했다.

AWS 인프라를 다시 구축하고 MSA 서비스를 배포하면서 어제 학습한 내용을 복습할 수 있었다.   
특히 실제 배포에서는 네트워크나 Docker 설정뿐 아니라 Linux 파일 권한, 환경변수와 컨테이너 실행 상태까지 함께 확인해야 한다는 점을 느꼈다.

Repoary에서는 프롬프트만 수정하는 것으로 AI 출력 품질을 해결하기 어렵다는 점을 확인했다.   
분석 데이터의 정확성과 입력 정보의 완전성, 서버의 출력 형식 제어까지 함께 고려해야 한다는 점이 의미 있었다.

4차 프로젝트를 고민하면서도 기능 구현이나 새로운 기술 도입 자체보다 실제 사용자 문제를 명확히 정의하고,   
운영 과정에서 발견한 문제를 측정하고 개선할 수 있는 서비스를 선택하는 것이 중요하다고 느꼈다.

---

AI 활용 입사서류 작성법 특강을 통해 프로젝트에서 사용한 기술보다   
본인이 발견한 문제와 해결 과정, 기술적 선택의 근거 및 검증 가능한 결과를 전달하는 것이 중요하다는 점을 다시 확인했다.

특히 프로젝트가 끝난 뒤 포트폴리오를 작성하는 것보다 개발 과정에서 문제 상황과 시행착오, 개선 전후 수치를 기록해 두는 것이 필요하다고 느꼈다.

Repoary에서는 AI 생성 결과의 정확성을 높이기 위해 프롬프트뿐 아니라 서버의 데이터 처리와 후처리 방식도 함께 개선해야 한다는 점을 확인했다.   
실제 사용자에게 제공하는 기능인 만큼 생성 결과의 검증뿐 아니라 외부 API 오류 처리와 민감정보 보호까지 고려하는 과정이 중요하다고 느꼈다.
