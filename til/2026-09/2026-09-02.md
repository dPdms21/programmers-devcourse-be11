## 오늘 배운 내용

오늘은 Kotlin의 반복문과 배열, 클래스와 생성자 문법을 실습하고 자판기·회원관리 과제에 직접 적용했다.

반복문에서는 `..`, `until`, `downTo`, `step`, `indices`, `withIndex()`처럼 Kotlin에서 범위와 인덱스를 다루는 방법을 확인했다.   
또한 `val`로 선언한 배열도 참조 자체만 변경할 수 없을 뿐 내부 원소는 수정할 수 있어, `val`이 객체 자체를 불변으로 만드는 것은 아니라는 점을 이해했다.

객체지향에서는 프로퍼티와 getter/setter의 관계,   
주 생성자와 `init`, 부 생성자, 생성자 매개변수에 `val`이나 `var`를 붙였을 때 프로퍼티가 되는 구조를 학습했다.

MSA에서는 `web-service`와 `board-service`를 연결해 게시글·댓글 요청을 Feign Client를 통해 전달하고,   
전날 구현한 `board-service → auth-service` 사용자 정보 조회와 연결해 `web-service → board-service → auth-service`의 전체 흐름을 확인했다.

과제에서는 Kotlin의 입력 처리, 배열, 반복문, 함수와 문자열·Collection 처리 문법을 실제 프로그램에 적용하면서
잘못된 입력이나 데이터 삭제·조회처럼 상태를 직접 관리해야 하는 부분을 연습했다.

## 실습 및 과제

> Kotlin 반복문과 배열 실습

Java와 유사한 `for`, `while` 구조를 사용하면서 Kotlin에서 범위를 표현하는 방법을 확인했다.

`..`는 양 끝 값을 포함하고, `until`은 마지막 값을 제외하며, `downTo`는 역순 반복, `step`은 증가·감소 간격을 지정할 때 사용한다.

배열이나 리스트의 인덱스를 순회할 때는 `indices`, 인덱스와 값을 함께 사용할 때는 `withIndex()`를 사용할 수 있다는 점도 정리했다.

중첩 반복문에서는 라벨을 이용해 원하는 반복문까지 `break`하거나 `continue`할 수 있다는 점을 확인했다.

`val`로 배열을 선언해도 배열 참조를 다른 배열로 바꿀 수 없을 뿐 `arr[0] = ...`처럼 내부 원소는 변경할 수 있다.

배열은 크기가 고정되어 있고, `listOf`는 읽기 전용 리스트, `mutableListOf`는 원소 추가·삭제가 가능해 크기까지 변경할 수 있다는 차이를 구분했다.

반복문과 조건문을 이용한 간단한 자판기 프로그램도 구현하면서 `while`과 `when`을 이용해 메뉴를 반복하고 입력에 따라 처리하는 흐름을 연습했다.

> Kotlin 클래스와 생성자 기초 실습

Kotlin의 프로퍼티는 클래스 내부의 단순 변수라기보다 getter/setter와 연결된 개념이라는 점을 확인했다.

`val` 프로퍼티는 읽기만 가능하고 `var` 프로퍼티는 읽기와 쓰기가 가능하다.

별도의 값을 저장하지 않고 getter에서 계산한 값을 반환하는 프로퍼티도 작성할 수 있다는 점을 확인했다.

생성자에서는 주 생성자, `init` 블록, 기본값과 부 생성자 문법을 살펴봤다.

특히 생성자 매개변수에 `val`이나 `var`를 붙이면 단순 생성자 인자가 아니라 클래스의 프로퍼티가 된다는 점을 Java와 비교해 정리했다.

> MSA 게시판과 댓글 서비스 연동 실습

전날 구현한 `board-service → auth-service` 사용자 정보 조회에서 더 나아가 `web-service → board-service`의 게시판·댓글 요청을 연결했다.

단일 애플리케이션에서는 다른 도메인의 Service를 직접 호출할 수 있지만,   
서비스가 분리된 환경에서는 다른 서비스 내부의 Service나 Repository를 직접 사용할 수 없기 때문에 HTTP 기반 서비스 간 통신이 필요하다.

게시글 상세 조회는 다음 흐름으로 처리했다.

`web-service → BoardClient → board-service → BoardService → BoardRepository`

`web-service`는 사용자 요청과 화면에 필요한 흐름을 담당하고, 실제 게시글·댓글 비즈니스 로직과 DB 접근은 `board-service`가 담당한다.

댓글 작성도 `web-service`에서 DB를 직접 처리하지 않고 다음과 같이 요청을 전달했다.

`CommentApiController → CommentService → BoardClient → board-service CommentApiController → CommentService → CommentRepository`

이를 통해 서비스가 분리돼도 각 서비스가 자신의 책임을 유지하고 필요한 기능은 API를 통해 호출한다는 점을 확인했다.

> BoardClient 역할 확인

`BoardClient`는 단순히 HTTP 요청 코드를 줄이는 파일이 아니라 `web-service`와 `board-service` 사이의 서비스 경계를 연결하는 역할을 한다.

`web-service`는 게시판 데이터가 필요할 때 `board-service`의 Repository나 Service에 직접 접근하지 않고 `BoardClient`를 통해 공개된 API만 사용한다.

전날 구현한 `board-service → auth-service` 사용자 정보 조회까지 연결하면 현재 요청 흐름은 다음과 같이 이어진다.

`web-service → board-service → auth-service`

각 서비스는 자신의 기능과 DB를 소유하고 다른 서비스의 기능이나 데이터가 필요한 경우에만 API 통신을 사용한다는 MSA의 기본 흐름을 확인했다.

> 자판기 과제

Java와 비교하면서 Kotlin의 변수·함수·입력 처리 문법을 자판기 프로그램에 적용했다.

Kotlin에서는 타입을 변수 이름 뒤에 `: Int`처럼 작성하고, 함수는 `fun getChoice(): Int`처럼 반환 타입을 선언한다.

`readln()`은 항상 `String`을 반환하므로 숫자로 사용하려면 `toInt()` 또는 `toIntOrNull()`로 변환해야 한다.

메뉴 입력에는 `toIntOrNull() ?: -1`을 사용해 숫자가 아닌 입력에서 예외가 발생하지 않도록 처리했다.

반면 금액 입력에서 잘못된 값을 그대로 `-1`로 반환하면 실제 보유 금액 계산에 영향을 줄 수 있어,   
함수의 역할에 따라 오류 시 반환값을 다르게 정해야 한다는 점을 확인했다.

음료마다 반복되던 구매 로직은 `buy(totalMoney, price, name)` 함수로 분리하고,   
잔돈이 부족하면 기존 금액을 그대로 반환하며 정상 구매일 때만 가격을 차감하도록 구성했다.

> 회원관리 과제

`Array(totalCnt) { Array(3) { "" } }` 형태의 2차원 배열에 이름, 이메일, 연락처를 저장하는 회원관리 프로그램을 구현했다.

`memberCnt`를 실제 저장된 회원 수이자 반복 범위로 사용하고 `0 until memberCnt`를 통해 실제 데이터가 있는 영역만 조회했다.

`findIndex()`를 이용해 이메일 중복 검사와 조회·수정·삭제 대상 탐색을 공통화했다.

회원 삭제 시에는 뒤쪽 데이터를 한 칸씩 앞으로 이동한 뒤 마지막 데이터를 비우는 방식으로 배열을 관리했다.

추가 개선에서는 `typealias Members = Array<Array<String>>`로 긴 타입에 별칭을 지정하고   
`NAME`, `EMAIL`, `PHONE` 상수를 이용해 숫자 인덱스의 의미를 명확하게 했다.

`isBlank()`를 이용해 빈 문자열뿐 아니라 공백만 입력한 경우도 검증하고, 이름 조회는 동일한 이름을 가진 회원을 모두 찾도록 변경했다.

전체 조회에서는 `take(memberCnt).sortedBy { it[NAME] }`을 사용해 현재 저장된 회원만 이름순으로 정렬했다.

여기서 `it`은 람다의 매개변수가 하나일 때 현재 처리 중인 값을 나타내는 기본 이름이라는 점을 다시 확인했다.

이메일 조회에는 `contains()`를 사용해 완전 일치뿐 아니라 부분 일치 검색도 가능하도록 확장했다.

## 헷갈렸던 점

`val`로 선언한 배열의 원소를 왜 수정할 수 있는지 헷갈렸다.

`val`은 변수에 저장된 배열의 참조를 다른 객체로 다시 할당할 수 없다는 의미이고, 배열 객체 내부의 원소까지 불변으로 만드는 것은 아니라는 점을 확인했다.

배열과 `listOf`, `mutableListOf`의 차이도 다시 구분했다.

배열은 생성 시 크기가 정해지고 내부 원소는 수정할 수 있지만 크기 자체는 변경되지 않는다.   
`listOf`는 읽기 전용이고 `mutableListOf`는 원소 추가·삭제가 가능하다.

생성자 매개변수에 `val`이나 `var`를 붙이는 이유도 처음에는 헷갈렸다.

단순 매개변수로 선언하면 생성 과정에서만 사용할 수 있지만 `val`이나 `var`를 붙이면 해당 값이 클래스의 프로퍼티가 되어 객체 생성 이후에도 사용할 수 있다.

MSA에서는 `web-service`가 게시판 기능을 사용하면서 왜 `board-service`의 Service를 직접 호출하지 않는지 다시 확인했다.

서로 독립된 애플리케이션으로 실행되기 때문에 코드 내부 메서드 호출이 아니라 `BoardClient`를 통한 HTTP 요청으로 서비스 경계를 넘어야 했다.

자판기 과제에서는 잘못된 숫자 입력에 항상 `-1`을 반환해도 되는지 헷갈렸다.

메뉴에서는 `-1`을 `when`의 `else`로 처리할 수 있지만 금액 계산 함수에서 `-1`을 반환하면 정상 데이터처럼 계산될 수 있어,   
오류 값을 정할 때 그 반환값이 이후 어디에 사용되는지까지 고려해야 했다.

회원관리에서는 2차원 배열에서 실제 회원 수와 배열 전체 크기를 어디까지 반복해야 하는지 헷갈렸다.

배열 전체 크기 `totalCnt`가 아니라 실제 저장된 회원 수인 `memberCnt`까지만 조회해야 비어 있는 데이터를 불필요하게 처리하지 않는다는 점을 확인했다.

## 오늘 느낀 점

Kotlin은 Java와 문법 구조가 비슷한 부분이 많지만 `until`, `withIndex()`, 프로퍼티, 생성자 매개변수의 `val`·`var`처럼   
Kotlin에서 더 간결하게 표현할 수 있는 방식이 많다는 점을 확인했다.

특히 문법 자체를 보는 것보다 자판기와 회원관리 프로그램에 직접 적용하면서 입력값 검증이나 배열 데이터 이동처럼   
실제 로직을 구현할 때 어떤 문법을 사용해야 하는지가 더 잘 이해됐다.

MSA에서는 전날까지 `board-service → auth-service` 데이터 조회 흐름을 봤다면   
오늘은 `web-service → board-service`까지 연결하면서 전체 구조가 더 명확해졌다.

단순히 서비스를 여러 프로젝트로 나누는 것이 아니라 각 서비스의 데이터와 비즈니스 로직은 해당 서비스가 소유하고,   
다른 서비스에서는 공개된 API를 통해서만 사용해야 한다는 서비스 경계를 실제 코드 흐름으로 확인할 수 있었다.

과제에서는 기본 기능을 구현한 뒤 `typealias`, 상수 인덱스, `isBlank()`, 정렬과 부분 검색을 추가하면서   
Kotlin 문법을 단순히 학습하는 것에서 끝나지 않고 기존 코드를 더 읽기 쉽고 사용하기 편하게 개선하는 과정도 연습할 수 있었다.
