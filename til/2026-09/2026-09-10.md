## 오늘 배운 내용

오늘은 Kotlin으로 Spring Boot 게시판 CRUD를 구현하면서 기존 Java 코드와 비교해 Kotlin이 같은 Spring·JPA 코드를 어떻게 더 간결하게 표현하는지 확인했다.

Controller에서는 함수 선언과 expression body, Entity에서는 주 생성자와 `val`, `var`, nullable 타입을 사용했다.   
DTO에서는 `data class`, `companion object`, 함수 참조를 활용했고,   
Service에서는 `findByIdOrNull()`, Elvis 연산자, `isNullOrBlank()` 등을 이용해 Java보다 null 처리를 간결하게 작성할 수 있었다.

Spring MVC, Spring Data JPA, 페이징, 트랜잭션과 dirty checking 같은 개념 자체는 Java와 Kotlin에서 동일하며,   
Kotlin 코드 안에 있다고 해서 모두 Kotlin 기능인 것은 아니라는 점도 구분해서 정리했다.

이후 컬렉션 기반 회원 관리 실습을 복습하면서 `indexOfFirst`, `any`, `filter`, `groupBy`, `sortedBy` 등 Kotlin 컬렉션 함수를 활용해   
기존 반복문 중심 로직을 더 간결하게 표현하는 방법을 확인했다.

## 실습 및 과제

> Kotlin Spring Boot 게시판 CRUD 실습

Controller, Entity, Repository, DTO, Service 구조로 게시판 CRUD를 구현했다.

Java의 `public String method()` 형태는 Kotlin에서 `fun method(): String`으로 표현하며,   
단순 반환 함수는 expression body를 이용해 더 짧게 작성할 수 있었다.   
Kotlin은 `public`이 기본값이고 타입도 `Long id`가 아니라 `id: Long` 형태로 선언한다는 차이를 다시 확인했다.

Entity에서는 주 생성자로 프로퍼티 선언과 생성자를 함께 표현했다.   
JPA 저장 전에는 id가 존재하지 않을 수 있으므로 `Long?`처럼 nullable 타입을 사용하고,   
Kotlin에서는 Java와 달리 null 가능 여부를 타입 단계에서 명확하게 구분한다는 점을 확인했다.

DTO에서는 `data class`를 사용해 반복 코드를 줄이고, `companion object`에 Entity를 DTO로 변환하는 `from()` 함수를 작성했다.

`page.content.map(BoardListItemResponse::from)`에서는 `Page<Board>` 안의 현재 페이지 데이터인 `content`를 DTO 목록으로 변환했다.   
`::from`은 함수를 바로 실행하는 것이 아니라 함수 자체를 `map`에 전달하는 함수 참조라는 점도 정리했다.

Repository의 `findByTitleContaining`, `Pageable`, `Page<Board>`는 Kotlin 기능이 아니라 Spring Data JPA에서 제공하는 기능이라는 점도 확인했다.

Service에서는 Java에서 `Optional`을 사용하는 흐름 대신 `findByIdOrNull()`로 `Board?`를 받고, Elvis 연산자로 null인 경우를 처리했다.   
`keyword.isNullOrBlank()`처럼 Kotlin에서 제공하는 null 관련 함수도 활용했다.

수정 로직에서는 트랜잭션 안에서 조회한 Entity가 영속 상태이므로 `board.update()`로 값을 변경하면   
트랜잭션 종료 시 dirty checking을 통해 UPDATE가 발생한다는 흐름을 다시 확인했다.

> Java와 Kotlin 비교 정리

Spring MVC, Spring Data JPA, 트랜잭션과 같은 Spring·JPA 개념은 Java와 Kotlin에서 동일하게 사용할 수 있지만,   
Kotlin은 nullable 타입, 주 생성자, `data class`, Elvis 연산자, 함수 참조 등을 통해 같은 로직을 더 간결하게 표현할 수 있었다.

특히 null 가능성을 타입 단계에서 구분하고 반복 코드를 줄일 수 있다는 점이 Java와 비교했을 때 Kotlin의 장점으로 느껴졌다.

반면 Java는 기존 서비스와 라이브러리, 개발 인력과 운영 경험이 오래 축적되어 있어 기업에서 여전히 많이 사용되고 있다.   
Kotlin은 기존 JVM·Spring 생태계를 그대로 활용할 수 있어 Java를 완전히 대체하기보다 기존 프로젝트에 점진적으로 도입하기 좋은 언어라는 점도 확인했다.

> Kotlin 컬렉션 기반 회원 관리 실습

기존 배열 중심 회원 관리 코드를 Kotlin 컬렉션 함수를 활용하는 방식으로 다시 구현했다.

`indexOfFirst`로 조건에 맞는 회원의 위치를 찾고, `any`로 중복 여부를 검사했으며, `filter`로 조건에 맞는 여러 회원을 조회했다.

또한 `sortedBy`로 이름순 정렬을 하고, `groupBy`와 `substringAfter`를 이용해 이메일 도메인별로 회원을 그룹화하는 흐름을 확인했다.

기존처럼 반복문과 인덱스를 직접 관리하는 방식보다 컬렉션 함수를 사용하면 코드가 짧아질 뿐 아니라   
검색, 검사, 정렬, 그룹화 등 수행하려는 동작이 코드에 더 직접적으로 드러난다는 점을 복습했다.

## 헷갈렸던 점

Kotlin으로 Spring Boot 코드를 작성하면서 어떤 기능이 Kotlin 문법이고 어떤 기능이 Spring에서 제공되는 것인지 헷갈렸다.

`data class`, nullable 타입, Elvis 연산자, 함수 참조 등은 Kotlin 기능이지만   
`findByTitleContaining`, `Pageable`, `Page<Board>`, dirty checking 등은 Spring Data JPA와 JPA에서 제공되는 개념이라는 점을 구분했다.

`Page<Board>`와 `page.content`의 관계도 다시 확인했다.

`Page<Board>`는 현재 페이지 데이터뿐 아니라 전체 개수와 페이지 정보까지 가지고 있고, `content`가 실제 현재 페이지의 `List<Board>`다.   
따라서 `page.content.map(...)`은 페이징을 하는 과정이 아니라 이미 조회된 현재 페이지 데이터를 DTO로 변환하는 과정이다.

`BoardListItemResponse::from`의 `::`은 `map { board -> BoardListItemResponse.from(board) }`에서 사용하는 함수를 직접 참조해   
전달하는 표현이라는 점을 확인했다.

dirty checking의 의미도 다시 정리했다.   
수정을 막거나 수정 여부를 검증하는 기능이 아니라, 트랜잭션 안에서 영속 Entity의 변경을 감지하고 DB에 UPDATE를 반영하는 기능이다.

## 오늘 느낀 점

오늘은 Java에서 이미 학습한 Spring Boot와 JPA 구조를 Kotlin으로 다시 구현하면서 두 언어의 차이를 비교해보는 것이 도움이 됐다.

Controller, Service, Repository, Entity와 같은 Spring 구조나 JPA 동작 자체는 거의 동일했지만,   
Kotlin에서는 주 생성자, nullable 타입, `data class`, Elvis 연산자 등을 이용해 같은 로직을 더 간결하게 표현할 수 있었다.

특히 Kotlin 코드 안에 등장한다고 해서 모두 Kotlin 기능이라고 생각하기보다 언어 기능과 Spring·JPA 기능을 구분해서 보는 것이 중요하다는 점을 느꼈다.   
Java에서 이미 알고 있는 개념은 그대로 연결하고, 그 위에서 Kotlin이 어떤 표현을 제공하는지를 비교하는 방식이 이해하기 더 쉬웠다.

컬렉션 기반 회원 관리도 다시 복습하면서 Kotlin의 간결함은 단순히 코드 줄 수를 줄이는 것이 아니라   
`filter`, `any`, `groupBy`처럼 코드 자체가 수행하려는 목적을 더 명확하게 표현할 수 있다는 데 있다는 점을 확인했다.
