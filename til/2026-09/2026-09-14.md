## 오늘 배운 내용

오늘은 결제 보상 재처리 흐름을 다시 정리한 뒤, 실제 주문·결제 상태를 조회해 AI가 CS 대응 내용을 생성하는 자동화 Workflow를 구현했다.

먼저 고객이 `orderId`와 문의 내용만 입력하면 서버에서 실제 `Payment`와 `Purchase` 상태를 조회할 수 있도록 내부 CS 조회 API를 추가했다.   
사용자 JWT를 자동화 시스템에서 재사용하는 대신 n8n과 Gudit 서버 사이의 인증을 분리해 `X-INTERNAL-KEY` 기반 내부 API Key 인증을 적용했다.

이후 n8n의 Form Trigger에서 고객 문의를 받고, 내부 API로 실제 주문 상태를 조회한 뒤 Claude CLI에 전달하도록 구성했다.   
Claude 결과는 CS 처리에 필요한 JSON 형태로 제한하고, 이후 Slack으로 전달할 수 있도록 각 필드로 분리했다.

## 실습 및 과제

> 결제 보상 재처리 흐름 정리

Redis Streams Consumer는 정상 처리한 메시지만 ACK하고,   
처리 중 실패하면 Pending Entries에 남겨 이후 다시 재처리하도록 구성되어 있다.

결제 보상에서는 재전달에 따른 중복 처리를 막기 위해 재고 복구와 다른 전략을 사용한다.

재고 복구는 Redis Lua Script에서 `eventId` 확인과 실제 Redis 변경을 원자적으로 처리하지만,   
결제 보상은 Toss의 `Idempotency-Key`, 실제 결제 상태 재조회, 내부 `Payment` 상태 검증을 조합해 멱등성을 보장한다.

Inbox는 중복 이벤트 자체를 식별할 수 있지만 Toss API 호출과 Inbox 저장을 하나의 Transaction으로 묶을 수 없기 때문에   
현재 결제 보상에는 필수적으로 적용하지 않는 방향을 유지했다.

> CS 상태 조회 내부 API 구현

고객이 입력한 `orderId`를 기준으로 실제 결제와 구매 상태를 조회할 수 있도록   
`PaymentCsStatusResponse`와 `getCsStatus(orderId)`를 추가했다.

자동화 시스템 전용 API는 다음과 같이 일반 사용자 API와 분리했다.

`/api/internal/payments/{orderId}/cs-status`

처음에는 기존 ADMIN Access Token을 n8n에서 전달하는 방식을 검토했지만,   
사용자 인증 토큰을 서비스 간 통신에 재사용하는 것보다 내부 자동화용 인증을 별도로 두는 것이 적절하다고 판단했다.

이에 따라 `X-INTERNAL-KEY`를 검사하는 `InternalApiKeyFilter`를 추가하고, API Key는 `INTERNAL_API_KEY` 환경변수로 관리하도록 했다.

내부 API Key가 없거나 잘못된 경우 `401 AUTH_008`, 존재하지 않는 주문이면 `404 PAYMENT_001`,   
정상 주문이면 `200`으로 `orderId`, `purchaseId`, `purchaseStatus`, `paymentStatus`, `amount`가 반환되는 것을 직접 확인했다.

> Spring Security Filter 구성 확인

내부 API 인증 Filter를 추가하면서 커스텀 Filter 간 등록 순서 문제를 확인했다.

다른 커스텀 Filter를 기준으로 `addFilterBefore()`를 등록하면   
Spring Security가 기준 Filter의 order를 판단하지 못해 실행에 실패할 수 있었다.

따라서 `InternalApiKeyFilter`와 `TokenAuthenticationFilter`를   
모두 `UsernamePasswordAuthenticationFilter` 앞에 등록하도록 수정했다.

또한 `/api/internal/**` 요청은 내부 API Key로 인증하므로   
일반 JWT 인증이 다시 수행되지 않도록 `TokenAuthenticationFilter`에서 해당 경로를 제외했다.

> n8n과 Spring Boot 연동

n8n은 WSL Ubuntu에서 실행되고 Spring Boot는 Windows에서 실행되고 있어   
n8n의 `localhost:8080`이 Windows의 Spring Boot를 가리키지 않는다는 점을 확인했다.

WSL에서 접근 가능한 Windows Host 주소를 사용해 n8n HTTP Request와 내부 CS API를 연결했다.

n8n에서는 Form Trigger로 `orderId`와 고객 문의 내용을 받고, HTTP Request를 통해 실제 주문·결제 상태를 조회하도록 구성했다.

이를 통해 사용자가 입력한 내용만 AI에 전달하는 것이 아니라 서버의 실제 상태를 함께 조회한 뒤 분석에 활용하도록 했다.

> Claude CLI 기반 CS 분석 자동화

Claude CLI는 n8n과 동일한 WSL 환경에 설치하고 `claude -p`를 이용한 비대화형 실행이 정상 동작하는 것을 확인했다.

n8n의 `Execute Command`에서 Expression을 Shell command에 직접 넣었을 때   
`$()`, `${}`, backtick 등이 Shell의 명령 치환이나 변수 치환으로 해석되는 문제가 발생했다.

이를 해결하기 위해 `Edit Fields` 노드에서 고객 문의와 주문 상태를 하나의 `prompt` 문자열로 먼저 완성하고,   
해당 문자열을 stdin으로 전달해 Claude가 읽도록 변경했다.

이 방식으로 Shell quoting 문제를 줄이고 고객 입력이 Shell 명령으로 해석되는 위험도 피할 수 있었다.

Claude에는 파일 수정, 명령 실행, 외부 API 호출, 결제 취소·환불, DB 변경 등을 수행하지 않고 제공된 정보만 분석하도록 제한했다.

응답은 `category`, `currentState`, `assessment`, `recommendedAction`, `customerReplyDraft`를 가진 JSON 객체로 반환하도록 하고,   
Markdown 코드블록 없이 순수 JSON만 출력하도록 프롬프트를 구성했다.

마지막으로 n8n Code 노드에서 Claude의 stdout을 `JSON.parse()`해 실제 필드로 분리했고,   
이후 Slack CS 채널로 전달할 수 있는 형태까지 구성했다.

## 헷갈렸던 점

n8n에서 기존 ADMIN Access Token을 사용해 내부 API를 호출해도 되는지 고민했다.

하지만 ADMIN Token은 사용자 인증·인가를 위한 토큰이고,   
n8n은 별도의 내부 시스템이므로 두 시스템 간 인증 목적에 맞는 `X-INTERNAL-KEY`를 별도로 두는 것이 더 적절하다고 정리했다.

WSL에서 실행한 n8n의 `localhost`가 Windows의 Spring Boot에 접근하지 못하는 이유도 처음에는 헷갈렸다.

WSL과 Windows는 실행 환경이 분리되어 있기 때문에 WSL의 `localhost`는 WSL 자신을 의미하며,   
Windows에서 실행 중인 서버에는 별도의 Host 주소를 이용해 접근해야 한다는 점을 확인했다.

또한 n8n Expression을 Shell command에 그대로 넣으면 왜 오류가 발생하는지도 확인했다.

Shell에서는 `$()`, `${}`, backtick 등이 특별한 의미를 가지기 때문에   
사용자 입력이나 JSON을 명령 문자열에 직접 섞으면 의도하지 않은 치환이 발생할 수 있었다.   
Prompt를 먼저 문자열로 만든 뒤 stdin을 통해 전달하는 방식이 더 안전하다는 점을 정리했다.

## 오늘 느낀 점

오늘은 기존에 구현한 결제 보상 재처리 구조를 실제 운영 업무와 연결해보는 과정이 의미 있었다.

단순히 AI에게 고객 문의를 보내는 것이 아니라 서버에서 실제 주문·결제 상태를 조회하고,   
그 정보를 기준으로 AI가 판단하도록 구성하면서 자동화에서도 실제 데이터와 권한 경계를 명확하게 두는 것이 중요하다는 점을 느꼈다.

특히 사용자 JWT를 그대로 재사용하기보다 내부 시스템 간 인증을 별도로 분리하고,   
Claude에도 조회된 정보를 분석하는 역할만 주도록 제한하면서 자동화 범위를 명확하게 설정하는 것이 필요했다.

n8n을 직접 연결하면서는 애플리케이션 코드뿐 아니라 WSL·Windows 네트워크, Shell quoting, 외부 CLI 실행 등 여러 실행 환경을 함께 이해해야   
전체 Workflow가 정상적으로 동작한다는 점도 확인했다.
