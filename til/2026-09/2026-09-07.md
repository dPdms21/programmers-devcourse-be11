## 오늘 배운 내용

오늘은 MSA에서 OAuth2 인증 흐름을 확장하고, 여러 서비스의 데이터를 함께 처리해야 하는 회원 탈퇴에 Orchestration Saga 패턴을 적용했다.

`auth-service`와 `board-service`가 서로 다른 DB를 사용하기 때문에 하나의 `@Transactional`로 전체 탈퇴 과정을 처리할 수 없었다.   
사용자 상태를 `WITHDRAWING`으로 변경한 뒤 board-service의 데이터를 삭제하고,   
성공하면 `WITHDRAWN`, 실패하면 `ACTIVE`로 복구하는 방식으로 흐름을 구성했다.

또한 Saga 도중 서비스가 종료되어 `WITHDRAWING` 상태가 남을 수 있으므로 Scheduler를 통해 중간 상태를 다시 확인하고 복구하는 방식도 적용했다.   
소프트 딜리트에서는 상태를 변경하는 것뿐 아니라 이후 로그인과 OAuth2 인증에서도 사용자 상태를 함께 검증해야 한다는 점을 확인했다.

커리어 정리에서는 Gudit의 구매·결제 담당 경험과 동시성 문제 해결 과정을 Fact & Lesson과 STAR 방식으로 정리했다.   
특히 결제 승인과 구매 취소 경쟁에서 발생한 Deadlock을 재현하고 락 획득 순서를 원인으로 찾아 개선한 경험을 대표적인 문제 해결 사례로 정리했다.

## 실습 및 과제

> MSA OAuth2 인증 흐름 확장

`CustomOAuth2UserService`를 통해 OAuth Provider의 사용자 정보를 조회하고 기존 회원과 신규 회원의 로그인 흐름을 구분했다.

기존 회원은 프로필을 갱신한 뒤 로그인 처리하고, 신규 회원은 `signupToken`을 이용한 별도 가입 흐름으로 연결했다.

일반 로그인과 OAuth2 로그인 모두 `UserStatus.ACTIVE` 여부를 확인하도록 해 탈퇴한 사용자가 다시 로그인하지 못하도록 보완했다.

> Orchestration Saga 기반 회원 탈퇴

회원 탈퇴는 `auth-service`와 `board-service`의 DB를 함께 변경해야 하므로 하나의 로컬 트랜잭션으로 묶을 수 없었다.

`UserService.withdraw()`가 전체 흐름을 조정하도록 하고 다음과 같이 처리했다.

`ACTIVE → WITHDRAWING → board-service 데이터 삭제 → WITHDRAWN`

board-service 처리에 실패하면 사용자 상태를 다시 `ACTIVE`로 변경하는 보상 처리를 적용했다.

Saga는 특정 어노테이션을 사용하는 기능이 아니라   
각 서비스의 로컬 트랜잭션과 중간 상태, 호출 순서, 실패 시 보상 방법을 직접 설계하는 패턴이라는 점을 확인했다.

전체 흐름에는 `@Transactional(propagation = Propagation.NOT_SUPPORTED)`를 적용해   
하나의 트랜잭션으로 묶지 않고 각 작업이 독립적으로 처리되도록 했다.

> Saga 중간 상태 복구

Saga 실행 중 auth-service가 종료되면 사용자가 `WITHDRAWING` 상태에 남을 수 있다.

`WithdrawRecoverScheduler`가 일정 시간 이상 해당 상태에 머무른 사용자를 찾아   
board-service의 삭제 작업을 다시 수행하고 `WITHDRAWN` 상태로 마무리하도록 구성했다.

복구 건수와 성공·실패 로그는 단순 HTTP 요청 로그가 아니라 실제 회원 탈퇴 상태를 나타내는 정보이므로   
공통 AOP 로그가 아닌 Scheduler 내부에서 직접 기록하도록 했다.

> 트랜잭션 설정으로 인한 삭제 미반영

회원 탈퇴 테스트 중 게시글과 댓글이 실제로 삭제되지 않는 문제가 발생했다.

`BoardService`가 클래스 수준에서 `@Transactional(readOnly = true)`를 사용하고 있었지만   
데이터 변경 메서드에는 별도의 쓰기용 `@Transactional`이 없었다.

`updateBoard()`, `deleteBoard()`, `deleteUserContents()`에 쓰기 트랜잭션을 적용해 실제 DB 변경이 반영되도록 수정했다.

클래스 수준에서 조회 전용 트랜잭션을 기본으로 사용할 경우 변경 작업에는 메서드 수준의 트랜잭션을 별도로 선언해야 한다는 점을 다시 확인했다.

> 소프트 딜리트와 로그인 상태 검증

회원 탈퇴 후에도 기존 계정으로 로그인이 가능한 문제를 확인했다.

회원 row를 실제로 삭제하지 않고 `WITHDRAWN` 상태로 변경하는 구조이므로   
로그인 과정에서 상태를 검사하지 않으면 기존 사용자 정보가 그대로 조회될 수 있었다.

소프트 딜리트를 사용하면 탈퇴 처리 자체뿐 아니라   
로그인, OAuth2 인증, 재가입과 기존 토큰 사용 등 이후 사용자 흐름에서도 상태 검증 정책이 함께 필요하다는 점을 확인했다.

> Gudit Fact & Lesson 작성

Gudit에서 담당한 구매·결제 기능, Toss Payments 연동, 결제·취소·Timeout 동시성 제어와 k6 검증 경험을 자소서와 면접에 활용할 수 있도록 정리했다.

특히 결제 승인과 구매 취소가 동시에 발생했을 때 PostgreSQL Deadlock을 재현하고,   
`Payment`와 `Purchase`의 락 획득 순서 차이를 원인으로 찾아 순서를 통일한 뒤 같은 조건에서 다시 검증한 경험을 대표 문제 해결 사례로 정리했다.

단순히 비관적 락을 적용했다는 사실보다 경쟁 상황을 재현하고 원인을 좁힌 뒤 최종 데이터 상태와 개선 결과를 다시 검증한 과정이 중요하다는 점을 확인했다.

Redis·RDB·외부 결제 시스템을 하나의 트랜잭션으로 묶기 어렵다는 한계도 함께 정리하고,   
이후 Outbox·MQ·Inbox와 모니터링을 통한 재처리·복구 방향까지 연결했다.

## 헷갈렸던 점

Saga는 여러 서비스의 로컬 트랜잭션을 하나의 비즈니스 흐름으로 조정하는 설계 패턴이며,   
중간 상태와 호출 순서, 실패 시 보상 로직을 직접 구성해야 한다는 점을 확인했다.

회원 탈퇴 전체를 하나의 `@Transactional`로 처리할 수 없는 이유도 다시 정리했다.

`auth-service`와 `board-service`는 서로 다른 DB를 사용하므로 한 서비스의 로컬 트랜잭션이 다른 서비스의 데이터 변경까지 롤백할 수 없다.

또한 탈퇴 후 게시글과 댓글이 남아 있던 원인이 Saga 자체가 아니라 `BoardService`의 `readOnly` 트랜잭션 설정이었다는 점을 확인하면서,   
분산 처리 문제에서는 서비스 간 호출뿐 아니라 각 서비스 내부의 로컬 트랜잭션이 정상적으로 수행됐는지도 함께 확인해야 한다는 점을 알게 됐다.

## 오늘 느낀 점

오늘 실습에서는 서비스를 분리하는 것보다   
여러 서비스에 걸친 하나의 기능이 중간에 실패했을 때 상태를 어떻게 유지하고 다시 복구할지가 더 어려운 문제라는 점을 느꼈다.

회원 탈퇴에서는 하나의 트랜잭션으로 모든 처리를 묶을 수 없기 때문에 중간 상태와 보상 처리, Scheduler를 통한 복구까지 함께 설계해야 했다.   
이전 Gudit에서 Redis·RDB·외부 결제 시스템 사이의 정합성을 고민했던 경험과도 비슷한 문제라고 느꼈다.

Gudit 경험을 다시 정리하면서도 어떤 기술을 사용했는지보다 문제를 어떻게 재현하고 원인을 좁혔는지,   
왜 해당 방법을 선택했으며 결과를 어떻게 검증했는지가 문제 해결 경험을 설명하는 데 더 중요하다는 점을 다시 확인했다.
