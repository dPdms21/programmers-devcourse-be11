## 오늘 배운 내용

오늘은 Kotlin의 지연 초기화와 위임부터 컬렉션, `data class`, 컬렉션 활용 함수까지 실습했다.

`lateinit`은 `var` 값을 나중에 직접 초기화하고, `by lazy`는 `val`을 처음 사용하는 순간 한 번 계산한다는 차이를 확인했다.   
`Delegates.observable`, `vetoable`과 클래스 위임을 통해 `by`가 프로퍼티의 동작이나 인터페이스 구현을 다른 객체에 맡길 때 사용될 수 있다는 점도 학습했다.

컬렉션에서는 `List`, `Set`, `Map`의 특성과 Mutable 타입을 구분하고, `filter`, `map`, `groupBy`, `sortedBy` 등 다양한 컬렉션 함수를 실습했다.   
`data class`가 값 비교에 필요한 `equals()`와 `hashCode()` 등을 자동 생성하고, Kotlin의 `==`와 `===`가 각각 값과 참조를 비교한다는 차이도 정리했다.

회원 관리4 과제에서는 배열 대신 `MutableList`를 사용하고 `data class Member`와 컬렉션 함수를 적용했다.   
이후 저장 기능을 `MemberStorage`로 추상화해 `ListMemberStorage`와 `MapMemberStorage`를 교체하면서   
자료구조에 따라 조회와 수정 방식이 어떻게 달라지는지도 확인했다.

## 실습 및 과제

> Kotlin 지연 초기화와 위임 실습

`lateinit`은 생성 시점에는 값을 알 수 없지만 이후 직접 값을 넣어야 하는 `var` 프로퍼티에 사용한다.

`by lazy`는 값이 처음 필요할 때 초기화 블록을 한 번 실행하고 이후에는 계산된 값을 재사용한다.

`Delegates.observable`은 값의 변경 전후를 관찰하고, `Delegates.vetoable`은 새로운 값을 실제로 적용할지를 반환값으로 결정한다.

클래스에서도 `Interface by origin` 형태로 인터페이스 구현을 다른 객체에 위임하고 필요한 기능만 직접 재정의할 수 있다는 점을 확인했다.

> Kotlin 회원 관리 실습

추상 클래스와 인터페이스를 적용한 회원 관리 예제를 다시 확인했다.

공통 상태와 기본 구현을 함께 공유할 필요가 있을 때는 추상 클래스를,   
공통 기능의 계약과 여러 구현체가 필요할 때는 인터페이스를 활용할 수 있다는 차이를 회원 관리 구조와 연결해서 복습했다.

> Kotlin 컬렉션과 data class 실습

`List`는 순서와 인덱스를 가지고, `Set`은 중복을 허용하지 않으며, `Map`은 Key를 기준으로 값을 관리한다.

읽기 전용 `List`가 객체 자체의 완전한 불변을 의미하지는 않는다는 점도 확인했다.

`data class`는 주 생성자의 프로퍼티를 기준으로 `equals()`, `hashCode()`, `toString()`, `copy()` 등을 자동 생성한다.

Kotlin의 `==`는 `equals()`를 이용한 값 비교이고 `===`는 같은 객체인지 확인하는 참조 비교라는 차이를 정리했다.

Set이나 Map의 Key로 사용하는 객체는 `equals()`와 `hashCode()`가 중요하며,   
해시 계산에 사용되는 값을 저장 이후 변경하면 조회에 문제가 생길 수 있다는 점도 확인했다.

> Kotlin 컬렉션 함수 실습

`filter`, `map`, `mapNotNull`, `flatMap`을 이용해 컬렉션을 필터링하거나 다른 형태로 변환하는 방법을 실습했다.

`partition`은 조건에 따라 두 그룹으로 나누고, `groupBy`는 같은 Key의 원소들을 묶으며, `associateBy`는 하나의 Key에 하나의 원소를 연결한다.

`takeWhile`은 조건이 처음 깨지는 순간 순회를 멈추지만 `filter`는 전체 원소를 검사한다는 차이도 확인했다.

람다의 `it`은 매개변수가 하나일 때 생략된 람다 매개변수의 기본 이름이라는 점도 다시 정리했다.

> 컬렉션 기반 회원 관리 과제

기존 배열 기반 회원 관리 구조를 `MutableList<Member>`로 변경하고, `Member`를 `data class`로 정의했다.

회원 수는 별도 변수 대신 `members.size`로 계산하고, 조회·검색·삭제에는 `find`, `filter`, `any`, `removeAll` 등의 컬렉션 함수를 사용했다.

회원 수정 시에는 `Member`의 프로퍼티를 `val`로 두고 기존 객체를 직접 변경하는 대신 `copy()`로 새 객체를 생성해 교체했다.   
이름 조회는 `find`가 첫 번째 결과만 반환하므로 동명이인을 모두 찾을 때는 `filter`를 사용했다.

이후 저장 기능을 `MemberStorage` 인터페이스로 분리하고 `ListMemberStorage`, `MapMemberStorage`를 구현했다.

`ListMemberStorage`는 값을 순회해 회원을 찾지만,   
`MapMemberStorage`는 이메일을 Key로 사용해 `members[email]`, `containsKey()`, `remove(email)`처럼 직접 처리할 수 있었다.

반면 이름 검색이나 통계처럼 이메일 Key를 활용할 수 없는 기능은 `members.values`를 다시 탐색해야 했고,   
이메일 수정 시에는 기존 Key를 제거한 뒤 변경된 이메일을 새 Key로 다시 저장해야 했다.

이를 통해 컬렉션은 단순히 문법 차이로 선택하는 것이 아니라 어떤 값을 기준으로 조회·중복 검사·수정을 많이 하는지에 따라 적합한 자료구조가 달라진다는 점을 확인했다.

## 헷갈렸던 점

`it`은 람다의 매개변수가 하나일 때 그 매개변수 이름을 생략하면 사용하는 기본 이름이며, `filter { it.score >= 80 }`에서는 현재 검사 중인 원소 하나를 의미한다.

Kotlin의 `==`와 `===`의 차이도 다시 확인했다.

`==`는 `equals()`를 통한 값 비교이고 `===`는 두 변수가 같은 객체를 참조하는지 비교한다.   
특히 `data class`는 프로퍼티를 기준으로 `equals()`를 자동 생성하므로 서로 다른 객체라도 값이 같으면 `==`가 `true`가 될 수 있다.

회원 수정에서 이메일 중복 검사를 항상 하지 않고 새 이메일이 기존 이메일과 다를 때만 수행하는 조건도 처음에는 헷갈렸다.

이메일을 변경하지 않고 이름이나 연락처만 수정할 수도 있기 때문에 실제로 이메일이 변경되는 경우에만 다른 회원과 중복되는지를 검사해야 한다는 점을 확인했다.

`List<Member>`와 `Member?`의 조회 실패 처리 방식도 구분했다.

단일 회원 조회는 찾지 못하면 `null`이 될 수 있지만   
여러 회원을 반환하는 `filter` 결과는 회원이 없어도 빈 리스트가 반환되므로 각각 null 검사와 `isEmpty()`를 사용해야 한다.

## 오늘 느낀 점

오늘은 Kotlin의 컬렉션 문법 자체보다 같은 회원 관리 기능을 배열, List, Map으로 구현했을 때 코드와 처리 방식이 어떻게 달라지는지가 더 중요하게 느껴졌다.

특히 이메일처럼 고유한 값을 Key로 활용하면 Map에서 조회와 중복 검사가 단순해지지만,   
이름 검색처럼 Key를 이용할 수 없는 기능에서는 다시 전체 값을 탐색해야 했다.   
자료구조마다 모든 기능이 좋아지는 것이 아니라 서비스에서 자주 수행하는 연산을 기준으로 선택해야 한다는 점을 이해할 수 있었다.

또한 `data class`, `copy()`, 컬렉션 함수들을 실제 회원 관리 코드에 적용하면서 Kotlin이 제공하는 기능을 단순히 문법으로 외우는 것보다   
기존 반복문과 배열 코드를 어떤 방식으로 줄이고 의미를 명확하게 만들 수 있는지 연결해서 보는 것이 도움이 됐다.

Repoary 주간보고를 정리하면서는 3주차에 TIL 기능의 전체 사용자 흐름을 완성했고,   
남은 MVP 기능도 README 생성과 누락 점검으로 구체화되어 다음 구현 범위가 더 명확해졌다.
