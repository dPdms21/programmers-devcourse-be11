## 오늘 배운 내용

오늘은 기존 추상 클래스 기반 회원 관리 과제를 확장하고, 인터페이스와 위임을 이용해 회원 저장 구조를 분리하는 방법을 학습했다.

회원 관리2에서는 입력 검증과 학생 등급, VIP 승급 기능을 추가하면서 추상 클래스와 다형성 구조를 복습했다.   
특히 등급별 월회비 계산은 부모 클래스에 공통화하고 자식 클래스에서는 할인율만 다르게 정의하는 방식으로 정리했다.

회원 관리3에서는 회원 저장 기능을 `MemberStorage` 인터페이스로 분리하고 `ArrayMemberStorage`가 실제 저장 기능을 구현하도록 구성했다.   
`MemberApp`은 구체 구현체가 아니라 인터페이스에만 의존하도록 하고,   
`by`를 이용한 위임으로 기존 저장 기능을 유지하면서 필요한 기능만 선택적으로 재정의하는 구조를 확인했다.

이후 여러 저장소 구현체와 로깅·호출 횟수 측정 기능을 추가하면서,   
동일한 인터페이스를 구현하는 객체를 교체하거나 조합해 기능을 확장할 수 있다는 점도 확인했다.

## 실습 및 과제

> 회원 관리2 - 입력 검증과 회원 등급 기능 확장

기존 추상 클래스 기반 회원 관리에 입력 검증과 회원 등급 관련 기능을 추가했다.

회원 추가·수정 시 `isBlank()`를 사용해 빈 값 입력을 막고, 수정 로직은 `MemberManager.update()`에서 처리하도록 변경했다.

기존 `NormalMember`, `VipMember`에 `StudentMember`를 추가하고,   
등급별 월회비는 각 클래스에서 금액을 직접 계산하는 대신 부모 `Member`가 공통 계산을 담당하고 자식 클래스는 `discountRate`만 재정의하도록 구성했다.

VIP 승급 기능에서는 객체의 프로퍼티를 변경하는 것만으로 실제 객체 타입이 바뀌지는 않는다는 점을 확인했다.   
일반·학생 회원을 VIP로 변경하려면 새로운 `VipMember` 객체를 생성해 기존 배열 위치에 교체해야 했다.

> 회원 관리3 - 인터페이스와 위임 기반 기본 기능 구현

회원 저장 기능을 `MemberStorage` 인터페이스로 분리하고, `ArrayMemberStorage`가 배열 기반 저장 기능을 구현하도록 구성했다.

인터페이스에는 `memberCnt`, `isFull`과 회원 추가·조회·삭제·전체 조회처럼 저장 방식과 관계없이 필요한 기능을 정의하고,   
`findIndex()`처럼 배열 구현에만 필요한 기능은 구현 클래스 내부에 두었다.

`MemberApp`은 `ArrayMemberStorage`가 아니라 `MemberStorage` 타입을 전달받도록 변경했다.

이를 통해 실제 저장 방식이 달라져도 `MemberApp`은 같은 인터페이스만 사용하면 되므로 애플리케이션 로직과 저장 구현을 분리할 수 있었다.

`MemberStorage`에서 `memberCnt`를 `val`로 정의해 외부에는 읽기만 허용하면서,   
실제 구현체에서는 `override var`와 `private set`을 이용해 내부적으로 값을 변경할 수 있도록 했다.

`isEmpty()`처럼 모든 저장소가 동일하게 사용할 기능은 인터페이스에 기본 구현을 둘 수 있다는 점도 확인했다.

Kotlin의 위임은 `MemberStorage by origin` 형태로 적용했다.

`LoggingMemberStorage`가 실제 저장소 객체를 전달받고, 직접 재정의하지 않은 기능은 `origin`에 넘기도록 했다.   
이를 통해 인터페이스의 모든 기능을 다시 구현하지 않고 로그가 필요한 기능만 `override`할 수 있었다.

> 회원 관리3 - 저장소 구현체와 위임 기능 확장

기본 저장 구조를 바탕으로 다른 구현체와 위임 기능을 추가했다.

실제 데이터를 저장하지 않는 `EmptyMemberStorage`를 만들어 `MemberApp`을 변경하지 않고도 저장소 구현체만 교체할 수 있음을 확인했다.

`CountingMemberStorage`도 위임을 이용해 기존 저장 기능은 그대로 사용하면서 `add()`, `delete()` 호출 횟수만 별도로 기록하도록 구성했다.

`LoggingMemberStorage(CountingMemberStorage(ArrayMemberStorage(...)))`처럼 여러 구현체를 중첩하면   
각각의 역할을 유지하면서 로깅과 호출 횟수 측정 같은 기능을 조합할 수 있었다.

또한 `capacity`처럼 `MemberApp`에서 공통으로 필요한 정보는 특정 구현체를 직접 확인해 가져오기보다   
`MemberStorage` 인터페이스의 계약으로 제공하는 것이 구현체 의존성을 줄이는 데 적절하다는 점을 확인했다.

## 헷갈렸던 점

회원 관리2에서 회원의 등급을 변경하면 실제 객체 타입도 함께 바뀌는지 헷갈렸다.

객체의 프로퍼티 변경과 실제 타입 변경은 별개이므로 `NormalMember`나 `StudentMember`를 VIP로 승급하려면   
새로운 `VipMember` 객체를 만들어 교체해야 한다는 점을 확인했다.

`MemberStorage`에서는 `memberCnt`를 `val`로 선언했는데 구현체에서는 `var`로 사용할 수 있는 이유도 확인했다.

인터페이스에서는 외부에 setter를 제공하지 않는 계약만 정의하고,   
구현체 내부에서는 `var`와 `private set`을 이용해 값을 변경하면서 외부에는 읽기 전용으로 제공할 수 있다.

Kotlin의 `by`도 처음에는 상속과 비슷하게 느껴졌다.

상속은 부모 클래스의 구조와 구현을 물려받는 방식이고,   
위임은 실제 다른 객체에게 인터페이스 기능 실행을 맡기면서 필요한 기능만 현재 객체가 재정의하는 방식이라는 차이를 정리했다.

## 오늘 느낀 점

회원 관리2에서는 기존 추상 클래스 구조에 기능을 추가하면서 공통 동작과 등급별 차이를 어디에 둘지 다시 생각할 수 있었다.

회원 관리3에서는 인터페이스를 단순히 메서드 목록을 분리하는 문법으로 보는 것이 아니라,   
사용하는 코드가 실제 구현체를 몰라도 동작할 수 있도록 계약을 만드는 방식이라는 점을 더 명확하게 이해했다.

특히 `MemberApp`을 수정하지 않고 저장소 구현체를 교체하고,   
위임을 통해 로깅이나 호출 횟수 측정 기능을 조합해보면서 인터페이스와 위임이 각각 구현체 교체와 기능 확장에 어떻게 활용되는지 확인할 수 있었다.
