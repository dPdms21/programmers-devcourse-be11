## 오늘 배운 내용

오늘은 Kotlin의 배열 기반 회원 관리와 상속·다형성을 실습하고, MSA에서는 게시글 첨부파일 처리와 AOP 기반 로깅을 학습했다.

Kotlin에서는 배열 기반 회원 삭제 과정에서 인덱스 범위를 잘못 다루면 `ArrayIndexOutOfBoundsException`이 발생할 수 있다는 점을 다시 확인했다.  
상속과 다형성의 기본 개념은 Java와 유사하지만, Kotlin에서는 클래스와 메서드가 기본적으로 `final`이므로 상속이나 재정의를 허용하려면 `open`을 명시해야 한다.  
타입 확인과 형 변환에는 `is`, `as`, `as?`를 사용한다는 문법 차이도 익혔다.

MSA에서는 게시글 CRUD 자체보다 파일 처리 책임을 `FileService`로 분리하는 구조와,   
`LoggingAspect`를 이용해 Controller의 공통 로깅을 AOP로 처리하는 방식을 확인했다.

Repoary에서는 TIL 생성 기능을 프론트까지 연결해 편집·미리보기·저장·복사 흐름을 완성하고,   
만료된 JWT 처리와 이후 README 행 생성·누락 점검 기능의 정책을 정리했다.

## 실습 및 과제

> Kotlin 배열 기반 회원 관리 실습

배열을 이용한 회원 추가·조회·수정·삭제 흐름을 다시 구현했다.

특히 회원 삭제 시 뒤쪽 데이터를 앞으로 이동하는 과정에서 반복 범위를 잘못 지정하면 배열 범위를 벗어날 수 있어,   
현재 회원 수와 마지막 인덱스를 구분해 처리해야 한다는 점을 확인했다.

어제 회원관리 과제에서도 배열 기반 CRUD를 구현했기 때문에 오늘은 기능 자체보다 반복문 인덱스와 삭제 처리 흐름을 다시 확인하는 데 의미를 두었다.

> Kotlin 상속과 다형성 실습

Kotlin의 상속과 다형성 개념은 Java와 유사하지만 문법에는 차이가 있었다.

클래스와 메서드는 기본적으로 `final`이므로 상속이나 재정의를 허용하려면 `open`을 명시해야 한다.

상속에는 `:`, 재정의에는 `override`, 부모 구현 호출에는 `super`를 사용한다.

모든 클래스의 최상위 타입은 `Any`이며, 타입 확인에는 `is`, 명시적 형 변환에는 `as`, 실패 시 `null`을 반환하는 안전한 형 변환에는 `as?`를 사용한다.

> MSA 게시글 관리와 파일 처리 실습

게시글 작성·조회·수정 흐름에 첨부파일 처리를 연결했다.

파일 관련 로직은 `FileService`로 분리하고, `storeFile()`, `downloadFile()`, `deleteFile()`을 통해 저장·조회·삭제 책임을 별도로 관리했다.

이를 통해 게시글 비즈니스 로직 안에 파일 입출력 코드가 섞이지 않도록 책임을 나누는 구조를 확인했다.

> AOP와 LoggingAspect

여러 Controller에서 반복되는 요청 로깅을 공통 처리하기 위해 AOP를 적용했다.

`@Pointcut`으로 적용 대상을 지정하고, `@Around`에서 `joinPoint.proceed()` 전후로 요청 URI, 파라미터, 처리 시간, 성공·실패 여부를 기록했다.

예외 발생 시 로그만 남기고 종료하지 않고 다시 예외를 던져 기존 예외 처리 흐름을 유지해야 한다는 점도 확인했다.

AOP는 MSA 전용 기술은 아니지만 서비스가 여러 개로 분리된 환경에서 로그 형식과 요청 추적 방식을 일관되게 유지하는 데 유용하다는 점을 이해했다.

> Repoary TIL 편집 및 미리보기 화면 구현

분석 완료 날짜에서 TIL 초안을 생성하고, 이미 TIL이 존재하는 경우에는 중복 생성하지 않고 기존 문서로 이동하도록 흐름을 구분했다.

TIL 편집 화면에서는 Markdown을 직접 수정하면서 실시간 미리보기를 확인하고, 저장 후 다시 접근해도 수정 내용이 유지되도록 연결했다.

Markdown 전체 복사 기능도 추가했다.

단순히 생성 버튼 하나로 처리하기보다 TIL 존재 여부에 따라 생성과 조회를 분리하는 것이 사용자 수정 내용을 보호하는 데 더 적절하다는 점을 확인했다.

> Repoary 인증 상태 처리 개선

`localStorage`에 토큰 문자열이 남아 있다는 이유만으로 로그인 상태를 유지하면 만료된 JWT에서도 화면과 실제 인증 상태가 달라질 수 있었다.

JWT의 `exp`를 확인해 만료된 토큰을 제거하고, 서버 인증 실패 시 access token과 저장소 선택 정보를 함께 정리한 뒤 로그인 화면으로 이동하도록 공통 처리했다.

> Repoary README·누락 점검 정책 정리

README 행은 별도로 저장하지 않고 작성된 TIL을 기준으로 요청 시 생성하도록 정했다.

누락 점검은 완료된 분석 기록이 존재하는 날짜만 대상으로 하고, GitHub의 실제 TIL 파일과 월별 README 행 존재 여부를 확인하는 방식으로 설계했다.

TIL이 없으면 TIL 생성으로, TIL은 있고 README 행만 없으면 README 행 생성으로 연결하도록 사용자 흐름을 정리했다.

## 헷갈렸던 점

Kotlin에서는 Java처럼 모든 클래스와 메서드를 바로 상속·재정의할 수 있을 것으로 생각했지만   
기본적으로 `final`이기 때문에 `open`을 명시해야 한다는 점을 다시 확인했다.

AOP와 Pointcut의 역할도 헷갈렸다.

AOP는 로깅 같은 공통 관심사를 핵심 로직과 분리하는 방식이고, Pointcut은 그 공통 로직을 어디에 적용할지 지정하는 조건이라는 점을 구분했다.

Repoary에서는 README 행을 TIL처럼 별도 저장할지 고민했지만,   
저장된 TIL을 기준으로 필요할 때 생성하는 결과물이므로 별도 상태로 관리하지 않는 방향이 더 단순하다고 판단했다.

MSA도 기존의 서비스 분리와 Feign 호출 구조를 반복해서 정리하기보다, 오늘 새롭게 추가된 파일 처리 책임 분리와 AOP 로깅에 집중하니 학습 내용이 더 명확해졌다.
