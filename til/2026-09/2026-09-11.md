## 오늘 배운 내용

오늘은 2차 Gudit 프로젝트를 기반으로 3차 프로젝트를 시작하며 Kotlin 전환과 추가 개선 방향을 정리했다.

담당인 구매·결제 영역에서는 PostgreSQL의 상태 변경과 Redis 재고 복구를 하나의 트랜잭션으로 묶을 수 없어 발생할 수 있는 정합성 문제를 다시 확인했다.

이를 보완하기 위해 Redis 재고를 즉시 복구하는 대신 재고 복구 요청을 DB에 먼저 기록하는 Transactional Outbox 구조를 적용하기로 했다.

비동기 메시징 방식으로 Kafka와 Redis Streams를 비교한 결과,   
현재 프로젝트에서는 대규모 이벤트 처리보다 이벤트 유실 방지·재처리·중복 처리 방지가 중요하고   
기존 Redis 인프라를 활용할 수 있다는 점에서 Redis Streams를 우선 적용하기로 했다.

첫 단계로 구매 취소 시 `Purchase`, `Payment` 상태 변경과 `STOCK_RESTORE_REQUESTED` Outbox 이벤트 저장을 하나의 DB Transaction에서 처리하고,   
단위 테스트와 실제 DB를 통해 정상 저장되는 것까지 확인했다.

## 실습 및 과제

> Gudit 3차 프로젝트 기획 및 개선 방향 정리

2차 프로젝트를 기반으로 3차에서는 Kotlin 전환을 주요 목표로 두고,   
MSA는 모든 기능을 무조건 분리하기보다 필요성과 구현 비용을 고려해 적용 범위를 결정하기로 했다.

각자 기존 프로젝트에서 개선할 문제와 추가로 검토할 기술을 정리하고,   
단순히 새로운 기술을 사용하는 것보다 현재 문제에 왜 필요한지와 다른 대안보다 적합한 이유를 설명할 수 있도록 방향을 잡았다.

구매·결제 영역에서는 기존 Redis·RDB 간 정합성 보상 처리에서 한 단계 더 나아가,   
실패한 작업을 유실하지 않고 다시 처리할 수 있는 구조를 주요 개선 대상으로 정했다.

> Transactional Outbox 적용 방향 설계

기존 구매 취소에서는 `Purchase`와 `Payment` 상태를 변경한 뒤 Transaction commit 이후   
`inventoryService.restoreStock()`을 호출해 Redis 재고를 복구했다.

하지만 DB commit 이후 Redis 복구가 실패하면 구매는 취소됐지만 재고 복구 요청 자체를 다시 확인하거나 처리할 근거가 남지 않는 문제가 있었다.

이를 해결하기 위해 Redis 복구를 직접 수행하는 대신 다음 흐름으로 변경했다.

`Purchase / Payment 상태 변경 → Outbox 이벤트 저장 → DB Transaction commit → 이후 비동기 재고 복구`

상태 변경과 Outbox INSERT를 하나의 DB Transaction으로 묶으면 Transaction이 성공한 경우 재고 복구 요청도 반드시 DB에 남기 때문에   
이후 발행이나 Redis 처리가 실패하더라도 다시 조회해 재처리할 수 있다.

Outbox는 공통 구조로 두고 `eventId`, `traceId`, `eventType`, `payload`, `status`, `createdAt`을 최소 필드로 구성했다.

`eventId`는 중복 이벤트를 식별하고 멱등 처리를 하기 위한 값이고,   
`traceId`는 HTTP 요청부터 이후 비동기 처리까지 하나의 흐름을 로그에서 추적하기 위한 값으로 역할을 구분했다.

현재 이벤트는 `STOCK_RESTORE_REQUESTED`, 상태는 `PENDING`, `PUBLISHED`를 기준으로 시작했다.

> Kafka와 Redis Streams 비교

재고 복구 이벤트 전달 방식으로 Kafka와 Redis Streams를 비교했다.

Kafka는 높은 처리량과 여러 Consumer의 독립적인 소비, 장기간 이벤트 보관과 재생 등에 강점이 있지만   
현재 Gudit에서 필요한 규모에 비해 별도 인프라와 운영 복잡도가 커질 수 있다고 판단했다.

현재 필요한 것은 재고 복구 이벤트의 유실 방지와 실패 재처리, 중복 처리 방지이며   
이미 Redis를 사용하고 있어 Redis Streams가 현재 프로젝트 범위에는 더 적합하다고 정리했다.

Kafka는 이후 MSA로 확장하면서 여러 서비스가 동일 이벤트를 독립적으로 소비하거나 장기간 보관·재생과 높은 처리량이 필요해질 경우 다시 검토할 수 있다.

Redis Streams의 Consumer Group은 여러 Consumer가 메시지를 나눠 처리할 수 있지만,   
Kafka처럼 파티션별 offset을 중심으로 소비 위치를 관리하는 구조와는 차이가 있다.

Redis Streams에서는 Stream Entry ID를 기준으로 메시지를 읽고,   
Consumer Group으로 전달됐지만 아직 ACK되지 않은 메시지는 Pending Entries로 관리한다.

따라서 이후 재고 복구 Consumer에서는 처리 성공 시 ACK하고, 실패한 메시지는 Pending 상태를 기반으로 재처리하는 흐름이 필요하다.   
메시지가 다시 전달될 수 있으므로 `eventId` 기반 멱등 처리도 함께 필요하다.

> 구매 취소 Outbox 적용 및 검증

첫 적용 대상으로 구매 취소 흐름을 선택했다.

기존 `afterCommit` 재고 복구 호출 대신   
`Purchase`·`Payment` 상태 변경과 `STOCK_RESTORE_REQUESTED` Outbox 저장을 동일 Transaction 안에서 처리하도록 변경했다.

반면 구매 생성 과정에서 Redis 재고를 먼저 차감한 뒤 DB Transaction 자체가 실패하는 경우   
사용하는 `registerStockRollback()`은 Outbox가 해결하는 상황과 다르므로 기존 보상 처리로 유지했다.

구조가 변경되면서 기존 테스트도 직접 Redis 복구 호출을 검증하는 대신   
`outboxEventService.saveStockRestoreRequested(...)`가 호출되는지 확인하도록 수정했다.   
취소가 거절되는 경우에는 Outbox 이벤트도 생성되지 않는지 함께 검증했다.

`PurchaseService`에 `OutboxEventService` 의존성이 추가되면서   
기존 테스트의 Mock 누락으로 빌드가 실패했지만 테스트 설정을 새 구조에 맞게 수정한 뒤 전체 `clean build`가 성공했다.

마지막으로 Mock 검증에서 끝내지 않고 실제 구매 후 취소를 수행해 DB 상태도 확인했다.

`Purchase`가 `CANCELED`로 변경되고 `outbox_events`에는 `STOCK_RESTORE_REQUESTED` 이벤트가 `PENDING` 상태로 저장됐으며,   
payload의 `purchaseId`, `saleId`, `userId`, `quantity`도 정상적으로 기록되는 것을 확인했다.

현재는 구매 취소 상태 변경과 재고 복구 요청 저장을 하나의 DB Transaction으로 보장하는 단계까지 구현했다.

## 헷갈렸던 점

Transactional Outbox를 적용하면 기존 `afterCommit` 보상 처리와 무엇이 달라지는지 다시 정리했다.

`afterCommit`에서 Redis 복구를 직접 수행하면 Redis 처리에 실패했을 때 다시 처리할 상태가 남지 않을 수 있지만,   
Outbox는 비즈니스 상태 변경과 복구 요청 자체를 같은 DB Transaction에 저장하기 때문에   
이후 실패하더라도 `PENDING` 이벤트를 다시 찾아 처리할 수 있다는 차이가 있었다.

Kafka의 offset과 Redis Streams의 Consumer Group도 비슷하게 느껴져 차이를 확인했다.

Redis Streams에도 Consumer Group이 있지만 Kafka처럼 파티션별 offset을 관리하는 구조는 아니며,   
Entry ID와 Pending Entries를 이용해 전달 여부와 ACK되지 않은 메시지를 관리한다는 점을 정리했다.

또한 구매 생성 실패 시 사용하는 `registerStockRollback()`도 Outbox로 바꿔야 하는지 고민했지만,   
해당 로직은 Redis 재고 차감 이후 DB Transaction이 실패했을 때 즉시 원상복구하기 위한 보상 처리이고   
이번 Outbox는 이미 DB에 반영된 취소·실패 결과에 따른 후속 Redis 복구를 안전하게 전달하기 위한 구조라 역할이 다르다고 구분했다.

## 오늘 느낀 점

3차 프로젝트를 시작하면서 새로운 기술을 추가하는 것보다 기존 구조에서 실제로 남아 있던 문제를 먼저 정의하는 것이 중요하다는 점을 다시 느꼈다.

이번에도 처음부터 Kafka나 Redis Streams를 적용하는 것을 목표로 한 것이 아니라,   
DB 상태는 변경됐는데 Redis 재고 복구가 실패하면 어떻게 다시 처리할 것인가라는 문제에서 시작했다.   
그 결과 Outbox가 필요한 이유와 이후 메시징 기술에 요구되는 조건도 더 명확하게 정리할 수 있었다.

Kafka와 Redis Streams도 어느 기술이 더 좋은지를 비교하기보다   
현재 처리 규모, 이미 사용 중인 인프라, 프로젝트 기간과 운영 복잡도를 함께 고려해 Redis Streams를 선택했다.   
앞으로도 기술 자체보다 현재 문제와 선택 근거, 적용 후 실제 결과를 함께 기록하는 방향으로 진행해야겠다고 느꼈다.
