## 오늘 배운 내용

오늘은 AWS에서 MSA 서비스를 배포하기 위한 네트워크와 서버 구조를 학습했다.

VPC 내부를 Public Subnet과 Private Subnet으로 나누고, 외부 요청을 받아야 하는 `msa-app`은 Public 영역에,   
외부에서 직접 접근할 필요가 없는 `msa-db`는 Private 영역에 배치했다.   
Public · Private 구분은 단순한 이름이 아니라   
Routing Table, Internet Gateway·NAT Gateway, 공인 IP, Security Group 구성이 함께 결정한다는 점을 이해했다.

일반적인 서비스 요청은 `사용자 → IGW → msa-app → Nginx → Docker 서비스 → msa-db → MySQL` 순서로 이동한다.   
Private Subnet의 NAT Gateway는 외부 사용자가 DB 서버로 들어오는 통로가 아니라   
`apt update`처럼 Private 서버가 인터넷으로 나갈 때 사용하는 경로라는 점도 구분했다.

Private DB 서버에 관리 목적으로 접근할 때는 `내 PC → msa-app → msa-db` 순서로 SSH 접속하며,   
이때 `msa-app`이 Bastion 역할을 한다. Bastion은 별도의 AWS 서비스가 아니라 Private 서버 접근을 중계하는 서버의 역할이라는 점을 정리했다.

Nginx를 외부 진입점으로 사용하는 배포 환경에 맞춰 카카오 OAuth 경로도 변경했다.   
로컬에서는 Edge Service의 `localhost:8000`을 직접 사용했지만 AWS에서는 상대경로 `/oauth2/authorization/kakao`를 사용해   
`브라우저 → Nginx → edge-service → auth-service`로 요청이 전달되도록 했다.

Repoary에서는 기존 규칙 기반 TIL 생성 기능을 유지하면서 Gemini API 기반 AI TIL 초안 생성 기능을 별도로 추가했다.   
사용자 자신의 Gemini API Key를 요청 시에만 입력하는 BYOK 방식을 선택하고, Key를 DB·Redis·세션 등에 저장하지 않도록 설계했다.

AI는 기존 분석 결과의 type·scope·category를 그대로 활용하고 실제 GitHub commit diff를 읽어 내용을 보완하는 역할로 제한했다.   
또한 외부 AI의 응답을 바로 저장하지 않고 preview를 먼저 제공한 뒤 사용자가 기존 TIL에 적용하거나 새 TIL을 생성하도록 흐름을 분리했다.

실제 Gemini 호출 과정에서는 반복적인 `503 UNAVAILABLE`을 확인했고,   
최소 요청에서도 같은 오류가 발생하는 것을 검증해 Repoary 로직이 아닌 Gemini 서비스의 일시적인 가용성 문제로 원인을 좁혔다.   
이에 503만 지수 백오프로 재시도하고 다른 오류는 불필요하게 재시도하지 않도록 외부 API 장애 처리도 보완했다.

## 실습 및 과제

> Nginx 경유 OAuth 경로 연동 실습

기존 Web Service의 카카오 로그인 링크는 로컬 MSA 환경에서  
Edge Service로 직접 접근하기 위해 `http://localhost:8000/oauth2/authorization/kakao`를 사용했다.

AWS 배포에서는 외부 진입점이 Nginx의 80 포트로 통일되므로   
해당 주소를 그대로 사용하면 사용자의 브라우저가 실행 중인 PC의 `localhost`를 가리키게 된다.

따라서 로그인 경로를 `/oauth2/authorization/kakao` 상대경로로 변경해 Nginx를 거쳐 Edge Service와 Auth Service로 전달되도록 구성했다.

`/oauth2/authorization/kakao`는 직접 작성한 Controller가 아니라   
Spring Security의 `OAuth2AuthorizationRequestRedirectFilter`가 처리하는 경로라는 점도 다시 확인했다.

> AWS 배포 아키텍처 시각화 자료 추가

AWS 배포 구조를 VPC, Public·Private Subnet, EC2, Nginx, Docker 서비스, MySQL의 관계와 실제 요청 흐름을 중심으로 시각화했다.

서비스 요청, 관리자 SSH 접근, Private 서버의 인터넷 아웃바운드 경로를 구분해 일반 사용자 요청에는 NAT Gateway가 포함되지 않고,   
DB 서버의 외부 인터넷 요청에서만 NAT Gateway가 사용된다는 점을 정리했다.

`msa-app`은 Public Subnet에서 Nginx와 Docker 서비스를 실행하며 동시에 Private Subnet의 `msa-db`에 접근하기 위한 Bastion 역할을 수행한다.

> AWS 인프라 구축과 배포

`msa-vpc` 안에 Public Subnet과 Private Subnet을 구성하고 각각 애플리케이션 서버와 DB 서버를 배치하는 구조를 학습했다.

Public Routing Table은 `0.0.0.0/0 → IGW`, Private Routing Table은 `0.0.0.0/0 → NAT Gateway`로 구성했다.

Security Group에서는 `msa-app-sg`의 HTTP 80을 외부에 허용하고 SSH 22는 내 IP로 제한했다.   
`msa-db-sg`는 SSH 22와 MySQL 3306을 `msa-app-sg`에서 오는 요청에만 허용해 애플리케이션 서버를 통해서만 DB에 접근하도록 제한했다.

Public IP는 인터넷에서 EC2에 접근하기 위한 공인 주소이고, Private IP는 VPC 내부 통신에 사용한다.   
Elastic IP는 고정해서 사용할 수 있는 공인 IP라는 차이도 정리했다.   
Public Subnet에 위치하는 것만으로 외부 접근이 가능한 것은 아니며 공인 IP, Routing Table, IGW, Security Group이 함께 구성되어야 한다.

Private EC2에는 MySQL을 직접 설치하고 `bind-address`를 `127.0.0.1`에서 `0.0.0.0`으로 변경해 애플리케이션 서버의 연결을 받을 수 있도록 했다.   
실제 접근 범위는 Security Group과 MySQL 사용자 권한으로 제한하고, 애플리케이션에서는 `root` 대신 별도의 `app` 사용자를 사용하도록 구성했다.

EC2는 Ubuntu Linux 환경이므로 SSH·SCP와 `apt`, `systemctl`, `tail -f`, `chmod` 등 기존 Linux 명령어도 함께 복습했다.   
`.pem` Private Key와 실제 DB 비밀번호는 저장소에 노출하지 않아야 한다는 점도 확인했다.

실습 후에는 비용이 발생할 수 있는 EC2, NAT Gateway, Elastic IP 등 직접 생성한 AWS 리소스를 기본 리소스와 구분해 정리했다.

> Repoary Gemini API 기반 AI TIL 초안 생성

기존 규칙 기반 TIL 생성 기능은 그대로 유지하고 AI 생성 기능을 선택적으로 사용할 수 있도록 분리했다.

처음에는 n8n과 사용자의 AI 구독 계정을 연동하는 방식을 검토했으나,   
다중 사용자 웹서비스에서 개인 Claude·ChatGPT 구독 계정을 일반적인 OAuth 방식으로 사용하는 구조는 적합하지 않다고 판단했다.   
이에 Gemini API와 사용자별 API Key 입력 방식을 선택하고 Spring Boot에서 직접 호출하도록 구성했다.

AI 입력에는 기존 분석 결과의 commit type·scope·category와   
실제 commit SHA로 조회한 변경 파일의 path, status, additions/deletions, patch를 사용했다.   
전체 파일을 무조건 전송하지 않고 diff를 중심으로 구성하며 generated·lock·build 파일을 제외하고 patch 크기도 제한했다.

Gemini API Key는 `x-goog-api-key` 헤더로만 전달하고 저장하거나 로그에 남기지 않도록 했다.   
잘못된 Key, rate limit, timeout, connection 오류, 잘못된 응답 등도 기존 `ExternalSystemException`과 ErrorCode 구조에 맞춰 구분했다.

프롬프트에서는 기존 Repoary가 결정한 분류를 AI가 다시 판단하지 않도록 하고, TIL의 6개 섹션과 실제 저장소 경로를 유지하도록 했다.   
GitHub 기록에서 확인할 수 없는 기술적 의도나 감정, 질문, 향후 계획을 임의로 생성하지 않도록 제한했다.

실제 Gemini 호출에서는 diff 기반 TIL 초안 생성에 성공했지만 이후 `503 UNAVAILABLE`이 반복적으로 발생했다.   
Repoary를 거치지 않은 최소 요청에서도 동일한 오류가 발생하는 것을 확인해 애플리케이션 로직이 아닌 외부 서비스 장애로 원인을 좁혔다.

503에 대해서만 `1초 → 2초 → 4초` 지수 백오프와 소량의 jitter를 적용해 최대 3회 재시도하고,   
400·401·403·429와 timeout·connection 오류는 별도로 처리하도록 했다.   
로그에는 API Key나 prompt 대신 안전한 HTTP status와 오류 코드만 남기도록 보완했다.

AI 결과를 즉시 `TilDocument`로 저장하던 구조에서는 기존 TIL과 중복 충돌이 발생할 수 있어   
`POST /til-documents/ai-preview` 형태의 미리보기 전용 API로 변경했다.

AI preview는 문서를 생성하거나 수정하지 않고 `title`과 `content`만 반환한다.   
사용자가 결과를 확인한 뒤 TIL이 없으면 기존 생성 API를 통해 DRAFT를 만들고, 기존 TIL이 있으면 PATCH API를 통해 적용하도록 역할을 분리했다.

프론트엔드에는 별도의 `AI로 초안 생성` 버튼과 Gemini API Key 입력 모달을 추가했다.   
Key는 컴포넌트 로컬 state에서만 사용하고 요청 이후 제거하며, 코드 diff가 외부 AI 서비스로 전달될 수 있다는 안내도 제공했다.

생성된 preview는 기존 Markdown 미리보기 UI를 재사용하고, 기존 TIL 유무에 따라 `이 내용으로 TIL 생성` 또는 `현재 TIL에 적용`으로 구분했다.   
사용자가 취소하면 기존 문서는 변경하지 않고, 적용 실패 시에도 preview는 유지해 다시 시도할 수 있도록 했다.

## 헷갈렸던 점

Public Subnet과 Private Subnet이 단순히 외부 접속 가능 여부를 이름으로 구분하는 것인지 헷갈렸다.   
실제로는 Routing Table의 경로와 IGW·NAT Gateway, 공인 IP, Security Group 설정이 함께 구성되어 Public·Private 역할이 결정된다는 점을 이해했다.

NAT Gateway가 외부에서 Private EC2로 접근하기 위한 통로인지 헷갈렸다.   
NAT Gateway는 Private 서버가 외부 인터넷으로 요청을 보낼 때 사용하며   
외부에서 시작되는 연결을 받아 Private 서버로 전달하는 역할은 아니라는 점을 확인했다.

Public IP와 Elastic IP의 차이와 Bastion이 별도의 AWS 서비스인지도 헷갈렸다.   
Elastic IP는 고정해 사용할 수 있는 공인 IP이며, Bastion은 특정 AWS 서비스명이 아니라 Private 서버 접근을 중계하는 서버의 역할을 의미한다.

MySQL의 `bind-address = 0.0.0.0`으로 변경하면 DB가 인터넷 전체에 공개되는 것인지 헷갈렸다.   
해당 설정은 여러 네트워크 인터페이스에서 연결을 받을 수 있도록 하는 것이고   
실제 접근 가능 대상은 Security Group과 MySQL 사용자 권한을 함께 통해 제한한다는 점을 정리했다.

Repoary에서는 처음 Gemini 503 오류가 프롬프트 길이나 애플리케이션 구현 문제인지 의심했다.   
최소 요청에서도 같은 503이 발생하는 것을 확인하면서 외부 서비스 장애와 애플리케이션 문제를 분리해 검증하는 과정이 중요하다는 점을 배웠다.

AI TIL을 생성 즉시 저장할 경우 기존 규칙 기반 TIL과 중복되는 문제도 확인했다.   
AI 결과를 최종 데이터로 바로 취급하지 않고 preview와 실제 저장을 분리하는 것이 기존 기능과 사용자 선택권을 유지하는 데 더 적합하다고 판단했다.

## 오늘 느낀 점

AWS 배포 구조를 직접 요청 흐름과 연결해보면서 Public·Private Subnet, IGW, NAT Gateway, Security Group을 각각 따로 외우는 것보다   
패킷이 실제로 어떤 경로를 이동하는지 이해하는 것이 중요하다고 느꼈다.

특히 DB를 Private Subnet에 두고 Security Group과 DB 사용자 권한까지 함께 제한하는 구조를 통해   
네트워크 격리만으로 보안을 끝내는 것이 아니라 여러 계층에서 접근 범위를 제한해야 한다는 점을 이해할 수 있었다.

Repoary에서는 AI 기능 자체를 추가하는 것보다 기존 분석 결과를 유지하고,   
외부 AI에는 실제 diff를 읽어 초안을 보완하는 역할만 맡기도록 범위를 제한한 점이 의미 있었다.

또한 사용자 API Key를 저장하지 않는 방식, preview 후 적용하는 흐름, 외부 서비스의 503 장애에 대한 재시도 정책을 함께 고민하면서   
AI 연동도 일반적인 외부 시스템 연동과 마찬가지로 보안·실패 처리·사용자 데이터 보호를 함께 고려해야 한다고 느꼈다.
