## 오늘 배운 내용

오늘은 Docker의 기본 동작 원리를 학습하고, 기존 MSA 프로젝트의 5개 서비스를 컨테이너로 실행해 연동하는 실습을 진행했다.

Dockerfile의 멀티 스테이지 빌드를 통해 JDK가 포함된 환경에서 JAR을 빌드하고, 최종 이미지에는 JRE와 실행 파일만 포함하는 구조를 이해했다.   
Gradle 설정 파일과 소스 코드의 복사 순서를 나누어 레이어 캐시를 활용하는 방법도 학습했다.

Docker 명령어에서는 이미지 빌드와 컨테이너 실행 옵션의 역할을 정리했다.   
특히 볼륨 마운트와 환경변수 주입은 서로 다른 역할이며, 컨테이너 내부의 `localhost`는 호스트 PC가 아닌 컨테이너 자신을 가리킨다는 점을 이해했다.

실습에서는 Config·Auth·Board·Edge·Web Service의 Dockerfile을 작성하고, 서비스 간 통신과 DB 연결을 위한 설정을 변경했다.   
이후 컨테이너 환경에서 회원가입·로그인·게시판 기능이 정상 동작하는 것을 확인했다.

Edge Gateway와 OAuth2 연동에서는 프록시 전달 헤더의 역할을 학습했다.   
`X-Forwarded-*` 헤더를 이용해 원래 요청 정보를 전달하는 방법과   
`trusted-proxies`가 클라이언트 접근 제어가 아닌 신뢰할 프록시 범위 설정이라는 점을 구분했다.

Repoary 개선 작업으로 TIL·README 누락 점검 기능에서 GitHub API 호출을 최적화했다.

기존 구조가 날짜마다 TIL 파일을 조회해 외부 API 요청이 반복된다는 점을 확인했다.   
누락 점검에 필요한 정보가 파일 본문이 아닌 존재 여부라는 점을 바탕으로, 월별 디렉터리를 한 번 조회해 파일 목록으로 판정하는 방식으로 변경했다.

동일한 Mock 조건에서 GitHub HTTP 호출 수는 13회에서 3회로 76.9% 감소했고, 평균 응답 시간은 406.554ms에서 101.898ms로 74.9% 감소했다.   
다만 실제 GitHub 네트워크와 DB 접근이 제외된 합성 지연 기반 측정이므로 운영 환경의 성능 개선과는 구분해야 한다는 점을 확인했다.

## 실습 및 과제

> Docker 명령어 및 멀티 스테이지 빌드 학습

Docker 이미지 생성과 컨테이너 실행에 필요한 `build`, `run`, `ps`, `logs` 명령어와 주요 옵션을 정리했다.

`docker build -t`는 이미지 이름과 태그를 지정하며,   
`docker run`의 `-d`, `-p`, `-v`, `-e`, `--env-file` 등을 통해 실행 방식과 포트·파일·환경변수를 설정한다는 점을 학습했다.

Dockerfile에서는 JDK로 JAR을 생성하는 Build Stage와 JRE·JAR만 포함하는 Runtime Stage를 분리하는 멀티 스테이지 빌드를 학습했다.   
`COPY --from=build`의 역할과 Gradle 설정 파일을 소스 코드보다 먼저 복사해 레이어 캐시를 활용하는 방법을 이해했다.

Gradle Daemon의 역할과 `--no-daemon` 옵션도 정리했다.

> MSA Docker 환경 구성 및 서비스 연동 실습

Config·Auth·Board·Edge·Web Service에 Dockerfile을 추가하고, 멀티 스테이지 빌드를 적용해 Docker Desktop에서 실행했다.

Config Service는 `-v`로 설정 디렉터리를 `/config-repo`에 읽기 전용으로 마운트하고,   
`CONFIG_REPO_PATH` 환경변수로 애플리케이션에 설정 경로를 전달했다.   
파일 시스템 연결과 환경변수를 통한 경로 지정이 서로 다른 역할이라는 점을 이해했다.

컨테이너의 `localhost`는 자기 자신을 가리키므로 `host.docker.internal`을 활용하고,   
서비스 간 호출 주소와 DB 연결 주소를 Docker 환경에 맞게 변경했다.   
로컬 실행도 유지할 수 있도록 환경변수에 기본값을 설정했다.

Edge Gateway에서는 `X-Forwarded-Host`, `X-Forwarded-Proto`를 활용한 OAuth2 콜백 주소 생성 구조를 정리했다.   
`trusted-proxies`는 접근 제어가 아닌 신뢰할 프록시 범위 설정이며, 클라이언트가 전달 헤더를 임의로 보낼 수 있다는 점도 확인했다.

Windows의 WSL 2 기반 Linux 컨테이너 실행 구조와 JVM의 `-XX:MaxRAMPercentage=75.0` 옵션도 학습했다.   
힙 외 메모리 사용량을 고려해야 하며, 힙 부족에 따른 `OutOfMemoryError`와 컨테이너 메모리 한도 초과로 인한 종료를 구분했다.

5개 컨테이너의 서비스 간 통신과 DB 연결을 확인하고, 회원가입·로그인·게시판 기능이 정상 동작하는 것을 검증했다.   
실제 서버 배포 및 운영 환경 검증은 진행하지 않았다.

> Repoary 누락 점검 API 호출 분석 및 최적화

누락 알림은 향후 n8n·AI 연동 가능성을 고려해 후순위로 미루고, 기존 기능의 성능과 정확성을 먼저 개선하기로 결정했다.   
API 호출 최적화와 학습 커밋 판별 정확도 개선은 별도 브랜치로 분리했다.

기존 누락 점검은 GitHub 커밋 조회 P회, README 조회 1회, 날짜별 TIL 조회 N회로 구성되어 모든 API 요청이 동기·순차적으로 실행되고 있었다.

누락 사례를 포함한 2026년 9월의 학습 날짜 11개를 대상으로,   
실제 Controller·Service·GitHubApiClient를 사용하고 DB Repository와 GitHub HTTP 응답만 Mock으로 대체해 측정했다.   
기존 구조에서는 커밋 1회, README 1회, TIL 11회로 총 13회의 GitHub HTTP 호출을 관측했다.

누락 점검에 필요한 정보가 TIL 본문이 아닌 파일 존재 여부라는 점을 확인하고,   
`til/YYYY-MM` 디렉터리를 한 번 조회해 파일명·경로·타입으로 존재 여부를 판정하도록 변경했다.   
README 본문 조회는 기존 방식을 유지했다.

디렉터리 항목이 1,000개 이상이거나 응답 항목이 비정상적인 경우 기존 날짜별 조회로 대체하도록 했다.   
디렉터리 404는 기존 누락 판정 정책을 유지하고, 인증·권한·요청 제한 등의 오류는 파일 누락으로 오인하지 않도록 처리했다.

캐시나 병렬 처리 대신 불필요한 외부 API 호출 자체를 제거하는 방식을 선택했다.

> Repoary 성능 개선 결과 측정 및 회귀 검증

동일한 Java 버전과 기대 결과, 호출당 20ms의 합성 지연, 워밍업 1회 및 본 측정 10회 조건에서 개선 전후를 비교했다.

| 측정 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| GitHub HTTP 호출 수 | 13회 | 3회 | 76.9% 감소 |
| 평균 응답 시간 | 406.554ms | 101.898ms | 74.9% 감소 |
| p95 응답 시간 | 422.680ms | 117.656ms | 72.2% 감소 |

다만 별도 테스트 JVM에서 진행한 Mock 기반 측정으로 실제 GitHub 네트워크와 DB 접근은 포함하지 않았다.   
본 측정이 10회이므로 nearest-rank 방식의 p95가 최댓값과 같다는 한계도 확인했다.

기존 11개 날짜의 TIL·README 누락 판정 결과가 유지되는지 비교하고,   
기존 Baseline 테스트 1개를 의도적으로 제외한 상태에서 백엔드 테스트 135개가 통과한 것을 확인했다.

로컬 서버 재시작 후 누락 점검 화면의 정상 동작도 검증했다.   
API 응답 형식과 화면 동작은 유지되어 프론트엔드 수정은 필요하지 않았으며, 측정 JSON은 Gradle `clean`으로 삭제되지 않도록 `build/` 외부에 보관했다.

## 헷갈렸던 점

Docker 실행 옵션 중 `-t`, `-d`, `-e`, `-v`의 의미와 역할이 헷갈렸다.   
`docker build -t`는 이미지 이름과 태그를 지정하고,   
`docker run`의 `-d`는 백그라운드 실행, `-e`는 환경변수 전달, `-v`는 파일 시스템 마운트에 사용한다는 점을 정리했다.

`-v`로 설정 파일을 마운트하고 `CONFIG_REPO_PATH`를 전달하는 과정에서 두 설정의 역할을 혼동했다.   
마운트는 호스트 파일에 접근할 수 있는 경로를 제공하고, 환경변수는 애플리케이션이 해당 파일을 어디에서 읽어야 하는지 알려준다는 점을 이해했다.

컨테이너에서도 기존 `localhost` 주소를 그대로 사용할 수 있는지 헷갈렸다.   
컨테이너의 `localhost`는 자기 자신을 가리키므로,   
이번 Docker Desktop 실습에서는 호스트를 경유해 다른 서비스에 접근하기 위해 `host.docker.internal`을 사용했다.

OAuth2 연동에서 `trusted-proxies`를 카카오 이외의 접근을 차단하는 기능으로 혼동했다.   
실제로는 프록시 전달 헤더를 신뢰할 범위를 지정하는 설정이며, 클라이언트 접근 제어와 다르다는 점을 확인했다.

Repoary에서 Mock 기반 성능 측정과 실제 API 측정의 차이를 확인했다.   
Mock은 동일한 조건에서 코드 변경 효과를 비교하는 데 유용하지만,   
실제 네트워크와 DB 지연을 반영하지 않으므로 운영 환경의 성능으로 해석해서는 안 된다는 점을 배웠다.

## 오늘 느낀 점

기존 MSA 프로젝트를 Docker 환경으로 전환하면서 Dockerfile 작성부터 환경변수 설정, 서비스 간 통신과 기능 검증까지 직접 연결해 볼 수 있었다.

특히 컨테이너의 네트워크 환경이 로컬 실행 환경과 다르다는 점을 경험하면서,   
단순히 이미지를 생성하는 것보다 실행 환경에 맞는 설정과 서비스 연동을 이해하는 것이 중요하다고 느꼈다.

Repoary에서는 새로운 기술을 추가하지 않고 불필요한 API 호출 자체를 제거해 성능을 개선한 점이 의미 있었다.

개선 전 호출 구조를 분석하고 동일한 조건에서 전후 결과를 비교했으며, 기존 누락 판정의 정확성도 유지했다.   
측정 수치뿐 아니라 테스트 환경과 한계를 함께 기록해야 신뢰할 수 있는 개선 경험이 된다는 점을 배웠다.
