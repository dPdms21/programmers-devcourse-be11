## 오늘 배운 내용

오늘은 AWS 환경에 기존 MSA 애플리케이션을 실제로 배포하면서 Docker Compose, Nginx Reverse Proxy, OAuth 연동까지 전체 요청 흐름을 확인했다.

`msa-app`은 Public Subnet, `msa-db`는 Private Subnet에 두고   
일반 사용자 요청은 `Internet → IGW → msa-app → Nginx → Docker Container → msa-db` 흐름으로 처리했다.   
NAT Gateway는 일반 요청 경로가 아니라 Private Subnet의 서버가 외부 인터넷으로 요청을 보낼 때 사용한다는 점을 다시 확인했다.

애플리케이션 EC2에는 Docker와 Git을 설치하고 GitHub Deploy Key를 구성했다.   
AWS용 Docker Compose에서는 5개 서비스를 동일한 `msa-network`에 연결하고, 서비스 간에는 Compose Service Name으로 통신하도록 했다.   
Edge와 Web Service는 `127.0.0.1`에만 Binding해 외부에서는 Nginx를 통해서만 접근하도록 구성했다.

Nginx는 일반 요청을 Web Service로, OAuth 관련 요청을 Edge Service로 전달하도록 설정했다.   
또한 Proxy Header를 전달해 뒤쪽 서비스가 브라우저의 원래 Host와 Protocol 정보를 확인할 수 있도록 했다.

배포 과정에서는 Kakao OAuth Redirect URI에 내부 Docker 주소가 사용되는 문제와 신규 OAuth 가입 시 `Connection is read-only` 오류를 확인했다.   
각각 Gateway의 Host Header 처리와 `oauthSignUp()`의 트랜잭션 설정을 보완해 해결했다.

## 실습 및 과제

> AWS OAuth 연동 오류 보완 실습

Kakao OAuth Redirect URI에 `auth-service:8082`와 같은 내부 Docker 주소가 포함되는 문제를 확인했다.

Edge Gateway의 OAuth Route에 `PreserveHostHeader`를 적용해 기존 Host Header를 유지하고,  
AWS 환경에서는 trusted proxy 설정을 보완해 Nginx가 전달한 Forwarded Header를 신뢰하도록 했다.
이후 Kakao 동의 화면까지 정상적으로 진행되는 것을 확인했다.

신규 OAuth 가입에서는 `UserService`의 클래스 수준 `@Transactional(readOnly = true)` 때문에   
`userRepository.save()` 시 `Connection is read-only` 오류가 발생했다.

일반 회원가입에는 이미 쓰기 트랜잭션이 적용되어 있었지만 `oauthSignUp()`에는 없었기 때문에,   
해당 메서드에 `@Transactional`을 추가해 신규 회원 저장이 가능하도록 수정했다.

> AWS Docker Compose 배포 설정

AWS 배포용 `docker-compose.aws.yml`에서 Config·Auth·Board·Edge·Web Service를 하나의 `msa-network`로 구성했다.

서비스 간에는 `config-service`, `auth-service`, `board-service` 등의 Service Name을 사용하고,   
외부에 직접 공개할 필요가 없는 서비스는 Host Port를 열지 않았다.

Edge와 Web Service는 각각 `127.0.0.1:8000`, `127.0.0.1:8080`에만 Binding해 같은 EC2의 Nginx만 접근할 수 있도록 했다.

DB·OAuth·JWT 등 환경별 값은 `.env`에서 주입하도록 했고,   
EC2 메모리를 고려해 `deploy.sh`에서 Docker Image를 서비스별로 순차 빌드하도록 구성했다.   
특정 서비스만 변경된 경우에는 해당 서비스만 선택적으로 재배포할 수 있다는 점도 확인했다.

> AWS 애플리케이션 배포 및 Nginx 설정

`msa-app` EC2에 Docker와 Git을 설치하고 GitHub Deploy Key를 이용해 Repository의 코드를 직접 가져오도록 구성했다.

Nginx는 외부 HTTP 요청의 단일 진입점으로 두고 `/oauth2/**`, `/login/oauth2/**`는 Edge Service로,   
그 외 요청은 Web Service로 전달하도록 설정했다.

`Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` Header를 전달해   
뒤쪽 서비스가 원래 요청 정보를 유지하도록 했다.

`sites-available`의 설정을 `sites-enabled`에 Symbolic Link로 연결해야 실제 적용된다는 점과,   
설정 변경 후 `nginx -t`와 reload를 통해 적용하는 흐름도 확인했다.

실습이 끝난 뒤에는 EC2뿐 아니라 NAT Gateway와 Elastic IP 등 비용이 발생할 수 있는 AWS 리소스도 함께 정리했다.

## 헷갈렸던 점

Kakao OAuth Redirect URI에 왜 `auth-service:8082`와 같은 내부 주소가 포함되는지 헷갈렸다.

Nginx가 원래 Host 정보를 전달하더라도 Gateway에서 해당 정보를 유지하고 Forwarded Header를 신뢰하도록 설정하지 않으면   
내부 서비스 주소를 기준으로 Redirect URI가 만들어질 수 있다는 점을 확인했다.

`SPRING_CLOUD_GATEWAY_SERVER_WEBMVC_TRUSTED_PROXIES`와 `PreserveHostHeader`의 역할도 비슷하게 느껴졌다.

`trusted-proxies`는 Forwarded Header를 신뢰할 Proxy 범위를 지정하고,   
`PreserveHostHeader`는 Gateway가 요청을 전달할 때 기존 Host Header를 유지한다는 차이를 정리했다.

OAuth 로그인 흐름은 진행되는데 신규 가입 단계에서만 `Connection is read-only`가 발생하는 이유가 헷갈렸다.

기존 사용자를 조회하는 경로에서는 `save()`가 실행되지 않을 수 있지만,  
신규 가입은 `userRepository.save()`를 통해 INSERT를 수행하므로 쓰기 가능한 트랜잭션이 필요하다는 점을 확인했다.

Docker의 8000·8080 포트를 사용하면서도 `127.0.0.1`에 Binding하는 이유도 다시 확인했다.

외부에 직접 공개할 필요 없이 같은 EC2에서 실행되는 Nginx만 접근하면 되므로 Loopback Interface에만 Binding해 직접 접근을 제한한 것이다.

## 오늘 느낀 점

AWS에 실제로 애플리케이션을 배포하면서 VPC, Docker Compose, Nginx, OAuth가 하나의 요청 흐름에서 어떻게 연결되는지 확인할 수 있었다.

특히 외부 요청은 Nginx 하나로 받고 내부 서비스는 Docker Network와 Loopback Interface 뒤에 두는 구조를 직접 구성하면서   
서비스 노출 범위를 분리하는 이유를 더 명확하게 이해했다.

OAuth 오류를 해결할 때도 Kakao 설정만 확인하는 것이 아니라   
Nginx의 Proxy Header, Gateway의 Host 처리, Spring Security의 Redirect URI 생성 흐름까지 따라가야 했다.   
여러 계층을 거치는 요청에서는 어느 지점에서 원래 요청 정보가 달라지는지 확인하는 것이 중요하다고 느꼈다.
