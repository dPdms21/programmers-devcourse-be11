## 오늘 배운 내용

오늘은 전날 구현을 이어서 AI CS Workflow v1을 Slack 연동과 실패 처리까지 완성하고,   
실제 서비스에서 사용할 수 있도록 구매 내역 기반 Workflow v2로 확장했다.

v1에서는 내부 결제 상태 조회 결과를 Claude CLI가 분석하고 Slack으로 전달하는 전체 자동화 흐름을 완성했다.   
정상 결과뿐 아니라 주문 조회 실패와 AI 응답 파싱 실패도 별도 Slack 메시지로 전달해 Workflow 실패 위치를 확인할 수 있도록 했다.

이후 v2에서는 사용자가 `orderId`를 직접 입력하지 않고 자신의 구매 내역에서 문의할 구매 건을 선택하도록 흐름을 변경했다.   
백엔드가 구매 소유권을 검증하고 내부에서 `orderId`를 조회한 뒤 n8n으로 전달하도록 해 실제 서비스에 맞는 인증·권한 구조를 구성했다.

프론트부터 Slack까지 전체 흐름을 연결한 뒤 Claude가 확인되지 않은 원인을 임의로 추측하지 않도록 Prompt를 보완하고,   
팀원이 Workflow를 재현할 수 있도록 환경별 설정값도 분리했다.

## 실습 및 과제

> AI CS Workflow v1 완성

전날 구성한 AI CS Workflow에 Slack Incoming Webhook을 연결해 Claude 분석 결과를 `#gudit-cs` 채널로 전달하도록 했다.

n8n에서는 Form으로 `orderId`와 문의 내용을 입력받고,   
내부 결제 상태 조회 API를 통해 실제 `Purchase`·`Payment` 상태와 금액을 조회한 뒤 Claude CLI에 전달했다.

Claude 응답은 `category`, `currentState`, `assessment`, `recommendedAction`, `customerReplyDraft` 형태의 JSON으로 반환하고,   
Code 노드에서 이를 파싱해 Slack 메시지에 활용했다.

정상 처리뿐 아니라 존재하지 않는 주문번호로 조회가 실패하거나 AI 응답 JSON 파싱에 실패하는 경우에도 별도의 Slack 실패 메시지를 전달하도록 했다.

이를 통해 `문의 입력 → 내부 결제 조회 → Claude 분석 → Slack 전달`까지 v1 전체 흐름을 완성했다.

> AI CS 코드 구조 정리

AI CS 관련 Controller와 DTO를 `cs` 도메인으로 분리했다.

CS Workflow의 요청·응답과 자동화 진입점은 CS 도메인에서 관리하고, 실제 `Payment`·`Purchase` 조회 로직은 기존 Payment 도메인에 유지했다.

이를 통해 자동화 기능을 추가하면서도 CS와 결제 도메인의 책임을 구분했다.

> 구매 내역 기반 AI CS 문의 연동

v1에서는 사용자가 `orderId`를 직접 입력했지만   
실제 서비스에서는 내부 주문번호를 직접 알 필요가 없다고 판단해 구매 내역 기반 문의 흐름으로 변경했다.

다음 API를 추가해 로그인 사용자가 자신의 구매 건을 기준으로 문의할 수 있도록 했다.

`POST /api/purchases/{purchaseId}/cs-inquiries`

백엔드에서는 `purchaseId`를 기준으로 구매 소유권을 검증하고,   
해당 구매와 연결된 `Payment`에서 내부 `orderId`를 조회한 뒤 n8n에는 `orderId`와 문의 내용만 전달하도록 했다.

프론트가 n8n Webhook을 직접 호출하지 않고 반드시 백엔드를 거치도록 해 인증·권한 검증을 수행하고,   
내부 주문 정보와 Workflow 주소가 사용자에게 직접 노출되지 않도록 했다.

이를 통해 v1의 단순 자동화 흐름을 실제 서비스의 사용자·권한 구조에 맞는 방식으로 확장했다.

> 구매 내역 AI CS 문의 UI 구현

구매 내역 화면에 `문의하기` 버튼과 문의 모달을 추가했다.

사용자는 주문번호를 직접 입력하는 대신 문의하려는 구매 건을 선택하고 문의 내용만 작성하면 된다.

프론트에서는 선택한 `purchaseId`를 기준으로 백엔드 CS 문의 API를 호출하고, 이후 백엔드가 내부 `orderId`를 조회해 n8n으로 전달하도록 했다.

실제로 다음 전체 흐름을 연결해 정상적으로 동작하는 것을 확인했다.

`프론트 → Spring Boot → n8n → 내부 결제 상태 조회 → Claude CLI → Slack`

이를 통해 AI CS 자동화를 기술적으로 연결하는 수준에서 실제 구매 사용자 흐름으로 확장했다.

> AI CS Workflow v2 구성 및 운영 형태 보완

v2에서는 Form Trigger 대신 Spring Boot에서 호출하는 Webhook 기반 Workflow로 변경했다.

n8n의 Test Webhook은 `Execute workflow` 또는 `Listen for test event` 상태에서만 활성화되기 때문에   
테스트 대기 상태가 아니면 404가 발생한다는 점을 확인했다.

테스트 완료 후 Workflow를 Publish하고 Production Webhook으로 전환해 실제 백엔드 요청과 연결했다.

Claude Prompt도 실제 서비스용으로 보완했다.

초기에는 캐시, 동기화 지연, 프론트 오류처럼 실제 조회 정보로 확인되지 않은 원인을 가능성으로 제시하는 경우가 있었다.

이를 보완해 Claude가 제공된 구매·결제 상태만을 근거로 판단하고,   
확인되지 않은 원인은 단정하지 않으며 필요한 경우 추가 확인이 필요하다고 응답하도록 제한했다.

또한 결제 취소·환불·DB 수정·외부 API 호출 같은 실제 조치는 수행하지 않고   
문의 분류, 현재 상태 판단, 권장 조치, 고객 답변 초안까지만 생성하도록 역할을 명확하게 했다.

> Workflow 공유를 위한 환경 설정 분리

Workflow v2를 export하고 팀원이 import해 자신의 환경에서도 실행할 수 있도록 환경 종속 값을 분리했다.

`INTERNAL_API_KEY`, `CS_SLACK_WEBHOOK_URL`, `GUDIT_INTERNAL_API_BASE_URL`을 환경변수로 관리해   
Workflow 안에 직접 값을 하드코딩하지 않도록 했다.

특히 n8n은 WSL에서 실행되고 Spring Boot는 Windows에서 실행되기 때문에 Windows Host 주소가 개발 환경마다 달라질 수 있다.

따라서 해당 주소도 환경변수로 분리해 팀원이 자신의 WSL·Windows 환경에 맞는 값만 설정하면 Workflow를 재사용할 수 있도록 정리했다.

## 헷갈렸던 점

v1에서 사용자가 `orderId`를 직접 입력하는 방식이 실제 서비스에서도 적절한지 고민했다.

`orderId`는 내부 결제 식별 정보에 가깝기 때문에 실제 사용자는 자신의 구매 내역에서 문의할 구매 건을 선택하는 것이 더 자연스럽다고 판단했다.   
이에 따라 프론트에서는 `purchaseId`를 전달하고 서버가 실제 `orderId`를 조회하도록 변경했다.

프론트에서 n8n Webhook을 직접 호출해도 되는지도 고민했다.

직접 호출하면 구매 소유권 검증을 우회할 수 있고 내부 Workflow 주소가 노출될 수 있으므로,   
인증된 백엔드에서 권한 검증과 내부 정보 조회를 수행한 뒤 n8n을 호출하는 구조가 더 적절하다고 정리했다.

Test Webhook에서 정상 동작하던 URL이 이후 404가 발생한 이유도 확인했다.

n8n의 Test Webhook은 테스트 대기 상태에서만 등록되므로 실제 서비스 연동에는 Publish된 Production Webhook을 사용해야 한다는 점을 구분했다.

Claude가 실제 결제 상태를 전달받고도 확인되지 않은 원인을 추측하는 경우도 있었다.

AI에 데이터를 제공하는 것만으로 충분한 것이 아니라 어떤 정보만 사용할 수 있는지와 어떤 행동까지 허용되는지를   
Prompt에서 명확하게 제한해야 한다는 점을 확인했다.

## 오늘 느낀 점

오늘은 단순히 n8n과 Claude를 연결하는 수준에서 끝나지 않고, 실제 사용자가 사용할 수 있는 CS 흐름으로 확장하는 과정이 중요했다.

v1에서는 전체 자동화 Workflow가 기술적으로 동작하는지 확인했다면,   
v2에서는 사용자가 어떤 정보를 입력해야 하는지, 구매 권한은 어디서 검증할지,   
내부 식별 정보와 Workflow 주소는 어디까지 노출할지까지 고려하면서 실제 서비스 구조로 바꿨다.

특히 프론트가 n8n을 직접 호출하지 않고 백엔드를 거치도록 한 것과,   
Claude의 역할을 실제 조치가 아닌 분석과 답변 초안 생성으로 제한한 것이 자동화 기능의 경계를 명확하게 만드는 데 중요했다.

또한 Workflow의 Host 주소와 API Key, Slack Webhook 같은 설정을 환경변수로 분리하면서   
자동화 Workflow 역시 애플리케이션 코드처럼 다른 팀원이 재현하고 실행할 수 있도록 관리해야 한다는 점을 확인했다.
