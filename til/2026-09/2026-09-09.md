## 오늘 배운 내용

오늘은 Kotlin의 코루틴과 Sequence를 중심으로 실습했다.

코루틴에서는 `suspend`, `runBlocking`, `launch`, `async`, `await`, `awaitAll`, `coroutineScope`의 역할과 취소·타임아웃 흐름을 확인했다.   
`suspend` 함수라고 해서 자동으로 동시에 실행되는 것은 아니며, 실제 동시 실행에는 `launch`나 `async` 같은 코루틴 빌더가 필요하다는 점을 정리했다.

또한 `Thread.sleep()`은 현재 스레드 자체를 막지만 `delay()`는 코루틴만 중단해 스레드가 다른 작업을 수행할 수 있다는 차이를 확인했다.   
부모와 자식 코루틴의 생명주기와 취소가 연결되는 구조화된 동시성도 함께 학습했다.

Sequence에서는 일반 컬렉션과 달리 최종 연산이 호출될 때까지 계산을 미루는 지연 연산 방식을 확인했다.   
특히 일부 결과만 필요한 경우 원하는 결과를 얻는 순간 처리를 종료할 수 있다는 장점이 있지만, 모든 상황에서 List보다 효율적인 것은 아니라는 사용 기준도 정리했다.

강사 개인 면담에서는 3차 프로젝트에서 Kotlin 적용을 우선하고 MSA는 서비스 요구사항에 따라 선택적으로 적용하는 방향을 확인했다.   
기술을 많이 사용하는 것보다 실제 문제에 대해 여러 대안을 비교하고 선택 근거와 결과를 설명할 수 있는 경험이 중요하다는 점도 정리했다.

## 실습 및 과제

> Kotlin 코루틴 실습

코루틴은 스레드를 직접 대체하는 것이 아니라 스레드 위에서 실행되며, 대기 중인 작업을 중단했다가 다시 재개할 수 있는 작업 단위라는 점을 확인했다.

`suspend`는 함수가 중단 가능한 함수임을 의미하지만 그 자체로 새로운 코루틴을 생성하거나 동시에 실행시키지는 않는다.

`launch`는 결과가 필요하지 않은 작업에 사용하고, `async`는 결과가 필요한 작업을 시작해 `Deferred`를 반환한다.   
`await()`로 결과를 기다리고 여러 `Deferred`는 `awaitAll()`로 한꺼번에 기다릴 수 있다.

`runBlocking`과 `coroutineScope`는 모두 내부 자식 코루틴이 끝날 때까지 기다리지만 동작 방식이 다르다.   
`runBlocking`은 현재 스레드를 막으면서 일반 코드와 코루틴의 시작점을 연결하고, `coroutineScope`는 suspend 함수 내부에서 자식 코루틴을 하나의 스코프로 관리한다.

부모 코루틴은 자식이 모두 종료될 때까지 기다리고, 부모가 취소되면 자식도 함께 취소된다.   
같은 스코프의 자식 중 하나에서 예외가 발생하면 다른 자식 코루틴에도 취소가 전파되는 구조화된 동시성 흐름도 확인했다.

> Kotlin Sequence 실습

일반 List는 컬렉션 연산 과정에서 각 단계별로 전체 데이터를 처리하고 중간 결과를 만들 수 있지만, Sequence는 최종 연산이 실행될 때까지 계산을 미룬다.

Sequence에서는 원소 하나가 `filter`, `map` 등의 연산 단계를 모두 통과한 뒤 다음 원소를 처리한다.

따라서 `first`, `find`, `take`처럼 전체 결과가 필요하지 않은 경우 원하는 결과를 얻은 시점에서 이후 연산을 생략할 수 있다.

`filter`, `map`, `take`, `drop`, `distinct`, `flatMap`은 중간 연산이고   
`toList`, `first`, `find`, `count`, `sum`, `forEach` 등은 실제 계산을 시작하는 최종 연산이라는 점을 구분했다.

`generateSequence()`를 이용해 규칙에 따라 값을 생성하거나 `sequence {}`와 `yield()`를 이용해 필요한 시점에 값을 하나씩 전달하는 방식도 실습했다.

다만 데이터가 적거나 연산 단계가 단순하고, `sorted()`처럼 전체 원소 처리가 필요한 경우에는 Sequence 사용이 항상 더 유리한 것은 아니라는 점도 확인했다.

> 강사 개인 면담

3차 프로젝트에서는 Kotlin 적용을 우선하고 MSA는 모든 서비스를 무조건 분리하기보다 필요한 일부 서비스에 적용해도 된다는 점을 확인했다.

최종 프로젝트에서는 기술 스택을 많이 추가하는 것보다 실제 문제를 기준으로 polling, Kafka, Redis 등 여러 대안을 비교하고   
왜 해당 기술을 선택했는지 설명할 수 있는 경험이 중요하다는 점을 들었다.

과제 전형과 테크 리뷰에서도 단순 구현 결과보다 `왜 이 방법을 선택했는가`를 설명하는 능력이 중요하며,   
코딩테스트에서는 투 포인터와 트리 유형이 자주 출제되어 이를 위주로 준비할 필요가 있다는 점을 확인했다.

PostgreSQL과 MySQL의 차이가 궁금해 질문했고, 좌표 처리 등 PostgreSQL이 가지는 장점을 확인했다.

추가로 취업 준비를 위해 관심 있는 기업을 찾아보고, 해당 기업의 기술 환경과 요구 역량을 함께 조사해볼 필요가 있다는 조언을 들었다.

> 코루틴 동시성 복습 과제

`suspend`, `delay`, `runBlocking`, `async`, `await`, `awaitAll`, `coroutineScope`, 취소와 예외 전파를 직접 구현하며 실습 내용을 복습했다.

`fetchName()`을 세 번 순차 실행했을 때는 약 1.5초가 걸렸지만, 세 작업을 먼저 `async`로 실행한 뒤 결과를 기다리자 약 0.5초로 줄었다.

반대로 `async { ... }.await()`를 매번 바로 호출하면 각 작업의 결과를 기다린 뒤 다음 작업을 시작하므로 다시 순차 실행과 비슷한 시간이 걸렸다.   
이를 통해 `async`를 사용했다는 사실보다 **언제 작업을 시작하고 언제 기다리는지가 동시 실행 여부를 결정한다**는 점을 확인했다.

`delay(500)`을 사용하는 10개의 작업은 약 0.5초에 완료됐지만 `Thread.sleep(500)`으로 변경하자 약 5.2초가 걸렸다.

취소 실습에서도 `delay()`를 사용할 때는 `cancelAndJoin()`으로 작업을 중단할 수 있었지만 `Thread.sleep()`을 사용하면 반복문이 계속 실행되었다.   
이를 통해 코루틴 취소는 스레드를 강제로 종료하는 방식이 아니라 suspend 지점 등에서 취소 상태를 확인하는 협조적 취소라는 점을 확인했다.

`withTimeoutOrNull()`은 제한 시간 안에 끝나지 않은 작업을 취소하고 `null`을 반환했으며, 제한 시간 안에 완료된 작업은 정상 결과를 반환했다.

## 헷갈렸던 점

`suspend` 함수가 코루틴 자체이거나 자동으로 동시에 실행되는 것인지 헷갈렸다.

`suspend`는 해당 함수가 중단될 수 있음을 나타낼 뿐이며, 실제 코루틴을 시작하려면 `launch`, `async` 등의 빌더가 필요하다.

`suspend` 함수 안에서 바로 `launch`나 `async`를 사용할 수 있는지도 헷갈렸다.

`suspend` 함수라는 사실만으로 `CoroutineScope`가 생기는 것은 아니므로,   
여러 자식 코루틴을 실행하려면 `coroutineScope {}`와 같은 스코프가 필요하다는 점을 확인했다.

`async`를 사용했는데도 순차 실행처럼 시간이 걸리는 경우도 있었다.

`async { fetchName() }.await()`처럼 생성 직후 바로 `await()`하면 첫 작업이 끝날 때까지 기다린 뒤 다음 `async`를 실행하게 된다.   
여러 작업을 동시에 처리하려면 먼저 여러 `async`를 실행한 뒤 결과를 기다려야 한다.

`cancelAndJoin()`을 500ms 뒤 호출했는데 `0`, `1`, `2`까지 출력되는 이유도 처음에는 헷갈렸다.

첫 출력은 즉시 실행되고 이후 `delay()` 사이에서 시간이 흐르기 때문에 취소 요청 이전에 실행된 출력까지는 정상적으로 나타난다는 점을 시간 순서로 확인했다.

## 오늘 느낀 점

오늘은 코루틴에서 문법 자체보다 실행 순서와 스코프를 이해하는 것이 더 중요하다고 느꼈다.

특히 `suspend`, `async`, `await`를 사용했다는 이유만으로 동시 실행이 되는 것이 아니라 작업을 언제 시작하고 언제 기다리는지에 따라 실제 실행 시간이 달라졌다.   
`delay()`와 `Thread.sleep()`을 직접 비교하면서 코루틴이 대기 시간을 효율적으로 처리한다는 의미도 더 명확하게 이해할 수 있었다.

Sequence 역시 단순히 List보다 빠른 기능이라고 보기보다 계산을 언제 수행하고 얼마나 많은 원소를 실제로 처리해야 하는지를 기준으로 선택해야 한다는 점이 중요했다.

강사 면담을 통해서는 3차 프로젝트에서 Kotlin이나 MSA 같은 기술을 사용하는 것 자체보다 실제 문제를 먼저 정의하고 여러 대안을 비교한 뒤   
선택 이유와 결과를 설명할 수 있는 경험을 만드는 것이 중요하다는 방향을 다시 확인했다.
