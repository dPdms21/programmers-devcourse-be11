## 오늘 배운 내용

오늘은 Y:ON의 공고 상세 조회 API를 설계하고, 사용자별 신청 가능성 판정 결과를 검색·추천에서 활용하는 방식을 구체화했다.

상세 조회는 청년정책과 직업훈련의 공통 정보를 유지하면서 유형별 상세 정보를 구분하도록 설계했다.   
또한 로그인 상태와 모집 마감 여부에 따라 개인별 신청 가능성을 다르게 제공하고,   
상세 조회 API와 사용자 행동 이벤트를 분리하는 방향을 검토했다.

신청 가능성 판정은 사용자 조건 설정 이후 필요한 시점에 수행하고, 결과를 저장해 재사용하는 방식을 선택했다.   
최초 판정은 동기적으로 완료한 뒤 검색 결과를 반환하도록 하였으며, 판정 결과의 최신성을 확인하기 위한 버전 관리도 함께 논의했다.

검색 품질 개선을 위해 가중치 기반 랭킹, TF-IDF, BM25, Trigram, 벡터 유사도 검색을 비교했다.   
초기에는 기본 통합 검색을 구현하고, 이후 실제 검색 품질과 성능을 측정해 개선하는 방향을 정리했다.

이후 저장·숨김 기능을 `preference` 도메인으로 구현하고,   
정책 엔진의 공통 코드와 연동하기 전에도 독립적으로 구현할 수 있는 기본 검색 기능부터 개발했다.  
이 과정에서 멱등성, 동시성 제어, 정렬과 페이지네이션의 정합성을 고려했다.

WTL 팀 미팅에서는 남은 개발 작업을 점검하고, 기능 간 세부 연동 정책에서 추가 협의가 필요함을 상기했다.   
또한 일정 관리를 위해 Jira를 단독으로 사용할지, GitHub Issues와 연동할지 검토했다.

## 실습 및 과제

> 공고 상세 조회 API 설계

청년정책과 직업훈련을 하나의 상세 조회 API로 제공하되, `type`으로 공고 유형을 구분하는 구조를 설계했다.

공통 필드는 응답 최상위에 배치하고,   
청년정책의 지원 내용·신청 방법과 직업훈련의 훈련기관·훈련기간 등 유형별 정보는 `detail` 객체로 분리했다.   
구체적인 필드는 정규화 모델과 연동하면서 확정하기로 했다.

비로그인 사용자도 상세 조회가 가능하도록 하고, 로그인 및 프로필 설정 여부에 따라 개인별 신청 가능성 제공 여부를 구분했다.   
마감 공고는 상세 조회를 허용하되 `eligibility: null`을 반환하는 방식으로 응답 구조의 일관성을 유지하도록 설계했다.

또한 상세 조회와 사용자 행동 기록을 분리하여 `DETAIL_VIEW`, `APPLICATION_CLICK` 등의 이벤트를 별도 API로 수집하는 방식을 검토했다.   
API 호출 횟수와 실제 사용자 행동 횟수가 일치하지 않을 수 있으므로 중복 집계에 주의해야 한다는 점을 확인했다.

> 신청 가능성 판정 및 결과 저장 방식 논의

신청 가능성 필터링을 페이지네이션 이후에 수행하면 검색 결과 수와 전체 페이지 수가 부정확해질 수 있다는 문제를 검토했다.

이를 해결하기 위해 사용자별 판정 결과를 `ELIGIBILITY_RESULT`에 저장하고, 검색·추천에서 공통으로 활용하는 방향을 논의했다.

전체 사용자와 공고를 사전 판정하는 대신, 사용자 조건 설정 이후 필요한 시점에 판정하는 방식을 선택했다.   
판정 대상은 모집 중·모집 예정 공고로 제한하고 마감 공고는 제외하기로 했으며, 예상 사용자 수는 500명으로 설정했다.

최초 신청 가능성 필터 검색에서 판정 결과가 없다면 판정을 완료한 후 응답을 반환하는 동기 방식을 선택했다.   
프론트엔드에는 로딩바를 표시하도록 하되, 로딩 UI와 서버의 비동기 처리 방식은 서로 다른 개념임을 정리했다.

또한 공고 버전, 프로필 버전, 규칙 버전, 유효 기한을 기준으로 저장된 판정 결과의 최신성을 확인해야 하며,   
실제 처리 비용은 측정을 통해 검증할 필요가 있다는 점을 확인했다.

> 검색 알고리즘 후보 탐색

현재 설계한 검색은 키워드와 필터 조건을 이용한 조회 중심으로,   
검색어와 공고 사이의 관련도를 평가하는 별도 랭킹 알고리즘은 적용하지 않은 상태임을 확인했다.

검색 품질 개선을 위한 후보로 가중치 기반 랭킹, TF-IDF, BM25, Trigram, 벡터 유사도 검색을 비교했다.

가중치 기반 랭킹은 제목·키워드·본문의 일치 수준에 차등 점수를 부여하며, TF-IDF와 BM25는 단어의 빈도와 희소성 등을 활용한다.   
Trigram은 오타와 부분 문자열 일치를 보완하고, 벡터 검색은 의미적으로 유사한 공고를 찾는 데 활용할 수 있다는 점을 정리했다.

Y:ON에서는 PostgreSQL을 사용하므로 `pg_trgm`과 Full-Text Search 등 기존 DB의 기능을 우선 검토하기로 했다.

V1에서는 기본 통합 검색을 구현하고,   
이후 실제 검색 품질 문제가 확인되면 알고리즘을 적용해 Precision@5, MRR, 응답 시간, DB 쿼리 시간 등을 비교할 계획을 세웠다.

> 저장·숨김 기능 설계 및 구현

사용자별 공고 저장과 숨김 기능을 별도 테이블로 관리하는 방식과 하나의 테이블로 통합하는 방식을 비교했다.

두 기능 모두 사용자와 공고의 관계를 관리하므로 `preference` 도메인으로 분리하고,   
`user_opportunity_preferences` 테이블에서 `is_saved`, `is_hidden`을 독립적으로 관리하도록 설계했다.

`UNIQUE(user_id, opportunity_id)` 제약으로 중복 데이터를 방지하고, 두 상태가 모두 `false`가 되면 해당 행을 삭제하도록 했다.   
동일한 요청을 반복해도 결과가 불필요하게 달라지지 않도록 멱등성을 보장하고,   
동시 요청에 따른 중복 생성을 방지하기 위해 사용자 단위 비관적 락을 적용했다.

저장 목록에는 페이지네이션을 적용하고 PostgreSQL 기반 동시성 테스트를 포함해 기능을 검증했다.

숨김은 추천 후보에서 제외하는 조건으로 사용하며, 일반 검색과 상세 조회에서는 숨긴 공고도 조회할 수 있도록 역할을 구분했다.

> 기본 통합 검색 구현

정책 엔진이 완성되기 전에도 독립적으로 구현할 수 있는 기본 검색 기능부터 개발했다.

청년정책과 직업훈련을 통합해 제목 키워드, 공고 유형, 대·중분류 필터를 구현했다.   
정규화된 공고만 검색 대상으로 사용하고, `createdAt DESC, id DESC` 정렬과 DB 페이지네이션을 적용했다.

여러 필터를 조합했을 때도 전체 검색 결과 수가 정확하게 계산되도록 처리했다.

구현 과정에서 신규 검색 Controller와 기존 보안 테스트용 Controller의 URL 매핑이 충돌했다.   
보안 테스트가 실제 검색 API를 대상으로 수행되도록 수정하여 문제를 해결했으며, 전체 62개 테스트 통과를 확인했다.

지역 검색과 모집 상태 필터는 정규화 모델과의 연동을 추가로 검토했다.

`OpportunityRegion`은 실제 지역 코드와 공고 버전의 관계를 관리하고,   
`OpportunityCondition`은 `SPECIFIC`, `NATIONAL`, `UNKNOWN` 등 지역 조건의 의미를 표현한다는 차이를 확인했다.

또한 모집 상태는 신청기간을 기준으로 계산해야 하므로,   
페이지 조회 이후 Java에서 필터링하면 전체 결과 수가 부정확해질 수 있다는 점을 확인했다.   
해당 기능은 정책 엔진의 공통 코드가 병합된 이후 구현하기로 했다.

저장·숨김 상태를 관리하는 `preference`와 추천 노출·상세 조회·신청 클릭 이력을 관리하는 `behavior`의 책임도 구분했다.   
행동 이벤트는 검색·추천의 기본 기능을 완성한 후 필요한 범위를 정의해 구현하기로 했다.

> WTL 팀 미팅

프로젝트에서 남은 개발 작업을 확인하고 전체적인 진행 계획을 수립했다.   
다만 도메인 간 세부 연동 정책은 아직 명확하지 않은 부분이 있어 추가 협의가 필요하다는 점을 확인했다.

일정 및 작업 관리를 위해 Jira를 단독으로 사용하는 방식과 GitHub Issues를 연동하는 방식을 비교했다.

GitHub Issues까지 연동하면 작업 이력과 코드 변경 사항을 함께 관리할 수 있다는 장점이 있지만,   
이슈 작성과 상태 관리, 브랜치·커밋 컨벤션 등을 일관되게 지켜야 하는 부담도 고려했다.

두 방식의 관리 효율성과 팀의 작업 부담을 비교했으며, 최종 활용 방식은 추가 논의하기로 했다.

## 헷갈렸던 점

최초 신청 가능성 필터 검색에서 판정 결과가 없는 경우, 서버가 판정을 완료할 때까지 기다리는 방식과 비동기 처리 방식의 차이를 검토했다.

프론트엔드에서 로딩바를 표시하는 것은 진행 상태를 보여주는 UI 처리이며, 서버의 비동기 처리 여부를 결정하는 것은 아니라는 점을 이해했다.   
초기에는 판정을 동기적으로 완료한 후 결과를 반환하는 방식으로 정리했다.

지역 필터에서 `OpportunityRegion`과 `OpportunityCondition`을 어떻게 구분해야 하는지도 확인했다.

`OpportunityRegion`은 공고가 연결된 지역 정보를 관리하고,   
`OpportunityCondition`은 특정 지역 대상인지 전국 대상인지 등 신청 지역 조건의 의미를 나타낸다는 점을 구분했다.

또한 모집 상태 필터를 Java에서 페이지네이션 이후에 적용해도 되는지 검토했다.   
신청기간으로 계산되는 상태를 조회 이후에 필터링하면 페이지 크기와 전체 결과 수가 달라질 수 있으므로,   
DB 조회 단계에서 필터 조건을 반영할 수 있는 구조가 필요하다는 점을 확인했다.

저장·숨김 기능에서는 동일한 요청의 반복과 동시 요청을 구분해 처리해야 한다는 점을 검토했다.   
멱등성은 반복 요청에 따른 상태 변화를 방지하고,   
동시성 제어는 여러 요청이 동시에 데이터를 변경할 때 발생할 수 있는 충돌을 방지한다는 차이를 정리했다.

## 오늘 느낀 점

오늘은 상세 조회와 신청 가능성 판정 방식을 구체화한 뒤, 저장·숨김 기능과 기본 통합 검색을 실제로 구현했다.

설계 단계에서는 검색과 추천이 정책 엔진에 의존하는 부분이 많아 개발 순서를 고민했지만,   
공통 데이터 계약을 기준으로 독립적으로 구현할 수 있는 기능부터 진행하면서 개발 범위를 구분할 수 있었다.

특히 저장·숨김 기능에서는 단순히 상태를 변경하는 API를 만드는 것보다   
반복 요청과 동시 요청에서도 데이터 정합성을 유지하는 것이 중요하다는 점을 확인했다.

검색 기능에서도 안정적인 정렬과 페이지네이션, 필터 조합에 따른 전체 결과 수를 함께 고려해야 했다.   
URL 매핑 충돌을 해결하고 테스트를 통과시키면서 기존 코드와 테스트 구조를 함께 확인하는 과정의 중요성을 느꼈다.

또한 검색 알고리즘을 조사하면서 다양한 기술을 바로 적용하기보다 기본 검색을 먼저 완성하고,   
실제 검색 품질과 성능을 측정한 후 필요한 개선 방법을 선택하는 것이 적절하다고 판단했다.
