## 오늘 배운 내용

오늘은 Y:ON의 개인화 추천 알고리즘을 구체화하고, 온통청년 정책과 고용24 훈련과정을 함께 조회하기 위한 통합 검색·필터 구조를 검토했다.

추천은 정책 엔진의 신청 가능성 판정 결과를 활용해 후보를 선정하고 우선순위를 결정하는 역할로 구분했다.   
초기에는 규칙 기반 필터링과 콘텐츠 기반 추천을 결합하고, 관심 분야 일치도를 주요 기준으로 활용하는 방향을 구체화했다.

통합 검색에서는 정책 유형과 지역, 관심 분야, 신청 가능성 등의 필터 조합을 검토했다.   
특히 여러 신청 가능성 상태를 선택하는 경우의 OR 조건과 신청 가능성 필터링·페이지네이션의 처리 순서가   
검색 결과의 정합성에 영향을 준다는 점을 확인했다.

마지막으로 인증·사용자 및 정책 엔진 관련 코드를 검토하면서 보안 설정뿐 아니라 정책 조건의 누락과 제한 없음 상태를 구분하고,   
신청 가능성 판정 결과를 다른 서비스에서 활용하는 방식도 고려해야 한다는 점을 확인했다.

## 실습 및 과제

> 개인화 추천 알고리즘 및 우선순위 설계

Y:ON의 초기 추천 방식을 규칙 기반 필터링과 콘텐츠 기반 추천을 결합하는 방향으로 구체화했다.

추천 후보는 모집이 종료됐거나 `NOT_ELIGIBLE`인 기회를 제외하고,   
`ELIGIBLE`을 우선 제공한 뒤 부족한 경우 `POSSIBLY_ELIGIBLE`로 보충하는 방식을 검토했다.

신청 자격조건은 정책 엔진에서 판정하므로 추천 영역에서는 이를 중복 평가하지 않고,   
판정 결과와 사용자 관심 분야를 활용해 우선순위를 결정하도록 역할을 구분했다.

관심 분야는 대분류와 중분류의 일치 수준을 구분하고, 세부 관심 분야가 일치하는 기회에 더 높은 우선순위를 부여하는 방향으로 설계했다.

신규 등록 여부와 마감 임박 여부는 보조적인 정렬 기준으로 고려했으며, 구체적인 가중치와 최종 추천 순서는 추가 검토하기로 했다.

또한 초기 사용자 행동 데이터가 부족한 상황에서는 협업 필터링이나 Learning to Rank를 바로 적용하기보다,   
명시적인 조건을 활용한 추천을 먼저 구현하는 것이 적절하다고 판단했다.

> 통합 검색·필터 및 페이지네이션 설계

온통청년 정책과 고용24 훈련과정을 통합 조회하기 위한 검색 구조를 구체화했다.

정책 유형에 따른 조회 범위와 지역, 관심 분야, 신청 가능성 등의 필터 조합을 검토하고, 정렬 및 페이지네이션 처리 방식도 함께 고려했다.

특히 `ELIGIBLE`과 `POSSIBLY_ELIGIBLE`을 동시에 선택하는 경우에는   
두 상태를 모두 포함하도록 OR 조건으로 처리해야 한다는 점을 정리했다.

신청 가능성 판정 결과를 검색에서 사용하는 과정에서는 필터링과 페이지네이션의 처리 순서도 중요했다.

페이지를 먼저 나눈 뒤 신청 가능성 조건으로 결과를 제외하면 응답 건수가 요청한 페이지 크기보다 적어지거나,   
실제 조건에 맞는 데이터가 다음 페이지에 남을 수 있다는 점을 확인했다.

따라서 신청 가능성 판정 결과를 검색 조건에 어떻게 반영할지,   
필터링 이후 페이지네이션을 수행할 수 있도록 어떤 데이터 구조가 필요한지 검토했다.

또한 검색 결과의 총 건수와 페이지 정보가 실제 필터링 결과를 반영하도록   
정책 엔진의 판정 결과 저장·조회 방식과 데이터 계약을 함께 고려해야 한다는 점을 정리했다.

> 영역 간 데이터 계약 검토

검색·추천·관심 기회·사용자 행동 이벤트 기능을 병렬로 개발하기 위한 공통 데이터 계약을 검토했다.

검색과 추천은 정책 엔진에서 생성한 신청 가능성 판정 결과에 의존하므로,   
결과의 저장 위치와 조회 방식, 갱신 시점을 담당 영역과 합의할 필요가 있었다.

특히 신청 가능성 판정 결과가 사용자별로 달라진다는 점을 고려해   
공통 기회 데이터와 사용자별 판정 데이터의 역할을 구분해야 한다는 점을 확인했다.

> 인증·사용자 및 정책 엔진 PR 코드 리뷰

팀원들의 인증·사용자 및 정책 엔진 관련 구현을 검토하면서 코드와 서비스 요구사항의 일치 여부를 확인했다.

인증 영역에서는 쿠키 기반 JWT 인증의 CSRF 대응, 쿠키 보안 속성, Refresh Token 재발급 동시성,   
카카오 이메일 누락 가능성, 비로그인 조회 API의 접근 권한 등을 검토했다.

특히 Y:ON은 비로그인 사용자도 기회 검색과 상세 조회를 이용할 수 있으므로   
공개 API와 인증이 필요한 API의 접근 정책을 구분해야 한다는 점을 확인했다.

정책 엔진 영역에서는 신청 조건이 확인되지 않은 정책을 무조건 신청 가능으로 처리해도 되는지 검토했다.

실제 제한 조건이 없는 정책과 데이터 누락으로 조건을 확인할 수 없는 정책은 서로 다르므로,   
정규화 과정과 신청 가능성 판정에서 이를 구분해야 한다는 점을 정리했다.

또한 신청 가능성 판정 결과를 저장하고 검색·추천 영역에서 활용하는 방식과 도메인 간 책임 분리의 필요성을 검토했다.

코드 리뷰를 통해 개별 기능의 정상 동작뿐 아니라   
다른 영역에서 해당 데이터를 사용할 때 발생할 수 있는 문제까지 고려해야 한다는 점을 확인했다.

---

> Y:ON 프로젝트 멘토링

사용자별 신청 가능성 판정 방식으로 전체 사전 판정, 요청 시 판정, 후보 선별 후 판정 중 어떤 방식이 Y:ON에 적합한지 질문했다.

전체 사전 판정은 사용자 수가 증가할수록 저장량과 재판정 비용이 커질 수 있으며, 판정 결과의 최신성을 관리해야 한다는 점을 확인했다.

멘토는 프로필 설정 이후 요청 시 판정하고, 반복 조회되는 결과에는 캐싱을 활용하는 방식을 제안했다.   
또한 대량 데이터는 청크·페이징 단위로 처리하고,   
판정 조건의 확장성에 따라 코드 기반 규칙이나 SpEL·JSON 기반 규칙 관리를 검토할 수 있다는 피드백을 받았다.

데이터 수집·정제 영역에서는 Spring Batch 활용과 처리 순서 보장, 실패한 데이터의 식별 및 선택적 재처리가 중요하다는 점을 확인했다.

AWS 기술 선택에서는 RDS와 EC2 직접 운영 등의 대안을 비용·성능·운영 부담 측면에서 비교하고,   
실제 측정 결과를 바탕으로 선택 이유를 설명할 수 있어야 한다는 피드백을 받았다.

또한 팀원별 진행 상황을 공유하고, 데이터 처리 실패나 장애를 감지할 수 있는 구조를 고려해야 한다는 점을 정리했다.

이번 멘토링을 통해 서비스 요구사항을 먼저 정의하고, 처리 비용과 안정성, 유지보수성을 기준으로 적절한 기술을 선택해야 한다는 점을 배웠다.

## 헷갈렸던 점

`ELIGIBLE`과 `POSSIBLY_ELIGIBLE`을 함께 선택한 검색 조건을 어떻게 처리해야 하는지가 헷갈렸다.

하나의 기회가 두 상태를 동시에 만족해야 하는 AND 조건이 아니라,   
선택한 상태 중 하나에 해당하면 포함하는 OR 조건으로 처리해야 한다는 점을 정리했다.

신청 가능성 필터링을 페이지네이션 이후에 수행해도 되는지도 고민했다.

페이지를 먼저 나누면 조건에 맞는 데이터가 뒤쪽 페이지에 남아 있어도 현재 페이지에서는 제외될 수 있으므로,   
필터링 결과를 기준으로 페이지를 구성해야 한다는 점을 확인했다.

정책에 신청 조건이 명시되지 않은 경우에도 신청 가능으로 판단해도 되는지가 고민됐다.

실제 제한 조건이 없는 경우와 데이터가 누락되어 판단할 수 없는 경우는 다르므로,   
정책 엔진에서 정보의 확실성을 구분하고 검색·추천에서도 해당 판정 결과를 활용해야 한다는 점을 정리했다.

---

전체 사전 판정, 요청 시 판정, 후보 선별 후 판정 중 어떤 방식이 Y:ON에 적합한지가 고민됐다.

멘토링을 통해 판정 방식마다 저장량, 응답 시간, 결과의 최신성에 차이가 있으며, 요청 시 판정과 캐싱도 고려할 수 있다는 점을 확인했다.   
따라서 실제 사용자 규모와 서비스 요구사항을 기준으로 비교할 필요가 있다는 점을 정리했다.

## 오늘 느낀 점

오늘은 추천 알고리즘의 기준을 구체화하면서 통합 검색·필터와 신청 가능성 판정 결과가 어떻게 연결되어야 하는지 검토했다.

특히 신청 가능성 판정 결과의 신뢰성이 확보되지 않으면 추천 후보를 올바르게 선정하기 어렵고,   
필터링과 페이지네이션의 처리 순서가 잘못되면 사용자에게 불완전한 검색 결과를 제공할 수 있다는 점을 확인했다.

또한 검색·추천 영역은 단순히 점수를 계산하는 기능이 아니라 정책 엔진의 결과를 정확하게 활용하고,   
사용자에게 일관된 조회 결과를 제공하는 역할도 중요하다는 점을 배웠다.

코드 리뷰와 데이터 계약 검토를 통해 담당 기능만 독립적으로 설계하기보다   
다른 도메인과의 의존성과 데이터 정합성을 함께 고려해야 한다는 점을 확인했다.

초기에는 복잡한 추천 알고리즘을 도입하기보다 현재 서비스의 데이터와 요구사항에 적합한 구조를 설계하고,   
구현 이후 실제 추천 결과와 사용자 행동을 측정해 개선하는 방향이 중요하다고 판단했다.

특히 대기업에서 근무하는 개발자로부터 실제 현업에서는 기술을 어떤 기준으로 선택하고 운영하는지 들을 수 있어 좋았다.   
평소에는 생각하지 못했던 문제를 대규모 서비스 운영 관점에서 살펴보고, 여러 대안을 비교해 볼 수 있었다는 점이 의미 있었다.

다만 일부 내용은 아직 충분히 이해하지 못해 추가 학습이 필요하다고 느꼈다.   
구체적인 대안과 해결 방향까지 제안해 주셔서 도움이 되었고, 동시에 기술의 동작 원리와 선택 근거를 더 깊이 공부해야겠다는 생각이 들었다.
