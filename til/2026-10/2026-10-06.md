## 오늘 학습 정리

**project**

* Y:ON: 4차 팀 프로젝트 - 주제 선정 및 서비스 기획

## 오늘 배운 내용

오늘은 4차 팀 프로젝트를 시작하며 각자 준비한 아이디어를 공유하고,   
실제 서비스로 운영할 수 있는지와 사용자에게 지속적인 가치가 있는지, 백엔드에서 의미 있는 문제를 다룰 수 있는지를 기준으로 비교했다.

단순 CRUD나 기능 수를 늘리는 것보다 실제 사용자가 필요로 하는 문제를 해결하고,   
운영 과정에서 성능·정합성·외부 시스템 연동과 같은 문제를 발견하고 개선할 수 있는지를 중요하게 봤다.

여러 아이디어를 검토하고 투표한 결과,   
여러 기관에 흩어진 청년 지원정책을 사용자 조건에 맞게 추천하고 정책 변화를 지속적으로 추적해 알려주는 서비스를 최종 주제로 선정했다.

이후 서비스의 핵심 기능과 백엔드 영역을 데이터 수집, 정책 엔진, 검색·추천, 추적·알림으로 나누고   
각 영역에서 해결할 기술적 문제를 함께 정리했다.

마지막으로 팀명은 **기웃기웃**, 서비스명은 **Y:ON**으로 결정했다.

## 실습 및 과제

> 4차 팀 프로젝트 아이디어 비교 및 주제 선정

팀원들이 각자 준비한 AI 업무 자동화, 코딩테스트 플랫폼, 스트리밍, 비용 관리, 청년 지원정책 등의 아이디어를 공유하고 비교했다.

아이디어를 선택할 때 단순히 구현할 기능이 많은지를 보기보다 실제 사용자가 지속적으로 사용할 이유가 있는지,   
필요한 데이터를 확보할 수 있는지, 운영 과정에서 백엔드가 해결할 의미 있는 문제가 있는지를 기준으로 검토했다.

여러 아이디어를 비교하고 투표한 결과, 여러 기관에 흩어진 청년 지원정책을 개인 조건에 맞게 추천하고 변화를 추적하는 서비스를 진행하기로 했다.

> 청년 지원정책 서비스 기획

서비스의 주요 사용자는 자신에게 맞는 지원정책을 찾기 위해 여러 사이트를 반복해서 확인해야 하는 청년으로 설정했다.

사용자의 나이, 지역, 취업·재학 상태 등의 조건과 정책의 자격 조건을 비교해   
신청 가능성이 높은 정책을 보여주는 것을 기본 기능으로 정했다.

단순 검색 서비스에서 끝내지 않고 사용자가 자신의 조건을 한 번 등록하면 서버가 정책 데이터를 지속적으로 추적해   
신규 정책, 조건 변경, 신청 시작, 마감 임박 등의 변화를 감지하고 필요한 사용자에게 알려주는 방향으로 차별화했다.

초기 데이터 소스는 온통청년과 잡아바를 중심으로 검토하기로 했다.

외부 API가 존재한다는 이유만으로 바로 사용할 수 있다고 가정하지 않고   
실제 제공 범위와 이용 조건, 접근 가능 여부를 먼저 확인해야 한다는 점도 정리했다.

> 백엔드 영역 및 역할 연결 정리

서비스에 필요한 백엔드 영역을 데이터 수집, 정책 엔진, 검색·추천, 추적·알림으로 나눴다.

데이터 수집에서는 외부 API 연동과 Scheduler 기반 동기화, Raw 데이터 저장, 수집 실패와 중복 데이터 대응을 다룬다.

정책 엔진에서는 서로 다른 정책 데이터를 내부 구조로 정규화하고 중복을 제거하며,   
사용자 조건과 정책 조건을 비교해 신청 가능성을 판단한다.

검색·추천에서는 복합 조건 검색과 랭킹, 개인화, 사용자 행동 데이터 수집을 다루고 검색 쿼리와 인덱스 등의 성능 개선도 검토한다.

추적·알림에서는 정책 변경을 감지하고 영향받는 사용자를 찾으며 중복 이벤트나 알림 실패를 처리한다.

이후 기존에 구분했던 PO, 아키텍트형 역할, API 구현 담당, 고급 기능·성능 개선형 역할, AI 서비스·추천 시스템 담당과 비교해   
각 영역이 어떤 역할과 가장 밀접한지 정리했다.

예를 들어 검색·추천 영역은 검색 API와 데이터 모델 구현 측면에서는 API 구현 담당,   
검색 쿼리와 인덱스 및 랭킹 개선 측면에서는 고급 기능·성능 개선형 역할, 개인화 측면에서는 AI 서비스·추천 시스템 담당과 밀접하다고 봤다.

이를 통해 각 영역이 기존 역할 분류 중 어떤 업무와 밀접한지 확인했다.

> 팀명 및 서비스명 결정

서비스 방향과 백엔드 영역을 정리한 뒤 팀명과 서비스명을 결정했다.

짧고 기억하기 쉬우면서 서비스 의미와 자연스럽게 연결되고, 기존 서비스와 검색 충돌이 적은 이름을 찾기 위해 여러 후보를 검토했다.

최종적으로 팀명은 **기웃기웃**, 서비스명은 **Y:ON**으로 정했다.

`Y:ON`은 `Youth + ON`의 의미를 담아 청년에게 필요한 기회를 발견하고 활성화한다는 서비스 방향을 표현한다.

## 헷갈렸던 점

서비스의 백엔드 영역을 데이터 수집, 정책 엔진, 검색·추천, 추적·알림으로 나눈 뒤,  
기존에 구분했던 PO, API 구현, 성능 개선, AI·추천 등의 역할과 어떻게 연결해서 볼 수 있는지가 헷갈렸다.

검색·추천 영역만 보더라도 검색 API와 데이터 모델 구현, 검색 성능 개선, 개인화 추천처럼 여러 성격의 업무가 함께 포함될 수 있었다.

따라서 각 영역을 특정 역할 하나에 억지로 대응시키기보다,  
실제로 어떤 문제와 업무를 다루는지를 기준으로 가장 밀접한 역할을 파악하는 것이 적절하다는 점을 정리했다.

외부 정책 API도 공개되어 있다는 사실만으로 실제 서비스에서 바로 사용할 수 있는 것은 아니었다.

API의 실제 접근 가능 여부와 제공 데이터, 이용 조건을 먼저 확인한 뒤 서비스 설계에 반영해야 한다는 점을 정리했다.

## 오늘 느낀 점

오늘은 코드를 작성하기보다 프로젝트의 주제를 선택하고 서비스 방향을 구체화하는 데 집중했다.

여러 아이디어를 비교하면서 기술적으로 다양한 내용을 넣을 수 있는 서비스보다 실제 사용자의 문제가 명확하고,   
서비스를 운영하는 과정에서 해결해야 할 백엔드 문제가 자연스럽게 발생하는 주제를 선택하는 것이 중요하다고 느꼈다.

특히 이번 프로젝트에서는 기능을 먼저 나누기보다   
데이터 수집 실패, 정책 데이터 변경, 검색 성능, 알림 실패와 같은 운영 상황까지 생각하면서 백엔드에서 다룰 영역을 정리했다.

앞으로도 단순히 기술을 적용하는 데서 끝내지 않고 어떤 문제가 발생했고 왜 해당 방법을 선택했는지,   
개선 결과가 어떻게 달라졌는지를 기록하는 것이 중요하다고 느꼈다.
