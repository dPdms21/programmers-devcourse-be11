# 2026-10-08 TIL (Today I Learned)

## 오늘 학습 정리

**project**

* Y:ON - 정책 데이터 정규화 PoC 및 LLM 신청 조건 추출·비교 실험

## 오늘 배운 내용

오늘은 Y:ON의 정책 데이터 품질 문제를 실제 데이터 기반 PoC로 검증하고, 복잡한 신청 조건을 구조화하기 위한 LLM 활용 가능성을 실험했다.

온통청년 API의 정책 데이터 200건과 필드·코드북을 분석하면서 빈 값, 형식 불일치, 자유서술 조건의 혼합, 공식 원문과의 정보 차이를 확인했다.   
이를 통해 데이터를 수집하는 것과 신청 가능성 판정에 활용할 수 있도록 신뢰성을 확보하는 것은 별개의 문제라는 점을 알게 됐다.

정책의 최신성을 확보하기 위해 API와 공식 원문 크롤링을 함께 활용하는 방향을 검토하고,   
기존 청년정책 서비스와 고용24 API를 조사해 데이터 활용 및 확장 가능성을 확인했다.

이후 정책 18건을 튜닝용 6건과 최종 평가용 12건으로 구분했다.   
GPT-5.6의 초기 추출 오류를 바탕으로 프롬프트를 개선한 뒤,   
동일한 프롬프트 v2와 출력 스키마를 적용해 GPT-5.6과 GPT-6의 신청 조건 추출 결과를 비교했다.

두 모델 모두 튜닝용 6건의 JSON·스키마 검증을 통과했지만 전체 자동 검증에서는 GPT-5.6이 1건, GPT-6이 4건 통과했다.   
다만 의미 해석 오류가 남아 있었고 Gold Dataset을 통한 정확도 검증도 진행하지 않아 실제 정확도의 우열을 판단할 수는 없었다.

이번 실험에서는 규칙 기반 처리와 LLM 활용의 가능성 및 한계를 확인했으며,   
팀원별 실험 결과를 비교한 뒤 Y:ON에 적합한 데이터 처리 방식을 결정하기로 했다.

## 실습 및 과제

> 온통청년 정책 데이터 분석 및 전처리 PoC

온통청년 API의 실제 정책 데이터 200건과 필드·코드북을 분석하고, 정규화 기준과 공식 원문 접근 가능성을 검토했다.

연령, 소득, 거주지역, 취업 상태 등의 신청 조건은 정형 필드뿐 아니라 자유서술 필드에도 혼합되어 있었고,   
빈 값이나 형식이 일정하지 않은 데이터도 존재했다.

정규화 과정에서는 지원금과 신청자의 소득 조건, 사업기간과 신청기간, 조건이 적용되는 주체와 지역 범위 등을 구분해야 한다는 점을 확인했다.

또한 값이 비어 있다는 이유만으로 제한 조건이 없다고 판단하거나,   
숫자만 보고 비교 연산자와 상한·하한을 임의로 결정해서는 안 된다는 점을 정리했다.

실제 데이터를 검토하면서 명확한 정형 데이터는 규칙 기반으로 처리할 수 있지만,   
여러 자격조건의 AND/OR 관계와 예외, 적용 대상 등이 포함된 자유서술 조건은 단순 규칙만으로 해석하기 어렵다는 점을 확인했다.

따라서 원본 데이터를 보존하면서 규칙 기반으로 정규화할 수 있는 부분과 추가적인 의미 해석이 필요한 부분을 분리하는 접근이 필요하다고 판단했다.

> 정책 원문 크롤링 및 최신성 관리 검토

온통청년 API와 공식 정책 공고 사이에 정보 누락이나 반영 시점의 차이가 발생할 수 있다는 점을 확인했다.

API를 기본 수집 경로로 활용하고 정책 상세 URL과 공식 원문을 추가로 확인해 정보를 보완하는 방식을 검토했다.

크롤링은 일반 HTML 수집이 가능한 경우와 사이트별 구조에 맞는 처리가 필요한 경우를 구분하고,   
모든 정책을 AI 크롤러로 탐색하는 방식은 비용과 구현 복잡도 측면에서 부담이 있다고 판단했다.

또한 공식 원문도 항상 최신이라고 가정하지 않고 출처와 수집 시점, 데이터 차이를 함께 관리해야 한다는 점을 정리했다.

Y:ON은 정책 변화를 추적하는 서비스이므로 초기 수집뿐 아니라 변경 감지와 최신 상태 유지도 중요한 설계 문제라는 점을 확인했다.

> 기존 청년정책 서비스 및 고용24 API 조사

온통청년 API를 활용하는 다른 서비스를 조사하고, 청년모아를 중심으로 기존 정책 정보 제공 방식과 Y:ON의 차이를 검토했다.

단순한 정책 탐색과 정보 제공에서 나아가 신청 가능성 판정과 정책 변화 추적을 제공하려면   
데이터의 정합성과 최신성 관리가 필요하다는 점을 확인했다.

또한 청년 지원정책 외에 부트캠프와 직업훈련 정보까지 제공하기 위해 고용24 API를 조사하고, 인증키를 발급받아 실제 응답 데이터를 확인했다.

교육·훈련 기회를 추가 데이터 소스로 활용하는 방향을 긍정적으로 검토했지만,   
일반 청년정책과 구조 및 신청 조건이 달라 별도의 정규화 기준이 필요하다고 판단했다.

> LLM 기반 신청 조건 추출 및 모델 비교 실험

GPT-5.6의 초기 신청 조건 추출 결과에서 오류를 확인하고 프롬프트를 개선한 뒤,   
동일한 프롬프트 v2와 출력 스키마를 적용해 GPT-5.6과 GPT-6의 결과를 비교했다.

두 모델 모두 JSON·스키마 검증은 6건 모두 통과했지만, 전체 자동 검증은 GPT-5.6이 1건, GPT-6이 4건 통과했다.

GPT-5.6은 명시되지 않은 비교 연산자를 임의로 확정하거나 예외의 적용 범위를 잘못 해석하는 문제가 있었다.

GPT-6은 복잡한 예외를 `UNKNOWN`으로 보류하고 일부 누락된 조건을 보존하는 사례가 있었지만,   
조건의 값 형식이나 논리 관계를 잘못 처리하는 문제도 남아 있었다.

또한 GPT-5.6의 일부 출력에서 한글 대체문자가 발생했으나, 모델 자체의 문제인지 전달·저장 과정의 문제인지는 확인되지 않았다.

이번 실험에서는 GPT-6의 자동 검증 통과 건수가 더 많았지만,  
Gold Dataset을 통한 정확도 검증은 진행하지 않았으므로 실제 성능이 더 우수하다고 단정할 수는 없었다.

> 실험 결과 및 향후 검토 방향

이번 실험을 통해 복잡한 비정형 신청 조건에 LLM을 활용할 가능성과 의미 검증의 필요성을 확인했다.

다만 사람이 검수한 Gold Dataset이 없고, 정책 6건을 각각 1회씩 추론한 결과이므로 실제 정확도나 모델의 우열을 확정할 수는 없었다.

따라서 개인 실험 결과만으로 Y:ON의 정규화 방식이나 사용할 모델을 결정하지는 않았다.

팀원들도 각자 데이터 처리와 LLM 활용 방법을 실험하고, 이후 결과와 오류 유형, 검증 방법 등을 비교해 프로젝트에 적합한 방식을 찾아보기로 했다.

## 헷갈렸던 점

정책 데이터에서 숫자나 코드가 확인되면 이를 그대로 신청 조건으로 변환해도 되는지가 헷갈렸다.

실제 데이터에서는 지원 금액과 소득 제한, 사업기간과 신청기간처럼 의미가 다른 값이 혼합되어 있었고,   
조건이 적용되는 대상이나 비교 연산자가 명확하지 않은 경우도 있었다.

따라서 값을 추출하는 것뿐 아니라 문맥과 적용 범위를 확인하고, 불명확한 조건을 임의로 확정하지 않아야 한다는 점을 정리했다.

LLM이 생성한 결과가 JSON·스키마 검증을 통과했는데도 전체 자동 검증에서 실패하는 이유도 고민했다.

스키마 검증은 데이터의 구조를 확인할 수 있지만, 조건 간 논리 관계나 예외의 적용 범위, 원문과의 의미 일치까지 보장하지는 않았다.

특히 예외의 효과가 명시되지 않았는데 `OVERRIDE`로 확정하거나 경력 면제를 학력 조건까지 적용할 위험이 있는 결과를 보면서   
조건의 참조 관계와 적용 범위를 별도로 검증해야 한다는 점을 확인했다.

GPT-6이 전체 자동 검증에서 더 많이 통과했는데도 정확도가 더 높다고 단정할 수 없는 이유도 정리했다.

이번 실험은 정책 6건을 각각 1회씩 추론한 결과이고 Gold Dataset이 없어 정답과 직접 비교하지 못했다.   
따라서 자동 검증 결과만으로 실제 신청 가능성 판정의 정확도를 평가할 수 없다는 점을 확인했다.

또한 한글 대체문자가 발생한 원인이 모델 출력인지 데이터 전달·저장 과정인지 확인되지 않아   
관찰된 오류를 모두 모델 성능 문제로 해석해서는 안 된다는 점을 정리했다.

## 오늘 느낀 점

오늘은 전날 발견했던 정책 데이터 품질 문제를 실제 데이터 분석과 PoC로 구체화하고, 해결 방법을 비교하는 데 집중했다.

200건의 정책 데이터를 분석하면서 데이터를 수집하는 것과 신뢰할 수 있는 신청 조건으로 변환하는 것은 다른 문제라는 점을 확인했다.

GPT-5.6과 GPT-6을 비교하면서 JSON 생성에 성공하는 것보다 원문의 의미를 정확하게 보존하는 것이 더 중요하고,   
자동 검증에서 더 좋은 결과를 보였더라도 확인하지 않은 정확도나 성능 개선율까지 주장해서는 안 된다는 점을 배웠다.

특히 Y:ON에서는 잘못된 신청 조건이 사용자에게 잘못된 추천이나 신청 가능성 판정으로 이어질 수 있으므로,   
불확실한 조건을 임의로 확정하지 않고 근거와 검증 상태를 유지하는 것이 중요하다고 판단했다.

이번 실험을 통해 LLM을 적용하는 것 자체보다 추출 결과의 신뢰성과 검증 방법을 함께 고려해야 한다는 점을 배웠다.   
이후 팀원들의 실험 결과와 비교하면서 현재 프로젝트에 적합한 처리 방법을 찾아갈 필요가 있다고 느꼈다.
