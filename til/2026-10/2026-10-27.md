## 오늘 배운 내용

오늘은 Y:ON 프런트엔드 V1의 코드 리뷰에서 발견된 인증·푸시·검색 관련 오류를 수정하고, 화면 변경에 맞춰 브라우저 E2E 테스트를 보완했다.

푸시 구독 정리와 인증 상태 관리 과정에서 발생하는 비동기 요청 경합을 수정하고, 푸시 알림 클릭 시 화면 이동과 지역 필터의 오류를 해결했다.   
이후 기존 테스트의 실패 원인을 분석해 검증 목적을 유지하면서 테스트를 갱신했다.

다음으로 정규화 공고 약 14만 건을 활용하는 독립적인 PostgreSQL 성능 측정 환경을 구성하고, 통합 검색의 SQL 실행 계획을 분석했다.

마감일 정렬의 중복 서브쿼리와 지역 검색의 비효율적인 실행 계획을 개선하고, 인덱스 후보를 비교했다.   
또한 JIT 컴파일 비용과 인덱스의 쓰기 성능 영향을 함께 측정하면서 실제 서비스에 적합한 최적화 방향을 검토했다.

## 실습 및 과제

> 프런트엔드 푸시 구독 정리 및 인증 상태 동기화 오류 수정

프런트엔드 V1 코드 리뷰에서 확인된 푸시 구독과 인증 상태 관리 문제를 수정했다.

브라우저에 푸시 구독이 남아 있지만 localStorage의 소유 정보가 유실되면 기존 로직이 구독 해제를 건너뛰는 문제를 확인했다.

또한 푸시를 사용하지 않는 사용자도 인증 확인 과정에서 불필요하게 푸시 락을 획득하거나 구독 정리를 시도하는 문제가 있었다.

이에 푸시 정리 흐름을 분리하여 정리 작업의 실패가 인증 조회, 로그아웃, 회원 탈퇴를 중단시키지 않도록 수정했다.

알림 설정에서는 자동 푸시 재연결 과정에서 이전에 조회한 설정을 다시 저장해 최신 사용자 설정을 덮어쓰는 경쟁 상태를 발견했다.   
자동 재연결의 불필요한 설정 PUT 요청을 제거하여 해결했다.

또한 토큰 재발급에 실패한 Promise가 재사용되어 이후 인증 요청까지 실패하는 문제를 수정하고,   
인증 오류 상태에 따라 재시도 여부를 구분하도록 했다.

이 과정에서 부가적인 푸시 구독 정리가 핵심 인증 기능의 성공 여부를 결정해서는 안 되며,   
실패한 비동기 작업의 상태도 적절하게 정리해야 한다는 점을 확인했다.

> 푸시 알림 이동 및 지역 필터 오류 수정

푸시 알림을 클릭했을 때 기존 앱 탭으로 이동하지 못하는 문제를 확인했다.

FCM 서비스 워커의 scope가 제한되어 있어 `client.navigate()`로 앱 화면을 직접 이동시키기 어려운 상황이었다.

이를 해결하기 위해 서비스 워커가 `postMessage`로 이동 요청을 전달하고, 앱이 자체 라우터를 통해 화면을 전환하도록 수정했다.

또한 동일 출처와 허용된 알림 경로를 검증하여 외부 주소로 이동하지 않도록 제한했다.

프로필 화면에서는 TanStack Query의 `isFetching`이 최초 조회뿐 아니라 백그라운드 재조회에서도 활성화되는 점을 확인했다.   
인증 재확인 중 입력 폼이 사라지지 않도록 최초 확인과 재확인을 구분했다.

검색 화면에서는 지역 API 로딩이나 오류가 발생했을 때 다른 필터까지 사용할 수 없었던 문제를 수정했다.   
지역 목록을 조회하기 전에는 코드 형식을 검증하고, 조회 완료 후에는 실제 지역 목록을 기준으로 검증하도록 처리했다.

> 브라우저 E2E 테스트 보완 및 프런트엔드 V1 검증

UI 변경 이후 실패한 브라우저 E2E 테스트의 원인을 분석했다.

Firebase 설정 안내, 저장 버튼의 접근 가능한 이름, 홈 화면 CTA 노출 조건, 상세 화면 구조가 변경됐지만   
일부 테스트는 이전 화면을 기준으로 작성되어 있었다.

기존 테스트의 검증 목적을 유지하면서 선택자와 기대 조건을 갱신하고,   
수정 전후 코드를 같은 조건에서 비교하여 새로운 회귀 오류가 발생하지 않았는지 확인했다.

최종적으로 Chrome E2E를 포함한 전체 287개 테스트가 통과했다.

이후 프런트엔드 V1을 병합하고 AWS 배포 환경에서 카카오 로그인을 확인했다.

CloudFront의 HTTPS 주소로 접속했지만 OAuth2 Redirect URI가 HTTP로 생성되어 카카오 `KOE006` 오류가 발생했다.

이에 CloudFront와 ALB/Nginx의 `X-Forwarded-Proto` 전달,   
Spring Boot의 Forwarded Header 처리 및 Redirect URI 설정을 확인해야 한다는 점을 파악했다.

로컬에서 정상 동작한 인증 기능도 배포 환경의 프록시와 HTTPS 설정에 따라 실패할 수 있으므로,   
프런트엔드뿐 아니라 백엔드와 인프라의 설정을 함께 검증해야 한다는 점을 확인했다.

> 검색 성능 측정용 독립 DB 환경 구성 및 병목 분석

정규화 공고 140,657건을 활용하여 기존 개발 DB와 분리된 PostgreSQL 성능 측정 환경을 구성했다.

검색 API의 응답 시간을 측정하고 `EXPLAIN ANALYZE`로 SQL 실행 계획을 확인했다.

특히 청년정책 마감일 정렬에서 Hibernate Criteria가 동일한 조건을 반복 생성하면서 서브쿼리가 51개까지 증가하는 문제를 발견했다.

이 과정에서 PostgreSQL의 예상 실행 비용이 높아져 JIT 컴파일이 발생했으며, 초기 측정에서는 컴파일에만 약 13.5초가 소요됐다.

JIT ON/OFF를 비교하면서 일부 검색에서는 실제 데이터 조회보다 JIT 컴파일 비용이 응답 지연에 더 큰 영향을 미칠 수 있다는 점을 확인했다.

이를 통해 SQL 실행 시간이 길더라도 실제 병목이 데이터 읽기인지, 정렬·조인인지, JIT 컴파일인지 구분하여 분석해야 한다는 점을 학습했다.

> 통합 검색 정렬 및 지역 필터 SQL 최적화

마감일 정렬에서 반복 생성되는 조건을 줄이고 `Nulls.LAST`를 적용하여 서브쿼리를 51개에서 21개로 감소시켰다.

이후 지역 검색에서는 청년정책과 직업훈련의 지역 판정 조건을 유형별로 분리하여 불필요한 서브쿼리 평가를 줄였다.

이 과정에서 전국 대상 청년정책이 검색 결과에서 누락되지 않도록 `NATIONAL` 판정 조건을 유지했다.

직업훈련 지역 검색에서는 기존 Seq Scan과 hashed SubPlan 중심의 실행 계획이 Parallel Hash Semi Join으로 변경됐으며,   
JIT ON 기준 약 10배의 실행 시간 개선을 확인했다.

청년정책 지역 검색에서는 `EXISTS` 개수 자체를 줄이지 않고 상관 구조를 변경하여 기존 인덱스를 활용하도록 개선했다.

해당 검색의 API 응답 시간 중앙값은 1,728ms에서 138ms로 감소했다.

이를 통해 서브쿼리의 개수만 줄이는 것보다   
상관관계와 실제 실행 계획, 인덱스 접근 방식을 개선하는 것이 성능에 더 큰 영향을 줄 수 있다는 점을 확인했다.

> 인덱스 후보 비교 및 조회·쓰기 비용 검증

SQL 구조 개선 이후에도 일부 지역·모집 상태 검색에서 전체 스캔과 높은 JIT 비용이 남아 있어   
별도 PostgreSQL 실험 DB에서 인덱스 5개 후보를 비교했다.

비교한 인덱스 중 전국 대상 조건의 부분 인덱스, 신청기간 부분 인덱스, 공고 유형·최신순 정렬 복합 인덱스 등 3개를 유력 후보로 정리했다.

세 인덱스를 조합한 실험에서 지역+모집 중 검색은 2,433ms에서 1,605ms로, 정책+지역+마감일순 검색은 3,472ms에서 2,508ms로 개선됐다.

반면 복합 인덱스의 쓰기 비용을 별도 테스트 테이블에서 반복 측정한 결과 INSERT 시간은 약 51%, UPDATE 시간은 약 35% 증가했다.

해당 수치는 실험용 테이블의 측정 결과이므로 실제 정규화 배치의 처리 성능에 그대로 적용할 수는 없다.

또한 일부 인덱스는 PostgreSQL의 예상 Cost를 크게 줄였지만 실제 실행 시간은 오히려 증가했다.

이를 통해 인덱스의 효과를 판단할 때 실행 계획의 예상 비용뿐 아니라   
실제 응답 시간과 JIT 비용, 쓰기 성능까지 함께 비교해야 한다는 점을 확인했다.

인덱스 조합은 실험 결과를 바탕으로 검토한 후보이며, 공유 DB에 적용할지는 추가적인 판단이 필요하다.

## 헷갈렸던 점

푸시 알림 클릭 시 서비스 워커가 기존 앱 탭을 직접 이동시키지 못하는 이유를 확인했다.   
서비스 워커의 scope에 따라 제어 가능한 클라이언트가 제한되므로, 앱에 이동 요청을 전달하고 라우터에서 처리하도록 구분했다.

또한 TanStack Query의 `isFetching`이 최초 조회뿐 아니라 백그라운드 재조회에서도 활성화된다는 점을 확인했다.   
인증 재확인 과정에서 입력 중인 폼이 사라지지 않도록 두 상태를 구분해야 한다는 점을 이해했다.

검색 성능 분석에서는 PostgreSQL의 JIT가 항상 성능을 개선하는지 확인했다.   
컴파일 비용이 실행 시간 절감 효과보다 크면 오히려 응답이 지연될 수 있으므로, JIT ON/OFF를 같은 조건에서 비교해야 한다는 점을 배웠다.

인덱스는 조회 시 임시로 생성되는 구조인지, 실제로 저장되는 자료구조인지 확인했다.   
인덱스는 별도로 저장·관리되며, 조회뿐 아니라 데이터 변경 시 쓰기 비용에도 영향을 준다는 점을 이해했다.

또한 일부 인덱스에서 예상 Cost가 감소했는데도 실제 실행 시간이 증가하는 이유를 검토했다.   
실행 계획의 예상 비용과 실제 측정 결과는 다를 수 있으므로, Cost만으로 최적화 효과를 판단해서는 안 된다는 점을 확인했다.

검색 API에만 JIT 비활성화를 적용할 수 있는지도 검토했다.   
공유 DB 설정 변경과 트랜잭션 단위 설정의 차이를 고려하고, 커넥션 재사용에 영향을 주지 않는지 추가 검증이 필요하다는 점을 정리했다.

## 오늘 느낀 점

오늘은 프런트엔드 코드 리뷰에서 확인된 오류를 수정하면서 개별 기능과 테스트가 정상 동작하더라도   
실제 인증 상태와 비동기 요청이 결합되면 예상하지 못한 문제가 발생할 수 있다는 점을 확인했다.

특히 푸시 구독 정리와 인증 흐름을 분리하고,   
서비스 워커의 제어 범위를 고려해 화면 이동 방식을 수정하면서 기능 간 책임과 실패 전파 범위를 명확히 하는 것이 중요하다고 느꼈다.

브라우저 E2E 테스트에서는 단순히 테스트를 통과시키는 것보다 기존 검증 목적이 유지되는지 확인해야 한다는 점을 배웠다.   
또한 AWS 배포 환경의 OAuth2 오류를 통해 로컬 테스트와 실제 배포 환경의 동작은 별도로 검증해야 한다는 점을 확인했다.

검색 성능 최적화에서는 SQL 구조와 실행 계획, JIT 컴파일 비용을 함께 분석해야 실제 병목을 파악할 수 있었다.   
특히 조회 성능이 개선되더라도 인덱스로 인해 데이터 수집·정규화 과정의 쓰기 비용이 증가할 수 있으므로,   
측정 결과와 운영 비용을 함께 고려해 적용 여부를 판단해야겠다고 생각했다.
