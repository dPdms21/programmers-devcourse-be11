## 오늘 배운 내용

오늘은 Y:ON의 직업훈련 NCS 분류 체계를 반영해 통합 검색에 세부 분류 필터를 추가했다.

청년정책과 직업훈련의 분류 기준 차이를 고려하여 공통 카테고리 구조를 유지하면서 NCS 2차분류까지 검색할 수 있도록 확장했다.   
이후 NCS 코드 정규화부터 DB 저장, 검색 API 조회까지 이어지는 흐름을 검증하고 검색 필드의 설명을 보완했다.

다음으로 개인화 추천 V1 구현을 위해 사용자별 숨김 공고 ID를 일괄 조회하는 기능을 추가하고,   
추천 후보를 DB에서 먼저 선별하는 조회 구조를 구현했다.

추천 후보 조회에는 ID 커서 기반 배치 조회를 적용했으며, PostgreSQL 테스트로 데이터의 중복·누락과 종료 조건을 검증했다.   
또한 배치 조회 도중 날짜 기준이 변경되지 않도록 KST 기준일을 고정했다.

## 실습 및 과제

> 직업훈련 NCS 세부 분류 검색 필터 추가

기존 통합 검색 API에서 직업훈련의 NCS 분류를 세분화하여 조회할 수 있도록 검색 조건을 확장했다.

청년정책은 온통청년의 `lclsfNm`, `mclsfNm`을 각각 `category`, `subCategory`에 저장하는 구조를 유지했다.

반면 직업훈련은 `category`를 서비스 공통 대분류인 교육·직업훈련으로 유지하고,   
`subCategory`에는 NCS 1차분류, `detailCategory`에는 NCS 2차분류를 저장하도록 구분했다.

검색 API에 `detailCategory` 조건을 추가하여 직업훈련을 NCS 2차분류까지 필터링할 수 있도록 했다.

이를 통해 청년정책과 직업훈련이 동일한 검색 API를 사용하면서도 서로 다른 원천 데이터의 분류 체계를 반영하도록 구성했다.

> NCS 세부 분류 정규화·검색 연동 검증

NCS 세부 분류 필터가 정확하게 동작하는지 확인하기 위해 원천 코드의 정규화부터 검색 API 조회까지 이어지는 흐름을 검증했다.

NCS 코드 `20010202`, `20020101`을 사용하여 동일한 정보통신 상위 분류에 속하더라도   
정보기술과 통신기술로 분류가 구분되는지 확인했다.

PostgreSQL 기반 연동 테스트에서는 특정 세부 분류 조건을 적용했을 때 해당 공고 1건이 조회되고,   
전체 조회에서는 44건이 반환되는 것을 확인했다.

이 과정에서 검색 쿼리가 정상적으로 동작하더라도   
원천 코드와 정규화된 분류명의 대응 관계가 잘못되면 검색 결과가 부정확해질 수 있다는 점을 확인했다.

따라서 검색 조건 자체뿐 아니라 정규화된 데이터가 DB에 올바르게 저장되는 과정까지 검증해야 한다는 점을 학습했다.

> NCS 분류 검색 필드 설명 수정

직업훈련의 `subCategory`와 `detailCategory`가 의미하는 분류 수준을 명확하게 구분하도록 검색 API 문서를 수정했다.

현재 구조에서 `subCategory`는 NCS 1차분류, `detailCategory`는 NCS 2차분류이므로   
API 사용자가 각 필드의 의미를 정확히 이해할 수 있도록 설명을 보완했다.

또한 분류 옵션 API와 공고 검색 API의 역할을 확인했다.

분류 옵션 API는 사용자가 선택할 수 있는 분류 목록을 제공하고, 검색 API는 선택된 분류 조건으로 실제 공고를 조회한다.

이를 통해 분류 정보는 검색뿐 아니라 사용자 관심 분야 설정에서도 재사용할 수 있으므로,   
특정 화면에 종속되지 않는 공통 데이터 구조로 관리해야 한다는 점을 확인했다.

> 추천용 숨김 공고 ID 일괄 조회 기능 추가

개인화 추천 V1에서 사용자가 숨긴 공고를 추천 후보에서 제외하기 위해 사용자별 숨김 공고 ID 일괄 조회 기능을 추가했다.

기존 저장·숨김 기능은 개별 공고의 상태를 관리했지만, 추천 과정에서는 여러 후보의 숨김 여부를 효율적으로 확인할 수 있어야 했다.

이에 사용자별 숨김 공고 ID를 한 번에 조회하도록 하고,   
검색·추천 영역이 Repository에 직접 접근하는 대신 기존 `PreferenceService`를 통해 필요한 데이터를 전달받도록 구성했다.

숨김은 개인화 추천에서만 제외하는 기능으로 유지하여, 숨긴 공고도 일반 검색과 상세 조회에서는 확인할 수 있도록 했다.

> 개인화 추천 후보 조회 기능 구현

개인화 추천 V1에서 전체 공고를 한 번에 메모리로 가져오는 대신, DB에서 기본 조건을 만족하는 추천 후보를 먼저 조회하도록 구현했다.

공고 유형·모집 상태·날짜·카테고리 등의 조건으로 후보를 선별하고,   
이후 신청 가능성 판정 결과와 사용자 관심 분야를 활용해 최종 추천 대상을 선정하도록 역할을 구분했다.

후보 조회에는 ID 커서 기반 배치 조회(Keyset Pagination)를 적용했다.

`id > afterId` 조건과 ID 오름차순 정렬, 배치 크기 제한을 사용해 마지막으로 조회한 ID 이후의 공고를 순차적으로 가져오도록 구성했다.

OFFSET 기반 페이지네이션과 달리 앞선 데이터를 건너뛰는 방식에 의존하지 않아 대량의 후보를 순회할 때 활용할 수 있다.

다만 ID는 후보 조회 순서를 관리하는 기준일 뿐 추천 우선순위를 의미하지 않으므로, 후보 조회와 최종 추천 선정 단계를 구분했다.

PostgreSQL 테스트에서는 배치별 조회 결과가 `2건 → 2건 → 1건 → 0건`으로 반환되는 상황을 확인했다.

마지막 조회 ID의 갱신, 빈 배치에서의 종료, 전체 공고 ID의 중복·누락 여부를 검증했다.

또한 기존에는 배치 조회 메서드가 호출될 때마다 KST 기준 날짜를 다시 계산할 수 있어,   
자정을 지나면 서로 다른 날짜를 기준으로 후보를 조회할 가능성이 있었다.

이를 해결하기 위해 후보 조회 시작 시점에 `today`를 확정하고, 모든 배치에 동일한 날짜를 전달하도록 수정했다.

이를 통해 배치 조회에서는 커서 이동과 종료 조건뿐 아니라 전체 조회 과정에서 사용하는 기준값의 일관성도 중요하다는 점을 확인했다.

> 프로젝트 멘토링 — 메시지 처리·성능 최적화 및 기술적 판단

MSA는 직접 적용하고 운영상의 문제를 경험하는 과정에서도 배울 점이 있으며,   
도입하지 않는다면 도입이 적합하지 않은 이유를 파악하는 것 역시 중요한 경험이다.

데이터 수집 영역에서는 SQS와 DLQ 활용을 논의했고, 알림에서는 중복 발송으로 인한 사용자 피로도를 고려해야 한다는 점을 확인했다.

메시지 전달 보장 방식인 `At Least Once`, `At Most Once`, `Exactly Once`의 차이를 이해할 필요가 있다.

또한 알림의 읽음 여부와 보관 기간에 따른 데이터 정리, 분석용 데이터의 별도 활용 방안도 논의했다.

성능 최적화에서는 프론트엔드·백엔드·DB 중 실제 병목 위치를 먼저 파악해야 한다는 점을 확인했다.

백엔드의 I/O-bound 작업은 SQL 최적화·캐싱 등으로 I/O 비용을 줄이거나,   
독립적인 요청의 병렬 처리로 대기 시간을 줄이는 방법을 고려할 수 있다.   
`EXPLAIN`을 통한 실행 계획 분석, 데이터 모델링과 인덱스 개선도 함께 검토해야 한다.

또한 백엔드 서버를 Scale-out하면 DB Connection이 증가할 수 있으므로 데이터베이스의 처리 용량도 함께 고려해야 한다.

Redis 캐싱에서는 데이터 변경에 따른 캐시 무효화와 동시 요청 문제를 다뤘다.   
여러 요청이 동시에 캐시 미스가 발생하면 DB에 부하가 집중되는 Cache Stampede가 발생할 수 있으므로,   
캐시 적용 시 데이터 최신성과 장애 상황까지 고려해야 한다.

마지막으로 AI 활용 경험은 특정 모델보다 새로운 기술에 대한 적응력과 AI 서비스 장애 대응 능력을 보여주는 것이 중요하며,   
면접에서 실제 경험과 기술적 판단의 근거를 설명할 수 있도록 준비해야 한다는 점을 확인했다.

## 헷갈렸던 점

직업훈련 NCS 분류를 검색에 연결하면서 서비스 공통 카테고리와 원천 데이터의 분류 체계를 어떻게 구분해야 하는지 확인했다.

청년정책과 직업훈련은 서로 다른 분류 체계를 사용하므로,   
`category`, `subCategory`, `detailCategory`의 의미를 유형별로 명확히 정의해야 한다는 점을 이해했다.

또한 분류 옵션 API와 실제 공고 검색 API가 분리된 이유를 확인했다.   
분류 목록을 제공하는 기능과 선택한 조건으로 공고를 조회하는 기능은 책임이 다르며,   
관심 분야 설정에서도 공통 분류 정보를 활용할 수 있다는 점을 정리했다.

개인화 추천 후보 조회를 구현하면서 ID 커서 기반 배치 조회의 동작 방식도 확인했다.   
마지막 조회 ID를 기준으로 다음 데이터를 가져오는 방식이며, 조회 순서와 최종 추천 우선순위는 별도로 구분해야 한다는 점을 이해했다.

배치 조회 도중 자정이 지나면 날짜 조건이 달라질 수 있다는 문제도 확인했다. 이에 전체 배치에서 동일한 KST 기준일을 사용하도록 수정했다.

## 오늘 느낀 점

오늘은 직업훈련 NCS 세부 분류 검색을 구현하면서 검색 결과의 정확성이 검색 쿼리뿐 아니라 데이터 정규화 과정에도 의존한다는 점을 확인했다.   
서로 다른 분류 체계를 하나의 API로 제공하더라도 데이터의 의미를 유지하고, 정규화부터 검색까지 연결해 검증하는 과정이 중요하다고 느꼈다.

개인화 추천 후보 조회에서는 모든 공고를 한 번에 처리하기보다 필요한 후보를 단계적으로 선별하는 구조가 중요했다.   
특히 후보 조회 순서와 최종 추천 우선순위는 별개이므로 각 단계의 책임을 명확히 구분해야 한다는 점을 배웠다.

또한 ID 커서 기반 배치 조회를 구현하면서 정상적인 결과뿐 아니라   
마지막 배치, 빈 결과, 날짜 변경과 같은 경계 조건도 검증해야 한다는 점을 확인했다.   
추천 기능의 안정성을 확보하려면 최종 알고리즘뿐 아니라 후보 조회 과정의 정확성과 일관성까지 고려해야 한다고 느꼈다.

특히 성능 최적화에서도 기술을 먼저 선택하기보다 실제 병목을 측정하고,
