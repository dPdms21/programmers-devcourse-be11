## 오늘 배운 내용

오늘은 특강을 통해 백엔드 개발자의 역할과 실제 업무 흐름, 문제 해결 방식과 성장 방향을 정리했다.

백엔드 개발자는 API와 비즈니스 로직 구현뿐 아니라 데이터베이스와 트랜잭션, 외부 시스템 연동,   
테스트와 배포, 모니터링, 장애 대응과 성능 개선까지 서비스 운영 전반을 이해해야 한다는 점을 확인했다.

`slow-board` 실습에서는 대량 데이터 생성 과정에서 발생하는 OOM의 원인을 객체 참조와 GC 관점에서 확인하고,   
일정 단위로 데이터를 저장한 뒤 참조를 제거하는 batch 처리 방식으로 개선했다.

제4회 알고리즘 코딩테스트에서는 1·2번은 비교적 수월했고 3·4번은 조금 난도가 있었다.  
4번은 전날 학습한 트리 내용이 도움이 되었고, 개인적으로는 3번이 더 까다로웠으며 풀이 중 제한 시간이 지나 제출하지 못했다.

제4회 Web Project 과제는 문제 수와 진행 시간이 길어 난이도보다 체력과 집중력 측면에서 부담이 컸다.

## 실습 및 과제

> 백엔드 개발자의 역할과 성장 방향 특강

백엔드 개발자의 업무가 API 구현에만 한정되지 않고 요구사항 분석, 설계,   
데이터 정합성, 테스트, 배포, 모니터링, 장애 대응과 성능 개선까지 이어진다는 점을 정리했다.

실제 업무에서는 기능을 구현하는 것뿐 아니라 왜 필요한 기능인지 이해하고,   
문제가 발생했을 때 로그와 지표를 바탕으로 원인을 좁혀 해결하는 능력이 중요하다는 점을 확인했다.

또한 자료구조·알고리즘, 운영체제, 네트워크, 데이터베이스 같은 기본기를 꾸준히 학습하고,   
프로젝트에서는 기능 수보다 문제를 발견하고 해결한 과정을 남기는 것이 중요하다는 점을 배웠다.

AI 역시 개발 효율을 높이는 도구로 활용할 수 있지만 사용한 기술의 동작 원리와 선택 이유, 대안까지 설명할 수 있어야 한다는 점을 정리했다.

> OOM 원인과 배치 처리 실습

Spring Boot와 Kotlin으로 `slow-board` 프로젝트를 구성하고 대량의 `Post` 객체를 생성할 때 발생하는 OOM 원인을 확인했다.

처음에는 1,000만 개의 객체를 하나의 `MutableList`에 계속 저장해 List가 모든 객체를 참조하고 있었고,   
이로 인해 GC가 해당 객체를 회수할 수 없는 상태가 됐다.

이를 해결하기 위해 `50,000`개 단위로 `saveAll()`한 뒤 `posts.clear()`를 호출해 처리한 객체에 대한 참조를 제거하도록 변경했다.

이를 통해 OOM은 단순히 데이터가 많아서 발생한다고 보기보다 어떤 객체가 계속 reachable 상태로 유지되는지를 확인해야 한다는 점을 이해했다.

대량 데이터 조회에서는 Offset Pagination의 한계와 Index, Cursor Pagination 같은 개선 방법도 소개받아 이후 추가로 학습할 주제로 정리했다.

## 헷갈렸던 점

OOM 문제에서는 GC가 객체를 단순히 오래 사용했는지나 객체 수를 기준으로 제거하는 것으로 생각하기 쉬웠다.

실제로는 GC Root에서 객체까지 참조가 이어져 있는지가 중요하며,   
List가 `Post` 객체를 계속 참조하는 동안에는 해당 객체가 reachable 상태로 남아 GC가 회수할 수 없다는 점을 확인했다.

따라서 메모리 문제에서는 단순히 데이터가 많다는 결과만 보는 것이 아니라 어떤 참조 관계 때문에 객체가 계속 살아 있는지를 확인해야 한다는 점을 이해했다.

## 오늘 느낀 점

오늘 특강을 통해 백엔드 개발은 기능 구현뿐 아니라   
서비스 운영 과정에서 발생하는 문제를 발견하고 원인을 분석하며 개선하는 과정까지 포함한다는 점을 다시 확인했다.

특히 OOM 실습을 통해 같은 대량 데이터 처리라도 객체 참조를 어떻게 관리하는지에 따라 메모리 사용 방식이 크게 달라질 수 있다는 점이 인상적이었다.  
프로젝트에서도 기능 수를 늘리는 것보다 실제 서비스 상황을 가정해 문제를 만들고,   
원인을 분석하고, 개선 전후를 검증하는 경험이 더 중요하다는 점을 느꼈다.

알고리즘 코딩테스트는 전체적으로 적절한 난이도였고 전날 학습한 트리 내용이 실제 문제 풀이에 도움이 됐다.  
Web Project 과제는 문제 자체보다 알고리즘 코딩테스트 직후 이어진 약 5시간의 연속 평가가 체력적으로 더 부담스러웠다.
