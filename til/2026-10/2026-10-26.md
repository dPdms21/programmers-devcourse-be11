## 오늘 배운 내용

오늘은 Y:ON의 분리된 백엔드 실행 환경에서 발생한 오류를 해결하고, 로컬 개발 환경에서 검색·상세 조회를 검증하기 위한 시드 데이터를 추가했다.

이후 프런트엔드에 마이페이지와 맞춤 조건 설정을 구현하고 지역 조회 API를 연동했다.   
백엔드에서는 공고 저장 시점의 정책 버전을 기록하도록 개선하고, 중복 저장과 재저장의 동작을 구분했다.

다음으로 프런트엔드의 저장·숨김 및 개인화 추천 기능을 연동하고, 인앱 알림과 FCM 웹 푸시 기능을 구현했다.

마지막으로 홈·검색·상세·마이페이지를 중심으로 UI/UX를 개선하고, 실제 API 연동 과정에서 확인된 오류와 미검증 사항을 정리했다.

## 실습 및 과제

> 백엔드 서버 분리 실행 오류 해결

백엔드와 데이터 수집·알림 서버가 분리된 환경에서 Spring Boot 실행 중 발생한 오류를 해결했다.

IntelliJ의 `Command line is too long` 오류는 `Shorten command line`을 `@argfile`로 설정하여 해결했다.

이후 PostgreSQL 인증 실패를 확인하면서   
`.env` 파일에 설정한 비밀번호와 기존 PostgreSQL 계정의 실제 비밀번호가 다를 수 있다는 점을 확인했다.   
`application_user`의 비밀번호를 재설정하여 DB 연결 문제를 해결했다.

또한 `application.yaml`의 `${환경변수:기본값}` 구문은 환경변수가 존재하지만   
값이 비어 있으면 기본값이 적용되지 않을 수 있다는 점을 확인했다.

`DATA_SERVICE_GRPC_ADDRESS` 설정을 수정해 gRPC 클라이언트 초기화 오류를 해결하고,   
Spring Boot와 JPA 및 Tomcat이 정상적으로 실행되는 것을 확인했다.

> 로컬 개발용 청년정책·직업훈련 시드 데이터 추가

실제 수집 데이터가 없는 로컬 환경에서 검색·상세 조회를 검증하기 위해   
기존 PostgreSQL `yon` 데이터베이스에 청년정책 10건과 직업훈련 10건의 시드 데이터를 추가했다.

SQL을 통해 공고와 현재 버전, 유형별 상세 정보, 신청기간 및 지역 데이터를 연결하고, 실제 정규화 규칙에 맞게 분류 정보와 검증 상태를 구성했다.

또한 시드 데이터를 반복 실행하더라도 중복 생성되지 않고 기존 참조 관계를 유지하도록 개선했다.

실제 HTTP 요청으로 전체 검색, 유형·카테고리·지역·모집 상태별 필터, 페이지네이션 및 상세 조회를 검증했다.   
등록한 공고 20건이 중복·누락 없이 조회되는 것을 확인했다.

다만 해당 시드는 검색·상세 조회 검증용이므로, 개인화 추천과 신청 가능성 판정에는 별도의 검증 데이터가 필요하다는 점을 구분했다.

> 프런트엔드 마이페이지·맞춤 조건 및 지역 API 연동

React 프런트엔드에 마이페이지와 맞춤 조건 설정 기능을 구현하고, 사용자 프로필과 관심 분야, 거주지역 정보를 등록·수정할 수 있도록 연동했다.

지역 선택에는 백엔드의 공개 지역 조회 API를 연결했다.

이 과정에서 공고 검색은 시·도 등의 상위 지역을 허용하지만, 거주지역 등록은 지역 사전에 존재하는 말단 지역 코드를 요구한다는 차이를 확인했다.

지역 API PR #78을 검토하면서 `GET /api/regions`의 응답 구조와 `RegionDirectory` 재사용, 기존 프로필 검증 규칙이 유지되는지 확인했다.

또한 맞춤 조건 미등록 사용자는 로그인 후 온보딩 화면으로 이동하도록 처리하고, 마이페이지에 회원 탈퇴 기능을 추가했다.

> 공고 저장 시 현재 정책 버전 기록

사용자가 공고를 저장한 이후 발생한 정책 변경을 추적할 수 있도록 `user_opportunity_preferences`에 `saved_version_id`를 추가했다.

최초 저장 시 `Opportunity.currentVersion.id`를 기록하고,   
이미 저장된 공고에 다시 저장 요청이 들어오면 기존 `savedVersionId`와 `savedAt`을 유지하도록 구현했다.

반면 찜 해제 후 재저장 시에는 새로운 저장 시점의 현재 버전을 기록하며, 숨김 상태 변경은 저장 버전에 영향을 주지 않도록 구분했다.

공고 버전은 data-service가 소유하고 저장·숨김 데이터는 backend가 소유하므로,   
`saved_version_id`는 nullable `BIGINT` 컬럼으로 정의하고 다른 서비스의 버전 테이블에 FK나 JPA 연관관계를 생성하지 않았다.

또한 현재 버전이 없는 공고와 기존 찜 데이터는 버전을 임의로 추정하지 않고 `null`로 유지하도록 했다.   
기존 찜 데이터의 추적 시작점은 후속으로 결정하기로 했다.

공고 버전 변경과 저장 요청이 동시에 발생하는 상황에서는 저장 트랜잭션에서 조회한 버전이 기록되므로,   
커밋 시점의 최신 버전까지 보장하지는 않는다는 한계도 확인했다.

최초 저장·중복 저장·재저장·숨김 상태 유지·사용자별 데이터 독립성을 검증하고,   
PostgreSQL Testcontainers에서 컬럼 생성과 FK 미생성 여부를 확인했다.

관련 테스트 85건과 전체 Gradle 테스트가 통과했으며, 코드 리뷰에서도 저장 버전 유지·갱신 동작을 확인했다.

> 프런트엔드 저장·숨김 및 검색 기능 연동

공고 저장·숨김 기능과 저장 목록을 구현하고, 홈·검색·상세 화면에서 저장 상태가 일관되게 반영되도록 개선했다.

기회 탐색 화면에는 지역·신청 가능성 필터를 연결하고, 로그인 여부에 따라 검색 요청과 캐시를 구분했다.

실제 API 연동 과정에서 공고 저장 요청은 HTTP 204로 성공했지만,   
이후 추천 데이터를 다시 조회하면서 발생한 `ELIGIBILITY_001` 오류가 저장 실패처럼 처리되는 문제를 발견했다.

이를 통해 상태 변경 요청의 성공 여부와 후속 데이터 조회 실패를 별도로 처리해야 한다는 점을 확인했다.

또한 개인화 추천 회귀 테스트를 보강하고, 서버에서 결정한 추천 순서와 추천 이유가 프런트엔드에서도 유지되도록 했다.

> 프런트엔드 인앱 알림 및 FCM 웹 푸시 연동

인앱 알림 목록과 읽음·클릭 처리, 미읽음 배지, 알림 설정 기능을 구현했다.

알림 목록은 기존 검색·저장 목록과 달리 커서 페이지네이션을 사용하므로, 다음 커서를 기반으로 추가 데이터를 조회하도록 구성했다.

FCM 웹 푸시는 Firebase SDK와 서비스 워커를 연결하고, 발급한 Registration Token을 백엔드의 `fcmToken` 등록 API로 전달하도록 구현했다.

Firebase 설정값과 VAPID 공개 키를 연동하고 SDK 초기화 및 빌드를 검증했다.

다만 실제 로그인 환경에서의 토큰 등록과 푸시 발송·수신은 아직 검증하지 못했으며,   
브라우저 알림 권한과 서버 토큰 등록, 사용자 알림 설정은 별도로 확인해야 한다는 점을 정리했다.

> 프런트엔드 UI/UX 개선 및 사용자 안내 정리

홈·검색·상세·마이페이지를 중심으로 전체 디자인과 정보 배치를 개선했다.

화이트·아이보리 중심으로 색상 체계를 정리하고, 청년정책과 직업훈련은 각각 그린과 블루로 구분했다.   
불필요한 안내 문구와 중첩된 카드·여백을 줄여 주요 정보를 쉽게 확인할 수 있도록 했다.

홈 화면에는 로그인 상태별 안내와 CTA를 적용하고, 상세 화면에서는 핵심 정보와 신청·저장 영역을 구분했다.   
모바일 반응형 레이아웃과 저장 버튼 접근성도 보완했다.

또한 날짜 형식, 페이지 링크, 로그인 안내 및 공고 유형 배지의 표시 기준을 통일했다.

공고 상세 정보에서는 청년정책의 신청기간과 직업훈련의 모집기간·교육기간을 구분하고,   
훈련비가 0으로 제공되더라도 무료 여부가 확인되지 않았다면 무료라고 단정하지 않도록 처리했다.

개인정보처리방침과 서비스 이용약관 페이지를 추가하면서 회원 탈퇴 이후 알림 데이터 정리가 비동기로 진행되는 구조도 확인했다.   
이에 모든 데이터가 탈퇴 즉시 삭제된다고 안내하지 않도록 주의했다.

## 헷갈렸던 점

공고 저장 버전 기록에서는 중복 저장과 찜 해제 후 재저장 시 버전을 어떻게 처리해야 하는지 고민했다.   
중복 저장은 기존 저장 시점을 유지하고, 재저장은 새로운 저장 시점의 버전을 기록하도록 구분했다.

현재 버전이 없는 공고와 기존 찜 데이터의 저장 버전을 어떻게 처리할지도 검토했다.   
확인할 수 없는 과거 버전을 임의로 추정하지 않고 `null`로 유지하는 방향으로 정리했다.

프런트엔드에서는 저장 요청이 성공한 뒤 추천 재조회에 실패했을 때 전체 저장 작업을 실패로 처리해야 하는지 확인했다.   
서로 독립적인 요청이므로 성공한 상태 변경과 후속 조회 실패를 구분해야 한다는 점을 이해했다.

FCM 연동에서는 브라우저 알림 권한만 허용하면 실제 푸시를 받을 수 있는지도 확인했다.   
권한 허용 이후 토큰 발급·서버 등록·실제 수신까지 각각 검증해야 한다는 점을 정리했다.

## 오늘 느낀 점

오늘은 백엔드 실행 오류를 해결하면서 코드뿐 아니라   
IDE 설정, 환경변수 및 데이터베이스 내부 상태도 서비스 동작에 영향을 준다는 점을 확인했다.   
로컬 시드 데이터로 실제 API를 검증하면서 프런트엔드 연동에 필요한 개발 환경을 마련하는 과정도 중요하다고 느꼈다.

공고 저장 버전 기록에서는 단순히 현재 버전을 저장하는 것보다 사용자 행동 시점과 정책 버전의 관계를 정확하게 보존하는 것이 중요했다.   
특히 멱등성과 기존 데이터의 불확실성, 서비스 간 데이터 소유권까지 고려해야 변경 추적과 알림의 정확성을 유지할 수 있다는 점을 배웠다.

프런트엔드에서는 여러 API를 연결하면서 개별 요청의 성공 여부와 전체 화면 상태를 구분해야 한다는 점을 확인했다.   
저장 요청이 성공했는데 후속 조회 오류를 저장 실패로 처리하는 문제를 통해 실제 사용 흐름을 검증하는 것의 중요성을 이해했다.

또한 FCM 연동과 UI/UX 개선을 진행하면서 기능 구현과 실제 서비스 환경에서의 정상 동작은 별개라는 점을 느꼈다.   
앞으로는 화면 기능을 추가하는 것뿐 아니라 실제 인증·알림·데이터 반영 흐름을 검증하고,   
사용자에게 필요한 정보를 명확하게 제공하는 데 집중해야겠다고 생각했다.
