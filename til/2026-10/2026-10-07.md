**project**

* Y:ON - 서비스 기획 구체화 및 정책 데이터 검토

## 오늘 배운 내용

오늘은 Y:ON의 기획을 구체화하면서 실제 서비스에서 어떤 정보를 다루고 어떤 흐름으로 동작할지 논의했다.

사용자에게 어떤 정보를 입력받을지, 정책 조건과 어떻게 비교할지, 검색과 추천은 어떤 역할로 나눌지,   
정책의 변경을 어떤 방식으로 추적할지 등을 중심으로 서비스 정책을 정리했다.

ERD에 필요한 엔티티도 논의했지만,   
실제 정책 데이터를 확인하면서 예상보다 데이터 구조와 값의 통일성이 낮다는 문제가 드러나 구조를 바로 확정하지는 못했다.

데이터 소스 측면에서는 잡아바 API가 개인 프로젝트에서 활용하기 어렵다는 점을 확인했고,   
온통청년이 여러 기관의 청년 정책 데이터를 통합해 제공한다는 점을 확인해 온통청년 API를 주요 데이터 소스로 사용하기로 했다.

다만 온통청년 API도 빈 값이 많고 구조화된 필드와 자유서술 내용이 일치하지 않거나   
실제 공식 사이트의 정보가 더 최신인 경우가 있어 API 데이터만으로 서비스를 운영하기는 어렵다고 판단했다.

따라서 API에서 기본 데이터를 확보하고 공식 페이지의 실제 내용을 추가로 확인하며, 수집과 의미 해석의 역할을 분리하는 방향을 검토했다.

## 실습 및 과제

> Y:ON 서비스 정책 구체화

전날 정한 서비스 방향을 바탕으로 실제 사용자가 어떤 정보를 입력하고 이를 어떤 방식으로 정책과 연결할지 논의했다.

나이, 지역, 취업·재학 상태 등 정책 신청 여부를 판단하는 데 필요한 사용자 정보를 어떤 형태로 받을지 검토했고,   
정책마다 조건 표현이 다를 수 있기 때문에 입력값과 정책 조건을 어떻게 비교할지도 함께 논의했다.

또한 사용자가 직접 조건을 입력해 정책을 찾는 검색과, 저장된 사용자 정보를 바탕으로   
정책을 우선적으로 보여주는 추천의 역할을 구분해 생각했다.

정책이 새로 등록되거나 조건이 변경되는 경우 사용자에게 어떤 식으로 다시 연결할지,   
알림은 어떤 경우에 제공할지 등 Tracking 기능의 흐름도 함께 검토했다.

다만 세부 조건과 판정 기준, 알림 기준 등을 모두 확정한 것은 아니며 기획 단계에서 정해야 할 항목을 구체화한 수준이다.

> ERD 엔티티 검토

서비스 정책을 바탕으로 어떤 데이터를 저장해야 하는지 논의하면서 ERD에 들어갈 엔티티를 검토했다.

회원 정보, 사용자 조건, 정책 정보, 저장한 정책, 정책 변경과 알림 등에 필요한 데이터를 중심으로 구조를 논의했다.

다만 실제 외부 정책 데이터의 형태를 확인하면서 예상보다 값과 표현 방식이 일정하지 않다는 문제가 드러나 엔티티 구조를 바로 확정하지는 않았다.

외부 데이터를 내부에서 어떤 형태로 사용할지 먼저 확인한 뒤 ERD를 다시 구체화하기로 했다.

> 실제 정책 데이터 소스 검토

온통청년과 잡아바 API를 데이터 소스로 검토했다.

잡아바 API의 이용 조건을 확인한 결과 개인 프로젝트에서는 활용하기 어렵다는 문제가 있어 다른 데이터 소스도 추가로 찾아봤지만,  
청년 지원정책 데이터를 서비스에서 활용할 수 있는 형태로 제공하는 적절한 대체 API를 찾기는 어려웠다.

이 과정에서 온통청년이 자체 정책만 제공하는 것이 아니라 여러 기관과 사이트의 청년 정책 데이터를 통합해 제공한다는 점을 확인했다.

따라서 여러 데이터 소스를 동시에 연결하기보다 온통청년 API를 주요 데이터 소스로 사용하는 방향으로 정리했다.

> 온통청년 정책 데이터 문제 확인

온통청년의 예시 데이터를 확인하면서 정책 수는 충분하지만 빈 값이 존재하고,   
구조화된 필드와 자유서술 내용이 일치하지 않거나 실제 공식 사이트의 정보가 더 최신인 경우가 있다는 문제를 확인했다.

따라서 온통청년 API만을 그대로 신뢰해 검색·추천과 사용자 조건 판정에 사용하는 것은 어렵다고 판단했다.

API는 정책 목록과 기본 정보를 확보하는 용도로 활용하고,   
필요한 경우 정책의 공식 페이지를 추가로 확인해 실제 내용을 보완하는 방향을 검토했다.

다만 많은 정책을 매번 AI가 직접 탐색하고 해석하는 방식은 비용과 처리 시간 측면에서 부담이 크기 때문에,   
공식 페이지의 본문 수집은 일반적인 크롤링 방식으로 처리하고 의미 해석이 필요한 부분에만 LLM을 활용하는 방향을 논의했다.

또한 이전에 수집한 본문과 동일한 경우에는 다시 LLM 분석을 수행하지 않도록 변경 여부를 먼저 확인하는 방식도 검토했다.

구체적인 크롤링 방식과 정규화 기준은 아직 확정하지 않았으며,   
다음 단계에서 실제 API 데이터와 공식 URL의 형태를 더 살펴본 뒤 처리 방법을 구체화하기로 했다.

## 헷갈렸던 점

사용자에게 어떤 정보를 입력받고 그 값을 정책 조건과 어떤 기준으로 비교해야 하는지가 아직 명확하지 않았다.

정책마다 조건 표현 방식이 다를 수 있기 때문에 사용자 입력 구조를 먼저 확정하기보다   
실제 정책 데이터를 함께 확인하면서 맞춰가야 한다는 점을 정리했다.

또한 외부 API에서 데이터를 제공하면 비교적 쉽게 내부 모델로 옮길 수 있을 것으로 생각했지만,   
실제 예시 데이터를 확인하니 빈 값과 표현 방식의 차이, 공식 사이트와의 정보 차이까지 존재했다.

따라서 ERD와 판정 로직을 먼저 확정하기보다 실제 데이터 구조와 예외를 충분히 확인하고,   
API 데이터와 공식 페이지 정보를 어떻게 함께 사용할지 결정해야 한다는 점을 확인했다.

온통청년 데이터의 전처리 방식도 아직 명확하지 않았다.

모든 정책을 AI로 직접 탐색하고 처리하는 방식과 일반 크롤링 후 필요한 부분만 LLM으로 해석하는 방식을 비교했고,   
비용과 처리 시간, 결과의 재현성을 고려하면 수집과 의미 해석의 역할을 분리하는 방향이 더 적절하다고 봤다.

다만 구체적인 적용 범위는 실제 데이터를 더 분석한 뒤 결정하기로 했다.

## 오늘 느낀 점

오늘은 기능을 확정하는 것보다 실제 서비스 정책과 데이터 흐름을 구체화하고, 실제 데이터 소스의 제약을 확인하는 데 집중했다.

처음에는 외부 API를 연동하면 정책 데이터를 비교적 바로 활용할 수 있을 것으로 생각했지만,   
실제 데이터를 확인하면서 값의 통일성 문제와 공식 사이트와의 정보 차이라는 현실적인 문제가 드러났다.

잡아바 API의 이용 제한까지 확인하면서 외부 API는 존재 여부만 확인할 것이 아니라   
실제 이용 가능 여부와 데이터 품질까지 함께 검증해야 한다는 점을 느꼈다.

또한 모든 처리를 AI에 맡기기보다 규칙적으로 처리할 수 있는 데이터 수집과 변경 감지, 의미 해석이 필요한 작업을 구분해야   
비용과 처리 시간, 결과의 추적 가능성을 함께 고려할 수 있다는 점을 확인했다.

오늘은 해결 방법을 모두 확정한 날이라기보다,   
Y:ON을 실제로 구현하기 위해 먼저 해결해야 할 데이터 문제와 설계 쟁점이 무엇인지 구체적으로 드러난 날이었다.
