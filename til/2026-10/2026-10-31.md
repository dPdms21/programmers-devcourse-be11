오늘은 Y:ON 사용자 행동 이벤트 PR #130의 코드 리뷰와 CI 실패 사항을 반영하고, 기존 이벤트 수집 정책과 개선 결과를 정리했다.

이후 알림·관심 분야 설정 UI를 개선하고, 기존 백엔드 API를 활용한 관리자 페이지를 구현했다.   
수집 이력과 행동 로그 보관 기능을 연동하면서 권한 검증과 운영 데이터 변경의 안전성을 확인했다.

다음으로 추천 공고 숨김 되돌리기와 모든 기기 로그아웃을 구현하고, 홈 일러스트·로고·검색 필터 등 주요 화면의 UI를 개선했다.

마지막으로 Chrome 브라우저 테스트의 자원 경합 문제를 분석하고, 동시 실행 설정을 조정하여 간헐적인 실패를 줄였다.

## 실습 및 과제

> 사용자 행동 이벤트 PR 코드 리뷰 및 개선 내용 정리

사용자 행동 이벤트 관련 PR #130의 코드 리뷰와 CI 실패 사항을 반영하고, 기존 행동 이벤트 수집 정책이 유지되는지 검증했다.

CI 실패 원인을 분석하면서 변경 코드의 문제와 테스트 환경에서 발생하는 문제를 구분했다.

또한 프런트엔드 행동 이벤트 연동, 저장 성능 측정, 보관 정책 구현 과정에서 확인한 기술적 선택과 한계를 정리했다.

> 알림 및 관심 분야 설정 UI 개선

알림 목록과 설정 화면에서 인앱 알림과 브라우저 푸시 알림의 역할을 구분하고, 사용자 설정과 구독 상태를 쉽게 확인할 수 있도록 개선했다.

계정의 알림 설정값과 브라우저 권한, 실제 푸시 구독 상태는 서로 다를 수 있다는 점을 확인했다.

관심 분야 설정에서는 대분류와 세부 분류의 관계를 명확하게 표시하고, 기존 백엔드 분류 체계와 저장 동작을 유지하면서 선택 UI를 개선했다.

> 관리자 페이지 구현 및 보관 실행 개선

기존 백엔드 관리자 API를 활용하여 수집 이력·작업 상세·원본 레코드·행동 이벤트 보관 상태를 조회하는 관리자 페이지를 구현했다.

수집 시작과 실패 작업 재시도, 행동 로그 보관 미리보기 및 실행 기능도 연동했다.

프런트엔드에서는 `ADMIN` 역할로 화면 접근을 제한하되, 실제 데이터 조회·변경 권한은 백엔드에서 검증하도록 구분했다.

보관 정리 요청에서 타임아웃이 발생하더라도 일부 파티션 정리가 이미 완료됐을 가능성이 있으므로,   
즉시 재실행하지 않고 최신 미리보기를 조회해 상태를 재확인하도록 했다.

또한 수집 이력은 실행 중인 작업이 있을 때만 주기적으로 갱신하고, 작업이 종료되면 불필요한 요청을 중단하도록 개선했다.

> 추천 공고 숨김 되돌리기 및 모든 기기 로그아웃 구현

추천 공고를 실수로 숨긴 경우 복구할 수 있도록 개인화 추천 제목 옆에 5초 동안 되돌리기 기능을 제공했다.

기존 숨김 해제 API를 호출해 서버 상태를 복구하고, 성공 시 추천 데이터를 다시 조회하도록 구현했다.   
요청 실패와 중복 실행, 계정 전환 시 이전 안내가 남지 않도록 처리했다.

또한 마이페이지 계정 관리 영역에 모든 기기 로그아웃 기능을 추가했다.

일반 로그아웃과 달리 전체 Refresh Token을 무효화하는 API를 사용하며,   
다른 기기의 Access Token은 기존 유효기간 동안 사용할 수 있다는 점을 확인했다.

로그아웃 이후에는 인증 상태와 개인화 캐시를 정리하고, 다른 계정 관련 요청과 충돌하지 않도록 처리했다.

> 홈 화면 및 검색 UI 개선

홈 일러스트를 새로운 SVG 이미지로 교체하고, `viewBox`와 실제 그림 영역의 차이로 발생하는 여백을 조정했다.

서비스 로고와 파비콘을 변경하고, 검색 필터의 초기화·적용 버튼을 상단에 배치해 사용 흐름을 개선했다.

검색 결과 카드의 중앙 여백도 검토했지만, 현재 API 응답 정보만으로는 배치 변경 효과가 크지 않다고 판단했다.

지역·기관·신청기간 등의 정보를 추가하려면 API 확장과 조회 비용을 고려해야 하므로 이번에는 추가 수정을 진행하지 않았다.

> Chrome 브라우저 테스트 실행 안정화

전체 프런트엔드 테스트 실행 중 Chrome과 Vite 프로세스가 동시에 다수 생성되면서 CPU 사용률이 95~99%까지 증가하는 문제를 확인했다.

이로 인해 개별 실행에서는 통과하는 테스트도 전체 실행에서는 브라우저 종료 지연이나 가상 시간 예산 소진으로 실패했다.

테스트 동시 실행 수를 2·3·4·6으로 비교한 뒤 4개로 제한하고, Chrome의 불필요한 백그라운드 서비스를 비활성화했다.

동일 시간대 교대 측정에서 전체 실행 시간은 평균 43.3초에서 40.7초로 약 6% 감소했다.

최장 테스트 시간은 약 38~43초에서 14~16초로 줄었으며, 과부하 재현 조건의 실패 9건은 개선 후 0건으로 감소했다.

기존 테스트 351개를 모두 유지한 상태에서 전체 테스트와 lint, build가 통과했다.

다만 CI는 로컬과 다른 동시 실행 설정을 사용하므로, 동일한 안정화 효과가 나타나는지는 추가 검증이 필요하다.

## 헷갈렸던 점

관리자 화면에서 `ADMIN` 역할에 따라 접근을 제한하면 관리자 API도 보호되는지 확인했다.   
프런트엔드 접근 제한과 실제 서버 권한 검증은 별개라는 점을 이해했다.

행동 로그 정리 요청에서 타임아웃이 발생하면 서버 작업도 중단되는지 검토했다.   
일부 작업이 이미 완료됐을 수 있으므로, 최신 상태를 확인한 뒤 재실행 여부를 결정해야 한다는 점을 확인했다.

추천 공고 숨김을 되돌릴 때 화면의 카드만 복구하면 되는지 고민했다.   
서버에 저장된 숨김 상태를 실제로 해제하고 추천 결과를 다시 조회해야 한다는 점을 확인했다.

모든 기기 로그아웃이 다른 기기의 Access Token까지 즉시 만료시키는지도 확인했다.   
Refresh Token 무효화와 이미 발급된 Access Token의 만료는 별개라는 점을 이해했다.

홈 일러스트의 크기를 조정해도 여백이 남는 이유를 확인했다.   
SVG의 `viewBox`와 실제 그림 영역을 함께 확인해야 한다는 점을 알게 됐다.

## 오늘 느낀 점

오늘은 프런트엔드 V2 기능을 구현하면서 화면에 표시되는 상태와 서버에 저장된 상태를 일관되게 유지하는 것이 중요하다고 느꼈다.   
특히 관리자 기능은 요청 실패나 중복 실행이 실제 운영 데이터에 영향을 줄 수 있으므로 예외 상황을 함께 고려해야 한다는 점을 확인했다.

추천 숨김 되돌리기와 모든 기기 로그아웃에서는 정상 동작뿐 아니라 요청 실패와 계정 전환 상황까지 검증해야 했다.   
이를 통해 사용자 편의 기능도 인증과 데이터 정합성을 고려해야 안정적으로 제공할 수 있다는 점을 배웠다.

UI 개선에서는 단순한 배치 변경이 항상 더 나은 결과로 이어지지는 않았다.   
현재 데이터와 사용 흐름을 고려하여 개선 효과가 크지 않은 작업은 보류하는 것도 합리적인 선택이라고 느꼈다.

브라우저 테스트에서는 전체 실행 시간의 개선 폭은 작았지만 간헐적인 실패를 줄일 수 있었다.   
이를 통해 테스트 성능을 평가할 때는 속도뿐 아니라 안정성과 실패율을 함께 고려해야 한다는 점을 확인했다.
