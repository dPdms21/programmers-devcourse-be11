## 오늘 배운 내용

오늘은 Y:ON의 데이터 수집·정규화, 정책 엔진 및 회원 기능의 PR을 코드 리뷰하고, 프로젝트 최신화와 README 작성을 진행했다.

이후 정책 엔진 담당자와 지역 검색 및 모집 상태 처리 기준을 협의하고,   
청년정책과 직업훈련의 데이터 특성을 반영해 통합 검색 기능을 확장했다.

검색·저장·숨김 코드의 주석을 보완하고 관련 PR을 추가로 검토했으며, 모집 상태·날짜 필터와 정렬 옵션을 순차적으로 구현했다.   
이 과정에서 검색 조건을 DB 단계에서 처리하고, 정렬·페이지네이션의 정합성을 유지하는 것이 중요하다는 점을 확인했다.

마지막으로 신청 가능성 필터 연동을 위해 기존 정책 엔진의 조회 방식과 제약을 검토하고,   
저장된 최신 판정 결과를 검색 조건에 활용하는 방안을 담당자와 협의했다.

## 실습 및 과제

> PR #4 코드 리뷰 및 프로젝트 최신화

원본 데이터 저장과 비동기 수동 최신화 기능을 검토했다.

외부에서 전달받은 `payloadHash`에 의존하기보다   
서버에서 원본 JSON을 기준으로 해시를 계산하는 방식이 변경 감지의 신뢰성을 높인다는 점을 확인했다.   
JSON 키 순서 차이를 정규화하고, PostgreSQL Testcontainers로 JSONB 저장·롤백·동시성 처리를 검증한 내용도 확인했다.

팀 저장소의 최신 PR과 구현 현황을 점검하고, PR #6 병합 이후 작업 브랜치에 최신 `main`을 반영했다.

> README 작성 및 정책 엔진 협의

프로젝트 README에 주요 기능, 담당 영역, 기술 스택과 협업 규칙을 정리했다.

이후 정책 엔진 담당자와 지역 검색 기준 및 모집 상태 필터의 구현 방식을 협의했다.

청년정책은 `OpportunityCondition`의 지역 조건을 활용하고,   
KDT는 거주 지역 제한이 없다는 의미에서 `NATIONAL`로 처리하되 실제 훈련 장소인 `IMPLEMENTATION` 정보는 별도로 유지하기로 했다.

모집 상태는 검색 영역에서 판정 규칙을 중복 구현하지 않고,   
정책 엔진에서 `ApplicationStatusCalculator`와 동일한 기준의 `Specification<Opportunity>`를 제공받아   
검색 조건에 결합하는 방향으로 정리했다.

이를 통해 판정 규칙은 정책 엔진에서 관리하고, 검색 영역은 필터 조합과 정렬·페이지네이션을 담당하도록 역할을 구분했다.

> 통합 검색 구현 및 PR #7 코드 리뷰

`GET /api/opportunities`의 통합 검색 구조를 점검하고,   
`Specification`과 Criteria API를 활용해 키워드·유형·카테고리·지역 조건을 DB 조회 단계에서 결합했다.

청년정책은 거주 지역과 전국 대상 조건을 반영하고,   
직업훈련은 실제 교육 장소인 `IMPLEMENTATION`을 기준으로 지역을 검색하도록 처리했다.   
지역 조건에는 `EXISTS`를 사용해 여러 지역이 연결된 공고의 중복 조회를 방지했다.

이후 회원 맞춤 조건 CRUD와 회원 탈퇴 기능이 포함된 PR #7을 검토했다.

기존 `EligibilityProfile`을 재사용해 회원 조건의 중복 저장을 방지하는 구조와,   
`PATCH`에서 미전달 필드는 유지하고 명시적인 `null`은 선택 항목 초기화로 처리하는 방식을 확인했다.

회원 탈퇴 시 저장·숨김 데이터도 함께 삭제하도록 추가 연동이 필요하다는 점을 정리했다.

> 주석 추가 및 PR 재검토

검색·저장·숨김 코드에 Javadoc을 추가하여 지역별 검색 기준,   
`EXISTS`를 통한 중복 방지, 저장·숨김 상태 관리와 동시성 설계 의도를 정리했다.

PR #4와 #7의 보완 사항을 다시 확인하고, PR #6의 모집 상태 `Specification`과 PostgreSQL 테스트를 검토했다.

또한 KDT는 직업훈련의 하위 유형이므로   
현재 정규화 범위가 KDT로 제한되더라도 검색 API는 `VOCATIONAL_TRAINING` 전체를 기준으로 설계해야 한다는 점을 확인했다.

고용24의 실제 모집 마감일 확보가 어려워 현재 KDT는 개강일 전날을 신청 마감일로 추정한다는 점도 확인했다.

> 모집 상태·날짜 필터 및 정렬 옵션 구현

통합 검색에 모집 상태, 날짜, 정렬 옵션을 순차적으로 추가했다.

먼저 `applicationStatus` 파라미터를 추가하고, 공통 `ApplicationStatusSpecifications.hasStatus()`를 기존 검색 조건에 결합했다.   
검색 영역에서 모집 상태를 다시 계산하지 않고 정책 엔진의 판정 규칙을 재사용했으며, `Asia/Seoul` 기준 날짜를 적용했다.

날짜 필터는 청년정책의 검증된 신청 마감일과 직업훈련의 교육 시작일을 구분해 구현했다.   
시작일·종료일을 독립적으로 선택할 수 있도록 하고, 날짜 역전이나 공고 유형과 맞지 않는 요청은 `400 Bad Request`로 처리했다.   
다중 신청기간에 따른 중복 결과는 `EXISTS` 조건으로 방지했다.

정렬 옵션으로 최신순 `LATEST`, 오래된순 `OLDEST`, 청년정책 마감 임박순 `DEADLINE_ASC`, 직업훈련 시작일순 `START_DATE_ASC`를 구현했다.

유형별 정렬 날짜는 DB 상관 서브쿼리로 계산하고, 날짜가 없는 공고는 후순위로 배치했다.   
정렬 값이 같을 때는 공고 ID를 기준으로 순서를 고정해 페이지 간 결과의 일관성을 유지했다.

전체 Gradle 테스트는 최종 377개 중 73개 건너뜀, 실패·오류 0개를 확인했다.   
인증 영역의 기존 HikariPool 연결 종료 경고는 검색 기능과 별개의 문제로 남겼다.

> 신청 가능성 검색 필터 연동 협의

신청 가능성 필터를 구현하기 위해 `EligibilityProvider`의 기존 조회 방식을 검토했다.

`getEligibilities()`는 지정한 후보의 판정 결과 조회에 적합하지만,   
`findByStatuses()`는 전체 재판정 후 ID순으로 페이지를 반환하므로 기존 검색 조건과 정렬을 결합하기 어렵다는 점을 확인했다.

이에 검색 요청마다 전체 재판정을 수행하기보다 저장된 최신 판정 결과를 DB 검색 조건으로 활용하는 방식을 검토했다.

정책 엔진 담당자에게 `userId`와 복수의 `EligibilityStatus`를 입력받는 읽기 전용 `Specification<Opportunity>` 제공을 요청했다.

해당 조건은 사용자·공고별 `EligibilityResult`를 `EXISTS`로 연결하고,   
공고·프로필·규칙 버전과 유효 기한을 확인해 최신 판정 결과만 포함하도록 제안했다.

판정 결과가 없거나 오래된 공고는 우선 검색 결과에서 제외하고, 프로필 변경이나 공고 갱신 이후 재판정 시점은 추가 협의하기로 했다.

이를 통해 정책 엔진의 판정 결과를 재사용하면서 기존 검색 조건과 정렬·페이지네이션의 정합성을 유지하는 방향을 정리했다.

## 헷갈렸던 점

신청 가능성 필터를 기존 `EligibilityProvider`만으로 처리할 수 있는지 고민했다.

`findByStatuses()`는 신청 가능성 상태로 조회하지만 키워드·지역 등 기존 검색 조건과 페이지네이션을 함께 처리하기 어렵다는 점을 확인했다.   
검색 결과를 먼저 나누면 전체 건수의 정합성이 깨질 수 있으므로,   
최신 판정 결과를 DB 검색 조건에 결합할 수 있는 구조가 필요하다는 점을 정리했다.

청년정책과 직업훈련의 지역 및 날짜 조건을 동일하게 처리해도 되는지도 검토했다.

청년정책의 지역은 거주·신청 조건과 관련되지만, 직업훈련의 지역은 실제 교육 장소를 기준으로 검색해야 한다는 차이를 확인했다.   
날짜 필터 역시 청년정책은 신청 마감일, 직업훈련은 교육 시작일을 사용하므로 공고 유형별로 기준을 구분해야 한다는 점을 정리했다.

## 오늘 느낀 점

여러 도메인의 구현을 검토하고 검색 기능과 연동하는 과정에서,   
담당 기능뿐 아니라 다른 영역의 데이터 구조와 처리 기준까지 이해하는 것이 중요하다고 느꼈다.

특히 신청 가능성 판정 결과를 검색에 적용하는 과정에서 기존 인터페이스를 그대로 사용하는 것보다   
검색 조건과 페이지네이션의 정합성을 유지할 수 있는 데이터 접근 방식이 중요하다는 점을 확인했다.

또한 청년정책과 직업훈련을 하나의 API로 조회하더라도 지역, 날짜, 모집 상태와 같은 조건은 데이터의 의미에 따라 다르게 처리해야 했다.   
공통 인터페이스를 유지하면서도 유형별 차이를 정확하게 반영하는 것이 통합 검색의 핵심이라고 느꼈다.

모집 상태·날짜 필터·정렬 옵션을 순차적으로 구현하고 회귀 테스트를 진행하면서,   
새로운 조건을 추가할 때 기존 검색 결과와 페이지 정보가 영향을 받지 않는지 검증하는 과정의 중요성을 확인했다.
