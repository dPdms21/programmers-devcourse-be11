## 오늘 배운 내용

오늘은 Y:ON 통합 검색의 성능 개선 작업을 이어가며 PostgreSQL 인덱스와 JIT 설정을 검토하고, 성능 측정 결과와 기술적 선택 근거를 정리했다.

이후 기존 제목 `LIKE` 검색에서 일부 검색어의 결과가 누락되는 문제를 확인하고,   
검색 기능을 후보 추출과 관련도 랭킹으로 나누어 개선 방향을 실험했다.   
검색 품질 평가 과정에서는 관련도를 모집 상태보다 우선해야 한다는 기준과 점수 동률 문제를 확인했다.

다음으로 검색 요청마다 공고 제목을 정규화하는 CPU 비용을 줄이기 위해 PostgreSQL STORED 생성 컬럼을 실험하고,   
성능 개선 효과와 저장·쓰기 비용을 비교했다.   
JPA의 스키마 변경 문제도 확인해 보완했다.

마지막으로 B1 후보 추출 로직을 Java로 구현하고 SQL 프로토타입과 결과를 비교했다.   
실제 API에서 발생한 추가 조회 비용을 분석하여 직업훈련 검색 조건을 개선하고, 남은 성능 문제와 B2 구현 방향을 정리했다.

## 실습 및 과제

> 검색 성능 개선 결과 및 인덱스 적용 검토

기존 검색 SQL 최적화 작업을 바탕으로 PostgreSQL 실행 계획과 JIT 설정을 추가로 검토했다.

조회 성능을 개선하기 위해 검토한 인덱스가 기존 수집·정규화 작업에 미치는 영향을 고려하고,   
DB 변경과 서비스 배포의 실행 순서 및 복제본 점검 절차를 확인했다.

또한 기존 측정 환경과 개선 전후 수치를 구분하여 검색 성능 개선 과정을 정리했다.

단순히 응답 시간이 감소한 결과만 기록하는 대신,   
병목을 확인한 근거와 SQL·인덱스 개선을 선택한 이유, 다른 영역에 발생할 수 있는 비용을 함께 남기도록 했다.

> 검색 후보 추출 및 관련도 랭킹 실험

기존 제목 `LIKE` 검색에서 사용자가 입력한 검색어와 공고 제목의 표현이 다르면 관련 공고가 누락되는 문제를 확인했다.

대표적으로 `청년 주거 지원`은 기존 검색에서 결과가 없었지만, 정규화와 토큰 검색을 적용한 B1 후보 추출에서는 117건이 조회됐다.

이를 바탕으로 검색 기능을 후보 추출(Retrieval)과 관련도 랭킹(Ranking)으로 구분했다.

B1은 표현 차이로 누락되는 공고를 찾아 검색 범위를 확보하고, B2는 추출된 후보를 사용자 검색어와의 관련성에 따라 정렬하는 역할로 구분했다.

기존 검색과 B1·B2, 여러 관련도 세분화 방식을 SQL 프로토타입으로 비교했다.   
다만 BM25나 PostgreSQL 전문 검색과 직접 비교한 것은 아니므로 해당 방식보다 우수하다고 판단하지 않았다.

> 검색 관련도 우선순위 및 동률 처리 검토

B2 관련도 랭킹에서는 제목 일치 등급과 필드별 보너스를 활용하는 규칙 기반 방식을 실험했다.

초기에는 모집 상태를 우선하여 마감된 공고를 뒤로 보내는 방식을 검토했지만,   
이 경우 검색어와 관련성이 높은 마감 공고도 낮은 순위로 밀리는 문제가 있었다.

이에 검색 관련도를 최우선으로 두고, 모집 상태와 날짜는 관련도가 같은 공고 사이에서만 순서에 영향을 주도록 기준을 정리했다.

또한 `AI`, `파이썬`과 같은 검색어에서는 수백~수천 건의 공고가 동일한 관련도 점수를 받아 날짜가 사실상 순위를 결정하는 문제를 확인했다.

이를 보완하기 위해 독립 단어 일치(F1)와 제목 내 검색어 비율(F2)을 검토했으나,   
한국어 조사·붙여쓰기 처리와 짧은 제목에 유리한 편향 등의 한계가 있었다.

따라서 V1에서는 추가 점수 규칙을 적용하지 않고, 검색 관련도 평가를 위한 사람 평가 라벨을 기존 95건에서 109건으로 확장했다.

> PostgreSQL 생성 컬럼 성능 및 JPA 호환성 검증

검색 요청마다 약 14만 건의 공고 제목을 정규화하는 CPU 연산이 주요 병목임을 확인했다.

이를 줄이기 위해 PostgreSQL STORED 생성 컬럼인   
`search_title_norm`, `search_title_strip`을 격리된 DB에 추가하여 기존 방식과 비교했다.

후보 집합과 관련도 점수, 전체 정렬 순서를 유지한 상태에서 COUNT와 목록 조회의 p50이 약 59~82% 개선됐다.

반면 테이블 본체 용량이 약 36% 증가하고 INSERT 및 제목 UPDATE 비용도 늘어났다.

이를 통해 조회 시 반복 계산을 줄이는 대신 저장 공간과 쓰기 비용이 증가하는 트레이드오프를 확인했다.

또한 생성 컬럼은 기존 제목을 변경하지 않고 검색용 값을 별도로 계산하지만,   
공통 DB 스키마가 변경되므로 backend와 data-service의 매핑 및 데이터 저장 동작을 함께 확인해야 했다.

실제 JPA 통합 테스트에서는 Hibernate의 `ddl-auto: update`가   
생성 컬럼의 타입을 `text`에서 `varchar(255)`로 변경하려는 문제를 발견했다.

이에 `columnDefinition = "text"`를 명시하고 재현 테스트를 통해 생성 컬럼의 스키마가 유지되는 것을 확인했다.

DB 마이그레이션을 서비스 배포보다 먼저 적용해야 하는 이유와, JPA 매핑이 기존 스키마에 미치는 영향을 검증하는 과정의 중요성을 이해했다.

> B1 검색 후보 추출 구현 및 기존 기능 검증

SQL 프로토타입에서 검토한 B1 후보 추출 방식을 Java 검색 로직으로 구현했다.

NFKC 정규화와 토큰 AND 검색, 동의어 확장, 영문 단어 경계 검사, 정책 키워드 및 직업훈련 구분 정보 매칭을 적용했다.

46개 검색어를 대상으로 SQL 프로토타입과 Java 구현의 후보 ID 및 COUNT가 일치하는지 확인했다.

또한 기존 지역·모집 상태 필터와 정렬 기능을 유지하여 검색 범위를 확장하더라도 기존 조건 검색이 영향을 받지 않도록 검증했다.

다만 검색 가능한 후보가 늘어나면서 첫 페이지 응답 시간이 기존 제목 `LIKE` 검색보다 크게 증가하는 문제가 발생했다.

이를 통해 검색 누락을 줄이는 것과 API 응답 시간을 개선하는 것은 서로 다른 목표이며,   
검색 품질이 향상되더라도 실제 서비스에서 사용할 수 있는 성능을 함께 확보해야 한다는 점을 확인했다.

> B1 추가 병목 분석 및 직업훈련 검색 개선

B1 구현 이후 추가로 발생한 조회 비용을 분석하면서 직업훈련의 `training_target_name` 정규화가 병목에 영향을 주는 것을 확인했다.

해당 값은 약 13만 건의 공고에 저장되어 있지만 실제 원문 값의 종류는 11개에 불과했다.

이에 각 행에서 문자열을 반복 정규화하는 대신,   
서로 다른 원문 값을 먼저 확인하고 검색 토큰과 일치하는 값만 `IN` 조건으로 비교하도록 변경했다.

그 결과 `내일배움카드` 검색은 703ms에서 258ms로, `파이썬` 검색은 655ms에서 203ms로 감소했다.

다만 기존 `LIKE` 검색보다 여전히 느리고, `AI` 검색에서는 서비스 호출 시간의 개선이 확인되지 않았다.

또한 일부 경계 입력은 최종 코드로 재검증이 필요하며, SQL 실행 시간 외에 추가 JDBC 조회에 따른 비용도 고려해야 한다는 점을 확인했다.

따라서 B1의 성능 개선을 완료했다고 판단하지 않고, 실제 API 기준으로 추가 검증하기로 했다.

## 헷갈렸던 점

기존 제목 `LIKE` 검색이 빠르게 동작하는데도 검색 후보 추출 방식을 확장해야 하는지 고민했다.

기존 방식은 응답 속도가 빠르더라도 표현 차이로 관련 공고를 찾지 못할 수 있으므로,   
검색 품질과 응답 성능을 별도로 측정해야 한다는 점을 확인했다.

또한 검색에서 후보 추출과 관련도 랭킹을 분리하는 이유를 검토했다.   
검색 누락을 줄이는 B1과 후보의 우선순위를 결정하는 B2는 서로 다른 문제를 해결하므로,   
각각의 정확성과 성능을 구분해 검증해야 한다는 점을 이해했다.

관련도 점수를 세분화하기 위해 독립 단어 일치나 제목 내 검색어 비율을 적용하는 것이 적절한지도 검토했다.   
일부 검색어의 동률 문제를 완화할 수 있지만 한국어 표현과 제목 길이에 따른 편향이 있어 V1 적용을 보류했다.

검색 성능 개선에서는 생성 컬럼을 사용하는 것이 반드시 필요한지 고민했다.   
반복적인 CPU 연산을 줄일 수 있지만 저장 공간과 쓰기 비용이 증가하므로,   
실제 검색 빈도와 데이터 갱신 비용을 함께 고려해야 한다는 점을 확인했다.

또한 SQL 프로토타입에서 성능과 후보 정합성을 검증했더라도 Java API에서 같은 성능을 보장할 수 있는지 확인했다.   
실제 구현에서는 추가 조회와 데이터 변환 비용이 발생할 수 있으므로 최종 API 기준의 재측정이 필요하다는 점을 이해했다.

## 오늘 느낀 점

오늘은 통합 검색을 개선하면서 검색 결과를 빠르게 반환하는 것뿐 아니라   
사용자가 찾고자 하는 공고를 정확하게 제공하는 것도 중요하다는 점을 확인했다.

특히 기존 `LIKE` 검색에서 누락되던 공고를 B1으로 찾을 수 있게 되었지만, 후보가 늘어나면서 응답 시간이 증가하는 문제를 경험했다.   
이를 통해 검색 품질과 성능을 함께 개선하려면 서로 다른 지표로 문제를 정의하고 검증해야 한다고 느꼈다.

관련도 랭킹 실험에서는 새로운 점수 규칙을 추가하는 것이 항상 더 나은 검색 결과를 의미하지는 않았다.   
실제 사례를 비교하고 사람 평가 라벨을 확보하면서, 사용자가 기대하는 검색 순서를 기준으로 알고리즘을 검증하는 과정이 필요하다는 점을 배웠다.

생성 컬럼과 B1 최적화 과정에서는 하나의 병목을 줄이더라도 저장·쓰기 비용이나 추가 JDBC 조회처럼 새로운 비용이 발생할 수 있다는 점을 확인했다.   
또한 JPA 스키마 변경 문제를 해결하면서 성능 개선이 다른 서비스의 데이터 처리에 영향을 주지 않도록 검증해야 한다는 점을 이해했다.
