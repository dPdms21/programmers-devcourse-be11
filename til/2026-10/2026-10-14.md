# 2026-10-14 TIL (Today I Learned)

**project**

* Y:ON - 엔티티·API 계약 구체화 및 인증 코드 리뷰 · 개인화 추천 알고리즘 설계

## 오늘 배운 내용

오늘은 Y:ON의 엔티티별 필드 정의서를 작성하고 API 명세를 수정하면서, 영역 간 데이터 계약과 개인화 추천 알고리즘의 역할을 구체화했다.

사용자별 데이터 조회 경로를 `/api/users/me/...` 형태로 정리하고,   
인증·사용자 도메인 이관 PR을 리뷰하면서 JWT 인증의 쿠키 보안 설정과 Refresh Token 동시성, 비로그인 API 접근 설정 등을 검토했다.

DB 스키마 관리와 Flyway 도입 시점을 논의했다.

이후 신청 가능성 판정과 개인화 추천의 역할을 분리했다.   
정책 엔진은 사용자 자격조건을 평가하고,   
검색·추천 영역은 전달받은 판정 결과를 바탕으로 추천 후보를 선정하고 우선순위를 결정하도록 정리했다.

추천 후보는 `ELIGIBLE`을 우선하고 부족한 경우 `POSSIBLY_ELIGIBLE`로 보충하며,   
관심 분야 일치도를 주요 정렬 기준으로 활용하는 방향을 검토했다.

마지막으로 대표적인 추천 알고리즘 6가지를 비교하고,   
초기 사용자 행동 데이터가 부족한 Y:ON에서는 규칙 기반 필터링과 콘텐츠 기반 추천을 결합하는 방식이 적합하다고 판단했다.

## 실습 및 과제

> 엔티티 필드 정의 및 API 명세 수정

Y:ON의 엔티티별 필드 정의서를 작성하면서 각 데이터의 역할과 필요한 속성을 구체화했다.

이후 API 명세서를 검토하고 사용자별 데이터 조회 경로를 `/api/users/me/...` 형태로 통일했다.

관심 기회 저장·해제 API는 기존 경로를 유지하기로 하여 사용자별 조회 API와 리소스 조작 API의 경로를 구분했다.

API 경로를 정리하면서 엔드포인트의 기능뿐 아니라 인증된 사용자 정보와 요청 데이터가 어떤 관계를 갖는지도 고려해야 한다는 점을 확인했다.

> 인증·사용자 도메인 PR 코드 리뷰

인증·사용자 도메인 이관 PR을 검토하면서 HttpOnly Cookie 기반 JWT 인증의 보안 및 예외 처리 문제를 확인했다.

쿠키 기반 인증에서는 브라우저가 인증 쿠키를 자동으로 전송하므로 CSRF 대응을 함께 고려해야 한다는 점을 정리했다.

또한 쿠키의 보안 속성 설정이 일관되지 않은 부분과 Refresh Token 재발급 과정에서 동시 요청이 발생할 수 있는 문제를 검토했다.

카카오 OAuth2 로그인에서는 이메일이 항상 제공된다고 가정할 수 없으므로 null 응답에 대한 처리가 필요하다는 점도 확인했다.

특히 Y:ON은 비로그인 사용자도 기회 검색과 상세 조회를 이용할 수 있어,   
해당 API는 Spring Security에서 `permitAll()`을 적용하도록 접근 정책을 구분해야 한다는 점을 정리했다.

> DB 스키마 관리 및 영역 간 데이터 계약 검토

초기 개발 과정에서 엔티티와 테이블 구조가 자주 변경될 가능성을 고려해 Flyway 도입 시점을 검토했다.

또한 담당 영역 간 입력·출력 데이터와 갱신 시점을 미리 합의해야 하며,   
공통 DB를 통해 데이터를 공유하더라도 각 영역의 데이터 책임과 정합성을 고려해야 한다는 점을 확인했다.

> 신청 가능성 판정과 추천 알고리즘의 역할 분리

개인화 추천 점수에 지역, 연령, 취업 상태, 관심 분야 등을 모두 반영하는 방식을 검토하면서   
정책 엔진과 추천 영역의 역할이 중복될 수 있다는 문제를 확인했다.

거주지, 학교 소재지, 연령, 취업 상태와 같은 신청 자격조건은 정책 엔진에서 판정하고,   
검색·추천 영역은 해당 결과를 전달받아 후보 선정과 우선순위 결정에 활용하도록 구분했다.

신청 가능성 판정 결과에는 전체 조건 중 충족·불충족·판단 불가 조건의 개수를 제공하는 방향을 정책 엔진 담당자와 논의했다.

다만 조건마다 중요도가 다르므로 단순 충족 개수를 신청 확률이나 자격 충족률로 해석해서는 안 된다는 점을 확인했다.

판정 결과는 기존 `ELIGIBILITY_RESULT`를 통해 공유하는 방향으로 검토했으며,   
구체적인 데이터 구조와 전달 계약은 정책 엔진 설계가 진행되면서 확정하기로 했다.

> 개인화 추천 후보 및 정렬 기준 설계

추천 후보에서는 `NOT_ELIGIBLE`과 모집이 종료된 기회를 제외하고,   
`ELIGIBLE`을 우선 제공한 뒤 후보가 부족한 경우 `POSSIBLY_ELIGIBLE`로 보충하는 방향을 정리했다.

관심 분야는 온통청년의 대분류 5개를 공통 분류 기준으로 사용하고,   
중분류는 온통청년 공식 분류와 고용24 NCS 분류를 각각 유지하는 방식을 검토했다.

이를 위해 `OPPORTUNITY.category`를 공통 대분류로 활용하고,   
청년정책에는 중분류 코드를 추가하며 직업훈련에는 기존 NCS 코드를 활용하는 방향을 논의했다.

추천 정렬에서는 세부 관심 분야 일치도를 우선하고, 마감 임박과 신규 등록 여부는 보조 기준으로 사용하는 방향을 정리했다.

다만 아직 실제 추천 알고리즘을 구현하거나 성능을 검증한 단계는 아니므로   
구체적인 가중치와 최종 정렬 방식은 구현 과정에서 추가 검토하기로 했다.

> 추천 알고리즘 조사 및 적용 방식 비교

개인화 추천에 활용할 수 있는 대표적인 알고리즘 6가지를 조사했다.

규칙·지식 기반 추천, 콘텐츠 기반 필터링, 협업 필터링, 하이브리드 추천,   
학습 기반 랭킹, 상황 인식 추천의 원리와 장단점, 필요한 데이터와 적용 조건을 비교했다.

Y:ON은 초기 사용자 행동 데이터가 부족하고 신규 정책과 직업훈련 정보가 지속적으로 등록되므로,   
사용자 행동 이력에 크게 의존하는 협업 필터링을 초기부터 적용하기는 어렵다고 판단했다.

따라서 V1에서는 신청 가능성과 모집 상태를 활용한 규칙 기반 후보 필터링에 관심 분야 등   
기회 특성을 활용하는 콘텐츠 기반 추천을 결합하는 방식이 적절하다고 정리했다.

이후 조회·저장·숨김·신청 페이지 클릭 등 사용자 행동 데이터가 축적되면 행동 기반 재정렬을 검토하고,   
충분한 데이터가 확보된 뒤 협업 필터링이나 Learning to Rank와 비교하는 방향을 계획했다.

## 헷갈렸던 점

HttpOnly Cookie를 사용하면 JWT 인증의 보안 문제가 모두 해결되는지가 헷갈렸다.

HttpOnly는 JavaScript를 통한 쿠키 접근을 제한하지만,   
브라우저의 자동 쿠키 전송으로 발생할 수 있는 CSRF 위험까지 해결하지는 않으므로 별도의 대응이 필요하다는 점을 확인했다.

추천 알고리즘에서 지역, 연령, 취업 상태 등 모든 사용자 조건을 다시 점수화해야 하는지도 고민했다.

해당 조건은 이미 정책 엔진에서 신청 가능성을 판정하는 데 사용하므로,   
추천 영역에서는 판정 결과를 활용하면서 관심 분야와 기회의 특성을 중심으로 우선순위를 결정하도록 역할을 분리해야 한다는 점을 정리했다.

또한 신청 조건의 충족 개수가 많으면 신청 가능성이 높다고 판단해도 되는지가 헷갈렸다.

조건별 중요도와 AND/OR 관계가 다르고 필수조건 하나가 전체 판정에 영향을 줄 수 있으므로,   
단순 충족 개수를 신청 확률로 해석하지 않고 최종 판정 상태와 함께 사용해야 한다는 점을 확인했다.

## 오늘 느낀 점

오늘은 Y:ON의 데이터 구조와 API 계약을 구체화하고, 개인화 추천 알고리즘을 본격적으로 검토했다.

인증 코드를 리뷰하면서 기능이 동작하는 것뿐 아니라   
쿠키 보안 설정과 동시 요청, 비로그인 사용자 접근 등 실제 사용 환경에서 발생할 수 있는 문제를 함께 고려해야 한다는 점을 확인했다.

또한 정책 엔진과 검색·추천 영역의 책임을 분리하면서 같은 자격조건을 여러 영역에서 중복 평가하지 않고,   
각 영역이 제공하는 결과와 계약을 명확히 정의하는 것이 중요하다고 느꼈다.

추천 알고리즘을 비교하면서 유명하거나 복잡한 알고리즘을 적용하기보다   
현재 서비스의 사용자 규모와 데이터 특성에 적합한 방식을 선택해야 한다는 점을 배웠다.

초기에는 규칙 기반 필터링과 콘텐츠 기반 추천으로 시작하되,   
이후 사용자 행동과 추천 결과를 측정하면서 개선 근거를 확보하는 방향이 합리적이라고 판단했다.
