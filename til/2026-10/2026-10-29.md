## 오늘 배운 내용

오늘은 Y:ON 통합 검색의 B1 후보 추출 성능을 개선하고, 기존에 설계한 B2 규칙 기반 관련도 랭킹을 Java 검색 API에 구현했다.

공고 제목과 유형별 필드의 중요도를 반영해 검색 결과를 정렬하고, 관련도 정렬 과정에서 반복되는 모집 상태 계산을 최적화했다.   
프런트엔드에는 관련도 정렬 옵션을 연동하고 실제 정렬 기준과 화면 표시가 일치하도록 보완했다.

이후 동일한 후보 집합에서 규칙 기반 랭킹과 BM25의 검색 품질을 비교했다.   
평가 결과와 운영 비용을 검토하여 현재 서비스에서는 규칙 기반 B2를 유지하기로 했다.

다음으로 공고 상세 조회에서 신청 가능성 판정 정보와 관련된 중복 SQL을 제거하고 개선 전후의 쿼리 횟수와 응답 시간을 측정했다.

마지막으로 개인화 추천의 대량 후보 순회 구조를 분석했다.   
SQL 조회 횟수 감소와 배치 크기 변경만으로는 충분한 개선을 얻지 못했으며,   
최종적으로 DB에서 그룹별 상위 후보를 선정하는 방식으로 변경해 응답 성능을 개선했다.

## 실습 및 과제

> 통합 검색 B1 후보 추출 최적화 및 B2 관련도 랭킹 구현

기존 `LIKE` 검색의 후보 누락을 줄이기 위해 구현한 B1 후보 추출 쿼리를 최적화하고, B2 규칙 기반 관련도 랭킹을 검색 API에 적용했다.

B2에서는 공고 제목의 일치 정도를 우선하고, 청년정책과 직업훈련의 유형별 필드에 가중치를 부여하여 관련도 점수를 계산하도록 구현했다.

검색 관련도가 가장 높은 공고를 우선 배치하고, 모집 상태와 날짜는 관련도 동점인 경우에만 정렬 순서에 영향을 주도록 했다.

이 과정에서 관련도 정렬 시 모집 상태를 반복 계산하는 부분을 최적화하고, 기존 검색 필터와 정렬 기능의 동작을 유지하도록 검증했다.

또한 프런트엔드에 관련도 정렬 옵션을 연동하고, 경계 입력에서 실제 정렬 기준과 화면 표시가 일치하지 않는 문제를 수정했다.

이를 통해 검색 후보를 확장하는 것뿐 아니라 사용자가 기대하는 순서로 결과를 제공하고,   
API와 프런트엔드의 정렬 기준을 일관되게 유지하는 것이 중요하다는 점을 확인했다.

> 규칙 기반 관련도 랭킹과 BM25 비교

B2의 관련도 랭킹 방식이 적절한지 검토하기 위해 동일한 검색 후보 집합에서 규칙 기반 랭킹과 BM25를 비교했다.

BM25는 일부 범위가 넓은 검색어에서 더 적절한 공고를 상위에 배치하는 결과를 보였다.

다만 기존 평가 라벨의 범위와 편향으로 인해 BM25가 전체 검색어에서 일관되게 우수하다는 근거는 확보하지 못했다.

또한 BM25를 적용하려면 토큰 통계의 관리와 공고 데이터 변경 시 동기화 처리가 필요하므로, 현재 서비스의 규모와 개발 일정을 고려해야 했다.

이에 현재 구현에서는 규칙 기반 B2를 유지하고, 동일 관련도 점수를 받는 공고의 세부 순위 품질은 후속 개선 과제로 남겼다.

검색 알고리즘의 선택에서는 복잡한 알고리즘을 도입하는 것보다 실제 검색 품질과 유지보수 비용을 함께 비교해야 한다는 점을 확인했다.

> 공고 상세 조회 중복 SQL 제거 및 성능 측정

공고 상세 조회에서 신청 가능성 판정 정보를 조회하는 과정에 중복 SQL이 발생하는 문제를 개선했다.

기존 상세 조회 흐름과 판정 결과를 유지하면서 불필요하게 반복되는 데이터 조회를 제거했다.

그 결과 정책 상세 조회의 SQL 실행 횟수는 10회에서 7회, 직업훈련 상세 조회는 11회에서 8회로 감소했다.

동일한 테스트 조건에서 평균 응답 시간도 두 유형 모두 약 30% 단축됐다.

조회 결과의 동일성을 검증하면서 불필요한 SQL을 제거하는 것이 실제 응답 성능에 미치는 영향을 확인했다.

다만 해당 결과는 측정에 사용한 데이터와 환경을 기준으로 하므로, 실제 운영 환경의 응답 시간 개선 효과와는 구분해야 한다는 점을 정리했다.

> 개인화 추천 후보 조회 병목 분석 및 초기 개선

기존 개인화 추천은 최대 5개의 공고를 선정하기 위해 약 10만 건의 후보를 Java에서 순회하는 구조였다.

우선 배치마다 반복하던 숨김 공고 조회를 요청당 한 번으로 변경하여 SQL 실행 횟수를 1,028회 줄였다.

그러나 조회 횟수가 감소한 것과 달리 응답 시간의 뚜렷한 개선은 확인되지 않았다.

이후 후보 조회의 배치 크기를 늘리는 실험을 진행했지만,   
PostgreSQL 실행 계획이 전체 정렬 방식으로 변경되면서 오히려 응답 시간이 2~3배 증가했다.

이를 통해 SQL 호출 횟수를 줄이거나 배치 크기를 늘리는 것이 반드시 성능 개선으로 이어지지는 않으며,   
개별 쿼리의 실행 계획과 전체 후보 처리 비용을 함께 분석해야 한다는 점을 확인했다.

> 개인화 추천 그룹별 상위 후보 선정 최적화

기존 구조의 대량 후보 순회 문제를 해결하기 위해 후보 선정 책임을 Java에서 PostgreSQL로 일부 이동했다.

CTE와 `row_number()`를 활용해 DB에서 신청 가능성·관심 적합도에 따른 그룹별 상위 후보를 선정하고,   
Java에서는 기존 그룹 혼합 규칙과 최종 응답 조립을 유지하도록 변경했다.

이를 통해 추천 정책 자체를 변경하지 않고 후보 추출 방식만 개선하도록 했다.

동일 기준일의 격리된 측정 환경에서 추천 결과가 존재하는 시나리오의 평균 응답 시간이 9.8~12.4초에서 0.57~1.04초로 감소했으며,   
같은 시나리오끼리 비교했을 때 약 11~17배 개선됐다. SQL 실행 횟수도 최대 4,933회에서 11회로 감소했다.

또한 H2·PostgreSQL 기반의 무작위 테스트와 실제 데이터 비교를 통해 기존 추천 결과 및 응답의 동일성을 검증했다.

이 과정에서 데이터베이스가 후보를 효율적으로 선정하고,   
Java는 서비스의 최종 추천 정책을 적용하도록 역할을 구분하는 것이 대량 데이터 처리에 적합하다는 점을 확인했다.

다만 측정 결과는 동일 기준일의 격리 환경과 해당 추천 시나리오를 대상으로 하므로,   
다양한 사용자 조건과 실제 운영 부하에서도 같은 개선 폭이 나타나는지는 추가 검증이 필요하다.

## 헷갈렸던 점

규칙 기반 관련도 랭킹과 BM25 중 어떤 방식이 현재 서비스에 더 적합한지 고민했다.   
일부 검색어에서는 BM25의 순위 품질이 더 좋았지만,   
평가 라벨의 한계와 토큰 통계 관리 비용을 고려해 일관된 우위를 확인하기 전까지는 규칙 기반 방식을 유지하기로 했다.

공고 상세 조회에서는 기존 판정 결과를 변경하지 않으면서 중복 SQL을 제거할 수 있는지 검토했다.   
조회 흐름을 개선하더라도 사용자에게 반환하는 신청 가능성 정보와 상세 응답이 동일해야 한다는 점을 확인했다.

개인화 추천에서는 SQL 실행 횟수를 1,028회 줄였는데도 응답 시간이 뚜렷하게 개선되지 않은 이유를 분석했다.   
전체 처리 시간은 쿼리 호출 횟수뿐 아니라 각 쿼리의 실행 비용과 Java의 후보 처리량에도 영향을 받는다는 점을 이해했다.

또한 배치 크기를 늘리면 데이터베이스 왕복 비용이 줄어 성능이 좋아지는지 확인했다.   
실제로는 PostgreSQL 실행 계획이 변경되면서 전체 정렬 비용이 증가할 수 있으므로,   
배치 크기 변경도 실행 계획과 실제 응답 시간을 기준으로 판단해야 한다는 점을 확인했다.

추천 후보 선정을 DB로 이동하면서 기존 그룹별 우선순위와 최종 추천 결과를 유지할 수 있는지도 검토했다.   
후보 추출 방식과 추천 정책을 분리하고, 기존 결과와의 동일성을 테스트로 확인하는 것이 중요하다는 점을 이해했다.

## 오늘 느낀 점

오늘은 통합 검색의 B1·B2를 구현하면서 검색 품질 개선이 단순한 키워드 일치나 정렬 방식 변경으로 끝나지 않는다는 점을 확인했다.   
실제 검색어와 공고 데이터를 기준으로 결과를 비교하고, 알고리즘 선택에 필요한 근거를 확보하는 과정이 중요하다고 느꼈다.

BM25 비교에서는 복잡한 알고리즘이 일부 검색어에서 좋은 결과를 보이더라도 모든 상황에서 더 적합한 것은 아니라는 점을 배웠다.   
검색 품질뿐 아니라 데이터 동기화와 운영 비용을 고려해 현재 프로젝트에 적합한 방식을 선택해야 한다는 점을 이해했다.

공고 상세 조회에서는 기존 기능을 유지하면서 중복 SQL만 제거해 응답 시간을 개선할 수 있었다.   
이를 통해 새로운 기술을 도입하지 않더라도 실제 병목을 찾고 불필요한 작업을 제거하는 것만으로 의미 있는 성능 개선이 가능하다는 점을 확인했다.

개인화 추천에서는 SQL 실행 횟수를 줄이거나 배치 크기를 늘리는 초기 시도가 기대한 결과로 이어지지 않았다.   
이후 실행 계획과 데이터 처리 구조를 분석하여 DB에서 상위 후보를 선정하도록 변경하고,   
기존 추천 결과의 정합성을 유지하면서 응답 성능을 개선했다.   
이를 통해 단순한 SQL 감소보다 전체 데이터 흐름을 이해하고 동일한 조건에서 개선 효과를 검증하는 것이 중요하다는 점을 배웠다.
