## 오늘 배운 내용

오늘은 Y:ON의 개인화 추천 V1을 구현하고, 기존에 설계한 추천 정책을 실제 서비스 로직에 적용했다.

먼저 사용자 관심 분야와 공고 분류를 비교하는 적합도 매칭을 구현하고, 정책 엔진의 최신 신청 가능성 판정 결과를 연동했다.   
이 과정에서 실제 정책 데이터의 판정 정확성과 정규화 단계의 한계도 함께 확인했다.

이후 그룹별 우선순위와 시급성·신규성 기준을 적용해 최종 추천 공고를 선정하고, 추천 API와 추천 이유 생성 기능을 구현했다.

PostgreSQL 통합 테스트로 추천 결과의 정합성을 검증하고 SQL 실행 횟수를 측정했다.   
최신 `main` 병합으로 발생한 패키지 경로 오류도 해결했다.

마지막으로 코드 리뷰에서 확인된 후보 조회 비용과 마감 배지 문제를 검토·보완하고, 개인화 추천 V1 PR을 병합했다.

## 실습 및 과제

> 개인화 추천 관심 분야 적합도 매칭

사용자의 관심 분야와 공고 분류를 비교하여 추천 적합도를 판단하는 기능을 구현했다.

청년정책은 중분류가 일치하면 `HIGH`, 대분류가 일치하면 `MEDIUM`으로 분류했다.   
직업훈련은 NCS 2차분류와 1차분류를 기준으로 동일하게 처리했다.

관심 분야가 일치하지 않는 공고는 추천 대상에서 제외하고,   
관심 분야를 등록하지 않은 사용자는 `UNRESTRICTED`로 처리해 전체 분야를 추천 후보로 허용했다.

이 과정에서 관심 코드와 정규화된 공고 분류명의 표기가 정확히 일치해야 한다는 제약을 확인했다.   
또한 하위 분류명이 유일하다는 전제로 상위 분류를 다시 확인하지 않는 현재 방식의 한계도 파악했다.

> 신청 가능성 판정 결과 연동

기존 정책 엔진의 `EligibilityProvider.findFreshStatuses()`를 활용하여 사용자별 신청 가능성 판정 결과를 추천에 연동했다.

`ELIGIBLE`과 `POSSIBLY_ELIGIBLE`만 추천 대상으로 포함하고,   
`NOT_ELIGIBLE`, `UNKNOWN`, 미판정 및 오래된 판정 결과는 제외하도록 구현했다.

공고 버전·사용자 프로필 버전·판정 규칙 버전·유효기간을 기준으로 최신성을 확인하며,   
추천 요청마다 재판정하지 않고 저장된 최신 결과를 재사용하도록 했다.

이후 정책 엔진 담당자와 실제 데이터의 판정 정확성을 확인했다.

청년정책 3,416건 중 추가 신청 자격이나 참여 제한 항목에 원문 확인 조건이 포함된 1,246건은 최대 `POSSIBLY_ELIGIBLE`로 판정됐다.

다만 해당 조건이 정책 설명 본문에만 존재하면 판정 과정에서 인식하지 못할 수 있으며,   
`ELIGIBLE` 판정 가능 공고 634건 중 14건에서 이러한 사례를 확인했다.

해당 문제는 정규화 단계에서 보완하기로 하고, 추천 영역에서 신청 자격을 중복 판정하지 않도록 책임을 구분했다.

> 개인화 추천 우선순위 및 최종 선정

기존에 설계한 신청 가능성·관심 적합도 기반 A~D 그룹 선정 규칙을 실제 추천 알고리즘으로 구현했다.

`ELIGIBLE`과 `POSSIBLY_ELIGIBLE`의 판정 결과, 관심 적합도 `HIGH`·`MEDIUM`을 조합하여 그룹을 구분하고,   
A 그룹 우선 선정과 B·C 혼합 선정, D 그룹 보충 규칙을 적용했다.

또한 청년정책의 신청 마감일, 직업훈련의 교육 시작일, 신규 등록 여부를 활용하는 기존 우선순위를 구현했다.

동일 우선순위에서는 고정 정렬 기준을 적용하여 추천 결과의 순서를 일관되게 유지하고,   
조건을 충족하는 공고가 부족하면 최대 5건까지만 반환하도록 했다.

이를 통해 기존에 정의한 추천 정책이 후보 수와 그룹 구성에 따라 의도한 결과를 반환하는지 검증할 수 있도록 했다.

> 개인화 추천 API 및 추천 이유 생성

`GET /api/opportunities/recommendations`를 구현하여 로그인 사용자에게 개인화 추천 결과를 제공하도록 했다.

응답에는 공고 기본 정보와 신청 가능성, 저장 여부, 지역 정보 및 추천 이유를 포함했다.

추천 이유는 신청 가능성, 관심 분야 일치 수준, 신청 마감일 또는 교육 시작일을 기준으로 최대 3개의 배지와 설명을 생성하도록 했다.

직업훈련의 교육 시작일은 실제 신청 마감일이 아니므로 두 날짜의 의미를 구분했다.

또한 기존 상세 조회의 지역 변환 로직을 재사용하여 응답의 일관성을 유지하고,   
추천 API에 인증이 적용되도록 Security 경로 매처의 우선순위를 조정했다.

> PostgreSQL 통합 테스트 및 SQL 조회 검증

PostgreSQL Testcontainers를 활용해 추천 후보 조회부터   
관심 분야 매칭, 신청 가능성 판정 연동, 숨김 공고 제외, 최종 API 응답까지 검증했다.

사용자별 데이터 격리, 판정 결과의 만료·버전 불일치, A~D 그룹 우선순위,   
커서 기반 후보 조회, 복수 지역 및 상세 조회 API와의 응답 일관성도 확인했다.

또한 Hibernate Statistics와 StatementInspector를 사용하여 SQL 실행 횟수를 측정했다.

단일 배치에서 추천 결과가 1건일 때와 5건일 때 모두 SQL 실행 횟수가 13회로 동일해,   
해당 테스트 조건에서는 추천 결과 수에 따른 N+1 문제가 관측되지 않았다.

다만 소규모 테스트 데이터에서 확인한 결과이므로 실제 서비스 규모의 성능으로 일반화할 수 없으며,   
배치 크기에 따른 SQL 실행 횟수만으로 최적 조회 크기를 결정할 수 없다는 점을 확인했다.

> 최신 main 병합에 따른 컴파일 오류 해결

최신 `main` 병합 이후 추천 관련 테스트에서   
`ApplicationPeriod`, `ApplicationStatus`, `ApplicationStatusCalculator`를 찾지 못하는 컴파일 오류가 발생했다.

원인을 확인한 결과 수집·정규화 영역의 패키지 구조가 변경되면서   
관련 클래스가 `opportunity.normalization`에서 `opportunity.domain.status`로 이동한 것이었다.

기존 클래스를 중복 구현하지 않고 운영 코드와 테스트 코드의 import 경로만 수정하여 해결했다.

이후 추천 관련 테스트와 검색·저장·숨김 기능의 회귀 테스트를 실행해 기존 동작을 확인했다.

> 코드 리뷰 반영 및 마감 배지 처리 보완

코드 리뷰에서 추천 요청마다 판정 결과를 재계산하지 않고 저장된 최신 결과를 사용하는 구조를 유지하되,   
실제 데이터 규모에서 후보 조회 비용을 검증해야 한다는 점을 확인했다.

현재는 ID 커서 기반 배치 조회와 그룹별 상위 후보 유지 방식을 사용하지만,   
약 14만 건의 공고를 대상으로 후보를 100건씩 순회하면 SQL 실행 횟수가 증가하고 읽기 트랜잭션이 길어질 수 있다는 문제가 제기됐다.

메모리에 보관하는 후보 수가 적더라도 DB 조회 비용까지 줄어드는 것은 아니라는 점을 확인했다.

실데이터를 보유한 `yon_e2e` 환경에 접근하지 못해 실제 응답 시간과 병목은 측정하지 못했다.   
관심 분야 조건의 SQL 적용, 그룹별 상위 후보 조회 및 트랜잭션 범위 개선은 후속 검증 대상으로 남겼다.

또한 판정이 완료되지 않은 사용자는 빈 추천 목록을 받을 수 있음을 Swagger에 명시하고,   
문자열 정확 일치 방식과 인증 매처 순서의 제약을 주석으로 보완했다.

마감 배지에서는 유효한 상시 모집과 일반 모집이 함께 존재하는 공고에 `마감 D-n`이 표시될 수 있는 문제를 확인했다.

상시 모집이 계속되는데도 공고 전체가 곧 종료되는 것처럼 오해할 수 있으므로,   
`PeriodType.ALWAYS`와 `ValidationStatus.VALID`를 기준으로 유효한 상시 모집 여부를 확인하고 해당 배지를 제외하도록 수정했다.

기존 모집 상태와 추천 우선순위는 유지했으며, 혼합 모집·일반 모집·검토가 필요한 상시 모집에 대한 회귀 테스트를 추가했다.   
최종적으로 추천 관련 테스트 47건이 통과했다.

## 헷갈렸던 점

관심 분야 적합도 매칭을 구현하면서 정규화된 공고 분류명과 사용자 관심 분야를 문자열 정확 일치 방식으로 비교해도 되는지 검토했다.

현재 방식은 분류명 표기가 동일하고 하위 분류명이 유일하다는 전제에 의존하므로,   
분류 체계 변경이나 이름 중복이 발생하면 잘못 매칭될 수 있다는 점을 확인했다.

신청 가능성 판정 결과를 연동하면서 정책 설명 본문에 포함된 자격 제한 조건이 판정에 반영되지 않을 수 있다는 문제도 확인했다.   
추천 영역에서 조건을 다시 판정하기보다 정규화와 정책 엔진의 책임으로 구분하고, 해당 영역의 개선 결과를 반영하기로 했다.

추천 결과가 1건일 때와 5건일 때 SQL 실행 횟수가 동일했지만,   
이를 실제 서비스 규모에서도 조회 성능이 충분하다는 근거로 볼 수 있는지 고민했다.   
소규모 테스트와 전체 후보 조회 비용은 다르므로 실데이터 기반 측정이 필요하다는 점을 확인했다.

또한 유효한 상시 모집과 일반 모집이 함께 존재하는 공고의 마감 배지 처리를 검토했다.   
상시 모집이 유지되는데도 공고 전체가 마감되는 것으로 오해하지 않도록 유효한 상시 모집이 있으면 `마감 D-n` 배지를 제외하도록 수정했다.

## 오늘 느낀 점

오늘은 기존에 설계한 개인화 추천 정책을 실제 코드로 구현하면서,   
여러 조건을 조합한 추천 결과가 의도한 우선순위에 따라 선정되는지 검증하는 과정이 중요하다는 점을 확인했다.

특히 관심 분야 매칭과 신청 가능성 판정 결과를 연동하면서 추천 기능의 정확성은 자체 알고리즘뿐 아니라   
정규화된 공고 데이터와 정책 엔진의 판정 결과에도 의존한다는 점을 배웠다.   
각 영역의 책임을 구분하면서도 데이터의 정확성을 함께 확인해야 한다고 느꼈다.

추천 API와 추천 이유를 구현하면서는 내부 선정 기준이 사용자에게 제공되는 설명과 일치해야 한다는 점을 확인했다.   
신청 마감일과 교육 시작일처럼 의미가 다른 데이터를 구분하는 과정도 중요했다.

PostgreSQL 통합 테스트와 회귀 테스트를 통해 기능 간 연동과 데이터 정합성을 검증했으며,   
`main` 병합 이후 발생한 컴파일 오류를 해결하면서 팀 프로젝트에서 변경 사항의 영향을 확인하는 과정이 필요하다는 점을 배웠다.

마지막으로 코드 리뷰를 통해 기능적으로 올바른 구현과 실제 서비스 규모에서 효율적인 구현은 다를 수 있다는 점을 확인했다.   
이후에는 실데이터를 기반으로 병목을 측정하고, 추천 결과의 정확성을 유지하면서 조회 비용을 개선해야겠다고 생각했다.
