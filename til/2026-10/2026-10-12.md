## 오늘 배운 내용

오늘은 Y:ON의 기술 스택과 인증 방식을 정하고,   
온통청년·고용24 API의 데이터 특성을 바탕으로 수집·정규화·신청 가능성 판정·변경 추적 구조를 구체화했다.

백엔드는 Java·Spring Boot, DBMS는 PostgreSQL, 프론트엔드는 React 기반 반응형 웹앱으로 결정했다.   
인증은 카카오 OAuth2를 우선 구현하고 다른 소셜 로그인은 추후 확장하는 방향으로 검토했다.

온통청년 API의 불완전한 조건 데이터와 고용24의 구조화된 훈련과정 데이터를 비교하면서,   
공통 검색·추천 기능을 제공하더라도 데이터 소스별 수집과 정규화 방식은 구분해야 한다는 점을 확인했다.

정책 신청 가능성은 조건의 충족 여부뿐 아니라 정보 부족과 해석 불가 상태까지 구분하고,   
정책 변경과 사용자별 자격 변화도 별도로 관리하는 방향으로 설계했다.

기획을 구체화하면서 단순히 데이터를 저장하고 추천하는 것보다   
원본 추적성, 판정 근거, 변경 이력과 알림의 신뢰성을 확보하는 것이 중요하다는 점을 확인했다.

## 실습 및 과제

> 기술 스택 및 사용자 인증 방식 결정

백엔드는 Java·Spring Boot, DBMS는 PostgreSQL, 프론트엔드는 React 기반 반응형 웹앱으로 구성하기로 했다.

PostgreSQL은 관계형 데이터와 함께 JSONB를 활용해   
외부 API 원본과 복합 신청 조건, 판정 근거 등을 유연하게 관리할 수 있다는 점에서 선택했다.

React는 사용자 프로필 입력, 복합 검색·필터, 추천과 알림 등 사용자 상호작용이 많은 화면에 적합하다고 판단했다.

인증은 초기 구현 범위를 고려해 카카오 OAuth2를 우선 적용하고, Google 등 다른 소셜 로그인은 추후 추가하는 방향으로 검토했다.

또한 웹에서도 사용자 행동 이벤트를 수집할 수 있지만,   
iOS 모바일 웹의 백그라운드 푸시에는 제약이 있으므로 알림 방식은 실행 환경을 고려해야 한다는 점을 확인했다.

> 온통청년 데이터 정규화 및 AI 활용 방향

온통청년 API의 연령, 지역, 취업 상태, 학력, 소득 등 신청 조건을 다시 분석하고 정규화 기준을 구체화했다.

특히 연령의 최소·최대 값이 모두 0이더라도 제한 여부 코드나 원문과 충돌할 수 있어,   
이를 무조건 연령 제한 없음으로 처리해서는 안 된다는 점을 확인했다.

정규화는 별도의 Python 실행 환경을 추가하기보다 Java·Spring Boot에서 수집·변환·검증·저장을 통합하는 방향으로 정했다.

코드 매핑과 명시적인 날짜·숫자 변환은 규칙 기반으로 처리하고,   
복합조건이나 자연어 예외처럼 의미 해석이 필요한 부분에만 AI를 선택적으로 활용하는 방향을 구체화했다.

AI는 최종 신청 가능성을 판정하기보다 조건의 구조화 후보를 생성하는 역할로 제한하고,   
원문 근거와 적용 대상, AND/OR 관계 및 예외 범위를 검증할 필요가 있다는 점을 정리했다.

또한 공식 정책 원문을 크롤링해 API 정보를 보완하고,   
정보가 충돌하거나 확인되지 않는 경우에는 임의로 확정하지 않고 근거와 검증 상태를 보존하는 방향으로 설계했다.

> 고용24 API 데이터 구조 및 활용 방식 검토

고용24 국민내일배움카드 훈련과정 목록 API의 실제 JSON 응답을 분석했다.

훈련과정 ID와 회차, 지역, 훈련기간, 비용, 정원 등은 비교적 구조화되어 있었지만, 과정 설명이나 취업률 관련 값이 비어 있는 경우가 있었다.

공식 필드 정의와 실제 응답값이 일치하지 않는 항목도 있어 명세만으로 데이터의 의미를 판단해서는 안 된다는 점을 확인했다.

고용24는 우선 목록 API를 기반으로 추천과 변경 추적을 제공하는 방향으로 정리했다.

다만 훈련 시작일과 종료일은 신청기간과 다르므로 이를 신청 마감일로 사용하지 않고,   
실제 마감일을 확인할 수 없는 경우에는 마감 임박 알림을 생성하지 않는 방향으로 검토했다.

수정일 필드도 확인되지 않아 이전 수집 데이터와 새로운 응답의 해시값 및 주요 필드를 비교하는 변경 감지 방식이 필요하다고 판단했다.

> 사용자 프로필 및 신청 가능성 판정 설계

온통청년 정책과 고용24 훈련과정의 조건을 함께 비교할 수 있도록 공통 사용자 프로필과 직업훈련 전용 정보를 구분했다.

공통 프로필에는 연령, 거주지역, 취업·학적 상태, 학교 소재지, 소득·가구 정보 등을 고려하고,   
고용24 관련 정보로 국민내일배움카드 발급 상태와 훈련 참여 이력 등을 검토했다.

사용자가 정보를 정확하게 모르는 경우도 고려해 미입력, 모름, 해당 없음을 구분하도록 했다.

신청 가능성은 `ELIGIBLE`, `POSSIBLY_ELIGIBLE`, `NOT_ELIGIBLE`, `UNKNOWN`의 네 단계로 구분했다.

명확한 필수조건 불충족은 `NOT_ELIGIBLE`, 사용자 정보나 추가 확인이 필요한 경우는 `POSSIBLY_ELIGIBLE`,   
정책 데이터 자체가 불명확한 경우는 `UNKNOWN`으로 구분하는 방향이다.

또한 단순히 판정 결과만 저장하지 않고 조건별 충족 여부와 불충족 이유, 추가 확인 사항, 원문 근거를 함께 관리하도록 설계했다.

> 정책 상태·변경 이벤트 및 알림 구조 설계

정책의 신청 상태와 데이터 관리 상태를 분리했다.

신청 상태는 `UPCOMING`, `OPEN`, `ALWAYS_OPEN`, `CLOSED`, `UNKNOWN`으로 구분하고,   
관리 상태는 `ACTIVE`, `ARCHIVED`로 별도 관리하는 방향으로 정리했다.

마감된 정책도 재모집이나 신청기간 연장이 발생할 수 있으므로 신청 종료와 데이터 보관을 동일하게 처리하지 않도록 했다.

또한 정책 자체의 변경과 사용자별 신청 가능성 변화를 별개의 이벤트로 설계했다.

특히 `BECAME_ELIGIBLE`은 정책 조건 변경뿐 아니라 사용자 프로필 수정으로도 발생할 수 있어 이벤트의 발생 원인을 구분할 필요가 있었다.

한 정책에서 여러 조건이 동시에 변경되면 개별 변경 이벤트를 기록하되,   
사용자별 신청 가능성은 최종 조건을 기준으로 재판정하고 관련 알림을 통합하는 방향으로 정리했다.

이를 위해 변경 내용, 정책 이벤트, 사용자별 자격 변화, 알림 전달 기록의 역할을 구분했다.

> Raw 데이터 보관 및 동기화 전략

외부 API와 크롤링 데이터를 주기적으로 수집할 때 동일한 원본을 반복 저장하지 않도록 해시값 기반 변경 감지 방식을 선택했다.

원본 해시가 동일하면 `lastSeenAt`만 갱신하고, 변경된 경우에는 새로운 Raw Snapshot을 저장한 뒤 정규화와 검증을 수행하는 흐름으로 정리했다.

원본 내용이 변경됐더라도 실제 정책 조건은 동일할 수 있으므로 Raw 데이터 변경과 정규화된 정책의 변경은 별도로 판단해야 한다는 점을 확인했다.

동기화는 현재 고려 중인 AWS 운영 환경을 기준으로 하루 한 번 Full Sync를 수행하고, 변경된 데이터만 선택적으로 재처리하는 방식을 검토했다.

또한 서버가 중지된 동안 Scheduler 실행이 누락될 수 있으므로 마지막 동기화 시점과 성공·실패 이력을 관리해야 한다는 점을 정리했다.

> 추천 성과 및 운영 지표 검토

추천이 실제 사용자 행동으로 이어지는지 확인하기 위해 정책 상세 조회율, 저장률, 신청 페이지 이동률, 알림 클릭률 등을 검토했다.

React에서 사용자 행동을 감지하고 Spring Boot 서버에 이벤트를 저장하면   
추천 노출 당시의 신청 가능성 결과와 이후 사용자 행동을 연결할 수 있다는 점을 확인했다.

다만 신청 페이지 이동이 실제 신청 완료를 의미하지는 않으며,   
소수의 테스트 사용자 데이터를 전체 서비스 성과로 일반화해서는 안 된다는 점도 정리했다.

사용자 행동 지표 외에도 API 응답 시간, 데이터 동기화 성공률, 이벤트 처리 실패율과 데이터 정합성 등 운영 지표를 함께 고려하기로 했다.

## 헷갈렸던 점

온통청년 API에서 연령의 최소·최대 값이 모두 0으로 제공되는 경우 이를 연령 제한 없음으로 해석해도 되는지가 헷갈렸다.

제한 여부 코드나 공식 원문과 충돌하는 경우가 있기 때문에 0이나 빈 값을 특정 의미로 단정하지 않고,   
제한 없음과 정보 누락, 해석 불가 상태를 구분해야 한다는 점을 확인했다.

고용24의 훈련 시작일과 종료일을 신청기간으로 사용해도 되는지도 고민했다.

훈련 일정과 신청 일정은 서로 다른 개념이므로 실제 신청 마감일이 확인되지 않으면 마감 임박 알림을 생성해서는 안 된다는 점을 정리했다.

Raw 데이터의 변경과 실제 정책 변경을 동일하게 처리해도 되는지도 고민했다.

API 응답의 단순 문구나 공백이 달라졌다고 실제 신청 조건이 변경된 것은 아니므로,   
원본 해시 비교와 정규화된 정책의 의미 있는 변경을 구분해야 한다는 점을 확인했다.

또한 신청 가능성이 새롭게 충족되는 이벤트가 정책 변경에 의해서만 발생하는지 헷갈렸다.

사용자의 프로필이 변경되어도 같은 결과가 발생할 수 있으므로   
정책 변경 이벤트와 사용자별 자격 변화 이벤트를 구분하고 발생 원인을 관리해야 한다는 점을 정리했다.

## 오늘 느낀 점

오늘은 그동안 논의했던 기능과 데이터 처리 방향을 실제 서비스 구조로 연결하면서 기획을 거의 마무리하는 단계까지 구체화했다.

특히 온통청년과 고용24는 데이터 구조가 다르지만 사용자에게는 동일한 검색·추천·저장 경험을 제공해야 하므로,   
공통 모델과 데이터 소스별 고유 구조를 적절하게 분리하는 것이 중요하다고 느꼈다.

또한 불완전한 데이터에서 조건을 임의로 확정하지 않고   
판정 근거와 불확실성을 관리하는 것이 잘못된 추천과 알림을 줄이기 위한 핵심이라는 점을 확인했다.

기획 과정에서 기술을 선정하는 것뿐 아니라 각 기술과 데이터 구조를 왜 선택했는지 설명할 수 있도록 정리했다는 점에서 의미가 있었다.
