## 오늘 배운 내용

오늘은 Y:ON의 기획을 거의 마무리하면서 데이터 저장 방식과 서비스 구현 범위를 정리하고, 시스템 구성도와 와이어프레임을 제작했다.

외부 데이터는 SHA-256 해시를 활용해 변경된 경우에만 새로운 Raw Snapshot을 저장하는 방향으로 정리했다.   
이를 통해 동일한 데이터를 반복 저장하지 않으면서 원본 이력을 관리하는 방식을 구체화했다.

이후 React·Spring Boot·PostgreSQL과 외부 데이터 소스의 연결 구조를 시스템 구성도로 표현하고,   
주요 화면과 사용자 흐름을 와이어프레임으로 정리했다.

검색·추천 백엔드 담당 영역의 API 8개와 Request·Response DTO를 Notion에 작성하면서,   
다른 팀원의 구현이 완료되기 전에도 공통 데이터 계약을 바탕으로 개발을 진행할 수 있다는 점을 확인했다.

프론트엔드에서는 통합 검색·필터, 로그인 상태별 화면 구성, 상단 네비게이션과 정보형 카드 구조를 검토하고   
세이지 그린 계열을 중심으로 디자인 방향을 구체화했다.

마지막으로 제출 문서를 검토하면서 신청 가능성별 추천 점수 등 세부 정책을 논의했다.

## 실습 및 과제

> 프로젝트 기획 구체화 및 데이터 저장 방식 정리

Y:ON 기획서와 요구사항 명세서를 검토하면서 서비스의 주요 문제와 실제 구현 범위가 일치하는지 확인했다.

청년 지원정책과 직업훈련 정보의 분산, 복잡한 신청 자격조건, 불완전한 외부 데이터의 어려움을 주요 문제로 정리했다.

외부 API와 크롤링 원본을 보관할 때 동일한 데이터를 반복 저장하지 않도록 SHA-256 해시 기반 Raw Snapshot 저장 방식을 정리했다.

또한 고용24의 대량 훈련과정 데이터를 고려해 초기 수집 범위를 제한하고, AWS 운영 환경에서의 수집·저장 부담을 줄이는 방향을 검토했다.

> 시스템 구성도 및 와이어프레임 제작

Y:ON의 전체 시스템 구조와 데이터 흐름을 시각화하기 위해 시스템 구성도를 제작했다.

React 반응형 웹앱과 Spring Boot 백엔드, PostgreSQL, 온통청년·고용24 API 및 공식 정책 원문 간의 관계를 정리했다.

백엔드는 인증·사용자 관리, 데이터 수집·정규화, 신청 가능성 판정, 검색·추천, 변경 추적·알림 영역으로 구분해 각 기능의 역할을 표현했다.

또한 홈·대시보드, 기회 탐색, 기회 상세, 관심 기회, 알림 등 주요 화면을 중심으로 와이어프레임을 제작했다.

비로그인 사용자도 기회 검색과 상세 조회를 이용할 수 있도록 하고,   
로그인 사용자에게는 개인화 추천과 관심 기회 저장, 알림, 프로필 기반 탐색을 제공하는 방향으로 화면 흐름을 정리했다.

로그인 후 모든 프로필 입력을 강제하기보다 기본 정보를 먼저 등록하고 나머지는 추후 보완할 수 있는 사용자 흐름도 검토했다.

> 검색·추천 API 명세서 및 DTO 작성

담당 영역인 검색·추천 백엔드의 API 명세서를 Notion에 작성했다.

기회 통합 목록 조회·검색·필터, 상세 조회, 변경 이력 조회, 개인화 추천 목록,   
사용자 행동 이벤트 기록, 관심 기회 목록·저장·해제 등 총 8개 API의 HTTP 메서드와 경로를 정리했다.

`OpportunitySearchRequest`, `OpportunityListResponse`, `OpportunityDetailResponse`, `RecommendationListResponse`,   
`UserBehaviorEventRequest`, `SavedOpportunityListResponse` 등 Request·Response DTO도 함께 정의했다.

관심 기회 저장은 `POST`, 저장 해제는 `DELETE`로 구분하고, 저장 관계가 삭제되더라도 사용자 행동 이력은 별도로 관리하도록 설계했다.

변경 이력 조회 API는 다른 담당자의 데이터 생성·관리 영역과 연결되므로 응답 데이터 계약과 구현 책임을 협의할 필요가 있다는 점을 확인했다.

실제 수집 데이터가 준비되기 전에도 Mock 데이터로 검색·필터·추천 기능을 개발할 수 있지만,   
공통 엔티티와 신청 가능성 판정 규칙을 임의로 확정하지 않도록 영역 간 계약을 먼저 정리해야 한다는 점을 확인했다.

> 프론트엔드 화면 구성 및 UI/UX 방향 구체화

React 기반 반응형 웹앱의 화면 구성과 검색·필터 구조, 디자인 방향을 검토했다.

청년정책과 직업훈련은 통합 탐색을 기본으로 제공하되 지역, 분야, 신청 가능성, 데이터 유형 등의 공통 필터를 두고   
선택한 유형에 따라 세부 필터를 추가하는 방향으로 정리했다.

비로그인 사용자는 검색 조건을 직접 선택할 수 있지만,   
프로필을 기반으로 자동 적용하는 ‘내 조건으로 보기’는 로그인 사용자에게만 제공하도록 구분했다.

홈 화면은 로그인 여부와 프로필 등록 상태에 따라 내용을 달리하고,   
비로그인 사용자에게는 서비스 소개와 신규 기회를, 로그인 사용자에게는 맞춤 추천과 내 조건 요약 등을 중심으로 구성하도록 검토했다.

레이아웃은 공통 네비게이션을 상단에 배치하고, 기회 탐색 화면에서는 좌측 필터와 우측 검색 결과를 사용하는 구조로 정리했다.

홈은 기회를 발견하기 쉬운 카드형 레이아웃, 검색 결과는 여러 공고를 비교하기 쉬운 목록형 레이아웃으로 구분했다.

디자인은 가독성과 신뢰감을 우선하여 세이지 그린·뮤트 그린 계열을 주요 색상으로 검토했다.   
웜 화이트와 아이보리 등 밝은 배경, 충분한 여백, 정돈된 정보 구조를 중심으로 여러 레퍼런스와 UI 시안을 비교했다.

또한 PWA의 개념과 웹 푸시 지원 조건을 확인하고,   
브라우저 및 iOS 환경의 제약을 고려해 인앱 알림과 웹 푸시를 구분할 필요가 있다는 점을 정리했다.

로고는 Y:ON의 성장과 기회 이미지를 표현하기 위해 전구 안에 Y 형태의 새싹을 배치한 시안을 제작했다.

> 제출 문서 검토 및 세부 정책 논의

기획서와 요구사항 명세서를 검토하며 실제 구현 범위와 문제 정의가 일치하도록 세부 내용을 조정했다.

신청 가능성이 확인된 `ELIGIBLE`과 추가 확인이 필요한 `POSSIBLY_ELIGIBLE`을 추천에서   
동일한 점수로 평가하는 것은 적절하지 않다는 점을 논의했다.

이에 따라 신청 가능성 상태별 추천 가중치를 구분하는 방향을 검토하고, 구체적인 점수 차이는 추천 정책 설계 과정에서 결정하기로 했다.

회원 탈퇴 시 개인정보와 관련 기록의 삭제 범위를 검토했으며,   
휴면 계정 처리는 초기 MVP에서 제외하고 장기 미접속 관리 정책을 추후 고려하는 방향으로 논의했다.

## 헷갈렸던 점

검색·추천 백엔드 개발을 다른 팀원의 데이터 수집과 신청 가능성 판정 구현이 완료된 뒤에 시작해야 하는지가 고민됐다.

공통 API와 DTO 계약을 먼저 정의하면 Mock 데이터로 병렬 개발할 수 있지만,   
다른 영역의 데이터 구조와 판정 결과를 임의로 확정하지 않아야 한다는 점을 확인했다.

프론트엔드에서는 청년정책과 직업훈련의 데이터 구조가 다른데 검색 화면을 하나로 통합해도 되는지가 고민됐다.

공통 필터를 기본으로 제공하고 데이터 유형에 따라 세부 필터를 구분하면   
통합 탐색의 편의성과 유형별 조건의 차이를 함께 반영할 수 있다는 점을 정리했다.

또한 좌측 네비게이션과 검색 필터를 동시에 배치할 경우 검색 결과 영역이 좁아지는 문제가 있었다.

이를 해결하기 위해 공통 네비게이션은 상단에 두고 탐색 화면에서만 좌측 필터를 사용하는 방향으로 정리했다.

React 기반 웹앱에서도 사이트에 접속하지 않은 상태로 푸시 알림을 받을 수 있는지도 확인했다.

FCM 웹 푸시는 브라우저와 운영체제의 지원 조건에 영향을 받으며,   
특히 iOS에서는 홈 화면에 추가한 웹앱 등 별도 조건이 필요하므로   
인앱 알림을 기본으로 제공하고 웹 푸시는 보조 수단으로 고려해야 한다는 점을 이해했다.

## 오늘 느낀 점

오늘은 Y:ON의 기획을 거의 마무리하면서 실제 구현에 필요한 시스템 구성도와 와이어프레임, API 명세서 및 DTO를 구체화했다.

검색·추천 백엔드와 프론트엔드를 함께 담당하기 때문에   
API 응답 구조와 사용자 화면에서 필요한 정보를 일관되게 설계해야 한다는 점을 확인했다.

또한 다른 팀원의 개발을 기다리기보다 공통 계약을 먼저 협의하고 Mock 데이터를 활용해 병렬 개발을 준비하는 것이 중요하다고 판단했다.

프론트엔드에서는 디자인의 완성도뿐 아니라   
사용자가 여러 정책을 쉽게 찾고 비교할 수 있는 검색·필터 구조와 정보의 가독성을 우선해야 한다는 점을 배웠다.

기획 단계에서 기능과 역할, 데이터 흐름, 화면 구조를 구체화함으로써   
이후 개발 과정에서 발생할 수 있는 영역 간 의존성과 구현 문제를 미리 검토할 수 있었다는 점에서 의미가 있었다.
