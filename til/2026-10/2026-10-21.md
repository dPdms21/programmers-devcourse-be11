## 오늘 배운 내용

오늘은 Y:ON의 공고 상세 조회 API를 구현하고, 로그인 상태에 따라 신청 가능성 판정 결과와 저장 여부를 제공하도록 구성했다.

이후 상세 조회 과정에서 발생하는 중복 SQL을 발견해 개선 전 성능을 측정하고,   
코드 리뷰에서 지적된 내부 디버깅 정보의 API 노출 문제를 수정했다.

정책 엔진의 배치 최신화 기능이 추가되면서 검색·상세 조회와의 연동을 통합 테스트로 검증했다.   
공고 버전 변경에 따른 판정 결과의 최신성, 재판정 전후의 조회 결과와 사용자별 데이터 격리를 확인했다.

마지막으로 개인화 추천 V1에서 미확정 상태였던 그룹별 선정 비율, 프로필 미등록 사용자 처리, 후보 조회 및 중단 조건을 구체화했다.

## 실습 및 과제

> 공고 상세 조회 API 구현

청년정책과 직업훈련의 공통 정보 및 유형별 상세 정보를 조회하는 API를 구현했다.

청년정책은 신청기간·지원 내용·신청 방법·운영기관·신청 URL 등을 제공하고,   
직업훈련은 훈련기관·교육기간·훈련비·정원 등을 제공하도록 구성했다.

비로그인 사용자에게는 공고 정보를 제공하고, 로그인 사용자에게는 신청 가능성 판정 결과와 저장 여부를 추가로 반환하도록 했다.

신청 가능성은 `EligibilityProvider.findFreshEligibility()`를 사용해 저장된 최신 판정 결과만 조회하며,   
상세 조회 과정에서 재판정하지 않도록 했다.

비로그인·미판정·만료된 판정은 `eligibility=null`로 처리하고, 실제 판정 결과인 `UNKNOWN`과 구분했다.

또한 직업훈련의 교육 시작일은 실제 신청 마감일이 아니므로 교육기간과 신청기간을 구분하고,   
`applicationStatus`는 `UNKNOWN`으로 유지했다.

> 공고 상세 조회 Before 성능 측정

상세 조회 과정에서 동일한 공고 데이터가 중복 조회되는 문제를 발견하고 최적화 전 성능을 측정했다.

`OpportunityDetailService`가 상세 정보를 조회한 이후   
`EligibilityProvider.findFreshEligibility()` 내부의 `OpportunityInfoAssembler`가 공고·신청기간·훈련 정보를 다시 조회하면서   
추가 SQL 3회가 발생하는 것을 확인했다.

PostgreSQL 16.14 Testcontainers 환경에서 시나리오별 워밍업 20회, 측정 100회를 수행했다.

중복 조회 JDBC 시간은 전체 평균 응답 시간의 약 16~17%에 해당했다.

다만 중복 쿼리를 제거해도 전체 응답 시간이 같은 비율로 개선된다는 의미는 아니므로,   
실제 개선 효과는 동일한 환경에서 After 성능을 측정해 비교하기로 했다.

> 공고 상세 조회 코드 리뷰 반영

코드 리뷰에서 상세 조회 응답의 `ConditionItem.reason`에 내부 정규화 과정의 디버깅 문구가 노출될 수 있다는 문제를 확인했다.

해당 필드는 사용자에게 제공할 설명이 아니므로 응답 DTO와 매핑에서 제거했다.

반면 조건 원문을 확인할 수 있는 `evidenceText`와 검증 상태인 `validationStatus`는 유지했다.

또한 `eligibility.conditions[].reason`은 사용자별 신청 가능성 판정 사유이므로 유지하여, 두 필드의 목적을 구분했다.

관련 회귀 테스트를 추가했으며, H2와 PostgreSQL 기반 상세 조회 테스트가 각각 9개씩 통과했다.

> 정책 엔진 배치 최신화와 검색·상세 조회 연동 검증

정책 엔진 담당자가 구현한 신규·변경 공고의 신청 가능성 배치 최신화 기능을 검색·상세 조회 API와 연결해 검증했다.

공고의 정규화 버전이 변경되면 이전 판정 결과를 최신 결과로 사용하지 않아야 한다. 배치 실행 전에는 미판정 상태를 반환하고,   
실행 후에는 현재 공고 버전에 대한 판정 결과를 제공하는지 확인했다.

PostgreSQL Testcontainers 기반 통합 테스트를 추가하여   
신규 공고 판정, 기존 공고 버전 변경에 따른 재판정, 신청 가능성 필터와 페이지네이션의 정합성을 검증했다.

또한 상세 조회의 판정 상태·사유·조건별 결과, 사용자별 판정 결과 및 저장 여부 격리, 예외 발생 이후 재시도 흐름을 확인했다.

검증한 경로에서는 운영 코드의 결함이 발견되지 않아 기존 기능을 수정하지 않고 통합 테스트만 추가했다.

전체 테스트 476개 중 385개가 실행·통과했고, 91개는 환경변수 조건으로 건너뛰었다.

다만 테스트용 정규화 데이터로 검증한 결과이므로   
실제 공공데이터의 수집·정규화부터 판정·조회까지 이어지는 전체 흐름과 DB 장애 상황은 추가 검증이 필요하다.

> 개인화 추천 V1 미확정 정책 구체화

기존 규칙 기반·카테고리 기반 추천 설계를 바탕으로 그룹별 선정, 프로필 미등록 사용자, 추천 후보 조회 및 중단 조건을 구체화했다.

B·C 그룹 혼합 추천은 A 그룹(`ELIGIBLE` + 관심 적합도 높음)을 우선 선정하고,   
부족한 자리를 B 그룹(`ELIGIBLE` + 관심 적합도 보통)과 C 그룹(`POSSIBLY_ELIGIBLE` + 관심 적합도 높음)으로 구성하기로 했다.

기존 B:C = 3:2 고정 비율 대신 후보 규모에 따라 유연하게 선정하는 방식으로 변경했다.

B·C가 모두 충분하고 남은 자리가 2개 이상이면 C 그룹을 최소 1건 포함하되, B 그룹에 더 높은 선정 비중을 부여하기로 했다.   
B·C 후보가 부족할 경우에만 D 그룹으로 보충한다.

판정 프로필 미등록 사용자 처리는 로그인하지 않은 사용자는 개인화 추천 API에 접근할 수 없으며,   
로그인했더라도 판정 프로필이 없으면 `PROFILE_NOT_FOUND`를 반환하도록 정리했다.

반면 판정 프로필이 있고 관심 분야만 등록하지 않은 사용자는 전체 카테고리를 추천 후보로 허용하기로 했다.

이를 통해 신청 가능성 판정에 필요한 프로필과 선택 정보인 관심 분야의 역할을 구분했다.

추천 후보 조회 및 중단 조건에서는 전체 공고를 조회하거나 모두 재판정하는 방식의 처리 비용을 고려해,   
DB에서 모집 상태·날짜·카테고리 등의 조건으로 후보를 먼저 선별하기로 했다.

이후 제한된 크기의 후보를 조회하고 `EligibilityProvider.getEligibilities()`로 일괄 판정하도록 설계했다.

추천 가능한 공고 5건을 확보하더라도 이후 후보에서 더 높은 우선순위의 공고가 등장할 수 있으므로,   
조회 순서가 추천 우선순위를 보장하지 않는다면 조기 종료하지 않기로 했다.

조회 크기 50건, 최대 판정 후보 200건은 초기 가설로 두고,   
구현 이후 추천 결과와 평균·p95 응답 시간 및 SQL 실행 횟수를 측정해 조정하기로 했다.

추가로 기존 코드 계약을 검토하면서 사용자 관심 분야 조회 기능은 회원 담당자에게 요청하고,   
숨김 공고 일괄 조회와 추천 전용 후보 조회는 검색·추천 영역에서 구현하기로 정리했다.

스타트업 개발자는 요구사항 분석부터 설계·구현·코드 리뷰·QA·배포·운영·장애 대응까지 서비스 개발 전반에 참여할 수 있다.   
배포 이후에도 사용자 피드백을 바탕으로 문제를 발견하고 개선하는 과정이 반복된다.

장애 발생 시에는 원인 분석보다 영향 범위 확인과 피해 최소화가 우선이다.   
필요에 따라 기능을 차단하거나 롤백한 뒤, 로그와 데이터를 바탕으로 원인을 분석하고 재발 방지책을 마련해야 한다.

AI는 코드 생성뿐 아니라 설계 검토·코드 리뷰·테스트 작성에도 활용할 수 있다.

다만 AI가 작성한 테스트도 실제 요구사항과 예외 상황을 검증하는지 직접 확인해야 한다.

취업 준비에서는 이력서에 핵심 경험을 간결하게 압축하고,   
포트폴리오에는 문제 정의·원인 분석·대안 비교·기술 선택 이유와 결과를 구체적으로 기록하는 것이 중요하다.

또한 비개발자도 이해할 수 있도록 기술적 내용을 설명하는 능력을 기르고,   
취업 이후에도 주간·월간·분기별로 업무와 문제 해결 경험을 기록해 커리어를 관리할 필요가 있다.

## 헷갈렸던 점

상세 조회에서 신청 가능성 판정 결과가 없는 상태와 실제 판정 결과인 `UNKNOWN`을 어떻게 구분해야 하는지 고민했다.

미판정·만료된 판정은 `null`로 처리하고, 실제 판정 결과가 존재하는 경우에만 해당 상태와 사유를 제공하도록 구분했다.

상세 조회에서 발생한 중복 SQL의 JDBC 시간이 실제 성능 개선 폭을 의미하는지도 검토했다.   
쿼리 실행 시간과 전체 응답 시간은 다르므로, Before 측정만으로 개선 효과를 단정할 수 없다는 점을 확인했다.

개인화 추천에서는 B 그룹을 우선하면 관심 적합도가 높은 C 그룹이 제외될 수 있다는 점을 고민했다.   
이에 고정 비율보다 실제 후보 규모에 따라 유연하게 선정하는 방향으로 정리했다.

또한 추천 공고 5건을 확보했더라도 이후 페이지에 더 높은 우선순위의 후보가 존재할 수 있으므로,   
후보 조회 순서가 최종 추천 우선순위를 보장하지 않는다면 조기 종료해서는 안 된다는 점을 확인했다.

## 오늘 느낀 점

오늘은 공고 상세 조회 API를 구현하고 실제 SQL 실행 내역과 성능 지표를 확인하면서,   
기능이 정상적으로 동작하는 것과 효율적으로 동작하는 것은 별개의 문제라는 점을 느꼈다.

중복 조회 문제를 발견했을 때 바로 최적화하기보다 Before 성능을 측정하고,   
이후 동일한 조건에서 개선 효과를 비교할 수 있도록 근거를 남기는 과정이 중요했다.

또한 정책 엔진과의 연동을 검증하면서 개별 기능의 정상 동작뿐 아니라   
공고 버전 변경에 따른 데이터 최신성과 사용자별 정합성까지 확인해야 한다는 점을 배웠다.

개인화 추천 설계에서는 추천 개수를 채우는 것보다 선정 기준과 우선순위를 명확하게 정의하는 것이 중요했다.   
추천 품질과 처리 비용 사이의 균형을 고려하고, 초기 가설은 실제 측정 결과를 바탕으로 검증해야겠다고 생각했다.

프로젝트 중 발생한 문제와 해결 과정, 측정 결과를 꾸준히 기록해 포트폴리오와 취업 이후의 커리어 관리에도 활용해야겠다고 생각했다.
