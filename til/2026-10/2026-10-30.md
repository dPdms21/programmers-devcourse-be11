## 오늘 배운 내용

오늘은 Y:ON 개인화 추천의 운영 경로와 성능 비교용 참조 구현의 역할을 구분하고, 사용자 행동 이벤트를 프런트엔드에 연동했다.

추천 공고의 노출과 상세 조회, 외부 링크 클릭을 수집하도록 구현하고, 중복 이벤트와 전송 실패가 사용자 경험에 영향을 주지 않도록 처리했다.   
또한 행동 이벤트의 현재 활용 범위와 향후 추천 품질 평가에 활용할 지표를 정리했다.

이후 약 200만 건의 이벤트 데이터를 활용해 PostgreSQL 저장 성능을 측정하고, 일반 테이블과 월별 파티션 테이블의 성능을 비교했다.

다음으로 행동 이벤트의 최근 4개월 보관 정책과 관리자 미리보기·실행 기능을 구현했다.   
코드 리뷰에서는 정리 계획 조회 시 잠금 대기 문제가 발생할 수 있음을 확인하고, PostgreSQL에서 재현한 뒤 보완했다.

## 실습 및 과제

> 개인화 추천 운영 경로 및 참조 구현 구분

전날 진행한 개인화 추천 성능 최적화 이후 실제 운영에서 사용하는 추천 경로를 확인했다.

기존에 Java에서 전체 후보를 순회하던 구현은 운영 요청에 사용하지 않고,   
PostgreSQL에서 그룹별 상위 후보를 선정한 뒤 Java가 최종 추천 규칙을 적용하도록 구성했다.

기존 전체 순회 구현은 새로운 후보 선정 방식이 동일한 추천 결과를 반환하는지 비교하기 위한 테스트용 참조 구현으로 유지했다.

이를 통해 실제 운영 로직과 정합성 검증용 구현의 책임을 구분하고, 최적화 이후에도 기존 추천 정책의 동등성을 확인할 수 있도록 했다.

> 사용자 행동 이벤트 프런트엔드 연동

기존 백엔드 행동 이벤트 API를 프런트엔드에 연동하여 `IMPRESSION`, `DETAIL_VIEW`, `EXTERNAL_LINK_CLICK` 이벤트를 수집하도록 구현했다.

`SAVE`, `HIDE`는 기존 백엔드의 상태 변경 시점에 기록되는 방식을 그대로 사용했다.

추천 공고의 `IMPRESSION`은 카드가 50% 이상 노출된 상태로 1초 동안 유지될 때 기록하도록 했다.

상세 조회와 외부 링크 클릭 이벤트에는 사용자가 진입한 경로를 전달하여 행동이 발생한 맥락을 구분할 수 있도록 했다.

또한 재렌더링과 데이터 재조회로 동일한 이벤트가 중복 기록되지 않도록 처리하고,   
이벤트 전송에 실패하더라도 화면 이동이나 링크 클릭이 중단되지 않도록 했다.

이 과정에서 행동 데이터 수집은 부가적인 작업이므로, 기록 실패가 사용자의 핵심 기능 이용을 방해하지 않아야 한다는 점을 확인했다.

> 사용자 행동 이벤트 활용 범위 및 저장 성능 검증

수집한 행동 이벤트의 목적과 현재 추천 알고리즘에 반영되는 범위를 구분했다.

현재 행동 이벤트는 추천 순위 계산에 직접 사용하지 않으며,   
향후 추천 노출 대비 상세 조회율·저장률·외부 링크 클릭률 등의 지표를 분석하는 데 활용할 예정이다.

행동별 가중치와 시간 감쇠 방식은 충분한 실제 데이터가 확보된 이후 기존 추천 방식과 비교하여 효과를 검증하기로 했다.

이후 PostgreSQL 16.14 격리 환경에서 합성 사용자 1만 명, 공고 약 14만 건, 배경 이벤트 200만 건을 대상으로 이벤트 저장 성능을 측정했다.

이벤트 INSERT의 DB 실행 시간은 평균 0.40~0.57ms였으며, 일반 테이블과 월별 파티션 테이블 사이에서 일관된 성능 차이는 확인되지 않았다.

동시 사용자 50명 조건에서는 커넥션 풀 대기가 발생했지만, 이벤트 INSERT 자체가 주요 병목이라는 근거는 부족했다.

따라서 추가적인 조회 제거 또는 비동기 처리로 구조를 변경하기보다 기존 트랜잭션 정합성과 이벤트 기록 실패 격리 방식을 유지하기로 했다.

이를 통해 성능 측정은 반드시 구조 변경으로 이어져야 하는 것이 아니라, 현재 구현을 유지할 근거를 확인하는 과정이기도 하다는 점을 이해했다.

> 행동 이벤트 보관 정책 및 자동 정리 구현

행동 이벤트가 지속적으로 누적되는 문제를 관리하기 위해 현재 월을 포함한 최근 4개월 보관 정책을 구현했다.

월별 파티션의 이름이 아니라 PostgreSQL 카탈로그에 기록된 실제 날짜 범위를 기준으로 정리 대상을 판단하도록 했다.

또한 롤백용 `_old` 테이블이 남아 있거나 DB와 애플리케이션 날짜가 크게 다른 경우에는 정리를 중단하여 잘못된 데이터 삭제를 방지하도록 했다.

중복 실행을 방지하기 위해 advisory lock을 적용하고, 파티션별 독립 트랜잭션과 잠금 제한 시간을 설정했다.

이를 통해 일부 파티션 정리에 실패하더라도 다른 정리 작업에 미치는 영향을 제한하도록 구성했다.

단순히 보관 기간이 지난 데이터를 삭제하는 것뿐 아니라, 삭제 대상의 정확성과 중복 실행, 부분 실패 상황을 함께 고려해야 한다는 점을 확인했다.

> 관리자 정리 API 및 수동 실행 경로 구현

자동 정리 외에도 관리자가 삭제 예정 파티션을 확인하고 직접 정리할 수 있도록 미리보기·실행 API와 Docker 수동 실행 경로를 추가했다.

관리자는 미리보기에서 삭제 대상을 확인한 뒤, 계획 토큰이 일치하는 경우에만 실제 정리를 실행할 수 있도록 했다.

정리 실행 시에는 관리자 권한을 다시 검증하여 계획 조회 이후의 권한 변경도 고려했다.

또한 자동 정리의 dry-run 설정과 관리자 실행의 실제 삭제 여부가 독립적이라는 점을 확인했다.

관리자 화면에서는 미리보기와 실제 삭제를 구분하고, HTTP 요청이 시간 초과되더라도 서버의 삭제 작업이 계속 진행 중일 수 있다는 점을 고려했다.

따라서 요청 실패 직후 무조건 재실행하기보다 실행 로그와 현재 파티션 상태를 확인해야 한다는 운영 기준을 정리했다.

> 코드 리뷰 반영 및 파티션 정리 잠금 문제 해결

코드 리뷰에서 파티션 생성·삭제 단계와 달리 정리 계획 조회 단계에는 잠금 제한 시간이 적용되지 않는 문제를 발견했다.

삭제 대상을 조회하는 `pg_total_relation_size()`와 DEFAULT 파티션 확인 과정에서도 다른 트랜잭션의 잠금으로 인해 장시간 대기할 수 있었다.

이를 실제 PostgreSQL의 `ACCESS EXCLUSIVE` 잠금으로 재현하고, 계획 조회를 별도 읽기 트랜잭션으로 분리한 뒤 `SET LOCAL`을 적용했다.

이후 시간 초과 시 트랜잭션 rollback, advisory lock 해제, 커넥션 설정 복원까지 검증했다.

이를 통해 데이터 삭제 작업에서는 실제 DDL 실행뿐 아니라 사전 조회 단계도 잠금 대기와 장애의 원인이 될 수 있다는 점을 확인했다.

## 헷갈렸던 점

사용자 행동 이벤트를 수집하면 개인화 추천에 바로 반영해야 하는지 고민했다.   
현재 이벤트는 추천 품질 분석을 위한 데이터로 수집하며,   
행동별 가중치를 적용하려면 실제 데이터와 비교 실험을 통해 효과를 검증해야 한다는 점을 확인했다.

행동 이벤트 저장에서 일반 테이블과 파티션 테이블 중 어느 방식이 더 빠른지도 확인했다.   
측정 결과 일관된 성능 차이가 없었으므로,   
파티셔닝의 목적을 INSERT 가속보다는 데이터 보관과 정리의 운영 편의성으로 구분해야 한다는 점을 이해했다.

동시 사용자 50명 조건에서 발생한 커넥션 풀 대기가 이벤트 INSERT의 성능 문제인지도 검토했다.   
DB 실행 시간과 커넥션 대기 시간을 분리해서 측정해야 실제 병목을 판단할 수 있다는 점을 확인했다.

파티션 정리에서는 실제 삭제 전에 수행하는 계획 조회에도 잠금 제한이 필요한지 확인했다.   
메타데이터와 테이블 크기를 조회하는 과정에서도 잠금 대기가 발생할 수 있어 읽기 트랜잭션의 시간 제한이 필요하다는 점을 이해했다.

또한 관리자 정리 API의 요청이 시간 초과되면 서버 작업도 중단되는지 검토했다.   
HTTP 요청 결과만으로 작업 종료 여부를 판단할 수 없으므로, 재실행 전 서버 로그와 파티션 상태를 확인해야 한다는 점을 정리했다.

## 오늘 느낀 점

오늘은 사용자 행동 이벤트를 프런트엔드에 연동하면서   
데이터 수집 기능이 사용자 경험을 방해하지 않도록 책임과 실패 범위를 구분하는 것이 중요하다고 느꼈다.   
또한 수집한 행동 데이터를 추천 품질 개선에 활용하려면 충분한 실제 데이터와 검증 근거가 필요하다는 점을 확인했다.

이벤트 저장 성능 측정에서는 파티셔닝이 항상 INSERT 성능을 높이는 것은 아니며,   
커넥션 풀 대기와 실제 DB 실행 시간을 구분해야 한다는 점을 배웠다.   
특히 측정 결과를 근거로 불필요한 구조 변경을 피하고 현재 방식을 유지하는 것도 의미 있는 기술적 판단이라는 점을 이해했다.

행동 이벤트 보관 정책과 관리자 정리 기능을 구현하면서 데이터 삭제는 보관 기간뿐 아니라   
잠금 충돌, 부분 실패, 재실행 및 복구 가능성까지 고려해야 한다는 점을 확인했다.

특히 코드 리뷰에서 발견한 잠금 문제를 실제 PostgreSQL에서 재현하고 보완하면서,   
예상 가능한 장애 상황을 테스트로 검증하는 과정의 중요성을 배웠다.
