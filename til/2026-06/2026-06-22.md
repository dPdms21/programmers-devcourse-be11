## 오늘 배운 내용

오늘은 JDBC 기반 `UserDAO`의 구조를 단계적으로 개선하며 관심사 분리, 인터페이스, 의존성 주입과 제어의 역전을 학습했다.

초기에는 `add()`와 `get()`이 각각 DB 연결 코드를 가지고 있었지만, 공통 연결 로직을 `getConnection()`으로 추출해 중복을 제거했다.

이후 DB 연결 방식을 하위 클래스에 맡기는 상속 구조를 거쳐, 연결 기능을 별도 객체와 인터페이스로 분리했다.  
마지막에는 `UserDAO`가 구현체를 직접 생성하지 않고 생성자를 통해 전달받도록 변경했다.

이를 통해 `UserDAO`는 사용자 저장·조회에 집중하고, DB 연결 구현과 객체 조립 책임은 외부로 분리할 수 있었다.

SOLID 과제에서는 SRP, OCP, LSP, ISP, DIP를 각각 별도의 예제로 구현하며 클래스와 인터페이스를 분리하는 기준을 확인했다.

SQL 문제에서는 `IN`, `YEAR()`, `MONTH()`, `DATE_FORMAT()`, `ROUND()`, `IFNULL()`, `IS NOT NULL`을 활용한 조회 방법을 복습했다.

## 실습 및 과제

> DAO 관심사 분리와 의존관계 실습

JDBC를 이용해 `users` 테이블에 사용자를 저장하고 조회하는 `UserDAO`를 구현했다.

DB 연결 정보는 `.env`에 분리하고 `dotenv-java`를 통해 읽었다.  
`System.getenv()`는 `.env` 파일을 직접 읽지 않으므로 `Dotenv.load()`를 사용해야 했다.

처음에는 `UserDAO`의 각 메서드에 중복된 연결 코드가 있었고, 이를 `getConnection()` 메서드로 추출했다.

다음 단계에서는 `UserDAO`를 추상 클래스로 만들고 연결 메서드를 하위 클래스가 구현하도록 구성했다.  
하지만 연결 방식 하나를 변경하기 위해 상속 계층이 필요하고 부모와 자식의 결합도가 높아지는 한계가 있었다.

이를 개선하기 위해 연결 기능을 `SimpleConnectionMaker` 인터페이스로 분리하고,   
`NConnectionMaker`, `DConnectionMaker`가 구현하도록 했다.

마지막에는 `UserDAO`가 구현체를 직접 만들지 않고 생성자를 통해 외부에서 주입받도록 변경했다.

이 구조에서는 `UserDAO`가 인터페이스에만 의존하고, 실제 구현체 선택과 객체 조립은 `Start`가 담당한다.

> SOLID 원칙 구현

SRP에서는 `Journal`이 내용 관리만 담당하고, 출력 책임은 `JournalSaver`로 분리했다.

OCP에서는 할인 로직을 `DiscountPolicy` 인터페이스와 구현체로 나눠 새로운 등급을 추가할 때 기존 코드를 수정하지 않도록 했다.

LSP에서는 모든 새가 날 수 있다고 가정하지 않고, 공통 행동은 `Bird`, 비행 가능한 새는 `FlyingBird`로 분리했다.

정사각형과 직사각형 예제를 통해 수학적인 포함 관계가 성립하더라도 부모 타입의 동작 약속을 지키지 못하면 올바른 상속이 아니라는 점을 확인했다.

ISP에서는 인쇄, 스캔, 팩스 기능을 각각의 인터페이스로 분리해 클래스가 필요하지 않은 메서드까지 구현하지 않도록 했다.

DIP에서는 `NotificationService`가 구체 발송 클래스를 직접 생성하지 않고 `MessageSender` 인터페이스를 통해 구현체를 주입받도록 했다.

추가로 `SilverDiscount`, `AllInOneMachine`, `MockSender`를 구현해 기존 구조를 수정하지 않고 기능을 확장했다.

> SQL SELECT 문제 풀이

`ORDER BY`는 기본적으로 오름차순이므로 큰 값부터 조회할 때는 `DESC`를 사용했다.

같은 컬럼의 여러 값을 비교할 때는 `OR`를 반복하기보다 `IN`을 사용했다.  
서브쿼리가 여러 행을 반환할 가능성이 있을 때도 `=`이 아니라 `IN`을 사용해야 했다.

날짜에서는 `YEAR()`와 `MONTH()`로 연도와 월을 추출하고, 출력 형식은 `DATE_FORMAT()`으로 맞췄다.

평균은 `AVG()`로 계산하고, 반올림은 `ROUND(AVG(컬럼), 자릿수)`처럼 별도로 적용했다.

NULL 값을 다른 문자열로 표시할 때는 `IFNULL()`을 사용하고, NULL인 행을 제외할 때는 `IS NOT NULL`을 사용했다.

## 헷갈렸던 점

`System.getenv()`가 프로젝트의 `.env` 파일을 자동으로 읽는다고 생각했지만, 운영체제나 실행 설정에 등록된 환경변수만 읽는다.  
`.env`를 사용하려면 `Dotenv` 객체를 생성한 뒤 값을 가져와야 했다.

상속 구조에서 인터페이스 기반 객체 조합 구조로 변경한 뒤에도 `UserDAO`를 `abstract`로 둘 필요가 있는지 헷갈렸다.  
추상 메서드가 사라지고 구현체를 생성자로 전달받는 구조라면 일반 클래스로 두는 것이 맞았다.

조회 결과가 없을 때도 값을 바로 꺼내려 했지만, `ResultSet.next()`가 `true`인지 먼저 확인해야 했다.

`static` 중첩 클래스 안에 메서드를 선언하면 메서드도 자동으로 `static`이라고 생각하기 쉬웠다.  
`eat()`, `fly()`, `swim()`이 인스턴스 메서드라면 객체를 생성한 뒤 호출해야 했다.

`MockSender`에 별도의 `save()` 메서드만 만들면 `MessageSender` 구현으로 인정된다고 생각했지만,   
인터페이스에 선언된 `send()`를 정확히 재정의해야 했다.

`AVG()`에 반올림 자릿수를 함께 전달하려 했지만, 평균 계산과 반올림은 각각 `AVG()`와 `ROUND()`로 나누어 작성해야 했다.

NULL은 일반 값처럼 `=`이나 `!=`로 비교하지 않고 `IS NULL`, `IS NOT NULL`을 사용해야 했다.

## 오늘 느낀 점

객체지향 설계는 단순히 클래스를 많이 나누는 것이 아니라 변경될 가능성이 있는 책임과 의존관계를 분리하는 과정이라는 점을 이해했다.

상속만으로 기능을 분리하면 구조가 경직될 수 있지만,   
인터페이스와 의존성 주입을 사용하면 기존 코드를 수정하지 않고 구현체를 교체하거나 확장할 수 있었다.

SOLID 예제를 직접 구현하면서 각 원칙이 독립적인 규칙이라기보다 낮은 결합도와 높은 확장성을 만들기 위해 서로 연결된 기준이라는 점을 확인했다.

SQL 문제에서는 알고 있는 문법이라도 조건 하나나 출력 형식 하나를 놓치면 실패할 수 있으므로   
문제의 요구사항을 끝까지 확인하는 습관이 중요하다고 느꼈다.
