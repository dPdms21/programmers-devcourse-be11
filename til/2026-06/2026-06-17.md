## 오늘 배운 내용

오늘은 Java 멀티스레드를 중심으로 스레드 생성과 실행, 데몬 스레드, 동기화, 실행 제어, 세마포어를 실습했다.

`start()`를 호출하면 새로운 스레드가 생성되어 `run()`을 실행하고, 메인 스레드는 다음 코드를 계속 실행한다.  
반면 `run()`을 직접 호출하면 새 스레드가 만들어지지 않고 현재 스레드에서 일반 메서드처럼 순차 실행된다.

`Thread.sleep()`은 특정 스레드 객체를 재우는 것이 아니라 해당 코드를 실행 중인 현재 스레드를 멈춘다.  
`join()`은 대상 스레드가 종료될 때까지 현재 스레드가 기다리게 하며, 모든 작업이 끝난 뒤 결과를 출력할 때 사용할 수 있다.

여러 스레드가 같은 값을 동시에 변경하면 경쟁 상태가 발생할 수 있다.  
`synchronized`를 사용하면 한 번에 하나의 스레드만 공유 데이터의 변경 작업을 수행하도록 제한할 수 있다.

세마포어는 permit 수를 기준으로 임계 영역에 동시에 들어갈 수 있는 스레드 수를 제한한다.  
`acquire()` 또는 `tryAcquire()`로 permit을 얻고, 작업이 끝나면 `release()`로 반환한다.

---

추가로 BFS와 DFS를 구현하며 그래프 탐색 방식의 차이를 확인했다.  
BFS는 `Queue`를 사용해 가까운 정점부터 탐색하고, DFS는 재귀 또는 `Stack`을 사용해 한 경로를 깊게 탐색한다.

## 실습 및 과제

> Java 스레드와 동기화 실습

메인 스레드와 새로 생성한 스레드가 서로 독립적으로 실행되기 때문에 출력 순서가 매번 달라질 수 있다는 점을 확인했다.

싱글 스레드는 작업을 순서대로 처리하고,   
멀티스레드는 여러 작업을 동시에 처리하는 것처럼 실행하거나 여러 CPU 코어에서 병렬로 실행할 수 있다.  
다만 스레드 생성과 컨텍스트 스위칭 비용이 발생하므로 멀티스레드가 항상 더 빠른 것은 아니다.

데몬 스레드는 일반 스레드를 보조하는 백그라운드 스레드다.  
모든 일반 스레드가 종료되면 데몬 스레드가 작업 중이어도 JVM이 종료되며, `setDaemon(true)`는 `start()` 전에 호출해야 한다.

`synchronized (this)`는 현재 객체를 잠금 대상으로 사용한다.  
같은 객체를 공유하는 스레드는 동기화되지만, 서로 다른 객체를 사용하면 잠금 대상도 다르므로 동시에 실행될 수 있다.

> 달팽이 경주 구현

각 달팽이를 별도의 스레드로 실행해 동시에 이동하는 경주 프로그램을 구현했다.

공유되는 경주 종료 상태에는 `volatile`을 사용해 한 스레드가 변경한 값을 다른 스레드가 확인할 수 있도록 했다.  
우승자와 순위를 기록하는 부분은 동기화해 여러 달팽이가 동시에 도착했을 때 결과가 충돌하지 않도록 처리했다.

`Thread.sleep()`으로 달팽이의 이동 속도를 조절하고, 모든 달팽이가 경주를 마친 뒤 결과를 출력하기 위해 `join()`을 사용했다.

추가로 경주 거리, 달팽이 수, 우승 예측 등의 옵션을 입력받도록 기능을 확장했다.

> 스레드 실행 제어 구현

`interrupt()`, `isInterrupted()`, `Thread.interrupted()`, `yield()`, `join()` 등 스레드 실행 제어 메서드를 실습했다.

`interrupt()`는 스레드를 강제로 종료하는 것이 아니라 중단 요청을 전달한다.  
실행 중인 스레드는 인터럽트 상태를 확인해 스스로 종료해야 하며,   
`sleep()` 중 인터럽트가 발생하면 `InterruptedException`으로 즉시 깨어난다.

`isInterrupted()`는 인터럽트 상태를 확인만 하고, `Thread.interrupted()`는 현재 스레드의 상태를 확인한 뒤 초기화한다.

`yield()`는 다른 실행 가능한 스레드에 실행 기회를 양보할 수 있음을 알리지만, 실제 실행 순서는 보장하지 않는다.

> 세마포어 게임 구현

던전에 동시에 입장할 수 있는 모험가 수를 제한하기 위해 `Semaphore`를 사용했다.

```java
new Semaphore(capacity, true);
```

두 번째 인자를 `true`로 설정해 먼저 기다린 스레드가 먼저 입장할 수 있는 공정한 세마포어를 적용했다.

`tryAcquire(5, TimeUnit.SECONDS)`를 사용해 일정 시간 동안 permit을 얻지 못하면 던전 입장을 포기하고 마을로 돌아가도록 구현했다.

각 모험가는 여러 번 던전에 도전하며 골드를 획득하고,   
모든 스레드가 종료된 뒤 `join()`으로 대기한 다음 총 골드를 기준으로 랭킹을 출력했다.

> BFS 구현

인접 리스트와 `Queue`를 사용해 너비 우선 탐색을 구현했다.

시작 정점을 먼저 방문 처리하고 Queue에 넣은 뒤, 정점을 하나씩 꺼내 인접한 미방문 정점을 추가하는 방식으로 탐색했다.  
추가로 각 정점까지의 최단 거리를 계산하고, 이전 정점을 저장해 시작점부터 도착점까지의 경로를 복원했다.

> DFS 구현

재귀와 `Stack`을 사용해 깊이 우선 탐색을 각각 구현했다.

재귀 DFS는 현재 정점을 방문한 뒤 인접한 미방문 정점을 재귀 호출하는 방식으로 동작했다.  
Stack 기반 DFS에서는 방문 순서를 맞추기 위해 인접 정점을 넣는 순서를 조절했다.

추가로 연결 요소 수, 사이클 여부 등 그래프 분석 기능을 구현했다.

## 헷갈렸던 점

`run()`과 `start()`의 차이가 가장 중요했다.

`run()`을 직접 호출하면 현재 스레드에서 순차 실행되므로 여러 작업이 동시에 실행되지 않는다.  
새 스레드에서 작업을 실행하려면 반드시 `start()`를 호출해야 한다.

`Thread.sleep()`도 호출한 객체가 잠드는 것으로 생각하기 쉬웠다.  
하지만 `sleep()`은 `static` 메서드이므로 `t1.sleep()`처럼 호출해도 실제로는 해당 코드를 실행 중인 현재 스레드가 멈춘다.

`volatile`은 공유 변수의 최신 값을 보이게 하지만 여러 스레드가 동시에 값을 변경하는 작업 자체를 안전하게 만들지는 않는다.  
공유 값 변경이 원자적으로 처리되어야 하는 경우에는 `synchronized` 같은 동기화가 별도로 필요하다.

`synchronized (this)`는 코드 전체가 아니라 현재 객체를 잠근다는 점도 헷갈렸다.  
같은 객체를 공유해야 같은 잠금을 사용하며, 각 스레드가 서로 다른 객체를 가지고 있으면 동기화되지 않는다.

세마포어에서는 `availablePermits()`가 스레드가 입장한 순간의 고정된 값이 아니라 호출 시점의 남은 permit 수를 반환한다.  
다른 스레드가 그 사이에 permit을 획득할 수 있으므로 출력이 일정한 순서로 감소하지 않아도 정상이다.

또한 permit을 실제로 얻지 못했는데 `finally`에서 무조건 `release()`하면 permit 수가 잘못 증가할 수 있다.  
따라서 `tryAcquire()`의 반환값으로 permit 획득 여부를 확인한 뒤, 획득한 경우에만 반환해야 한다.

멀티스레드의 출력 순서는 실제 실행 순서와 정확히 일치하지 않을 수 있다는 점도 확인했다.  
로그가 섞였다는 이유만으로 스레드 동작이 잘못되었다고 판단하면 안 된다.

---

BFS에서는 정점을 Queue에서 꺼낼 때가 아니라 Queue에 넣을 때 방문 처리해야 중복 삽입을 막을 수 있다는 점을 정리했다.

DFS는 재귀 호출이 끝나면 이전 정점으로 돌아가 아직 방문하지 않은 다음 인접 정점을 탐색한다는 흐름이 헷갈렸다.  
Stack 기반 DFS에서는 재귀와 같은 방문 순서를 만들기 위해 인접 정점을 역순으로 넣어야 한다는 점도 확인했다.

## 오늘 느낀 점

멀티스레드는 코드를 작성하는 것보다 여러 스레드가 어느 시점에 실행되고 어떤 값을 공유하는지 흐름을 이해하는 것이 더 어려웠다.

특히 `sleep()`, `join()`, `interrupt()`처럼   
현재 스레드와 대상 스레드가 다르게 동작하는 메서드는 호출 형태만 보고 판단하면 헷갈릴 수 있었다.

달팽이 경주와 세마포어 게임을 구현하면서 스레드를 동시에 실행하는 것뿐만 아니라,   
공유 상태를 안전하게 변경하고 모든 작업이 끝난 시점을 기다리는 제어가 중요하다는 점을 느꼈다.

---

BFS와 DFS는 같은 그래프를 탐색하더라도 사용하는 자료구조와 방문 순서가 다르므로,   
문제에서 요구하는 탐색 목적에 따라 방식을 선택해야 한다고 느꼈다.
