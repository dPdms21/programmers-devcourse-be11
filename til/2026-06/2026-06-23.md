## 오늘 배운 내용

오늘은 객체 생성과 관계 설정 책임을 `DaoFactory`로 분리하고,   
Spring IoC 컨테이너가 설정 정보를 바탕으로 빈을 생성하고 관리하는 흐름을 학습했다.

`DaoFactory`는 어떤 객체를 생성하고 어떻게 연결할지 정의하는 설정 역할을 한다.  
`ApplicationContext`는 해당 설정을 읽어 실제 객체를 생성하고, 의존관계 설정과 빈 조회·생명주기를 관리한다.

`@Configuration`은 설정 클래스임을 나타내고, `@Bean`이 선언된 메서드의 반환 객체는 Spring 빈으로 등록된다.  
`context.getBean("userDAO", UserDAO.class)`에서 빈 이름은 기본적으로 `@Bean` 메서드명이고, 두 번째 인자는 조회할 빈의 타입이다.

일반 팩토리 메서드는 호출할 때마다 새로운 객체를 반환하지만,   
Spring 컨테이너에서 같은 빈을 여러 번 조회하면 기본 싱글톤 스코프에 따라 같은 객체를 반환한다.

싱글톤 빈은 여러 요청과 스레드가 공유하므로 요청마다 달라지는 값을 인스턴스 필드에 저장하지 않고,   
매개변수나 지역변수로 처리하는 무상태 설계가 필요하다.

SQL 문제에서는 `JOIN`, 날짜 범위 조건, `LIKE`, `GROUP BY`, `AVG()`를 사용해 여러 테이블의 데이터를 연결하고   
그룹별 결과를 조회하는 방법을 복습했다.

## 실습 및 과제

> 오브젝트 팩토리와 IoC 컨테이너 실습

`Start`가 직접 `ConnectionMaker`와 `UserDAO`를 생성하던 구조에서 객체 생성과 조립 책임을 `DaoFactory`로 분리했다.

`Start`는 완성된 `UserDAO`를 받아 사용하는 역할만 담당하고, `DaoFactory`는 객체 생성과 의존관계 설정을 담당하도록 구성했다.

`AccountDAO`, `MessageDAO`를 추가해 여러 DAO가 같은 `ConnectionMaker` 생성 구조를 사용할 때   
조립 코드를 팩토리 한곳에서 관리할 수 있음을 확인했다.

이후 `DaoFactory`에 `@Configuration`, 객체 반환 메서드에 `@Bean`을 선언하고,   
`AnnotationConfigApplicationContext`를 통해 빈을 조회했다.

일반 `DaoFactory`를 직접 호출하면 호출할 때마다 새로운 `UserDAO`가 생성되지만,   
Spring 컨테이너에서 같은 빈을 조회하면 동일한 객체가 반환되는 것도 비교했다.

> 제어의 역전 구현

`CoffeeMaker`가 필요한 객체를 내부에서 직접 생성하지 않고 `Bean`과 `MilkFrother`를 생성자로 주입받도록 구성했다.

구체 클래스가 아니라 인터페이스에 의존하도록 설계해 외부에서 구현체를 선택하고 전달할 수 있도록 했다.

`Button`에는 여러 `ClickListener`를 등록해 버튼 자체는 실행할 동작을 알지 못하고, 실제 동작은 외부 객체가 결정하도록 구현했다.

이를 통해 객체 생성과 관계 설정의 제어권이 객체 내부가 아니라 외부 조립 코드로 이동하는 제어의 역전 흐름을 확인했다.

> 싱글톤 구현

생성자를 `private`으로 제한하고 클래스 내부에 하나의 인스턴스를 보관한 뒤 `getInstance()`로 반환하는 싱글톤 구조를 구현했다.

eager 초기화는 클래스가 로딩될 때 인스턴스를 생성하고, lazy 초기화는 처음 요청되는 시점에 생성한다.

lazy 초기화에서는 여러 스레드가 동시에 인스턴스를 생성하지 않도록 `synchronized`를 적용했다.

`reset()`과 `peek()`을 추가해 하나의 싱글톤 객체가 가진 필드 상태가 모든 참조에서 공유된다는 점도 확인했다.

> 싱글톤 상태 공유 문제 구현

하나의 싱글톤 객체를 여러 스레드가 동시에 사용할 때 요청별 데이터를 필드에 저장하면 값이 섞일 수 있는 상황을 구현했다.

`GreetingServiceBad`는 요청받은 이름을 인스턴스 필드에 저장해 다른 스레드의 값이 반환될 수 있었다.

반면 `GreetingServiceGood`은 요청값을 매개변수와 지역변수로만 사용해 여러 스레드가 동시에 호출해도 데이터가 섞이지 않도록 했다.

`new Thread()`로 실행 작업을 만들고 `start()`로 실제 스레드를 실행했으며, 모든 작업이 끝난 뒤 결과를 확인하기 위해 `join()`을 사용했다.

충돌 횟수를 세는 `bad++`, `good++`도 여러 스레드가 동시에 수행하면 증가값이 누락될 수 있어 `synchronized`로 보호했다.

> SQL JOIN 문제 풀이

중고거래 게시글과 댓글은 `BOARD_ID`를 기준으로 `JOIN`했다.

특정 월을 조회할 때는 `YEAR()`와 `MONTH()`로 분리하기보다 시작일 이상, 다음 달 시작일 미만의 범위 조건을 사용했다.

```sql
CREATED_DATE >= '2022-10-01'
AND CREATED_DATE < '2022-11-01'
```

주소가 특정 문자열로 시작하는 조건은 `LIKE '강원도%'`로 작성했다.

식당 정보와 리뷰는 `REST_ID`를 기준으로 연결하고, 식당별 여러 리뷰를 하나로 묶기 위해 `GROUP BY I.REST_ID`를 사용했다.

평균 리뷰 점수는 `AVG(R.REVIEW_SCORE)`로 계산하고 `ROUND(..., 2)`로 소수점 둘째 자리까지 반올림했다.

## 헷갈렸던 점

`DaoFactory`와 Spring 컨테이너가 같은 역할을 한다고 생각하기 쉬웠다.

`DaoFactory`는 어떤 객체를 만들고 연결할지를 정의하는 설정이고, Spring 컨테이너는 그 설정을 읽어 실제 빈을 생성하고 관리한다.

일반 팩토리에서 반환되는 객체와 Spring 빈의 차이도 헷갈렸다.  
일반 메서드는 호출할 때마다 새로운 객체를 만들지만, Spring 빈은 기본적으로 컨테이너 안에서 하나의 객체가 재사용된다.

싱글톤 객체의 모든 필드가 위험한 것은 아니었다.  
사용자 이름이나 userId처럼 요청마다 달라지는 상태는 필드에 두면 안 되지만, 모든 요청이 함께 사용해도 되는 의존 객체 참조는 필드에 둘 수 있다.

`new Thread()`만 호출하면 스레드가 실행된다고 생각하기 쉬웠지만, 실제 실행은 `start()`를 호출해야 시작된다.  
`join()`은 대상 스레드들이 끝날 때까지 현재 스레드가 기다리도록 하는 메서드다.

`if (!s.equals(name))`은 요청한 이름과 반환된 이름이 다를 때 값이 섞였다고 판단하는 조건이었다.

`GROUP BY`에는 평균 대상인 리뷰 점수나 계산 결과인 `SCORE`를 넣는 것이 아니라, 어떤 단위로 결과를 묶을지에 해당하는 식당 ID를 사용해야 했다.

특정 월을 조회할 때 `YEAR()`와 `MONTH()`도 사용할 수 있지만,   
인덱스 활용과 날짜 범위 표현을 고려하면 시작일 이상, 다음 달 시작일 미만 조건이 더 적절했다.

## 오늘 느낀 점

Spring은 단순히 객체를 생성해주는 도구가 아니라 객체 생성, 관계 설정, 생명주기 관리의 제어권을 가져가는 컨테이너라는 점을 이해했다.

직접 작성한 `DaoFactory`에서 Spring IoC 컨테이너로 넘어가는 흐름을 따라가니 의존성 주입과 제어의 역전이 왜 필요한지 더 명확해졌다.

싱글톤은 객체를 하나만 만드는 것보다 여러 요청이 같은 객체를 공유해도 안전하도록 무상태로 설계하는 것이 더 중요하다고 느꼈다.

SQL 문제에서는 테이블을 연결하는 것뿐 아니라 조회 범위, 그룹 기준, 집계 대상이 각각 무엇인지 구분하는 것이 중요했다.
