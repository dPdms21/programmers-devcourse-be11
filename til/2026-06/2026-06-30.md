## 오늘 배운 내용

오늘은 여러 DAO 작업을 하나의 작업 단위로 처리하기 위해 Spring 트랜잭션을 적용하고,  
비즈니스 로직과 트랜잭션 처리 로직을 분리하는 방법을 학습했다.

`PlatformTransactionManager`로 트랜잭션을 시작한 뒤 모든 작업이 성공하면 커밋하고,  
중간에 예외가 발생하면 전체 작업을 롤백하도록 구성했다.

하나의 트랜잭션에 참여하는 DAO 메서드는 같은 커넥션을 사용해야 한다.  
따라서 `DataSourceUtils.getConnection()`으로 커넥션을 가져오고,  
직접 닫지 않고 `DataSourceUtils.releaseConnection()`을 통해 반환해야 한다.

메일 발송 기능은 `MailSender` 인터페이스로 추상화해 실제 구현체 대신 테스트용 구현체를 주입할 수 있도록 했다.

과제에서는 알림 발송 기능을 `NotificationSender` 인터페이스로 추상화하고, 로깅·재시도·시간 측정 등의 부가 기능을 데코레이터로 분리했다.  
이를 통해 기존 구현체를 수정하지 않고 객체를 감싸는 방식으로 기능을 추가할 수 있었다.

---

PBL에서는 `List`를 이용한 메모리 기반 회원 저장소와 `Map` 및 파일 입출력을 이용한 출석 관리 기능을 구현했다.   
자동 증가 ID, 중복 검증, 방어적 복사로 내부 상태를 관리하고, 파일 데이터를 읽을 때는 전체 검증이 끝난 뒤 메모리 상태를 교체하도록 구성했다.

## 실습 및 과제

> 트랜잭션 적용

사용자 등급 변경 과정에서 발생하는 여러 DAO 작업을 하나의 트랜잭션으로 묶었다.

`PlatformTransactionManager`를 사용해 트랜잭션을 시작하고, 모든 사용자 처리가 정상적으로 완료되면 커밋했다.   
처리 중 예외가 발생하면 롤백해 앞에서 수행한 변경까지 모두 취소되도록 구성했다.

트랜잭션 안에서 실행되는 DAO 작업은 같은 커넥션을 공유해야 하므로 `DataSourceUtils.getConnection()`을 사용했다.   
커넥션도 DAO 메서드에서 직접 닫지 않고 `releaseConnection()`으로 반환해 Spring이 현재 트랜잭션 상태에 맞게 관리하도록 했다.

> 서비스 추상화와 트랜잭션 분리

`UserServiceImpl`은 사용자 등급 변경과 같은 비즈니스 로직만 담당하고, `UserServiceTx`는 트랜잭션 시작·커밋·롤백을 담당하도록 분리했다.

`UserServiceTx`는 실제 처리 객체인 `UserServiceImpl`에 작업을 위임한다.   
이를 통해 기존 비즈니스 로직을 수정하지 않고 트랜잭션이라는 부가 기능을 추가할 수 있었으며,   
객체를 감싸 기능을 확장한다는 점에서 데코레이터 패턴과 연결됐다.

메일 발송 기능도 `MailSender` 인터페이스로 추상화했다.   
`UserServiceImpl`이 실제 메일 구현체를 직접 생성하지 않고   
인터페이스에 의존하도록 구성해 `DummyMailSender`나 `MockMailSender`를 주입할 수 있었다.

이를 통해 외부 메일 서버에 실제로 연결하지 않고도 메일 발송 요청이 발생했는지 테스트할 수 있었다.

> 추상화와 데코레이터 과제

`NotificationService`가 `EmailNotificationSender`, `SmsNotificationSender`, `KakaoNotificationSender` 같은 구체 구현체가 아니라   
`NotificationSender` 인터페이스에 의존하도록 구성했다.

생성자로 주입하는 구현체만 바꾸면 `NotificationService`를 수정하지 않고도 알림 발송 채널을 변경할 수 있었다.

로깅, 재시도, 시간 측정 기능은 실제 발송 구현체에 직접 추가하지 않고 각각 별도의 데코레이터로 분리했다.   
데코레이터 내부의 `delegate`도 구체 클래스가 아닌 `NotificationSender` 타입으로 선언해   
실제 발송 구현체뿐 아니라 다른 데코레이터까지 연속해서 감쌀 수 있도록 했다.

재시도 데코레이터는 내부 발송 중 예외가 발생하면 최대 3번까지 다시 호출했다.   
성공하면 즉시 종료하고, 모든 시도가 실패하면 마지막 예외를 다시 던지도록 구현했다.   
테스트에는 처음 두 번 실패하고 세 번째 호출에서 성공하는 `FlakyEmailSender`를 사용했다.

시간 측정에는 구간 측정에 적합한 `System.nanoTime()`을 사용했다.

```java
long elapsedTime = (end - start) / 1_000_000;
```

먼저 `end - start`로 경과 시간을 계산한 뒤 나노초를 밀리초로 변환했다.   
실행 시간이 1ms보다 짧으면 `long` 변환 결과가 `0ms`로 출력될 수 있다는 점도 확인했다.

데코레이터는 조립 순서에 따라 실행 흐름이 달라졌다.

* `Logging(Retry(...))` → 전체 재시도 흐름을 한 번 로깅
* `Retry(Logging(...))` → 재시도할 때마다 로깅을 반복

금칙어 차단 데코레이터는 메시지에 특정 단어가 포함되면 내부 `delegate.send()`를 호출하지 않고 실행을 종료했다.   
이를 통해 데코레이터가 항상 내부 객체에 위임하는 것은 아니며, 조건에 따라 실행 흐름을 차단할 수도 있음을 확인했다.

발송 속도 제한 데코레이터는 마지막 발송 시각을 저장하고,   
다음 호출이 1초 안에 들어오면 남은 시간만큼 `Thread.sleep()`으로 대기한 뒤 발송했다.   
첫 번째 호출은 즉시 실행되고 두 번째 연속 호출부터 제한이 적용됐다.

`InterruptedException`을 처리할 때는 다음과 같이 현재 스레드의 인터럽트 상태를 다시 복구했다.

```java
Thread.currentThread().interrupt();
```

Spring DI를 이용해 데코레이터 조립 책임을 컨테이너에 맡기는 방법도 검토했지만,   
이번 과제에서는 여러 조합의 순서에 따른 차이를 직접 비교하는 것이 핵심이므로 `Main`에서 명시적으로 조립했다.

> Git과 GitHub 특강

Git과 GitHub의 기본 사용법뿐 아니라 브랜치 전략, Pull Request, 코드 리뷰, 자동화 도구를 활용한 협업 흐름을 학습했다.

Git hooks는 커밋이나 push 같은 Git 동작 전후에 스크립트를 실행해 코드 검사나 테스트를 자동화하는 기능이다.   
다만 로컬 설정이므로 저장소를 clone한 팀원에게 자동으로 공유되지 않아 별도의 설정 방법이 필요하다.

GitHub Actions는 원격 저장소에서 push나 Pull Request 같은 이벤트가 발생했을 때 빌드, 테스트, 배포 작업을 자동으로 실행한다.   
로컬 환경에 의존하는 Git hooks와 달리 저장소의 workflow 파일을 통해 팀 전체에 동일한 자동화 과정을 적용할 수 있다.

CodeRabbit은 Pull Request의 변경 코드를 분석해 리뷰 의견을 제공하는 AI 코드 리뷰 도구다.   
사람이 모든 변경 사항을 직접 확인하기 전에 잠재적인 오류나 개선 지점을 빠르게 확인하는 보조 수단으로 활용할 수 있다.

Harness는 빌드와 배포 과정을 관리하고 자동화하는 CI/CD 플랫폼으로,   
코드 변경 이후 테스트와 배포가 이어지는 전체 파이프라인을 구성할 수 있다는 점이 인상 깊었다.

이번 특강을 통해 Git과 GitHub는 단순히 코드를 저장하는 도구가 아니라, 코드 리뷰와 테스트, 배포까지 연결하는 협업의 중심이라는 점을 확인했다.

> PBL Mission 02

메모리 기반 회원 저장소를 구현하며 `List`와 상태값을 관리하는 방법을 학습했다.

회원 등록 시 이름과 이메일을 검증하고, 기존 회원 목록을 순회해 중복 이메일이 있으면 예외를 발생시켰다.   
회원 ID는 `nextId`를 이용해 자동으로 증가시켰으며, 회원을 삭제하더라도 이전 ID를 다시 사용하지 않도록 했다.

`findById()`는 목록을 순회해 ID가 일치하는 회원을 반환하고, 회원이 존재하지 않으면 예외를 발생시켰다.   
삭제는 조건에 맞는 회원을 제거한 뒤 실제 삭제 여부를 확인하는 방식으로 처리했다.

전체 회원 목록을 반환할 때 내부 `List`를 그대로 반환하면 외부에서 저장소의 내용을 직접 수정할 수 있다.   
따라서 새로운 `ArrayList`에 데이터를 복사해 반환하는 방어적 복사를 적용했다.

회원 수는 현재 목록의 크기로 확인했다.    
회원 삭제 후 목록의 크기는 감소하지만, 다음 회원에게 부여할 `nextId`는 감소하지 않는다는 점도 구분했다.

> PBL Mission 03

파일 입출력을 이용해 출석 데이터를 저장하고 불러오는 기능을 구현했다.

출석 정보는 날짜와 이메일을 결합한 값을 key로 사용하고, 출석 여부를 `Boolean` 값으로 저장했다.   
같은 날짜와 이메일로 다시 `put()`하면 기존 값이 덮어써지며, 출석 기록이 없을 때는 `getOrDefault(..., false)`로 `false`를 반환했다.

`save()`에서는 `Map.Entry`를 이용해 key와 value를 한 쌍씩 꺼내 `날짜,이메일,출석여부` 형식의 문자열로 변환했다.   
`Files.createDirectories()`로 상위 디렉터리를 생성하고, `Files.write()`로 현재 메모리의 출석 데이터를 파일에 저장했다.

파일 관련 메서드에서 발생하는 `IOException`은 `try-catch`로 처리한 뒤 `UncheckedIOException`으로 전환했다.

`load()`에서는 `Files.readAllLines()`로 파일의 모든 줄을 읽고, `split(",", -1)`을 사용해 각 줄을 세 개의 컬럼으로 분리했다.

컬럼 수, 날짜 형식, 빈 이메일, `true` 또는 `false`가 아닌 출석값을 검증하고,    
잘못된 줄이 하나라도 있으면 `IllegalArgumentException`을 발생시켰다.   
검증된 출석값은 `Boolean.parseBoolean()`으로 실제 `boolean` 값으로 변환했다.

파일이 존재하지 않을 때는 예외를 발생시키지 않고 기존 출석 데이터를 비운 뒤 종료했다.

로딩 중 형식 오류가 발생했을 때 기존 메모리 데이터가 일부만 변경되는 것을 막기 위해 임시 `Map`에 전체 데이터를 먼저 저장했다.   
모든 줄의 검증이 끝난 뒤 `attendances.clear()`와 `putAll()`을 실행해 최종 데이터를 교체했다.

## 헷갈렸던 점

트랜잭션에 참여하는 커넥션을 일반 JDBC 코드처럼 `try-with-resources`로 직접 닫으면 안 되는 이유를 정리했다.

트랜잭션이 진행 중인 커넥션은 Spring이 트랜잭션 종료 시점까지 관리해야 한다.   
DAO 메서드에서 직접 닫으면 이후 작업이 같은 커넥션을 사용할 수 없으므로 `DataSourceUtils.releaseConnection()`을 통해 반환해야 한다.

데코레이터는 같은 객체를 사용하더라도 감싸는 순서에 따라 로깅 횟수와 예외 처리 범위가 달라진다는 점을 확인했다.

---

회원 목록을 반환할 때 내부 `List`를 그대로 반환하면 외부 코드가 저장소의 상태를 직접 변경할 수 있다는 점을 확인했다.   
저장소의 내부 상태를 보호하려면 새로운 `ArrayList`로 복사해 반환해야 한다.

회원 삭제 후 회원 수는 감소하지만, 자동 증가 ID인 `nextId`는 감소하거나 이전 값으로 돌아가면 안 된다.   
목록의 현재 크기와 다음에 부여할 ID는 서로 다른 상태값으로 관리해야 한다.

출석 파일을 읽으면서 기존 `Map`을 바로 수정하면 중간에 잘못된 줄이 발견됐을 때 일부 데이터만 반영될 수 있다.   
따라서 임시 `Map`에 모든 줄을 저장하고 검증이 끝난 뒤 기존 데이터를 교체해야 한다.

`split(",", -1)`의 두 번째 인수 `-1`은 문자열 끝의 빈 컬럼도 결과 배열에 유지한다.   
이를 통해 이메일이나 출석값이 비어 있는 잘못된 데이터도 누락하지 않고 검증할 수 있었다.

`IOException`은 checked exception이므로 직접 처리하거나 선언해야 한다.   
이번 구현에서는 파일 처리 실패를 호출자에게 전달하기 위해 `UncheckedIOException`으로 전환했다.

## 오늘 느낀 점

트랜잭션은 단순히 커밋과 롤백 코드를 추가하는 것이 아니라, 여러 작업이 같은 커넥션과 하나의 작업 경계를 공유하도록 만드는 것이 중요했다.

비즈니스 로직과 트랜잭션 로직을 분리하면서 기존 기능을 직접 수정하지 않고도 부가 기능을 덧붙일 수 있다는 점을 이해했다.

데코레이터 패턴은 상속 없이 객체 조합으로 기능을 확장할 수 있지만,   
조립 순서가 실제 동작에 영향을 주므로 각 데코레이터가 어느 범위를 감싸는지 확인해야 한다고 느꼈다.

Git hooks, GitHub Actions, CodeRabbit, Harness처럼 개발 과정의 검사와 리뷰, 배포를 자동화하는 도구를 함께 사용하면   
반복 작업을 줄이고 협업 품질을 높일 수 있다는 점이 인상 깊었다.

처음 사용하는 파일 입출력 API를 모두 외우기보다 요구사항을 등록, 조회, 검증, 변환, 저장 단계로 나누고    
IDE의 오류 메시지와 메서드 선언을 확인하면서 구현하는 것이 더 중요하다고 느꼈다.

## 추가 학습 예정

* Spring 트랜잭션 동기화와 커넥션 공유 과정 복습
* `DataSourceUtils`와 일반 JDBC 커넥션 반환 방식 비교
* 데코레이터 조립 순서에 따른 실행 흐름 복습
