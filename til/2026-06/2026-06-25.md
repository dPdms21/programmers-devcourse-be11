## 오늘 배운 내용

오늘은 코딩 테스트 특강 문제를 풀며 배열과 문자열 순회, 연속 중복 제거, Stack과 Deque, 시뮬레이션 문제의 상태 관리 방식을 복습했다.

Stack이 필요한 문제에서는 `Stack` 클래스보다 `Deque`와 `ArrayDeque`를 사용해 `push()`, `pop()`, `peek()`로 LIFO 구조를 구현했다.

시뮬레이션 문제에서는 실제 상태를 바로 변경하지 않고 임시 상태에서 조건을 확인한 뒤,   
모든 조건을 통과했을 때만 실제 값을 갱신하는 방식이 중요했다.

예전에 풀었던 문제들이 다시 나와 문제 유형은 익숙했지만, 기존에 사용했던 풀이 방식이 바로 떠오르지 않아 다른 방식으로 해결한 문제도 있었다.

---

추가로 기능개발을 완료일 계산과 Queue 방식으로 다시 풀고, Map을 활용하는 폰켓몬, 완주하지 못한 선수, 의상 문제를 복습했다.

Map은 값의 등장 횟수나 종류별 개수를 `key-value` 형태로 관리할 때 사용할 수 있다.  
`getOrDefault()`로 기존 개수를 가져와 누적하고, 문제 조건에 따라 `size()`, 남은 개수, 종류별 경우의 수를 계산했다.

## 실습 및 과제

> 배열과 문자열 순회

배열의 유사도에서는 두 배열의 모든 문자열을 비교하며 같은 원소의 개수를 셌다.

행렬의 덧셈은 이중 반복문을 사용해 같은 행과 열 위치의 값을 더했다.  
바깥 반복문은 행, 안쪽 반복문은 열을 순회했다.

그림 확대에서는 한 문자를 `k`번 이어 붙여 가로로 확대한 뒤, 완성된 한 행을 결과 배열에 `k`번 저장해 세로로 확대했다.

`StringBuilder`를 전체 반복문 밖에 두면 이전 행의 문자열이 계속 누적되므로 각 행을 처리할 때마다 새로 생성해야 했다.

> 연속 중복과 문자 개수 처리

같은 숫자는 싫어는 전체 중복이 아니라 연속된 중복만 제거하는 문제였다.

첫 번째 값을 저장한 뒤 현재 값과 바로 이전 값을 비교해 값이 다를 때만 결과에 추가했다.  
`Set`이나 `contains()`를 사용하면 떨어져 있는 같은 숫자까지 제거되므로 문제 조건과 맞지 않았다.

문자 개수 세기에서는 대문자는 `c - 'A'`, 소문자는 `c - 'a' + 26`으로 배열 인덱스를 계산했다.

문자열 내 p와 y의 개수는 문자열을 한 번 순회하며 각각의 개수를 세고 두 값이 같은지 반환했다.

> Stack과 Deque 활용

올바른 괄호에서는 여는 괄호를 Stack에 넣고 닫는 괄호가 나오면 기존 여는 괄호를 제거하는 방식으로 검사했다.

짝지어 제거하기에서는 현재 문자와 Stack의 맨 위 문자가 같으면 제거하고, 다르면 현재 문자를 추가했다.

Java에서는 다음과 같이 `Deque`를 Stack처럼 사용할 수 있다.

```java
Deque<Character> stack = new ArrayDeque<>();
```

`push()`, `pop()`, `peek()`를 사용하면 LIFO 구조로 동작하고, 일반 Queue로 사용할 때는 `offer()`, `poll()`, `peek()`를 사용한다.

> 공원 산책 시뮬레이션

공원 산책에서는 이동 명령을 받을 때 현재 좌표를 바로 변경하지 않고 임시 좌표에서 한 칸씩 이동했다.

각 이동마다 배열 범위와 장애물 여부를 확인하고, 이동 중 하나라도 실패하면 해당 명령 전체를 취소했다.

모든 이동이 유효할 때만 실제 좌표를 갱신했다.

배열에 접근하기 전에 범위를 먼저 검사해야 하며, 결과 좌표는 다음처럼 반환했다.

```java
return new int[]{h, w};
```

> 기능개발 시뮬레이션

기능개발에서는 아직 배포하지 않은 첫 작업의 위치를 인덱스로 관리했다.

첫 작업이 완료될 때까지 모든 미완료 작업의 진행도를 증가시키고, 첫 작업부터 연속으로 완료된 작업 수를 하나의 배포 단위로 저장했다.

중간에 완료되지 않은 작업을 만나면 그 뒤 작업이 완료됐더라도 함께 배포할 수 없으므로 반복을 종료했다.

현재 풀이는 매일 진행도를 갱신하는 시뮬레이션 방식이며, 각 작업의 남은 날짜를 먼저 계산해 배포 단위로 묶는 방식도 있다는 점을 확인했다.

---

> 기능개발 Queue 풀이

각 기능이 완료되는 데 필요한 일수를 먼저 계산한 뒤, 완료일을 `Deque`에 순서대로 저장했다.

가장 앞 기능의 완료일을 기준으로 뒤 기능의 완료일이 작거나 같으면 같은 배포 묶음으로 계산하고,   
더 큰 완료일을 만나면 새로운 배포를 시작했다.

Deque를 Queue로 사용할 때는 `offer()`, `poll()`, `peek()`를 사용했다.  
배열로도 같은 로직을 구현할 수 있고 이 문제에서는 배열 방식이 더 간결했지만, Deque 풀이를 통해 Queue의 동작을 복습했다.

> LMS w2 - 03

폰켓몬에서는 종류별 개수를 Map에 저장하고, 선택 가능한 수인 `nums.length / 2`와 실제 종류 수인 `map.size()` 중 작은 값을 반환했다.

완주하지 못한 선수에서는 참가자 이름별 인원수를 저장한 뒤 완주자 이름의 개수를 하나씩 감소시켰다.  
동명이인이 존재하므로 중복을 제거하는 Set이 아니라 이름별 인원수를 관리할 수 있는 Map이 필요했다.

의상에서는 의상 종류별 개수를 Map에 저장했다.  
각 종류에서 하나를 선택하거나 선택하지 않는 경우를 포함해 `(종류별 개수 + 1)`을 모두 곱하고,   
아무것도 입지 않는 경우를 제외하기 위해 마지막에 `1`을 뺐다.

등장 횟수는 다음과 같이 `getOrDefault()`를 사용해 누적했다.

```java
map.put(key, map.getOrDefault(key, 0) + 1);
```

Map의 key와 value가 모두 필요할 때는 `entrySet()`, key만 필요할 때는 `keySet()`, value만 필요할 때는 `values()`를 사용했다.

## 헷갈렸던 점

그림 확대에서 하나의 `StringBuilder`를 계속 사용하면 이전 행의 내용까지 누적됐다.  
행마다 새로운 문자열을 만들어야 각 결과가 독립적으로 저장됐다.

같은 숫자는 싫어 문제에서 중복 제거라는 표현만 보고 `Set`을 생각하기 쉬웠지만, 실제 조건은 연속된 숫자만 제거하는 것이었다.

Deque는 양쪽 삽입과 삭제가 가능한 자료구조이지만,   
Stack으로 사용할 때는 `push()`, `pop()`, `peek()`만 사용하면 된다는 점을 다시 정리했다.

공원 산책에서는 좌표를 먼저 변경한 뒤 되돌리는 방식보다 임시 좌표에서 전체 이동을 검증한 뒤 반영하는 방식이 더 안전했다.

기능개발에서는 이미 선언한 인덱스 변수 `i`를 같은 메서드 범위에서 다시 반복 변수로 선언할 수 없어 다른 변수명을 사용해야 했다.

이전에 풀었던 문제들이었지만 당시 사용했던 풀이 방식이 바로 떠오르지 않았다.  
문제 유형은 기억났지만 구현 흐름은 다시 정리해야 했고, 일부 문제는 이전과 다른 시뮬레이션 방식으로 해결했다.

---

폰켓몬은 종류 수만 필요하므로 Set으로도 풀 수 있지만, 이번에는 Map의 개수 누적 방식을 복습하기 위해 Map으로 구현했다.

의상에서는 각 종류에서 반드시 하나를 선택하는 것이 아니라 선택하지 않는 경우도 있으므로 종류별 개수에 `1`을 더해야 했다.  
다만 모든 종류를 선택하지 않는 경우는 허용되지 않으므로 최종 결과에서 `1`을 빼야 했다.

## 오늘 느낀 점

이미 풀어본 문제라도 풀이를 외우는 것이 아니라 핵심 조건과 상태 변화를 이해해야 다시 만났을 때 스스로 구현할 수 있다는 점을 느꼈다.

배열과 문자열 문제는 반복문 자체보다 비교 대상과 인덱스 범위를 정확히 관리하는 것이 중요했다.

Stack과 시뮬레이션 문제에서는 현재 상태, 임시 상태, 실제 반영 시점을 구분해야 구현 오류를 줄일 수 있었다.

기존 풀이 방식이 기억나지 않더라도 문제 조건을 다시 분석해 다른 방식으로 정답을 만들 수 있었고,   
이후에는 여러 풀이를 비교해 더 효율적인 방식을 익힐 필요가 있다고 느꼈다.
