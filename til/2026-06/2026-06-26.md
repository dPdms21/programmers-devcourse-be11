## 오늘 배운 내용

오늘은 제1회 알고리즘 코딩테스트에 응시한 뒤,   
JDBC 코드에 전략 패턴을 적용하고 전략의 구현 방식을 별도 클래스에서 로컬 클래스와 익명 클래스로 변경하는 과정을 학습했다.   
이후 LMS w2 - 04 Set(집합) 강의를 듣고 관련 문제를 풀었다.

전략 패턴에서는 데이터베이스 연결, `PreparedStatement` 실행, 자원 반환처럼 반복되는 흐름을 컨텍스트에 모으고,   
INSERT와 DELETE처럼 작업마다 달라지는 부분은 `StatementStrategy`에 위임한다.   
컨텍스트가 구체 전략 클래스가 아닌 인터페이스에 의존하므로 새로운 전략을 추가해도 기존 실행 흐름을 수정하지 않아도 된다.

전략은 사용 범위에 따라 구현 형태를 선택할 수 있다.

* 여러 곳에서 재사용하는 전략 → 별도 클래스
* 특정 메서드 안에서만 사용하는 전략 → 로컬 클래스
* 한 번만 사용하고 이름이 필요하지 않은 전략 → 익명 클래스
* 추상 메서드가 하나인 함수형 인터페이스 → 람다

또한 조회 결과를 찾은 즉시 `return`하면 이후의 연결 종료 코드가 실행되지 않을 수 있으므로,   
자원 반환은 `finally`에서 처리해야 한다는 점을 확인했다.

## 실습 및 과제

> 제1회 알고리즘 코딩테스트

제1회 알고리즘 코딩테스트에 응시해 주어진 문제를 풀이했다.   
문제 내용은 외부 유출이 불가능하므로 풀이 과정과 코드는 별도로 기록하지 않았다.

오늘 문제들은 모두 처음 접하는 유형이라 풀이 방향을 잡는 데 시간이 걸렸다.   
해결했다고 생각한 뒤에도 일부 테스트를 통과하지 못해 조건과 예외 상황을 다시 확인해야 했다.   
이를 통해 구현 전에 문제의 조건을 정확히 정리하고, 다양한 입력 사례를 직접 검증하는 과정이 중요하다는 점을 느꼈다.

> 전략 패턴과 로컬·익명 클래스 실습

공통 JDBC 실행 흐름을 `jdbcContextWithStatementStrategy()`에 모으고,   
SQL을 생성하는 부분은 `StatementStrategy` 구현 객체가 담당하도록 분리했다.

이전 실습에서는 `UserDAOAdd`, `UserDAODeleteAll`처럼 전략마다 별도 구현 클래스를 만들었다.   
이번에는 한 메서드에서만 사용하는 전략을 로컬 클래스나 익명 클래스로 구현해 전략 패턴의 구조는 유지하면서 불필요한 클래스와 파일을 줄였다.

> 전략 패턴 과제

데이터베이스 연결 열기, 전략 실행, 연결 닫기 순서를 컨텍스트가 담당하고,   
사용자 추가와 전체 삭제처럼 달라지는 작업은 전략 객체가 담당하도록 구현했다.

별도 클래스 전략은 실행에 필요한 `User`를 생성자로 전달받아 필드에 저장했다.   
반면 익명 클래스와 람다는 메서드 내부의 지역 변수 `user`를 캡처할 수 있어 별도의 생성자와 필드 없이 구현할 수 있었다.

`StatementStrategy`는 추상 메서드가 하나인 함수형 인터페이스이므로 익명 클래스 구현을 람다로 줄일 수 있었다.

추가로 `get(String id)` 조회 기능을 구현하고, 조회 성공이나 예외 발생 여부와 관계없이 연결이 닫히도록 `try-finally`를 적용했다.

기존 `UserDao` 내부의 공통 실행 로직은 `JdbcContext`로 분리했다.   
`UserDao`는 사용할 전략을 결정하고, `JdbcContext`는 연결 열기 → 전략 실행 → 연결 닫기 순서를 담당하도록 역할을 나눴다.

> LMS w2 - 04

같은 숫자는 싫어 문제에서는 전체 중복이 아니라 연속된 중복만 제거해야 하므로,   
현재 값과 바로 이전 값을 비교해 값이 다를 때만 결과에 추가했다.   
`Set`을 사용하면 떨어져 있는 같은 숫자까지 제거되므로 문제 조건과 맞지 않았다.

추가로 `Set`의 구현체와 활용 방법을 정리했다.   
빠른 추가와 탐색에는 `HashSet`, 삽입 순서 유지에는 `LinkedHashSet`, 정렬된 상태 유지에는 `TreeSet`을 사용한다.   
합집합은 `addAll()`, 차집합은 `removeAll()`, 교집합은 `retainAll()`로 구현하며, 원본을 유지해야 할 때는 복사본에서 연산해야 한다.

## 헷갈렸던 점

핵심 차이는 전략 패턴을 새로 적용한 것이 아니라, 이미 분리된 전략을 어떤 형태로 구현하는지에 있었다.   
재사용 여부와 사용 범위를 기준으로 별도 클래스, 로컬 클래스, 익명 클래스, 람다 중 적절한 방식을 선택해야 한다.

또한 조회 메서드에서 사용자를 찾은 즉시 `return`하면 메서드 아래에 작성한 `db.close()`가 실행되지 않는다는 점을 확인했다.   
자원 반환이 반드시 실행되어야 하는 경우에는 정상 반환과 예외 발생을 모두 고려해 `finally`에 작성해야 한다.

같은 숫자는 싫어 문제에서 중복 제거라는 표현만 보고 `Set`을 사용할 수 있다고 생각하기 쉽지만,   
이 문제는 전체 중복이 아니라 연속된 중복만 제거해야 한다.   
따라서 `Set`이 아니라 이전 값과 현재 값을 비교하는 방식이 적절하다.

## 오늘 느낀 점

코딩테스트에서는 풀이를 구현하는 것만으로 끝내지 않고,   
조건을 빠뜨리지 않았는지와 예외 입력에서도 올바르게 동작하는지를 확인해야 한다는 점을 느꼈다.

전략 패턴은 단순히 인터페이스와 구현 클래스를 분리하는 것보다,   
변하지 않는 실행 흐름과 변경되는 작업을 구분하는 것이 핵심이라는 점을 이해했다.

같은 전략이라도 재사용 범위에 따라 별도 클래스, 익명 클래스, 람다로 표현할 수 있었으며,   
코드가 짧다는 이유만으로 람다를 선택하기보다 역할과 재사용 가능성을 함께 고려해야 한다.
