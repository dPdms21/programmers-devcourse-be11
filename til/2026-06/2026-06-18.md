## 오늘 배운 내용

오늘은 Java 파일 입출력과 스트림을 실습하고, wait/notify, 기아 현상, 파일 기반 가계부와 회원 관리 과제를 구현했다.

`Path`는 파일이나 폴더 경로를 객체로 표현하고, `Files`는 경로 존재 여부 확인과 폴더 생성 같은 작업에 사용한다.  
`Path.of()`로 경로를 만들고, `resolve()`로 기준 경로 뒤에 파일명을 연결할 수 있다.

바이트 스트림은 `FileInputStream`, `FileOutputStream`을 사용해 텍스트와 이미지 같은 바이너리 데이터를 처리한다.  
문자 스트림은 `FileReader`, `FileWriter`를 사용하며, `BufferedReader`로 감싸면 `readLine()`을 이용해 한 줄씩 읽을 수 있다.

`wait()`는 현재 스레드를 대기 상태로 전환하면서 객체의 락을 반납하고,   
`notify()`와 `notifyAll()`은 같은 객체에서 대기 중인 스레드를 깨운다.  
파일 입출력에서는 이어쓰기와 덮어쓰기, 임시 파일을 이용한 수정, 저장 형식과 객체 복원이 중요했다.

## 실습 및 과제

> Java 파일 입출력 실습

파일과 폴더 경로를 `Path`로 표현하고,   
`Files.notExists()`와 `Files.createDirectories()`를 사용해 존재 여부 확인과 폴더 생성을 실습했다.

바이트 스트림에서는 문자열을 `getBytes()`로 `byte[]`로 변환해 파일에 쓰고,   
`readAllBytes()`로 읽은 데이터를 다시 문자열로 변환했다.  
QR 코드 실습에서는 문자열을 이미지로 저장하고, 이미지 파일을 다시 읽어 QR 코드 안의 내용을 추출했다.

문자 스트림에서는 `FileWriter`로 문자열을 직접 저장하고, `BufferedReader`와 `readLine()`을 사용해 파일을 한 줄씩 읽었다.  
스트림은 `try-with-resources` 안에서 선언해 작업이 끝난 뒤 자동으로 닫히도록 처리했다.

> wait/notify 구현

여러 스레드가 하나의 공유 객체를 기준으로 질문과 응답 순서를 맞추도록 구현했다.

`wait()`는 단순히 스레드를 멈추는 것이 아니라 현재 객체의 락을 반납하면서 대기한다.  
`notify()`를 호출해도 상대 스레드가 바로 실행되는 것은 아니고,   
현재 스레드가 `synchronized` 영역을 벗어나 락을 반납한 뒤 실행될 수 있다.

`wait()`와 `notify()`는 같은 객체의 `synchronized` 영역 안에서 사용해야 했다.  
깨어난 뒤 조건이 여전히 만족된다는 보장이 없으므로 `if`가 아니라 `while`로 조건을 다시 검사했고,   
`wait(timeout)`으로 제한 대기도 적용했다.

> 기아 현상 구현

여러 스레드가 제한된 공유 자원을 반복해서 경쟁하는 상황을 구현했다.

`notify()`는 어떤 스레드를 깨울지 보장하지 않기 때문에 특정 스레드가 계속 자원을 얻지 못하는 기아 현상이 발생할 수 있었다.  
`notifyAll()`로 모든 대기 스레드를 깨우고,   
별도의 `Queue`에 대기 순서를 저장해 먼저 기다린 스레드가 먼저 자원을 얻도록 개선했다.

각 스레드의 자원 획득 횟수는 `Map`에 기록했으며, 정확한 통계를 확인하기 위해 모든 스레드가 종료된 뒤 결과를 출력해야 했다.

> 가계부2 구현

날짜별 가계부 내역을 `YYYY-MM-DD.txt` 파일로 저장하고 조회·삭제·검색하는 기능을 구현했다.

같은 날짜에 새 내역을 추가할 때는 기존 항목과 합계를 읽은 뒤 새 항목을 추가하고 전체 파일을 다시 덮어썼다.  
이어쓰기를 사용하면 합계 줄이 계속 누적될 수 있으므로 기존 합계는 제외하고 마지막에 갱신된 합계를 한 번만 저장했다.

특정 항목 삭제는 원본 파일의 중간 줄을 직접 지우는 대신,   
삭제할 항목만 제외해 임시 파일에 작성한 뒤 원본을 교체하는 방식으로 처리했다.

항목명 비교에서는 `contains()`가 아니라 마지막 `:` 앞부분을 잘라 `equals()`로 비교했다.  
월별 합계는 입력한 `YYYY-MM`으로 시작하는 날짜 파일들의 합계 줄을 더해 계산했다.

> 회원 관리5 구현

기존 회원 관리 프로그램에 파일 저장과 불러오기 기능을 추가했다.

`List<Member>`에 `NormalMember`와 `VipMember` 객체를 함께 저장하고,   
저장할 때는 `toFileString()`으로 한 줄의 문자열로 변환했다.  
불러올 때는 저장된 등급 값을 기준으로 실제 구현체를 직접 선택해 객체를 다시 생성했다.

회원 파일 첫 줄에는 요금제를 저장하고, 둘째 줄부터 회원 정보를 저장했다.  
`load()`에서는 첫 줄을 회원 정보로 처리하지 않고 요금제와 최대 회원 수를 복원하는 데 사용했다.

회원 데이터 구분자로 `|`를 사용했기 때문에 `split("\\|")`처럼 정규식 이스케이프가 필요했다.  
회원 추가·수정·삭제 후에는 전체 목록을 다시 저장하고, 덮어쓰기 전 기존 파일을 백업해 직전 상태를 남겼다.

## 헷갈렸던 점

생성자에서 경로를 설정했다고 실제 폴더나 파일이 바로 만들어지는 것은 아니었다.  
경로 객체만 준비된 상태이므로 폴더 생성이나 파일 쓰기·읽기 메서드를 `main()`에서 직접 호출해야 했다.

`Files.notExists()` 조건이 있으면 같은 이름의 파일이 이미 존재할 때 아무 작업도 하지 않을 수 있다는 점도 확인했다.

`wait()`와 `Thread.sleep()`의 차이가 헷갈렸다.  
`wait()`는 객체의 락을 반납하지만, `sleep()`은 락을 유지한 채 현재 스레드만 일정 시간 멈춘다.

`notifyAll()`을 사용하면 모든 스레드가 깨어나지만 실행 순서까지 공정해지는 것은 아니었다.  
정확한 순서를 보장하려면 별도의 대기 `Queue`가 필요했다.

가계부에서는 이어쓰기와 덮어쓰기 차이가 중요했다.  
`FileWriter(file, false)`는 덮어쓰기이고,   
`true`는 이어쓰기이므로 합계처럼 기존 값을 갱신해야 하는 경우에는 전체 내용을 다시 작성해야 했다.

회원 관리에서는 인터페이스 타입으로 저장된 객체의 실제 구현체가 파일에서 자동으로 복원되지 않는다는 점이 헷갈렸다.  
저장된 등급 값을 확인해 `NormalMember` 또는 `VipMember`를 직접 생성해야 했다.

또한 저장할 때 사용한 구분자와 필드 순서가 불러올 때와 정확히 같아야 하며,   
빈 줄이나 필드 개수가 맞지 않는 줄은 건너뛰어야 했다.

## 오늘 느낀 점

파일 입출력은 단순히 파일에 값을 쓰고 읽는 것보다 저장 형식과 수정 방식, 예외 상황을 먼저 설계하는 것이 중요하다고 느꼈다.

스레드 과제에서는 `wait()`, `notifyAll()`, 대기 큐처럼 실행 순서와 락 상태를 함께 고려해야 해서   
단순한 메서드 호출보다 전체 흐름을 이해하는 것이 더 중요했다.

가계부와 회원 관리에 파일 저장을 적용하면서 프로그램을 다시 실행해도 상태를 유지하려면   
객체를 문자열로 변환하고 다시 복원하는 규칙이 명확해야 한다는 점을 확인했다.
