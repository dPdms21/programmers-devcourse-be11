## 오늘 배운 내용

오늘은 의존관계 주입과 Spring 테스트를 학습하고, 템플릿 메서드 패턴과 전략 패턴의 구조 차이를 확인했다.

의존관계 주입은 객체가 필요한 구현체를 직접 생성하지 않고 외부에서 전달받는 방식이다.  
설계 시점에는 인터페이스에 의존하고, 실행 시점에 실제 구현 객체가 연결된다.

JUnit에서는 `@Test`로 테스트 메서드를 지정하고,   
`assertEquals()`로 기대값과 실제값을 비교하며, `assertThrows()`로 예상한 예외 발생 여부를 검증한다.

`@BeforeEach`는 각 테스트 실행 전에 공통 준비 작업을 수행하고,   
`@Disabled`는 학습용 실패 테스트를 실행 대상에서 제외할 때 사용한다.

`@SpringJUnitConfig(DaoFactory.class)`를 사용하면 테스트에서 Spring 컨테이너를 생성하고 설정 클래스를 등록할 수 있다.  
`@Autowired`를 통해 컨테이너가 관리하는 `UserDAO` 빈을 주입받았다.

템플릿 메서드 패턴은 공통 흐름을 추상 부모 클래스에 두고 변경되는 부분만 자식 클래스에서 구현한다.  
전략 패턴은 변경되는 로직을 인터페이스와 별도의 전략 객체로 분리해 실행 시점에 전달하거나 교체한다.

람다 과제에서는 익명 클래스와 함수형 인터페이스, `Predicate`, 메서드 참조를 실습했다.

스트림 과제에서는 `filter()`, `map()` 등 중간 연산과 `forEach()`, `collect()`, `reduce()` 등 종료 연산을 실습했다.

## 실습 및 과제

> 의존관계 주입과 Spring 테스트 실습

`UserDAO`가 구체 구현 클래스를 직접 생성하지 않고 인터페이스 타입의 객체를 외부에서 전달받도록 구성했다.

이 구조에서는 실제 구현체를 변경하더라도 `UserDAO`의 코드를 수정하지 않아도 되며, 객체 사이의 결합도를 낮출 수 있었다.

JUnit 테스트에서는 회원 추가와 조회 결과를 `assertEquals()`로 검증하고,   
존재하지 않는 사용자를 조회할 때의 예외는 `assertThrows()`로 확인했다.

각 테스트가 동일한 DB 상태에서 실행되도록 `@BeforeEach`에서 `deleteAll()`을 호출해 테스트 데이터를 초기화했다.

`@SpringJUnitConfig`와 `@Autowired`를 사용해 테스트 코드가 직접 `UserDAO`를 생성하지 않고 Spring 컨테이너에서 빈을 주입받도록 했다.

실제 Spring 컨테이너와 MySQL을 함께 사용하므로   
하나의 클래스만 독립적으로 확인하는 순수 단위 테스트보다는 통합 테스트의 성격도 가진다는 점을 확인했다.

> 템플릿 메서드와 전략 패턴 실습

템플릿 메서드 패턴에서는 공통 JDBC 실행 흐름을 추상 부모 클래스에 두고, SQL 생성 부분만 하위 클래스가 구현하도록 구성했다.

공통 코드를 재사용할 수 있지만 상속에 의존하므로 부모와 자식의 결합도가 높고, 기능별 하위 클래스가 계속 늘어날 수 있었다.

`ex_3_1`의 `UserDAO`는 추상 클래스이므로 직접 객체를 생성할 수 없었다.  
이 코드는 실행 가능한 완성 구조가 아니라 상속 방식의 한계를 보여주기 위한 중간 단계였다.

전략 패턴에서는 SQL 생성 부분을 별도의 전략 객체로 분리했다.

`UserDAO`는 공통 JDBC 실행 흐름을 담당하고, `UserDAOAdd`, `UserDAODeleteAll`은 각각 추가와 전체 삭제에 필요한 SQL을 제공했다.

템플릿 메서드 패턴이 상속을 사용한다면, 전략 패턴은 인터페이스와 객체 조합을 사용해 동작을 유연하게 교체한다는 차이가 있었다.

> 람다 구현

익명 클래스와 람다식으로 함수형 인터페이스를 구현하고, `@FunctionalInterface`를 통해 추상 메서드가 하나인지 확인했다.

`Predicate<String>`은 문자열 하나를 받아 조건을 검사한 뒤 `boolean`을 반환하며, `test()`로 결과를 확인했다.

람다식이 기존 메서드 하나만 호출하는 경우에는 `::` 메서드 참조로 더 간단하게 표현했다.

> 스트림 구현

스트림에서는 `filter()`, `map()`, `sorted()` 같은 중간 연산과   
`forEach()`, `count()`, `sum()`, `average()`, `collect()`, `reduce()` 같은 종료 연산을 사용했다.

`mapToInt()`로 객체 스트림을 정수 스트림으로 변환해 가격 합계와 평균을 계산했다.

`flatMap()`으로 여러 주문의 상품 목록을 하나의 문자열 스트림으로 펼친 뒤 `distinct()`로 중복을 제거하고 `sorted()`로 정렬했다.

`groupingBy()`를 사용해 상품을 가격대별로 묶고 `Map<String, List<Product>>` 형태로 결과를 생성했다.

`reduce()`로 여러 상품 가격을 하나의 합계 값으로 누적했다.

## 헷갈렸던 점

`DaoFactory`와 Spring 컨테이너의 역할이 헷갈렸다.

`DaoFactory`는 어떤 객체를 생성하고 어떻게 연결할지에 대한 설정을 제공하고,   
Spring 컨테이너는 해당 설정을 읽어 실제 빈을 생성하고 관리한다.

테스트에서 추가한 ID와 조회할 ID가 일치해야 하며,   
테스트 전 데이터를 초기화하지 않으면 동일한 기본키로 인해 중복 오류가 발생할 수 있었다.

`flatMap()` 이후에는 스트림 요소가 `Order`가 아니라 각 주문의 상품명인 `String`으로 변경된다.  
따라서 이후에는 `getItems()`를 다시 호출할 수 없었다.

`groupingBy()`의 결과는 `Map` 안에 `List`가 들어 있는 구조이므로 그룹 이름과 상품 목록을 각각 꺼내 출력해야 했다.

`reduce()`는 여러 요소를 하나의 값으로 만드는 종료 연산이므로 뒤에 `forEach()`를 연결할 수 없었다.  
결과를 변수에 저장하거나 바로 출력해야 했다.

## 오늘 느낀 점

테스트는 단순히 메서드 실행 결과를 확인하는 것이 아니라 매번 동일한 조건을 만들고,   
예외 상황까지 명확하게 검증하는 과정이라는 점을 이해했다.

템플릿 메서드 패턴과 전략 패턴을 비교하면서 공통 코드를 재사용하더라도   
상속과 객체 조합에 따라 확장성과 결합도가 달라진다는 점을 확인했다.

람다와 스트림은 반복문을 짧게 바꾸는 문법이 아니라 데이터 처리 과정을 조건, 변환, 정렬, 집계 단계로 나누어 표현하는 방식이라고 느꼈다.

스트림에서는 현재 요소의 타입과 중간 연산 이후의 결과 형태를 계속 확인하는 것이 중요했다.
