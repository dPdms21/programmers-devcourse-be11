## 오늘 배운 내용

오늘은 Java 객체지향 문법 중 다형성, 업캐스팅과 다운캐스팅, 추상 클래스, 인터페이스, List를 학습했다.

부모 타입 변수에 자식 객체를 담을 수 있고, 같은 메서드를 호출하더라도 실제 객체 타입에 따라 오버라이딩된 메서드가 실행된다는 점을 확인했다.  
또한 부모 타입으로는 부모 클래스에 정의된 기능만 바로 사용할 수 있고, 자식 클래스에만 있는 기능을 사용하려면 다운캐스팅이 필요하다는 점을 정리했다.

추상 클래스와 인터페이스의 차이도 학습했다.
추상 클래스는 공통 필드, 생성자, 공통 메서드를 가질 수 있어 공통 상태를 부모가 관리하기 좋고,   
인터페이스는 구현해야 할 기능의 규칙을 정하는 데 적합하다는 점을 확인했다.

## 실습 및 과제

> Java 다형성 실습

다형성과 업캐스팅, 다운캐스팅을 실습했다.

`K_animal myDog = new K_dog();`처럼 부모 타입 변수에 자식 객체를 담고,   
`sound()`를 호출했을 때 실제 객체인 `K_dog`의 오버라이딩 메서드가 실행되는 흐름을 확인했다.  
또한 실제 객체가 자식 타입일 때만 다운캐스팅할 수 있으며,   
부모 타입 변수로 자식 클래스에만 있는 메서드를 호출하려면 다운캐스팅이 필요하다는 점을 정리했다.

> 추상 클래스와 인터페이스 실습

추상 클래스와 인터페이스를 비교하며 실습했다.

추상 클래스는 직접 `new`로 객체를 만들 수 없고, 자식 클래스가 추상 메서드를 반드시 구현해야 한다는 점을 확인했다.  
인터페이스는 여러 클래스가 공통으로 지켜야 할 기능의 규칙을 정하고, 구현 클래스에서 실제 동작을 작성하는 구조로 이해했다.

> 자판기와 회원 관리 과제

자판기와 회원 관리 프로그램을 각각 추상 클래스 기반 구조와 인터페이스 기반 구조로 구현하며 차이를 비교했다.

자판기2에서는 `Drink`를 추상 클래스로 만들고, `Coke`, `Cider`, `Fanta`, `Water`가 이를 상속하도록 구현했다.  
공통 상태인 `name`, `price`, `stock`은 부모 클래스에서 관리하고, 음료마다 다른 출력 동작은 `dispense()`를 오버라이딩했다.

자판기3에서는 `Drink`를 인터페이스로 바꿔 구현했다.  
인터페이스는 인스턴스 필드와 생성자를 가질 수 없기 때문에 각 음료 클래스가 직접 상태를 가져야 했고,   
공통 재고 처리 로직은 `default` 메서드로 분리해 중복을 줄였다.

회원 관리2에서는 `Member`를 추상 클래스로 만들고, `NormalMember`, `VipMember`가 이를 상속하도록 구현했다.

회원 관리3에서는 `Member`를 인터페이스로 바꾸고, 각 구현 클래스가 필드 초기화와 등급·혜택 반환 기능을 직접 구현하도록 수정했다.

## 헷갈렸던 점

추상 클래스와 인터페이스를 각각 언제 사용해야 하는지가 헷갈렸다.

추상 클래스는 공통 필드, 생성자, 공통 메서드를 가질 수 있기 때문에   
여러 자식 클래스가 공유하는 상태와 기본 동작을 부모 클래스에서 관리할 때 적합했다.  
예를 들어 자판기2의 `Drink`처럼 `name`, `price`, `stock` 같은 공통 상태가 있고,   
이를 생성자로 초기화해야 한다면 추상 클래스를 사용하는 것이 자연스러웠다.

반면 인터페이스는 인스턴스 필드와 생성자를 가질 수 없기 때문에 객체의 상태는 각 구현 클래스가 직접 관리해야 했다.  
대신 “이 클래스는 어떤 기능을 반드시 가져야 한다”는 규칙을 정하는 데 적합했고,   
서로 다른 클래스들을 같은 타입으로 묶어 다형성으로 다룰 수 있었다.

인터페이스에서도 `default` 메서드를 사용하면 모든 구현 클래스에서 공통으로 사용하는 동작을 어느 정도 줄일 수 있었다.  
다만 `default` 메서드가 있어도 인스턴스 필드를 직접 가질 수는 없기 때문에,   
상태를 기반으로 한 로직은 결국 getter 같은 메서드를 통해 처리해야 한다는 점을 확인했다.

정리하면, 공통 상태와 기본 구현을 부모가 관리해야 하면 추상 클래스가 더 적합하고,   
여러 클래스가 지켜야 할 기능 규칙을 정하고 다형성으로 묶고 싶을 때는 인터페이스가 더 적합하다고 느꼈다.

또한 `switch-case`는 자동으로 별도 스코프를 만들지 않기 때문에 여러 case에서 같은 이름의 변수를 선언하면 충돌할 수 있었다.  
각 case를 `{}`로 감싸 변수 범위를 제한하는 방식으로 해결했다.

## 오늘 느낀 점

추상 클래스와 인터페이스는 둘 다 구현을 강제할 수 있지만, 추상 클래스는 공통 상태와 로직을 가진 부모 구조를 만들 때 사용하고,   
인터페이스는 기능의 규칙을 정할 때 사용한다는 차이를 확인했다.  
과제에서 같은 자판기와 회원 관리 구조를 추상 클래스와 인터페이스로 각각 구현해보니 차이가 조금 더 명확해졌다.
