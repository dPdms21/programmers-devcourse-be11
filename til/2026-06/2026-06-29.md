## 오늘 배운 내용

오늘은 JDBC 공통 실행 흐름을 별도의 컨텍스트로 분리하고, 예외 처리 원칙과 서비스 계층의 역할을 학습했다.

`UserDAO`가 직접 처리하던 연결 생성, `PreparedStatement` 실행, 자원 반환 로직을 `JdbcContext`로 분리했다.   
`UserDAO`는 실행할 SQL 전략을 결정하고, `JdbcContext`는 실제 JDBC 실행 순서를 담당하도록 역할을 나눴다.

예외는 단순히 `catch`하는 것으로 끝내지 않고 상황에 따라 복구, 회피, 전환해야 한다.

* 복구 → 재시도나 대체값을 통해 정상 흐름으로 복귀
* 회피 → `throws`나 재던지기를 통해 상위 호출자에게 처리 책임 전달
* 전환 → 저수준 예외를 애플리케이션 의미가 드러나는 예외로 변경

또한 DAO는 데이터 조회와 저장을 담당하고, 서비스 계층은 등급 변경과 같은 비즈니스 로직을 담당하도록 분리했다.   
사용자 등급은 `enum Level`로 관리해 문자열이나 숫자보다 의미를 명확하게 표현했다.

## 실습 및 과제

> JdbcContext와 JDBC 공통 로직 분리

`UserDAO` 내부에 반복되던 연결 생성, SQL 실행, 자원 반환 흐름을 `JdbcContext`로 이동했다.

`UserDAO`는 SQL을 생성하는 `StatementStrategy`를 전달하고,   
`JdbcContext`는 연결 열기 → 전략 실행 → 자원 반환 순서를 담당하도록 구성했다.

DAO가 구체적인 JDBC 실행 절차를 직접 처리하지 않게 되면서 책임이 줄었고, 공통 실행 흐름을 다른 DAO에서도 재사용할 수 있는 구조가 됐다.

> 예외 처리 원칙

예외를 잡은 뒤 아무 처리도 하지 않거나 로그만 출력하고 종료하면 호출자가 작업 실패를 알 수 없는 예외 블랙홀이 발생한다.

현재 위치에서 정상 상태로 되돌릴 수 있으면 복구하고, 직접 처리할 수 없으면 상위 계층으로 회피해야 한다.   
기술적 예외의 의미가 불분명한 경우에는 애플리케이션에서 이해할 수 있는 예외로 전환해야 한다.

`checked exception`은 컴파일러가 처리 또는 선언을 강제하고, `unchecked exception`은 컴파일러가 처리를 강제하지 않는다는 차이도 확인했다.

> 서비스 계층과 비즈니스 로직 분리

서비스 계층에서는 로그인 횟수와 추천 횟수를 기준으로 사용자 등급을 판단하고 변경했다.

DAO는 사용자 조회와 저장을 담당하고, `UserService`는 등급 변경 조건과 같은 비즈니스 규칙을 담당하도록 역할을 분리했다.   
사용자 등급은 `enum Level`로 관리해 문자열이나 숫자로 직접 관리하는 것보다 의미를 명확하고 안전하게 표현했다.

> 예외 처리 과제

예외 복구에서는 작업이 실패하면 정해진 횟수만큼 다시 시도하고, 성공하면 즉시 결과를 반환하도록 구현했다.   
모든 시도가 실패하면 마지막 `SQLException`을 원인으로 포함한 예외를 발생시켜 실패 사실과 실제 원인을 확인할 수 있도록 했다.

재시도 사이에는 시도 횟수에 비례한 백오프를 적용했으며, 마지막 시도 뒤에는 더 이상 재시도하지 않으므로 대기하지 않도록 처리했다.

예외 전환에서는 `"Duplicate entry"`와 같은 오류 메시지는 `getMessage()`로,   
`"23000"`과 같은 SQL 상태 코드는 `getSQLState()`로 확인했다.   
새로운 예외에는 `super(message, cause)`를 사용해 기존 예외를 원인으로 보존했다.

도전 과제로 `FileWriter(file, true)`를 사용해 기존 로그에 내용을 이어서 기록하고, `try-with-resources`로 자원이 자동 반환되도록 했다.   
최소 로그 레벨을 적용해 `WARN` 이상만 기록했으며, 날짜별로 `app-YYYY-MM-DD.log` 파일이 생성되도록 구현했다.

문자열 유틸리티에서는 다음 기능을 구현했다.

* `normalizeSpaces()` → 앞뒤 공백 제거와 연속 공백 정규화
* `reverse()` → `StringBuilder.reverse()`를 이용한 문자열 뒤집기
* `isPalindrome()` → 대소문자와 공백을 무시한 회문 판별
* `countWords()` → 연속 공백 기준 단어 개수 계산

공백 정규화에는 `trim()`과 `replaceAll("\\s+", " ")`를 사용했다.   
회문 판별에서는 중간 공백까지 제거해야 하므로 `replaceAll("\\s+", "")`를 적용했다.

모든 메서드의 `null` 입력은 요구사항에 따라 `IllegalArgumentException`을 던지도록 수정했다.

Docker public test 9개와 hidden test 26개를 모두 통과했고, PR Checks에서 PASS를 확인한 뒤 병합했다.

## 헷갈렸던 점

예외 복구와 단순한 예외 무시의 차이를 정리했다.   
`catch` 후 아무 처리도 하지 않는 것은 복구가 아니라 예외를 숨기는 것이다.   
복구라면 재시도, 대체값 반환, 대체 동작 수행과 같이 정상 흐름으로 돌아가기 위한 처리가 있어야 한다.

`SQLException`의 메시지와 SQLState도 구분해야 했다.   
오류 설명은 `getMessage()`, 데이터베이스 상태 코드는 `getSQLState()`로 확인한다.

PBL 환경에서는 Docker Desktop이 설치되어 있어도 Docker Engine이 실행되지 않으면 `docker info`의 Server 항목에서 연결 오류가 발생했다.   
Docker Desktop을 실행한 뒤 서버 정보가 정상적으로 출력되는지 확인해야 했다.

정규표현식의 `\s+`는 하나 이상의 연속된 공백 문자를 의미하지만, Java 문자열에서는 역슬래시를 이스케이프해야 하므로 `"\\s+"`로 작성해야 했다.
